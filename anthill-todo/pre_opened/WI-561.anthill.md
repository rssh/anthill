## Description

Collection deconstruction syntax (first-class, type-directed patterns). DESIGN (settled in WI-560 discussion): a collection PATTERN [], [h | t], [a, b], [a, b | t] should destructure ANY collection by desugaring (type-directed) to the abstract Iteration API -- the dual of construction. The API ALREADY EXISTS: anthill.prelude.Iteration.split(i) -> Option[(Element, Iterator)] effects Effect (prelude/iteration.anthill), provided by List purely (split(xs:List)->Option[(xs.T,List)]); construction dual = PersistentCollection.empty/insert (prelude/collection.anthill). Pattern semantics: [] == split(c)=none; [h|t] == split(c)=some((h,t)); [a,b] == split(c)=some((a,c1)),split(c1)=some((b,c2)),split(c2)=none. So NO new collection vocabulary is needed -- the gap is entirely in the PATTERN MACHINERY. KEY BOUNDARIES (load-bearing): (1) Two roles by POSITION, opposite operations: a collection literal in EXPRESSION/value position is CONSTRUCTION -> Collection.insert/empty (List: cons/nil); a collection literal in PATTERN position is DESTRUCTURING -> Iteration.split. split is a destructor and NEVER appears in list-literal/expression position. (2) Logical vs operational: rule-head destructuring is matched by UNIFICATION, which can only take apart concrete inductive structure (cons/nil) -> rule-head collection patterns are intrinsically List-only (desugar to cons; abstract carriers cannot be unified because unification cannot RUN split). Operational destructuring (match case / op body) CAN run split -> works for any Iteration/Stream carrier, but is EFFECTFUL (split's effect row: {} for List, s.E for Stream) -- so matching a Stream pattern is an effectful guard the typer must attribute. (3) For LIST, split is never needed at all: cons/nil serves both construction and (unification) destructuring. split is purely an abstract-collection, match-position, operational feature. (4) Set has NO Iteration -> head-tail over Set is a correct type error (Set only has membership/union). CURRENT STATE (why this is greenfield): patterns today are PURELY STRUCTURAL (Pattern enum = Var/Wildcard/Literal/Constructor/Tuple in node_occurrence.rs; eval/pattern.rs matches constructor symbol + recurses, NEVER calls an operation). [h|t] is NOT in the _pattern grammar (was expression-only and is now removed entirely, WI-560). match cases destructure lists via explicit case cons(h,t) -> (see stdlib/cli/parse.anthill, help.anthill). So there is NO view/extractor/active-pattern mechanism and NO syntactic entry point for split-based destructuring. STAGING: occurrence-build happens at LOAD (materialize_from_handle), BEFORE the typer (type_check_sorts, load.rs ~3041). The loader does a List-ONLY construction desugar (convert_term_with_expected/find_list_element_type/build_list). The typer types ListLit as List[T] but does NOT desugar. The principled home for the type-directed pattern desugar is the TYPER (only stage with the expected type for abstract carriers; already tree-producing for ListLit via reassemble_group). IMPLEMENTATION SKETCH (when prioritized): (a) add collection patterns to the _pattern grammar ([], [h|t], [a,b], [a,b|t]); (b) add Pattern::Collection{elements, tail} OR a general Pattern::View{extractor, args} (Scala unapply-style) to the Pattern enum + parse IR + loaders + pattern_to_term; (c) typer/pattern-compiler desugars type-directed: List -> cons/nil structural pattern (no split); abstract Iteration/Stream -> run split, match the Option[(E,Rest)] structurally (view pattern), attributing split's effect row; (d) rule-head collection patterns stay List/cons-only (unification limit); (e) law: split(insert(h,t))=some((h,t)), split(empty())=none as a provider obligation. SCOPE DECISION when picked up: MVP could be List-only structural ([h|t] -> cons pattern in match + rule head, no split, no effects); full version adds the view-pattern mechanism + effectful matching for abstract carriers. Likely warrants its own proposal (it is a language feature with the logical/operational + effect boundaries above).
