## Description

A GENERATED C++ ENTITY STRUCT HAS NO COMPARISON OPERATOR, so a composite anthill certifies as lawfully Eq is uncomparable in C++ — library/004 build step 4 shipped only its PARTIAL half, and the proposal's Status line claims otherwise.

MEASURED (driven, at 5424e7be, freshly built CLI):

  namespace probe.cppeq
    entity Pt(x: Int64, y: Int64)          -- all fields lawfully Eq
  end
  $ anthill codegen cpp -n probe.cppeq ...
  struct Pt {
      int64_t x;
      int64_t y;
  };

No operator==, no <=>, no `= default`. Meanwhile WI-664 DERIVES `provides PartialEq[Pt]` + `provides Eq[Pt]` for exactly this shape, and WI-835 accepts `Map[K = Pt]` at every written instantiation — so the loader certifies a lawful key whose emitted C++ type cannot be compared, cannot key a std::map, and cannot key a std::unordered_map. The anthill side guarantees a property the emitted C++ does not carry.

WHAT SHIPPED vs WHAT DID NOT. library/004 §"Build order" step 4 reads: "`Eq`/`Ord`/`TotalFloat` emit a total `operator==`/`<=>` (and the `= default` for entity structs); `PartialEq`/`PartialOrd` keep `==`/`<`." The SECOND clause shipped — render_as_operator (rustland/anthill-cpp-gen/src/lib.rs:4279-4297) maps PartialEq.eq/neq -> ==/!= and PartialOrd.gt/lt/gte/lte -> > < >= <=, which is what makes interpreter and codegen agree on IEEE Float (the WI-645 acceptance). The FIRST clause did not: the deferral is a code comment at lib.rs:4288-4290 — "The total Eq/Ord/TotalFloat would emit a total comparator instead (a `= default` operator== / <=> on the generated struct) — a follow-up, tracked with the entity operator== gap." It was tracked NOWHERE: `grep operator== anthill-todo/workitems.anthill` returns two hits, both inside WI-644's own description. TEMPLATE_ENTITY_STRUCT (lib.rs:70-73) emits fields and closes the brace.

TWO DOC CLAIMS TO REPAIR (the first is fixed inline with this ticket's filing; the second is this ticket's own):
 - docs/proposals/library/004: "Status: Implemented (all five §Build order steps)" overstates — step 4 is half. Corrected when this was filed.
 - WI-644's ACCEPTANCE does not name the total comparator (only "interpreter Float eq/neq/ordered ... AGREE with the C++ codegen", which the partial half satisfies), so WI-644 closes correctly without this. This is a library/004 build-step remainder, not a WI-644 acceptance failure.

WHY PREOPENED, NOT OPEN — the emitter cannot ask the question yet. `grep -n "sort_provides|SortProvidesInfo" anthill-cpp-gen/src/lib.rs` returns ZERO hits: cpp-gen has no read of a carrier's provisions at all, so "which struct gets which comparator" needs a lawfulness channel that does not exist. Decide before claiming:
 (a) `= default` operator== for an entity WI-664 classifies Eq (all fields lawful);
 (b) for one classified NonEq (any Float field), emit NOTHING or an explicitly `= delete`d operator== — a silently defaulted one would compare doubles by IEEE `==` and reintroduce precisely the interpreter-vs-codegen divergence WI-645 exists to close, so this arm is a soundness decision, not an ergonomics one;
 (c) the `<=>` half needs Ord, not Eq — and TotalFloat is a lawful Eq key but is NOT Ord (library/004 §Open questions 1; totalfloat.anthill says so at its declaration), so the ordering half may have no lawful source until that question resolves. Splitting `operator==` (do now) from `<=>` (blocked) is a live option;
 (d) TotalFloat wraps a Float — decide whether it needs its own host mapping giving a total ==, or whether the newtype's generated struct inherits the (b) problem;
 (e) the RUST backend: codegen/rust.rs emits `#[derive(...)]` from a CONFIGURED list (rust.rs:470-474), not from a carrier's provisions, so it plausibly has the same hole in the other direction (deriving PartialEq for a NonEq composite). CHECK, do not assume — this ticket does not claim it.

ACCEPTANCE:
 - An entity whose fields are all lawfully Eq emits a C++ struct carrying a total operator==, pinned by a test that goes RED when the operator is dropped (state the control at the test site).
 - An entity classified NonEq (a Float field) does NOT silently receive a defaulted operator== over doubles; whichever of "omit" or "= delete" is chosen is pinned by its own test.
 - The <=> / Ord half is either delivered or explicitly deferred IN WRITING with its blocker named (library/004 §Open questions 1).
 - library/004's Build order step 4 and its Status line agree with the code.
 - cargo-test green.
