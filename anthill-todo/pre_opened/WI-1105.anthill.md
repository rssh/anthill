## description

C++ CODEGEN LOSES EVERY NON-MONADIC EFFECT FROM THE EMITTED SIGNATURE — the EffectMapping fact that says what to emit is resolved and then DISCARDED for every receiver except ResultWrap.

MEASURED (read, at b4874dce):

(1) OPERATION LEVEL. rustland/anthill-cpp-gen/src/lib.rs:2220-2251 walks the op's effect row, resolves each label through cpp_effect_receiver (which queries the realizes_effect rule set), and uses the answer for EXACTLY ONE thing: `wraps_result |= receiver == "ResultWrap"`. Error realizes as ResultWrap, so Error survives as `tl::expected<R, std::string>` — the MONADIC case, and the only one that reaches the signature. stdlib/anthill/realization/cpp_std.anthill:61 declares `EffectMapping(effect: "Modify", receiver: MutRef, lang: some("cpp"))`, and MutRef is NEVER APPLIED: grep MutRef over anthill-cpp-gen/src/lib.rs returns one hit, a doc comment at :5445 about DECODING the receiver form. So `operation reset(self: Sensor) -> Unit effects Modify[self]` emits the same C++ parameter as a pure operation — no `&`, no context parameter. The effect is checked, then forgotten.

(2) ARROW / CALLBACK LEVEL. lower_arrow_type (lib.rs:4805-4842) builds `std::function<R(Args...)>` from the arrow's param and result only; the effect child is never read. A callback declared `(x: S) -> Dst @ {EffP}` lowers identically to a pure one.

(3) WHY IT HAS NOT BITTEN YET. anthill-cpp-gen/tests/conversion_test.rs:33-70 is the Modify[self] fixture and it passes because that carrier binds to a POINTER host type (`::vendor::Sensor *`), which carries mutability independently of the effect. A carrier bound to a VALUE host type silently emits a by-value parameter for a mutating operation: the caller's object is not modified and nothing in the pipeline says so. That is the failure this ticket is about — a silent wrong emission, not a refusal.

RELATED, DIFFERENT, ALREADY LOUD — do not conflate: a DENOTED-bearing arrow row (`-Modify[x]`, `Modify[c]`) is REFUSED rather than dropped, by lower_type_value (lib.rs:4844-4858) and by the op param/return check (:2174-2186), both erroring 'denoted-bearing type ... unsupported by C++ codegen'. Since WI-441 every stdlib HOF signature carries `-Modify[x]` (iterable.anthill:41/61/67, finite_collection.anthill:68/72, combinators.anthill:66/125, stream.anthill:88), so Iterable.map/find/filter are unemittable to C++ as written. That refusal is the CORRECT direction and is not what this ticket asks to change; it is recorded because any work on (2) meets it first.

SCOPE / SHAPE OF A FIX: apply the resolved ReceiverForm at the emission site instead of testing it for one value. For cpp, MutRef -> `T&` on the parameter the Modify label NAMES — the label is region-keyed (`Modify[self]`, not a bare `Modify`), so the target parameter is known. ReceiverForm's other variants (ByValue, ContextCapability, CanThrow, CapabilityCapture) are declared by the scala profiles (scala_std.anthill:44-46, scala_caps.anthill:29-32), so the seam should be per-form and profile-driven, not a second hardcoded string test.

OPEN QUESTIONS FOR WHOEVER TAKES IT: (a) does a Modify on a NON-parameter place (Modify[result], a WI-353 re-keyed callback label) have any C++ signature meaning, or is MutRef defined only for a parameter target; (b) can an arrow-level row be represented in C++ at all without a capability/context argument, or do callbacks stay effect-erased with a loud refusal for any non-empty ground row; (c) rust-gen looks to have the same hole — codegen/rust.rs has no MutRef hit either and analyze_effects ignores arrows (rust.rs:1815) — decide whether that is this ticket or a sibling.

CONTEXT: surfaced while delivering WI-266 (the 027.1 HOF-discharge doc reconciliation) and recorded in that proposal's resolved-question entry as 'codegen does not carry the sharpened rows'.

ACCEPTANCE: an operation declaring `effects Modify[p]` emits the C++ parameter form its profile's EffectMapping declares (MutRef -> `T&`) for a value-typed carrier, driven by a test that FAILS when the resolved receiver is discarded (the control: back the change out and the test must go red); the existing pointer-carrier fixture in conversion_test.rs keeps passing; cargo-test green.
