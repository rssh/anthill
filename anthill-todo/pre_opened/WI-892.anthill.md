## Description

ALLOW `if`/`then`/`else` IN A RULE BODY — the grammar gate is the ONLY reason `anthill.prelude.Bool.ite` exists, and WI-887 settles `ite` as a `[simp]`-rule-only functor rather than removing the need for it. THE GATE, exactly: `if_expr` is a member of `_expr_body` (tree-sitter-anthill/grammar.js:1354, under the "Expressions (operation bodies)" heading) while `_goal` is `choice($.cut, $.let_binding, $._term)` (:459) and `rule_body` is `commaSep1($._goal)` (:451) — so a rule body reaches `_term` and never `if_expr`. THE EVIDENCE THAT THIS IS THE WHOLE REASON: `rustland/anthill-smt-gen/tests/wi680_ite_lowering_test.rs`:10 states it in its own words — "a rule-body twin must spell it `ite(...)`" — and its demonstrator rule is `clamp(?x, ?r) :- ?r = ite(gte(?x, 0), ?x, 0)`, which is `if gte(?x,0) then ?x else 0` with no conditional surface to write it in. WI-680's ticket says the same ("if/then/else does NOT parse in rule-body position (only operation bodies), so the hand-written demonstrator uses the ite(...) functor form"). The three stdlib laws that spell `ite` — `ordered.anthill`:108-109 (`max`/`min`) and `int64.anthill`:73 (`sign`) — are the same case. WHAT IT WOULD BUY. (1) One conditional surface instead of two. Today the SAME conditional is written `if` in an operation body and `ite` in a rule body, and the two lower differently — smt-gen has a path for the `Expr::If` occurrence (lib.rs:1152) AND a separate one for the `Bool.ite` functor (:1182, `is_ite_op`, which also matches the BARE short name "ite" and so can reinterpret an unresolved same-named user op — WI-680's own review recorded that hazard). Allowing `if` in a rule body would let the functor path be retired and the bare-name match with it. (2) It removes the LAZINESS question that WI-887 had to settle. `Expr::If` is lazy by construction; `ite` as an operation could not be (an operation's arguments are evaluated before the call), which is exactly why WI-887 took it OUT of the operation block. With `if` available in a rule body, an author who wants a conditional writes the lazy one everywhere. (3) The refold in `kb/body_specialize.rs` (WI-669) already produces `Expr::If`; a rule-body `if` would be the same shape the synth seam emits, so one representation serves the hand-written and the derived rule alike. WHAT TO WATCH. (a) GRAMMAR AMBIGUITY: `_goal` is comma-separated, and `if_expr`'s branches are `_expr_body` which is not comma-delimited — an `else` arm followed by `, next_goal` needs a precedence decision, and tree-sitter is GLR so a wrong one shows up as a conflict rather than an error. `if_expr` is already `prec.right`. (b) `occurrence_to_term` ASSERTS/⊥s on `If` (recorded in docs/design/abstract-interpreter-and-rules.md §3.4.1: control flow "cannot be represented" in a `TermId`, called "an intrinsic fact of goal position"). So an `If` reaching a hash-consed-term boundary must be refused LOUDLY at that boundary, and the consumers that convert a rule body to terms have to be enumerated before this lands — this is the substantive risk, not the grammar. (c) SLD: a rule-body `if` still has to mean something during resolution, or be refused there. WI-887's probe measured that a rule-body `ite` reduces at SLD only via the `apply_eq_rules` path, only under `ResolveConfig.simplify = true` (NOT the default), and only where the condition is already a literal — so "what a conditional means in a goal" is an open question this ticket inherits rather than creates. ACCEPTANCE: `rule f(?x, ?r) :- ?r = if gte(?x, 0) then ?x else 0` parses, loads and lowers to SMT-LIB `(ite ...)` through the EXISTING `Expr::If` path; the tree-sitter corpus covers a rule-body `if` followed by a further comma-separated goal; every rule-body→`TermId` boundary either handles `If` or refuses it loudly (enumerated, not assumed); `ordered.anthill`/`int64.anthill`/`bool.anthill` and `wi680_ite_lowering_test` are considered for restatement in the `if` surface, and whether `Bool.ite` (and `is_ite_op`, and its bare-name match) can then be RETIRED is answered explicitly; full workspace green via rustland/scripts/test.sh. REFERENCE: WI-887 (`ite` is `[simp]`-rule-only; its feedback carries the SLD probe), WI-680 (the functor lowering and the "must spell it ite" note), WI-669 (the `Expr::If` refold and the `occurrence_to_term` limitation).

## Changes

### 2026-07-31T08:12:49Z — feedback — user

THE `occurrence_to_term` BOUNDARY IS THE SUBSTANTIVE WORK, and it will NOT have been eliminated by then (user). Two things pin it. (1) THE CONVERSION STAYS BY DESIGN: WI-348's goal is that logic/matching/identity never reify, NOT that the conversion is deleted — it is kept at genuine term boundaries (hash-consing, codegen, persistence, TermId-keyed indexes). So this ticket cannot wait for it to go away. (2) `Term` HAS NO CONTROL-FLOW VARIANT AT ALL: the enum is `Const | Var | Fn | Ref | Bottom | Ident | ParseAux` (kb/term.rs:213-239). An `If` is not merely unhandled, it is UNREPRESENTABLE, so "extend `occurrence_to_term`" means either adding a control-flow representation to `Term` (with everything that implies for hash-consing and the discrimination tree) or keeping the boundary TOTAL AND LOUD.
THE INVARIANT THIS TICKET FALSIFIES IS STATED IN THE FUNCTION'S OWN DOC, twice, and both statements become false the moment `if` parses in a goal: "Recursion is bounded by the goal-atom structure (predicate applications over leaves); CONTROL-FLOW FORMS CAN'T APPEAR AT A GOAL POSITION and fall to ⊥" and, on the `None` arm, "A child-bearing control-flow / post-elaboration form CAN'T OCCUR AT A GOAL POSITION" (kb/node_occurrence.rs:2466-2489).
AND THE GUARD IS A `debug_assert!`. In a RELEASE build the `None` arm falls through to `kb.alloc(Term::Bottom)` — a rule-body `if` would SILENTLY REIFY TO ⊥ rather than fail, which is precisely the silent-skip this repo's principles forbid, and it would be invisible to a debug-mode test suite. Whatever else this ticket does, that arm must become a real error before `if` can reach it.
THE TWO NAMED CONSUMERS, from the same doc comment: the resolver's dedup `seen_goals` key and `Solution.residual`. Both are goal-position boundaries, so both are reached by exactly the shape this ticket introduces. `try_occurrence_to_term` (the total variant, WI-297) already returns `None` for `If`/`Let`/`Match`/`Lambda`/`HoApply` and is the right shape to build on. There are ~76 `occurrence_to_term` references in anthill-core and a prior audit of ~20 real call sites exists — enumerate against it rather than from scratch, and note its lesson: reading a site is NOT enough to classify it, RUN the live tests (a "removable" verdict on the lambda-annotation sites was wrong because the conversion there INTERPRETS rather than round-trips).
