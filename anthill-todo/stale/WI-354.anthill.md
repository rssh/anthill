## Description

Proposal: relations/rules inside an operation declaration (option B of docs/design/modify-effect-derive.md §'Where flow facts live'). Today operation_clause is only requires/ensures/effects + optional = body + meta_block — there is NO fact/rule form inside an operation, so per-op relational annotations (e.g. the Modify-effect flow facts for opaque FFI ops with no body and no defining laws) must be written top-level with fully-qualified names (foldLeft.f.a ...), which is too verbose to use. Propose a small grammar addition: an in-operation block reusing the rule_body term grammar so edges are written with BARE params in scope (e.g. flow direct(z, f.a), element_of(xs, f.t)), co-located with the op and closer to the stdlib op-plus-sibling-laws idiom; lowers to the same top-level facts the loader derives. Must NOT overload ensures (runtime postcondition, different semantics). Alternative considered: option A, a flow-specific compact table (narrower, bespoke). SCOPE: write the proposal (grammar form, scoping rules with op.param projection in scope, lowering). ERGONOMICS-ONLY and DEFERRED — native ops + law-specified ops cover the stdlib without it (see WI-352). Depends on op.param projection.

## Reason

Obsolete. The only consumer of flow facts is region::op_boundary_effects, called solely while an operation BODY is typed (kb/typing/op_bodies.rs); a bodyless operation never reaches it and its declared effects row is trusted as written. So in-operation flow edges on an opaque FFI op — this ticket's whole motivation — would have no reader; such an op already states the analysis result directly (effects Modify[l]), shorter than the edges. Every op that needs flow facts has a body and gets them from flow_derive::run (WI-352); the stdlib's bodyless higher-order ops are spec ops whose providers have bodies (monad flatMap/map, delay), pure-callback ops (relation where/join), or reify. No flow(...) fact is hand-written anywhere outside reflect/feed.anthill. The law-derivation half of WI-352 never landed (flow_derive reads bodies only), and since WI-881/884 a bodyless op's defining equation is a top-level @[simp] rule with ?x variables, not qualified op.param paths, so the verbosity complaint does not apply. To revive: a CALL-SITE consumer that re-keys a callback's Modify through a bodyless op's flow facts would have to exist first.
