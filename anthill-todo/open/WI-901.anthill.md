## Description

WI-757 follow-up (proposal 043.1 §7): an anthill-written macro's rejection has no SPAN. WI-757 (and its follow-on) gave a macro two negative outcomes -- DECLINE (keep the template) and REJECT (a load error carrying the macro's own words) -- and an anthill-written macro reaches the reject channel by RAISING: 'operation m(x: NodeOccurrence) -> NodeOccurrence effects Error[E] = Error.raise(payload)', with the payload rendered by eval::render_raised_payload. That works (wi757_macro_diagnostic_test::an_anthill_macro_rejects_by_raising) because WI-702/054's effectful-rewrite gate now EXEMPTS a macro at the [simp] RHS head -- the macro is the rewriter, evaluated away at compile time, so its call never reaches runtime and cannot be duplicated/reordered/dropped there. What is still missing is PRECISION: 'raise' carries a payload and no occurrence, so a raised rejection is located at the REDEX, while a HOST macro (EvalError::MacroRejected) additionally names the offending sub-expression -- 'where(lambda c -> Person.alwaysTrue())' points at the condition, not at the whole call. The shape that closes it is an effect-free reflect op, e.g. 'operation reject(message: String, at: NodeOccurrence) -> Nothing', whose eval builtin returns EvalError::MacroRejected{detail, span: Some(at.span)}. NO CLIENT TODAY: both macros in the tree (Relation.guarded_of / conjoin_of) are host builtins that already use the precise channel, so this is unbuilt on purpose. Build it when the first anthill-written macro needs to point at a sub-expression. ACCEPTANCE: an anthill-written macro can locate its rejection at an occurrence it names, asserted by span (not just by message); raising without a span keeps working and stays at the redex; the decline path stays unchanged; cargo-test green via scripts/test.sh.
