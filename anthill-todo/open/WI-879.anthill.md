## description

MAKE THE SLD BUILTIN REGISTRY FACT-DRIVEN TOO, and stop `builtin_cmp` failing SILENTLY on operands it cannot compare. The half of WI-876 that could not move. WHAT MOVED: the EVALUATOR's registry now reads `anthill.realization.OperationMapping` facts (`register_operation_mappings`, eval/builtins.rs), so a host implementation is keyed to the CARRIER that declared it. WHAT DID NOT: `KnowledgeBase::register_standard_builtins` (kb/mod.rs) is still a hardcoded `(qualified name -> BuiltinTag)` list, because it runs BEFORE `load_all` — there are no facts to read yet. WI-876 did the one thing it could without a new pass: the four comparison tags are no longer SPEC-OP-KEYED — a loop registers `{Int64,BigInt,String,Float}.{gt,lt,gte,lte}` beside `PartialOrd.*`, because those carriers now declare their own comparison members and a bare `gt(?a, 0)` in a rule inside `sort Int64` resolves to `Int64.gt`, which would otherwise have lost the resolver builtin it always had. WORK: a post-load pass that registers resolver tags from the same `operation_mappings` reader the evaluator uses (one owner for the fact shape already exists — `load::operation_mappings`), so the hardcoded loop and its carrier list go away and a NEW carrier's binding block gets the resolver behaviour without a Rust edit. Needs a decision on WHERE it runs (`resolve_builtins` already re-resolves the pre-load registrations after `scan_definitions`, which is the natural neighbour) and on what a mapping means for the RESOLVER, which has `BuiltinTag`s, not host functions — probably a second, resolver-side key column rather than reusing `host_fn`. SECOND, SEPARABLE DEFECT in the same function, and it violates the repo's no-silent-skip rule: `builtin_cmp` (kb/resolve.rs) reads NUMERIC operands only (`value_num`: Int/Big/Float) and returns `BuiltinResult::Failure` on anything else. So an SLD goal `lt("a", "b")` does not compare strings and does not complain — it FAILS, indistinguishably from "a >= b". That is pre-existing and unchanged by WI-876 (it was equally true when the goal resolved to `PartialOrd.lt`), but registering `String.lt` makes the claim more visible: the tag says the resolver can compare strings and it cannot. Either teach `builtin_cmp` the carrier's comparison (the eval side already has `value_compare`, which handles `Str` and `Bool`) or make a non-comparable operand pair a LOUD error rather than a silent failure. ACCEPTANCE: the resolver's comparison tags come from the binding blocks, not a Rust list — adding `operation_map { lt: ... }` to a new carrier's binding is enough; the hardcoded carrier loop in `register_standard_builtins` is DELETED; an SLD `lt("a", "b")` either answers correctly or raises, never silently fails; `wi876_operation_mapping_test` and the WI-863 operator-desugaring tests stay green; full workspace green via rustland/scripts/test.sh. REFERENCE: docs/design/058-implementation.md §10; kb/mod.rs `register_standard_builtins`; kb/resolve.rs `builtin_cmp`; eval/builtins.rs `register_operation_mappings`.
