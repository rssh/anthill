## description

Proposal 052 OQ5 REVISION: split the relation SCHEMA from the ROW TYPE, so a one-column relation stops being ambiguous. Filed out of WI-1128 (delivered 2026-08-18), whose delivery left this open with a reason and no owner.

THE DEFECT THAT MAKES THIS URGENT, and it is a SILENT WRONG ANSWER rather than a refusal. `collapse_schema` (rustland/anthill-core/src/kb/typing.rs) erases the relation's ARITY: the 1-arm returns the sole column's TYPE, the 0-arm returns `Unit`. So a schema type that IS a named tuple reads equally as "n columns" and as "ONE column whose type is that n-field tuple". MEASURED on the current tree: over `entity pair_holder(p: (a: Int64, b: String))`, `rule pairs(?p)` has ONE column, and `person_row.join(pairs, ...)` TYPE-CHECKS against a declared four-column `(name, age, a, b)` while the row `join_run` materializes is `(name, age, p)` — three columns, `a`/`b` promised and never delivered, `p` delivered and never promised. Pinned as a recorded limit by `wi1128_a_tuple_typed_column_is_indistinguishable_from_two_columns`.

`Concat` IS THE ONLY MEMBER OF THE FAMILY WITH NO BACKSTOP, structurally rather than by omission. `fix`, `project` and `negate` each ask the VALUE a question it can answer — "is there a column of this name?" — and refuse loudly at runtime (measured: "fix: restricts column `a`, which is not in the relation's schema"; "project_run: the projection selects column `a`, which is not in the relation's schema"). MERGING IS NAME-FREE, so `join` has no such question and nothing to detect: `join_run` merging a 2-column relation with a 1-column one is CORRECT, and only the type is not. No type check can exist either — the two schemas are the SAME TYPE. So this cannot be fixed anywhere except in the representation.

THE DESIGN: `T` currently answers TWO questions — "what is a row's type" (where the collapse is the ergonomic win: `colouring.takeN(20) : List[Board]`) and "what are the columns" (where it is a loss). Split them. TWO WAYS TO DO IT, AND OPTION A IS RECOMMENDED (user, 2026-08-18, on reading the first version of this ticket: "why we need Collapse[T]? Why we don't want just work with one-element tuple?").

OPTION A — DROP THE COLLAPSE. The schema IS the row type, always the full named tuple: `Relation[(age: Int64)]`, `queens.head : (board: Board)`, read as `row.board`. NO NEW CONSTRUCTOR, and simpler than the code we have TODAY rather than merely simpler than option B. `Membership` becomes exact for free — a 0-column relation stays `Unit` while a one-`Unit`-column one is `(u: Unit)` — so WI-728's recorded limit retires without depending on the `()`-vs-`Unit` typing gap (measured: `()` in an entity field is refused, "expected Unit, got TupleLiteral"). `Concat` / `Without` / `Project` just work at arity one, and WI-1128's refusal messages become dead code rather than better prose.

OPTION B — KEEP THE COLLAPSED ROW TYPE behind a new `Collapse[T]` constructor in the family (`Concat` / `Without` / `Project` / `Membership`), reduced at the SAME return-type normalization boundary. This was the first version of this ticket. What it buys is EXACTLY 052's one stated rationale for the collapse — "a relation with only `board` free is `Relation[Board]`, so `queens.head : Board`" — and nothing else. It also carries the risk that most likely kills it: whether a ctor reduces across the `provides LogicalStream[T = T, E = E]` edge with the sort's own abstract `T` as operand (WI-734 says an abstract operand leaves it symbolic). Option A deletes that risk instead of measuring it. Keep B only if the census below turns out to have missed a reader that needs `.head : Board`.

THE CENSUS THAT DECIDES BETWEEN THEM, measured on shipped sources (examples/, stdlib/, rustland/*/anthill/): 46 rules have exactly one head variable, and NONE is consumed as a relation VALUE — every one is a goal in a rule body, where the schema type never arises. The only 1-column drain anywhere is `examples/classic-mini/ancestor`, reached by APPLICATION (`ancestor("bart")` binds the first column and narrows to the second), and it does `length(ofBart.takeN(100))` — it never touches an element. So the number of call sites that would have to change from `x` to `x.col` under option A is currently ZERO. And that application case is an argument FOR A: `ancestor("bart")` is exactly where a column name is destroyed today, and under A the narrowed relation keeps `(is: String)`.

WI-1131 REMOVED THE OLD OBJECTION to A: a one-field named tuple was a syntax error as a VALUE until 2026-08-18, so "just use a one-element tuple" was not fully writable when 052 chose the collapse.

WHAT IT COSTS, so it is costed before it is started rather than discovered (all four apply to BOTH options unless marked):
 * It is a BREAKING CHANGE to a SPECIFIED rule — kernel-language.md 6.8's paired type-and-value convention, which records "revisiting it means moving both halves together". The value half is fixed at the term level (`x.(f)` yields the scalar `x.f`; a single rename collapses too), so the schema half cannot move alone.
 * It moves `where`'s bare-binder spelling. Today a 1-collapsed row is read as `eq(c, 30)` via the `WHOLE_ROW_HOLE` sentinel; with an uncollapsed schema `c` is a 1-field tuple and the spelling becomes `c.age`. Existing tests drive `eq(c, 30)`.
 * OPTION B ONLY: it must thread through the `provides LogicalStream[T = T, E = E]` edge in relation.anthill, or every inherited Stream consumer starts seeing the uncollapsed tuple. Whether a ctor reduces across a provides binding (with the sort's own abstract `T` as operand, which WI-734 says leaves it symbolic) is the FIRST thing to measure — it decides whether option B is reachable at all. Option A does not need it: with no collapse there is nothing to reduce.
 * OPTION A ONLY, and it is structural rather than ergonomic: kernel-language.md 6.8 desugars `x.(f)` to `x.f` at CONVERT time, before any type exists, and calls the collapse a paired type-and-value convention. So a relation projection `r.(f)` currently becomes a scalar member access — which is precisely why `ages.(age)` reports "no such member" (WI-20260818-7X7NK). Under A a one-member relation projection must yield a ONE-COLUMN RELATION with schema `(f: T)`, so relation projection must stop riding the convert-time desugar, and `r.(f)` diverges from `t.(f)` on a plain tuple. Decide whether that divergence is acceptable, or whether the term-level collapse moves too; entangled with WI-20260818-7X7NK, and the two should be looked at together.
 * THE SECOND, INDEPENDENT BLOCKER already found and documented (WI-1128, at `WHOLE_ROW_HOLE` in eval/builtins.rs): the whole-row sentinel is ONE symbol shared by BOTH `join` binders, so it can say neither which row it means nor match `fill_recipe_holes`' sole-column arm over a MERGED column list. It is unreachable today only because `Concat` refuses the operands that would reach it — this redesign REMOVES that gate, so the sentinel must be keyed per binder in the SAME change or the natural spelling `join(r, ages, (c, q) -> eq(c.age, q))` still fails. Today it has no drivable control; under this ticket it does.

ACCEPTANCE: a decision recorded in 052 (do it or decline it, with the measurement that decides); if done — a join / fix / project over a one-column relation RUNS end-to-end with the recovered column name, driving the values; the tuple-typed-column fixture above becomes a correct schema or a loud error, and its recorded-limit test is RETIRED rather than patched; `Membership` distinguishes 0 columns from one `Unit`-typed column (WI-728's recorded limit retires with it); the whole-row sentinel is per-binder; `where`'s changed spelling is migrated with its tests; kernel-language.md 6.8 and relation.anthill updated together; cargo-test green via scripts/test.sh.
