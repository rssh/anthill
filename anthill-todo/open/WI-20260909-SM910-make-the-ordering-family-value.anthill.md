## Description

MAKE THE ORDERING FAMILY VALUE-DIRECTED, LIKE `eq` ALREADY IS — a rule-body `gt`/`lt`/`gte`/`lte` must reach the carrier's own member, and the spec-op registration must stop being a claim about carriers it cannot serve. WHAT IS TRUE TODAY, all measured: (1) A PROGRAM CANNOT WRITE A `<` THAT DISPATCHES. `parse::pratt` maps `<` to the literal address `..anthill.prelude.PartialOrd.lt` (LT_FUNCTOR); the `..` marker is unspellable by any identifier, so it bypasses the name ladder, imports and scope by design (WI-20260825-KD9SW, which introduced it because a same-spelled name in scope used to CAPTURE the operator — driven: `import Weird.{add}` made `1 + 2` answer `99`). Every `<` in every program is therefore the one symbol `anthill.prelude.PartialOrd.lt`. "Is it builtin" is then a raw hash lookup on that symbol (`get_builtin_view` -> `builtin_of` -> `self.builtins.get(&sym)`), which `register_builtin_tags` fills at bootstrap. No call-site information — not the operand, not the carrier, not the rule's typing — is consulted anywhere on that path. So there is no non-builtin `<` to distinguish. (2) TYPING THE RULE CHANGES NOTHING, AND NEITHER DOES WRITING THE DICTIONARY. MEASURED on one carrier `Pt` that `provides PartialOrd[T = Pt]` AND supplies its own `operation gt(a: Pt, b: Pt) -> Bool = true`, with the same call written four ways: untyped rule body -> UNDECIDED; TYPED head (`?r: Bool`) -> UNDECIDED; explicit `requires(PartialOrd[T = Pt])` in the body -> UNDECIDED; OPERATION BODY -> `true`, the carrier's own member. Only the operation body reaches it. (3) THE REASON IS ONE LINE, and it is the first statement of `check_one_spec_op_requirement` (kb/typing.rs): `if kb.is_builtin(functor) { return; }`. A typed rule gets no dictionary for `gt` either — the registration does not merely serve untyped rules, it OVERRIDES the dictionary path everywhere. Its stated justification is that these builtins "NEVER consult an `Ord`/`Numeric` instance, so a `requires Ord[...]` could not even fix them; a non-numeric carrier is a plain resolution failure, not a missing dictionary". That was true when written and is circular as a defence: they never consult an instance because nothing makes them. (4) `+` IS THE COUNTER-EXAMPLE IN THE SAME TABLE. `pratt`'s own doc records it: "THE ADDRESS IS THE SPEC OP, NOT A CARRIER, so this costs no polymorphism: the spec op is what dispatches. Driven — a `Money` providing `Additive[T = Money]` answers `money(700) + money(25)` = 725 through its own `add`." True for `+` in an operation body, false for `<` in a rule body, and the difference is the position, not the operator. WHAT `eq` DOES INSTEAD, and it is the shape to copy: `sem_eq_dispatch_target` reads the OPERAND's head functor, finds the carrier's own member through a load-built index (`load::build_eq_dispatch_index`) in one O(1) hit — scalars and headless values read `None` and stay structural — and `sem_eq_dispatch` then RUNS that member, via `bridge_eq_op_to_eval` when it has a runnable body and `prove_rule_predicate` when it is rule-backed, three-way with the truncation bit carried. The structural compare is only the DEFAULT for a carrier with no override. That IS a dictionary built from the concrete argument values at resolve time, which is what `docs/kernel-language.md` already promises for a rule-body goal ("dictionaries are built from the concrete argument values at resolve time"). The ordering family got the registration and never got the dispatch. WORK: give `gt`/`lt`/`gte`/`lte` the same value-directed step ahead of `builtin_cmp`, so the primitive becomes the default rather than the decision. TWO CANDIDATE DESIGNS AND THE CHEAPER ONE IS UNMEASURED — probe it first rather than building the index: WI-1036 measured that the PIN IS ALREADY STAMPED (`PartialOrd.gt -> wi1036.own.Point.gt`, observed at `classify_pin_or_apply_within`) and simply never read, "because a goal takes `BuiltinTag::Gt` off its SPELLED functor and no goal-position reader consults a pin" — and in OPERAND position the pin IS read (`wi1036...::a_supplied_override_reaches_a_rule_body_operand` passes today). So teaching the goal-position builtin path to consult the pin may be far smaller than a second dispatch index. Measure that before choosing. THE SECOND HALF IS FORCED, NOT OPTIONAL: the `is_builtin` skip quoted in (3) is justified by "a `requires` could not even fix them", which becomes FALSE the moment they dispatch — so `check_one_spec_op_requirement` and the op-scoped `requires WeakOrd[T]` on `PartialOrd.gt`/`gte`/`lt`/`lte`'s default bodies must move in the SAME change. That requirement's CALL-SITE half is currently masked by exactly this skip (MEASURED under WI-876: a generic operation with `requires PartialOrd[T]`, and even one with no `requires` at all, calls `PartialOrd.gt(a, b)` and loads clean); the cost is recorded at the clause in `stdlib/anthill/prelude/ordered.anthill`, where WI-879 declined to pay it and left it ownerless. This ticket owns it. NOTE THE SAME OPEN QUESTION EXISTS FOR `PartialEq.eq` and is stated in 058 §10a — "A dispatching builtin is still a workaround for a missing key; what would retire it is a value-directed entry not spelled as a spec-op registration, and nothing owns that yet." `eq` at least dispatches; the ordering family does not, which is why it goes first. ACCEPTANCE: on a carrier that provides `PartialOrd` and supplies its own `gt`, the rule-body goal `PartialOrd.gt(pt(2,1), pt(1,9), ?r)` answers what the OPERATION BODY answers (`false` for WI-1036's fixture, `true` for this ticket's) instead of withholding — and `wi1036_builtin_defaulted_dispatch_test::a_supplied_override_of_a_builtin_mapped_spec_op_is_unreachable_from_a_rule_body_goal`, which names WI-879 as its owner and asserts `UNDECIDED`, is updated to that answer and re-owned here; the four-way table in (2) collapses to one answer; a scalar carrier's comparison is UNCHANGED (`builtin_cmp` remains the default for a carrier with no override — the `wi879_fact_driven_resolver_builtins_test` rows and `wi645`/`wi644` Float IEEE rows stay green); the `is_builtin` skip in `check_one_spec_op_requirement` is re-decided with its reason rewritten, and `ordered.anthill`'s recorded cost is either paid or re-recorded with a new reason; full workspace green via rustland/scripts/test.sh. REFERENCE: kb/resolve.rs `builtin_cmp` / `sem_eq_dispatch` / `sem_eq_dispatch_target`; kb/load.rs `build_eq_dispatch_index` / `derive_carrier_builtin_tags`; kb/typing.rs `check_one_spec_op_requirement` / `classify_pin_or_apply_within`; parse/pratt.rs `LT_FUNCTOR` and its doc; stdlib/anthill/prelude/ordered.anthill; docs/design/058-implementation.md §10a and §10b.

THE REGISTRY IS ANSWERING THREE QUESTIONS UNDER ONE `HashMap<Symbol, BuiltinTag>`, READ AT ONE PLACE, AND ONLY ONE OF THEM IS THIS TICKET'S. Folded in because it changes the SHAPE of the work, not the wording: the goal is not a dispatch step bolted in front of `builtin_cmp`, it is moving the registry BEHIND dispatch and retiring one of its three populations. Q1 — "IS THIS THE RESOLVER'S OWN CONTROL STRUCTURE?" `not` (negation-as-failure), `cut`, `push_choice`, `push_and`, `unify`, `find_dictionary`, `domain`, the whole reflection surface (`qualified_name`, `lookup_symbol`, `kind`, `scope`, `occurrence_*`, `field_access`, `ho_apply`), and `struct_eq`, whose definition is literally "never dispatches". These are NOT sort operations: `not(G)` has no carrier and `cut` prunes the choice-point stack. A dictionary has nothing to say about any of them and no amount of dispatch machinery removes the need for a registry here. UNTOUCHED by this ticket. Q2 — "DOES THE RESOLVER HAVE A PRIMITIVE THAT REALIZES THIS MEMBER?" The thirty carrier rows (`Int64.gt`, `Float.add`, `BigInt.mod`, …) that WI-879 made DERIVED from the `operation_map` facts. This one cannot be replaced by a dictionary either, and the reason is worth stating because it is the load-bearing distinction: A DICTIONARY TELLS YOU *WHICH* IMPLEMENTATION, NOT *WHAT RUNS IT*. Dispatch can resolve a `gt` call to `Int64.gt`; something must still EXECUTE `Int64.gt`, and in the resolver that something is `builtin_cmp`. This registry is the resolver's half of `operation_map` and it STAYS. Q3 — "WHAT RUNS A SPEC OP WHEN THE CARRIER HAS NO OVERRIDE?" `PartialOrd.gt`/`lt`/`gte`/`lte`, `Additive.add`/`sub`, `Multiplicative.mul`, `Divisible.div`, `EuclideanDomain.mod`. THIS IS THE POPULATION THAT SHOULD NOT EXIST IN ITS CURRENT FORM, and it is the same shape WI-876 spent itself deleting on the EVAL side: one implementation serving every carrier that never wrote its own, including carriers it cannot handle. 058 §10a already says it for `PartialEq.eq` — "A dispatching builtin is still a workaround for a missing key; what would retire it is a value-directed entry not spelled as a spec-op registration". SO THE DEFECT IS POSITION, NOT EXISTENCE. The registry is keyed on the SPELLED FUNCTOR and read IN FRONT of dispatch: `get_builtin_view` takes the head symbol, the tag decides, and no provision is consulted. Behind dispatch it is unobjectionable — carrier, then provision, then member, then "what realizes this member", then primitive. THE `eq` / ORDERING ASYMMETRY IS THE ARGUMENT, AND IT NEEDS ITS SPELLING CORRECTED FIRST. `check_one_spec_op_requirement`'s justification for skipping builtins reads "structural equality IS the default `Eq` instance … so EVERY carrier already satisfies `Eq`". THAT SENTENCE IS FALSE, and the tree enforces that it is: `Float` provides `PartialEq`, `PartialOrd` and `NonEq` and deliberately NOT `Eq` (WI-644 / proposal 004; WI-658 makes a user's `provides Eq[Float]` a LOAD ERROR), and WI-664 derives `NonEq` for every COMPOSITE carrying a `Float` field — so a plain `Point(x: Float, y: Float)` is `NonEq` too. It is a class, not one carrier. What the early return actually needs is the narrower claim about `PartialEq`, the partial BASE, which every carrier does satisfy — structurally by default or by override (`Float`'s IEEE `eq`, `Set`/`Map`'s membership `eq`) — and `PartialEq.eq` is the operation the return is about, so the return is SAFE and only its stated reason is wrong. A WI-644 leftover: the comment cites WI-616, which predates the split, while the registration site two lines above states it ("eq/neq live on PartialEq, gt/lt/gte/lte on PartialOrd (the partial bases); Eq/Ord are the lawful/total markers"). The sentence is corrected in WI-879's commit; it is recorded here because the corrected spelling is what makes the next paragraph exact. WITH THE SPELLING RIGHT, THE ASYMMETRY IS THE WHOLE CASE: `PartialEq` HAS a total default — structural equality — so every carrier has an equality and a front-position registry entry there is a defensible DEFAULT standing in for an instance nobody had to write. `PartialOrd` HAS NO DEFAULT. There is no order on an arbitrary carrier, which is exactly why `Ord.max`/`min` were never resolver builtins and why `Ordered.compare` carries no tag. So `PartialOrd.gt`'s registry entry is not a default standing in for a missing instance — it is AN ANSWER INVENTED WHERE THERE IS NONE. That is why the ordering family is the wrong one to have in front of dispatch, and why it goes before the `eq` question does. AND IT CHANGES WHAT THE RIGHT ANSWER IS for a carrier with no provision at all: behind dispatch, `PartialOrd.gt` over such a carrier ends at a MISSING DICTIONARY — a real diagnosis with a repair the author can act on — instead of at "no order for this operand pair", which is a resolver limitation wearing a semantic answer's clothes (WI-879's arm, and the best that arm can do). PERFORMANCE IS NOT AN OBJECTION, BECAUSE THE `eq` DESIGN ALREADY SOLVED IT: `sem_eq_dispatch_target` is documented as "One O(1) hash lookup; scalars and headless values read `None` (structural)", so the hot integer comparison short-circuits to the primitive with no dispatch at all. The dispatch step does not have to sit on the fast path, and the same trick applies here — a literal operand reads `None` and goes straight to `builtin_cmp`.
