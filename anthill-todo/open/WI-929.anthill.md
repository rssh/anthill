I independently verified only the two it found that WERE live -- the by-qualified-name arm dropping SymbolKind::Entity, and symbol_is_value_place losing exclusivity -- and both are already FIXED in WI-925. The items below are REPORTED, NOT independently re-verified; DRIVE each before fixing it.

ROOT CAUSE (common to most): define reuses an existing symbol on a repeated SHORT NAME in one scope, and now records the second declaration's category too. So two genuinely different declarations sharing a name merge their categories, and any has_kind reader that meant the EXCLUSIVE question ("was declared as X") silently widens.

(1) MOST SEVERE -- SILENT TRIGGER-SORT HOLE. Item::SortWithBody (load.rs ~2618) reuses an existing by_qualified_name symbol WITHOUT calling define. If that qualified name was already claimed by a non-Sort declaration -- an explicit namespace, an implicit namespace minted by ensure_intermediate_namespaces for a dotted name, or an operation, scanned earlier in the same file OR in ANY earlier file since pass 1 is global -- then the sort's symbol never gets SymbolKind::Sort while register_sort still runs. sort_of_head(X) then returns None where it used to return Some(X), and collect_trigger_sorts DROPS the trigger sort of a constraint whose pattern head is X: the guard is registered under no sort and never re-fires on an assert. A silent hole on a clean load -- the failure mode this repo's development principles single out.

(2) is_sort_scope WIDENING via a merged Namespace/Sort. Source shape:
    namespace Foo ... end
    sort Foo = Int64
yields kinds {Namespace, Sort}, so is_sort_scope answers TRUE for the namespace's scope term.

(3) PASS-1 vs LOAD DISAGREEMENT. Item::AbstractSort ALWAYS defines, so a later "sort Foo = Int64" merges Sort into a namespace Foo that pass 1 already used as a non-sort scope. An "entity Bar" inside "namespace Foo" then takes add_kind(Sort) in pass 1 but is treated as sort-body at load (the !is_sort_scope block is skipped, so NO EntityInfo and NO register_self_sort). One declaration, two answers.

(4) ensure_intermediate_namespaces (load.rs ~2166): for a dotted name whose PREFIX is a free-standing entity, the has_kind(Namespace) filter fails, define merges Namespace into the ENTITY symbol and returns it, and the resulting ns_term is Fn{E} -- which is_sort_scope now answers true for. So "entity E.Bar(...)" would become a constructor OF THE ENTITY.

(5) load.rs ~11964, the guard "if !has_kind(head_resolved, Sort) { return None }", is a live WIDENING: every free-standing entity now carries Sort, so a two-segment "E.Member" in type position no longer bails. It falls into the else arm, which looks up by_qualified_name of "<E_qn>.<Member>" -- and emit_entity_info registers entity FIELDS under exactly that key. So "entity Foo(Bar: Int64)" plus a type annotation "x: Foo.Bar" resolves to the FIELD symbol as a sort ref. Latent only because uppercase field names are unusual; the arm's own doc ("Enum.Entity") no longer describes what reaches it.

(6) logical_sort_qn (load.rs ~11897) states the EXCLUSIVE reading in its own doc ("app.Config is a Namespace", and therefore not stripped). has_kind(Sort) no longer excludes a symbol that is both, so that doc is false as written.

(7) DOWNWARD ASYMMETRY. register_self_sort pushes into sort_entities, so sort_children(E) == [E] and constructors_of_sort(E) == [E] for a wrapped entity, while constructor_parent_sort cuts the fixpoint on the UPWARD side only. Current readers are harmless (sort_constructor_syms feeds match candidates; the exhaustiveness reader is gated on sort_kind == Enum, unreachable for a free-standing entity), but the asymmetry needs either a strict downward view or a stated reason none is needed, recorded next to constructor_parent_sort's doc.

(8) PRE-EXISTING, now inherited by add_kind (WI-720): for a DOTTED entity name both is_sort_scope guards read the OUTER scope while the symbol is defined in actual_scope, so "sort S { entity a.B(...) }" marks B a constructor of S although B lives in namespace a.
