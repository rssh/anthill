## Description

THE TYPER'S RULES ARE ACCEPTED ON HAND-WRITTEN EXAMPLE ROWS ONLY; A GENERATED FAMILY OF PROGRAMS PER RULE, HELD TO STATED PROPERTIES, IS NOT PART OF THE SUITE — so a rule is tested on the programs someone thought of, and the interactions between its cases are found one review at a time. From WI-20260929-0RP29 (user, 2026-10-02). WHAT A FAMILY IS: every program obtained from ONE template by filling a few holes from short lists — the cross product, enumerated, not drawn at random. The one built during that ticket's ninth pass: a spec `Sp { sort T = ?; sort K = ?; sort L = ?; sort J = ?; operation op(<receiver> t: T, x: K, y: L) -> <return> }` and a carrier `Car { sort V = ?; entity car(v: V); <provisions>; operation op(<receiver> t: Int64, x: <X>, y: <Y>) -> <return> = … }`, with <X> one of 8 shapes (`Car[V = List[T = V]]`, `Car[V = Car[V = V]]`, `Car[V = Car]`, `List[T = Car[V = V]]`, `Option[T = Car[V = List[T = V]]]`, `Car[V = (a: V) -> V]`, `Car[V = V]`, `Car`), <Y> one of 7 projections (`x.J`, `x.V`, `x.v.T`, `x.v.J`, `x.v.V`, `List[T = x.J]`, `List[T = x.V]`), <receiver> one of 4 (none; `c: Car` on both sides; `s: Sp` against `c: Car`; `s: Sp` on both), <provisions> one of 4 (`J = V` in the same provision; `J = V` lent by a second spec; both; `J = List[T = V]`), and <return> `Int64` or the projection: 1,152 programs. MEASURED: run through `anthill load`, 104 of them overflowed the loader's stack on the tree before the fix (exit 134) — a crash that ticket's example rows (434 at its end) had not found, and that came to light only because backing a guard out killed the test process; after the fix none crashes and no other verdict differs from the build before it. The run took 2 m 17 s with twelve processes, each loading the standard library again. MEASURED on the same ticket, for why examples do not converge: eight /code-review passes each reported the cap of 15 findings; of the eighth's fifteen, fourteen were regressions of the two passes it read, and about a third were one program judged two ways by two spellings or two readers. THE PROPERTIES a family is held to: (P1) NO CRASH — each program loads or is refused; none overflows, panics or hangs, and the runner NAMES the program that does instead of dying with it (a stack overflow kills the test process, so the runner isolates programs — child processes, or a re-invocation of the test binary per chunk); (P2) NO UNEXPLAINED CHANGE — each family has a committed verdict file (program name → loads / refused, with the refusal's class), so a change of any verdict is a diff of that file in the commit that caused it, read by a person, where today it is found by a reviewer or not at all; (P3) SOUNDNESS — a program that LOADS and has a `go()` runs to its value: no "type mismatch: expected …, got …", no "entity has no field", no `match_failed` at run time (the template supplies a `go()` that drives the member through the spec call with concrete values; families without one are held to P1, P2 and P4 only); (P4) ONE VERDICT FOR TWO SPELLINGS — the family declares which of its programs are the same program written two ways (`x.J` and the type it reduces to; a lambda written at the call and the same lambda held in a `let`; `E = EC` and `E = {EC}`; an alias and the type it names; a braced and an unbraced row), and each such pair gets one verdict, a known exception being listed with its ticket (WI-20261002-DNDZF's tuple spelling). WHAT EXISTS TODAY: the rows of tests/include/*.rs through `common::load_errors_of` / `run_int64`, each loading the standard library and one source, with a back-out ledger per file; no generator, no verdict file, no dependency for property testing in the workspace (no proptest / quickcheck / snapshot crate); the generator, the two-build comparison and their reports used in WI-20260929-0RP29 were scripts in a session's scratch directory and are not in the repository.
