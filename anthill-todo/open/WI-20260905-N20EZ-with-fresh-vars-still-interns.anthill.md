## Description

WITH_FRESH_VARS STILL INTERNS ONE TERM PER OPENED CLAUSE, and `walk` is why. WI-20260904-J0RM4 moved the QUERY PATTERN off the hash-consed store and measured what was left: converting a pattern now grows the term store by 0, but RESOLVING a rule goal still grows it, once per rebuilt spine node, for ever. MEASURED per query (convert delta 0 in every row): a FACT goal `Box(v: ?x)` +0 (no clause opened); `simple(?x)` +1; `two_var(?a, ?b)` +2 (one per linked query var); `chain(?x)` :- simple(?x) +2 (one per clause opened); and where a query var matches a COMPOUND head subterm, the rebuilt spine counts too -- head `wrapped(Box(v: #0))` queried `wrapped(?p)` is +2, `wrapped2(Pair(a: #0, b: #1))` is +3. So a leaf-only repair would miss a real share of it. THE SITE is `KnowledgeBase::term_from_debruijn` (kb/mod.rs), whose `Var::DeBruijn` arm does `self.alloc(Term::Var(Var::Global(vid)))` and whose `Fn` arm re-allocs the rebuilt spine through `map_fn_children`; `with_fresh_vars` calls it to build the ANSWER LINK for each query var that matched a rule-head slot. A fresh `VarId` makes each var term NEW, so hash-consing cannot dedup it, and the store is monotone under a scoped-KB layer by design (WI-SPGBP), so releasing it is unavailable exactly where a long-running process would need it. THE STORAGE WAS NEVER THE OBSTACLE, and J0RM4's delivery note said otherwise -- correct it: `Substitution.bindings` is already `ImHashMap<VarId, Value>`, `bind_value` exists, `occurs_in_value` already takes a `&Value`, and `Value::Var` / `Value::Entity` are exactly the carriers wanted. THE MECHANICAL PART IS SMALL: a non-allocating `value_from_debruijn` -- `Value::Var(Global(fresh))` for a DeBruijn leaf, `Value::Entity` for a spine node, and `Value::term(tid)` shared unchanged for any subtree with NO DeBruijn beneath it. That last rule is what keeps `Value`'s missing `Ident` carrier out of the picture (the thing that forced J0RM4 onto the occurrence carrier): only `Term::Fn` spine nodes are ever converted, and `Ident` / `Bottom` / `Const` / `Ref` ride through as `Value::Term`. Then `bind_value` for the links, and `bind_compressed` generalized from `(VarId, TermId)` to `(VarId, Value)` -- its whole Term-dependence is ONE predicate ('does this existing binding just name var v?'), which `resolve.rs`'s `caller_fresh_vars` filter duplicates, so both collapse onto one carrier-neutral helper. That is a simplification, not only a port. THE ACTUAL OBSTACLE, AND THE WHOLE OF THIS TICKET, IS `KnowledgeBase::walk`. It chases var chains in TermId space and RETURNS a `TermId`, so it cannot express 'this chain ended at global var v' without interning a term for v -- which is precisely why the link leaf is interned today. It currently STOPS at any non-`Term` carrier. So an answer link carrying `Value::Var` would make `walk` return the QUERY var where it used to reach the FRESH var, and every `walk`-based reader inherits that silently. `resolve.rs` even asserts the invariant being removed: a `debug_assert!` that `answer_links` is Term-only 'by construction', with the note that a non-Term entry would be SILENTLY DROPPED by `iter_terms`. That assertion must be rewritten, never quietly deleted, and `iter_terms`'s silent drop is the trap the whole change turns on. THE CALLER SET IS FOUR, all in `kb/resolve.rs`, and each has a natural var-valued reading: `is_ground` (a var end is `HasVar`), `collect_unbound_vars` (push the var id), `term_has_var_ref` (reads the walked term's structure), and the spec-op argument chase at ~5824 (which already re-wraps the result as `Value::term`, so it would take the `Value` directly). `walk` is `pub` but nothing outside `kb/` calls it. SHAPE: give `walk` a var-valued end -- either a `WalkEnd { Term(TermId), Var(VarId) }` or, better, retire it in favour of the existing carrier-faithful `walk_view` (which already returns a `Value` and already surfaces a non-`Term` binding) and convert the four callers. Retiring it is the stronger reading: `walk`'s own doc says to use it only 'where a `TermId` is genuinely the right shape', and the inability to represent a var-valued binding is not a narrowing, it is a hole. ACCEPTANCE: a test DRIVES it by running N rule-goal queries against a loaded KB and asserting `term_store_len` is UNCHANGED after the first, across ALL the shapes measured above -- the simple link, two links, a chained clause, and the two COMPOUND head-subterm shapes, which are what a leaf-only repair would leave leaking (today they grow by 1/2/2/2/3, and that is the control); `with_fresh_vars` makes no `kb.alloc` on the answer-link path; `bind_compressed` and `caller_fresh_vars` share ONE carrier-neutral 'does this binding name var v' predicate; the resolve.rs Term-only `debug_assert!` is REPLACED by whatever the new invariant is rather than dropped; answers are identical before and after (the same solutions, the same bindings, the same definiteness) across the whole suite; cargo-test green via scripts/test.sh. AND ONE ROW MUST GO RED AND BE DELETED: `wi_j0rm4_query_pattern_carrier_test::resolution_of_a_rule_goal_still_grows_the_store_by_one` asserts BOTH halves of today's state on purpose, so that closing this leak trips it -- that is the designed signal, and deleting it is part of the work, not a casualty of it. NOT SCALAND: this is a representation choice in the rust resolver; scaland's own resolver is untouched.
