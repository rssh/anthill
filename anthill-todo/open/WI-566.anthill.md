## description

Proposal 048 Phase 4 — Generalize guarded Error-effects to the remaining partial stdlib operations (head, nth, last, tail, and any other op that can fail on a precondition), migrating each from an unconditional Error payload to a guarded one { Error[E] :- guard } the way WI-479 did for Int64.div/mod/rem/divExact + Field.div/recip (Phase 3). The 048 MECHANISM is fully delivered and reusable UNCHANGED: grammar+representation (WI-478 Phase 1), typer discharge over Gamma (WI-067 Phase 2), and the migration pattern itself (WI-479 Phase 3) — so Phase 4 is pure stdlib content plus tests, no new typer/loader code (cf. WI-479 which added zero engine code). DEMAND-DRIVEN per the proposal (048 §Phasing item 4: 'apply to other partial stdlib operations as their error payloads are introduced'): the trigger is an op acquiring an Error payload (e.g. head on an empty list -> Error[EmptyList] guarded by isEmpty(l)). NOT actionable until such payloads exist — today head/nth/etc. are total-by-type or panic, not Error-typed; introducing the payload is the prerequisite and is the natural place to also add the guard. Guard vocabulary is the decidable boolean fragment refutable under step_cap (048 OQ-A: isEmpty/outOfBounds/eq/neq). Acceptance (per migrated op, as it lands): the op declares { Error[E] :- guard }; a call with a statically-refuted guard (literal/flow-fact) type-checks pure; a call that can't refute keeps the effect; cargo-test green. See docs/proposals/048-conditional-effects.md §Phasing(4) + §Generalization. Builds on WI-479 (Phase 3 precedent) + WI-067 (discharge).

## Feedback

### 2026-06-25T12:09:36Z — claude

Design refinement (2026-06-25): the criterion for a Phase-4 subject is that the failure condition be a VALUE-DECIDABLE guard — literal-foldable / verbatim flow-fact over the ARGUMENTS, like div's eq(b,0) — NOT an opaque or effectful call to another operation. A guard phrased as another op (isEmpty(s)) discharges only when that op reduces to the evaluable fragment on a concrete constructor (isEmpty(cons)->false) or matches verbatim in Gamma; it gets NO cross-operation reasoning (gt(length,0) does NOT refute isEmpty). So head is NOT a clean example: it returns Option (total) today, and a guarded isEmpty on an abstract/lazy receiver never discharges. The concrete head/headOption split (guarded head on CONCRETE List only) is filed separately as WI-567.

### 2026-06-25T14:36:44Z — claude

Criterion sharpened (via WI-567 probes): 'value-decidable guard' precisely means the predicate bottoms out in a NATIVE SCALAR BUILTIN (Int eq/neq/lt...). A guard over any anthill-RULE-defined predicate (isEmpty, Eq[List].eq, structural ops) does NOT discharge today -- empirically confirmed, neither literal nor flow-fact nor eq(l,nil) refutes it -- because the type-erased resolver cannot fire the defining rules on the prove path (= WI-502/WI-292). So a Phase-4 op is dischargeable NOW only if its failure condition is a native scalar predicate over arguments; emptiness/bounds guards over rule-defined predicates are gated on WI-502.
