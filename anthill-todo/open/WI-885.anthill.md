## Description

`[simp]`-DEFINEDNESS IS A BACKING KIND NO PREDICATE CAN SEE — give `op_is_executable` / `op_is_interpretable` a leg for it, or mark a definitional equation apart from a normalization hint. FOUND during WI-881's review, on the change that created the first stdlib case. `op_is_executable` (kb/typing.rs) is `builtin │ host mapping │ runnable body`; `op_is_interpretable` is that minus the builtin leg. NEITHER knows about a `[simp]` equation — and MEASURED (WI-881's `a_bare_nullary_simp_head_never_fires` control), a `[simp]` equation MAKES A BODY-LESS OPERATION RUN by inlining LHS->RHS at the typer, while the same equation untagged dies `OperationBodyMissing`. So there is a fourth way an operation runs and the two predicates that answer 'can this run' both say no. `anthill.prelude.Float.recip` is the first shipped operation backed that way (WI-881: its equation `recip(?a) <=> div(1.0, ?a)` IS the definition — `f64::recip` is literally `1.0/self` — so it carries `[simp]` and has no `operation_map` entry). THE LOAD CHECK IS NOT THE EXPOSURE, and that was checked rather than assumed: `check_provider_operations` enumerates `own_ops.get(&p.spec)`, `Float` provides PartialEq/PartialOrd/NonEq/Numeric/Ring, and `recip` is declared only by `anthill.prelude.Field` — which `Float` does not provide — so `op_backed` is never asked about it, however far WI-880 narrows the host-carrier skip. THE EXPOSURE IS `carrier_override_op` (kb/typing.rs), whose doc states the exclusion as 'a member backed only by rules, WHICH THE INTERPRETER CANNOT INVOKE'. That sentence is now false for a `[simp]` rule, and the failure shape it produces is verbatim WI-876's: a `[simp]`-backed carrier member reads as ABSENT, so the spec default runs on the value-directed route while the typer's inlining answers on the static route — one call, two answers by route. Unreached today only because no spec `Float` provides names `recip`; WI-876's own review insisted the gate must not depend on that coincidence. A SECOND, DESIGN-LEVEL QUESTION THE TICKET SHOULD ANSWER: `[simp]` is proposal 043's DIRECTIONAL-REWRITING attribute ('commutative laws must stay bare or the phase loops'). Making it double as the definitional-backing switch couples two intents — an operation whose defining equation is not orientation-terminating can never be backed this way, and tagging `recip` to make it run also forces every `recip(x)` in every body to normalize to `div(1.0, x)`, which is worse symbolic output for the proof and codegen layers. Options: (a) add the leg, keyed off `simp_equation_rids`, so one predicate still answers the question; (b) a distinct marker for 'this equation is the definition'; (c) decide `[simp]` is NOT backing and host-map `Float.recip` like its 25 siblings. NOTE WI-881 ALREADY MEASURED ONE REACH LIMIT that (c) would also fix and (a) would not: a `[simp]` head is an APPLICATION, so it rewrites `tau()` and NOT a BARE `tau` call site (a `var_ref`) — which is exactly why `tau`'s equally-exact equation was NOT tagged and `tau` is host-backed instead. The reaches that were never enumerated are value-directed dispatch, `ho_apply`/`OpRef`, and any second backend. WI-884 plans the same `[simp]`-instead-of-host move for `String.isEmpty`, so this decides that one too. ACCEPTANCE: 'can this operation run' has ONE answer per route, and the route that cannot run a `[simp]`-defined operation says so rather than reading it as absent; `carrier_override_op`'s doc matches what its predicate does; a test drives a `[simp]`-defined member of a carrier that PROVIDES the spec declaring it, on both the static and the value-directed route, and gets the same answer; full workspace green via rustland/scripts/test.sh. REFERENCE: WI-881 (which created the case and measured the head/call-site reach limits), WI-876 (the same absent-member defect, for host mappings), WI-818 (a rule is not backing — the claim this refines), kernel-language.md 'Equational rules'.

A BODY AND A HOST MAPPING COEXIST, so (c)-vs-(d) is not a fork. `dispatch_resolved_operation` reads the builtin registry at STEP 2 and the anthill body at STEP 3, and `register_operation_mappings` writes into that same registry — so the mapping WINS at eval while the body remains the portable definition (visible to op_is_executable / carrier_override_op, extractable by WI-669, and what a second backend emits when it has no primitive). MEASURED: `tau` carrying BOTH loads clean and passes.

WHY `isEmpty` WENT HOST-ONLY RATHER THAN BODY+MAPPING: `length` is declared in UNICODE SCALARS, so `eq(length(s), 0)` is O(n) — structurally, needing no benchmark, since Rust's str::len and C++'s std::string::size are O(1) BYTE counts and neither language has an O(1) character count over UTF-8. Emptiness is the one question that does not need the count. WI-884 had recorded this cost as UNMEASURED after an interpreter benchmark was swamped by the per-call argument copy; that benchmark was answering the wrong question. The equation SURVIVES, untagged, as the total specification of the operation — which also stops it inlining eq(length(s), 0) into every proof and codegen output where the author wrote isEmpty(s), the symbolic-quality cost this ticket raises.

REMAINING WORK IS SMALLER; THE ACCEPTANCE STILL STANDS. ### 2026-07-31T07:04:22Z — feedback — user

CORRECTIONS TO THE PRECEDING FEEDBACK — three claims in it are FALSE, found by review. Read this entry, not that one, for the counts and the cpp consequence.

1. ROOT CAUSE (user, and it settles the option list). A [simp] equation CANNOT BACK A DISPATCHED CALL, because NO REQUIREMENT DICTIONARY CAN BE BUILT FROM ONE. Confirmed at both halves. (i) The dictionary slot holds an operation SYMBOL and the symbol gets INVOKED: dispatch_via_sort_ops_table (eval/eval.rs:932) resolves a Symbol out of the dict's (impl_sort, op_short) table and eval.rs:1352-1356 hands it to dispatch_apply_with_requirements -> dispatch_resolved_operation, whose steps are builtin (2), body (3), value-directed impl (3b). A rewrite rule is in none of them; there is no slot it could occupy. (ii) [simp] needs a STATICALLY KNOWN CARRIER, which is exactly what a dictionary abstracts away — set.anthill:55-57 says so in the stdlib's own words ('tagged [simp] so the type-directed rewriter fires them once the redex's carrier is KNOWN to provide Set'). So [simp] requires a syntactic REDEX and a known carrier; dictionary-passing polymorphism has neither.
   CONSEQUENCE FOR THIS TICKET'S OPTIONS: (a) and (b) are WRONG, not merely worse. A predicate leg — or a distinct definitional marker — would make op_is_executable promise an implementation for which no dictionary entry can be constructed, i.e. lie at the one site that matters. It also RETROACTIVELY JUSTIFIES carrier_override_op: reading a [simp]-backed member as ABSENT is the CORRECT answer to 'can the interpreter invoke this', not the defect this ticket's description calls it. kernel-language.md's ''[simp] is what makes an equation run'' paragraph said [simp] was 'a third way beside a body and a host mapping'; that sentence is now corrected in place with this argument.
   LEFT OPEN DELIBERATELY (user): building a dictionary entry FROM a [simp] equation — synthesizing a callable out of the rewrite — may well be possible. Not attempted; recorded as the door this ticket may choose to open rather than a settled no.
