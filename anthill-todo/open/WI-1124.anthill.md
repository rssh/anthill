## Description

anthill-todo: `help <command>` — per-command help, rendered from the specs that already describe each command. USER REQUEST 2026-08-17, and it came from being bitten: `anthill-todo migrate` printed 'project already up to date' while workitems.anthill was still one shared file, because TWO different commands share the name `migrate` -- the bundle's WI-434 SCHEMA stamp (StoreFormat version) and WI-1118's LAYOUT move (`migrate --to item-per-file`). Top-level `--help` lists one-line descriptions and nothing else, so there was nowhere to discover the difference. (The immediate message was fixed inline in the same change that filed this; the missing capability is this ticket.)

MOST OF THE DATA ALREADY EXISTS, which is why this is a rendering job and not a documentation project. `anthill.cli.spec` (stdlib/anthill/cli/spec.anthill) declares `OperationSpec(name, description, params: List[ParamSpec], parent)` and `ParamSpec(name, kind, required, description)`, where ParamKind is positional / flag / repeated / bool_flag. The registry in main.anthill builds 24 specs. So `help <command>` is: find the spec by name, print its description, then one line per param -- spelling positional as `<name>` and flag as `--name VALUE`, marking required, and printing each param's own description. No new per-command prose has to be invented for the 16 commands built through the richer spec_* helpers.

THE GAPS, and they are the actual work:
  (1) EIGHT commands are built with `spec_named(name, description)`, which passes `params: nil()`. Their help would render a description and no arguments -- which for `list`, `next`, `status` is correct and for others is a silent under-report. Audit the eight and fill in real params rather than shipping empty ones; an argument that exists and is undocumented is worse than no help.
  (2) TWO commands are HOST-SERVED and are not in the bundle's spec model at all: `fsck` (WI-1114) and `migrate --to` (WI-1118). Both already carry hand-written usage constants in main.rs (FSCK_USAGE, MIGRATE_USAGE) reachable only via `<cmd> --help`. `help <cmd>` must reach those too, or it will confidently report less than `--help` does for exactly the two commands that most needed explaining. Either lift them into OperationSpecs the bundle registers, or have the host intercept `help fsck`/`help migrate`. The first is better and is the reason to prefer it over just adding more `--help` arms.
  (3) DECIDE whether `help <cmd>` and `<cmd> --help` are the same output. They should be, and one of them should delegate. Today `--help` works for the two host-served commands only, and is swallowed as an argument-error for the other 22.

ALSO WORTH DOING while in here: top-level `--help` could mark which commands take arguments, so the list itself hints where `help <cmd>` is worth asking.

Acceptance: a test that DRIVES it -- run `help <cmd>` for a spec'd command and assert the rendered params appear (not merely that it exits 0), and run it for `migrate` and assert BOTH the schema-stamp form and the `--to item-per-file` form are described, since that ambiguity is what filed this ticket. Assert an unknown command name is a loud error naming the closest matches rather than silence.

## Changes

### 2026-09-06T12:05:01Z — feedback — user

PARTIALLY COVERED 2026-09-06, by the argument-error half rather than by `help <cmd>`. What landed: the four subcommand-level ParseError variants (unknown_flag / flag_expects_value / unexpected_argument / missing_required) no longer collapse into one 'anthill-todo: argument error' line. Each now names the offending token AND the command, then prints that command's usage block rendered by a new anthill.cli.help.format_usage from the very ParamSpec list specs() declares — so this ticket's premise ('MOST OF THE DATA ALREADY EXISTS, this is a rendering job') is now demonstrated, and every ParamSpec description: string has a reader for the first time. To make that possible the stdlib ParseError variants were widened to carry the OperationSpec (and the ParamSpec, where the fault is about a declared parameter) instead of their names, which also removed a registry re-lookup and its impossible not-found branch. render_args/render_flags now pad the name column like print_help always did; anthill-core's EXPECTED_HELP golden moved with them. Tests: rustland/anthill-todo/tests/include/cmd_arg_error_test.rs, 7 driving the real binary, with three stated back-outs measured (collapsed arm -> 5 fail, happy path passes; single_dash_flag skipping find_param -> 1 fails, its sibling green; dashed_param_named skipping the ParamKind gate -> only the positional arm fails).

WHAT THIS TICKET STILL OWNS, unchanged: gap (1), the eight spec_named commands built with params: nil(); gap (2), fsck and migrate --to being host-served and outside the spec model; gap (3), help <cmd> itself. On (3) there is one NEW data point: '<cmd> --help is swallowed as an argument-error for the other 22' is no longer silent — 'anthill-todo list --help' now prints 'unknown flag `--help`' followed by the full flag list, so the information is reachable, but it is still exit 2 and still an error. Making it exit 0 with format_help belongs in dispatch, not in the error reporter: routing it through the reporter would make a parse failure double as a feature, and it would still miss fsck/migrate, which is exactly why gap (2) has to be settled first. Also still open: the ticket's ALSO-WORTH-DOING (top-level --help marking which commands take arguments).

### 2026-09-06T12:41:45Z — feedback — user

CENSUS CORRECTION 2026-09-06 — this ticket's stated populations are wrong in BOTH directions, measured against the code today.

GAP (1), 'EIGHT commands built with spec_named(name, description)': there are SEVEN (main.anthill:95-126 — init, status, graph, migrate, fsck, skill, version), and only THREE actually under-report. init takes <name> or --name <name>; migrate takes --to item-per-file|document and --created-from FILE; fsck takes --fix and --renumber [<id>]. status, graph, skill and version genuinely take nothing, so their empty params are CORRECT and need no audit. The registry is also 27 entries, not the 24 the ticket says, and its own header comment still calls itself 'The 16-subcommand registry'.

GAP (2), 'TWO commands are HOST-SERVED': there are FIVE intercepted before the bundle ever parses — version (src/main.rs:4573), init (4590), skill (4605), fsck (4836), migrate (4862). Only fsck and migrate carry usage constants; init now has INIT_USAGE too (added below). skill and version have none, and both SWALLOW --help silently: 'skill --help' prints the skill, 'version --help' prints the version. So the ticket's 'help <cmd> must reach those two' is really five, and the two it names are the two already in the best shape.

GAP (3), 'help <cmd>': absent, and 'anthill-todo help list' prints the TOP-LEVEL help and discards the argument — help is not a subcommand at all, it falls into main.anthill's unknown_subcommand arm which matches the word and ignores the rest of argv. That is the shape to fix, not just a missing renderer.

A DEFECT FOUND WHILE CENSUSING, FIXED INLINE (not left for this ticket): 'anthill-todo init --help' in a fresh directory SCAFFOLDED A PROJECT NAMED --help and exited 0 — init's name is positional and host-served, so the bundle's argument reporter never saw the flag. init now prints INIT_USAGE for --help/-h and refuses every other dash-led token, a value-less --name, and any token after the name. Tests in wi748_init_honors_dir_test.rs (5 added), control measured: restore the old two-arm match and exactly those 5 fail while init_names_the_project_from_a_bare_argument stays green.

ALSO LANDED, from /code-review high on the argument-error change: a required FLAG is no longer reported as a positional (insert's --before said 'missing required argument <before>', a spelling the parser refuses when followed); required params render unbracketed in the usage line; a POSITIONAL is no longer reachable as --<name> (show --id used to say 'flag --id expects a value' above a 'usage: show <id>' block denying it exists); the seven params whose descriptions say '(repeatable)' are declared kind: repeated() so usage_token's repeated arm stops being dead. The dash-spelled predicate now lives once, on anthill.cli.spec beside the ParamKind it reads — parse.anthill had no copy, main.anthill had its own, and they disagreed.
