## Description

Multi-instance Modify state. Today's default_modify_handler (eval/effects.rs) keys cells by functor symbol only — `resource_key` extracts only `Value::Entity { functor, .. }` and ignores the entity's fields. Consequence: two `wis(backend_a, ...)` and `wis(backend_b, ...)` share a single cell; setting one overwrites the other. Proposal 027 §Modify[T] line 564 acknowledges this: 'an arena keyed by the target's functor symbol. set(store, v) and set(counter, v) share one handler but live in distinct slots (store vs counter as functor symbols).' Different sorts get distinct slots; different instances of the same sort collide. OK for singletons (one project per CLI invocation, global config, single counter); broken for tests exercising multiple isolated stores, multi-tenant servers, or any composition where two ops want independent state of the same sort. Three design directions, each viable: (a) Identity-by-field — sort declares which entity field is the instance identifier; cells key by (functor, identity_value); minimal change but every multi-instance sort must designate an identity field. (b) Opaque resource handles — new `Value::Resource(uid)` variant; mkResource allocates a fresh uid per construction; cells key by uid; works for any sort but adds a value variant and resources stop printing structurally. (c) Per-instance handler scope — `with_handler(Modify, instance_handler) { ... }` lexically introduces a scoped handler owning one instance's state; matches algebraic-effects-handlers tradition; composes naturally; needs lexical handler-scoping construct that proposal 027 mentions but doesn't fully specify. Choosing (a) is least-invasive; (c) is most flexible; (b) is most general. Driver: documented as a limitation in proposal 036 §'Single-instance-per-functor limitation'; WI-192 v0.1 ships without addressing it (the bundle is single-instance). Becomes blocking when anthill-todo-server lands, or when tests want parallel-isolated fixtures, or when composition demands scoped state. Acceptance: pick one direction; implement; resource_key extension or new value variant or with_handler primitive; tests covering two coexisting wis instances with independent state.

### 2026-10-16T21:33:48Z — feedback — claude

STOPGAP IN PLACE (WI-20260908-9WVT7's fourth review, user 2026-10-16): since that review `anthill run` registers the standard Modify handler, and its one-slot-per-functor keying made `box(id: 1)` and `box(id: 2)` one place (written 10 and 20, the first read 20). `default_modify_handler` now REFUSES a resource built with fields — `EvalError::ResourceWithFields`, at run time, at the first `ModifyRuntime.get`/`set` on it, before anything is stored — and a read of a resource nothing set is `EvalError::ResourceUnset` (it was an internal evaluator error). Nullary resources and cells are unaffected. This ticket's fix (any of the three directions above) removes the refusal, and `eval_test::m5_modify_a_resource_with_fields_is_refused` then becomes the two-instance value row: 10 to `box(id: 1)`, 20 to `box(id: 2)`, each read back. The refusal is the handler's and not the typer's on purpose: the language admits `Modify[b]` on such a place, and a handler that keeps instances apart runs the program correctly.
