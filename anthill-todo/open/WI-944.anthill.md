## Description

`fact Ring[Float]` is an UNBACKED provision: nothing implements Ring's members at Float, on any route.

MEASURED 2026-08-02 during WI-942, and pinned by vec3_ops_test::control_ring_now_loads_and_its_residual_failure_is_the_unbacked_provision, which asserts the CURRENT (defective) behaviour so it cannot be lost.

REPRO, with NO generics anywhere -- this is the control that attributes it:
  sort CR
    operation dbl(a: Float) -> Float = Ring.add(a, a)
  end
loads clean and dies at the call:
  operation has no body: anthill.prelude.algebra.Ring.add -- this is a
  typer-guaranteed invariant violation (should be unreachable).
The generic route (`dbl[T](a: T) -> T requires Ring[T]`) fails IDENTICALLY, which is how WI-942 established the cause is the provision and not generic consumption.

WHY. `rustland/anthill-stl/anthill/float.anthill:79` asserts `fact Ring[Float]`, naming Float as the provider of Ring[T = Float]. But `anthill.prelude.Float` declares no `add`/`sub`/`mul`/`zero`/`one` of its own -- its arithmetic comes from `Numeric`, a DIFFERENT spec -- so `spec_op_suppliers_for_carrier(Ring, Float, Ring.add, add)` finds nothing runnable. Five of Ring's five members are in this state.

THIS IS EXACTLY §8.7's WI-818 CLASS ('a rule is not backing') AT A HOST CARRIER: Ring's members are defined only by its law rules, which are not backing, and Float's host operation_map names no Ring member. WI-880 narrows the host-carrier exemption from the load-time backing check; whatever that check covers today, it did not cover this.

SECOND FINDING, and it may be the cheaper half: the error text claims 'this is a typer-guaranteed invariant violation (should be unreachable)' (rustland/anthill-core/src/eval/error.rs:167). It is plainly REACHABLE from four lines of ordinary user source. Either the invariant holds and this KB violates it (then the LOADER must refuse `fact Ring[Float]`), or it does not hold and the message is lying to the reader. Decide which; do not leave a message that tells a user their program is impossible.

OPTIONS, not prescribed: (a) make Float supply Ring's members (delegate to the Numeric/host ops, or a per-language operation_map entry); (b) delete `fact Ring[Float]` and re-express `VectorSpace requires Ring[F]` against a spec Float does provide; (c) leave the fact and make the LOAD refuse it. Note VectorSpace requires Ring[F] and `fact VectorSpace[Vec3, Float]` discharges that requirement TODAY -- so (b)/(c) must keep `anthill.geometry.Vec3`'s provision loading, which WI-935 delivered and vec3_ops_test drives.

ACCEPTANCE: `Ring.add(2.5, 2.5)` at Float either answers 5.0 or is REFUSED AT LOAD naming the unbacked member -- not certified-then-dead. Driven both ways; the WI-942 control test flipped to assert the new behaviour rather than deleted; `anthill.geometry.Vec3`'s VectorSpace provision still loads and `the_four_members_evaluate` still green. cargo-test green.

SOURCE: WI-942 (it was that ticket's CONTROL B; re-measuring it is what showed the Ring construct's residual failure is the provision, not the consumer).
