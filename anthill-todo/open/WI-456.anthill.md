THE SECOND CLAUSE IS ANSWERED AND THE ANSWER IS NO. "maybe local Eq should be derived from Ord?" is decided in proposal 058 §3.8's closing paragraph, by a stated predicate rather than by taste: derive the provision for a required floor IFF the upper floor's laws determine that floor's surface AND the floor is SELECTABLE. PartialOrd qualifies (Ord's laws derive gt/lt/gte/lte from compare, and WI-876 already gives that derivation real default bodies); Eq does NOT — §3.7 makes the Eq family permanently coherent, one supplier per carrier, because equality dispatches from UNIFICATION and no call site exists at which to select. A derived Eq would be a second provider, which AmbiguousEqDispatch (WI-837) refuses at load. So Ord requires Eq stays a REQUIREMENT, not a derivation, and compare_eq stays a LAW (a rule is not backing — WI-818). NOTE FOR WHOEVER TAKES THIS: that answer currently lives ONLY in the proposal — neither eq.anthill nor ordered.anthill states it at the declaration a reader would consult.

WHAT REMAINS, on the reading that "(Persistent version)" means the PersistentCollection PROVISION: SortedSet provides no Iterable / FiniteCollection / PersistentCollection, so no generic container consumer takes one — toList at the boundary. Sibling state, which argues this is library-wide rather than a SortedSet hole: Set provides none of them either; List / Map / MutableStack / FiniteStream and the stream carriers do.

MEASURED — WRONG, and wrong in the direction that matters:

 (1) THE DECLARATION IS NOT BLOCKED. provides PersistentCollection[C = SSet[T = T, O = O], Element = T] together with provides Iterable[C = SSet[T = T, O = O], Element = T, E = {}] and operation iterator(s) = toList(s), on a sort whose requirement slot is NAMED, LOADS CLEAN. (Without the Iterable provision it is the ordinary missing-provision refusal: "provides PersistentCollection, which requires Iterable, but does not provide Iterable" — plumbing, not a wall.)

 (2) AND IT RUNS. Monomorphic consumption through the spec op, with ONE Ord provider for the element: SSet[T = Int64, O = Int64], insert 7 then 3, reads back 3. The ordering genuinely threads through the provision.

 (3) WHAT BREAKS IS THE PROGRAM THE TYPE EXISTS FOR — two rival orderings in scope. Dispatching MyColl.insert on SSet[T = String, O = ByLength] is refused: "ambiguous dispatch ... 3 instances provide anthill.prelude.Ord (String, ByLength, Alphabetical) and the call selects none. The tie is in a SUB-GOAL of this call's resolution, which no call-site bracket reaches (§4.5)". It is refused MONOMORPHICALLY — carrier written out in full, ordering and all — so the erasure belongs to the SPEC-OP INDIRECTION, not to the abstract carrier. The generic-consumer form fails on the same root ("constructing Ord[T = String] is ambiguous among providers"), and the CONTROL separates the cause: the identical generic consumer over an UNCONDITIONED provider (a Bag with no requirement slot) loads and runs, so it is the provision's CONDITION that has no channel, not the container-spec plumbing.

 (4) SEPARATE DEFECT, FOUND BY TAKING THE DIAGNOSTIC'S OWN ADVICE — THE §4.5 MESSAGE NAMES A REPAIR THE NEXT CHECK REFUSES. It says: "give the conditional provider a NAMED requirement slot and bind it in the value position (f[Spec = W[Slot = Chosen]])". SSet ALREADY has the named slot, and writing the bracket — MyColl.insert[MyColl = SSet[T = String, O = ByLength]](c, x) — is refused by a different check: "expected no explicit witness — this dispatch is value-directed ... SSet is a CONCRETE provider of MyColl — its values carry their own sort, so the dispatch is already directed by the value and an explicit [MyColl = SSet] cannot change it". For a CONCRETE provider the first repair is inapplicable; the only escape actually offered is the second one, "keep a single provider of Ord". Two checks disagreeing about what the author should do.

SO THE SHAPE OF THE WORK, for whoever claims this. The provisions are a handful of lines and work TODAY wherever the element has one Ord provider — which is most programs. Landing them without touching §4.5 would give SortedSet a generic-container surface that is refused in exactly the two-ordering programs SortedSet was built for. Three separable pieces, and they should be decided before code: (a) land the provisions with the limitation recorded at the declaration; (b) give the §4.5 sub-goal tie a channel, which is the real feature and is not this ticket's size; (c) at minimum fix the diagnostic in (4) so it stops naming a repair a concrete provider cannot take. Probe source (7 shapes, reconstructible) is not committed — it asserted nothing, it only reported, and a no-assertion test is not one this repo keeps.
