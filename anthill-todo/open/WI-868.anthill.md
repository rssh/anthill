## Description

WI-857 FOLLOW-UP (design question, depends on the runtime marker payload) — TWO coexisting representations of 'this slot has no evidence', and the refusal ordering is what keeps them apart. WI-857 left two: (a) ResolvedRequiresNode::Unavailable -> an empty bundle over the anthill.reflect.NoProvider marker, which resolve_op_target_checked REFUSES to dispatch through; (b) stand_in_requirement (eval/mod.rs), the host-entry stand-in, whose sub-slots are markers but whose OWN functor is a claim that e.g. Main provides WorkItemStore — a claim call_with_requirements' own doc already calls 'wrong impl, runtime mis-dispatch'. They cannot be unified TODAY because the marker refusal sits at resolve_op_target_checked, i.e. BEFORE the WI-350/WI-822 value-directed rescue that is exactly what makes the stand-in work: a stand-in dispatches onto the spec's own op, which for a bodyless spec op resolves the impl from the RUNTIME VALUE and gets the right answer (pinned by wi818_executable_backing_test::variant_b_carrier_impl_loads_and_evaluates, which MEASURED this — it failed when the stand-in was not layout-valid). If the refusal moved to AFTER the rescue fails, ONE representation would serve both: a marker functor would mean 'this dictionary pins nothing; let the value decide, and be loud if it cannot'. THE OPEN QUESTION is whether that is sound: the rescue is sound when it finds a carrier member, but when the spec op is a BUILTIN (PartialEq.eq, Ordered.compare) falling through runs the HOST default and decides structurally — which is the silent-wrong-answer case the refusal exists to prevent. So the move probably needs to distinguish 'the spec op is builtin-backed' from 'the spec op is bodyless and value-directable', and that distinction should be measured, not assumed. DEPENDS on carrying the marker's payload to runtime (the arena-slot variant), since a merged representation must still say WHY it pinned nothing. ACCEPTANCE: either one representation with a measured account of the builtin case, or a written decision that the two stay separate, recorded where stand_in_requirement is defined.
