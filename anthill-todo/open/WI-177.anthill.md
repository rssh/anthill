## Description

KB mutation epoch for proof-cache invalidation. Proposal 030 phase alpha is landed: rustland/anthill-cli/src/prove.rs:70 writes ProofRecord.state_hash via rustland/anthill-smt-gen/src/cache/key.rs:79. Today state_hash is recomputed from scratch by walking visited_rules and their referenced functors over the whole KB on every prove --check / cite resolution. Correct, but O(visited * kb_size) per record. With WI-175 enabling routine retract from interpreted anthill code (claim/deliver/verify/update on every anthill-todo invocation after WI-009), the proof-cache check path becomes hot. Required primitive: monotonic kb.epoch: u64 bumped on every assert_rule / assert_fact / retract, plus optional per-functor kb.functor_epoch(sym) for fine-grained invalidation. ProofRecord caches an (epoch, state_hash) pair; on access, if kb.epoch() matches cached_epoch (or every relevant functor_epoch matches) skip recomputation, otherwise recompute and compare. Brings the no-mutation case to O(1). Out of scope: changing the state_hash algorithm; persisting epochs across processes (epochs are in-memory; on KB reload the persistence layer round-trips ProofRecord.state_hash, which already covers cross-process correctness). Acceptance: kb.epoch() exists and bumps on each mutation; existing prove_cache_test still passes; new test asserts mutation-free second check skips recomputation (instrumentation counter shows zero state_hash recomputations on a hot cache). Correctness unchanged; this is a perf optimization. Design: see examples/github-todo/docs/anthill-migration.md section 6.
