## Description

DIAGNOSTICS: a materialized rule-body node can still be reported at another site's (or another file's) span — what is LEFT of WI-458's "shared subterm" half, rewritten 2026-10-04 against the code at d49fd0b6 (most of the original ticket has since been delivered by others).

WHY IT HAPPENS. `materialize_from_handle*` (kb/node_occurrence.rs) rebuilds a `NodeOccurrence` from a stored, HASH-CONSED term, and locates each node it builds by `TermId`. Two sources answer that lookup: a caller-supplied per-atom table, and, when the table has no entry or none is passed, `kb.term_span(t)` — keyed by the shared `TermId` and filled first-write-wins, so a node structurally identical to one seen first ELSEWHERE (a bare `Ref(x)`, a `Const`, any repeated subterm) inherits that first site's span, possibly in another file.

ALREADY FIXED — not this ticket's any more:
- `build_expr_leaf` takes its span as a parameter from the parse node (WI-20260819-33H3P); it no longer reads `kb.term_span`.
- A rule-body atom passes a per-atom span table (`parse_span_table`, WI-1039) to `materialize_from_handle_spanned`, so its nodes are located in their own file.
- Entity constructors (WI-20260902-2SZ88) and the three collection literals (WI-20260902-2NXAC) are built from the PARSE node, not materialized, so they no longer take this path at all.

WHAT IS LEFT — each to be DRIVEN first (a fixture whose diagnostic lands on the wrong site), then fixed or closed with the reason at its site:
1. THE REMAINING EARLY-RETURN FORMS. `build_body_atom_occurrence`'s reflect-form early return still materializes ~92 nodes: `dot_apply` (49) and the control-flow forms, whose arms live in `visit_fn`. They reach a rule body only as reflection PATTERNS. They do get the per-atom table, so the residue is (2).
2. IDENTICAL SIBLINGS INSIDE ONE ATOM share one table entry (the key is hash-consed), so `x.m(y.n(), y.n())` reports both `y.n()` at the first one's offset. The fix recorded at `materialize_from_handle_spanned`'s doc: carry the PARSE `TermId` beside the KB one in `WorkOp::Visit` and read the parse span directly — no hash-cons collision, at the cost of a parse-IR dependency in node_occurrence.rs. Decide whether that is wanted; if not, record why at the site and drop this item.
3. FOUR UNSPANNED CALLERS in kb/load.rs pass no table, so every node they build falls back to the first-write-wins `kb.term_span`:
   - `visit_load` (the `materialize_from_handle(self.kb, kb_id)` after `create_occurrence`) — the term was just stamped for THIS parse id, but first-write-wins keeps an earlier site's stamp for a shared term;
   - `lower_effect_row_aux_occ` — an effect-row binding inside the rule-body child loops: no table, so its nodes lose spans entirely or take a foreign one;
   - `cons_spine_expr` — the tail cells of a cons spine;
   - `entity_ctor_children`, an INVENTED slot (`complete_named_slots`'s fresh var or WI-716's `none()`) — a leaf with no parse node, documented at the site as harmless; confirm and leave.
   `bare_entity_goal_occurrence` passes a table that stamps nothing (a synthesized term no `term_map` key reaches; recorded at its site) — confirm its diagnostics are located some other way or say so there.

ACCEPTANCE: for each item, either a row in a test file that FAILS when its fix is backed out (a diagnostic located at the wrong line/file before, the right one after), or a sentence at the site saying why the item cannot be reached or does not matter. cargo-test via rustland/scripts/test.sh.
