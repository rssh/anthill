## Description

DIAGNOSTICS: a materialized rule-body node can still be reported at another site's (or another file's) span — what is LEFT of WI-458's "shared subterm" half, rewritten 2026-10-04 against the code at d49fd0b6 (most of the original ticket has since been delivered by others).

WHY IT HAPPENS. `materialize_from_handle*` (kb/node_occurrence.rs) rebuilds a `NodeOccurrence` from a stored, HASH-CONSED term, and locates each node it builds by `TermId`. Two sources answer that lookup: a caller-supplied per-atom table, and, when the table has no entry or none is passed, `kb.term_span(t)` — keyed by the shared `TermId` and filled first-write-wins, so a node structurally identical to one seen first ELSEWHERE (a bare `Ref(x)`, a `Const`, any repeated subterm) inherits that first site's span, possibly in another file.

ALREADY FIXED — not this ticket's any more:
- `build_expr_leaf` takes its span as a parameter from the parse node (WI-20260819-33H3P); it no longer reads `kb.term_span`.
- A rule-body atom passes a per-atom span table (`parse_span_table`, WI-1039) to `materialize_from_handle_spanned`, so its nodes are located in their own file.
- Entity constructors (WI-20260902-2SZ88) and the three collection literals (WI-20260902-2NXAC) are built from the PARSE node, not materialized, so they no longer take this path at all.

THE SOLUTION: ELIMINATE THE node → TermId → node ROUND TRIP. Every remaining defect has one cause: an occurrence the loader already had (or could build) from the PARSE node is lowered to a hash-consed `TermId` and then re-materialized from it, so its location has to be looked up by a key that many sites share. Patching the lookup (a better table, threading the parse `TermId` beside the KB one through `WorkOp::Visit`) keeps the round trip and its failure class. Build each occurrence natively from its parse node instead, as 2SZ88 (entity constructors) and 2NXAC (collection literals) already do — then there is no lookup to get wrong, and identical siblings (`x.m(y.n(), y.n())`) are two parse nodes with two spans by construction. This is the CLAUDE.md representation note applied: hash-consing is a storage optimization for persistent shared structure, not the identity of a source occurrence.

THE ROUND-TRIP SITES TO REMOVE (kb/load.rs unless noted), each DRIVEN first by a fixture whose diagnostic lands on the wrong site:
1. `build_body_atom_occurrence`'s reflect-form EARLY RETURN → `materialize_from_handle_spanned` — the ~92 nodes still taking it: `dot_apply` (49) and the control-flow forms (arms in node_occurrence.rs `visit_fn`), reached in a rule body as reflection patterns. Needs native builders for those shapes; then the per-atom tables (`parse_span_table`, `parse_dot_chain_table`) and `materialize_from_handle_spanned`'s `spans` / `dot_chains` parameters become dead and are deleted with it.
2. `visit_load` — `materialize_from_handle(self.kb, kb_id)` right after `create_occurrence(parse_id, kb_id)`: the parse id is in hand; build from it.
3. `lower_effect_row_aux_occ` — an effect-row binding inside the rule-body child loops; build from `pid`.
4. `cons_spine_expr` — the tail cells of a cons spine; build each cell from its parse node.
NOT round trips, and stay: `entity_ctor_children`'s INVENTED slot (a fresh var or WI-716's `none()` — a synthesized leaf with no parse node, so materializing the term IS its content) and `bare_entity_goal_occurrence` (a synthesized term no parse node maps to). Each keeps a sentence at its site saying so, and says how its diagnostics are located.

Once the load path has no round trip left, re-ask what `kb.term_spans` still serves; the readers that only existed to locate re-materialized occurrences go with it, and any that remain say at the site why a first-write-wins, hash-consed key is right for them.

ACCEPTANCE: no `materialize_from_handle*` call remains on the loader's occurrence path except the two synthesized cases above; a test row per removed site that FAILS when it is backed out (a diagnostic at the wrong line or file before, the right one after) — including `x.m(y.n(), y.n())` reporting each `y.n()` at its own offset; cargo-test via rustland/scripts/test.sh.
