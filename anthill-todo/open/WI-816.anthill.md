## Description

DECIDE the fate of the requirement-carrying `*Within` IR variants that NO producer builds, with `Expr::LambdaWithin` as the worked case: DELETE as superseded, or IMPLEMENT. DEFINITION -- what lambda_within is FOR. `entity lambda_within(param: Pattern, body: NodeOccurrence, requirements: List[NodeOccurrence])` (stdlib/anthill/reflect/reflect.anthill) is the requirement-carrying twin of `lambda_expr`: the BINDER-shaped peer of `apply_within`. Under the WI-237 NAMES model a callee reads its dispatching dictionaries BY NAME out of `frame.requirements` via `var_ref(__req_*)`; `apply_within` carries the list holding that dictionary at a CALL site, and `lambda_within` was to carry it at a LAMBDA site -- a lambda whose body calls a spec op must have the dictionaries available in the frame its closure pushes, and `requirements` is where they would ride (docs/design/operation-call-model.md, "The IR"). PROBLEM -- it is built NOWHERE in EITHER carrier, and the problem it names is ALREADY SOLVED ANOTHER WAY. Measured across the workspace: nothing constructs `Expr::LambdaWithin`; nothing allocs a `Fn{anthill.reflect.Expr.lambda_within}` term; and `eval::ReflectSyms.lambda_within` (eval/mod.rs:132, :175) resolves the symbol and is then NEVER READ. What makes the variant unnecessary is WI-223 choosing a DIFFERENT mechanism: `reduce_lambda` (eval/eval.rs:773-798) SNAPSHOTS the enclosing `frame.requirements` (and `type_args`, WI-272) into `Closure.requirements` (eval/closure.rs) at lambda-CONSTRUCTION time and restores them on invocation, preserving the lexical scope where the lambda was CREATED rather than where it is INVOKED (operation-call-model.md, "Closure invocation: the one runtime exception"). So a spec-op call inside a lambda body ALREADY gets its dictionaries -- the CLOSURE VALUE carries them and the IR node is not needed. STATE THIS PLAINLY: this ticket does NOT report a broken program. Calling it "unimplemented" would predict a failure nobody can reproduce; it is SUPERSEDED, and the open question is whether that supersession should be finished or reversed. THE COST OF LEAVING IT is paid at every walker, each handling a variant no producer builds and therefore untestable against one: `for_each_child` / `drain_pattern_children` (node_occurrence.rs), the DeBruijn open/close pair, `substitute_occurrence`, `simp_rewrite::reassemble`, `persistence/print.rs`, anthill-smt-gen's cache key, anthill-cpp-gen's reject arm, the typer's `Lambda|LambdaWithin` param read (typing.rs), eval's reject arm, and load.rs's describe. WI-814 hit this directly: it gave `Lambda` the term-twin head its loader twin already had but left `LambdaWithin` `Opaque`, on the stated ground that a twin written against no producer could not be tested against one -- so the dead variant now also costs an asymmetry in `occ_head`. SIBLINGS, same status, decide together: `HoApplyWithin` and `ConstructorWithin` are likewise constructed nowhere and referenced only by the same walker / reject arms. `ApplyWithin` is DIFFERENT and must NOT be swept in: its TERM side is LIVE -- `req_insertion` (WI-231) does rewrite a classified call to `Fn{Expr.apply_within, ...}` into `kb.dispatch_rewrites` (`record_apply_within_concrete`, typing.rs) -- but the OCCURRENCE stays `Expr::Apply` carrying its `CallClass`, which is what the runtime reads post-WI-248 ("the term-keyed redirect is now diagnostic-only"), so `Expr::ApplyWithin` is reached only by reading such a term BACK through `visit_fn`. DECIDE, do not assume: (a) DELETE `LambdaWithin` / `HoApplyWithin` / `ConstructorWithin`, their reflect declarations, the dead `eval::ReflectSyms` field and every walker arm -- if the closure-snapshot mechanism is the settled design, in which case SAY SO at `reduce_lambda`, which is then the SOLE carrier of a lambda's requirement scope and should not be silently re-derivable; or (b) IMPLEMENT it -- `req_insertion` would have to visit LAMBDA sites and not only Apply sites, and the ticket must then say what `lambda_within` gives that `Closure.requirements` does not. The leading candidate for (b), and the only one found: a requirement scope decided at TYPE time and visible to REFLECTION / CODEGEN rather than one materialized only at eval time -- anthill-cpp-gen currently REJECTS the variant, so a codegen backend needing a lambda's dictionaries STATICALLY is the case that would justify keeping it. ACCEPTANCE: the decision is recorded WITH ITS REASON; if (a), the variants and every arm handling them are deleted and the suite is green with no `LambdaWithin` left in the workspace; if (b), `req_insertion` emits it, a test drives a spec-op call inside a lambda body through the new IR, and `occ_head` gains the twin head WI-814 declined to write. Either way `eval::ReflectSyms.lambda_within` stops being a resolved-but-unread field. Full workspace green via rustland/scripts/test.sh.

BETTER STATEMENT OF THE PROBLEM (supersedes the framing in the description; user correction). The description leans on "nothing constructs it" and treats the question as delete-vs-implement. The sharper framing: requirements are SIGNATURE data analysed at COMPILE time -- spec-level `requires` per kernel-language.md:907, which is the sort-level SPEC DEPENDENCY and is DISTINCT from the operation-level `requires <RuleBody>` PRECONDITION (:1023, :1034; do not conflate them). For EVERY operation the typer derives the SET OF USED REQUIRES from the body, and a LAMBDA BODY IS NO DIFFERENT -- the same classification runs inside it (`for_each_child` descends `Expr::Lambda`, so `req_insertion::collect_classified` sees nested spec-op calls; MEASURED: an uncovered call inside a lambda raises MissingRequiresForSpecOp with the span on the NESTED call, two binders deep, and does not over-fire). So the analysis is UNIFORM and a requirement channel on the `Function` TYPE is NOT what is missing: the derived set attaches to the CODE, not the type. THE ASYMMETRY THAT IS REAL is the BINDING TIME of that set: an OPERATION has its requirements supplied BY THE CALLER, per call (the uniform rule, operation-call-model.md:805, `callee.frame.requirements = caller.apply_within.requirements`), so a recursive call with a DIFFERENT type argument supplies a DIFFERENT instance; a LAMBDA has them supplied by its CREATOR, ONCE (`reduce_lambda` snapshots `frame.requirements` into `Closure.requirements`; the doc calls this "the only place the uniform rule is overridden"). Same analysis, different binding time -- and NOTHING justifies the difference. CONSEQUENCE, the case that decides the design: MUTUAL RECURSION IN WHICH A REQUIREMENT CHANGES TO THE TYPE-ARGUMENT TYPE. Each step needs a different instance. Per-call resolution delivers that; resolve-once cannot. So the case is EXPRESSIBLE AS AN OPERATION AND INEXPRESSIBLE AS A LAMBDA -- lambdas are SECOND-CLASS with respect to requirements. It is also the case that cannot be closed by compile-time resolution alone: the set of needed instances is unbounded, so `CallClass::PinNow` is unreachable (there is no single instance to pin) and only `DeferToRequirement` can serve. THIS REFRAMES OPTION (b): `lambda_within` is not an exotic feature, it is the lambda's DERIVED REQUIREMENT SET MADE EXPLICIT IN THE IR, instead of recovered at run time by copying the whole enclosing frame. Note the snapshot is also IMPRECISE -- `frame.requirements` wholesale rather than the set the body uses. Harmless for execution (the body reads by name via `var_ref(__req_*)`), but it is why anthill-cpp-gen can do nothing with the variant and REJECTS it: there is no static record of which dictionaries a given closure needs. THREE OPTIONS, and the language must pick rather than land on one by accident: (1) REJECT -- keep requirements fully compile-time-resolvable and DIAGNOSE the varying-instance recursion as unresolvable (what a monomorphising compiler does); (2) DEFER -- accept `DeferToRequirement` as the general case, which requires the derived set to travel WITH the closure, which is `lambda_within`; (3) TODAY -- neither, decided by accident: capture works when the creating scope happens to know the instance, and the cases needing a varying dictionary are NOT EXPRESSIBLE RATHER THAN DIAGNOSED. Option (3) is the current state and is the actual defect. Whatever is chosen, the lexical-capture RULE ITSELF is correct and must stay for the monomorphic case -- the body is type-checked in the creation scope, so running it against a callee's dictionaries would execute code against dictionaries it was never checked against; MEASURED: a closure built under one spec evaluates correctly when invoked by a callee that cannot even NAME its spec op. STILL UNVERIFIED, do not treat as fact: an agent reported that `requires` on a sort makes its operations untrappable at eval (`DeferToRequirement: projection index 0 out of range`); a hand reproduction produced a DIFFERENT error (`UnknownOperation`) on a differently-shaped program, so the claim is NOT established and needs its own reproduction before it is filed or relied on here.
