## Description

Grammar+typer: ADMIT TERM/CALL forms in a TYPE-ARGUMENT slot -- computed type args (List[T = f(x)], Function[B = result_type(br)]) and CALL-VALUED value-in-type indices (Modify[f(x)], Modify[c.foo(x)]). GAP: _common_type_expr (tree-sitter-anthill/grammar.js ~147) admits _type | int/float/string/bool literal | effect_row but NOT _expr/fn_term/a call, so a call where a type-arg value is expected is ungrammatical (parse rejects it). Grammar comment: 'Calls (Modify[f(x)]) are reduce-tier and deferred until the typer has a reduction hook.' This is the WI-302 deferred item #1 (calls in a type-arg slot don't parse) and the dual of WI-301 (effect-set-in-type-arg, REJECTED -- rows parse now). WHY HARD (validated by WI-311): admitting a call/field_access form as the type-arg-slot/application base CASCADES type/term grammar conflicts -- WI-311 measured 'field_access's _atom_term receiver CASCADES type/term conflicts ([_atom_term,application]->[_atom_term,_type]->[_atom_term,_effect_type]->...)'. WI-311 therefore did STEP 1 only (parameterized_type+instantiation_term -> one 'application' rule, dotted $.name base) and DEFERRED the rest. This ticket IS that deferred 'FULL type/term conversion' -- the part that admits a term/call where a type is expected, LOADER classifying (sort_ref vs denoted vs application vs computed-redex). DESIGN DECISION REQUIRED FIRST (do not just implement): this REVERSES the project's current 'loader-classifies, no CFG-level types-are-terms' stance. WI-311 was closed partly because 'CLAUDE.md's representation note walked back the types-are-terms-at-CFG-level motivation', and WI-302 (value-in-type denoted) + WI-311 (application merge) both doubled down on loader-classification of forms that ALREADY parse. Admitting calls needs EITHER (i) the full type/term CFG unification (route every term/call through shared rules, loader classifies -- the conflict-cascading path WI-311 validated; contradicts the walked-back motivation = a real direction change), OR (ii) a NARROWER targeted widening of just the type-arg-value slot to accept a call/expr if it can be done conflict-free. Pick one. NO ACTIVE DRIVER today: the original computed-call driver (typing_pass_spec Function[B=result_type(br)] / List[T=...apply_subst...]) was SIDESTEPPED by WI-308 (rewrite to explicit Type constructors), and WI-301 was rejected -- so this is a future/speculative capability; file-and-park until a real consumer needs it. REPRESENTATION: a CALL-VALUED index rides as Type.denoted(value: <call-occurrence>) (WI-302's denoted carrying a redex, not a field-path); a COMPUTED-TYPE arg (List[T=f(x)] where f(x) evaluates to a Type) additionally needs the typer ELABORATION hook = denoted->concrete-Type REDUCTION (evaluate the redex to a type) -- the genuine 'reduction' deferral, distinct from value-in-type which indexes opaquely and never reduces. SCOPE: grammar (grammar.js type-arg-value slot / application base + precedence; corpus rebaseline) + converter (parse/convert.rs) + loader classification (load.rs type_expr_to_child) + optionally the typer reduction hook for computed-type args. BUILDS ON WI-311 (application merge, delivered). RELATED: WI-302 (denoted, delivered), WI-303 (parse-error substrate), WI-301 (effect-set-in-type-arg, rejected). ACCEPTANCE: record a design decision FIRST (CFG-unification vs targeted widening); then Modify[f(x)] / List[T=f(x)] parse (0 errors) and load (call-valued -> denoted redex; computed-type -> reduced or denoted), full suite green.
