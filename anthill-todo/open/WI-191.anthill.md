## Description

CLI spec → typed args. Today every cmd_X operation receives `bindings: List[Binding]` and re-extracts each parameter via `get_binding(bindings, "name")` + nested Option matches + (for repeatable flags) `collect_all_bindings`. The OperationSpec already declares param names + kinds + types — the typed args entity can be derived. Surface: `spec_add` declares params; the loader emits a synthetic entity `AddArgs(description: String, depends: List[String] = [], acceptance: List[ToolPasses] = [ToolPasses("cargo-test")])`; cmd_add is rewritten to take `a: AddArgs` and use `a.description` / `a.depends` directly. parse_argv elaborates argv into AddArgs instead of List[Binding]; positional / flag / bool_flag kinds map to single-value / list-or-single / Bool fields respectively. Default values live on the spec param declaration. Work: (a) extend ParamSpec with `default_value: Option[Term]` and a derived-args-entity flag; (b) loader: for each spec, synthesize an entity declaration matching the param shape; (c) parse_argv reshape: walk argv producing the synthetic-entity Value rather than List[Binding]; (d) bundle ports — cmd_X bodies switch from get_binding cascades to dotted field access; (e) tests: parser produces typed args matching declared param types; missing required positional becomes a typed error not a `none()` extraction. Acceptance: every existing cmd_X drops its get_binding / collect_all_bindings glue; cargo test green; bundle bytes shrink by an estimated ~40%. Independent of WI-189 in v1 (typed args are derived from spec at load time, not via runtime ↓ over a Bindings term — that is a possible v2 unification once brackets land).

Design direction 2026-06-19: defer the literal load-time entity synthesis (the WI v1); pursue the reflect-machinery route (the WI v2) instead. Nomenclature drift for future readers: the bundle glue is get_arg / collect_all_args / collect_all_args_acc (main.anthill), NOT the WI's get_binding/collect_all_bindings; Binding(name,value) lives in anthill.cli.parse, specs (OperationSpec/ParamSpec/ParamKind) in anthill.cli.spec. WHAT load-time entity synthesis meant: per command, derive a NEW entity sort from that command's DECLARED ParamSpec list (not from runtime argv) -- e.g. spec_add gives entity AddArgs(description: String, depends: List[String]=[], acceptance: List[ToolPasses]=[ToolPasses('cargo-test')], tag: List[String]=[]); mapping positional/required-flag to a single field, repeatable flag to a List field, bool_flag to Bool, defaults from a new ParamSpec.default_value; cmd_add would then take a: AddArgs and dot-access, and parse_argv would fill an AddArgs instance from argv. WHY it is the costly path (verified by exploration): specs are OPERATIONS (operation spec_add() returns OperationSpec), not declarations/facts, and the Rust loader does not eval operations; there is NO post-load API to inject a sort/entity DECLARATION into the KB -- load is a monolithic pipeline (scan-resolve-witness-typecheck) with no mid-stage injection hook (~500+ lines to add one). Workarounds are all heavy: (i) Interpreter::call on Main.specs at load, then hand-build TermIds + register_sort/register_entity_of per command -- tedious, brushes WI-348; (ii) move specs to fact OperationSpec(...) (the cheapest load-time variant; KB query API exists via rules_by_functor/query) but it still needs Rust to materialize the per-command types AND a two-phase load since the bundle text references AddArgs. Insertion point if ever revisited: main.rs between register_runtime and Main.main. REFLECT-MACHINERY route (preferred): build a generic accessor, do not synthesize types. Building blocks already exist and are WI-348-compliant (no missing Rust): term_field(t:Term,name) returns Option[Term], term_as_string, term_list_items, term_as_entity[E](t:Term) returns Option[E] (Term::Fn to a typed entity Value; already used by cmd_list_tagged/cmd_claim via facts_of), as_term[E], field_access(receiver:Value,field) returns Value (eval-side Entity field read), make_fn. WI-348 boundary: ALLOWED = TermView walking + value-level field reads (term_field/field_access/facts_of/as_term); FORBIDDEN = materializing Value to TermId from logic (reify_to_term retired); the reflect route stays inside this. TWO orthogonal wins to capture: (1) independent of reflect -- parse_argv ALREADY validates required params (check_required) before dispatch, so the case none() -> error branches on REQUIRED args in every cmd_X are dead code; a total arg(args,name) returns String (loud Error if absent, per the repo loud-over-silent principle) collapses each match get_arg none()/some into one 'let id = arg(args, id)'. Big mechanical shrink, no reflect needed. (2) reflect -- typed dotted access still needs the per-command shape to exist; cheapest is to hand-declare the ~15 small args entities in the bundle (far cheaper than load-time synthesis) plus a generic parse_into[E](spec, argv) returns E that builds the typed value from bindings via make_fn + term_as_entity[E], filling defaults from the spec; OR drop static dotting for a reflect accessor field[F](args,name) returns Option[F] (less typed, tiny). OPEN for next session: decide between true typed dotted access (hand-declared args entities + parse_into[E]) vs a generic reflect accessor + the dead-none() cleanup, judged against the WI ~40% shrink target. ### 2026-06-19T08:25:01Z — feedback — claude

Addendum 2026-06-19 (re: the dot-access macro). Confirmed the CONSUMPTION side, and it sharpens the recommendation rather than changing it: dot-access is NOT a way around declaring the per-command shape -- it is the consumer of it. ?x.field lowers in the converter to a dot_apply(?x, field, []) node (NOT desugared to apply, to avoid re-resolving through lexical scope), then the prelude [simp] rule rewrites it: dot_field: dot_apply(?x,?name,[]) = field_access(?x,?name) :- is_entity(min_sort(?x)), has_field(min_sort(?x), ?name) (proposal 043 sec 6.1-6.3; reflect.anthill:382 dot_apply entity + the field_access builtin at resolve.rs). The guard REQUIRES min_sort(?x) to be a DECLARED entity that HAS the named field, so a.description dispatches only if AddArgs is a real declared sort carrying that field; anonymous tuples are not is_entity, so they do NOT dot-dispatch. UPSHOT for the reflect route: this makes route (2) -- hand-declare the ~15 small args entities -- clearly DOMINANT over the generic field[F](args,name) accessor (route 2 alt). Once the entities exist, a.description is FREE via the existing dot_field rule: no new dispatch machinery, no import. The ONLY remaining work is PRODUCING the typed value: a generic parse_into[E](spec, argv) returns E built from bindings via make_fn + term_as_entity[E], defaults from spec. Bonus: method-call dot (?x.m(args)) also resolves via the default rule find_operation_on_sort(min_sort(?x), name) (043 sec 6.4), so arg-validation methods ON the args sort would dot-dispatch for free too. Net plan crystallizing for next session: (1) total arg(args,name) returns String to kill the dead none() branches (no reflect, independent win); (2) declare the per-command args entities + one generic parse_into[E]; dot reads are already handled by the existing macro. The earlier generic-accessor alternative is dominated and can be dropped.

### 2026-06-19T08:31:24Z — feedback — claude

Addendum 2026-06-19 (sort-specific dot-apply). Confirmed the dot-dispatch engine is LIVE, not just proposed: the typer rewrites every Expr::DotApply, and sort-specific [simp] dot rules already fire (typing.rs ~2336-2367 fires a sort-scoped dot rule at a DotApply or falls through to the default dot_field; simp_rewrite.rs is the engine; design doc simp-rewrite-design.md sec 7.1). So WI-191 can lean on the proposal-043 sec 6.3 extensibility lever: write a sort-specific dot rule on the args carrier instead of relying on the default dot_field (which needs declared fields via has_field). THE CRUX is result typing, and it splits the route cleanly. (A) Per-FIELD sort-specific rules with concrete names -- dot_apply(?a, description, []) = arg_str(?a) [simp]; dot_apply(?a, depends, []) = arg_list(?a, 'depends') [simp] -- give correct per-field types (String vs List[String]) because each RHS op has its own return type, BUT that is one rule per field, MORE verbose than just declaring the entity fields, so no win over route 2. (B) ONE GENERIC rule dot_apply(?a, ?name, []) = arg_field(?a, ?name) [simp] on the carrier is maximally DRY (no per-command anything; parse_argv emits a single carrier value), BUT arg_field has a SINGLE return type, so a.description:String and a.depends:List[String] cannot both hold -- the typing wall. Resolving (B) needs the result type sourced from OUTSIDE the runtime value: either a type-indexed arg_field[F] inferred from the EXPECTED type at each use site (bidirectional, fragile), or SPEC/TYPE-DIRECTED dot typing where the typer consults the param's declared kind/type for ?name at the dot site (the elegant endgame = the WI v2, real new typer work; note ParamSpec today carries NO type field, only kind, so it would need ParamSpec.type or a kind-to-type derivation). NET of the whole analysis: cheapest CORRECT landing is route 2 (declare per-command args entities + a generic parse_into[E]; the default dot_field rule handles reads, correctly typed, zero new dispatch rules). Route B (generic carrier + sort-specific dot rule + spec-directed result type) is the genuinely DRY endgame but its value rests on solving result-type sourcing -- that is the WI-191 v2 research item. RECOMMEND for the build session: ship route 2 first plus the dead-none() arg(args,name) returns String cleanup (independent win); keep Route B as v2 once spec-directed dot typing is scoped. Ticket stays OPEN.
