## Description

DERIVED PROVISIONS ARE ASSERTED IN A HASH ORDER, AND `Result`'S TWO DERIVED `NonEq` CLAUSES ARE NUMBERED EITHER WAY ROUND FROM RUN TO RUN — make what equality derivation writes into the KB the same on every load of the same sources. Found 2026-10-10/11 while taking WI-20261010-ANK4X's control (3); it is in the tree before that ticket as after it, and was not fixed there.

MEASURED (docs/measurements/test-infrastructure/provider-index-2026-10-10.txt §3). A temporary example printed every clause of `anthill.reflect.SortProvidesInfo` and `anthill.reflect.ProvidesConditionInfo` — rule id, fact or rule, head as source text — after the stdlib's own load (413 and 89 clauses), after a later load that derives, and for the stdlib and that file in one call (429 and 94 in both). The binary of main at 1312cc45 run six times, and the binary of ANK4X as delivered six times: (1) AS PRINTED, twelve different files — no two runs of either tree agree. The derived rows get their rule ids in another order at every run. (2) WITH RULE IDS DROPPED AND THE ROWS SORTED, four listings, the same four from each tree. The only rows that differ are `anthill.prelude.Result`'s two derived `NonEq` condition clauses, `:- NonEq[T]` and `:- NonEq[E]`: which is `clause: 4` and which `clause: 5` changes from run to run — in the stdlib's own load (and so in a later load into it), and separately in the one-call load. (3) WITH THE CLAUSE NUMBERS MASKED AS WELL, one listing for all twelve.

WHY, read off the code. (a) `eq_derive::composite_sorts` builds the list every derivation walks from `KnowledgeBase::entity_field_type_functors()`, which is `entity_field_types.keys()` — a `HashMap` with the standard per-process seed. `EqClassification.sorts` is in that order, and `derive_total_eq`, `derive_conditional_eq`, `eq_derive::run` and `derive_conditional_noneq` assert in it. (b) `KnowledgeBase::constructors_of_sort` collects a sort's constructors by walking `entity_parent`, also a `HashMap`; `derive_conditional_eq` builds a carrier's conditions constructor by constructor (`field_constructors_of_sort`), so `Result`'s — `ok(value: T)`, `err(error: E)` — come out as [T, E] or [E, T], `conditional_eq_params` keeps that order, and `derive_conditional_noneq` files one clause a parameter in it, each taking the next clause index. The comment at `derive_conditional_noneq` says the opposite: "Registration order, so the clause indices a program gets do not depend on a hash iteration order (they appear in `ProvidesConditionInfo` facts a test can read)" — true of neither the carriers' order nor a carrier's parameters'.

WHAT IT COSTS, as far as is known. NOT MEASURED to give a wrong answer: the same rows and the same conditions are derived at every run, and every suite is green. What varies is observable all the same — a `ProvisionConditions.clause` a reader groups by, the relation order of the derived rows (bucket order in the provider index is relation order, and a dispatch that takes the first of several candidates takes the first in it), the order of a refusal's lines, any dump of a KB — and a run cannot be reproduced byte for byte, which is what control (3) of ANK4X needed and had to do without. Whether any READER's answer depends on the order is part of this ticket to find out, not assumed either way.

WHAT TO BUILD. Both orders made a function of the sources. For (b), a sort's constructors in DECLARATION order: `sort_entities` already holds them as a `Vec` per sort (`sort_children`), where `constructors_of_sort` walks a map — to be checked that the two list the same symbols for every sort before one replaces the other (`constructors_of_sort`'s own comment, WI-697, says how its keys came to be what they are), and that no caller relies on the hash order by accident. For (a), the composites in an order of the sources' own — the order the field-type registry was filled in, or sorted by something stable (`sort_domain_derive::run` sorts by symbol index and says why) — whichever is the order a program's author would expect of its diagnostics. And the comment at `derive_conditional_noneq` made true or corrected. Survey, do not guess: every other `HashMap`/`HashSet` walk whose order reaches an ASSERT in the load's derivation passes (`type_value_derive`, `sort_domain_derive`, `derive_forwarded_provisions`, `fill_derive`), each either shown ordered or fixed with the two above.

THE CONTROL. Each `HashMap` takes a seed of its own, so two loads in ONE process already disagree — one run of the example made three loads and the four listings came from the pairs among them. So a test can load the same sources N times in a process and require ONE listing, rule ids and clause numbers in: for (a) that fails with near certainty when the fix is backed out (dozens of derived rows in a hash order); for (b) it is a coin a load, so N is chosen and said at the site (eight loads miss a back-out once in 128). Beside it a unit row that does not depend on luck once the fix is in: `Result`'s derived `NonEq` clause for `T` is the lower-numbered one, as its constructors are declared — a back-out fails it half the time, which is why it stands beside the N-load row and not instead of it. Across PROCESSES is the full statement, and what a dump is compared by; if the N-load row leaves doubt, the listing run from a spawned binary N times, as the CLI suites spawn theirs. Say at each row's site what fails when (a) and when (b) is backed out, measured over enough runs to say it.

DONE WHEN: the listing is the same on every load and every run, rule ids and clause numbers in, for the stdlib's own load, a later load that derives, and a one-call load; the survey of order-reaching-an-assert walks is written down with its verdict for each; the controls and their measured back-outs are in; the comment at `derive_conditional_noneq` says what the code does; the gate is green under all three recipes.
