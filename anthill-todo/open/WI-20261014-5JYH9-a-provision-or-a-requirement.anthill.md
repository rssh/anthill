## Description

A PROVISION OR A REQUIREMENT AT AN ARROW IS MATCHED WITHOUT ITS EFFECT ROW, SO A MEMBER DECLARED OVER A PURE FUNCTION RUNS ONE THAT WRITES TO THE CONSOLE. `sort Apply { sort F = ?  operation run(f: F) -> Int64 }`, `sort Q { provides Apply[F = (Int64) -> Int64]  operation run(f: (Int64) -> Int64) -> Int64 = f(41) }`, `operation via(f: (Int64) -> Int64 @ {ConsoleOutput}) -> Int64 effects ConsoleOutput = Apply.run(f)`, called from `main` with a lambda that prints and returns x + 1: loads, prints 'printed inside a pure member' and answers 42. The same through a requirement: `sort User { requires Apply[F = (Int64) -> Int64]  operation go(f: (Int64) -> Int64 @ {ConsoleOutput}) -> Int64 effects ConsoleOutput = Apply.run(f) }` prints and answers 42. CONTROL, measured: the same function passed to `operation pureRun(f: (Int64) -> Int64) -> Int64 = f(41)` is refused, 'the callback `f` declares `ConsoleOutput`, which the closed row does not admit'. MEASURED on bf21865f, each a lone provider at the first arrow answering a call at the second (40): `@ {Error[T = String]}` at `@ {Error[T = Int64]}`; `@ {Error[T = String]}` at a pure arrow; a pure arrow at `@ {ConsoleOutput}`; `@ {ConsoleOutput}` at `@ {Error[T = Int64]}`. The result is compared: a provider at `(Int64) -> String` is refused at `(Int64) -> Int64`. AND A PROVIDER'S PARAMETER INSIDE THE ROW IS HELD TO NOTHING: `sort P { sort A = ?  provides Apply[F = (A) -> A @ {Error[T = A]}]  operation run(f: (A) -> A @ {Error[T = A]}) -> Int64 = 30 }` answers a call at `(Int64) -> Int64 @ {Error[T = String]}`, `A` at Int64 and at String at once, on the tree before WI-20261013-34822 as well; that ticket's clause canon leaves an effect row as a type position holds it (a row's tail is a variable, which the member rule reads), so `A` in the row is its variable and nothing binds it. A requirement written there, `requires Mark[T = (A) -> A @ {Error[T = A]}]`, is supplied by a provider of `Mark` at `(Int64) -> Int64 @ {Error[T = Int64]}`. SPEC: kernel-language §5.2 ('A binding that is an arrow or a tuple is compared by its parts') says two arrows are one binding when their parameter lists relate and their results are the same; the row is not mentioned, so the measured verdicts follow its letter. MECHANISM: `arrow_part_pairs` (typing/tuples.rs) pairs the two rows, and `match_candidate_against_goal` (typing/candidates.rs) hands the pair to its leaf arm, `dispatch_values_match` (typing/carrier.rs), which accepted every pair above — which of its legs does is NOT TRACED; the cover of a requirement against a call (`parts_verdict`, dep_projection.rs) pairs arrows through the same function. The member rule and a direct call do compare rows. FOUND while WI-20261013-34822 was reviewed. TO DECIDE FIRST (spec §5.2, with the user): how two arrows' rows relate where a provision is looked up and a requirement is held against a call — one row (identity, as the result is compared), or the call's row conforming to the provision's, as a function is passed to a parameter typed by the provision's arrow (a provider at `@ {ConsoleOutput}` answering a call at a pure arrow, not the reverse); and with that, whether the lookup binds a provider's row parameter (`@ {R}`) and a type parameter inside a label (`Error[T = A]`). ACCEPTANCE: the two printing programs are refused at load, or answer under a relation that is sound by the families' P3; the four lone-provider programs and the label program are decided by the relation and recorded as rows; WI-20261013-0GYW1's, WI-20260929-12NKG's and WI-20261013-34822's rows stay as they are, or move as the decided relation says; the families run green on both carriers; full workspace green via rustland/scripts/test.sh.

## Changes

### 2026-10-14T09:57:28Z — feedback — user

DECIDED (user, 2026-10-14, asked with five programs): A — IDENTICAL ROWS. Where a provision at an arrow is looked up, and where a requirement at an arrow is held against a call, two arrows are one binding when their parameter lists relate, their results are the same AND their effect rows are the same row; a row is not compared by conformance (a pure call is not answered by a provider at @ {ConsoleOutput}), as a tuple with a component more is another binding though it conforms (§5.2). A provider that answers any row writes a row parameter (@ {R}), which the lookup binds to the call's row exactly, and its requires and conditions are read at that row; a type parameter inside a label (Error[T = A]) is bound and held to one type as elsewhere. Consequences, from the examples: Q at (Int64) -> Int64 no longer answers a call at @ {ConsoleOutput} (the printing program is refused at load); Logger at @ {ConsoleOutput} no longer answers a pure call; Q and Logger together are two bindings, no tie (each call answered by its own); AnyRow's requires Mark[T = (Int64) -> Int64 @ {R}] is asked at the call's row; P at (A) -> A @ {Error[T = A]} is refused at @ {Error[T = String]} and at a pure arrow, answers at @ {Error[T = Int64]}. Spec §5.2 to say so. The stdlib writes no provision or requirement at an arrow (grep), so no library clause moves.
