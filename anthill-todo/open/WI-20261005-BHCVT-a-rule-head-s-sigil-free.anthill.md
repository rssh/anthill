## Description

A RULE HEAD'S SIGIL-FREE PARAMETER BOUND IS NEVER FITTED AGAINST ITS SORT'S PARAMETERS, SO A TYPO THERE IS A DEAD CLAUSE: over `sort Buf { sort T = ?  sort N = ?  entity buf(v: T) }` and `fact q(buf(v: 1))`, `rule p(x: Buf[W = Int64]) :- q(x)` loads clean and `p` answers NOTHING, where the bound `Buf[T = Int64]` answers `buf(v: 1)` (MEASURED; `Buf[T = String]` answers nothing, as it should). The sigil spelling of the same head is refused where it is written: `rule p(?x: Buf[W = Int64]) :- true` — "`Buf` has no type parameter named 'W' — it declares type parameter(s) T, N". An over-application is the same: `x: Buf[Int64, 3, Bool]` loads, `?x: Buf[Int64, 3, Bool]` is refused as over-applied. kernel-language §5.3 ("The parameter form", proposal 060 §2.1) says `name: Type` is the same rule as `?name: Type` and that the written type may be a parameterized application, "the same three the `?x: T` spelling accepts, since the two lower to one internal form"; here one spelling is refused and the other loads and silently matches nothing. CAUSE: `convert_rule_head_with_params_inner` (kb/load.rs) converts an APPLIED bound with `convert_term` — its comment: "Converted as a TERM, so it passes none of the doors that lower a written type — and needs none" — and the term path's own argument check (WI-710, in `convert_term_inner`) is gated on `term_depth > 1`, because a top-level bracketed term is an instance claim; the bound is converted at depth 1, so nothing fits its arguments. The `?x: T` form lowers its annotation as a `TypeExpr` (`type_expr_to_child`), which does (`Loader::type_application_keys`, WI-20260929-AAQT5). FOUND while delivering WI-20260929-AAQT5 (its /code-review probes), PRE-EXISTING, not caused by it. FIX: a rule-head bound is a TYPE position — fit its arguments by the one reading the type lowerings use (`KnowledgeBase::type_arg_owner` + `fit_type_args`: the arguments bind the sort's parameters, and one that binds nothing is refused where it is written and not built), keeping the bound a term (it is installed as one, `rule_head_type_bounds`, and a head-introduced type variable inside it resolves through `rule_head_bound_alias`). A bound nested one level down (`x: List[T = Buf[W = Int64]]`) is already caught by WI-710's check: see that the two reports do not double. ADJACENT, NOT THIS TICKET'S ACCEPTANCE, recorded so the reader of that gate has it: WI-710's nested check asks `kind_of == Sort`, so a bracket on any other head in a data term is not read at all — `fact tagged(1, Option.some[Zork = Int64])`, `rule r(?x) :- tagged(?x, Option.some[Zork = Int64])`, `fact tagged(1, g[Zork = Int64])` (`g` an operation) and an operation's `requires Eq[T = Option.some[Zork = Int64]]` each load clean, where the same argument on a sort head (`Buf[W = Int64]`) is refused in each of those positions (MEASURED). What a bracket on a constructor or an operation MEANS in a data term is not written down — in an operation body `Option.some[T = Int64]` is a value of `Option`, not a type (`-> Type = Option.some[T = Int64]` is refused "expected Type, got Option") — so that is a question for the user before it is a defect. ACCEPTANCE: `rule p(x: Buf[W = Int64]) :- true` and `rule p(x: Buf[Int64, 3, Bool]) :- true` are refused where they are written, with the sigil spelling's message, each once; the well-formed bound still loads and still filters (`x: Buf[T = Int64]` answers `buf(v: 1)`, `x: Buf[T = String]` answers nothing — driven, not "it loads"); a head-introduced type variable inside an applied bound (`rule g[A](x: List[T = A]) :- …, Spec[A]`) still resolves; full workspace green via rustland/scripts/test.sh; scaland — run the same two heads through its loader and report what it does.
