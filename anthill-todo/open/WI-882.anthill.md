## description

THE STDLIB'S 11 DENIAL CONSTRAINTS ARE INERT, AND `kernel-language.md` §8.4 PROMISES THEY ARE NOT — decide which way the divergence resolves, then make the stdlib say it once in a channel that fires. FOUND by a user question: 'I see constraint statement in Float. Where is constraint described in kernel-language.md?', followed by 'we have precondition in operations and can use preconditions directly. Or error effect if x < 0 (as div)'. Both halves of that turned out to be exactly right. WHAT THE SPEC SAYS. `constraint` is documented in three places and they agree with each other: §5.3 (`constraint I :- G` = integrity constraint, invariant I must hold when guard G holds — listed under Rule because it is sugar over one), §6.2 with the grammar and the desugaring (`constraint non_negative: gte(balance(?a), 0) :- balance(?a, ?b)` -> `rule non_negative: ⊥ :- balance(?a, ?b), lt(balance(?a), 0)`), and §8.4 'Constraint Enforcement': 'Constraints (denials) are checked whenever a new fact is asserted. … If the body is fully satisfied, the assertion is REJECTED.' WHAT THE KERNEL DOES. Nothing. `load_constraint` (kb/load.rs) says so in its own comment: 'Historical behavior: store an inert Constraint(head:, guard:) fact. Denial/invariant constraints are NOT registered as guards (WI-023 wires only the quantified forms; enforcing the existing denial constraints is a separate concern with its own regression surface — THE STDLIB RELIES ON THEM BEING INERT TODAY).' Only the QUANTIFIED forms (no/lone/one/some/forall + aggregations) reach `check_all_guards`. MEASURED, three ways, each loading CLEAN: (a) `constraint always_false: gt(0, 1)` — guardless and plainly false; (b) a fact-guard denial in §6.2's own documented shape with a VIOLATING fact (`constraint non_neg: gte(?v, 0) :- bal(?v)` + `fact bal(v: -5)`); (c) the stdlib's own `constraint mod_positive: gt(?b, 0) :- mod(?_, ?b)` — `mod(5, -3)` evaluates to 2 with no complaint. THE 11: int64 (in_bounds, div_nonzero_primary, div_nonzero, rem_nonzero, mod_positive), float (recip_nonzero, div_float_nonzero, sqrt_nonneg, log_positive, log10_positive, log2_positive). Every one of them is a PRECONDITION written in a channel that does not fire. THE TWO LIVE CHANNELS ALREADY EXIST and are enforced at LOAD — MEASURED: an operation-level `requires` (`operation root(a: Int64) -> Int64 requires gte(a, 0)`) refuses the call site: 'expected precondition gte provable at the call site, got unsatisfied precondition'; and a GUARDED ERROR EFFECT (`div(a, b) -> Int64 effects { Error[DivisionByZero] :- eq(b, 0) }`) propagates to the caller: `div(1, 0)` refuses with 'undeclared effect: Error[T = DivisionByZero]'. NOTE `Int64.div`/`rem`/`mod` ALREADY DECLARE BOTH — the live effect row AND the dead constraint — so the stdlib states the same precondition twice, once in a channel that works and once in one that does not, which is precisely how a reader is misled into writing the dead one (as `float.anthill` did: its six constraints have NO effect-row twin, so `sqrt(-1.0)` is unguarded by anything). THE DECISION THIS TICKET OWNS, and it is a decision, not a cleanup: EITHER (1) implement §8.4 — register denial constraints as guards and enforce them, which the loader comment warns has 'its own regression surface' and would need the 11 re-checked (`in_bounds` over every Int64 is not obviously a decidable post-load check); OR (2) accept that a denial constraint over an OPERATION APPLICATION is not the mechanism, delete the 11, express each as a `requires` precondition or a guarded `Error` effect (whichever the operation's totality calls for — `div` already shows the pattern), and CORRECT §8.4, which currently describes behaviour the kernel does not have. Option 2 is the smaller change and matches what the working code already does; option 1 is what the spec says. Either way §8.4 and the loader must stop disagreeing. NOTE a THIRD reading the spec does not document at all, and which the 11 rely on: §6.2's guard is a FACT PATTERN ('when this fact exists'), while these guards are OPERATION APPLICATIONS ('wherever this call is formed'). If option 1 is taken, that reading has to be specified — it is a different quantification over a different domain. ACCEPTANCE: the 11 are each resolved explicitly (enforced, or replaced by requires/effects and deleted); `sqrt(-1.0)`, `log(0.0)` and `recip(0.0)` are guarded by something that FIRES; §8.4 matches the implementation; a test drives one guarded operation per mechanism; full workspace green via rustland/scripts/test.sh. REFERENCE: kb/load.rs `load_constraint`'s ConstraintBody::Denial arm and its comment; WI-023 (which wired the quantified forms only); WI-881 (`Float`'s unbacked operations — the same file, the same 'declared but not real' shape).
