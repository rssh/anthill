## Description

MODIFY FRAMEWORK — DESIGN, IN THE PROPOSALS FIRST: what identifies a resource at run time, and what a Modify handler is. No code. Decided with the user, then written into the proposals: revise proposal 037 (a Draft that 027, 036 and 047 cite as the canonical framework) and bring into agreement with it, or mark superseded, what disagrees — 027 §"Modify[T]" and its handler model, 027.1's handler contract (it still dispatches "on `Modify[T]`"), 036 §"Single-instance-per-functor limitation", 047 (Modify as State; §10's WI-200 and "State vs direct store access" questions) and 050.1 (§2's construction and fresh-result rules, §6's spec text). A change to kernel-language.md §5.6 or §5.7 is agreed with the user before it is written. Then docs/design/037-implementation.md, the realization: the four write paths today (`Cell.*` builtins straight to the arena, `ModifyRuntime.*` through the global handler, the Store mirror, the KB) and what each becomes.

Settles, in this order: (1) what identifies a resource at run time — the contradiction below; (2) what a handler is — the store behind references (037), the owner of state for a scope (047, WI-200's direction (c)), or nothing beyond mutation of the argument (every compiled target) — and the single door the user directed on 2026-10-16 (WI-20260908-9WVT7, note F10: every Modify through `ModifyRuntime`, `Cell.set` included, so time travel can intercept it); (3) allocation, and the run-time counterpart of the typer's masking; (4) installation and scope, which decides the shape of WI-078 (h); (5) whether a raise rolls back state — spec §5.7's `StateT Env (ExceptT Err …)` says yes at `Error.reify`, the runtime keeps the write (measured in WI-20260926-7D48J), 047 leaves its ranks undecided. Branch stays with WI-070.

THE WI-200 CONTRADICTION. Over `sort Box { provides Modifiable[T = Self]; entity box(id: Int64) }` and the pure `mk(n) = box(id: n)` (`eval_test::m5_modify_a_resource_with_fields_is_refused`), is `let a = mk(1); let b = mk(1)` one resource or two? Spec §5.6: two — two places are two resources. 050.1 §2 and §8: two and unconnected — each call's result is fresh, and a construction adds no region of its own. WI-200's fix as recorded on 2026-10-16: one — the handler receives only the value, so keeping `box(id: 1)` and `box(id: 2)` apart means keying by it. Then `operation demo() -> Unit = (let a = mk(1); put(a, 10))` loads pure (a let-bound local's write is dropped, the path WI-20261016-HE2J6 measured) and changes what `fetch(mk(1))` reads, and no row could name that write. Ways out: (A) a value of a modifiable sort names a slot, as a nullary constructor does — equal values are then one resource, a write through one is never masked or fresh, and one no row can name is refused (HE2J6's rule); (B) identity is minted by an allocating operation (050.1 §6 with Cell's model) — a constructed `box(id: n)` is data, not a resource, and the stopgap becomes a load error; (C) the place is the resource, as compiled code reads `Modify[r]` (`&mut r`). WI-200 implements the chosen rule and depends on this; WI-078 (h) waits on (4) without an edge, since the rest of WI-078 does not.

### 2026-10-17T09:06:06Z — feedback — claude

DECISION 1 (user, 2026-10-17) — WHAT IDENTIFIES A RESOURCE, AND WHAT A HANDLER IS. Reached in discussion; it supersedes the description's "Ways out" (A)/(B)/(C), which framed the question around the generic `ModifyRuntime`.

(1) IDENTITY belongs to the language, per base sort; a handler never chooses it (037 §1's "identity is a property of the handler" goes; Rule 6 stays). A base sort with an allocating operation (`new`, `effects Modify[result]`) is ALLOCATED: each call makes a fresh resource, and its values come only from `new` (a public constructor beside it is refused). One without is KEYED by its values, which name something outside (a store's root and convention, a device, a mailbox's owner): equal values are one resource, the key provides total `Eq` as `Map`'s keys do, and identity follows `Eq`, not the canonical printing the Store mirror keys by today.

(2) BASE AND SECONDARY. A base modifiable sort holds its state outside every anthill value, and only its own operations change it (today Cell, KB and the Store family; ExecutionEnvironment, the webots devices and guardians' Mailbox are declared only). A secondary sort (MutableStack) is written in anthill over the base resources it holds: it has no identity of its own (two values are one resource exactly when they hold the same base resources), it is modifiable by containment (`region::type_admits_modify`), and an `internal` constructor keeps its invariants (WI-369). Map and Substitution are persistent values, not resources.

(3) NO GENERIC `ModifyRuntime` SPEC. One with operations forces Cell's on every sort; one without says what the base `Modifiable` claim says. A base sort's runtime is its own state operations: the mutating ones, the reads and the allocation.

(4) A HANDLER IS AN IMPLEMENTATION OF A BASE MODIFIABLE SORT, one per handler. The default is today's host realization (`provides S language rust { operation_map … }`, proposal 038, held to the declarations by WI-20260922-BRT4Y), generalized from one realization per language at build time to one per installation at run time. A handler that owns the state answers the reads too; allocation (minting the identity, storing the initial value) is the implementation's.

(5) THE FRAMEWORK knows two things: which sorts are base, read from declarations at load; and dispatch — a call to a base sort's operation goes to the implementation installed for it, the single door the user directed (WI-20260908-9WVT7 note F10), so a handler sees every write. `Modifiable` stays a marker spec, with no dictionary.

(6) CONSEQUENCES FOR THE CODE. The stdlib's `ModifyRuntime` (fixed `get`/`set`) and Cell's `provides ModifyRuntime[T = Self, V = V]` go, and so does `default_modify_handler`'s functor map, which only served sorts with no operations of their own (`Box` and `counter` in the m5 fixtures, which become load refusals). WI-200's goal, two boxes kept apart by the generic handler, has no counterpart, since nothing writes a Box; its scope follows from this ticket.

CORRECTION TO THE DESCRIPTION: on 2026-10-16 the user decided only "refuse" (F1 in d4f93591); "the language admits `Modify[b]` on such a place, and a handler that keeps instances apart" was that session's gloss, restating WI-200's May acceptance.

OPEN, for the later decisions: the type system's additions (an implementation written in anthill, checked against the sort's operation signatures; possibly a name for a sort's interface); what answers an allocation when no implementation is installed (rule bodies; the run-time side of masking); how and where an implementation is installed (WI-078 (h)); whether a raise rolls back state; Branch (WI-070).

### 2026-10-17T10:24:54Z — feedback — claude

DECISION 4 (user, 2026-10-17) — HOW A CALL FINDS ITS IMPLEMENTATION, AND HOW ONE IS INSTALLED.

THE RULE. Each resource is bound to one implementation of its sort, and every call on it goes to that implementation. A resource made by an allocating operation (`Cell.new`) is bound when it is made, to the implementation that made it, and its handle remembers which (as a Cell handle reads the arena that minted it today, WI-20260923-9R5HN). A resource whose value is plain data (a store named by its root) is bound when its key is mounted, and is found by that key. An implementation lives as long as the resources bound to it; unmounting a key makes a later call on it fail loudly ("no store registered for key", as today). Considered and not taken: dispatch by what is installed at the call, which splits state between implementations (a cell made under one and written under another); and interceptors that see every call whatever it is bound to, which need a definition the type system cannot express yet, so they stay open.

INSTALLING decides what the resources made or mounted while it is in force are bound to. (1) Extent: a whole-run default the embedder chooses at startup, and scopes inside the program, installed by an ordinary higher-order operation that works as the `Error.reify` frame does: it nests and unwinds on a raise. (2) A scope affects the allocations that RUN inside it, not the code written inside it. (3) Wrapping: an implementation may wrap another and pass calls on to it (audit, logging); a wrapper sees only the resources bound to it. Today's registry forbids that (`EffectRegistry::take_for_invoke` takes a handler out of its slot while it runs). (4) Rule bodies fall back to the sort's default host implementation, so a local cell that never escapes keeps working there; that answers most of decision 3. (5) Compiled code fixes the default implementation at build time; choosing another at run time is an interpreter feature. (6) An implementation is host code for now. One written in anthill needs a form to declare it, a check of its operations against the sort's signatures (as `check_override_refinement` checks a provider), a way to name the implementation it wraps, and possibly a type for "an implementation of S".

AMENDS DECISION 1 — NO IDENTITY KIND. Its "allocated" and "keyed" kinds are withdrawn, and with them the refusal of a public constructor beside `new`. What they decided statically, whether a write may be dropped and whether two places may be one resource, comes from proposal 050.1's memory postconditions. `Cell.new` declares none, so its result is fresh. A keyed sort's constructor, which in an operation body is a call like any operation's (kernel-language §5.4), declares `ensures memory_maybe_connected(result, pool)`, with `pool` an ambient resource of the sort, one per keyed sort: its values are never fresh, and any two of them may be one resource. That needs `ensures` on an entity declaration, which the grammar lacks; how `pool` is spelled is open. Facts are unaffected: in a clause a constructor is a term, and a fact writes nothing. Total `Eq` is required where a value is a mount key, on mounting. A value built by a public constructor of a sort that also allocates is bound to no implementation, so a call on it fails loudly, and no load check is needed for it.

### 2026-10-17T10:32:21Z — feedback — claude

DECISION 3 (user, 2026-10-17) — AN ALLOCATION IN PURE-TYPED CODE, AND THE RUN-TIME SIDE OF MASKING. Every base sort's default implementation is always available: in a normal run, in a rule body's run, and in load-time evaluation of a `const`. So a cell an operation makes and keeps to itself, `localCell(n) = (let c = Cell.new(n); let _ = Cell.set(c, n + 6); Cell.get(c))`, typed pure by the masking WI-314 delivered, always runs, and `localCell(3)` answers 9 from a rule body. Such a local allocation follows the same rule as every allocation (decision 4): it is served by the implementation in force where it runs, so an implementation installed for a scope also sees the private cells of pure code (time travel records them, a test fixture isolates them, a wrapper logs their writes). That breaks nothing the typer promised: an installed implementation is host code outside the program's semantics, like a debugger. Considered and not taken: serving every local allocation by the default implementation whatever is installed, which would hide it from installed implementations but needs a new channel carrying the typer's masking decision to each allocation site. No such channel is needed: the run-time counterpart of masking (WI-20260908-9WVT7 note F10) is that the default implementation is always present.

### 2026-10-17T10:36:30Z — feedback — claude

DECISION 5 (user, 2026-10-17) — A RAISE KEEPS THE WRITES MADE BEFORE IT. When `Error.reify` catches a raise, the writes made inside its boundary stay: in `caller(c) = (let _ = Error.reify(lambda () -> risky(c)); Cell.get(c))`, where `risky` sets `c` to 5 and then raises, the read answers 5. That is the runtime's behaviour today (measured in WI-20260926-7D48J), ordinary exception semantics, and the only behaviour state outside the process admits. The spec half: kernel-language §5.7's stack is to read `ExceptT Err (StateT Env …)` rather than `StateT Env (ExceptT Err …)`, which says a raise rolls state back; written with the proposal revision, after the wording is agreed with the user. Rollback, where wanted, becomes an explicit construct for later: a transaction scope (proposal 047 §7).

### 2026-10-17T10:37:56Z — feedback — claude

DECISION ON BRANCH (user, 2026-10-17) — AN ABANDONED ALTERNATIVE'S WRITES ARE UNDONE. Under `Branch` (WI-070; `branch(a, b)` as proposal 027 describes it, not implemented), each alternative starts from the state at the branch point: in `pick(c) = branch((let _ = Cell.set(c, 1); Branch.fail()), Cell.get(c))` the second alternative reads `c`'s old value. Keeping the writes would make an alternative depend on the order its siblings were tried, and proposal 037 requires alternatives to be independent. Unlike a raise (decision 5), which is a computation that happened and failed, an abandoned alternative is one that never happened. The undo is done by the implementation each resource is bound to (decision 4), which logs old values while a branch is open and restores them when an alternative is abandoned (the `register_undo` design of 027, 037 and docs/design/cell-runtime.md); every implementation of a base sort owes it. State outside the process cannot be undone, which is why `Branch` with `External` is already refused at load (proposal 054). SLD backtracking itself needs nothing, since a rule body never writes shared state (WI-20260926-7D48J's rule). This is the contract WI-070 implements.

### 2026-10-17T10:40:08Z — feedback — claude

DECISION ON RULE BODIES (user, 2026-10-17) — A BRIDGED CALL SEES THE INSTALLED IMPLEMENTATIONS, FOR NOW. An operation call from a rule body runs in a fresh scratch interpreter (the SLD→eval bridge). That interpreter inherits the implementations installed in the interpreter that started the query (time travel, a test fixture), so decision 3 holds there too: the private cells of pure code called from a rule are served by the implementation in force. The costs, accepted for now: each re-run of a bridged call on backtracking allocates again under the installed implementation (time travel records every run), and the bridge must carry the installations into every scratch interpreter. A FUTURE QUESTION, not this ticket's: with `Branch` implemented (its undo, decided above), a rule-body call may need no child interpreter at all, running in the querying one with the abandoned paths undone through the implementations their resources are bound to.
