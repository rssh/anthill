## Description

A PROVISION OF `Eq` DOES NOT GIVE `PartialEq` WHERE IT IS CONDITIONAL OR A WITNESS'S, AND A WITNESS THAT WRITES `Eq` ALONE IS NOT SEEN BY THE DERIVATION, SO ITS `eq` IS SILENTLY NEVER USED (filed with the user 2026-11-21; found answering their question about QAA6S, whether two equality provisions can be produced for one type). `eq.anthill` says `Eq provides PartialEq[T = T]` and promises "a carrier writing `provides Eq[X]` thereby provides `PartialEq[X]` — one `eq`, one equality". MEASURED on c3371cd0 (probe programs run through `run_int64`, each comparing two distinct values with eq and answering 1 for true, 0 for false): (1) `sort C { entity c(v: Int64); provides Eq[T = C] }` answers 0 and, with `operation eq(x: C, y: C) -> Bool = true`, 1 — the unconditional own provision gives `PartialEq`. (2) `sort Box { sort T = ?; entity box(v: T); provides Eq[Self] :- Eq[T]; operation eq(x: Box, y: Box) -> Bool = true }` with `eq(box(v: 1), box(v: 2))` is REFUSED: 'no impl matches — unresolved: PartialEq[T = Box[T = Int64]]' and 'Box provides Eq, which requires PartialEq…' — the conditional provision gives no `PartialEq`, under its condition or otherwise. (3) A witness `sort W { provides Eq[T = C]; operation eq(x: C, y: C) -> Bool = true }` for a plain `sort C { entity c(v: Int64) }` LOADS and answers 0: `C` derived its own equality beside `W`'s, and `W.eq` is never called. (4) The parametric witness `sort W2 { sort A = ?; provides Eq[T = Box[T = A]] :- Eq[T = A]; operation eq(x: Box[T = A], y: Box[T = A]) -> Bool = true }` likewise answers 0; `anthill query 'SortProvidesInfo(sort_ref: ?p, spec: ?s)'` over it lists `Box provides PartialEq`, `Eq`, `Hash`, `NonEq` beside `W2 provides Eq[T = Box[T = A]]`. CAUSE of (3)/(4): `eq_derive`'s two `spoken_for` sets (derive_conditional_eq, total_composites) read which sort a provision is about through `provision_carriers_of_spec` → `witness_dispatch_carrier`, whose carrier parameter is the one an operation RECEIVES on (`spec_carrier_param`, rung 1) — `None` for `Eq`, which declares no operation, so the row is filed under the witness. `provisions_about` (typing/provision.rs) reads rung 2 too and was written for exactly this ("a witness that writes `Eq` alone … adds to a carrier's equality where nothing looking at the carrier can see it"); the later-load check uses it — the same witness in a later load over the stdlib's `List` is refused `EqualityOfEarlierSort` as it should be. TRIED AND REVERTED: switching both `spoken_for` sets to `provisions_about` alone makes (3) answer 1 (the witness's `eq`), but a witness `provides Eq[T = C]` with NO `eq` then loads clean and fails at run time, `EqualityWithNoMember`, and (4) is refused for the missing `PartialEq[Box[Int64]]` as (2) is — so the reader fix needs the transitivity fix beside it. TO DO: `provides Eq[X] :- c` gives `PartialEq[X] :- c` (the same condition; the conversion row is derived in typing/provides_index.rs, `mark_derived_provision`), own or witness; the derivation reads an `Eq`-only witness as speaking for its carrier; a witness whose equality reaches no `eq` is refused at load rather than at run time; the spec (kernel-language.md, Closed by the load that defines the carrier, and the `Eq provides PartialEq` text) checked against what is decided. ACCEPTANCE: rows driving (2)-(4) to the witness's or the carrier's `eq` and the no-`eq` witness to a load error, each back-out measured; families green on both carriers; full workspace green via rustland/scripts/test.sh; scaland testFull.
