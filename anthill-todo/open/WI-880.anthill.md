## Description

MIGRATE THE REMAINING SPEC-OP-KEYED HOST REGISTRATIONS to per-carrier `operation_map` bindings — the generalization WI-876 proved on the ordering family and deliberately did not attempt in one go. THE HOLE IS THE SAME AND IT IS LATENT EVERYWHERE: `eval/builtins.rs` registers `anthill.prelude.Numeric.add`/`sub`/`mul`/`neg`, `anthill.prelude.PartialEq.eq`/`neq` and friends by SPEC-OP qualified name, so ONE host implementation is the backing for every carrier that never wrote its own — including carriers whose values it cannot handle. `op_backed`'s `kb.is_builtin` leg then certifies the operation as backed for ALL of them, which is WI-876's defect A stated for a different family. It has not bitten yet only because no structural carrier provides `Numeric` — exactly the position `Ordered` was in until `anthill.prelude.Pair` became its first structural provider (WI-858), which is how the ordering defect was found. NOTE `PartialEq.eq` is the ONE that is already safe, and for an instructive reason: `builtin_eq` -> `semantic_equal` DISPATCHES to a carrier's own `eq` before deciding structurally. It should still migrate — a dispatching builtin is a workaround for the missing key, not a design — but it is not urgent, and unlike the others it cannot simply be re-keyed: equality fires from UNIFICATION, where there is no call site and no dictionary (058 §3.7), so the value-directed step has to stay. WORK, per family: declare the operations on each host carrier (`Int64.add` etc., body-less), add the `operation_map` entries to the binding blocks, add the host functions to `host_fn_by_key`'s closed registry, delete the spec-op `register_if_present` lines, and give the spec real default bodies wherever a derivation exists. SIZE CHECK BEFORE STARTING: `Numeric` is the big one — `add`/`sub`/`mul`/`neg` across `Int64`/`Float`/`BigInt`, with the overflow behaviour differing per carrier (`Int64.add` raises `Overflow`, `Float` saturates, `BigInt` cannot), which is itself an argument FOR per-carrier keying: today one function branches on the operand carrier to decide which arithmetic it is implementing. Watch the same two traps WI-876 hit: a carrier's own member must be EXECUTABLE for `carrier_override_op` (`op_is_executable` now covers host mappings, so this is already paid for), and a spec default body may only call operations the spec's own `requires` chain covers — otherwise an OP-SCOPED `requires` on the default is the only place it can live. ALSO EXPECT the WI-883 class of fallout: a spec-op call on a carrier that does not provide the spec stops resolving, which is correct and may look like a regression in tests that relied on the builtin ignoring provisions. ACCEPTANCE: no `register_if_present` in `eval/builtins.rs` names an operation of a spec that has per-carrier providers; a structural carrier providing `Numeric` gets a working surface from its own primitives with no per-carrier boilerplate beyond what the spec cannot derive; a test drives that carrier the way `wi876_operation_mapping_test` drives the ordering one; full workspace green via rustland/scripts/test.sh. REFERENCE: WI-876 and docs/design/058-implementation.md §10 (the mechanism and its two surprises); CLAUDE.md's 'A HOST IMPLEMENTATION IS KEYED PER CARRIER' entry.

### 2026-07-31T05:49:07Z — feedback — user

WI-886 FOUND A SECOND, WIDER FACE OF THE HOST-CARRIER EXEMPTION, and shipping cpp binding blocks is what made it bite: `check_provider_operations` (kb/typing.rs) builds its skip set from `anthill.realization.Implementation` facts with NO LANGUAGE FILTER, while `emit_implementation_fact` (kb/load.rs) emits one for EVERY `provides X language <L>` block. So a `provides Box language cpp` block alone puts `Box` in `host_targets` and exempts its provisions from the backing check — for the RUST build too.

Before WI-886 this was invisible because every binding block in the tree said `language rust`, so 'the carrier is host-realized' and 'THIS host realizes it' were the same sentence. They are not any more, and the ticket's own test program (`wi886_cpp_mapping_language_test.rs`, `CPP_ONLY_MEMBER`) is the first thing in the tree shaped to notice: it declares a body-less `Box.max` realized ONLY in C++ and loads clean — because of this skip, NOT because `op_is_executable`'s language-agnostic leg counted the cpp mapping. That distinction was asserted wrongly in the test's first draft and is now stated correctly there.

CONSEQUENCE FOR THIS TICKET'S SHAPE: narrowing the exemption 'now that backing is knowable per operation' is not only about per-operation granularity — it must also decide the LANGUAGE question. A cpp mapping is a real implementation of the operation (which is why `is_host_mapped_op` is language-agnostic and `op_is_executable` reads it) and is NOT one the rust build can run (which is why WI-886 split `is_interpreter_mapped_op` out for eval, `kb/mod.rs`). Whichever way `op_backed` should answer, `check_provider_operations`' `host_targets` must agree with it, or the two legs of one check disagree about what 'host-realized' means.

ALSO RECORDED HERE because this ticket's acceptance is spec-op-worded and does not currently claim them: WI-886 added `anthill_core::kb::op_info::declared_arity` (pub, two tiers, the `operation_is_declared` shape) so a backend crate can ask an operation's arity without building a whole `OpInfoRecord` — `op_record` is `pub(crate)`, which is why the rust registry's documented-cheap path was unreachable from cpp-gen. Any further host-surface migration should use it.
