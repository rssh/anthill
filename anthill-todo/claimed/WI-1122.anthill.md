## description

EMBEDDER-SUPPLIED HOST FUNCTIONS: a host cannot bind its own carrier's operations today. HOST_FNS in rustland/anthill-core/src/eval/builtins.rs is a CLOSED const slice, host_fn_by_key consults only that, and register_operation_mappings turns an unknown host_fn key into an EvalError::Internal that kills every interpreter built for the program. So an embedder -- anthill-todo, or any other -- CANNOT WRITE an operation_map naming its own functions: a block like

  provides GithubForge language rust
    artifact "rustland/anthill-todo/src/forge/gh.rs"
    operation_map { create_entry: "gh_create_entry", entry_comments: "gh_entry_comments" }
  end

is not constructible as things stand. VERIFIED still true 2026-08-17 (builtins.rs:366 const HOST_FNS, :450 host_fn_by_key, :479 and :568 document the unknown-key refusal).

NOT A NEW MECHANISM -- THE MISSING HALF OF AN EXISTING ONE. Corrected 2026-08-18 after reading the registration path; the original wording ("embedder-supplied host functions") reads like a third registration tier and would send an implementer down the wrong path. There are two tiers today. TIER 1 is ~60 hardcoded `register_if_present(interp, "anthill.prelude.Map.put", map_put)` lines, keyed by qualified name, SILENTLY skipped when the name does not resolve, arity-unchecked, and invisible to every load-time reader (WI-884's comment records the cost as measured: `String.contains` reads as backed to the typer and `String.concat` does not, though one interpreter runs both). TIER 2 is `operation_map` + HOST_FNS: loud on an unknown key, arity-checked against the declaration, visible to `is_interpreter_mapped_op` / `op_is_interpretable` / cpp-gen, and keyed PER CARRIER. The project is already migrating tier 1 into tier 2 (WI-880).

WHY AN EMBEDDER CAN USE NEITHER. `Interpreter::register_builtin` is already `pub` (eval/mod.rs:436), so an embedder CAN call it -- it just does not work, for four reasons, the fourth fatal: (1) a silent skip on an unresolvable name, precisely where an embedder gets it wrong; (2) no arity check; (3) invisible to the typer, so the op reads as unbacked; (4) IT DOES NOT SURVIVE `run_in_bridge_interp`. The stdlib's tier-1 registrations survive the scratch interpreter only because `register_standard_builtins` is a function compiled INTO anthill-core that is re-run on every fresh interpreter. An embedder has no such function. So: BOTH existing tiers work because their content is compiled into anthill-core -- tier 1 bakes in the names and the function pointers, tier 2 opened the DATA half (any .anthill file may write an `operation_map`) and left the FUNCTION half frozen in a const slice. That asymmetry is the whole gap.

THE FIX: `host_fn_by_key` consults an EMBEDDER-SUPPLIED TABLE alongside HOST_FNS. Same keys, same arity check, same loud refusal on a miss -- the table extensible at runtime instead of at compile time. The registry stays CLOSED in the sense WI-876 cares about: the arity is carried because the registry is closed, and without it a mapping may bind an operation to a host function that cannot take its arguments (measured there: an arity-1 operation bound to a 2-arg host fn loaded clean and failed at runtime). An embedder entry carries its arity the same way and the same check applies to it.

THE TABLE MUST LIVE ON THE KnowledgeBase, NOT THE Interpreter -- the load-bearing constraint, absent from the original description and the thing a first attempt gets wrong. `KnowledgeBase::run_in_bridge_interp` (kb/resolve.rs) `mem::take`s the KB and builds a FRESH Interpreter per bridged evaluation -- one per [simp] fire, per bridged eq dispatch -- then registers builtins on THAT. A table held by the embedder's own interpreter is absent there, and since an unknown key is FATAL the scratch interpreter would fail to BUILD: one operation_map entry would break resolution program-wide, at call sites having nothing to do with the mapping. The KB is what survives the mem::take. `KnowledgeBase::register_extent_owner` (kb/extent.rs:1293) is the same seam in the same place for the same reason, and anthill-todo already uses it.

ORDERING: register BEFORE load, not merely before the embedder's own interpreter. Load itself builds interpreters (a [simp] macro fire crosses run_in_bridge_interp), so a table registered after load_all can already be too late. THIS IS ENFORCED, NOT DOCUMENTED -- `set_host_op_mappings` seals the registry when the loader builds its mapping cache, and a later `register_host_fn` returns `HostFnRegError::AfterLoad`. The enforcement exists because the unenforced failure is SILENT IN RELEASE, which the /code-review pass surfaced and the code confirmed: the scratch interpreter's build error is an `EvalError::Internal`, and both bridge callers residualize one -- `simp_rewrite.rs`'s macro arm and `resolve.rs`'s `bridge_op_to_eval` each `debug_assert!` on `Internal` and then answer "nothing". A debug build asserts; a release build silently does not expand the macro and silently does not answer the rule, on a program that loaded clean. Before this ticket that state was unreachable (the valid-key set was fixed at compile time); the seam made it reachable by call ordering alone, so the seam owes the refusal.

THE FUNCTION IS ANY `Fn + 'static`, NOT A BARE `fn`. A host binding a carrier of its own generally needs configuration to do it -- a client, a token, a repo handle -- and a bare `fn` pointer captures none of it, which would force every embedder into a `static`/thread-local or into smuggling config through KB facts. WI-1117, this seam's stated first consumer, is exactly that case (`gh_create_entry` needs a repo and a token). `Interpreter::register_builtin_sym` already accepts any `Fn + 'static`, so this costs only the Arc. `HostFn` carries `Static(fn)` for the runtime's own HOST_FNS entries -- keeping the hot lookup allocation-free -- and `Dynamic(Arc<dyn Fn>)` for an embedder's.

THE EMBEDDER'S DECLARED ARITY IS ON TRUST, and that is the one place the open half is weaker than the closed one. The runtime's entries are audited by `every_host_fn_key_declares_the_arity_its_function_accepts`, which probes each function with `arity` operands; no equivalent is possible here, because a Rust function's expected argument count is not introspectable. An embedder declaring 1 for a function doing `expect_args::<2>` reproduces the WI-876 defect exactly. Documented at the type rather than left to be discovered.

COLLISIONS ARE REFUSED, NOT ORDERED. A precedence rule would mean a working program silently changes behavior when the other side later adds the same key, and the operation_map site spells only the key, so nothing there would show it.

WHY IT IS ITS OWN TICKET, split out of WI-1115 on 2026-08-17. It is anthill-core SUBSTRATE, in a different crate from the WI-437 work, and it is needed by ANY host binding a carrier of its own -- nothing about it is specific to forges, to anthill-todo, or to mirroring. Putting the gh shell-out into anthill-core would fix the symptom in the wrong direction (the kernel would learn about forges), which is exactly why the design named this a prerequisite rather than folding it in (design backend-github-coordination.md §8.3).

FIRST CONSUMER: WI-1117 (export/import), which needs it to bind gh_create_entry and friends. That is a dependency, not a scope: this ticket ships the seam and a test that an embedder-registered function is callable from an operation_map, with the arity check refusing a mismatch. It does NOT ship a forge.

NOT TAGGED wi437 deliberately -- it is not one of that chain's increments, it is a capability the chain happens to need first.
