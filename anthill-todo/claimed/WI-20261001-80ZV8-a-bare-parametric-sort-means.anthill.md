## Description

A BARE PARAMETRIC SORT MEANS FRESH `?` SLOTS EVERYWHERE, `Self` IS THE ENCLOSING SORT AT ITS OWN PARAMETERS, AND `s.Sort` BECOMES `s.Self` — the implicit self-sort tie is removed (user decision, 2026-10-01, from WI-20260929-0RP29's seventh /code-review). TODAY one text has two meanings: inside a sort's own definition a bare reference to that sort is THIS instance (docs/design/type-parameter-scoping.md §3; WI-374 enforces it at a call, `expected consistent bindings for the sort's shared type parameter`, and WI-1082 writes it into the signature at load), while anywhere else a bare sort is the sort at a fresh `?` per unwritten slot, per occurrence (§4). So `mix(a: Car, b: Car)` inside `sort Car` takes one `Car[V]` twice, and the same text in a witness or a top-level operation takes any two; and `provides Rel[A = Car, B = Car]` was read three ways — the declaration rule (THIS instance for a parameter an operation receives on, an independent one otherwise), the carrier-param call (as the rule since 0RP29's sixth pass, the binding dropped before it), dispatch (one instance). The questions of 0RP29's reviews 5–7 (received parameters, witnesses, a member narrower than its spec by a tie its text does not show) all come from that tie. DECIDED (user): (1) a bare, or partly written, parametric sort reference means a fresh anonymous `?` in every unwritten slot, per occurrence, in EVERY position — operation parameters and returns, entity fields, `provides` bindings — inside or outside the sort's own definition, as `?` ("each occurrence distinct") and an omitted term field already mean; `Rel[A = Car, B = Car]` is `Rel[A = Car[V = ?], B = Car[V = ?]]`, two unrelated `Car`s. `provides` and operations must read ALIKE. (2) `Self` is a sort name meaning the ENCLOSING sort at its own parameters (`Car[V]`): `entity cons(head: T, tail: Self)`, `append(xs: Self, ys: Self) -> Self`, `provides Rel[A = Self, B = Self]`; in a witness it is the witness sort, not the sort it provides for. Any other tie is written — the sort's parameter (`Car[V]`), a projection (`a.V`), an operation type parameter or a shared variable (the scoping doc's §2). `Self` is RESERVED: no sort, type parameter or member is named it. (3) The value projection `s.Sort` — the whole parameterized sort of the value `s` (WI-376) — is renamed `s.Self`: one word for one notion, the sort at its parameters, of the enclosing definition (`Self`) or of a value (`s.Self`). This reverses the scoping doc's §1, which rejected `s.Self` as carrying "receiver/enclosing-type baggage" when there was no `Self` sort for it to agree with. PROPOSED with this ticket, to confirm when the design text is written: (4) inside a sort's own definition a bare reference to THAT sort is refused at load, asking for `Self` (this one) or `Car[V = ?]` (any). It is the one place the C++/Swift habit (the bare name is the current instantiation) and the `?` reading collide; without the refusal a forgotten `Self` silently WIDENS a signature — sound, since a body needing the tie fails to check, but a body-less operation (`eq(a: Set, b: Set) @[host_implemented]`) simply accepts more. CONSIDERED AND NOT TAKEN: the C++ rule applied consistently (a sort's name inside its own definition is the current arguments, in operations and `provides` alike) — sound and terser, but one text keeps two legal meanings, because the bare name outside already means "any". MEASURED (2026-10-01): the written form already works on the 0RP29 tree and on the build before it (`provides Rel[A = Car[V], B = Car[V]]` with `mix(a: Car[V], b: Car[V])`: one `V` runs to 42, two are refused at the call "expected Car[V = Int64], got Car[V = String]"), so declarations can be migrated BEFORE the tie is removed; a direct `Car.mix(x, y)` over two `V`s and `List.append([1, 2], ["s"])` are refused today by the tie. Bare self-references in an entity field or an operation signature: about 90 declarations in 14 stdlib files (`cons(head: T, tail: List)`, `append(xs: List, ys: List) -> List`, `get(c: Cell) -> V`, `eq(a: Set, b: Set)`), at least 321 in 81 files under rustland/anthill-core/tests (a lower bound — fixtures assembled from helper strings are not counted), 43 in 14 files under docs/; `Self` names nothing in stdlib/ or examples/. The `.Sort` projection is written 1 time in stdlib/ (a doc comment), 1 in examples/, 22 in 8 docs files, 24 in 4 test files and 13 in 6 files of rustland/anthill-core/src. STAGES, each leaving the suite green: (a) the design text — §3 and §4 of the scoping doc, kernel-language.md §8.1's self-sort paragraphs (the unwritten-slot skolem's self exception, WI-1059/1061; "The tie is WRITTEN", WI-1082; the bare self return left untied) and the member-rule paragraph; (b) `Self` — resolved to the enclosing sort's own application wherever a type is read (signatures, fields, `provides`/`requires` bindings, annotations in bodies), refused outside a sort — and `s.Sort` renamed `s.Self` (its own step: a rename, no fallback spelling); (c) the stdlib, examples, docs and test fixtures migrated to `Self` or the written form while the tie still exists — no behaviour change; (d) the load refusal of (4), which proves none is left; (e) the tie removed: `elaborate_self_ties` (typing/elaborate.rs), `enforce_member_tie` (typing/sort_alias.rs), the self exceptions of the slot filler and of the deep expansion's `callee_parent_canon`, the canonical-channel binding of a bare self reference in `unify_parameterized_with_sort_ref`, the rule side's self reading, and in 0RP29's declaration rule whatever reads a BARE carrier as this instance (`is_this_instance`'s bare arm, `independent_this_instance`, the `received` reading of a `provides` binding, `Narrower::Tied` over a bare name) with the call's bare-carrier arm (typing/carrier.rs `bind_spec_params_from_carrier_param`). scaland to be checked for parity (a keyword search found no tie there — unverified).
