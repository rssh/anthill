## Description

Deferred-release queue: reclaim WI-471's pinned cache terms when their NodeOccurrence drops, instead of pin-for-lifetime. WI-471's term_cache owns a +1 it never releases (Drop cannot reach the store), so cached terms live until KB teardown -- a bounded but real leak under retract/re-assert churn or heavy transient-type inference. Mechanism (KB-DECOUPLED, no node->KB reference): NodeOccurrence::Drop, if term_cache is Some((KbId, TermId)), pushes that Copy pair into a process-wide thread_local release queue (Drop stays store-free); the KB force-drains its OWN KbId entries at safe op boundaries (top of assert/retract/query), calling terms.release once PER CELL (matching the per-cell +1; NOT per-unique-TermId -- see WI-472 note 1); KnowledgeBase::Drop purges its own orphan KbId entries (no release -- its store is dying). Drop fires only at last-Rc-drop, so sharing is handled automatically (no unique-ownership gating needed). Reconciles the WI-246 invariant exception WI-471 introduced (a cached occurrence now owns a term-store refcount). OPTIONAL, NOT a gate: WI-470 and WI-472 work with pin-for-lifetime and do NOT depend on this; it only trims the leak once they populate the cache in production. Depends only on WI-471; buildable + testable against WI-471's mechanism alone (cache occurrences, drop them, drain, assert refcounts released and the term freed).

## Reason

Dissolved by WI-815: cached_term / term_cache / KbId are deleted, so the pinned term-store +1 this queue existed to drain no longer exists. See the feedback entry for the full rationale.

DISSOLVED by WI-815 (2026-08-05), not implemented — there is nothing left to reclaim. This ticket's entire subject was the `+1` that `NodeOccurrence::term_cache` owned and could never release. WI-815 deleted `cached_term`, the `term_cache` field on every occurrence, and the `KbId` stamp that existed only so a queued `TermId` could be routed back to the store that minted it (`KnowledgeBase::id` and the `KbId` type are gone with it — grep confirms no other reader existed in any crate, test or doc). The one non-test caller, `value_fact_dedup_key`, now keys on a carrier-agnostic `GoalKey` structural fingerprint walked through `TermView`, which allocates nothing in the term store and needs only `&kb`. So: no cached term, no pinned refcount, no queue to drain, no `KnowledgeBase::Drop` purge, and no per-cell-vs-per-TermId release-counting hazard (this ticket's and WI-472's note 1 — the subtlest part of the design, now moot). The WI-246 invariant this was filed to reconcile — "body/head occurrences hold no term-store refcount" — is true again with no exception. Closing rather than deleting so the mechanism and the reason it became unnecessary stay findable from WI-471/WI-472.
