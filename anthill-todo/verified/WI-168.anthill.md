## Description

Revise proposal 007 (persistence layer) for Value/TermView integration. 007 was written pre-Value (proposal 026/026.1) and reads as TermId-only — its §5 'Backward Chaining Integration' speaks neutrally of 'facts' returning from queryable stores without committing to representation. The unreconciled gap with 026.1: 007's queryable-store path (SQL retrieval, backward-chaining hooks) and 026.1 Q4's external-stream path (Value::Entity rows via bind_value, no TermStore allocation) describe overlapping concerns in unreconciled vocabularies. The 026.1 Q4 motivation (avoid hash-consing 1M rows from a 1M-row scan) is *exactly* a SQL-store scaling concern — i.e. canonical 007 use case — but Q4 is filed as 'deferred/optional' and 007 doesn't reference it. Concrete tasks: (1) Add §'Value integration' to 007 specifying that retrieved facts from queryable stores currently enter the KB via assert_fact (TermId path), hash-consing every row into the main TermStore. (2) Cross-reference 026.1 Q4 as the path for queryable-store row scaling — describe how bind_value + TermView would let SQL rows surface as Value::Entity bindings without TermStore allocation. (3) Decide and document: is 026.1 Q4 a 'future optimization' or a 'required path' for queryable stores beyond N rows? The threshold matters for downstream (proposal 033 §Open questions §5 references this gap). Alternative form: write a new proposal that synthesizes 007 + 026.1 Q4 into a unified 'external data sources' architecture, supersedes the relevant sections of both, and gives one canonical answer to 'how does external data flow through σ'. Independent of WI-075/076/033 implementation; recorded as parallel proposal-base hygiene work. Acceptance: docs/proposals/007 (or successor proposal) addresses Value integration explicitly; proposal 033 §Open questions §5 either resolved or replaced with a concrete cross-reference.
