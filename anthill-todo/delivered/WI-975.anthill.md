## description

FOUND WHILE DRIVING WI-956 item 4. Not fixed there: this is a LANGUAGE decision, and WI-956's gate fix is right whichever way it goes.

WHAT LOADS TODAY, clean, no diagnostic:

    namespace n
      entity Rec(n: Int64)     -- §6.3 sugar: desugars to `sort Rec { entity Rec(n: Int64) }`
      sort Rec                 -- the SAME name, declared again, with a different body
        sort T = ?
        operation peek(x: T) -> T
      end
    end

`Rec` ends up `kinds == [Entity, Sort]` with `type_params_of_sort(Rec) == ["T"]` and a member `Rec.peek`. Nothing warns that `Rec` was declared twice.

AND IT IS HALF-WIRED. The second declaration's body does not resolve names from its enclosing namespace. MEASURED, three separate shapes:
  - `operation peek(r: Rec) -> T`         -> "unresolved name 'Rec' in scope 'peek'"
  - `provides Resource[C = Counter, ...]` -> "unresolved name 'Resource' in scope 'Counter'", and the same for `Counter` and for the IMPORTED `Int64`
Only a body referring exclusively to names declared INSIDE it (like `peek(x: T) -> T` above) loads. So the shape is accepted, but a sort declared this way can carry no `provides`, no member typed by its own sort, and no imported type.

WHY IT MATTERS BEYOND THE ODDITY. This is the shape that made WI-956's `kind_of` bug reachable: `kind_of` reports the FIRST-declared category, so a sort registered `[Entity, Sort]` failed five `kind is Sort` gates and `call_bracket_scopes(Rec.peek)` came back EMPTY. WI-956 fixed the gates (they were asking a display question at a membership site, wrong regardless). The declaration itself is untouched.

THE DECISION, which the spec should make, not a reader:
  §6.3 says the sugar and the long form are an EQUIVALENCE -- `entity Account(...)` and `sort Account { entity Account(...) }` denote the same thing. It does not say whether a LATER `sort Account { ... }` EXTENDS that sort, CONFLICTS with it, or is simply undefined behaviour. Pick one:
  (a) REFUSE -- a duplicate sort declaration is a load error naming both spans. Simplest, and consistent with "prefer a loud error over a silent skip".
  (b) MERGE -- define re-declaration as extension, and then the scope wiring is a real bug to fix (the second body must see its namespace).
  (c) Something else the spec author intends.

Do NOT pick (b) by default just because it currently half-works.

ACCEPTANCE: docs/kernel-language.md §6.3 states the rule; the loader implements it; a test drives the fixture above and pins whichever answer was chosen (if (a), pin the diagnostic text and the two spans; if (b), pin that `provides` and an imported type resolve inside the second body). cargo-test green via rustland/scripts/test.sh.
