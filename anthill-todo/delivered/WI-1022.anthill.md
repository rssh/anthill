scaland Bootstrap maps a sort's `requires` onto the DATA declaration as `extends`, so two requirements of one spec at different type arguments emit Scala that is refused outright -- measured, "trait PartialEq is extended twice".\n\nMEASURED (2026-08-05, delivering WI-940). stdlib/anthill/prelude/pair.anthill declares\n\n  requires PartialEq[A]\n  requires PartialEq[B]\n\nand Bootstrap emits (renderMainSort, scaland/core/src/main/scala/anthill/codegen/scala/Bootstrap.scala):\n\n  enum Pair[A, B] extends PartialEq[A], PartialEq[B]:\n    case Pair(fst: A, snd: B)\n\n`scala-cli compile --scala 3.6.3`, with `PartialEq` as eq.anthill's own emission defines it, reports:\n\n  trait PartialEq is extended twice\n  class Pair cannot be instantiated since it has conflicting base types\n    anthill.prelude.PartialEq[A] and anthill.prelude.PartialEq[B]\n\nThis is not "an abstract member was left unimplemented" -- that would at least be a coherent shape. Scala forbids one trait in a class's linearization twice at ALL, so no implementation could rescue it.\n\nWHY IT IS THE MAPPING AND NOT THE STDLIB. docs/scala-forward-mapping.md §2.7 already says a `requires` "can be either a type-class supertrait or a `using` context parameter, DEPENDING ON THE CALL SHAPE", and the summary table's row reads "upper bound or `using Eq[T]`". Bootstrap implements only the first half: `renderMainSort` builds one `extends` clause from every `Item.RequiresDeclItem` and hangs it on whichever declaration the sort maps to. The `using` half is unwritten, and `PartialEq[A]` / `PartialEq[B]` on `Pair` is exactly the shape it exists for -- a requirement PER TYPE PARAMETER is evidence, not a supertype. `Pair` is not a `PartialEq`; it HAS componentwise equality GIVEN one for each component. pair.anthill's own header says so ("The `requires` clauses do double duty: they CONDITION the provisions and they are the EVIDENCE the `eq` body dispatches through").\n\nSCOPE. Decide, per §2.7's "depending on the call shape", when a `requires` is a supertrait and when it is `using` evidence, and implement the second. The obvious discriminator is whether the requirement's argument is one of the sort's OWN type parameters (`requires PartialEq[A]` on `sort Pair[A, B]` -- evidence) versus the sort itself or a ground type (`requires PartialEq[T]` on `sort Eq[T]`, which §2.7's own example maps to `trait Eq[T] extends PartialEq[T]` and which the existing BootstrapTest pins) -- but verify that against eq.anthill, ordered.anthill and set.anthill before committing to it, and note that the DATA shapes (`case class` / `enum`) may want a different answer from the ALGEBRA shape (`trait`), since only the last can carry a supertrait cheaply.\n\nRELATED, DO NOT CONFLATE: WI-1021 is the other mechanism making this same file uncompilable (a sort's own name rewritten through the prelude type map).
