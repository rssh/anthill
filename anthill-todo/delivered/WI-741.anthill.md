## Description

WI-714 follow-up (relation schema typing): a relation column typed ONLY by a SPEC operation takes the spec's UNINSTANTIATED TYPE PARAMETER, so a multi-clause relation mixing it with a concretely-typed column is a spurious LOAD error. VERIFIED live (2026-07-17), realistic shape: 'rule named(?x) :- eq(?x, "root")' + 'rule named(?x) :- parent(of: ?x, is: ?y)' => 'type mismatch in named.rule (rule): expected a common column type across relation clauses, got disjoint types for column x' -- though BOTH clauses plainly mean String. MECHANISM (instrumented, not inferred): relation_clause_columns (kb/typing.rs) types a column from collect_rule_var_types' var_types map; for 'eq(?x, ...)' that records ?x at 'anthill.prelude.PartialEq.T' -- the spec op's own type PARAMETER, carried as a Term::Ref to the parameter symbol (probe: 'a=anthill.prelude.PartialEq.T | b=anthill.prelude.String'). The cross-clause lub then compares Ref(PartialEq.T) against Ref(String), finds them incomparable, and reports the column disjoint. This is a THIRD spelling of 'the type is unknown', alongside the TypeVar inference wildcard (which join_types already short-circuits) and the raw Var::Global (which WI-714's join_column_types now treats as no-information -- the recursive-relation fix). A Term::Ref to a type param is neither, so it still reaches join_types. FIX DIRECTION (a HYPOTHESIS to verify first, not a diagnosis): collect_rule_var_types builds a Substitution and DROPS it (returns only (var_types, contradiction)), so var_types holds the UNRESOLVED PartialEq.T rather than the String the subst very likely bound when it constrained the literal argument "root" against the same param. Walking var_types through that subst in relation_clause_columns would then yield String. VERIFY that the subst actually binds it before building on this. BLAST RADIUS -- this is why it was NOT folded into the recursion fix: resolving var_types through the subst changes column types for EVERY relation, not just multi-clause ones (a single-clause 'rule r(?x) :- eq(?x, "a")' types Relation[PartialEq.T] today and would become Relation[String]), so it needs its own tests + review. Alternative narrower framing: treat an uninstantiated spec type param as no-information in join_column_types (gated on is_type_param, cf. WI-708) -- but that LOSES information the producer could have had, so prefer the producer fix. NOT a soundness bug: it fails LOUDLY at load, never silently. Orthogonal to recursion (WI-714's recursive schema gap is fixed and green). ACCEPTANCE: the two-clause 'named' relation above loads and drains, its column typed String; a genuinely disjoint pair (String vs Int64) is STILL a loud load error; cargo-test green via scripts/test.sh.
