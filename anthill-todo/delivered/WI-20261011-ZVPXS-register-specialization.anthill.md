## Description

`register_specialization_witnesses` WALKS EVERY PROVISION OF THE KB AT EVERY LOAD, AND FOR EACH ONE EVERY PROOF RECORD — measure where its time goes on a later load, then decide with the user what a later load owes it. The fourth pass of lever A3 in docs/design/test-infrastructure.md §4 (one ticket a pass, filed one at a time: user, 2026-10-06; this one asked for 2026-10-11, after WI-20261011-A3NND).

MEASURED 2026-10-11 on the tree of WI-20261011-A3NND as delivered (docs/measurements/test-infrastructure/provider-requires-2026-10-11.txt §10, §12, §14). One thread, the gate's build (anthill-core at opt-level 2), medians of 15, the bench's loads: on a LATER load — one small user file that writes no provision, into a copy of the sealed stdlib — the pass is 10.1–11.1 ms of 37–41 ms, 27 %. On a full load it is 2.9–3.3 ms of 274–299 ms, 1 %. So it costs three and a half times more on the load that adds nothing than on the one that loads the library. Over one traced run of anthill-core (12 threads, a machine at two thirds of its speed): 28.7 ms of the 112.8 ms a test's load on the shared base costs, 25.5 %, the largest phase now; those loads are 66 % of `wi_tests`' thread-time, and loading is 87 % of it.

WHAT IS KNOWN OF WHY, read off the code and one profile, not measured by marks. The pass (`load::register_specialization_witnesses`, kb/load.rs) takes no list of what the load added. It reads the `rule` name of every `ProofRecord` fact of the KB into a set (`collect_existing_proof_record_qns`), then walks every `SortProvidesInfo` fact (413 after the stdlib's own load; the rows a derivation marked are passed over), decodes its spec (`resolve_provides_spec`), and for EACH row filters the WHOLE set of record names for the ones under `<spec>.requires.` — with the prefix built by a `format!` inside the filter's closure, once per record per row — then builds each `<carrier>.provides.<spec>.<law>` name and asks the set whether it is there. On a later load it is: the stdlib's own load emitted them, so the pass derives every name again to find it exists ("idempotent across loads via `existing_rule_qns`"). A profile of a loop of later loads taken for A3NND, before that change (its raw file's §8; 19 897 samples under `load_all`), has 13 % of a later load under `alloc::fmt::format_inner` and a `Vec::from_iter` closure frame directly under `load_phase_inner` at 15 %, neither attributed to a pass by the sampler; 13 % of that 65 ms load is 8.5 ms, where this pass was 10.3 ms. That is the lead, and why the later load would be the dearer: the set it filters is empty while the stdlib's own load runs the pass and full after it. Measure before leaning on it.

WHAT IS NOT KNOWN, and is to be measured before anything is designed: how many `ProofRecord` facts the stdlib's load leaves, and how the 10 ms divides between collecting their names, decoding the rows, the filter with its `format!`, building the names, and asserting (which a later load that adds no provision should not do at all — count it); what `register_requires_axiom_witnesses` and `register_induction_axiom_witnesses`, which stand beside it and read the same set, cost; and what the pass does in a load that DOES bring provisions and laws of its own.

FIRST, MEASURE, as A3NND was: temporary marks inside the pass (not kept), each with the count of what the step visited; the bench at ITERS=15, the BEFORE and AFTER binaries run side by side so that a row is of one machine state; a second and a third run of the pass straight after the first, which is what refuted A3NND's lead in one build; the raw file into docs/measurements/test-infrastructure/.

THEN DECIDE, with the user, which this is — not decided here. Either the pass's reads want an index, as equality derivation's did (WI-20261010-ANK4X; no rule about loads): the record names grouped by the spec they are a `requires` of, once, so that a row asks for its own and the pass is rows plus records and not rows times records. Or the pass is a frontier's, as `check_provider_requires` became behind a seal: a provision's witnesses are emitted by the load that asserted it, and a later load emits for its own rows — and then the question that has to be answered first is which EARLIER row a later load can owe a new record for. A `requires` law record registered since for a spec that was there (a law added to an earlier spec; A3NND found a `requires` written into a sealed sort refused where it is written and asserted all the same) is one way; a record retracted is another. Each such way is re-walked or refused, and said so at its site. The first shape may leave little for the second to take: measure it before choosing the second.

THE CONTROL. What this pass gets wrong fails quietly and far away: a `Specialization` record not emitted is not a load error — phase β.5's check reads the registry, so it surfaces in `anthill check`'s integrity audit, or not at all where nothing asks. So a value at a call site is not the control. (1) THE RECORDS ARE THE SAME RECORDS: a listing of every `ProofRecord` — its `rule`, its witness's `parametric` and `substitution` — after the stdlib's own load, after a later load that brings a provider of a spec with laws, and for the two in ONE call, BEFORE and AFTER, compared as sets (the listing ANK4X made of the provision rows; say if rule ids or order differ run to run, which WI-20261011-6GMCN found of derived provisions). (2) A fixture for a later load that MUST emit — a program's own provider of a library spec that has requires-laws — asserting the record by name, in one call and as a later load; and one for each way a later load can owe an earlier row a record, if the frontier is what is built. Each back-out measured and written at its site. (3) If rows are skipped: an oracle switch for tests, with a control of its own that counts NARROWED runs compared with a full one and says in the run's log whether it took — A3NND's first cut counted every run and said ON beside a suite in which nothing was narrowed. And a check that the change ENGAGES on the shared base, by a count and not by a wall time: the shared base is sealed by `seal_declarations_of`, and A3NND's first cut held its state only for the other door, green throughout. (4) The gate green under all three recipes.

EXPECTED, by arithmetic, to be replaced by the measurement: a later load 37–41 ms -> about 27–30 ms if the pass costs nothing where nothing was added; a test's load on the shared base 44 ms -> about 34 ms; `wi_tests` 122.8 s -> about 102 s, the pass being a quarter of the later loads that are two thirds of its thread-time. Twelve-thread wall times are of a machine that throttles — the limit is at two thirds within half a minute of a `wi_tests` run's start (A3NND's raw file, §14); the one-thread bench is the measurement.

NEXT, not this ticket, filed after this lands: the typer's remainder (22 % of a later load today), `check_override_refinement` (10 %).

DONE WHEN: the pass's time on a later load is accounted for step by step in a raw file; the shape is decided and recorded here; the records are shown the same, BEFORE and AFTER, in the three loads; each fixture's back-out is measured; the bench's rows and one traced run are re-taken into docs/measurements/test-infrastructure/ and the design doc's §2.4 and §9 row 4; the gate is green under all three recipes.
