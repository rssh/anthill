## Description

Typer: ground the Stream access-effect E at iterator consumption. When an iterator(x) -> Stream is consumed via collect/takeN/splitFirst in a context that declares no effect, the consumed Stream access-effect row E leaks as an undeclared ?_ instead of grounding to {} (a pure carrier) or the carrier real effect -- 'type mismatch in F.effects: expected declared: [], got undeclared effect: ?_'. GENERAL, not carrier-specific: surfaced in WI-364 Phase 0 -- a plain-List control List.length(collect(List.iterator(xs))) leaks IDENTICALLY to a MutableStack walked via iterator. ROOT: the Iterable contract is iterator(c: C) -> Stream[Element, E], but a carrier iterator BODY returns a BARE Stream (List.iterator = l; MutableStack.iterator = Cell.get(c)); the bare Stream return type hides the producing carrier, so the WI-357/365 effect-row grounding never fires at the consumption boundary and E stays an unbound row var. FIX DIRECTION (kb/typing.rs): at a Stream-consuming spec-op call (collect/takeN/splitFirst on a value of static type Stream), ground the consumed Stream E from the producer -- the carrier feeding the consumer -- defaulting to {} when that carrier is pure (List, Cell-backed); mirror the WI-357 concrete-path effect-close (check_apply_iter ~3115) but source the producer carrier from the consumed expression, and likely thread the carrier through iterator bare Stream return so the consumer sees it. ACCEPTANCE: length(collect(List.iterator(xs))) typechecks pure (no undeclared ?_); a MutableStack (WI-364) walked via iterator typechecks; wi357/wi362/wi365 + full anthill-core green. REF: WI-357 (carrier element threading + effect-close, delivered), WI-365 (abstract self-typing), check_apply_iter effect-close. BLOCKS WI-364 (walk via iterator). Rust-only (typer; scaland has no typer).

### 2026-06-03T12:00:09Z — feedback — user

SOUNDNESS REFINEMENT (design discussion): the fix is NOT 'found a producer -> close the row'. Walking one hop into iterator(xs) does not guarantee the producer's RECEIVER is concrete -- it can be abstract too -- so grounding E to {} unconditionally is unsound. The producer receiver splits THREE ways: (a) CONCRETE PURE (List, Cell-backed): length(collect(List.iterator(xs))) -- ground E to {} (the acceptance case, today MISCLASSIFIED as abstract because the bare-Stream return erases the carrier -> receiver_carrier returns Abstract -> the WI-357 effect-close is skipped -> floating ?_ with no enclosing E to absorb it -> the spurious 'undeclared effect: ?_'). (b) CONCRETE EFFECTFUL (MutableStack with real effects): ground E to the carrier's ACTUAL effects, not {} -- the WI-365 dispatched_impl_effects direction. (c) GENUINELY ABSTRACT (operation walk(c: C) effects E where C provides Iterable = collect(iterator(c)); producer receiver c : C): E must NOT close to {} -- doing so would assert a possibly-mutable Iterable is pure (a silent-skip soundness bug, violates 'loud error over silent skip'). The correct answer is that the abstract row IS the enclosing op's declared effects E: unify the row var with E and stay effect-polymorphic; error ONLY when there is no enclosing E (a top-level pure context consuming an unknown-effect stream -- a CORRECT error). KEY INSIGHT: the bug is a MISCLASSIFICATION, not a missing close. The spurious ?_ arises iff (1) the row var is floating AND (2) no enclosing E exists. Case (a) hits both; case (c) hits (1) but not (2) so it legitimately unifies -- correct today. The HAZARD for a naive approach-1 is replicating today's blanket filter(!effect_is_unresolved_var) drop WITHOUT re-checking concreteness, which would flatten case (c) to {} and silently claim a mutable Iterable is pure. CONSEQUENCE FOR DESIGN: this three-way split is the strongest argument for approach 2 (thread the producer carrier into iterator's return TYPE) over approach 1 (recover from the consumed EXPRESSION). With the carrier in the type, the existing receiver_carrier classification does the split for free: concrete carrier -> Concrete(...), type-param carrier -> Abstract -> stays polymorphic. The bare-Stream erasure is exactly what collapsed (a) and (c) into the same Abstract bucket; restoring the carrier in the type un-collapses them, and approach 1's expression-walk cannot tell (a) from (c) without re-deriving the producer's receiver type by hand.
