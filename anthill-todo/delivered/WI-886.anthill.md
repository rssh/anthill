NO CODEGEN BACKEND READS `OperationMapping` TODAY. THE DIVERGENCE, counted on `Float` after WI-881: the INTERPRETER (`host_fn_by_key`) has 29 host functions plus `div`/`isNaN`/`isInfinite`/`isFinite` and `recip` by `[simp]` inlining. CPP-GEN (`render_as_math_call` / `render_as_math_constant` / `render_as_float_special`) has 21 math calls, `neg`/`div` as operators, the three constants and the IEEE specials — MISSING `isNaN`/`isInfinite`/`isFinite` and `recip` ENTIRELY, and missing `Int64.max`/`min`/`compare` which WI-876 declared. Worse, cpp-gen's comparison entries are still keyed on `PartialOrd.gt` while WI-876 moved `Float`'s comparisons to `Float.gt`, so the table is now inconsistent WITHIN ONE BACKEND: WI-881 added a CARRIER-keyed `Float.max`/`min` pair beside SPEC-keyed comparisons. AND THE FALL-THROUGH IS SILENT: an unmatched apply becomes `Ok(format!("{fn_short}(...)"))`, i.e. an unresolvable C++ call that the anthill layer never complains about — a generated program that does not compile, reported nowhere. SMT-GEN is also partial (only `div`, `cos`, `sin`, `abs`, `neg` plus spec-op comparisons) but is NOT part of this ticket's defect: an unmapped op there is `'v0: unhandled arithmetic op'`, so it errors rather than mis-lowers, which is what the repo's loud-over-silent rule asks. Only the SILENT one needs fixing, and it needs fixing at the source rather than by topping up a table. THE WORK: feed `render_as_math_call` (and its constant/special siblings) from `kb.host_op_mappings()` filtered to `lang == \"cpp\"`, move the pairs into `provides Float language cpp` / `provides Int64 language cpp` blocks, and make the fall-through LOUD so an operation with no cpp mapping is a codegen error naming the operation and the carrier — not an emitted call to a function that does not exist.
