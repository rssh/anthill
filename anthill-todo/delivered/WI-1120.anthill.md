## Description

anthill-todo backend, INCREMENT 2b of WI-437: WORK ITEMS ARE DOCUMENTS -- a declared fact<->markdown mapping. Design: backend-github-coordination.md §5.3 (the rules) and §5.4 (the artifact: mapping declaration + worked example). §5.3 was written and then REVISED the same day, after review falsified three of its rules against live data; the doc is authoritative, this description summarises it.

THE ARTIFACT (§5.4). File name is WI-NNN.anthill.md -- trailing .md so editors and GitHub render it, .anthill before it so an item file is self-identifying and a README.md in the same tree is not mistaken for one. This is a SUFFIX test, not an extension test: Path::extension() returns "md" for WI-690.anthill.md, so fs_util::has_extension cannot express it and the loader needs ends_with; a plain .md glob would sweep in every ordinary markdown file under the project directory. The head is the file's first fenced block with the `anthill` info string -- no new delimiter syntax, markdown already has one, GitHub renders it highlighted, and it composes with the fence tracking §5.3 needs anyway. A chapter-bearing field is simply ABSENT from the head; no marker in the fact, nothing to keep in sync, and the declared mapping is what says where it comes from: fact Chapter / fact ChapterGroup as above, plus fact DocumentFormat(level:) fixing the structural levels (fields and containers at `level`, entries at level+1, prose below). Tag and MirrorEntry need no Chapter fact -- no prose, so they stay in the head. NAME COLLISIONS ARE POSITIONAL, NOT A NAMING PROBLEM: named_by is not injective (WI-599, below), but under a container that needs no disambiguating suffix -- entries are ORDERED SIBLINGS, so the Nth Feedback fact in the head binds to the Nth ### under ## Feedback and the reader checks that the two counts agree. Positional binding is safe ONLY because the entry heading is CHECKED against its fact rather than ignored: a reordered or hand-edited entry mismatches its at/author and is a loud diagnostic, not a silent rebinding onto the wrong entry. Drop that check and this scheme becomes the worst of the options. No domain field has to be added to carry an identity the data does not have.

WHY, measured per fact record on this repo's own tracker with string literals stripped (1110 WorkItem, 1129 Feedback, 281 Tag): the volume is prose. 1110 descriptions average 2107 chars (max 20345); 1129 feedback contents average 2116 (max 19915). Together 4729493 of the file's 5115651 characters and 4744325 of its 5130561 bytes -- 92.5% OF THE TRACKER IS PROSE INSIDE STRING LITERALS, in either unit. The encoding is not self-consistent about it: 344 descriptions bare, 766 as some(value: "..."), one datum two ways in one file. The grammar has NO multi-line string (string_literal: /"([^"\\]|\\.)*"/, tree-sitter-anthill/grammar.js), so every document is ONE PHYSICAL LINE of escaped text -- longest 20616 chars / 20711 bytes; 2153 lines over 500; 239 feedback entries carry an escaped quote, 274 an escaped newline. The structured half is thin and partly dead: acceptance is 92% ToolPasses(cargo-test) across 12 distinct values, and context / generates / requires_capability are each written exactly 709 times of 1110 (one long-form/short-form split, not three independent fields), always none; all three ContextRef constructors, FileRef the supplied-file hook included, have ZERO uses.

HEADING vs CHAPTER (the distinction the format rests on): a HEADING is markdown syntax, a line beginning with #/##/###. A CHAPTER is this design's unit of meaning -- a named region of prose filling exactly one field of one fact, introduced by a heading at a STRUCTURAL level and running to the next heading at that level or to end of file. Every chapter begins with a heading; NOT every heading begins a chapter. A heading below the structural level is ordinary markdown, part of that chapter's text, carried verbatim. That is why those levels are reserved: if any heading could start a chapter, a user's subsection would silently cut a field in half.

STRUCTURAL LEVELS NEST, AND THERE ARE TWO. A repeated fact is not a field of the item and the document must not pretend otherwise: feedback entries are grouped under one `## Feedback` CONTAINER, one `###` per entry, instead of being strewn across the top level as siblings of `## description`. So ## carries fields and containers, ### carries a container's entries, and prose begins at ####. The flat alternative needs only one reserved level and is marginally simpler to check, but it files an entry in a log at the same structural rank as a field of the work item. The mapping splits accordingly -- fact Chapter(functor:, field:, named:) for a prose field of the item's own fact, and fact ChapterGroup(functor:, container:, field:, named_by:, decorate:) for a repeated satellite fact -- so Chapter has NO `repeated` flag to get wrong: repetition is not a property of a field, it is the whole point of a ChapterGroup.

THE SHAPE. One item file = an anthill HEAD followed by markdown CHAPTERS. The head is anthill syntax, not YAML: no second scalar language, so status: Claimed(agent:, since:) needs no encoding and the head stays the single writable home for all structure. A declared mapping names which prose fields leave the head and become chapters, keyed by name; the store learns ONE concept ("this field's text is the chapter named N") and never stage0's schema. ELIGIBLE FIELDS ARE String AND Option[T = String] -- both: Feedback.content is a bare String but WorkItem.description is Option[T = String] (domain.anthill), and a String-only rule would exclude the very field this increment exists for. The mapping is BUNDLED WITH THE stage0 DOMAIN, not project.anthill -- it is a property of the schema, not of the project -- so §3 stays "two facts, two questions" and §11 step 3 has nothing new to write. Variants-as-sections is OUT OF SCOPE.

FEEDBACK. Repeated 0..n, so several chapters for one field is correct and the mapping must declare repetition. The chapter name is the machine's key and its ONLY requirement is uniqueness WITHIN THE FILE; it is derived from the timestamp for readability with a deterministic disambiguator on collision -- because the timestamp is NOT unique, measurably: WI-599 carries two Feedback facts with identical at AND identical author (one collision in 1129, but the one-time migration meets it on real data). Related finding about EXISTING design: §7.3 dedups ingested comments on (workitem, author, at), and that key is not unique on the data the tracker already holds. Everything after the name in a heading is DECORATION -- regenerated from the head AND CHECKED against it at load, a mismatch being a loud diagnostic that fsck --fix repairs, exactly as §4/§10 treat the directory name. A projection regenerated without being read would silently overwrite a hand correction, which this repo's conventions rule out. Feedback is APPEND-ONLY (21 subcommands; feedback adds, nothing edits or deletes an entry), so the store never re-serializes the 1129 feedback chapters -- a CORRECTNESS property, not a volume one: feedback is 50.5% of the prose and descriptions 49.5%, so the half that IS rewritten is the same size. The precise claim: the only prose the store ever rewrites is one description chapter, via update.

CHAPTER LEVEL IS RESERVED. Headings at the declared level belong to the mapping; prose uses deeper levels. This closes the hole the first draft left open: with unreferenced chapters merely "legal", a user typing a level-N heading mid-description would END that chapter there, silently truncating the field, and the tail would reappear as an innocuous unreferenced chapter -- precisely the failure the section claims to close, and invisible to the opacity test. So an unreferenced heading at the reserved level is an ERROR, and hand-added material lives INSIDE a chapter at a deeper level.

MALFORMED EDITING -- the acceptance surface:
 (1) chapter named by the head is missing: Option field -> none; otherwise LOAD ERROR naming file and expected chapter.
 (2) two chapters with one name, field not declared repeated: LOAD ERROR -- update could not know which to rewrite.
 (3) heading at the reserved level that the head does not name: LOAD ERROR naming file and heading. This is the truncation case and must not look like a note.
 (4) heading below the reserved level: prose belonging to the enclosing chapter, carried verbatim, never interpreted.
 (5) unknown key in the head: LOAD ERROR. The head is the machine's region.
 (6) a heading marker inside a fenced code block: NOT a heading; the scanner must track fences.
 (7) heading decoration disagrees with the head: loud diagnostic + fsck --fix.
 (8) filename disagrees with the head's id: a NEW check this increment adds. §10 today designs directory-vs-status and duplicate-id, NOT filename-vs-id -- do not cite it as already designed.

Rule 4 keeps notes alive and holds only as a TESTED invariant: hand-add a sub-section inside a description, run claim (which rewrites the head AND renames the file), assert it survives byte-identical. That test fails the day the store starts reserializing a whole file from facts -- the one failure mode that would quietly eat a user's notes.

§5.1's RELOCATION RULE NEEDS ONE SENTENCE MORE under this encoding: it says the move "rewrites the item's fact block in place", and here there is no fact block. replace receives a whole WorkItem term, so the store must split it into head fields and chapter fields, rewrite only the head and the chapters whose text actually changed, and leave every other chapter byte-identical. Both the rule-4 invariant and "never re-serializes the feedback chapters" rest on that split, so it belongs to the store's contract.

FENCES ARE PROSPECTIVE BUT NOT IMPOSSIBLE TODAY: 392 descriptions and 240 feedback entries already contain backticks, and while no prose currently holds a fence or a # heading, both ARE writable in a one-line literal (three backticks are literal characters; \n# is one escape away, and 274 entries already carry escaped newlines). Migration must therefore run the fence-aware scanner over all 2239 existing prose bodies rather than assume pre-migration content is fence-free.

COST / SPLIT RATIONALE. No markdown dependency: we never RENDER markdown (GitHub does), we find headings at the reserved level while tracking fences. The .anthill glob is NOT the reason to split this out -- collect_files_recursive takes its extension list as a parameter (anthill-core/src/fs_util.rs) and anthill-todo supplies &["anthill"] at its one call site (src/main.rs:100), so widening it is a caller-side one-literal change; row 2 already carries loader coverage. The genuine anthill-core surface is the READER, parsing a head-plus-chapters document into facts. The real reason to keep it out of WI-1114 is §14.1: bundled, a format bug would mask a store bug on the tracker we are running on.

PLACE IN THE CHAIN. Depends on WI-1114 -- the store must exist before its serialization can be swapped. Blocks WI-1118 (migrate), because the live tracker migrates EXACTLY ONCE and must migrate into the final format.

DRIVE THE CAPABILITY, do not assert that it loads: round-trip a real item -- add / feedback / update --description / claim -- through the markdown format on a fixture project, assert the reparsed facts equal the pre-write facts, and include a fixture carrying the WI-599 duplicate-timestamp shape. CONTROL: the rule-4 opacity test fails when the store is changed to rewrite a file from facts; the rule-1/2/3 tests fail when their checks are removed; the round-trip test passes either way against an unmodified store and measures only the serializer.

EXTERNAL CORROBORATION 2026-08-17, and a possible export target. Google Cloud published the OPEN KNOWLEDGE FORMAT (OKF v0.1) -- https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing -- and it arrives independently at most of §5.3's shape: ONE MARKDOWN FILE PER CONCEPT, a STRUCTURED HEAD plus a PROSE BODY, a DIRECTORY HIERARCHY that becomes a graph through inter-file links, plain text managed like code, explicitly so that agents can read and update it while humans curate. That two designs converged on this from unrelated motivations (theirs: feeding internal context to foundation models; ours: git-mergeable, greppable, reviewable work items) is evidence the direction is right.

THREE DIFFERENCES, and ours are deliberate rather than accidental, so do not drift toward OKF on any of them:

1. THE HEAD IS TYPED. OKF is 'minimally opinionated': it requires exactly one field, type, and leaves every other field, the type vocabulary and the body structure to the producer -- unvalidated by design, because any producer must be able to emit it. §5.3's head is anthill facts against the declared stage0 domain, and the loader CHECKS them; WI-928 found 921 description mismatches the first time that check ran. Optimising for 'anything can emit it' and optimising for 'the KB can reason over it' pull opposite ways, and we want the second.

2. IDENTITY IS THE FACT, NOT THE PATH. OKF says file paths serve as concept identity. We cannot: §4 makes the directory an INDEX and the id the truth, because status is in the path and status CHANGES -- path-as-identity would mean an item's identity changed every time it was claimed. OKF concepts presumably do not move.

3. LINKS ARE IDS, NOT PATHS. OKF links concepts with ordinary markdown links, which are paths, so a rename breaks every inbound link. depends_on holds IDs, resolved through WI-1121's ladder, which is exactly what makes §5.1's relocation safe -- the whole file moves and nothing that points at it needs rewriting.

THE ACTIONABLE PART IS NOT A FORMAT CHANGE. Do NOT add YAML frontmatter beside the fenced anthill head: two heads is two writable homes for one datum, the failure §7's governing principle exists to prevent, and §5.3 chose the fenced block deliberately (no new delimiter, markdown already has one, GitHub renders it highlighted). Instead, OKF is a natural EXPORT TARGET under §7 as amended -- that amendment already says a target need not be a forge, and names 'a static site or a directory of files' as candidates. An OKF tree is precisely a directory of files with a type field. So interoperating costs one export implementation and no change to the native format. Cheap, reversible, and it does not bet the tracker's own encoding on a v0.1 spec.
