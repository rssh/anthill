### 2026-08-17T09:45:34Z — feedback — user

SCOPE NARROWED 2026-08-17 -- READ BEFORE CLAIMING. The continuously reconciled mirror is now a FUTURE EXTENSION; what this ticket ships is EXPORT and IMPORT (design §7, amended).

  export -- write the tracker's current state to the target. Idempotent, keyed by MirrorEntry, and UNCONDITIONALLY TRACKER-WINS.
  import -- pull comments back in as Feedback, for review before they land.

WHAT COLLAPSES, and it is most of §7. §7.2's 'reconciliation, not write-through' exists because sync tried to be bidirectional-ish; export has ONE direction, settled, so reconciliation becomes a loop that overwrites. §7.4's close-as-verify -- an EVENT honoured in exactly one legal transition and re-derived otherwise, with a drift report for every other case -- collapses entirely. §10's 'permanent-id item with no MirrorEntry' check goes with it, since export creates the link as it goes and there is no continuous invariant to violate. §7.3's ingest-once bookkeeping softens to a cheap dedup on (author, at), because import is REVIEWED rather than automatic. Deletion tombstones, --check and the CI gate all belong to the future extension, not here.

WHAT IT COSTS is that a reader sees the last export, not live state. Running export from CI on main recovers most of that FOR FREE -- precisely because it is idempotent and tracker-wins, so there is no drift machinery to get wrong.

MirrorEntry MOVED HERE from the retired WI-1116, and its shape changed twice as a consequence of retiring §6.1:
  entity MirrorEntry(workitem: String, target: String, entry: String)
  * entry is a STRING, not Int64. The draft required a number because §6.1's soundness rested on identifiers TOTALLY ORDERED BY CREATION. With the allocator gone the external id is an opaque handle and must be -- a Jira key is PROJ-123, a Linear id is a ULID, a URL is a URL. Requiring a counter would exclude every target that is not a forge.
  * target says WHICH external system. Implicit while there was one GitHub repo; cannot stay implicit now that an item's external ids are a SET.
AN ITEM'S EXTERNAL IDS ARE A SET AND THE RELATIONAL FORM ALREADY IS ONE: N MirrorEntry facts for one item is N rows, exactly how Tag gives an item a set of tags. No list field, no schema change, no Option nesting. It stays OUT of the WorkItem entity -- a field there would read none in 1110 of 1112 items and would put a mirror concern in the stage0 domain.

CONFIG RENAMED: fact Coordination is now fact Mirror(target: Term, access: MirrorAccess), with no allocation field (one policy is not a seam) and no Option on target (an ABSENT fact means no mirror). The field is target rather than forge because an export target need not be a forge -- Jira, Linear, a static site or a directory of files can all be one.

### 2026-08-21T01:02:11Z — feedback — claude

DELIVERED 2026-08-21. SHIPPED: the `Forge` carrier (`coordination.anthill`, bundled) with `Mirror`/`MirrorAccess`/`GithubForge`/`FakeForge`/`MirrorEntry`/`ForgeEntry`/`ForgeComment`; the gh and fake implementations plus five host fns registered through WI-1122's seam (`src/forge/{mod,gh,fake}.rs`); `export` and `import` in the bundle; `WorkItemStore.link_entry` and the `forget` cascade; the `ANTHILL_TODO_MIRROR`/`--offline`/`--mirror` ladder.

FIVE PLACES IT DIFFERS FROM THE SKETCH, each because building it made the sketch's reason lapse. (1) `Forge` has FIVE operations, not four: `target_name` was added because `MirrorEntry.target` has to be filled from somewhere and only the carrier can tell TWO GITHUB REPOS apart. (2) `list_entries` earns its place by ADOPTION -- under the narrowed scope nothing needed a listing, so it was about to ship with no caller; it now links an entry already on the target under the `<id>: ` title prefix instead of duplicating it, which is what makes a fresh clone or a lost link recoverable, and it is why §7.1's title prefix stays load-bearing after the allocator that motivated it was retired. (3) The body carries the DESCRIPTION -- §7.1's 'a pointer and nothing else of substance' was right for a body re-derived on every state change; export writes it once per run either way, and a pointer-only entry is one nobody on the target can act on. (4) `Feedback.author` is `<target>:<login>`, not `github:<login>` -- the design's spelling is the one-target special case, and naming the target is the same argument that put `target` on `MirrorEntry`. (5) `GithubForge` has NO `project` field: `add_to_board` is not in the narrowed op set, so nothing would have read it, and a declared field nothing reads is the silent skip the repo's rules forbid.

THE LINK IS A SATELLITE LIST LINE (`- mirrors: github:o/r=42`), exactly how `Tag` gives an item a set of tags. That needed `SatelliteList` to carry a LIST of written fields rather than one (document-mapping.md §3.2.1): `target` and `entry` identify a link only together, and the other repeated-satellite mapping writes its payload as PROSE. `MirrorEntry` coverage in `covers:` is required only of a project that HAS a mirror -- requiring it unconditionally would refuse, at startup, every existing tracker that cannot reach the failure the requirement prevents.

TWO STRUCTURAL THINGS FOUND WHILE BUILDING. The rust binding lives in a SEPARATE file (`coordination_rust.anthill`) from the declaration, on the `anthill.persistence` precedent -- and not for tidiness: a binding block naming a host function the runtime lacks is fatal for the WHOLE program, and anthill-core's own `store.anthill` type-check fixtures load the declaration without this binary behind it. Merged into one file it broke ten anthill-core tests, which is how it was found. And the `Forge` operations map at the SPEC level with one host fn each resolving the receiver to a backend, not per carrier: an `operation_map` key resolves as `<carrier>.<op>`, so per-carrier keying needs the carrier to be a SORT, and the config spelling `Mirror(target: GithubForge(repo: ...))` needs it to be an ENTITY.

NOT SHIPPED, and named rather than silently omitted: §7.1's entry OPEN/CLOSED state -- follow-up WI-20260820-8B6W0, which says why it is a design increment and not a parameter. §7.1's labels are absent too; that section already calls them optional.
