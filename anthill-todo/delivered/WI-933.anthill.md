## Description

A namespace-level bracket-less 'fact Spec' is SILENTLY DROPPED, while the docs say it means 'the sort declared in this namespace provides Spec'.

MEASURED (WI-931, by dumping every anthill.reflect.SortProvidesInfo fact of a full stdlib + host-bindings load): two such lines existed in the tree and NEITHER produced a provision.
  stdlib/anthill/persistence/filesystem.anthill  'fact BulkStore'     after entity FileStore(...)  -> no FileStore -> BulkStore edge
  stdlib/anthill/persistence/sql.anthill         'fact QueryableStore' after entity SqlStore(...)  -> no SqlStore -> QueryableStore edge
Their bracketed neighbours on the very next line (fact NonMonotonicStore[FileStore], fact NonMonotonicStore[SqlStore]) DID produce one, so this is the spelling and not the position.

WHY IT IS NOT AN AUTHORING SLIP. docs/rust-forward-mapping.md documents exactly this spelling, twice, as a FEATURE:
  'fact QueryableStore in the namespace where SqlStore is defined means "SqlStore is-a QueryableStore", which maps to implementing the trait'
  'fact QueryableStore in the SqlStore namespace becomes impl QueryableStore for SqlStore'
So a reader following the docs writes a line that reads as a declaration and does nothing. The same spelling INSIDE a sort body ('sort NonMonotonicStore { fact Store }') works and is what the store hierarchy is built from -- so the two positions disagree about what a carrier-less fact means.

WHAT MUST BE DECIDED, and it is one of two:
 (a) IMPLEMENT the documented reading -- derive the carrier from the enclosing namespace's sole/most-recent entity declaration. Note this is a guess by proximity, which is why option (b) may be better.
 (b) REFUSE it loudly -- a namespace-level 'fact Spec' over a spec with type params or operations has no carrier and cannot be a provision; report it at load and correct the doc. This is the project's stated 'prefer a loud error over a silent skip' direction, and it is what would have caught both stdlib lines the day they were written.
Whichever is chosen, docs/rust-forward-mapping.md must be corrected or confirmed IN THE SAME COMMIT -- it is currently the only written statement of the rule and it disagrees with the loader.

BLAST RADIUS TO MEASURE FIRST: how many bracket-less namespace-level 'fact X' lines exist across stdlib/, examples/, anthill-todo/ and the test corpus, and how many of those X are SPECS (rather than data sorts, where 'fact Color[Holder]' is a data fact and correctly not an edge -- see wi407_provider_edges_test's data_sort_fact_does_not_widen_* pins). Only the spec ones are in scope.

ACCEPTANCE: the carrier-less namespace-level spelling either produces the documented provision or is refused with a located diagnostic naming the spec and saying what to write instead; docs/rust-forward-mapping.md agrees with the implementation; a test drives both the namespace-level and the sort-body positions so they cannot silently diverge again; cargo-test green via rustland/scripts/test.sh.
