## Description

POLYTYPE: AN OPERATION TYPE IS A FORALL OVER AN ARROW, AND THE PAYOFF IS THAT A TYPE-PARAMETERIZED OPERATION CAN FINALLY BE A FUNCTION VALUE.

THE CAPABILITY, which is this ticket acceptance rather than its motivation. typing.rs:6274, in operation_as_function_value:

    // Only a type-parameterized op stays excluded: its arrow would carry unfreshened
    // type-param vars that alias across multiple eta-lifts of the same op.
    if !op.type_params.is_empty() { return None; }

So Iterable.map, find, filter, FiniteCollection.foldLeft and the finite-combinator collect/iterator CANNOT be passed as function values. WI-1063 recorded the same fact from the other end ("an arrow type has nowhere to write exists; it is why an operation with type parameters has no function-value form either"), and its eta site opens the existential once per LIFT rather than once per application for the same reason. An arrow has nowhere to put binders; a PolyType does.

THE SHAPE, decided with the user on WI-1079 (2026-08-11) and not re-opened here: a TypeExtractor VARIANT beside Arrow / Parameterized / NamedTuple, forall BY CONSTRUCTION, storing no quantifier —

    entity PolyType(binders: List[Symbol], body: Term)

— because every binder in anthill attaches to a DECLARATION, never to a free-floating type, so a mixed binder list has no position to arise in; and because the polarity rule makes the quantifier a function of POSITION, so a per-binder quantifier would let a binder tagged exists sit in a forall position. A binder carries NO BOUND (the grammar has none: kernel-language 5.4 says TypeParam ::= Name); bounds live at SORT level as requires clauses and are already reflected as SortRequiresInfo. AN OPERATION IS A FUNCTION FROM A NAMED TUPLE, which the reflect layer already says — Arrow(param, result, effects, arity) with WI-791 rule that at arity != 1 param IS the parameter list — so OperationInfo params/return_type/effects are a DECOMPOSITION of one type, and this ticket probably adds NO field to OperationInfo.

    empty : PolyType([A], Arrow(NamedTuple([]), List[A], {}, 0))

ANSWER THIS FIRST, AND IT IS THE ONE THING THE DESIGN DOES NOT YET COVER: WHO GENERALIZES, AND WHEN. WI-1078 delivered "a variable is bound by the signature" as a scan over THREE sources — parameter types, requires clauses, and the operation own [A] binders. A binder list is only the THIRD of those. mplus(a: LogicalStream[?A], b: LogicalStream[?A]) -> LogicalStream[?A] writes no brackets, so its type_params is EMPTY and ?A is a free logical variable shared across the signature. MEASURED: the params-dropped back-out of WI-1078 (which leaves requires + type_params intact) fails exactly wi1078_unbound_return_var_test::a_signature_bound_variable_is_left_flexible. So "bound iff the variable appears in the binder list" REFUSES A PROGRAM THAT LOADS TODAY unless PolyType construction GENERALIZES a signature free logical variables into binders. Decide where that happens — at load, at reflection, or at instantiation — and say what it does to a variable shared across two DIFFERENT declarations. Getting this wrong makes PolyType contradict WI-1078 instead of subsuming it.

THE SECOND THING TO SETTLE: WHAT INSTANTIATION FRESHENS. The aliasing the eta gate names is precisely un-freshened binders shared across two lifts of one operation, so per-use instantiation is the mechanism that retires it. State where instantiation happens for a function VALUE (which has no OperationInfo — only a type), and how it interacts with WI-1063 "once per lift" limit: with a PolyType result the existential could open per APPLICATION instead, which is a second capability worth measuring rather than assuming.

ACCEPTANCE: the eta gate second clause is DELETED and a type-parameterized operation is passed as a function value, applied at TWO different instantiations in one program, with the values asserted — not merely loaded; wi420_eta_of_curried_requires_op_is_loud_type_error keeps its loud verdict (WI-1063 measured that REFUSING the lift instead of opening it turns that into a clean load that crashes at eval); the generalization question above is answered in the ticket and at the construction site; kernel-language records PolyType as a type FORM and says which binders it carries; every seven-tier corpus load keeps its fact/rule totals; each test says which case fails when the change is backed out. cargo-test green via rustland/scripts/test.sh.

REFERENCE: WI-1079 (the three variable forms this builds on, and where this shape was decided), WI-1078 (the signature scan this must subsume, and the measurement that shows a bare binder list is not enough), WI-1063 (the existential opening, the eta lift once-per-lift limit and the refuted alternative), WI-700 (why a nullary op eta-lifts at all), WI-791 (arrow arity, which is what makes an operation type an arrow over a named tuple), kernel-language 5.4 and 5.6.
