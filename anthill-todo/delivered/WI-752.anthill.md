## description

Loader/name-resolution: UNIFY THE DOTTED-NAME LADDER ACROSS ALL RESOLVERS. Six resolvers in kb/load.rs resolve a dotted name, and they use FIVE different ladders; the divergence looks like accident, not design, and it is the drift that produced WI-729, WI-749, WI-750 and WI-751 in sequence -- each of those fixed ONE resolver and left the others spelling the same question differently. VERIFIED SYMPTOM (the headline, user-visible): the same spelling in the same scope resolves in TERM position and fails in TYPE position. `namespace app.util { sort T { entity t(v: Int64) } ; operation f() -> Int64 = 1 }` plus `namespace app { operation callSite() -> Int64 effects Error = util.f() ; operation typeSite(x: util.T) -> Int64 = 2 }` -- `util.f()` resolves via head-qualification, `util.T` fails `unresolved type name 'util.T' in scope 'typeSite'`. Cause: remap_name (load.rs 6877), the resolver for structured multi-segment Names (types, sort refs, entity/op names, proof targets), has the ABSOLUTE by_qualified_name rung but NO head-qualification rung at all, so it is missing the very rung that makes the term path work. INVENTORY (ladder per resolver, after WI-751): remap_name_str_inner 6645 (term functors/identifiers) = scope -> head-qual -> absolute(guarded) -> implicit -> forbid -> intern, the reference ladder; resolve_qualified_rule_readonly 8586 (bare + prefix rule citations) = scope -> head-qual -> absolute, agrees; qualified_name_resolves 8286 (the dot-call re-route gate) = ABSOLUTE FIRST -> scope -> head-qual, so it ranks absolute first while the resolver it gates ranks it last; remap_name 6877 (types/structured names) = scope -> absolute, NO head-qual; resolve_name_in_kb_opt 5647 (query patterns, a free fn over &KnowledgeBase) = ABSOLUTE FIRST -> scope -> implicit, no dotted gate, and it is the only one that resolves SHORT names absolutely (the WI-476 global-scan hazard); remap_symbol_strict 6845 (strict refs) = scope only, neither dotted rung. FOURTH ITEM, same family: a head-qualified hit that fails the `internal` visibility gate is TERMINAL -- accept_qualified_hit 6832 pushes ForbiddenInternalAccess and returns, never falling through to the absolute rung -- so a shadowing declaration carrying an `internal` member of the right name still breaks the path AND names a symbol the user never wrote (`namespace lib { operation util() }` + `sort lib { internal operation util() }` in the citing scope: reports "'lib.util' is internal to '<ns>.lib'"; rename only the internal member and the identical file loads clean via the absolute rung). CONSEQUENCES BEYOND THE TYPE-POSITION BUG: the qualified_name_resolves priority inversion lets the re-route DECLINE on the strength of an absolute hit that the resolver would have ranked BELOW a local reading, so a local rule receiver can be captured by a same-spelled foreign namespace; and loader-vs-query divergence means `anthill query` can bind the same dotted text to a different symbol than the program it queries. WHY ONE TICKET, NOT FOUR: the fix is a single shared ladder, and settling precedence four times independently is how the current five-way split happened. WHY THIS WAS NOT FOLDED INTO WI-751 (deliberate, not deferral-by-default): WI-751's fix was safe precisely because its new rung sits BELOW an existing one and fires only where nothing resolved -- strictly additive, no existing program changes meaning. Adding head-qualification to remap_name puts a rung ABOVE the existing absolute one, so a type name that resolves absolutely TODAY could start resolving scope-relatively; that is a silent meaning change for existing code and needs its own decision plus regression sweep. Same for demoting the absolute rung in qualified_name_resolves / resolve_name_in_kb_opt. THE DESIGN QUESTION, to settle ONCE: is WI-751's term-position ladder (scope-relative head-qualification OUTRANKS the bare absolute path; the absolute rung stands down when the head resolves to an owning NAMESPACE or resolves AMBIGUOUS; dotted-only, never short names) correct for ALL positions -- or do types / query patterns / the re-route gate have a principled reason to differ? Prior: they do not, and any survivor should be an explicitly documented exception. Note ONE known-deliberate exception to preserve: qualified_name_resolves is intentionally NOT visibility-gated and counts Ambiguous as resolving, because it asks 'does the qualified path have an ANSWER' (a forbidden-internal reference IS an answer, with a precise diagnostic that peeling the name into a member chain would bury). ACCEPTANCE: the dotted ladder is expressed ONCE and consulted by every resolver that resolves a dotted name, with any deviation carrying a stated reason at the deviating site; `util.T` and `util.f()` in the repro above resolve identically; the loader and resolve_name_in_kb_opt bind the same dotted text to the same symbol; a head-qualified hit hidden by `internal` falls through to the absolute rung rather than terminating (or the termination is justified in place); a test fixture exercises EVERY position -- term functor, type reference, rule citation, re-route gate, query pattern -- against the same source and asserts they agree, so a future rung cannot be added to one and forgotten in the others; docs/kernel-language.md 8.6 updated to describe the ladder as position-independent; WI-714/WI-723/WI-729/WI-749/WI-750/WI-751 suites unaffected; cargo-test green via rustland/scripts/test.sh. SCOPE: Rust-only (scaland has no operation loading and no dot-call/name re-route).
