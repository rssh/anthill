## Description

AN OPERATION CALL'S ARGUMENT COUNT IS NOT CHECKED AT LOAD — a wrong-arity call loads clean and fails only if that branch executes.

Reproduced against the built CLI, both directions, host-backed and anthill-defined:

  namespace probe.arity
    import anthill.prelude.String.{concat}
    sort Probe
      operation four_args() -> String = concat("a", "b", "c", "d")   -- concat is BINARY
      operation one_arg()   -> String = concat("a")
    end
  end

`anthill load` answers `loaded: 2602 facts, 176 rules` — no diagnostic. `anthill check` on the same file passes `128 pass, 0 failed`. A user-defined binary operation called with four arguments loads equally clean, so this is not a host-mapping gap: the loader/typer never compares a call's argument count against the callee's declared arity.

What happens instead, and both answers are wrong in a different way:
- THE EVALUATOR CATCHES IT, LATE. `EvalError::ArityMismatch` (rendered rustland/anthill-core/src/eval/error.rs:240 as `{op}: expected {expected} args, got {got}`) fires when the call actually runs. So the error exists — it is just deferred to whichever execution first reaches that expression.
- THE RESOLVER SWALLOWS IT. `anthill query -p probe.anthill 'probe.arity.Probe.four_args()'` answers `no solutions` — no error at all. A wrong-arity call on the resolution path is indistinguishable from a goal that legitimately has no answer, which is the silent-skip shape the repo's rules single out.

WHY THIS IS NOT ACADEMIC — the defect that surfaced it. WI-1097's duplicate-id store gate (rustland/anthill-todo/anthill/main.anthill) built its refusal message with a four-argument `concat`. The bundle loaded, the binary built, and the whole anthill-todo suite stayed green — because no test drove a store that actually HAD a duplicate. The error appeared only on the first store with a collision, i.e. the error path of an error-detection gate was itself broken, and only a test that drove the refusal found it. Any diagnostic branch, any rarely-taken `case`, carries the same exposure.

WHERE THE CHECK BELONGS: the typer (rustland/anthill-core/src/kb/typing.rs) already resolves an operation call to its declaration, which carries the arity; `typing.rs:697` even names 'arity blindness' as a hazard on the mismatch-rendering path. The count comparison is available wherever the callee is resolved. Named arguments and defaults mean the rule is not a bare integer compare — the check must be 'every declared slot is filled exactly once, and no argument names or occupies a slot that does not exist' — so it should reuse whatever the named-argument binder already computes rather than re-deriving it.

EXPECT EXISTING OFFENDERS. Turning this on will refuse files that load today; a wrong-arity call sitting in a never-executed branch is exactly what this ticket says is invisible, so finding some is the point, not a reason to weaken the check. Fix them, do not soften the rule to a warning.

Acceptance (each DRIVES the check, not just 'it loads'):
- a file with a host-backed binary operation called with 4 args is REFUSED by `load`, with a diagnostic naming the operation, its declared arity and the count given. FAILS before (loads clean today), passes after.
- same for 1 arg (too few, not just too many). FAILS before.
- same for an anthill-DEFINED operation called with the wrong count — pins that the rule is about declarations, not about host mappings. FAILS before.
- a correct-arity call still loads, and a call using NAMED arguments / omitted defaulted slots still loads. Passes either way by design: this is the false-positive control, and it is the half most likely to break the stdlib.
- the resolver path no longer answers `no solutions` for a wrong-arity goal — after the load-time refusal such a file never reaches the resolver, so assert the refusal, not the query.
- the whole workspace suite still passes, which is where any pre-existing offender will show up.
