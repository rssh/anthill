## Description

Parse/grammar BUG: a COMMENT line immediately preceding an operation declaration breaks scope of names in that operation's requires/ensures clause -- they resolve at the ENCLOSING NAMESPACE scope instead of the OP scope, so op-type-params (and other op-local names) silently become unresolved. MINIMAL REPRO: 'namespace m / sort Eq { sort T = ? } / -- doc / operation f[T](x: T) -> T requires Eq[T = T] end' emits 'unresolved name T in scope m' (namespace, not op 'f'); DELETE the '-- doc' line and it resolves cleanly. A blank line between the comment and the op does not help. The RETURN type is unaffected (only the trailing requires/ensures clause breaks), pointing at a comment-node attachment shift in the CST->IR conversion (tree-sitter-anthill grammar.js and/or parse/convert.rs) that mis-associates the trailing clause or mis-wires the op scope -- a cousin of WI-446's trailing-attachment quirk. SEVERITY: latent / silent -- it is a WARNING, file still checks green (violates loud-error-over-silent-skip: the clause binds to a namespace-scoped unresolved symbol rather than the op-type-param). Does NOT break the stdlib today (no stdlib op uses an op-level requires). Surfaced during WI-383 probing (the explicit-bound 'requires Resource[C=T]' licensing surface): a DOCUMENTED operation with a requires clause mis-resolves. SCOPE: parse/grammar only (NOT typing). Acceptance: cargo-test green + the repro resolves the op-type-param in the requires clause to the OP scope regardless of a preceding comment.
