## description

SCALAND: `typeExprSpan` RE-DERIVES ITS ANSWER AT EVERY RECURSION LEVEL — O(n^2) in nested type depth. FOUND by /simplify on WI-961 (2026-08-03). MECHANISM: `typeExprToRef`'s `Arrow` arm computes `val span = typeExprSpan(arrow)`, which walks the whole remaining chain to find the first located leaf — O(n). It then recurses into `typeExprToRef(ret)`, which independently recomputes `typeExprSpan` over the SAME subtree it just walked. Total O(n) + O(n-1) + ... = O(n^2) for a right-nested chain like a curried `(A) -> (B) -> (C) -> D`. `namedTupleTypeTerm` compounds it with a further ~2x constant: for a tuple field whose type is an arrow, `typeExprSpan(ty)` runs once for `fieldSpan` and again inside the recursive `typeExprToRef(ty)`. CURRENTLY INERT, and the reasons are worth keeping because they are what makes this safe to defer: (a) an operation PARAMETER type is kept as IR and never lowered by the parser, so `typeExprToRef` is only entered from TERM position — typed vars, instantiation arguments, `let` annotations, bounded quantification; (b) hand-written .anthill nests arrow/tuple/effect types 2-3 deep at most, and nothing in the stdlib or in `ParseSpanCoverageTest`'s corpus nests an arrow inside an arrow. At depth <= 5 the difference is invisible. FIX DIRECTION: stop re-deriving from the raw `TypeExpr` — the children are BUILT either way, so each level can read its children's spans back in O(1) via `terms.spanOf(childId)`, or the once-computed span can be threaded down as a parameter to the recursive `typeExprToRef` calls. ACCEPTANCE: a parse of a type nested ~50 deep in term position, with the term count or a timing assertion showing linear rather than quadratic growth; state which test fails when the change is backed out. WATCH: whichever fix is chosen must not weaken WI-961's invariant — `ParseSpanCoverageTest` must stay green, and blanking the derived span must still fail exactly the corpus case.
