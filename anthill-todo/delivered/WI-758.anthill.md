## Description

WI-509 gap found while delivering WI-730: field_access_projection_type (kb/typing.rs) -- the RE-TYPE of a desugared 'field_access(recv, "f")' back to the FIELD's type -- has no NAMED-TUPLE receiver arm. It resolves the field only through sort_functor_of_view + field_constructors_of_sort, i.e. an ENTITY/sort receiver. A NAMED TUPLE has functor 'named_tuple', not a sort, which is precisely the case WI-638's THIRD dot-dispatch mode exists for: that mode types 't.x' on a named-tuple receiver and REWRITES it to a synthesized 'Apply{field_access, [recv, Const::String("x")]}' whose type it stamps directly. So the forward direction (DotApply -> field type) handles named tuples and the reverse (re-type of the rewritten node) does not -- and when the rewritten body is re-typed, that node is checked against the DECLARED reflect signature 'field_access(object: Term, field: Symbol)' and fails 'type mismatch in field_access.field (op-arg): expected Symbol, got String' -- a diagnostic naming an internal desugaring, not anything the user wrote. REPRO (today, via the only path that re-types such a body): 'person_row.where(lambda c -> not(eq(c.name, "alice")))' BEFORE WI-730 -- the [simp] rewrite where <=> guarded_of fires and REWRITES the body, guarded_of then declines (it could not compile the nesting), the kept template is re-typed, and the lambda body's already-synthesized field_access nodes surface this error instead of anything about the condition. WI-730 removed that particular trigger by making the nesting compile, but the gap is untouched and will resurface on any future re-type of a body carrying a mode-3 synth node. FIX DIRECTION: give field_access_projection_type the same named-tuple arm its forward twin has -- when the receiver type extracts as TypeExtractor::NamedTuple(fields), resolve the component by name and return its type -- so the forward and reverse directions agree on which receivers have fields; a receiver that is neither a sort nor a named tuple keeps falling through to ordinary op typing (the genuine field_access call). Check the WI-369 companion field_access_owning_ctor for the same asymmetry (internal-field visibility on a named-tuple projection). ACCEPTANCE: a named-tuple field access survives a re-type round-trip (a regression test that re-types a body containing one and asserts the field's type, not the reflect signature); the existing WI-638 / WI-509 tests stay green; cargo-test green via scripts/test.sh.
