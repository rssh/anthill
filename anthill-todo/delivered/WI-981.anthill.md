## description

R4's CAPTURE CLAUSE (proposal 059) is a change to behaviour the spec currently
PERMITS. Measure the migration before implementing it.

MUST AGREE WITH docs/proposals/059-secondary-entries.md R4, third clause, which
defines the rule: no declaration may CAPTURE a name that already resolves in the
sort's scope. Do not re-decide the policy here; if the migration cost makes the
rule untenable, amend 059 rather than diverging from it.

THE HAZARD, MEASURED (all three rows drive `Rec(n: 0).use()` after load):

  namespace lib
    operation f(x: Int64) -> Int64 = 1
  end
  namespace app
    import lib.f
    sort Rec
      entity Rec(n: Int64)
      operation use(r: Rec) -> Int64 = f(r.n)    -- bare `f` -> the import
    end
    ...
  end

  base, nothing else added                        => 1
  + `namespace Rec  operation f(...) = 2  end`    => 2   (a SECOND ENTRY)
  + the same operation in Rec's OWN body          => 2   (the CONTROL)

The unedited body changed meaning in both cases. Note the control: this is NOT
created by secondary entries, so the fix belongs to the SCOPE, not to secondary entries --
an entry-local patch would be aimed at the wrong object and would split the one
shared scope 059 R2 rests on.

ALREADY KNOWN, AS A CAUTION: kernel-language.md §6.3 records exactly this for the
long form (WI-935) -- "Mind the short name ... the new member is a second binding
for it, and an `import ns.{f}` elsewhere may bind to the member rather than to
the namespace-level `f` -- silently, since both are legal (measured)". 059 R4
turns that caution into a refusal, for both spellings at once.

ALSO COVERED by the same clause, so the measurement must include them:
  - IMPORTS are shared across all entries of a scope, MEASURED in both
    directions: an import written in a secondary entry resolves a bare name in the
    sort's BODY (=7, against a control with the import deleted that fails
    `unknown functor`), and an import in the body resolves one in the entry (=9).
    So an import is a capture route exactly as a declaration is.
  - CONSTS capture too: a secondary entry `const K` shadows an imported `K` (=2,
    control =1). (A const is NOT a member -- `X.K` and `receiver.K` resolve to
    nothing in EITHER placement -- it is a name in the sort's scope. See 059 R2.)

THE MEASUREMENT THIS TICKET IS FOR, and it gates the rest: across stdlib,
anthill-stl, examples/ and every fixture, count the declarations whose SHORT NAME
already resolves in the scope they are declared in -- i.e. the sites the new
refusal would reject. Report the count and the sites BEFORE changing behaviour.
Zero means the rule can simply land. Non-zero means it needs a migration and
possibly a narrower rule (e.g. refuse only where the captured name is reached by
IMPORT, not by an enclosing declaration), which is an amendment to 059.

WATCH FOR a false positive that would inflate the count: a member legitimately
sharing a spelling with something in an UNRELATED scope is not a capture. The
question is only whether the name resolves at the declaring scope, by the same
ladder `resolve_in_scope` runs.

ACCEPTANCE: the count and the site list are reported first. Then, if the rule
lands: a capturing declaration is a load error naming both the declaration and
what it would capture; a test drives the three rows above (base => 1, second
entry => refused, own body => refused) plus one row per capture route (operation,
const, import). Say at the test site which rows fail when the fix is backed out.
cargo-test green via rustland/scripts/test.sh.

  (stdlib alone: 56 = 4 + 33 + 19; examples/anthill-todo add 7, all enclosing)

SO THE CLAUSE CANNOT LAND AS WRITTEN -- 63 refusals, including the stdlib's
central pattern. Nor does the narrowing this ticket anticipated rescue it:
"import route only" is 4 sites, and all four are `FiniteFilteredStream.collect`
/ `FiniteMappedStream.iterator` and kin -- a sort declaring the operation of a
spec whose name it imported. Legitimate overrides, every one.

MOST OF THE 63 ARE NOT MEMBER DECLARATIONS AT ALL, and should never have been in
scope:
  - PARAMS. `Float.pow.exp`, `String.contains.sub`, `KB.assert.kb` and many more
    are an operation's PARAMETER shadowing an operation name. A binder is not a
    declaration.
  - TYPE NAMES. `IndexedSeq.Effect` over `prelude.Effect`, `TypeExtractor.Error`
    over `prelude.Error`, `logic.Classical.Classical` over its own namespace.
    Dot dispatch never routes through these.

RESTRICTED TO THE R4-RELEVANT SHAPE -- a declared OPERATION capturing an
OPERATION:

  25 total  =  import 4  +  enclosing-scope 2  +  requires/provides 19

  23 of the 25 are the OVERRIDE pattern: a member implementing an operation of a
  spec the sort requires/provides (`List.length` over `IndexedSeq.length`,
  `List.head` over `Stream.head`, ...), reached either through the requires
  parent link or through an import of the spec's member. Refusing these would
  refuse the way the standard library is written.

  EXACTLY 2 have no override relationship, and both are the P1a shape -- a sort's
  operation shadowing a namespace-level operation of the same name:

      anthill.reflect.KB.nonvar   captures  anthill.reflect.nonvar
      anthill.reflect.KB.ground   captures  anthill.reflect.ground

VERDICT. The only formulation with a defensible blast radius is: refuse a MEMBER
OPERATION that captures an OPERATION with NO OVERRIDE RELATIONSHIP -- the
captured name is not a member of a spec the declaring sort requires or provides,
nor imported from one. That is 2 sites, both in anthill.reflect, and both would
need a decision (rename, or exempt as intentional) before it lands.

WORTH WEIGHING BEFORE IMPLEMENTING: at 2 sites, a WARNING may be the right
instrument rather than a refusal -- WI-346 already warns for the neighbouring
requires-shadow case, and this would be its sibling. That is a call for the
proposal (059 R4), not for this ticket; 059 has been updated with the numbers.

NOT MEASURED: inline test fixtures. The corpus above is what is on disk; a
fixture that captures would be found by the guard test when the rule lands, not
by this count.
