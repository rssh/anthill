## Description

SCALAND: A MISSED `allocAt` SILENTLY REINTRODUCES A LOCATIONLESS DIAGNOSTIC, and nothing fails when it does. WI-957 gave `SimpleTermStore` a TermId->Span table and located every name-bearing allocation site that a resolution path reaches. The COVERAGE IS CONVENTIONAL, NOT ENFORCED: `alloc` and `allocAt` are both public and equally easy to call, so the next parser production that mints a resolvable functor — a new desugar, a new literal form — compiles clean with `alloc`, and the only symptom is an `AmbiguousSymbol` (or a future located diagnostic) that renders with no position. That is exactly the WI-947/957 bug, silently restored. WHY THE LINE IS EASY TO GET WRONG, from WI-957's own review: 'the functor looks synthetic' is NOT the criterion. `Loader.reallocTerm` resolves the functor of EVERY `Term.Fn` it walks, so `unify`, `ho_apply`, `ListLiteral`, `SetLiteral` and `TupleLiteral` — all pure desugar markers — reached `resolveName` and reported locationless; WI-957's first draft cited `ListLiteral` as an example of a SAFE marker and was wrong. Only the markers `convertExprTerm` dispatches on BY NAME (`if_expr`, `pattern_var`, ...) and the `TypeExtractor.*` type lowerings are genuinely shielded, and that shielding is an emergent consequence of two unrelated pattern-matches, not a stated invariant. OPTIONS, roughly increasing depth: (a) a test-only assertion that no `LoadError` carrying a resolvable NAME is ever raised with `Span.empty`, run over the whole embedded stdlib load — cheap, catches a regression the moment any stdlib construct trips it, but blind to surface forms the stdlib does not use; (b) make the distinction structural — a distinct constructor (`allocSynthetic`) whose name states the claim, plus a narrowed `alloc` that REFUSES a `Term.Fn`/`Ref`/`Ident` whose functor is not in an explicit shielded set, so a new name-bearing marker cannot reach the store without a decision; (c) carry the shielded set in ONE place that both `convertExprTerm`'s dispatch and the store consult, so 'this marker never reaches resolution' stops being two facts that happen to agree. ACCEPTANCE: introduce a NEW parser production that mints a resolvable functor via `alloc`, and show the chosen mechanism fails — a green suite with that production present is the thing this ticket exists to prevent. NOTE the enforcement site comments in `IR.scala` (`spans`) and `Loader.resolveName` already state the invariant this would enforce.
