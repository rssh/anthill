## Description

Investigate why eq_neq_emit_double_equals test required load_kb_with_lenient under WI-264, and restore it to load_kb_with. The cpp-gen test environment loads stdlib/anthill but not the per-language binding files (rustland/anthill-stl/anthill/*.anthill where fact Eq[T=Int] / Ordered[T=Int] / Numeric[T=Int] live). Stdlib has fact Eq[T=Type] (in anthill/prelude/sort.anthill), so calling eq(a, b) with a:Int, b:Int triggers DispatchOutcome::NoMatch (candidates exist but none match) rather than DispatchOutcome::NoCandidates (no candidates -> legacy permissive path). Pre-WI-264 the typer eprintln'd and silently returned None, so the cpp-gen pipeline still emitted == output and the test passed. Post-WI-264 the strict Result propagation surfaces DispatchNoMatch as a load error, failing the test. Workaround applied: switched the test to load_kb_with_lenient so cpp-gen still emits despite the typer error. Proper fixes to evaluate: (a) make the cpp-gen test environment include a cpp-binding facts file (parallel to rustland/anthill-stl/anthill/int.anthill) so Int's Eq impl is registered for dispatch; (b) treat NoMatch the same as NoCandidates when the only candidate is the generic Eq[T=Type] umbrella (semantic change: umbrella spec impl does not gate concrete-type dispatch); (c) split Eq[T=Type] out of stdlib and put it behind a Rust-binding-style provides block. Cross-check Numeric and Ordered: both stdlib-only currently produce NoCandidates so add(x,y) on Int still type-checks under cpp-gen - the asymmetry is the Eq[T=Type] fact specifically. Acceptance: revert load_kb_with_lenient back to load_kb_with in anthill-cpp-gen/tests/expr_body_e_test.rs::eq_neq_emit_double_equals, cargo-test green, no regressions in other cpp-gen tests. Driver follow-up to WI-264 - the strict Result propagation correctly surfaces this dispatch gap that the legacy None-return masked.
