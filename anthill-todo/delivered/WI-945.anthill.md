## description

A SORT-level requirement element nothing pins dies at EVAL, where §5.2 says it is a LOAD error -- and the OP-level twin of the same shape IS refused at load.

MEASURED 2026-08-02 during WI-942 (probe S / probe T on the post-WI-942 tree).

DIES AT EVAL (sort-level):
  sort HolderVS
    sort V = ?
    sort F = ?
    requires VectorSpace[V, F]
    operation twice(a: V) -> V = VectorSpace.vec_add(a, a)
  end
  sort Driver
    operation drive(a: Vec3) -> Vec3 = HolderVS.twice(a)
  end
LOADS CLEAN, then:
  internal evaluator error: DeferToRequirement: requirement param `__req_vectorspace`
  not bound in caller frame (running `HolderVS.twice`, requires-chain owner `HolderVS`)
The call pins V = Vec3 from its argument; NOTHING pins F, so `build_concrete_dispatch_dict` returns None and the callee frame is entered with no dictionary.

REFUSED AT LOAD (op-level, the same missing element):
  operation twice[V, F](a: V) -> V requires VectorSpace[V, F] = VectorSpace.vec_add(a, a)
  operation drive(a: Vec3) -> Vec3 = twice(a)
  -> type mismatch in ....twice.type_arg: expected a type for 'F',
     got unconstrained -- use `twice[F = ...](...)`
which is the RIGHT behaviour and names the fix. Writing `twice[F = Float](a)` loads and answers Vec3(2.0, 4.0, 6.0) (vec3_ops_test::a_generic_consumer_of_vector_space_loads_and_dispatches drives it).

THE DISAGREEMENT IS THE FINDING. docs/kernel-language.md §'Requirement supply at a call site is checked at load' (WI-828) states the rule for BOTH: 'A requirement element left genuinely unconstrained at the call ... is a load-time error naming the requirement, the unconstrained element, any σ-refused covering entry, and the construction outcome. There is no fallback semantics: ... deferring the failure to evaluation would be a clean load that crashes at run time.' The sort-level route does exactly the thing that sentence forbids.

CONTROL that isolates it to the UNPINNED ELEMENT and not to the sort-level route: pin F concretely in the holder's own clause --
  sort HolderVS
    sort V = ?
    requires VectorSpace[V = V, F = Float]
    operation twice(a: V) -> V = VectorSpace.vec_add(a, a)
  end
-- and the identical Driver call answers Vec3(2.0, 4.0, 6.0). So the machinery works; what is missing is the refusal when an element is left open.

NOT ROOT-CAUSED. `build_concrete_dispatch_dict` is documented to return Ok(None) for a same-sort call OR when a requirement fails to project outside the WI-828 refusal signature, and WI-828 already turned the σ-refused case into a load diagnostic. The unconstrained-element case appears to fall in the Ok(None) hole rather than the Err(RequirementRefusal) one. Lead, not a diagnosis -- read `build_concrete_dispatch_dict` / `RequirementRefusal` before assuming.

PRE-EXISTING, not created by WI-942 (which touched the op-scoped σ bridge and the runtime carrier reader, neither on this path).

ACCEPTANCE: the two routes AGREE -- the sort-level shape is refused at LOAD with a located diagnostic naming the requirement and the unconstrained element, in the same words the op-level one already uses. Driven: the refusal asserted, AND the F-pinned control still answering Vec3(2.0, 4.0, 6.0) so the fix is a refusal and not a regression. cargo-test green.
