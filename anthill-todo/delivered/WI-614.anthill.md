## description

Typer: dot-dispatch a REQUIRED-spec's member on a receiver whose static type is the requiring spec. A value of type FiniteCollection[C=..,Element=..,E=..] (e.g. the WI-599 thin FiniteCollection.map/filter result) cannot resolve Iterable-only members .find(p)/.isEmpty()/.iterator() via dot-dispatch: it errors 'FiniteCollection.isEmpty: no such member (dot dispatch)' because dot-dispatch searches the receiver spec's OWN members (and PROVIDED specs) but NOT the members of specs it REQUIRES. FiniteCollection requires Iterable[C=C,Element=Element,E=E], so a FiniteCollection IS walkable and Iterable ops are sound on it. Reproducer: 'operation f(xs: List[T=Int64]) -> Int64 = match xs.map(inc).find(is_big) case some(v) -> v case none() -> 0' fails (find not found on the FiniteCollection map-result). WI-599 works around it by collect-ing to a List first (List -> Stream -> Iterable transitively; see wi492/wi278 tests). DISTINCT from WI-612 (abstract-E effect threading on a bare Stream) and WI-608/609 (carrier-param call-site grounding). FIX SKETCH: dot-dispatch member resolution on a Spec[..]-typed receiver should also consider members of specs Spec REQUIRES (traverse the requires-graph as it does provides), binding the required-spec's params from the requiring-spec's own (FiniteCollection.Element/E -> Iterable.Element/E). ACCEPTANCE: xs.map(f).find(p) / xs.map(f).isEmpty() on a thin FiniteCollection map-result type-checks; wi492 can drop its collect-first workaround; cargo-test green.
