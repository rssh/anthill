## Description

`require[X]` — bring a requirement dictionary into a rule clause's environment, so body calls that need one can be PASSED it, instead of only checking that it exists. DESIGN: `docs/design/requirement-channel.md`.

SURFACE, NO GRAMMAR CHANGE. `require[X]` already parses in a rule body: WI-311's `application` is the UNIFIED type/term application (it absorbed the old `instantiation_term`), the converter classifies type-vs-term BY POSITION and builds functor + pos_args + named_args (`convert.rs:2312`), and the path `application` in `_non_name_atom_term` in `_atom_term` in `_term` in `_goal` in `rule_body` is open. What is added is an INTERPRETATION, not a production.

  p(?x,?y) :- requires(Eq[T]), eq(?x,?y)       -- today. Checks only
  p(?x,?y) :- require[Eq[T]], eq(?x,?y)        -- new. In scope for the clause; eq dispatches through it
  p(?x,?y) :- ?d = require[Eq[T]], f(?x,?d)    -- named, when the author wants to pass it by hand

THREE SPELLINGS, THREE THINGS, NO OVERLOAD: `requires <T>` DECLARES a slot (sort/op level, `grammar.js:584`, untouched — `requires` is already overloaded three ways in declaration position and needed `prec.dynamic(1)` to break a GLR tie a COMMENT could flip, `grammar.js:590`; do not add a fourth); `require[X]` DENOTES a dictionary in term position; `anthill.kernel.find_dictionary` (`kb/load.rs:2345`) is the KERNEL RELATION both lower to, gaining an output argument.

FORMALIZED AS A RULE TRANSFORMATION DURING TYPING — after elaboration the "environment" does not exist at run time at all. Per rule body: (1) each `require[X]` goal becomes `find_dictionary(X, ?d)` with a FRESH `?d` (the author's own variable when written `?d = require[X]`); (2) each body call covered by X carries `?d` in its requirements channel; (3) attribution — which call is covered by which require — is WI-613's σ-class matcher (`find_requires_slot` / `find_requires_location`), reused wholesale. BOTH HALVES EXIST ONE PHASE AWAY: `record_find_dictionary_grounding` (`typing.rs:40046`) already rewrites rule bodies at typing time (walks `kb.live_rule_ids()`, rebuilds the goal list, `set_rule_body_nodes`) — it just rewrites into a CHECKING goal; and `req_insertion::run` (`kb/req_insertion.rs:46`) already performs step 2's weave but walks `kb.op_bodies` ONLY, never rule bodies. This is that weave extended to rules — `requirement-dictionaries.md` §3.3's "the op-body weave transfers to rules in full", with its Γ slot replaced by an ordinary logic variable.

THE CALL SITE DRIVES IT; `require[X]` IS ONLY THE EXPLICIT FORM. A body call to an operation whose sort declares `requires` needs no author-written anything: the transformation reads the callee's dictionary chain (`provider_dict_entries` / `synth_req_names` — the SAME producers `resolve_bridge_requirements` reads, so there is one list, not two) and synthesizes one `find_dictionary` goal per slot — `... op(a,b) ...` becomes `... find_dictionary(X, ?dx), find_dictionary(Y, ?dy), apply_within(fn = op, args = (a,b), requirements = [?dx, ?dy]) ...`. PLACEMENT: immediately BEFORE the call each goal serves. `?dx`/`?dy` are bound FROM THE BODY, so they must be bound before the call reads them — and as late as possible, because resolving them needs the carrier type, which comes from the call's own arguments and may itself only be bound by earlier body goals. Immediately-before satisfies both: no delay in the common case, and the transformation stays local (no whole-body reordering). Placement is not a CORRECTNESS condition — a goal reading an unbound dictionary variable delays until it is bound, which is what keeps a hand-written `require[X]` sound wherever the author puts it; it is what makes the generated case not pay for that safety net. `apply_within` is the EXISTING carrier (`req_insertion` already emits exactly this for op bodies), so no new node kind. An author-written `require[X]` simply PRE-BINDS one of those variables, which the generated goal meets in its BOUND mode (check by unification). Automatic is the default; writing it is how you name or share one.

EMIT A GOAL ONLY WHERE THE TYPER DID NOT ALREADY PIN. Where the 058 §3.2 ladder resolved the witness at compile stage the dict is already built and installed (`ConcreteApplyWithin.dispatch_dict`, WI-415); synthesizing a run-time goal there is a straight pessimization of a solved case. The generated goal is the FALLBACK for what the typer could not pin — in a rule body the common case, because the carrier is often unbound until run time.

NOT A BREACH OF 058 §3.9 ("instances are never CHOSEN at run time"), though it looks adjacent: §3.9 forbids CHOOSING, and `find_dictionary` is deterministic — at most one answer, a tie refused. WI-300's guard already resolves from the runtime binding, so a rule body resolving at run time is the established precedent; 058 §4.2 puts rule bodies out of scope for selection precisely because the typer often cannot pin there.

REQUIREMENTS STAY ON THE RIGHT OF `:-`. `rule_heads` is `commaSep1($._goal)` — the same `_goal` as the body — so `require[X]` parses and converts on the left too. But a multi-head rule CONCLUDES each head (each becomes its own rule; the rule must carry a label for a unique citation handle, `load.rs:15613`, `:15623`), so a `require[X]` there would ASSERT the requirement rather than demand it. Considered and rejected on semantics, not on parsing.

CONSEQUENCE: THE RESOLVER GETS NO NEW CONCEPT. After elaboration a rule body is goals and arguments; `ResolverFrame` is untouched. An earlier draft of the design gave it a `requirements: [(Symbol, VarId)]` slot map inherited on push like `assumed_facts` — DROPPED, that was eval's shape imported where it does not apply (eval needs a frame slot because its variables are frame locals; a clause's are clause-scoped already). Likewise NOT Γ (`ResolveConfig.gamma`, `resolve.rs:367`, is a fact overlay global to one resolve call, seeded only by `prove_from_gamma` — not per-activation, not backtrackable).

WHY A DICTIONARY NEEDS NO NEW CARRIER: an arena slot is `{ functor: Option<Symbol>, requirements: Option<SmallVec<[RequirementHandle]>> }` (`eval/requirement_arena.rs:28`) — an impl symbol and its sub-dictionaries, no closure, no host handle, no value. So a dictionary is exactly a first-order term `Dictionary(sub_0 .. sub_n-1, impl: S)`, and WI-1019's `TermView` already presents it as precisely that, totally and losslessly (`kb/term_view.rs:2228`, `:2322`, `:2364`, `:2386`). Matchability is not a property to engineer — a dictionary that could NOT be matched is not constructible. σ already binds `VarId -> Value` (`kb/subst.rs:60`) and `Value::Requirement` is a `Value` (`eval/value.rs:127`).

SEMANTICS of the lowered `find_dictionary(X, ?d)` — a FUNCTION, never a generator: at most one ANSWER, because 058 §3.9 forbids choosing an instance at run time; a tie is REFUSED loudly naming the candidates, never enumerated as two solutions. Unbound `?d` + ground X + unique provider: resolve `provides`, construct, BIND. + no provider: FAIL. Non-ground X: DELAY — the resolver's ordinary delay, replacing the bespoke `FindDictOutcome::Suspend` (`typing.rs:37635`); an unbound var IS the undecided state. BOUND `?d`: CHECK by unification — the mode a caller-supplied dictionary takes ("run time only copies it along", 058 §3.9).

058 §3.9 COMPLIANCE, and why the bracket does not breach it: §3.9 permits a dictionary VALUE to fill an ANONYMOUS slot but never a named one ("a named slot is a type parameter, and a value cannot determine a type"). The bracket in `require[X]` is on the INPUT side — it names the spec instance being asked for, exactly as 058 §3.3's `f[Spec = W](...)` does. The OUTPUT `?d` is an ordinary logic variable in term position, not a type parameter, and is not addressable in any type. DO NOT read the bracket as making `?d` a type parameter — the one misreading this spelling invites.

CONDITIONAL PROVISIONS DECIDE THE REPRESENTATION (058 §3.8, delivered WI-869). A conditional provision IS a Horn clause over `provides`, so resolving `find_dictionary` over it is ordinary SLD. But it settles what rides in σ: a TERM, not an arena handle. A conditional provision makes a PARTIALLY RESOLVED dictionary reachable — `Eq[Pair[Int64, ?B]]` pins the outer impl while `?B` is unbound, so one sub-dictionary is not yet known. A term represents that natively (`Dictionary(impl: PairEq, d_A, ?d_B)`, refined later); a HANDLE CANNOT, because an arena slot's subs are `SmallVec<[RequirementHandle]>` with no variable inhabitant. The handle stays eval's form, where everything is ground by construction; the boundary converts.

SETTLE BEFORE WRITING THE READ — the one genuine interaction with WI-869. WI-869 made strictness PER-PROVISION: a slot is demanded when it is sort-level or a condition of the provision dispatched, "otherwise left unfilled, and reading an unfilled slot is refused at the read". In the term model an unfilled slot is an UNBOUND VARIABLE, so the natural reading of that read is DELAY, not refuse — and a later binding could fill a slot the dispatched provision never promised. Refuse-vs-delay here is a SOUNDNESS decision, not a diagnostic-quality one. Decide it first, and say at the site which of WI-869's four producers the answer is keyed to.

CROSSINGS (the payoff — "pass it to operations that require dictionaries"): `bridge_op_to_eval` reads the clause variable's σ-value and installs it into the callee's `eval::Frame::requirements`, where a body's `var_ref(__req_*)` reads it; where the clause has no covering `require`, `resolve_bridge_requirements` (`typing.rs:14667`) re-derives at the concrete argument types as today — supplying beats re-deriving only where re-derivation cannot decide (Unresolvable / Ambiguous, WI-855). `prove_rule_predicate` (`resolve.rs:4788`) hands the eval caller's `frame.requirements` to the goal so a lowered `find_dictionary` CHECKS rather than re-resolves; today they are dropped entirely. FOOTGUN to pin at the site: two scratch interpreters are two arenas, so handles from different crossings must be compared STRUCTURALLY (the WI-1019 view), never by `raw()`. A handle stays valid after `run_in_bridge_interp` drops its interpreter because it owns an `Rc` to its arena (`eval/requirement_arena.rs:90`, `:167`).

RESOLVES an open question elsewhere: `requirement-dictionaries.md` §3.4's "[Open] whole-rule vs positional requires" was open only under the Γ substrate. With a clause variable, a goal reading it before `require[X]` binds it sees an unbound var and DELAYS — ordering is a performance question, not a correctness one. Already amended in that doc.

ACCEPTANCE — each test DRIVES the capability (resolve the goal, assert the value; "it loads clean" is not evidence) and says at its site which case fails when the change is backed out: (a) `require[X]` in a body puts the dictionary in scope and a body spec-op call dispatches through it — assert the supplied impl's value, with the control that impl and spec default return DIFFERENT values; (b) the named form `?d = require[X]` binds and can be passed by hand; (c) a bound `?d` is CHECKED by unification, not re-derived — control: it differs from what re-derivation would pick; (d) a non-ground carrier DELAYS and re-fires once bound; (e) a provider tie is refused loudly and does NOT yield two solutions; (f) the existing arity-1 `requires(X)` form and every WI-300 guard-tier test behave exactly as before. `cargo-test` green via `rustland/scripts/test.sh`.

CONSUMERS: WI-1037 needs only the crossing half (and is otherwise independent — see its description); WI-070 (`Branch`) with WI-069 (`Suspension` snapshot/resume) — jointly 027.2's eval-to-SLD switch — get per-branch dictionaries FOR FREE, since a dictionary is a term bound in σ and each branch has its own σ, and being immutable it needs none of 047 §8's `register_undo` machinery. Sequencing note, deliberately NOT a dependency edge in either direction.
