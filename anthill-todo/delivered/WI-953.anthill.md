## Description

RUSTLAND'S FOUR SCAN/LOAD WALKS EACH RE-SPELL THE SAME NAMESPACE/SORT RECURSION, and a missing scope is a SILENT SKIP in three of them. The scaland twin was fixed under WI-949 (2026-08-03); the rust side is untouched and is the reason this is a ticket. TODAY (rustland/anthill-core/src/kb/load.rs): `scan_items_pass1` (~2685), `scan_items_pass2` (~2948), `scan_items_pass3` (~3016) and the phase-2 `load_items` (~13261) each derive the child scope the same way — join_segments -> make_qualified(prefix, name) -> `find_scope_by_name` (~3087) -> recurse with the new (scope, prefix) — and differ ONLY in what they do at a rule / operation / import / requires item. THE MISS HAS NO SINGLE ANSWER: pass 2 and pass 3 both write `if let Some(scope) = find_scope_by_name(..)` and drop the whole subtree with NO diagnostic (pass 3 does not even take an `errors: &mut Vec<LoadError>`, so it CANNOT report); pass 1 cannot miss because it defines. That is the silent skip CLAUDE.md forbids: a namespace whose symbol is absent has its imports unwired and its rule heads unregistered, and the load reports success. Note phase 2 dodges the question by a DIFFERENT route — `load_items` builds the scope term from the name (`name_to_sort_term`, ~11614) instead of looking it up, so it cannot miss but also cannot notice a name pass 1 never defined. WORK, mirroring the delivered scaland shape: extract ONE walker parameterised by the per-item action (scaland spells it `walkScopes` + a `ScopePass` trait with `enter_scope`/`at_item`, plus a `ScopeDecl` view over the two scope-opening items so the defining pass can still tell a namespace from a sort without an unreachable third arm); express all four walks through it; give the miss ONE answer — report it, from one helper (scaland: `lookupDefined`), which means threading an `errors` vec into pass 3. SAME-CLASS SITE to fold in, as scaland did: any phase-2 `by_qualified_name.get(..)`-then-skip over a pass-1-defined NON-scope name (scaland's was the `EntityItem` arm dropping its `entity_of` fact). ACCEPTANCE: the walker extracted and all four walks expressed through it; a test that DRIVES the loud miss and FAILS when the report is backed out (scaland's drives `load` without `scan_definitions`, the only reachable miss there — find rustland's equivalent rather than asserting the message alone); the existing suite green via rustland/scripts/test.sh.

ONE walker: `walk_scopes(pass, items, root)` owns the descent (join_segments -> make_qualified -> obtain child scope -> recurse with the new (scope, prefix)); a pass supplies `enter_scope` (yields the scope to descend into), `at_item`, and optionally `exit_scope`. `ScopeDecl` (Namespace | SortWithBody, forwarding name/imports/items) is what lets the DEFINING pass tell the two apart without an unreachable third arm. FIVE passes, not the four the ticket counted: DefinePass / ImportPass / RuleHeadPass / DeclarePass / LoadPass — `declare_field_types` (the WI-936 declaration pass) was a fifth copy of the same recursion, so it joined. THE MISS ANSWER, stated once, in `lookup_defined`: report, via the new span-bearing `LoadError::UndefinedAfterDefinePass`. `lookup_scope` is its scope-shaped use. Sub-pass 3 gained the `errors` vec it never had (its silent skip was not a choice the code could have made differently), file-stamped like sub-pass 2's.

TWO OF THE TICKET'S PREMISES DID NOT SURVIVE. (a) `exit_scope` HAD to exist. scaland's LoadPass only descends at a scope; rustland's `load_sort_with_body` does substantial work AFTER the body (the SortInfo roll-up, the induction rule) that reads names the body has just resolved. A pure enter->recurse shape cannot express that, so the trait carries an `exit_scope` hook and `load_sort_with_body` split into `enter_sort_with_body` / `exit_sort_with_body`; the carrier bindings each sort displaces ride a stack on the pass, since sorts nest. `current_scope` needs no stack — `site.enclosing` is the answer the walker already holds. (b) THE SAME-CLASS SITE HAS NO RUSTLAND TWIN. MEASURED: all nine phase-2 `by_qualified_name.get` sites — none is scaland's EntityItem shape. rustland's entity handling goes through `name_to_sort_term` (resolution), and the rest are speculative classification probes (`logical_sort_qn`, the rigid-projection parent gate, the sort-child ref) whose misses are legitimate and documented.

THE LOAD PHASE JOINED, and the ticket's 'it dodges the question' is now answered: it still DERIVES the scope by resolving the written name (`resolve_declared_scope` -> `name_to_sort_term`), because that is how it resolves every other name — imports and aliases included — and a scope reached differently from the members inside it would be a second answer to one question. What it gained is the CHECK: `lookup_defined` against the key sub-pass 1 writes, so a name the defining pass never defined is reported and its subtree abandoned instead of bare-interned into a phantom scope (`remap_name` cannot fail — that fallback is why the phase could not notice). Suite green with the check in place across ~2900 tests, so the qualified-lookup gate and `remap_name` agree on every scope in the corpus.
