 (1) PARAMETRIC FIELD -- `sort Hold { entity hold(p: Pair[A = Float, B = Int64]) }`.
     WI-1098's documented gap: the classifier resolves a field type to its BASE sort,
     so it sees `Pair`, not `Pair[A = Float]`, and derives nothing rather than claim a
     Float lawful. REPAIR the author wants told: write the two provision lines, or wait
     for conditional derivation.
 (2) DISPATCHED eq, NO PROVISION ON THE CARRIER -- `sort Pebble { entity pebble(n:
     Int64) }` plus a WITNESS `sort PebbleEq { provides PartialEq[T = Pebble];
     operation eq(a: Pebble, b: Pebble) -> Bool = true }`. `eq(pebble(1), pebble(2))`
     DISPATCHES fine; the provision files under the WITNESS (WI-1069: provider and
     carrier are two questions), so `Pebble` itself has no row to build a dictionary

 (3) GENUINELY NonEq -- `sort Pt { entity pt(x: Float) }`. `requires Eq[T]` is
     UNSATISFIABLE here, and no provision line can fix it. This one is not a missing
     declaration at all: it is a program that should be REFUSED, naming `Pt`, `Float`
     and `Eq`.

WHY THIS IS NOT A MESSAGE TWEAK. The right site is the CALL, at LOAD: `Driver.has`
calls `contains(l, x)` with `x : Pt`, and both the carrier and the spec are in hand
there (the typer's per-call subst). At the eval site (`eval.rs` `start_apply_deferred`,
the `find_requirement(...).ok_or_else` arm) the SPEC is reachable -- `op_dict_entries`'
`RequiresEntry.required_sort` for the slot -- but the CARRIER is not, so an eval-side
edit can only name half of what the ticket asks and would still fire at run time
instead of at load. WI-325's `MissingRequiresForSpecOp` is the neighbouring refusal and
covers a different shape (an ABSTRACT spec-op call with no covering `requires`); this is
a CONCRETE carrier whose op-scoped `requires` has no provider.
