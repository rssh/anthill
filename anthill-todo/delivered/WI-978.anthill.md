## Description

FOUND WHILE DRIVING WI-975 (see docs/proposals/059-secondary-entries.md). The
load-time BACKING OBLIGATION for a provision does not reach a provision declared
inside a NAMESPACE AT A SORT'S ADDRESS (059 calls that a "secondary entry" to the
sort's scope; `entity Rec(...)` beside `namespace Rec ... end`).

MEASURED, with the detector "declare the provision with NO backing and see
whether the load is refused":

  namespace y                              -- fires
    sort Show { sort T = ?; operation show(x: T) -> Int64 }
    entity Rec(n: Int64)
    fact Show[T = Rec]
  end
  => REFUSED: 'y.Rec' provides 'y.Show' but backs no operation 'y.Show.show'
     (no default on 'y.Show', no own 'show' on 'y.Rec')

  ...the SAME fact moved inside `namespace Rec ... end`  => LOADS CLEAN.
  ...and it still loads clean with the backing member sitting right beside it.

So the obligation is skipped for that placement, both when it would have fired
and when it would have passed. The check is not reporting a different answer --
it never runs.

LIKELY MECHANISM (not confirmed): the provision scan walks declared sort BODIES,
i.e. `Item::SortWithBody` items; a secondary entry's items arrive under an
`Item::Namespace`, so they are never visited.

NOT ESTABLISHED, and the FIRST thing to pin: whether a provision declared there
participates in INSTANCE DISPATCH at all, or only misses the check. The
generic-caller fixture built to test it (`operation useIt[T](x: T) -> Int64
requires Show[T] = Show.show(x)`) failed identically for BOTH placements
("operation has no body: z.Show.show"), so it measured nothing. Answer that
before choosing the fix: if dispatch also misses the provision, the defect is
larger than a missing check.

WHY IT MATTERS: proposal 059 R3 explicitly ALLOWS `fact Spec[X]` and host
`provides ... language ... end` blocks in a secondary entry -- that placement is
most of the point of the mechanism (a secondary entry supplying members for a foreign
carrier must be able to carry the provision for them). It is allowed into a
placement the obligation scan skips, so a carrier can claim a spec with nothing
backing it and load clean.

ACCEPTANCE: the obligation fires for a provision declared in a secondary entry,
with the same message it gives one level out; a test drives BOTH placements with
backing absent (both refused) and present (both accepted) -- the both-sides pair
is the control, since a test that only asserts the refusal passes on an
implementation that refuses every provision. State at the test site which half
fails when the fix is backed out. cargo-test green via rustland/scripts/test.sh.

### 2026-08-05T03:58:29Z — feedback — user

DELIVERED. The ticket's LIKELY MECHANISM was refuted; the real one is narrower
and order-dependent.

NOT the obligation scan. It does not walk `Item::SortWithBody` items — it walks
the `SortProvidesInfo` FACTS in the loaded KB (`check_provider_operations`,
typing.rs). It was never skipped for a secondary entry: measured, it already
fired for a `sort X` main entry AND for an `enum X` one, and for a free-standing
`entity X` when the `namespace X` block was written FIRST.

The EMITTER dropped it, keyed on DECLARATION ORDER. `maybe_emit_fact_provides_info`
(load.rs) branched on `kind_of(domain)` = `primary_kind()` = the FIRST category
added to the symbol, while a secondary entry's symbol carries a SET of them
(WI-956/WI-926). Measured, beside a `namespace X` block:

    sort X … end     primary = Sort       has_kind(Sort) = true
    enum X … end     primary = Sort       has_kind(Sort) = true
    entity X(…)      primary = ENTITY     has_kind(Sort) = true

So a claim in a secondary entry to a §6.3 free-standing entity matched NEITHER
arm and fell out of the `_ => return`: no `SortProvidesInfo` was emitted at all.
That answers the ticket's "FIRST thing to pin" — the provision did not merely
miss the check, IT DID NOT EXIST, so every reader missed it, dispatch included.
The defect was larger than a missing check, but in the other direction: one
emitter, not a scan that needed teaching about a new item shape.

FIX: `has_kind(domain, Sort)` — "does this scope name a type" — the reading 059
itself prescribes. One branch, one site (the only `kind_of(domain)` in load.rs).

A SECOND POPULATION, found by making the fallthrough LOUD rather than by
reasoning about it: a `fact Spec[X]` at a FILE'S TOP LEVEL, whose domain is the
synthetic `_global` root scope — no declared category at all, so `Namespace` was
as false for it as `Sort` was. It emitted no provision either, while the
identical text one `namespace` in did. Hence the else is "everything else", not
`has_kind(…, Namespace)`: the classification is binary, and there is no third
case left to fall out of. `parse_test::load_polynom_with_ring_requirement` is
that fixture; it fails loudly against the three-arm spelling.

TESTS: `rustland/anthill-core/tests/wi978_secondary_entry_provision_test.rs`,
5 tests. The 2x2x2 acceptance matrix (entity/sort carrier x claim in-entry/one-
level-out x backing absent/present) is split into two tests that report EVERY
bad row rather than panicking on the first, so backing the fix out names the
discriminating row exactly. MEASURED by reverting the branch: in each half
exactly ONE of the four rows fails — `entity` carrier, claim IN THE SECONDARY
ENTRY. The unbacked half loads clean; the BACKED half also loads clean and
records `[]`, which is why the test counts provisions instead of reading the
