## Description

BUG (diagnostic quality, surfaced by WI-744): a load error names NO FILE and often NO LINE — it renders a raw byte offset into an unidentified file, and for 2 of 3 `UnresolvedName`/`AmbiguousSymbol` producers that offset is `0..0`. Harmless while these were demoted to `warning:`; now that WI-744 makes every `LoadError` blocking, they are errors the user MUST locate and sometimes CANNOT.

VERIFIED LIVE (2026-07-17, during WI-744's code review):
  - `anthill run <ambiguous-symbol fixture>` → `error: ambiguous symbol 'widget' in scope 'app' at 0..0: candidates ["lib.one.Thing.widget", "lib.two.Gadget.widget"]` — printed TWICE, span `0..0`. Locatable only because the candidate list names the two colliding symbols; the USE SITE is unlocated.
  - `anthill-todo list` on a project with one stale file → `error: unresolved name 'RenamedAwaySort' in scope 'f' at 220..233` — byte 220 OF WHICH FILE? The todo CLI loads embedded stdlib + embedded bundle + N project files, so the offset identifies nothing.

THREE DISTINCT DEFECTS, one theme (a blocking diagnostic you cannot act on):
  (1) NO FILE IDENTITY. `load_all` / `load_all_per_file` merge N `&ParsedFile`s into one KB and return a FLAT `Vec<LoadError>`. No `LoadError` variant carries a file id (`UnresolvedImport.path` is the IMPORT path, not the source file), and `ParsedFile` itself holds no path or source text (`items`/`symbols`/`terms` only). CONSEQUENCE beyond messages: `LoadError::format_with_source(source)` (load.rs:521) — which DOES render line:col — has ZERO production callers and is structurally unusable at the three CLI sites, because they have no way to pick the right source string per error. It is reachable only from single-file `load::load` tests. This is also why anthill-todo's load arm cannot "skip the offending file" the way its parse arm does (see the DELIBERATE ASYMMETRY comment at anthill-todo/src/main.rs:549).
  (2) BYTE-0 SPANS. `remap_name_str_inner(&mut self, name: &str)` (load.rs:6428) and `remap_symbol_strict(&mut self, sym: Symbol)` (load.rs:6516) push `UnresolvedName`/`AmbiguousSymbol` with `span: Span::default()` — NEITHER TAKES A SPAN. Only `remap_name(&mut self, name: &Name)` (load.rs:6548) has `name.span` and passes it. Fixing means threading a `Span` through both fns and all their callers — a real refactor, which is why WI-744 scoped it out.
  (3) DUPLICATE EMISSION. The ambiguous-symbol error prints twice for one `fact widget(n: 1)`; presumably the name is remapped on two passes. Dedup at the push site or at the report site.

WHY IT MATTERS NOW: WI-744's whole thesis is loud-over-silent, but a loud error that cannot be located is only half-delivered — and the anthill-todo case is the sharp end, where the CLI is hard-dead until the user finds a file the diagnostic declines to name. WI-744 traded a silent write-corruption for a loud-but-vague failure; this ticket closes the gap.

LIKELY SHAPE: give the load pipeline a per-file provenance channel — either a `file: FileId`/`Arc<Path>` on every `LoadError` (stamped where the loader already knows which `ParsedFile` it is walking), or a `LoadError`-to-file map returned alongside the flat vec. Then (a) the three CLI sites can call `format_with_source` and print `path:line:col`, retiring the raw-offset Display; (b) anthill-todo's load arm gains the option to skip-and-warn per file exactly as its parse arm does (WI-505 parity), which would ALSO settle the asymmetry WI-744 deliberately accepted; (c) `format_with_source` stops being dead code. Do (2) in the same pass — the threading is the same shape of work. NOTE the CLI sites currently print the bare `Display`; anthill-todo's PARSE arm already does the good thing (`eprintln!("warning: {}:{}", file.display(), err.format_with_source(&source))`, main.rs:535) and is the model.

RELATED (small, separate, pre-existing — fold in only if convenient): the two anthill-cli load paths disagree on exit code for the same failure class — `run.rs build_kb` returns `runner::EXIT_COMPILE` (=2) while `main.rs load_kb_with_stdlib` returns a bare `Err(1)` (= EXIT_RUNTIME's value), so `anthill check` and `anthill run` report a load error as different codes. `main.rs` uses no `runner::EXIT_*` constant at any of its ~10 error returns, so this is that file's own convention, not a typo; WI-744 preserved it deliberately (changing it is a behavior change to every `anthill check`/`query`/`bundle` caller).

ACCEPTANCE: a load error names the FILE and a line:col (`path:line:col: message`), not a raw byte offset; `UnresolvedName`/`AmbiguousSymbol` from every producer carry a real span (no `Span::default()` reaching a user-visible diagnostic); one error is printed once; `format_with_source` has production callers (or is deleted if the design lands elsewhere); the WI-744 regression tests (`unresolved_name_blocks_the_run`, `ambiguous_symbol_blocks_the_run`, `catch_all_load_error_blocks_the_run`) still pass with their message anchors updated; cargo-test green via scripts/test.sh (FULL workspace).
