## Description

FOUND WHILE DRIVING WI-978 (see docs/proposals/059-secondary-entries.md R2). An
operation declared in a SECONDARY ENTRY backs a spec claim at LOAD TIME but is
UNREACHABLE by the requires-dictionary DISPATCH route at run time: the program
loads clean and dies. That is the WI-818 failure mode, in the placement 059 R2
makes the whole point of the mechanism.

MEASURED, three fixtures differing only in where the backing op sits. Spec:
`sort Show { sort T = ?; operation show(x: T) -> Int64 }`. Caller:
`sort Caller { sort T = ?; requires Show[T = T]; operation useIt(x: T) -> Int64 = show(x) }`.

  (1) op in the SORT BODY, provision in the sort body
      => loads clean, 1 provision, `Rec.show` = 111, `Caller.useIt` = 111
      <- CONTROL, works

  (2) op in a SECONDARY ENTRY (`namespace Rec { operation show(x: Rec) = 111 }`),
      provision ONE LEVEL OUT
      => loads clean, 1 provision, `Rec.show` = 111,
         `Caller.useIt` = EvalError::OperationBodyMissing { name: "…Show.show" }

  (3) op AND provision both in the secondary entry
      => identical to (2)

So the PROVISION placement is not the discriminator -- (2) and (3) fail alike
while (1) passes. The OP placement is. `op_backed` (typing.rs,
`check_provider_operations`) finds the secondary entry's `show` and accepts the
claim; the runtime dictionary route does not, and reports the SPEC op as missing
a body.

NOT ESTABLISHED, and the decision this ticket has to make: which side is wrong.

  (a) WIDEN dispatch -- the requires-dictionary route should see a secondary
      entry's members, since 059 R2 says what a secondary entry declares IS a
      member of the sort and may back its claims. Note the DIRECT call already
      dispatches (`Rec.show` = 111 in (2)), so membership is partly wired
      already; find which reader the dictionary route consults instead.

  (b) NARROW `op_backed` -- refuse a secondary entry's op as backing, so the
      LOAD is refused rather than the run. This CONTRADICTS 059 R2 and would
      make the mechanism unable to supply members for a foreign carrier, which
      is most of why one writes a secondary entry. Named for completeness, not
      recommended.

WI-978 fixed the neighbouring EMITTER defect (a claim in a secondary entry to a
free-standing `entity` recorded no provision at all, so no reader saw it) and
deliberately did not reach this: different subsystem, and (a)/(b) is a design
call. WI-978's own test file states the split at its head.

ACCEPTANCE: a test DRIVES the generic caller through the requires path with the
backing op declared in a secondary entry and asserts the VALUE -- not that it
loads. Fixture (1) is included unchanged as the both-sides control, since it
passes either way and is what attributes a failure to the placement rather than
to the fixture. State at the test site which of the three fixtures fails when
the fix is backed out. cargo-test green via rustland/scripts/test.sh.
