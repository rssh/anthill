## Description

Expr::Lambda should NOT be Opaque in occ_head -- give it the head its term twin already has, and settle what opacity under a BINDER was protecting. CONTEXT: surfaced reviewing WI-762. occ_head (kb/term_view.rs) gives a real ViewHead to Apply, Constructor/Instantiation, Const, Spliced, Ref, Ident, VarRef, Var, Bottom, DotApply and ListLit, each justified by pointing at the term the loader emits for the same source -- e.g. DotApply reads "STRUCTURALLY as its dot_apply(receiver, name, args: List[ApplyArg]) term twin ... so a fact embedding a DotApply indexes/matches identically to the term the loader emits" (WI-278/397/425). Expr::Lambda has no arm and falls to `_ => ViewHead::Opaque`, whose comment scopes the intent narrowly: "control-flow and post-elaboration forms ... are opaque to rule-LHS MATCHING". THE TERM TWIN ALREADY EXISTS, so the head is not a new invention: LoadBuildFrame::Lambda (kb/load.rs:8860-8872) builds Term::Fn{functor: anthill.reflect.Expr.lambda_expr, named_args: [param, body]} -- 0 positional, 2 named -- so the mechanical shape is exactly ViewHead::Functor{Some(lambda_expr), 0, 2}, the same one-liner DotApply/VarRef/ListLit use. WHY IT MATTERS NOW: head() is no longer read only by rule-LHS matching. It also backs views_structurally_equal (an IDENTITY question) and goal_fingerprint/GoalKey (dedup keys). Opaque has no (Opaque, Opaque) equal arm, so as an identity test it returns FALSE NEGATIVES. MEASURED: using views_structurally_equal to compare two projection receivers of the form `person_row.where(lambda c -> eq(c.age, 30))` reported them UNEQUAL and rejected all ten wi714_project tests -- not because of the dot (DotApply heads fine) but because the LAMBDA nested in its args is Opaque. That blocked WI-762's receiver-divergence guard, which had to be abandoned. THE REAL QUESTION, and why this is not just "fill the arm": Lambda is the BINDER case, and the opacity may be load-bearing for MATCHING rather than merely unwritten. Matching into a binder's scope without capture-avoidance is unsound, so `Opaque` may be deliberately protecting rule-LHS matching from descending under a lambda -- unlike DotApply, which binds nothing. CLAUDE.md's representation note states the adjacent position: hash-consing is "specifically inappropriate for binders (arrow / dependent types), whose scope and alpha-equivalence don't fit a global dedup store". So the ticket must decide, not assume: (a) is a head wanted for IDENTITY/fingerprint while matching still refuses to descend (two different consumers of head(), possibly needing to be distinguished), or (b) is descending safe once capture-avoidance is handled where matching happens? ALPHA-EQUIVALENCE, stated because it decides the semantics: WI-550 mints binder symbols via intern_unique memoized on the pattern_var PARSE-NODE id (load.rs:6373-6378). So two occurrences derived from ONE source lambda -- e.g. the N copies convert.rs's distribute-dot makes of one receiver -- SHARE a gensym and would compare EQUAL (which is exactly what WI-762's guard needs), while two independently-written identical lambdas get DIFFERENT gensyms and compare UNEQUAL. That makes the proposed head SYNTACTIC, not alpha-aware. State whether views_structurally_equal is supposed to hold for two alpha-equivalent lambdas; if yes, the binder symbols must be normalized (de Bruijn-style) in the fingerprint rather than compared as symbols. BLAST RADIUS -- measure before changing, since Opaque->Functor changes three consumers at once: (1) the discrimination tree begins INDEXING lambda-bearing facts/goals instead of treating them as opaque, changing which candidates are returned; (2) goal_fingerprint/GoalKey values change, so the resolver's seen_goals answer-dedup and the per-query cache key differently (GoalKey::is_cacheable's Opaque exclusion may start admitting keys it used to reject); (3) rule-LHS matching may now descend under a binder -- the soundness question above. NOTE the occurrence->term direction is deliberately NOT part of this: try_occurrence_to_term has no Lambda arm, and per the standing reify audit (WI-348/482/621/678/692) the shim should be shrinking, not growing. This ticket fills the VIEW, which is the carrier-neutral interface consumers should read. ACCEPTANCE: Expr::Lambda reads ViewHead::Functor{Expr.lambda_expr, 0, 2} (or a documented alternative if (a) wins), with the alpha-equivalence semantics STATED in the arm's comment; a test pins that two occurrences of ONE source lambda compare structurally equal and two distinct source lambdas do not; the effect on discrim candidate sets and on GoalKey/seen_goals dedup is measured and reported, with a test pinning that no goal that used to dedup stops dedupping (or the change is stated as intended); if matching must still refuse to descend under a binder, the mechanism that keeps it out is named and tested; WI-762's receiver-divergence guard becomes writable on views_structurally_equal with no second comparator; full workspace green via rustland/scripts/test.sh.

## Changes

### 2026-07-22T14:34:46Z — feedback — user

MEASUREMENT AND REPORT, the acceptance clause that asked for the discrim / GoalKey / seen_goals effect to be "measured and reported". (1) DISCRIM CANDIDATE SETS. Before, a lambda-bearing structure was NON-INDEXABLE: `Opaque` carries no discrimination key at all, `insert_walk` / `remove_walk` PANIC on it, and only the `view_is_indexable` pre-check kept them from firing; a query with an `Opaque` head followed universal var-edges only and did NOT descend. Now a lambda keys `Functor(lambda_expr)` -> `Arity(2)` -> per-child `NamedKey` edges and the walk descends into `param` and `body`. Pinned by `lambda_cross_carrier_discrim_match`: a fact indexed under the TERM carrier is found by an OCCURRENCE-carrier query (1 hit), a DIFFERENT binder does NOT match (0 hits, so the candidate set is genuinely keyed on the lambda's structure rather than merely widened), and a term-side pattern matches the occurrence target. (2) GoalKey / seen_goals. `StructToken::Opaque` is PAYLOAD-FREE, so two goals differing only inside a lambda used to produce the SAME key -- i.e. `seen_goals` OVER-DEDUPED and silently dropped the second answer -- while `is_cacheable` rejected the key outright. Both moved the SAFE way and both are pinned by `lambda_goal_keys_separate_and_become_cacheable`: identical goals STILL key identically (`k1 == k1_again`, so nothing that used to dedup stops dedupping -- the clause's explicit requirement), distinct lambdas now SEPARATE (`k1 != k2`, the over-dedup fixed), the key is now CACHEABLE, and the TERM and OCCURRENCE carriers produce the SAME key (so the change is carrier-neutral). (3) BINDER SOUNDNESS. Matching does NOT need to refuse to descend, so the "name the mechanism that keeps it out" branch does not apply; what makes the descent capture-free is named in the arm's comment: WI-550 mints every binder symbol through `intern_unique` memoized on the binder's PARSE-NODE id, so binder symbols are globally unique BY CONSTRUCTION and a `var_ref` names exactly one binder -- Barendregt's convention enforced at the producer. `Var::DeBruijn` remains the second line of defence (discrim keys it as an inert var-edge; `unify_match_values` still refuses to bind it). The observable consequence is pinned by `one_source_lambda_equal_two_distinct_sources_not`. (4) ALPHA-EQUIVALENCE, stated as the clause required: the view is SYNTACTIC. Two occurrences of ONE source lambda compare EQUAL (they share the parse node, hence the gensym -- what WI-762's guard needs); two independently written `lambda x -> x` / `lambda y -> y` compare UNEQUAL despite being alpha-equivalent, because the term twin they must agree with is compared structurally, not up to alpha. SCOPE DELIVERED BEYOND THE TICKET, recorded so the delivery is not read as narrower than it is: `If` / `Let` / `Match` / `Proof` and ALL FIVE `Pattern` variants also became structural, under one shape table that makes `head`'s arity and `named_keys` structurally unable to disagree; and the PROOF TERM gained its `using` premise list (loader + `visit_fn` reader + view), correcting a term that had been an INCOMPLETE representation of a proof -- `proof Y using X` and `proof Y using Z` had compared EQUAL. KNOWN GAPS LEFT OPEN, each with an owner: `Let.type_annotation` is still invisible to the view and now yields a CACHEABLE GoalKey, so `let x: Int64 = 1` and `let x: String = 1` conflate -> WI-819 (which removes the second annotation channel rather than restoring the slot); `Pattern::Tuple.labels` is dropped by `pattern_to_term` -> WI-803; the `*Within` IR stays `Opaque` -> WI-816.
