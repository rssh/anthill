## Description

An ENTITY's field names must be DISTINCT. MEASURED with WI-805's tuple guards in place: `sort S entity mk(a: Int64, a: Int64) end` with `operation drive() -> Int64 = mk(1, 2).a` loads with ZERO errors and returns Int(1), the second `a` permanently unaddressable by name. Recorded as out of scope while delivering WI-805 and fixed here on request. THE HARM IS NARROWER THAN THE TUPLE CASE and the fix must say so rather than overstate it: a tuple component under a repeated name is unreachable ENTIRELY (by name AND by position, the relation being name-keyed) so its declared type is never checked against anything, whereas an entity's second field is still BUILT and READ positionally -- measured, `mk(1, 2)` type-checks both slots against their declarations (`type mismatch in mk.b (entity-field)`) and `case mk(p, q) -> q` reads the second. What it loses is its ACCESS PATH: `x.f`, a named argument and a rule pattern all resolve a field name to the FIRST match. Refused anyway because a field name IS the field's public interface, so a name identifying two fields addresses neither -- the same principle the spec states for a projection's result keys and a call's named arguments. FIX: check at convert_entity through WI-805's owner, generalized to take a per-kind rationale (check_label_unique with what/why). Field names scope PER ENTITY -- sibling entities in one sort may each declare `a`, the ordinary variant shape. NOT extended to operation/arrow parameters, per WI-805's settled reasoning (applied positionally, names are local binders not a type's interface). ACCEPTANCE: the program above is refused at load with a located diagnostic naming the repeated field and pointing at the SECOND occurrence; sibling entities sharing a field name still load; spec 6.3 states the rule alongside 4.5's tuple one; full workspace green via scripts/test.sh.
