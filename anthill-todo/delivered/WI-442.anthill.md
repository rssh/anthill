## Description

Typer: NAMED-BINDER multi-param arrow types in higher-order argument positions. A declared callback type '(acc: Acc, x: Elem) -> Acc @ {EffP}' loads where written, but every call site fails LOUDLY with 'EffP unconstrained': operation_as_function_value (typing.rs ~1848) builds a multi-param op's eta arrow with the WI-355 positional _1/_2 named-tuple param, which never unifies with the named binder fields (acc, x) of the expected arrow, so the best-effort arrow unify binds nothing and the callback's row var stays unbound. PROBED (foldLeft modernization session, 2026-06-11): single-param arrows bind EffP fine (bare {EffP} row, no absence needed); two-param NAMED binders fail at external call sites; two-param UNNAMED '(Acc, Elem)' fails even on the stdlib body's recursive self-call. WORKAROUND IN PLACE: Stream.foldLeft/foldRight + Iterable.foldLeft/foldRight use the WI-355 positional-tuple arrow '((Acc, Elem)) -> Acc @ {EffP}' applied 'f((init, h))' (documented in stream.anthill). FIX DIRECTION: unify arrow param tuples positionally when one side carries the canonical _1.._n positional convention (or mint the eta arrow's field names from the expected arrow's binders). This also unlocks binder NAMES on multi-param arrows for dependent absences (-Modify[x]) and unlocks the row-gated Modify-bearing fold callback (see wi424 pinning test iterable_fold_mutating_callback_not_lacks_rejected_but_row_gated). ACCEPTANCE CRITERIA: Stream.foldLeft/foldRight and Iterable.foldLeft/foldRight rewritten to the two-param arrow form '(acc: Acc, x: Elem) -> Acc @ {EffP}' / '(x: Elem, acc: Acc) -> ...', bodies apply 'f(init, h)' directly; wi064 + wi424 fold suites (incl. the effectful decoupled-row pair) pass with NO explicit [EffP = ...] at any call site.
