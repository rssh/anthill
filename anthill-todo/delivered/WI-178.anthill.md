## description

Import resolution: walk enum-entity scopes when looking up short names. Today rustland/anthill-core/src/kb/load.rs process_imports tries qualified-name lookup, then short-name resolve_in_scope at the base path. For an import like 'import anthill.cli.parse.{parse_ok, parse_err}' where parse_ok is declared inside 'enum ParseResult { entity parse_ok(...) }' under 'namespace anthill.cli.parse', neither lookup hits: qualified name is anthill.cli.parse.ParseResult.parse_ok (not anthill.cli.parse.parse_ok), and the namespace scope's resolve_in_scope does not descend into the enum sort's scope. Use-sites (match arms) still resolve because pattern resolution walks parent scopes including the enum, so the import-side miss is masked at runtime — producing 'unresolved import' warnings that are harmless but noisy. Required: extend the short-name fallback in process_imports to walk child sort/enum scopes within the base namespace, so the import binds a local alias when the symbol is reachable via any nested scope. Acceptance: integration test where an anthill program imports an enum entity by short name, then uses it in a match arm and as a constructor; load produces zero LoadError::UnresolvedImport warnings; existing tests still pass. Follow-on: once import resolution is reliable, promote LoadError::UnresolvedImport to is_type_error()=true in load.rs:168 so use-site name lookups can no longer mask broken imports. Motivated by: rustland/anthill-todo/anthill/main.anthill (WI-009 phase 1b) which currently emits 4 unresolved-import warnings for parse_ok / parse_err / no_subcommand / unknown_subcommand despite all four working at use-site.
