## description

A GENERIC consumer of a spec certifies at load and dies at the call -- and two specs disagree about the identical construct.

MEASURED 2026-08-02 on the post-WI-935/937/938/941 tree, via common::try_load_kb_with + interp_for. Pinned by vec3_ops_test::a_generic_consumer_of_vector_space_loads_clean_and_fails_at_the_call, which asserts the CURRENT (defective) behaviour so it cannot be lost.

SUBJECT -- two type params, VectorSpace:
  sort G
    operation twice[V, F](a: V) -> V requires VectorSpace[V, F] =
      VectorSpace.vec_add(a, a)
  end
LOADS CLEAN. At the call: Err(OperationBodyMissing { name: "anthill.prelude.algebra.VectorSpace.vec_add" }). The requires-dictionary route does not reach anthill.geometry.Vec3.vec_add.

CONTROL A -- the SAME call at a concrete carrier WORKS:
  operation twice_vec3(a: Vec3) -> Vec3 = VectorSpace.vec_add(a, a)   -> Vec3(2.0, 4.0, 6.0)
So the provision is sound and the member is backed. What fails is abstract dispatch, not the carrier.

CONTROL B -- THE SAME SHAPE OVER A ONE-PARAM SPEC IS REFUSED AT LOAD:
  sort H
    operation dbl[T](a: T) -> T requires Ring[T] = Ring.add(a, a)
  end
  -> type mismatch in anthill.prelude.algebra.Ring.add.requires: expected `requires Ring[...]`
     covering abstract type parameter, got missing `requires Ring[T = ...]` on enclosing sort

THAT DISAGREEMENT IS THE FINDING, not the failure alone. One spec is caught loudly at load, the other is certified and dies at run time, for the identical construct. At least one of the two is wrong and the ticket must decide WHICH -- do NOT assume the Ring refusal is the correct behaviour and the VectorSpace pass is the bug; it may be the other way round (stdlib list.anthill:57 `operation member(x: T, l: List) -> Bool requires Eq[T]` is the same op-level-requires shape and loads, so the refusal may be over-firing on an OP-DECLARED type param where the working case inherits its param from the enclosing sort).

WHY IT MATTERS. Writing code against the SPEC rather than the carrier is the entire point of the WI-138 lift that WI-935 completed. This is the first generic consumer of it, and it does not work. docs/kernel-language.md 8.7 (WI-818) says the loader rejects a provision "rather than certify a program whose call fails only at run time" -- that check guards the PROVIDER; nothing guards the generic CONSUMER, which is the same failure one level up.

PRE-EXISTING, not created by WI-935: this is a generic-dispatch gap. WI-935 is what makes it reachable against a STDLIB type, and what makes it matter -- before it, nothing provided VectorSpace at all.

NOT ROOT-CAUSED. I did not read the dictionary-construction path. Candidates, unverified: WI-357 records that a shorthand `requires Ring[F]` where Ring names its param T loads as `Ring[T = Ring.T]` -- the cross-param link dropped -- and that `Eq[T]` only APPEARS to work because the names coincide; that is the right neighbourhood but it is a lead, not a diagnosis.

ACCEPTANCE: the two constructs AGREE -- either both load and both dispatch (preferred: `twice` returns Vec3(2.0,4.0,6.0)), or both are refused at load with a located diagnostic naming the spec and the op. Driven both ways, with the existing test flipped to assert the new behaviour rather than deleted, plus a CONTROL that the concrete-carrier route is unaffected and that stdlib `List.member` (op-level `requires Eq[T]` over a SORT-declared param) still loads. cargo-test green.

SOURCE: reported by /code-review on WI-935, reproduced and controlled after delivery.
