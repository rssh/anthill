## Description

A SPEC WITH NO TYPE PARAMETERS CANNOT BE CALLED THROUGH THE SPEC: THE CALL LOADS CLEAN AND DIES AT RUN TIME. `sort Sp { operation size(s: Sp) -> Int64 }`, `sort Car { entity car(n: Int64); provides Sp; operation size(c: Car) -> Int64 = 42 }`, `operation go() -> Int64 = Sp.size(car(n: 1))` loads with no diagnostic and `anthill run` dies 'operation has no body: …Sp.size — nothing this runtime can run is registered for it'; so does a call through an abstract receiver, `operation measure(s: Sp) -> Int64 = Sp.size(s)` called as `measure(car(n: 1))`. Adding one unused parameter (`sort T = ?` in Sp, `provides Sp[T = Int64]`) makes both run to 42, and the carrier's own member called directly (`car(n: 1).size()`) runs. MECHANISM: an operation counts as a dispatched spec operation only in a PARAMETRIC sort — `spec_op_parent_sort` (typing/call_class.rs:33; WI-210: 'at least one `sort <Param> = ?`'), which gates the typer's self-receiver classification (`self_receiver_spec_sort`, typing/carrier.rs:908, and `lookup_spec_op_dispatch` built on it) and eval's value-directed dispatch (eval/eval.rs:5236) — while the loader accepts `provides Sp` and the member, so nothing names the gap before run time. MEASURED identically on the trees before and after WI-20260929-0RP29's ninth and tenth passes; FOUND by the tenth pass's gate (verify/S1b/s2/min_noparam: a spec op returning a function, behind a parameterless spec). Nothing in stdlib/ or examples/ provides a parameterless spec. FIX: decide which rule holds and apply it everywhere — either a sort something PROVIDES is a spec whether or not it declares a parameter (the dispatch gates ask for a body-less operation of a provided sort, typer and eval alike), or a parameterless sort cannot be provided and `provides Sp` is refused at load naming the rule; the spec says neither today. ACCEPTANCE: under the first rule the two programs above run to 42 through the spec call, the one-parameter twin unchanged; under the second, both refused at the `provides` clause; full workspace green via rustland/scripts/test.sh.

### 2026-10-13T07:49:45Z — feedback — claude

DELIVERED. THE RULE, decided by the user 2026-10-13: every sort is a spec, and a sort provides itself, by its own operations. A call `S.op(…)` is answered by the member of its carrier — the sort of the argument standing at `S`, or the type bound to the parameter of `S` the operation receives on, or `S` where the operation names neither — and the carrier provides `S`: it is `S`, or it declares the provision. Whether `S` takes a type parameter plays no part. The description's second option was never available: the library itself provides a sort with no parameter (`NonMonotonicStore provides Store`, `QueryableStore provides Store`, the Rust bindings' `provides Store language rust`) — 'nothing in stdlib/ provides a parameterless spec' was wrong, 278 test loads reach `anthill.persistence.Store`.

WHAT RUNS NOW. Both programs of the description run to 42. With a default body on `Sp.size` the provider's member answers (42) and a provider that declares none gets the default (7): before, the default answered for both, in silence. A rule-body goal `Sp.size(car(n: 1), ?x)` answers 42 where it answered nothing. A sort declared by one load may be provided by a later one, sealed or not.

HOW. (1) The gates an operation body reads (typing/call_class.rs: `spec_op_parent_sort`, and `defaulted_spec_op_parent` and `lookup_spec_op_dispatch` on it) read nothing off the declaring sort but that it may be provided — it has no constructor, the loader's own rule. No type parameter, and no 'does a sort provide it yet': a declaration's answer does not move with what is loaded after it. (2) `sort_provides` answers that a sort provides itself; the relation holds no row for it. Where the carrier turns out to be the sort, the readers find its own operation; a law written in `Set` fires at a `Set`. (3) ONE gate asks more, the rule body's — `spec_op_call_parent`: a type parameter or a provider. A rule body is typed and woven at load with its arguments unbound, so whether the walk types a goal as a call, and whether the call carries one dispatch dictionary or requirement slots, is decided without a carrier. MEASURED with that gate at 'every sort that may be provided': 35 rows fail (wi_p7vp4 16, wi_nekr0 10, wi_9r5hn 3, wi_mhrn1 3, wi_prva2 3) — a module-style `sort Util`'s operations woven as dispatched, its goals typed as calls. That is proposal 068's ground. (4) An operation that names neither its sort nor one of its parameters (`signature_names_no_carrier`) is the sort's own where the sort has no parameter or no provider, and its `@[simp]` equation is its definition; with both, a requirement or a selection names the provider through the parameter. The third shape of the defect was found here — `sort Util { sort T = ?; operation f(x: Int64) -> Int64; rule f(?x) <=> ?x + 1 @[simp] }` loaded clean and died, where the same sort without `T` ran. (5) RM247's leftovers: the `requires` reading (`clause_is_dispatchable`: `sort Narrow requires Box[V = Int64]` over a data sort is a refinement, as it was without the parameter) and the loader's own-sort key (`enclosing_is_spec`) no longer read a sort with a parameter and constructors as provided. (6) A clause-defined operation of a sort with no parameter that names no carrier is refused at load where an operation body calls it, as a namespace's is; one called on a receiver typed at the sort is left to the dispatch, with a provider in sight or not. (7) The resolver's body-less arm no longer takes an operation the interpreter has a host function for: the host arm's effect check decides those, and an effectful one ran at a rule-body operand through the other arm — for a sort with a type parameter before, a hole that arm's own comment recorded.
