## description

CLI/resolver: an UNRESOLVABLE functor in a query pattern returns `no solutions` (exit 0) SILENTLY instead of erroring, so it reads as "no such fact" when the truth is "that name could not resolve to any known functor." Violates the repo's 'loud error over silent skip' rule.

NARROWED 2026-07-29. This ticket originally reported TWO grammar/CLI causes by which a query pattern could not use imports AT ALL: (1) top-level `import` was ungrammatical (`_declaration` omitted `import_clause`), so anthill-cli's `collect_queries` synthesized `import <name>` prefix died at parse and `query -i/--import` could never succeed; (2) the namespace-wrap workaround was also closed because `collect_queries` only scanned TOP-LEVEL `Item::Fact`. BOTH are now RESOLVED by WI-853 (`7a32bc79`), which added `import_clause` to `_declaration` so a file's top level admits an import the same way a namespace/sort body does. `query -i <ns> "<pattern>"` now resolves and exits 0, and a plain top-level `import` in an ordinary .anthill file parses. Verified live on a clean rebuild (grammar edits need `cargo clean -p tree-sitter-anthill` first — `parser.c` is generated by build.rs from grammar.js and is NOT git-tracked, so an incremental build silently keeps the stale parser). WI-853 shipped 7 end-to-end `-i` CLI tests + 4 top-level-import loader tests + a corpus case, full workspace green.

WHAT REMAINS (why this stays open): the import MECHANISM works, but an unresolvable name is still a silent zero. Measured on the fresh binary against a KB with `namespace app.util sort Q entity q(row: Int64) end fact q(row: 7) end`:
  $ anthill query -p kb.anthill 'app.util.Q.q(row: 999)'   -> no solutions   (exit 0)   # KNOWN functor, no matching row — legitimately empty
  $ anthill query -p kb.anthill 'nope(row: ?x)'            -> no solutions   (exit 0)   # UNKNOWN short name — SILENT, should be loud
  $ anthill query -p kb.anthill 'app.util.Q.nope(row: ?x)' -> no solutions   (exit 0)   # UNKNOWN qualified name — SILENT, should be loud
  $ anthill query -p kb.anthill -i 'app.util.Q' 'q(row: ?x)' -> ?x = 7        (exit 0)   # import path works (control)
All three unknowns are INDISTINGUISHABLE from the legitimately-empty case today. The distinction to draw: a name that RESOLVES to a known functor with no matching facts legitimately yields `no solutions` (exit 0); a name that does NOT resolve to any known functor should ERROR (non-zero) naming the functor, not be conflated with the empty-answer case.

NOTE ON A NON-BUG (kept so nobody re-chases it): an entity declared inside `sort Q` registers under `<ns>.Q.q`, so the qualified spelling is `app.util.Q.q(row: ?x)`, NOT `app.util.q(...)`. The sort segment is part of the entity's qualified name; a wrong spelling there is user error, not this silent-zero defect.

FIX DIRECTION (not settled): in the query path (anthill-cli `collect_queries` / `convert_query_term`, and/or the resolver entry), detect a query whose head functor resolves to NO known symbol/rule/fact and surface a loud diagnostic naming the functor, rather than handing an unresolvable pattern to SLD (which correctly finds nothing and is right to). Decide whether this belongs in the CLI (a pre-resolve symbol lookup) or in the resolver (an "unknown predicate" signal distinct from "no solutions"), and whether an anonymous/variable head is exempt.

ACCEPTANCE: `anthill query -p <kb> "<unknown_functor>(...)"` exits NON-ZERO with a message naming the unresolvable functor (not `no solutions`); a KNOWN functor with no matching facts still prints `no solutions` and exits 0 (both the short-name-via-import and fully-qualified spellings); an anthill-cli test drives both the unknown-functor and the known-but-empty case; full workspace green via rustland/scripts/test.sh.
