## description

Eval type-arg channel is keyed by the WRONG symbol: a body reference to an operation's type parameter never resolves through it. Repro (anthill-core, needs WI-707): `operation ty[T]() -> Type = Cell[V = T]` + `operation ty_int() -> Type = ty[T = Int64]()` evaluates to `Cell[V = Ref(T)]`, NOT `Cell[V = Int64]` -- the type param is left dangling. Diagnosis: the typer writes `occ.set_resolved_type_args` (typing.rs, WI-272) keyed by the declared-name Symbol carried in `OperationInfo.type_params`; eval installs that verbatim on `Frame.type_args` and `reduce_var` looks it up with `find_type_arg`, which matches by SYMBOL IDENTITY. But the symbol a BODY reference to `T` resolves to is a different interning (the op-scoped `<ns>.<op>.T`) than the one in `type_params` -- observed live: body sym Symbol(2241) qualified `test.ty.T` vs channel key Symbol(2256), both short-named `T`. So the lookup always misses and the reference falls through (today: to WI-206's bare-sort arm, which delivers a bare `Ref(T)`; before WI-206 it would have been an UnresolvedName). Impact: the WI-272 frame type-arg channel is effectively dead for body-side reads -- any feature that wants to read a type param as a VALUE in a body silently gets a dangling ref instead of the binding. Currently harmless ONLY because no consumer reads type ARGUMENTS: every Type-taking reflect op keys on the head sort. It is a live trap for the next one that does. Fix: make the two keyings agree -- either key `type_params` by the op-scoped symbol the loader defines for the param (preferred: symbol identity stays the single source of truth, per the typed-wrapper/by-reference direction of WI-632/WI-352), or resolve body-side type-param refs to the same symbol `type_params` holds. Do NOT paper over it by matching on short name in find_type_arg -- that reintroduces name-based resolution the codebase has been moving away from. Acceptance: the repro above evaluates to `Cell[V = Int64]`; a test pins that a body reference to a type param reads its binding; cargo test green.
