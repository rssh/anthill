## Description

scala-gen: an operation that REFINES a required sort's operation has no Scala supertrait spelling, and Bootstrap cannot even DETECT the conflict -- decide between a refusal, a carrier binding, and handing it to the KB-driven gen.

SPLIT FROM WI-1064 (2026-08-09, feedback there). That ticket keeps the DATA-SORT half (shape 2), whose rule is decidable from syntax: a `requires` becomes a supertrait only on an ALGEBRA sort, because on a sort with constructors the requirement's carrier slot names a PARAMETER and never the sort. This is the other half, and the split is not tidiness -- the two halves fail for unrelated reasons and only one of them is within Bootstrap's reach.

THE DEFECT. finite_collection.anthill:25 writes `requires Iterable[C = C, Element = Element, E = E]`. That IS a supertrait under WI-1064's rule -- the carrier slot is bound to FiniteCollection's own `C` -- so the rule does not touch it and must not. Then finite_collection.anthill declares `operation map(c, f) -> FiniteCollection[C = FiniteMappedStream[...], Element = Dst, E = {E, EffP}]` while Iterable.map (iterable.anthill:61) returns `Stream[Dst, {E, EffP}]`. In anthill the two are related through `provides` and by-carrier dispatch, with no nominal subtyping between the return types; in Scala `extends` means override, and RefChecks reports `error overriding method map in trait Iterable ... has incompatible type`. Same for `filter`. TWO errors -- the residue of WI-1064's measured round of four, in one file.

WHY BOOTSTRAP CANNOT DECIDE THIS ITSELF, which is the whole reason this is a separate ticket and not a second arm of WI-1064's fix: recognizing the conflict means knowing Iterable's MEMBER SIGNATURES, and they live in another file. Proposal 034 gives Bootstrap a `ParsedFile` and no KB. WI-1062's item 2 recorded the identical wall for effect parameters ("knowing it is the effect one means knowing Stream's declared parameter kinds, which live in another file: exactly the cross-file knowledge proposal 034 denies Bootstrap"). Any answer here is therefore a decision about SCOPE or about who owns the emission -- not a rule Bootstrap can apply.

THE OPTIONS, with what each costs.

 1. REFUSE finite_collection.anthill, naming the construct (an operation whose signature conflicts with one inherited from a `requires`). Cheapest and loud. THE COST TO MEASURE FIRST: finite_combinators.anthill names FiniteCollection both in `fmapped`'s field type and in its `provides`, so a WI-1055 B1 refusal ("the emitted tree has no such type") plausibly CASCADES and takes finite_combinators.anthill out with it -- which would remove WI-1064's shape-2 fix from the emitted tree even though its rule is right, and re-open part of the cascade WI-1062 closed. Measure the cascade before choosing; do not assume it.

 2. BIND FiniteCollection to a hand-written Scala trait through a codegen CONFIG. This is §1's channel (2) -- "an `Implementation` fact (kernel spec §8.5) pointing to a host-side artifact (carrier binding)" -- and the fact type already exists: `CarrierBinding(sort_name, host_type)` at stdlib/anthill/realization/realization.anthill:54. Rustland implements it KB-free as `CodegenConfig.carrier_bindings`, a caller-supplied map emitted as `type X = HostType` (codegen/rust.rs:876), with anthill-stl/build.rs passing `"Term" -> "anthill_core::eval::Value"`. Scaland already has the precedent for threading a KB answer WITHOUT a KB: `Bootstrap.buildSbt(scalaVersion: String)` takes the profile's value as a parameter, "which is what keeps this a pure function of its inputs". TWO THINGS ARE MISSING and neither is a port: `Bootstrap.generate(pf: ParsedFile)` takes no config at all, so a `BootstrapConfig` seam has to be introduced; and rustland's arm fires only on `AbstractSortItem` (a bodyless opaque sort), whereas FiniteCollection HAS a body, so binding a bodied sort is a new arm. Also state what the closure test then MEASURES -- a bound sort's Scala is hand-written, so "the emitted closure compiles" covers less than it did, and that shrinkage must be recorded rather than absorbed.

 3. HAND IT TO THE KB-DRIVEN `anthill-scala-gen` (proposal 034 §anthill-scala-gen), which CAN see Iterable's members and could emit the form Scala actually uses for return-type refinement -- an abstract type member on the supertrait (`type MapResult[_]`) refined in the subtrait. Correct, idiomatic, and by far the largest: it changes the emitted shape of every operation returning the sort, so it is a §2.14-scale mapping decision and not a fix.
