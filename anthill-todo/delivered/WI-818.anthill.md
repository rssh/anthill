## description

A spec-level `rule` DEFAULT satisfies the load-time provider-backing check but CANNOT BE EXECUTED, so the program LOADS CLEAN and fails at RUN time -- and the diagnostic it fails with names the wrong problem. MEASURED, three variants that differ ONLY in how the spec operation is backed; carrier `Widget` provides spec `Nameable` (`operation tag(x: T) -> Int64`), and a third sort `Box` declares `requires Nameable[T = T]` with `operation same(x: T) -> Int64 = tag(x)`. (A) NO backing at all -- LOAD IS REJECTED, with a diagnostic that is exactly right: "'probe.a.Widget' provides 'probe.a.Nameable' but backs no operation 'probe.a.Nameable.tag' (no default on 'probe.a.Nameable', no own 'tag' on 'probe.a.Widget')". (B) carrier supplies a real implementation (`operation tag(x: Widget) -> Int64 = 111` in the Widget sort body) -- LOADS CLEAN and EVALUATES: `Widget.tag(widget(1))` = Ok(Int(111)) and, through the `requires` path, `Box.same(widget(1))` = Ok(Int(111)). (C) THE DEFECT -- the spec carries a `rule tag(?x) = 111` DEFAULT and the carrier supplies nothing: LOADS CLEAN, then `Box.same(widget(1))` = Err(UnknownOperation { name: "tag" }) and the direct call `Nameable.tag(widget(1))` = Err(OperationBodyMissing { name: "probe.c.Nameable.tag" }). THE DIAGNOSIS IS EXACT, because (A)'s own message names the two conditions the check tests -- "no default on <spec>" and "no own <op> on <carrier>". Adding the `rule` default satisfies the FIRST condition, so the load check passes; the evaluator then cannot execute a rule default, because a RULE IS NOT A BODY (rules are SLD clauses; `invoke_op_with_requirements` wants an operation body). So the backing check and the evaluator DISAGREE ABOUT WHAT COUNTS AS BACKING, and the load-time guarantee that (A) exists to provide is void for exactly the programs that take the default path. SECOND, SMALLER DEFECT visible in the same run: the SAME missing body reports as `OperationBodyMissing` when the op is called DIRECTLY but degrades to `UnknownOperation { name: "tag" }` when reached THROUGH the `requires` path. `tag` is not unknown -- it is declared on `Nameable`, and `requires Nameable[T]` is precisely what brings it into scope. The requires path loses the information the direct path has, and reports a name-resolution failure for what is a missing-implementation failure. WHAT THIS TICKET IS NOT: an agent reported that a sort-level `requires` makes ANY of that sort's operations untrappable at eval ("DeferToRequirement: projection index 0 out of range (requirement `__req_eq` bundles 0 sub-requirement(s))"). Variant (B) REFUTES the general claim -- the `requires` dispatch path works and returns the right value. That separate error was seen on a differently-shaped program (stdlib `Eq`/`PartialEq`) and is NOT reproduced here; if it is real it is its own ticket, and it should not be conflated with this one. DECIDE, do not assume, because the fix could go either way: (1) the rule default is MEANT to be executable and the evaluator should route a bodyless spec op to its default rule (via SLD, the WI-580 body-derived-rule machinery being the nearby precedent) -- then (C) should return 111; or (2) a `rule` default is NOT executable backing, and the load check must STOP counting it -- then (C) should be REJECTED AT LOAD with (A)'s message, and the check's "no default on <spec>" condition needs to mean "no executable default". Option (2) is the smaller change and restores the load-time guarantee; option (1) is the larger and gives spec defaults real meaning. Whichever is chosen, the `UnknownOperation`-vs-`OperationBodyMissing` degradation is a bug in EITHER world and should be fixed alongside. ACCEPTANCE: the three variants are committed as tests, with (A) pinning the load rejection, (B) pinning the working value through the `requires` path, and (C) pinning the CHOSEN behaviour; the decision between (1) and (2) is recorded with its reason; a spec op reached through `requires` with no executable backing reports the SAME error as the direct call, naming the missing implementation rather than an unknown name; full workspace green via rustland/scripts/test.sh.
