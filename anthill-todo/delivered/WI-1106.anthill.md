## Description

A namespace-level `fact <Spec>[<binding>]` whose binding names NO TYPE is still silently dropped, and it cannot be refused until a provision claim is told from a DATA CONSTRUCTION by its written SURFACE.

WHERE. `maybe_emit_fact_provides_info` (rustland/anthill-core/src/kb/load.rs), the carrier-derivation `None` arm. WI-933 closed the sub-case with NO binding at all (the bracket-less `fact <Spec>`, now `LoadError::CarrierlessProvisionFact`). The sibling sub-case — a binding WAS written and resolves to no type (an unbound `?`, a literal, an operation on a non-parametric spec) — still `return`s with no diagnostic. The branch comment there names this ticket.

WHY IT WAS NOT CLOSED WITH WI-933, MEASURED. That same arm is where an ordinary DATA CONSTRUCTION lands. `fact Wi933Box(value: 1)` over an EPONYMOUS PARAMETRIC sort (`sort Box { sort T = ?; entity Box(value: T) }`, WI-926 — one symbol that is both) reaches it: the data-sort skip above needs `spec_params.is_empty()`, which a parametric sort is not, and the literal `1` resolves to no type exactly as a malformed carrier binding does. Measured by instrumenting the arm and running the full suite: 4 arrivals, and 2 of them were this shape (`wi927_bracket_surface_test::the_parenthesized_surface_still_constructs_and_still_checks_fields`, which requires a clean load). Refusing the sub-case outright breaks that test.

THE REAL QUESTION, and it is not about bindings. Parens construct, brackets apply types — parse already records which was written (`mark_type_application`, WI-927), and `maybe_emit_fact_provides_info` does not read it: it recognises a provision by the FUNCTOR's kind plus a constructor heuristic (`spec_params.is_empty() && sort_has_constructors`), which is why a parametric sort with constructors falls through both readings. Deciding this properly means asking the surface, and that changes which facts are provisions AT ALL — the blast radius is every `fact` in stdlib/, anthill-stl/, examples/ and the corpus, not one branch.

RELATED LATENT DEFECT TO MEASURE IN THE SAME PASS: on that path a construction whose field value DOES name a sort would derive that sort as a carrier and emit a bogus provider edge. This is the parametric twin of what `wi407_provider_edges_test::data_sort_fact_does_not_widen_*` pins for non-parametric data sorts. Whether it is reachable (a bare sort name in a value slot is refused by WI-707/WI-206) is the first thing to measure — if it is not, say so at the site and the scope shrinks to the diagnostic.

ACCEPTANCE: the loader decides provision-vs-construction by the written surface, or states at the site why it cannot and what the heuristic covers instead; the carrier-less-binding sub-case is either refused with a located diagnostic or documented as a construction; wi927's parenthesised-construction test and wi407's data-sort pins both stay green; a test drives the parametric-eponymous case from BOTH surfaces so the two readings cannot silently converge; cargo-test green via rustland/scripts/test.sh.

SOURCE: measured while delivering WI-933 (2026-08-15).

### 2026-08-15T10:39:11Z — feedback — user

SECOND MEASURED SHAPE, found in WI-933's own /code-review and fixed there by narrowing rather than by answering the question: a NULLARY CONSTRUCTION is written BARE.

`sort ZzBox { sort T = ?; entity ZzBox }` plus `fact ZzBox` at namespace level is a construction, is indistinguishable by SHAPE from the bracket-less provision WI-933 refuses, and reaches the same branch for the same reason (the data-sort skip needs `spec_params.is_empty()`). WI-933's first cut keyed on the written bare shape alone and BROKE it — it had loaded clean before. The shipped predicate is therefore `written_bare && !sort_has_constructors(functor)`: a sort that can be CONSTRUCTED keeps the lenient reading.

So this ticket now owns THREE shapes at that branch, not one, and they are one question:
  (a) `fact Box(value: 1)`   — bindings, construction
  (b) `fact ZzBox`           — bare, construction (nullary constructor)
  (c) `fact Spec[T = ?]`     — bindings that name no type, malformed provision
`sort_has_constructors` separates (b) from a provision only by a proxy — 'could this have been constructed' — and says nothing at all about (a) vs (c). The surface (parens construct, brackets apply types) answers all three at once, which is why it is the fix.

ALSO IN SCOPE NOW, same root: `fact Spec[op = impl]` on a spec with NO carrier type parameter. WI-431 (E) declines it for want of a parameter to name in its repair, and WI-933 will not take it because its own message would tell an author who wrote brackets to write brackets. It is silent today. Pinned as silent by `wi933_carrierless_provision_test::an_op_only_bracketed_fact_keeps_its_silence_rather_than_be_told_to_add_brackets`, which is where the wording decision goes.

NOT IN SCOPE, measured and settled: the bootstrap Rust mapper's twin of this defect. `emit_namespace_fact` derived the carrier from the PRECEDING ENTITY and ignored the bindings — `entity SqlStore(..) entity ColumnDef(..) fact QueryableStore[SqlStore]` emitted `// impl QueryableStore for ColumnDef`. Fixed in WI-933's commit (reads the brackets; a bare fact emits no marker), pinned by `codegen_test::fact_takes_its_carrier_from_the_brackets`.
