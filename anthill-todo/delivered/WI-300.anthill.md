## Description

Requirement goals in rule bodies (conditional-rule requirements). Today a realization requirement cannot be expressed as a rule-body goal: req_insertion::run (req_insertion.rs:41) weaves requirement forms (Expr::ApplyWithin / ConstructRequirement / RequirementAtSort / VarRef) ONLY into kb.op_bodies, never rule body_nodes. A 'requires(Eq[T])' written in a rule body (e.g. 'something(?x,?y) :- eq(?x,?y), requires(Eq[T])') parses — keywords are soft (grammar.js:23) — as an ordinary Expr::Apply{functor: requires, pos_args:[Eq[T]]} goal with NO requirement semantics: convert_rule_body (convert.rs:1647) has no special case, and at resolution it is just an undefined predicate that fails. Requirements today live only as: the standalone 'requires <Type>' decl -> SortRequiresInfo fact (load.rs:6004), and operation requires/ensures clauses -> OperationInfo reflect fact fields (load.rs:5850). SCOPE: design + implement rule-body requirement goals (conditional rules) — decide the surface syntax/semantics (likely a distinguished goal recognized in convert_rule_body or a type-directed weave), extend req_insertion (or an analog) to process rule body_nodes, and represent the woven form as occurrences consistent with the op-body *Within forms. Builds on the per-rule is_requires_resolved/mark_requires_resolved flags (mod.rs:456) which already exist but are not backed by body-level occurrence synthesis. Surfaced during WI-246 Phase 3c review.
