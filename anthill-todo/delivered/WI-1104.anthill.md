## Description

THE RULE-BODY ARITY TOLERANCE IS POSITION-BLIND, so one position of WI-1100's defect stays open — and the relational goal's RESULT COLUMN is never type-checked.

WI-1100 made a call's argument count a load error (`call_arity_error`, rustland/anthill-core/src/kb/typing.rs). It carries ONE tolerance: in a rule body a call at the operation's arity + 1 is admitted, because that is the FUNCTIONAL-RELATION view (kernel §5.3, WI-938) — `vec_add(a, b, ?c)` resolves as `unify(vec_add(a, b), ?c)`, and it is the shape WI-1043's rule-body spec-op dispatch is written in. MEASURED: back the tolerance out and 17 tests across five files fail (wi1026 / wi1035 / wi1043 / wi1044 / wi1100), so it is not optional.

WHAT IS WRONG WITH IT. The tolerance is gated on `TypingEnv::rule_body_dispatch`, a PER-RULE flag. The distinction it actually wants is GOAL vs VALUE position, which is `BodyPos` — and `BodyPos` lives in the rule-body walk (`dispatch_calls_in_occ`), not in the typing env. So the +1 is admitted in a VALUE position too. Review-found, and it is a live program, not a hypothetical:

  rule r(?y) :- leaf().describe(?d), ?y = concat("a", "b", "c")   -- loads clean

`concat` is binary; the three-argument call sits in the right-hand side of an `=` goal, which loads as a call on the body-less `PartialEq.eq` and so gets type-checked as one whole atom with the rule-body flag set. An operation body carrying the same expression is refused. One program, two verdicts, decided by where it is written — the shape WI-1035's own header calls out.

Note what is NOT open: the tolerance is exactly one column (`a_rule_body_goal_two_over_the_arity_is_still_refused`), and an operation body has no tolerance at all, so WI-1100's whole population is refused.

SECOND HALF, same site and same cause. The extra relational column is admitted but never TYPE-checked: the positional validation loop reads `written_params.get(i)`, so an argument past the declared list is skipped, and `Desc.describe(leaf(), "not an int")` relates nothing between the result column and `describe`'s declared `Int64` return. Nothing anywhere does — the goal shape is decided at resolution (`functional_relation_arity` / `dispatched_relation_arity`, kb/resolve.rs) where the declared return is not consulted either. Once the position is known at the check, this is the natural place to put it: at a GOAL at arity + 1, the last column is the operation's RETURN and can be validated like any argument.

WHERE THE WORK IS. Threading the position to `check_apply_iter` is the whole ticket. `dispatch_calls_in_occ` knows `BodyPos` and calls `type_check_node` on the atom, but the iterative typer types the atom's CHILDREN first, with envs cloned from the same parent env — so a plain env flag is inherited by nested calls and separates nothing. Approaches to weigh, none free: pass the position into the work-loop's Visit frames and derive child positions there (the honest fix, and `child_body_positions` already exists for the walk); or decide the arity in `dispatch_calls_in_occ` per position and stop deciding it in Path 1 for rule bodies — which must not grow a SECOND owner of the rule (`bind_call_arguments` + `call_arity_error` stay the one owner, called from two sites), and must not re-derive the WI-727 capture rewrite's argument list.

Acceptance (each DRIVES it):
- `rule r(?y) :- leaf().describe(?d), ?y = concat("a", "b", "c")` is REFUSED, naming `concat`, its arity and the count. FAILS before (loads clean).
- the same program with `?y = concat("a", "b")` still loads — the value-position control.
- every rule-body GOAL at arity + 1 still loads: the 17 tests above stay green, and `wi1100_call_arity_test::a_rule_body_relational_goal_still_loads` in both spellings (qualified and dotted).
- a rule-body goal whose result column contradicts the operation's declared return (`Desc.describe(leaf(), "s")` against `-> Int64`) is REFUSED. FAILS before (loads clean, answers nothing at resolution).
- a well-typed result column (`Desc.describe(leaf(), ?r)`, and a ground `Desc.describe(leaf(), 7)`) still loads — the control for the half above.
- the whole workspace suite passes.
