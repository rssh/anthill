## Description

Proposal 058 (WI-648) PHASE 5 — SPEC: amend docs/kernel-language.md §Instance coherence to the ladder actually implemented, and document the named requirement slot. KEPT AS ITS OWN TICKET DELIBERATELY: folding a doc change into the phase that implements it is how spec drift happens, and §3 of this proposal exists BECAUSE the spec drifted — three texts describe three different rules and none matches the code (kernel-language.md:2109 / :2111 promise PER-SCOPE selection, "the per-`import` choice"; WI-648's own framing says global default + named opt-in; the implementation is GLOBAL, unconditional, refused at LOAD). The ruling (§3): the per-`import` text is not merely unimplemented, it CANNOT EXPRESS EITHER DRIVER — the deciding argument needs both monoids in ONE body (`fold[Monoid = AddM](xs)` beside `fold[Monoid = MulM](ys)`) and per-`import` selection admits at most one provider per scope; `SortedSet.new(cmp)` chooses per CONSTRUCTION SITE, and two differently-ordered sets routinely coexist in one function. So it is the TEXT that must change, and the amendment NARROWS a promise the code never kept, so no loading program changes meaning. WORK: (a) replace the §Instance coherence paragraph with §10's text — at most one DEFAULT provider per carrier; a second is permitted, but only when EVERY candidate can be NAMED, and every dispatch must then say WHICH by binding the requirement slot at the call; an unselected dispatch with two candidates is an error naming both; selection is EXPLICIT and PER-CALL, not per-scope; implicit scope-directed selection (a nearer provider silently winning) is deliberately NOT the rule. (b) Replace the sentence at :2109 ("A consumer chooses which instantiation to use via `import`") — an import governs VISIBILITY, and among visible providers the CALL selects. (c) DROP, do not reword, the retained clause "resolved in that sort's scope and captured when its instance is constructed, so `Spec[carrier]` behaves consistently within any one instance": under §4.7 an ANONYMOUS slot records nothing, and every embedded requirement in the stdlib today is anonymous (`requires Eq[T = K]`, map.anthill:7; `requires Eq[T]`, set.anthill:10) — keeping it would repeat in the REPLACEMENT exactly what §3 charges the current text with. State instead the named-vs-anonymous rule: a NAMED slot is a type parameter, so the chosen provider is part of the sort's type identity and every value of that type carries it; an ANONYMOUS slot is a constraint — solved, not recorded — so it fixes nothing about the type and is re-answered at each dispatch, which is why two `Map[K = Int64]`s cannot differ by which `Eq` satisfied them. (d) Document §5.4 named requirement slots and the §4.7 named-vs-anonymous rule. (e) Split kernel-language.md:909's description of operation-level `requires` in TWO — a VALUE precondition (`requires neq(b, 0)`, WI-539) and a TYPE precondition (`requires Ord[T]`, WI-448); the implementation already draws that line, the call-site contract check filtering to the value goals via `is_value_precondition_clause` and leaving the type ones to dispatch. ACCEPTANCE (§9 phase 5): spec and implementation AGREE, which is what §3 says they do not today; every claim in the new text is either measured or cites the code that enforces it; the proposal's Status line is updated to Accepted/Landed. REFERENCE: docs/proposals/058-modular-instances.md §3, §10, §4.7, §9 phase 5.
