## Description

IndexedFileStore + QueryableStore foundation (proposal 036 phase 1). Prerequisite for proposal 036's domain store sorts (WorkItemStore over QueryableStore). Three concrete pieces, all backend-side; downstream consumers (the WorkItemStore spec, future GitHub/RemoteApi backends, any other domain store needing pattern-matched lookup) build on top. Pieces: (a) stdlib declaration. In stdlib/anthill/persistence/filesystem.anthill, add 'entity IndexedFileStore(root: String, convention: FileConvention)' alongside the existing FileStore entity, plus 'fact QueryableStore[IndexedFileStore]' (the existing 'fact BulkStore' on FileStore stays). The bundle's host already wires an IndexedFileStore Rust impl behind a FileStore Value::Entity (canonical-key shape coincides); this declaration makes the Value-side type honest. Both entities can coexist — FileStore for projects that don't need source-span retract, IndexedFileStore for those that do. (b) retrieve Rust builtin. The QueryableStore spec declares 'operation retrieve(store: QueryableStore, pattern: Term) -> Stream[Term, Error] effects Error'. Implement it for IndexedFileStore: walk the in-memory fact cache that IFS already maintains post-pull, unify each fact against the pattern using the existing unification machinery from kb/subst.rs, yield matches as a Stream via the existing StreamSource::External path (proposal 026.1 Q4 / 007 §11) so each row enters σ as Value::Entity without TermStore allocation. Register as a builtin in anthill-stl/src/persistence/builtins.rs (sibling to the existing persist/retract/flush/pull builtins from WI-051's persistence wiring). O(N) scan per query — fine at bundle CLI scale (tens to hundreds of facts); a future variant could index by functor or field for sublinear queries. (c) tests. retrieve(ifs, WorkItem(id: "WI-001")) returns the matching fact (one element if present, empty if not). retrieve(ifs, WorkItem(status: Open())) streams every WorkItem with status Open. retrieve(ifs, WorkItem()) — pattern with no fields bound — streams every WorkItem fact. Pattern variables (?x) are unbound on the result side; concrete values bind. Acceptance: cargo test green; the new builtin is reachable from anthill source as 'anthill.persistence.retrieve'; the IndexedFileStore entity loads cleanly. Independent from proposal 036's project-side phases (phase 2: WorkItemStore spec + FileBasedWorkitemStore impl; phase 3: bundle refactor). Phase 1 is committable on its own and unlocks any future QueryableStore consumer beyond just WorkItemStore.

## Changes

### 2026-05-08T09:11:15Z — feedback — user

Scope expansion: WI-202 also extends the IndexedFileStore Rust struct with a primary-key index — by_id: HashMap (String to RuleId) populated at pull, maintained on persist/retract. The id field name is a v0.1 convention (every domain entity in an IndexedFileStore is expected to have a String-typed id field; a future generalization via PrimaryKey marker fact is out of scope). retrieve uses the index for O(1) lookup when the pattern has id bound; falls back to O(N) scan otherwise. This makes the Indexed in IndexedFileStore honest in both senses: indexed for retract (WI-187, already landed) AND indexed for query (this WI). Without the primary-key index, retrieve would be O(N) scan-and-unify which is fine at CLI scale but misnames the struct. See proposal 036 §3 for the design.
