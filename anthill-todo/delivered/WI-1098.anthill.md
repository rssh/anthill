## description

DERIVE Eq for a TOTAL composite, symmetric with the NonEq derivation eq_derive already does -- today an entity without `provides Eq` loads clean and PANICS THE EVALUATOR when it reaches a `requires Eq[T]`.

MEASURED, three fixtures, all against the shipped stdlib:

  (1) NO `provides Eq` -- sort Colour { entity red; entity green }
      LOADS CLEAN.
      eq(red, red)   => 1 solution   (works -- the structural reflexivity shortcut)
      eq(red, green) => 0 solutions  (correct)
      List.contains(cons(head: red, tail: nil), red)
        => *** PANIC ***
           bridge_op_to_eval: internal evaluator error bridging
           'anthill.prelude.List.contains': DeferToRequirement: requirement param
           '__req_eq' not bound in caller frame (running
           'anthill.prelude.List.contains', requires-chain owner
           'anthill.prelude.List.contains'; frame binds [])

  (2) CONTROL, the same program WITH 'provides PartialEq[T = Colour]' and
      'provides Eq[T = Colour]': loads clean, eq answers 1, contains answers 1.
      So the ONLY difference is the two provision lines.

  (3) A FLOAT FIELD -- sort Point { entity pt(x: Float, y: Float) }: eq_derive
      already asserts BOTH provisions, measured --
      [("eqp3.Point", "anthill.prelude.NonEq"), ("eqp3.Point", "anthill.prelude.PartialEq")].

SO THE DERIVATION EXISTS AND RUNS ONLY ON ONE HALF. eq_derive (WI-664 / proposal 004, kb/eq_derive.rs) computes the lawfulness classification as a monotone FIXPOINT over the field-reference graph -- the hard part -- and its own doc says it 'asserts the derived NonEq+PartialEq provision facts for each PARTIAL composite'. The TOTAL composites are classified by the same fixpoint and get nothing. This ticket is the symmetric half: assert 'provides Eq' (and its PartialEq base -- Eq requires it) for a composite the classifier finds TOTAL.

WHY DERIVE RATHER THAN REFUSE. The obvious alternative -- make an entity without Eq a load error -- was considered and is worse. Structural equality IS derivable for any ADT whose fields are Eq; that is precisely what the fixpoint already decides. Refusing 'sort Colour { entity red }' until its author writes two provision lines taxes every enum in the language for a fact the compiler already knows. Deriving makes the measured program WORK; refusing makes it not compile. Note also that the classifier's boundary is already exactly the resolver's dispatch boundary (it reads load::EqDispatchIndex), so a sort that declares its OWN eq is not overwritten -- TotalFloat stays lawful, which is the case that would break a naive derivation.

THE FAILURE MODE IS THE ONE THIS REPO KEEPS PAYING FOR: a program that loads clean and dies at eval, and it dies with an INTERNAL error ('internal evaluator error'), not a diagnostic naming what the author should write. Same family as WI-945 / WI-1095. Even if this ticket were somehow rejected, that panic must become a diagnostic naming the sort and the missing provision.

SCOPE NOTES, from eq_derive.rs's own doc so they are not rediscovered:
 - the classifier's DOMAIN is entities + named tuples with CONCRETE fields; a partial leaf reached only through a parametric container is out of scope there and presumably here too -- state which way this ticket goes;
 - it runs AFTER the provider-coverage checks and BEFORE check_eq_noneq_exclusive; a derived Eq must not collide with a user-written 'provides Eq' for the same carrier (idempotent, not a duplicate-provision error) nor with a derived NonEq (the two are exclusive by construction -- the fixpoint puts a sort in exactly one class, but that must be ASSERTED, not assumed);
 - defaults.rs builds a provision-derived table twice, the second time after eq_derive::run, precisely because provisions are only ADDED between the two calls. A new provision source must respect that ordering or the typer sees a table missing these rows.

ACCEPTANCE:
 - fixture (1) above ANSWERS -- 'List.contains(cons(head: red, tail: nil), red)' returns a solution rather than panicking, driven, with the negative twin (contains of an absent colour) answering ZERO so a vacuously-true derivation fails;
 - CONTROL (2) kept: the explicit-provides twin still works and does not become a duplicate-provision error;
 - CONTROL (3) kept: a Float-field composite still gets NonEq and NOT Eq -- this is the row that fails if the derivation is asserted for every composite rather than for the TOTAL ones;
 - a sort declaring its OWN eq (the TotalFloat shape) still dispatches to it and is not shadowed by a derived provision;
 - a RECURSIVE composite (sort Tree { entity leaf; entity node(l: Tree, r: Tree) }) driven, since the classifier is a fixpoint for exactly that reason;
 - say at the test site which tests fail when the change is backed out and which pass either way by design;
 - full workspace green via scripts/test.sh (a provision-source change => FULL workspace; check cpp-gen and scaland, which pin stdlib shapes).
