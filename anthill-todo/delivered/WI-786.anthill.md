## Description

`classify_ctor_arg` splits a tuple literal's components into `Value::Tuple.pos` vs `.named` by a `_`-PREFIX TEST ON THE LABEL TEXT, so a USER-WRITTEN label beginning with `_` is silently reclassified as positional -- the pos/named split then no longer follows source order, and the label is discarded. eval/eval.rs ~2583 does `kb.resolve_sym(sym).starts_with('_')`; the test exists to unwrap the parser's SYNTHETIC `_1`/`_2` labels (positional surface syntax lowers to them, per kernel-language.md "Positional syntax is sugar for auto-generated names `_1`, `_2`"), but the identifier grammar is `/[a-zA-Z_][a-zA-Z0-9_-]*/`, so `_id`, `_b`, `_total` take the same branch. MEASURED: `(a: 3, _b: 10)` builds `Value::Tuple { pos: [10], named: [(a, 3)] }` -- the SECOND written component first, the first one second. A three-component `(a: 1, _b: 2, c: 3)` builds `pos: [2], named: [(a,1),(c,3)]`. THIS IS A KNOWN HAZARD THAT WAS GUARDED IN EXACTLY ONE PLACE: `validate_projection_labels` (parse/convert.rs ~1139-1147, WI-639 distributive projection) rejects `_`-prefixed labels with the comment "classify_ctor_arg re-slots ANY `_`-keyed tuple field positionally in argument order, discarding the label, so a reordered projection silently returns the wrong column". The same guard was never applied to the PLAIN tuple-literal producer, which is the common path. CONSEQUENCES BEYOND THE PRODUCER: (a) any consumer that reconstructs source order as `pos ++ named` gets the wrong order -- measured while fixing WI-785, where binding a destructuring lambda across the split returned 7 instead of -7 and made an operation declared `-> Int64` return `Str("ess")` on a clean load; WI-785 now REFUSES the mixed shape rather than guessing, which is a workaround, not a fix; (b) `t.x` field access (eval/builtins.rs ~272) looks the label up in `named` ONLY, so a component reclassified into `pos` becomes unreachable by name -- `t._b` would have to be spelled positionally, and `_b` is indistinguishable from the synthetic `_2`; (c) the label is DISCARDED on the move to `pos` (`pos` is a bare `Vec<Value>`), so the split is UNRECOVERABLE downstream -- no consumer can re-interleave. FIX DIRECTIONS (pick one): (1) narrow the test to a label that is exactly `_<index+1>` for its own position, so only genuinely synthetic labels are unwrapped and `_b`/`_id` stay named -- smallest, and makes `pos ++ named` source-order-faithful whenever the tuple came from a literal; (2) reject `_`-prefixed user labels at the tuple-literal producer the way `validate_projection_labels` already does for projections -- consistent with the existing guard but a surface-compatibility break; (3) stop encoding positionality in the label text -- carry an explicit arity/positional marker on the tuple literal so the classifier never has to guess from a name. Direction (1) is the least invasive and preserves the existing surface. NOTE this interacts with the repo's stated direction that a tuple is an ORDERED PRODUCT whose "source order IS its identity" (kb/resolve.rs `canonicalize_record_named_args` returns early for `TupleLiteral`): that exemption keeps `named` internally ordered but cannot help once components have been split across two vectors by label text. ACCEPTANCE: a tuple literal mixing plain and `_`-prefixed user labels preserves source order in whatever representation survives (either both stay in `named`, or the literal is rejected at load with a located diagnostic); `t._b` on such a tuple resolves the component the user wrote; the WI-785 mixed-shape refusal (`mixed_pos_and_named_tuple_refuses_rather_than_misbinding`) can be relaxed to a successful positional bind, or is restated as the permanent rule with its reason updated; a regression test drives a mixed-label tuple end-to-end through destructuring AND field access and asserts they agree; full workspace green via scripts/test.sh.
