## Description

Proposal 058 (WI-648) PHASE 1 — DECLARE: grammar + loader for the NAMED requirement slot `requires name: Spec[…]`, on an OPERATION and on a SORT (§4.7), plus the §4.2 shadowing guards. Today `requires d: Desc[E]` does not parse (measured: `syntax error near ': Desc'`): the two existing productions carry no name slot — `requires_declaration: 'requires' <type>` (sort/namespace level, a bare TYPE) and `requires_clause: 'requires' <rule_body>` (op-scoped, WI-448) — and design/operation-call-model.md states the current property outright, sub-requirements are "positional and nameless (impl-side `requires` clauses have no source-level names)". WHY IT IS NOT OPTIONAL PLUMBING: a NAMED slot IS a type parameter, which is what lets a witness enter a TYPE (`SortedSet[T = String, O = ByLength]` vs `… O = Alphabetical]` are then different types by the ordinary checker); without a name the SortedSet merge hazard cannot be STATED at all. The SELECT surface needs no grammar change (§4.2 reuses 042's bracket); this DECLARE binder is the only new grammar in the proposal. THREE WRINKLES, all found by reading the productions rather than assumed (§4.7): (1) the op-scoped clause is OVERLOADED — one `rule_body` list holds both spec requirements (`operation member(x: T, l: List) -> Bool requires Eq[T]`, stdlib/anthill/prelude/list.anthill:58) and VALUE preconditions (`requires neq(b, 0), gt(b, 0)`, WI-539); a binder attaches only to the TYPE flavor and must coexist with predicates in the same comma list (the implementation already draws that line — `is_value_precondition_clause`); the sort-level form takes a type only, so it is clean there; (2) `d: Desc[E]` sits next to named-argument syntax inside a rule_body (`f(x: 1)`) — a bare `name: Type` is not valid at rule-body top level today so the extension is available, but `requires_clause` already needs `prec.dynamic(1)` to win a GLR tie against `requires_declaration`, so this wants a tree-sitter CORPUS TEST, not an assumption; (3) the binder names the TOP-LEVEL slot only — sub-nodes inside a ResolvedSortNode stay positional (`requirement_at_sort(node, k)`); phase 1 adds a name where one was missing, it does NOT re-key the projection path. GUARDS (§4.2 — refused AT THE DECLARATION, not at the call): an operation may not declare a type parameter whose name collides with (a) one of its own requirement SPEC SHORT NAMES, and for a spec's own operations with the SPEC's own short name (which would shadow the direct-dispatch key `Desc.describe[Desc = …]`); (b) one of its ENCLOSING SORT's type parameters, including a sort-level named slot — phase 2 makes bracket rule (1) span both scopes, and an ordered ladder there would be a silent capture the reader cannot see. Binder-vs-parameter collision needs no separate case: a named slot IS a parameter, so the ordinary duplicate-parameter rule covers it. ACCEPTANCE (§9 phase 1, verbatim): a two-slot op loads; a named sort-level slot is addressable in type position (`Box[E = …, O = …]`); a colliding type-param name is refused AT THE DECLARATION. PLUS: a tree-sitter corpus test pins the GLR tie (binder form vs `requires <type>` vs a value precondition in one clause list). SCOPE: tree-sitter-anthill grammar + Rust loader; scaland mirrors. Full workspace green via rustland/scripts/test.sh. REFERENCE: docs/proposals/058-modular-instances.md §4.7, §4.2, §9 phase 1.
