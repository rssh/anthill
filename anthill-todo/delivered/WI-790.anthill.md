## Description

`term_ser` mints positional field labels ZERO-based (`_0`, `_1`, ...) while the language convention and all seven other minters are ONE-based (`_1`, `_2`, ...), so a serialized `Term::Fn`'s positional slots carry keys no reader in the codebase interprets correctly. persistence/term_ser.rs ~896 does `all_fields.insert(format!("_{i}"), val)` over `pos_args.iter().enumerate()`. Every other producer emits `format!("_{}", i + 1)`: parse/convert.rs `intern_positional_label` (~326, the canonical one, serving both tuple literals and tuple TYPES), kb/load.rs ~1628, kb/load.rs ~10688, and kb/typing.rs ~4638 / ~7432 / ~17603 / ~27179. The spec agrees with the 1-based form -- docs/kernel-language.md states positional syntax is sugar for auto-generated names `_1`, `_2`, `_3`. CONSEQUENCES for a mixed positional+named `Term::Fn` serialized to JSON: (a) the key `_0` is rejected by every reader -- `field_access` (eval/builtins.rs ~280) does `idx.checked_sub(1)` so `_0` underflows to not-found, and `field_step_in_value` (kb/load.rs ~10133) filters `n >= 1` and drops it; (b) worse, the keys that DO parse are off by one in meaning -- `_1` in that JSON denotes source index 1, while `_1` everywhere else in the system denotes source index 0 -- so a value that round-trips through this encoding shifts by a slot; (c) after WI-786, `is_synthetic_positional_label` classifies `_0` as a USER label (it rejects a zero digit outright), so a reloaded positional component would additionally be re-slotted as named. BLAST RADIUS IS LOW TODAY -- this is a one-way encode with no matching decoder in the same file, so nothing currently reads these keys back -- which is precisely why it has survived; it is a latent trap that fires the moment anyone writes the decoder or feeds this JSON to an existing reader. WHY IT MATTERS BEYOND THE OFF-BY-ONE: this is the clearest single piece of evidence that the `_N` convention has NO OWNER. Eight sites mint it and five parse it, with five different rules (see the sibling ticket on the printer for the enumeration), and one of the eight has silently disagreed with the other seven for as long as it has existed. WI-786 narrowed one of the five recognizers and thereby de-synchronised it from the rest; adding a ninth spelling rather than removing the shared namespace is what makes each of these tickets necessary. FIX DIRECTIONS: (a) minimal -- change term_ser.rs ~896 to `format!("_{}", i + 1)`; (b) better and shared with the printer ticket -- extract `positional_label(index) -> String` and `positional_label_index(label) -> Option<usize>` into `intern.rs` (which sits below parse/, kb/, eval/ and persistence/ in the dependency order, so every producer and consumer can call it), then route all eight minters and five recognizers through that one pair, so the convention can only be changed in one place. Note that direction (b) would have made this bug a compile-time impossibility rather than a silent textual divergence. Found by /code-review on 93b23188. ACCEPTANCE: `term_ser` emits `_1`-based keys agreeing with `intern_positional_label`; a round-trip test serializes a `Term::Fn` carrying both positional and named args and asserts the positional slots reload to the SAME indices (not merely that serialization succeeds); if direction (b) is taken, no module spells the convention with its own `format!`; full workspace green via scripts/test.sh.
