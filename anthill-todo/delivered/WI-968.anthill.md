## Description

Two different functions are both named `register_standard_builtins`, and one is imported BARE.

MEASURED (WI-967):
  KnowledgeBase::register_standard_builtins  (kb/mod.rs)          - registers builtin TAGS on the KB. 1 caller: register_prelude. Now pub(crate).
  eval::builtins::register_standard_builtins (eval/builtins.rs)   - registers host fns on an Interpreter, returns Result. 29 call sites, legitimately re-run per fresh interpreter.

They do unrelated things to unrelated receivers on unrelated schedules, and nothing in either name says so. WI-967 could only survey the KB one by matching the METHOD-call form `.register_standard_builtins` to separate them mechanically.

WORST CASE, and it is live: anthill-core/tests/include/type_extract_test.rs:5 does `use anthill_core::eval::builtins::register_standard_builtins;` and then calls a BARE `register_standard_builtins(&mut interp)` five times. A reader who knows the KB method reads those as KB bootstrap. eval_test.rs and several others spell it fully qualified, so the codebase is inconsistent about which one a bare name means.

ALSO STALE: kb/load.rs's OperationMapping doc-comment says '`register_standard_builtins` is re-run for every FRESH interpreter'. True of the eval one, false of the KB one, and the sentence does not say which - it sits in load.rs, where the KB one lives.

THE QUESTION: rename one of them. The eval one is arguably the odd one out (it registers host FUNCTIONS, not 'builtins' in the KB's tag sense) - e.g. `register_host_fns` / `register_interpreter_builtins`. Alternatively rename the KB one to `register_builtin_tags`, which is what it actually does and would pair with its `register_builtin` element function.

ACCEPTANCE: one name per concept; no bare import of either that could be read as the other; the load.rs OperationMapping comment names which function it means; cargo-test green.
