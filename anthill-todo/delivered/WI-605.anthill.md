## Description

Typer: an inline lambda expression passed as a higher-order argument in an OPERATION BODY fails to resolve its parameters. Minimal repro: `operation sum_inc(xs: List[T=Int64]) -> List[T=Int64] = foldRight(xs, nil, (x, acc) -> cons(head: x + 1, tail: acc))` errors with 'type mismatch in x.name: expected resolved name, got unresolved' (and same for acc) — the lambda's bound params x/acc are not entered into a resolution scope, so their uses in the body read as unresolved names. Adding explicit param type annotations does NOT help (same error on the annotation names too). Surfaced while authoring the WI-590 finite-combinator consolidation: a recursion-free `collect` drain wants `foldRight(FiniteCollection.collect(src), nil, (x, acc) -> cons(head: fn(x), tail: acc))`, which is blocked by this. Likely a converter/scope gap: lambda_expr params in an op-body argument position are not registered as locals the way op params or match-case binders are. ACCEPTANCE: the minimal repro type-checks; an inline lambda arg can reference its own params; cargo-test green.

## Changes

### 2026-07-02T22:32:04Z — feedback — user

Diagnosis correction: there is NO lambda-scope gap. The repro's `(x, acc) -> cons(...)` is not a lambda at all — the lambda keyword is required (kernel-language.md §4.7, proposal 018, deliberate). Keyword-less `pattern -> body` in expression position parses as an infix `->` chain, which the pratt desugar lowers to an arrow-TYPE term `arrow(tuple(x, acc), body)`; its LHS names then load as unresolved value refs, producing the misleading per-binder 'expected resolved name, got unresolved' cascade. The keyword form `lambda (x, acc) -> ...` in the same op-body argument position loads clean (regression-tested). Fix delivered: targeted load-blocking diagnostic LoadError::ArrowTermInExprPosition at the arrow term ('a lambda needs the lambda keyword'), gated on `arrow`/`arrow_effect` not resolving in scope so a user-defined arrow operation keeps the normal call path; Bottom-leaf recovery keeps the load walk shaped. Acceptance amended accordingly: the repro now fails with ONE actionable error instead of type-checking (making bare arrows BE lambdas would collide with arrow-type terms in term position — types are terms). WI-590's drain should just use the lambda keyword.
