## description

The FUNCTIONAL-RELATION form 'f(args, ?result)' answers NOTHING at ordinary resolve time, while the spec documents it as an equivalence and the typer deliberately exempts it.

THE SPEC CLAIM. docs/kernel-language.md (the WI-583 paragraph, 'A Bool-returning operation may be used directly as a rule-body goal'): '...the functional-relation form f(args, result) (one extra argument, the result column -- e.g. status(?fs, ?p, FileStatus(...)) = eq(status(?fs, ?p), result)) is unaffected'. It is written as a stated equivalence.

MEASURED (2026-08-02, delivering WI-935), via common::load_kb_with + query_unary -- stdlib + rust bindings from disk, not the CLI:

  rule rel(?c) :- Vec3.vec_add(Vec3(x: 1.0, y: 2.0, z: 3.0),
                               Vec3(x: 10.0, y: 20.0, z: 30.0), ?c)
  -> LOADS CLEAN, 0 solutions, no diagnostic.

anthill.geometry.Vec3.vec_add is a 2-param bodied operation; the goal is at arity+1. Nothing implements the equivalence at resolve time: bare_bodied_bool_relation (resolve.rs:6147) grants a relational view only to BOOL-returning ops (routing f(args) to eq(f(args), true)), and there is no arity+1 sibling. check_goal_atom_op (typing.rs:37318) SKIPS any call whose arity != the op's param count, so WI-583's loud NonBoolOpInGoalPosition never fires either. The result is precisely the silent failed relation lookup WI-583 exists to eliminate, one arity over.

WHERE IT IS ACTUALLY IMPLEMENTED, and where it is not: the PROVE tier builds it. anthill-cli/src/prove.rs:1931 calls synthesize_body_derived_defrules, which synthesizes 'op(?0..?n-1, ?result) :- ?result = <body>' under the op's own functor (WI-669) for the obligation's transitive body. That is run-scoped and prove-only. lf1 depends on it in production (safety_gps.anthill:153, FollowerController.desired_position(?leader_real, ?off, ?target)). SLD resolution outside a prove run has no such path.

STDLIB IS WRITTEN IN THIS FORM AND NEVER DRIVEN. stdlib/anthill/realization/platform.anthill:147 'rule needs_rebuild(?fs, ?input, ?output) :- exists(?fs, ?input), status(?fs, ?input, FileStatus(...)), ...' calls Filesystem.status/2 at arity 3, with the file comment 'needs_rebuild below uses the Filesystem operations as relations'. No test resolves needs_rebuild -- grep found only typer-pass tests naming it. So whether it answers is UNMEASURED, and on this ticket's evidence it probably does not.

WHAT MUST BE DECIDED (the ticket does not prescribe):
 (a) IMPLEMENT it -- give a non-Bool bodied op the arity+1 relational view at resolve time, the same way WI-580 gives a Bool op the arity+0 one. The prove tier already shows the shape. Note the precedence rule must carry over: a hand-written clause of the same functor WINS (design abstract-interpreter-and-rules.md 3.3), which WI-935 measured -- adding a clause under Vec3.vec_add's functor stops the derivation.
 (b) REFUSE it -- widen check_goal_atom_op's arity gate so an arity+1 call on a rule-less bodied op is a located load error, and rewrite stdlib needs_rebuild. Cheaper, but it deletes a form the spec, lf1 and stdlib all use.
Either way the spec paragraph must stop stating an equivalence the resolver does not provide.

ACCEPTANCE: driven either way -- (a) a resolve that BINDS the result var, plus a control that a hand-written clause still wins; or (b) a located diagnostic plus a rewritten needs_rebuild that is itself driven. In both cases needs_rebuild gains a test that RESOLVES it. Spec updated. cargo-test green.
