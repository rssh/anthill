CLI/resolver: the WI-754 unknown-functor guard is HEAD-ONLY and covers only the TOP-LEVEL query pattern's functor, so two adjacent silent-skip cases survive. Both measured 2026-07-29 on the WI-754 build.

(A) NESTED unknown functor inside a goal-consuming builtin is NOT flagged, and `not(...)` over one silently SUCCEEDS. `anthill query -p kb 'not(nonexistent(42))'` prints `true` / `1 solution(s)` (exit 0). The head is `not` (a resolved builtin, so the WI-754 guard passes it); the unknown `nonexistent` sits at `pos_args[0]`, which the head-only `undefined_query_functor` never inspects. `step_naf` resolves the inner goal, an undefined functor yields a complete-empty search (not truncated, not floundered), and NAF reads that as "the negand is false, so `not` holds" — a confident `true` for a predicate that does not exist. This is WORSE than the silent-empty WI-754 fixes: it asserts a negation. (An unbound inner `not(nonexistent(?y))` correctly flounders; only the GROUND inner goal hits this.) The same blindness applies to any functor nested below the head — a conjunct of a bounded quantifier body, an argument that is itself a goal. NOTE the tension: NAF-over-undefined = false is standard closed-world Datalog, so "fix" here means a QUERY-MODE diagnostic (warn/refuse when a nested goal names a functor with no clause), not a change to resolution semantics — decide the altitude. FIX DIRECTION (unsettled): walk the query term's goal positions (not just the head) collecting undefined functors, gated to the CLI query path so NAF elsewhere is untouched.

(B) A SURFACE OPERATOR that desugars to an unloaded functor is refused with the DESUGARED name, which misattributes the cause. `anthill query -p kb '6 / 2'` -> `error: 'div' ... does not resolve to a known functor` (exit 1); likewise `7 mod 3` -> `mod`, `2 ^ 3` -> `pow`, `a and b` -> `and`. Two causes compound: (b1) `div`/`mod`/`pow` are defined in NO loaded scope, and `and`/`or`/`neg` are stdlib-only while `anthill query -p` loads with `include_stdlib=false` (main.rs), so the operator's target functor genuinely is not present; (b2) the pratt table (parse/pratt.rs) desugars `/` to `div` BEFORE the query is checked, so the diagnostic names `div`, not the `/` the user wrote. The WI-754 refusal is not wrong (the functor really is absent, and loud beats the old silent `no solutions`), but the message sends the user to "qualify or import" a name they never typed. FIX DIRECTIONS (pick, unsettled): (i) load the stdlib into `anthill query` so arithmetic/boolean operators resolve — the larger, likely-correct fix, but it changes query's default KB; (ii) map a desugared operator functor back to its surface spelling in the diagnostic; (iii) leave arithmetic unloaded but special-case the message. `or` is currently accepted where `and` is refused (kernel.or is registered, Bool.and is stdlib-only) — an inconsistency (i) would also erase.

(C) An undefined functor whose SHORT NAME collides with a resolver scoping marker escapes the report. `anthill query -p kb 'some_in(x)'` with `some_in` declared nowhere prints `no solutions` (exit 0), because `undefined_query_functor` exempts `forall_in`/`some_in`/`forall_impl`/`__pop_assumption` via `is_scoping_marker_name(resolve_sym(sym))` — a SHORT-name check. The exemption is deliberate and consistent: the resolver ALSO keys these forms on the short name (`bounded_quant_kind` → `resolve_sym`), so the resolver already reserves the whole `some_in` name (even a qualified `myns.some_in` is intercepted as a malformed quantifier), and reporting it while the resolver hijacks it would be incoherent. The residual is only that a user who genuinely typos one of these four names gets silent `no solutions` instead of a loud report. FIX DIRECTION (unsettled, low value): if the resolver's marker recognition were tightened (e.g. arity-checked, or the markers moved to a reserved namespace), the CLI check could tighten in lockstep — do NOT diverge the two independently.
