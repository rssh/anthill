## Description

Retract/persistence identity and seam redesign -- rework the write-side boundary on top of the WI-773 accessor pattern (depends on it landing the decided bodied-rule policy and the raw-access scoping precedent). THREE identities coexist for a stored fact: domain key (IndexedFileStore.by_id String->RuleId, persistence/indexed_file_store.rs:54), content (hash-consed ground head TermId -- canonical identity for ground facts), and event (RuleId -- an ephemeral in-process index). The identity crossing the anthill boundary today is the EPHEMERAL one: FactId = Literal::Handle(HandleKind::Fact, RuleId.raw) (eval/builtins.rs:2842) -- meaningless across processes, guarded in-process only by is_rule_alive. The composed flow even maps content->RuleId (find_fact bucket scan) and then RuleId->content again (FileStore::retract canonical head print) -- the durable identity was the content all along. Second wart: a comment-enforced temporal protocol -- Store::retract must run BEFORE kb.retract or the store reads released TermIds (eval/builtins.rs:3609-3611, persistence/mod.rs:117). DIRECTION: (1) boundary retract keyed by content or domain key; RuleId demoted to the store/persistence layer private address -- the same visibility ratchet as the WI-773 read side; (2) ONE retract_persistent seam owning the store+kb ordering so the two-phase discipline is not caller-visible; (3) FactId handle becomes an internal optimization or is dropped; (4) decide where the proposal-053 monotonicity guard lives in the new seam. Related: WI-774 (resolve-vs-refuse) covers the READ semantics; this item is store addressing only. WI-779 is the interim loud guard this redesign subsumes. ACCEPTANCE: design note or implementation with the boundary API switched; ordering no longer caller-visible; cargo-test green via scripts/test.sh.
