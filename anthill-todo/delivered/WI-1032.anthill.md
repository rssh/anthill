## Description

Two provisions that say the same thing are ONE dispatch candidate. MEASURED, two defects from one cause: (a) 'sort Leaf { provides Desc[T = Leaf]; operation describe(x: Leaf) = 7 }' beside a namespace-level 'fact Desc[T = Leaf]' is ONE dictionary written in two places - exactly WI-859's admitted cell (1 fact, 0 witnesses, 1 self-provider) - yet 'collect_provides_candidates' produced TWO structurally identical candidates, they tied at equal specificity in 'pick_most_specific', and the CALL was refused 'ambiguous dispatch ... 2 instances provide Desc (Leaf, Leaf)'. A program with a SINGLE implementation, refused, naming one carrier twice, advising 'pin the carrier through the call's receiver' - a repair that changes nothing since the carrier IS pinned. WI-859's admission rests on the cell 'admitting a group whose conflict, IF IT HAS ONE, is refused by a check that can see it'; a check that refuses the no-conflict half is not what it licensed. (b) the same pair where the fact BINDS an op ('fact Desc[T = Leaf, describe = otherDescribe]') is a GENUINE conflict, and it reached the same wrong rendering - 'Leaf, Leaf' with 'TieRepair::ValueDirected' - which is the exact rendering WI-1012 gave the supplier tie its own variant to AVOID. FIX: dedup structurally-equal candidates in 'collect_provides_candidates'. Sound by construction - a Candidate is (impl_sort, resolved_head_bindings, impl_subst, head_specificity) and every downstream product (the resolved tree node, the subgoals 'requires_chain(impl_sort)' instantiates through 'impl_subst') is a function of exactly those, so two equal candidates resolve identically. NOT first-match: candidates differing in ANY field are all kept and 'pick_most_specific' still refuses among them. The op-binding leg is why (b) collapses too - the candidate loop 'continue's on any binding that is not a spec TYPE param, so a fact's 'describe = otherDescribe' differs in nothing Candidate records; deduping lets it reach the reader that CAN see the conflict, WI-1027's supplier tie, which names both texts by supply route. Corpus-inert: full suite green apart from the two fixed shapes. NOT DONE and deliberately not: a defensive dedup in 'render_instance_tie'. A second same-impl_sort tie shape was attempted (two provisions differing in whether they bind a second TYPE param) and it does NOT tie - tier-2 specificity picks the ground one - so the duplicate-name rendering has no remaining driver and an undriven dedup there would be untested code. Recorded at that site instead. REFERENCE: WI-1027; WI-859; WI-1012; WI-843; docs/design/058-implementation.md S15.
