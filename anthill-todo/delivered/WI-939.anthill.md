## description

May a namespace-level rule and a sort member share one short name? WI-935's handoff -- the question it removed the instance of rather than answered.

WI-935 asked it as its option (a) and then made it moot: 'anthill.geometry.vec_add/3' (a namespace rule) and 'anthill.geometry.Vec3.vec_add/2' (a sort member) were about to coexist, and finishing the WI-138 lift deleted the former instead of adjudicating the pair. The language question survives, unanswered and unowned.

THE MEASUREMENT THAT RAISED IT (WI-931, re-confirmed by WI-935's control perturbation). With both present, a rule body doing 'import anthill.geometry.{vec_add}' and calling the relational form went from ONE solution to ZERO, silently -- the bare name bound to the arity-2 sort member instead of the arity-3 namespace rule. The FULLY QUALIFIED name kept resolving both ways, so nothing was broken except which target the bare name reached, and no diagnostic was emitted. WI-935's control perturbation (re-adding the namespace rule beside the member) reproduces the coexistence and loads clean.

THE THREE OPTIONS, none of them today's behaviour:
 (a) RESOLVE BY ARITY -- the import binds per call site by argument count. Note this cannot be decided at the import: 'import ...{vec_add}' names a symbol, not an arity.
 (b) AMBIGUITY ERROR at the import or at the call -- the WI-907 shape ('an ambiguous dotted head ends the ladder'), applied to a bare imported name whose namespace and sort tiers both answer.
 (c) FORBID the coexistence at DECLARATION -- refuse a namespace-level name that a sort in the same namespace also declares. Loudest and earliest; would have refused the pre-WI-935 geometry outright.
Today it is none of these: it silently picks one.

RELATED, NOT THE SAME. A distinct duplication exists under ONE functor: a hand-written clause plus a body on the same operation. There the precedence IS defined (rules win -- design/abstract-interpreter-and-rules.md 3.3, and WI-935 drove it: adding a clause under Vec3.vec_add's functor stops WI-669's derived relational view). That doc already names its own follow-up -- "'both exist' should eventually be a loader warning (it is exactly the duplication WI-580 outlaws)". Whoever takes this ticket should decide whether the two warnings are one pass or two; they key on different things (short-name collision across tiers vs. same-functor rule-and-body).

FAMILY: WI-907 (ambiguity ends the ladder), WI-933 (a declaration that silently does nothing), WI-908/WI-914 (name ladders).

ACCEPTANCE: the rule is stated in docs/kernel-language.md and ENFORCED at one site, driven by a test that constructs the collision and asserts the chosen behaviour, plus a CONTROL that a non-colliding pair is unaffected. If the answer is (c), the refusal must name both declarations. cargo-test green.

SOURCE: WI-935 option (a), handed off on delivery.
