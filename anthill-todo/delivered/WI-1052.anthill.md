## description

`types_definitely_differ` CLAIMS A PROOF IT DOES NOT HAVE: A SORT ALIAS AND ITS EXPANSION READ AS 'DEFINITELY DIFFERENT', SO THE WI-346 SHADOW ADVISORY IS SILENTLY SUPPRESSED ON A GENUINE COLLISION.

WI-1048 gave the requires-shadow lint a two-sided contract: `types_definitely_differ` returning true is a PROOF the two types cannot be reconciled by any instantiation, and everything else is UNDECIDED (fail open, warn). `type_ctor_view` (typing.rs ~22440) implements the read as a head-constructor comparison and does NOT resolve sort aliases, so `IntList` and `List[T = Int64]` compare as different constructors. That is a FALSE PROOF, and it fails CLOSED — the warning the lint exists to emit is dropped.

MEASURED, with a control (found by /code-review during WI-1049):

    sort IntList = List[T = Int64]
    sort ASpec    sort T = ?   operation a_op(x: T) -> List[T = Int64]  end
    sort AReq     requires ASpec[T = ACar]
                  operation a_op(x: ACar) -> IntList = ?   end

  * `anthill check` prints NO shadow warning.
  * CONTROL: spell the return type `List[T = Int64]` instead of `IntList` — semantically the same type — and the warning appears:
    'operation `a_op` in `probe.alias.AReq` shadows the inherited …'.
So the verdict turns on the SPELLING of a type, which is the property WI-1048 was built to stop turning on (its whole subject is that a name match alone must not decide).

THE SHAPE OF THE FIX, and the two traps in it. `resolve_sort_alias` (typing.rs ~30884, `&KnowledgeBase`, O(1) off the WI-659 index) already answers 'what does this name expand to', and is used a few lines away in `type_param_sym_of_binding` — so the ingredient is in reach and `type_ctor_view` has exactly ONE call site. Traps: (1) follow the alias only for the BARE-NAME spelling (`Ref`/`Ident`/nullary `Fn`) — an alias head carrying arguments would lose them if the expansion simply replaced the term, and undecided is the safe answer there; (2) bound the chain (alias-to-alias) and say what the bound is, rather than recursing on user input.

WHY IT IS NOT INLINE WITH WI-1049. Relaxing a 'definitely differs' proof makes `requires_shadow_is_confusable` say yes MORE often, so this ADDS warnings — and whether the corpus grows any is unmeasured. If it does, each new warning is a design question about that pair (the FiniteCollection/Iterable family is exactly where WI-1048 had to stop the lint firing), not a mechanical fix. Measure the corpus delta FIRST and report it; a silent warning storm is as bad as the silent suppression.

ACCEPTANCE: the fixture above warns, and the control spelling still warns identically — one test, both spellings, asserting the SAME diagnostic (the WI-979 idiom: the two fixtures differ only in how the type is written, and that is the whole experiment); `wi1048_requires_shadow_refinement_test`'s two `*_is_silent` tests still pass — that is the control that this did not simply un-do WI-1048; the corpus warning delta is stated in the delivery (zero, or each new warning named and justified); each test says which case fails when the change is backed out. cargo-test green via rustland/scripts/test.sh. REFERENCE: WI-1048 (the contract and the predicate); WI-346 (the lint); WI-659 (the alias index); WI-1049 (the review that found it).
