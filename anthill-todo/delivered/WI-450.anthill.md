## description

Typer/eval: make VALUE-DIRECTED dispatch resolve a spec op by UNIFYING THE SPEC APPLICATION against provisions (param-agnostic), exactly as the requires-dict path already does -- so a WITNESS SORT (`sort OptionMonad provides CpsMonad[F=Option]` + member impl ops, or first-order `sort TagCombiner provides Combiner[T=Tag]` + combine) resolves a spec op called directly on a carrier VALUE identically to a `fact CpsMonad[F=Option,...]`.

DISCOVERY (WI-431 (D) probe, 2026-06-13, decided w/ user): the "carrier" -- privileging ONE spec type-param as the dispatch key -- is an ARTIFACT of value-directed dispatch's "value -> its sort -> look up by sort_ref" mechanism, NOT a principle. The `requires` path is ALREADY param-agnostic: it unifies the whole spec application (`Combiner[T=Tag]` / `Iterable[C=List, Element=Int]`) against provisions, no privileged param -- which is exactly why it finds a witness and value-directed does not. Value-directed ALREADY computes the structured bindings (the typer binds `T:=Tag` from the args, increment 2) but THROWS THEM AWAY, collapsing to (carrier_sym=Tag, match sort_ref).

FIX: value-directed dispatch should KEEP the bindings and unify the spec application against provisions, dropping the sort_ref/carrier privilege. Witnesses then resolve with no "which param is the carrier" question. The two value-directed lookups that key on sort_ref==carrier_sym: find_spec_op_for_provided_sort (typing.rs ~2215), provider_spec_view_bindings (typing.rs ~8445).

SUB-PROBLEMS: (1) OP-LOCATION -- a `fact` stores the op in the provision bindings (`combine=tagCombine`); a witness stores it as a MEMBER of the witness sort (`TagCombiner.combine`), with no op in the provision; so value-directed op-resolution (instance_fact_op_binding, which reads bindings only) must also resolve in the PROVIDER's scope (sort_ref) -- the requires path already does this. (2) COHERENCE -- two witnesses for one application are a live ambiguity; extend the rule-2 check (provision_binds_any_op gates it to op-binding facts today) to witness provisions.

STRATEGY: dispatch-side param-agnostic unification -- NOT a load-time desugar. (Desugar would have to PICK a carrier to index the provision under, re-introducing the very privilege the param-agnostic model removes.)

OUT OF SCOPE (genuinely different shapes, NOT touched by the param-agnostic change): self-receiver specs (`Stream.splitFirst(s: Stream)` -- no type-param pinned by an arg; element comes from the provider fact = WI-357); result-determined params (`CpsMonad.pure(a: A) -> F[T=A]` -- `F` appears only in the result, so the args cannot pin it; it comes from the expected type = WI-383 HK fill).

HOT PATH (eq / List.member / Iterable.find+map -- WI-415/418/424) plus Stream (self-receiver) and Iterable (carrier = enclosing sort, a normal provider) MUST stay green -- heavy regression testing, not just the new witness tests. SUPERSEDES design path-dependent-types.md sec.5.4 rule 3 (reworded to the decided direction). Reuses WI-431's provision/coherence machinery (depends WI-431). Est. ~2-4 reviewable commits.
