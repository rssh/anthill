## Description

A bodied operation reading an ENTITY FIELD panics the SLD->eval bridge when called in VALUE position from a rule body.

MEASURED (2026-08-02, while delivering WI-935), reproduced four ways -- with a free-standing entity AND a sort-declared one, with an entity-returning AND a scalar-returning body, with an inline-constructor argument AND a fact-bound one:

  sort Geo2
    operation padd(a: P, b: P) -> P = P(x: a.x + b.x, y: a.y + b.y)
  end
  rule val_form(?c) :- ?c = Geo2.padd(P(x: 1.0, y: 2.0), P(x: 10.0, y: 20.0))

  thread 'main' panicked at anthill-core/src/kb/resolve.rs:5870:
  bridge_op_to_eval: internal evaluator error bridging 'test.funrel2.Geo2.padd':
  internal evaluator error: field_access: receiver is not an entity (got Term)

WHERE. resolve.rs's bridge_op_to_eval carries a debug_assert!(!matches!(e, EvalError::Internal(_))) -- so a DEBUG/test build aborts and a RELEASE build residualizes SILENTLY (the arm returns None). Both halves are wrong: the assert says this is an evaluator-INVARIANT bug, and it is being reached from ordinary user source.

THE COMMENT AT THE SITE NAMES THE INTENDED BEHAVIOUR AND IT IS NOT HAPPENING: 'materializing each term/occurrence operand into the interpreter's native form (Value::Term(box(...)) / Value::Node -> Value::Entity), else a body that reads a field errors with "receiver is not an entity"'. materialize_value (eval/mod.rs:729) delegates Value::Term -> builtins::term_to_value, which is evidently NOT reconstructing a Value::Entity for an entity-constructor term. ROOT CAUSE NOT ESTABLISHED -- term_to_value was not read; do not take the preceding sentence as a diagnosis.

WHAT WORKS, for contrast (so this is a bridge defect, not a body defect): the SAME operations called through the interpreter with a Value::Entity argument evaluate correctly -- vec3_ops_test::the_four_members_evaluate drives anthill.geometry.Vec3.vec_add/vec_sub/vec_scale/vec_zero and asserts (11,22,33) / (-9,-18,-27) / (2,4,6) / (0,0,0). So the bodies are fine; what fails is the SLD-side entry.

WHY IT MATTERS MORE AFTER WI-935. Vec3 now carries four such operations, and '?c = vec_add(?a, ?b)' from a rule body is the natural way to use them. That call is this bug. WI-935 shipped anyway because its own surface (interpreter calls + the WI-669 derived relational view for the SMT tier) does not go through this path, but the gap is real and user-visible.

ACCEPTANCE: a rule body calling a bodied op whose body reads an entity field either EVALUATES (preferred) or reports a located, user-facing diagnostic -- never a debug_assert abort and never a silent release-mode residual. Driven by a test that resolves the goal and asserts the bound value; a CONTROL that the same op still answers via the interpreter. cargo-test green.

SOURCE: measured while delivering WI-935.

### 2026-08-02T18:58:26Z — feedback — user

DELIVERED with WI-935 (commit 1a8435dd). ROOT CAUSE was NOT what this ticket guessed. The ticket said the comment at the site names the intended behaviour and pointed at materialize_value -> term_to_value, with the explicit caveat 'ROOT CAUSE NOT ESTABLISHED -- term_to_value was not read'. Reading it settled it, and the defect is one predicate call:

  term_to_value asked kb.constructor_parent_sort(functor), whose body is
    self.entity_parent.get(&functor).copied().filter(|&p| p != functor)

The .filter is the STRICT (irreflexive) view -- correct for a walker CLIMBING to a parent, and the wrong question here. term_to_value is asking 'is this an entity constructor'. For an EPONYMOUS constructor entity_parent[Vec3] == Vec3, so the filter drops it, the answer is None, and the value stays Value::Term -- whereupon a body reading a.x reports 'field_access: receiver is not an entity (got Term)'.

FIX: use sort_of_constructor, the TOTAL (reflexive) view. Its own doc already says which to use -- 'Prefer this wherever the question is "which sort does this belong to". constructor_parent_sort is the STRICT (irreflexive) view, for walkers that climb the chain.' One line, two call sites (TryFn and TryRef).

BLAST RADIUS WIDER THAN THE TICKET: this affected EVERY 6.3 free-standing / eponymous entity reaching the SLD->eval bridge, not just Vec3 -- reproduced with a free-standing entity AND a sort-declared eponymous one, entity-returning AND scalar-returning bodies, inline-constructor AND fact-bound args. Same WI-926 family as WI-928 / WI-931 / WI-940: a predicate that silently reads an eponymous name as 'not the thing'.

DRIVEN: vec3_ops_test::the_imported_short_name_answers_through_the_derived_view and every_member_answers_relationally resolve goals whose bodies read a.x / b.x and assert the BOUND VALUE. CONTROL: the_four_members_evaluate calls the interpreter directly and passes either way BY DESIGN, which is why it is kept separate -- it isolates the bridge from the bodies. Full workspace green.
