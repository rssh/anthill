## Description

Value facts: make the KB fact-store + discrimination-tree + resolver matching carrier-agnostic over TermView, so a fact can carry Value::Node (denoted/occurrence) subterms. Driving consumer: OperationInfo must be SLD-queryable (reflect introspection API: operations(...), :- OperationInfo(name: ?n)) AND it carries denoted (effects Modify[c], eventually params/return) — so it must be a queryable, Node-carrying fact = a value fact. End state: one carrier-agnostic OperationInfo fact (queryable + Node-carrying), with op_effects/op_bodies collapsing BACK into the fact (no Rust-side record — a record isn't queryable). Most substrate already carrier-agnostic (WI-246 rule-body occurrences, Substitution bind_value, TermView query_view/match_view, Frame.goals: Vec<Value>, 24/29 builtins). Load-bearing work = Phase A: rewrite discrimination-tree insert/remove to walk TermView instead of TermStore/TermId. The tree uses NO hash-consing (keys are purely structural DiscrimKeys; no TermId is a key/leaf/compare), so a Node decomposes into the same keys via TermView and is structurally indexed like a term — no hash-cons semantics to preserve; Node-as-wildcard is an optional fallback. Then Phase B value-fact storage (assert_fact_value, carrier-agnostic RuleEntry.head; the only genuine hash-cons reliance is fact_dedup, keyed on TermIds -> skip-for-Node = dedup-miss not unsound; plus a by_sort/by_domain key decision), C De Bruijn for value rule heads, D 5 remaining builtins, E boundary reify points. Full scope + worked example (effects Vec<TermId> couldn't hold Modify[c]) + why the Rust-record is the wrong fix: docs/design/value-facts-carrier-agnostic-resolver.md
