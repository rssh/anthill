## Description

Implement proposal 053 external-store fact monotonicity + the 007 §2 trait/policy capability model (follow-on to WI-666, which delivered the in-memory substrate + runtime guard). DESIGN converged 2026-07-08 (with user): store capability is TWO kinds — PROVISION (a trait carrying an operation) and POLICY (a per-predicate predicate over universal ops). `retract` is not universal, so it becomes a TRAIT op; write policy governs the universal persist/retract, so it is the monotonicity predicate. No caps/StoreCaps (never built; the wrong shape — a marker value for an operation-bearing capability), no monotonicity<=capability bound (it falls out of the type structure). STDLIB (stdlib/anthill/persistence/store.anthill): (1) ADD to `sort Store` the policy query `operation monotonicity(store: Store, functor: Symbol) -> Monotonicity` — every store answers, per functor, its write policy; a QUERY the system reads to plan (persist available iff != constant, retract iff non_monotone), NEVER by attempting a write and catching failure. (2) MOVE `retract` OUT of base `Store` into a NEW trait `sort NonMonotonicStore { fact Store  operation retract(store: NonMonotonicStore, id: FactId) -> Bool effects {Modify[store], Error} }` — retract joins retrieve (QueryableStore) / pull (BulkStore) as a trait op; an append-only backend simply does not provide NonMonotonicStore and has no retract at all. QueryableStore/BulkStore unchanged. Consistency is STRUCTURAL: a store without NonMonotonicStore has no retract, so its monotonicity answers are monotone/constant only — non_monotone IMPLIES the trait (this is the dropped monotonicity<=capability bound, now from the type structure; a load-time coherence check is optional). RUST (coordinated — why this is NOT a standalone stdlib edit): (a) split the persistence `Store` trait (rustland/anthill-core/src/persistence/mod.rs) so `retract` lives on the NonMonotonicStore side (or is gated), and retract-capable backends (FileStore, IndexedFileStore) declare `fact NonMonotonicStore`; (b) retarget the eval `persistence_retract` builtin (registered/dispatched as `anthill.persistence.Store.retract`, rustland/anthill-core/src/eval/builtins.rs) and WI-666's guard error-paths to `anthill.persistence.NonMonotonicStore.retract`; (c) give each store a `Store.monotonicity(store, functor)` answer (a builtin or reflect-rule contribution) and WIRE it under the reflect `fact_monotonicity(functor)` FACADE WI-666's guard already reads — for an external-store functor `fact_monotonicity(functor)` resolves via 007 routing (route(functor) -> Store) to that store's `monotonicity`; for an in-memory functor, by reflect rules. IMPL choice (open): MATERIALIZE each store's monotonicity into the reflect predicate at store registration (guard unchanged, cheapest — recommended) vs ROUTE live per query (reflects live backend state). CALLERS to migrate off base-Store.retract: the todo store (rustland/anthill-todo/anthill/store.anthill forget_buffer/untag_item — its IndexedFileStore backend declares fact NonMonotonicStore) and any other retract caller; WI-666 tests + the anthill-todo suite must stay green. ACCEPTANCE: (1) `Store.monotonicity(store, functor)` queryable per functor, read WITHOUT attempting a write. (2) `retract` is a NonMonotonicStore-trait op — a store not providing NonMonotonicStore has no retract (structural); `fact_monotonicity(functor)` for an external functor resolves to the owning store's monotonicity (a synthetic store-backed functor resolves to the store's policy, not the in-memory monotone default). (3) a backend that cannot honor a declared non_monotone retract fails LOUD via the Error effect at the write, not a static load check. (4) 007 §2 (trait/policy model) is the spec; full suite green; a synthetic test per (1)/(2)/(3). deps WI-666; sibling of WI-665 (Rust KB cache invalidation keyed off the same monotonicity).
