## description

RUSTLAND: AN AMBIGUOUS `requires` BASE IS READ AS A MISS, AND THE ABSOLUTE RUNG THEN WIRES A SORT NOBODY SELECTED. `ImportPass::at_item`'s `RequiresDecl` arm does `resolve_name_to_scope(kb, name, scope).or_else(|| find_scope_by_name(kb, name))`, and `resolve_name_to_scope` collapses `ResolveResult::Ambiguous` to `None` (`_ => None`). So an ambiguity falls through to the absolute rung instead of ending the ladder — §8.6 says an ambiguity ENDS it, and `ResolveResult::or_else` (`intern.rs`) exists to spell exactly that; its own doc names a site that "re-derived it WRONG (silently standing an ambiguity down as if it were a miss)" as the whole point of WI-917. This site re-derives it, in that direction. DRIVEN, not inferred — fixture: a top-level `sort Rival { operation zap }`, plus `pa.Rival { operation aaa }` and `pb.Rival { operation bbb }`, plus `namespace pc { import pa.*; import pb.*; sort User { requires Rival } }`. Measured from `User`'s scope: `resolve_in_scope("Rival")` = `Ambiguous(["Rival", "pa.Rival", "pb.Rival"])`; `resolve_in_scope("zap")` = `Found(Rival.zap)`; `resolve_in_scope("aaa")` = `NotFound`. The top-level homonym's member is reachable and neither actual candidate's is — the absolute rung wired the one sort nobody named. CORRECTION TO THE OBVIOUS FRAMING, and this is why the ticket is not "a silent phantom parent": the load DOES fail, with `18:14: ambiguous symbol 'Rival' in scope 'User'`. What is silent is the WIRING and its ORDERING. The reporter is `Loader::push_ambiguous_symbol` — the LOAD phase. The wiring is `scan_definitions` sub-pass 2, which runs first, and the loader accumulates errors and continues by design ("one bad declaration must not hide the rest of the file's diagnostics"). So between the two, sub-pass 3's rule-head registration and the entire load phase resolve every name in `User` against a scope with an unrelated sort spliced in: one bad declaration corrupts the scope used to diagnose everything else in it. The parent link also persists in the symbol table across `load_incremental` re-scans. WORK: route this ladder through `ResolveResult::or_else` so the ambiguity stands the absolute rung down, as every other ladder in the tree does. ACCEPTANCE — TWO ROWS, and the second is load-bearing: (1) the fixture above, asserting that with the ambiguity present NO parent is wired (`zap` is `NotFound` from `User`); (2) THE CONTROL — an UNAMBIGUOUS `requires` whose base resolves only by qualified/absolute name must still wire its parent. Without row 2 a "fix" that merely deletes the `.or_else(find_scope_by_name)` fallback passes row 1 and silently kills every absolute-rung `requires`. Say at the site which test fails when the change is backed out. Note the sibling spelling `match { Found(s) => Some(s), _ => None }` is hand-written at four sites in `load.rs`; `ResolveResult` has `denotes()` and `or_else()` but no `found() -> Option<Symbol>`, which is why the collapse keeps being re-derived. Found by code review of WI-1028. REFERENCE: WI-917; WI-1028; kernel-language.md §8.6.
