## Description

A RULE-INTRODUCED FUNCTOR IS NOT SORT-SCOPED — it is one BARE GLOBAL NAME, so two sorts defining the same short name silently share one definition and the loser's own laws are ignored INSIDE ITS OWN SORT. Silent wrong answer on a program that LOADS CLEAN, which is the worst category. Found by the user while reviewing WI-887.
MEASURED, one file, two sorts, the second deliberately INVERTED so a collision is visible rather than inferred:
  sort A  rule pick(true, ?t, ?_) = ?t [simp]  /  rule pick(false, ?_, ?e) = ?e [simp]
          operation drive(n: Int64) -> Int64 = pick(true, 10, 20)   -> 10  (correct)
  sort B  rule pick(true, ?_, ?e) = ?e [simp]  /  rule pick(false, ?t, ?_) = ?t [simp]
          operation drive(n: Int64) -> Int64 = pick(true, 10, 20)   -> 10  (WRONG; B's own laws say 20)
Loads clean, no diagnostic. A's definition wins for BOTH sorts. Sort B cannot use its own rules.
THE MECHANISM: a `[simp]` rule head introduces a FUNCTOR, not a namespace-qualified operation symbol. The symbol stays `SymbolDef::Unresolved`, and `qualified_name_of` (kb/mod.rs:1444) returns the RAW SHORT NAME for an unresolved symbol — so `pick` in sort A and `pick` in sort B are literally the same interned name. Contrast a DECLARED operation, which is qualified: `anthill.prelude.Bool.and`. So the two kinds of member a sort can introduce are scoped OPPOSITELY, and only one of them says so.
THE SECOND HALF, AND WHY THIS IS NOT A ONE-LINE FIX: there is today NO WAY TO IMPORT A RULE-INTRODUCED FUNCTOR. WI-887 measured that `import anthill.prelude.Bool.{ite}` is `unresolved import` once `ite` stops being a declared operation — an import names an operation or a sort, never an equation's LHS head. The stdlib RELIES on the current bare-global behaviour: `ordered.anthill` and `int64.anthill` write bare `ite(...)` in laws and it reaches `bool.anthill`'s `[simp]` rules only because the name is global. So SCOPING ALONE WOULD BREAK THE STDLIB. Both halves are needed together: a scope for a rule-introduced functor, and a way to name one from another sort or file.
WHY IT MATTERS BEYOND THE TOY: WI-887 makes `anthill.prelude.Bool.ite` exactly such a functor, so the PRELUDE now claims the unqualified global name `ite`, and any user writing their own `ite` rules collides with it silently. It is also why `anthill-smt-gen`'s `is_ite_op` (lib.rs) can only match the bare `"ite"` — there is nothing more specific to match, and WI-680 already recorded that short-name matching can reinterpret a same-named user op. That hazard is now unavoidable rather than incidental.
ACCEPTANCE: the two-sort program above is either CORRECT (each sort uses its own rules) or REFUSED at load naming both definitions — not silently merged; whichever is chosen, a test drives the INVERTED pair so a merge cannot pass; the stdlib's existing cross-file bare `ite` uses keep working, with the naming path they use stated explicitly (if scoping lands, say how `ordered.anthill` reaches `bool.anthill`'s rules); the answer says whether a rule-introduced functor is scoped to its SORT, its NAMESPACE, or its FILE, and why; full workspace green via rustland/scripts/test.sh. CONSIDER: whether the two kinds of sort member should be scoped alike at all, or whether a rule functor is deliberately global and the real fix is refusing a DUPLICATE definition loudly. REFERENCE: WI-887 (which made `ite` such a functor, and measured that the member import does not resolve), WI-680 (the short-name matching hazard in smt-gen), WI-893 (the other silent `[simp]` defect found in the same review).

### 2026-07-31T09:47:02Z — feedback — user

DECISION (user): "rule should not travel to the global namespace from its places." So the answer to this ticket's open question is SCOPED, not global — a rule-introduced functor stays where it is declared, and the alternative this ticket floated (leave it global and merely refuse a duplicate loudly) is REJECTED. A duplicate is not the disease; the travel is.
WHAT THAT MAKES MANDATORY, and it is the half this ticket already flagged as the reason it is not a one-liner: there is TODAY NO WAY TO NAME A RULE-INTRODUCED FUNCTOR FROM ELSEWHERE. `import anthill.prelude.Bool.{ite}` is `unresolved import` — an import names an operation or a sort, never an equation's LHS head (MEASURED under WI-887). So scoping without an import path does not tighten the language, it breaks it. Both halves land together or neither does.
THE STDLIB IS ALREADY A CONSUMER OF THE BEHAVIOUR BEING REMOVED, which sets this ticket's real scope: `ordered.anthill` (`max`/`min` laws) and `int64.anthill` (`sign` law) write BARE `ite(...)` and reach `bool.anthill`'s `[simp]` rules ONLY because the name is global today. Under the decision they must reach it by an explicit path instead. Those two files are the acceptance case — if they still load and their laws still connect after scoping, the import path works.
AND IT BITES WHAT WI-887 JUST SHIPPED, recorded here rather than discovered later: WI-887 deleted the `ite` OPERATION, so `ite` is now exactly a rule-introduced functor, and the arrangement RESTS ON THE TRAVEL. `bool.anthill` defines it, three other files use it, and nothing but globality connects them. That is not an argument to undo WI-887 — its own reason stands and is independent (an operation at `ite`'s signature evaluates both branches, so no operation is the only correct form) — but it does mean this ticket must carry `ite` as its worked example, and that WI-887's state is provisional until this lands.
