## description

A MULTI-BINDER LAMBDA'S PARAMETER ANNOTATIONS ARE NEVER CHECKED against the callback parameter slot, so a contradicting annotation loads clean. MEASURED on the WI-793 delivery branch, with the boundary bisected -- the discriminator is BINDER COUNT and nothing else:

  (1) THE DEFECT, LOADS CLEAN:
      operation apply2(f: (a: Int64, b: Int64) -> Int64) -> Int64 = f(1, 2)
      operation drive() -> Int64 = apply2(lambda (a: Int64, b: String) -> a)
      Annotating BOTH binders wrong (`lambda (a: String, b: String) -> 1`) also loads clean.

  (2) THE ONE-BINDER CONTROL, REJECTED:
      operation apply1(f: (a: Int64) -> Int64) -> Int64 = f(1)
      operation drive() -> Int64 = apply1(lambda (a: String) -> 1)
      "5:32: type mismatch in apply1.f (op-arg): expected Int64 -> Int64, got String -> Int64"

NO OTHER FACTOR IS INVOLVED -- each of these was measured, not assumed. It is NOT about projections: (1) has none, and a projection-bearing ONE-binder callback (`f: (x: xs.T) -> Acc`) with a contradicting annotation IS rejected. It is NOT about a decoupled effect row: the same one-binder contradiction is rejected both with `@ {EffP}` and with a closed `@ {}` row. It is NOT about an unbound accumulator type param: a one-binder callback with `Acc` in the slot is rejected (`expected Int64 -> ?Acc, got String -> Int64`). Adding a SECOND binder to any of those refused shapes makes it load clean.

WHY IT MATTERS: the annotation is the user's explicit statement of intent, and at arity 2+ it is inert -- silently accepted and then ignored, which is worse than being rejected. The multi-binder lambda is the common callback shape (every fold), so this is the arity most callbacks actually use. Note the VALUE is still typed correctly from the context (kernel-language.md 4.7: the context type wins over the annotation), so this is a missing DIAGNOSTIC on a contradiction, not a wrong runtime value -- which is exactly why it stayed invisible.

LIKELY LOCUS, not verified: the whole-arrow conformance check at the argument position compares the lambda's synthesized arrow against the declared param type. At arity 1 the two arrows compare component-wise and the mismatch surfaces. At arity 2+ the written binder types apparently do not reach that comparison -- WI-791 made arity a ground sibling of the param slot and WI-782 aligned a ParamList positionally, so the reader that builds a MULTI-binder lambda's arrow from its ANNOTATIONS is the thing to look at first.

RELATION TO WI-793: found while measuring WI-793's acceptance line 'an annotated binder that CONTRADICTS the element type is still rejected'. That line turned out to describe behaviour that never existed, and WI-793's mechanism (resolving a path-dependent element type) cannot deliver it -- the defect reproduces with no projection, no literal receiver and no path-dependent type anywhere. WI-793 delivered the one-binder half of that acceptance line (`a_contradicting_binder_annotation_is_rejected`) and this ticket owns the rest.

ACCEPTANCE: a multi-binder lambda whose binder annotation contradicts the corresponding callback parameter slot is REJECTED AT LOAD with a located diagnostic naming the binder and both types; case (1) above is refused and case (2) keeps its current diagnostic; a lambda whose annotations AGREE still loads and evaluates; an UNANNOTATED multi-binder lambda is unaffected (its binders are typed from the slot, which is the normal path); full workspace green via scripts/test.sh.
