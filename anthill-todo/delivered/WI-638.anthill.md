## description

Named-tuple component field access (t.x): a dot projection t.x where t types as a named tuple ((x: A, y: B), TypeExtractor.NamedTuple) does NOT resolve today — verified it errors with no-such-member (dot dispatch) on BOTH a tuple literal ((x:10, y:20).x) and a statically-typed param (t: (x: Int64, y: Int64)). kernel-language.md 6.7 dot-projection has only two dispatch modes: (1) entity-constructor fields, (2) sort components; a named tuple is neither — its functor is TupleLiteral whose entity_field_types is empty Some([]), and the component names live in the named-args of the value plus the TypeExtractor.NamedTuple type, which the field resolver never consults. Adjacent DELIVERED WIs do not cover this: WI-013 (field access in expression bodies, entity/sort), WI-262 (TYPE-level projection Modify[c.field], explicitly out-of-scope for term-level field access), WI-490 (free-standing-entity field access via field_constructors_of_sort). FIX: add a THIRD dispatch mode — when the receiver synthesized type is a TypeExtractor.NamedTuple, resolve .field against its element names. TOUCH-POINTS: typer field resolution — resolve_field_type (typing.rs ~11565) and the DotApply field-fallback (typing.rs ~3565): add a NamedTuple arm reading the element (name,type) list, typing the access at the field type; eval field_access — read Value::Tuple.named by field name (the named_arg lookup in term_view already does this). Also support positional projection t._1 / t._2 since positional tuples desugar to _N names. DRIVER: proposal 052 (Relations as first-class values, docs/proposals/052) — its relational-algebra lambda surface reads columns as row.x; without this it falls back to tuple destructuring, awkward for a two-row join. ACCEPTANCE: (x:10, y:20).x evaluates to 10 and .y to 20; t.x on a param typed (x: Int64, y: Int64) type-checks and evaluates; positional ._1 works; existing entity/sort field access unaffected; cargo test green with a test paralleling the diagnostic probe in tests/include/tuple_order_test.rs.
