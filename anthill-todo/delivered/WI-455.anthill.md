## Description

Typer/eval: route the OpRef / spec-op REDISPATCH through the run() trampoline so host call depth stays O(1). After the WI-179 iterative-eval transform the value-cascade is trampolined (StepOutcome::Deliver), but dispatch_call_with_requirements_inner's OpRef arm (eval.rs ~1042/1047) and the spec-op-by-value redispatch still tail-call dispatch_call_with_requirements NATIVELY (do NOT return to run() between hops), so a pathological eta-chain recurses on the host Rust stack and can overflow before step_cap ticks. Narrow edge (eta-chains are 1 hop), documented in-code. FIX: add StepOutcome::Dispatch{target,args,requirements,type_args} re-entered by run() (like Deliver) and have the redispatch RETURN it instead of native-tail-calling. Acceptance: cargo-test green; a synthetic deep eta-chain surfaces StepsExhausted (named) not a native overflow. Rust-only (eval).

## Changes

### 2026-07-12T20:09:48Z — feedback — user

ACCEPTANCE SUPERSEDED. The filed acceptance -- 'a synthetic deep eta-chain surfaces StepsExhausted (named) not a native overflow' -- is NOT met as written, and cannot be: such a chain is no longer CONSTRUCTIBLE. The chain was never a legitimate feature that merely recursed too deep. It existed only because dispatch re-resolved an OpRef's already-resolved operation Symbol by SHORT NAME against the caller's locals (an OpRef hop pushes no frame, so those locals were still on top). A caller-local merely SHARING the callee op's name therefore hijacked the call -- dynamic scoping of a resolved reference. Its quiet form was a SILENT WRONG ANSWER, worse than the crash: apply_it(f, double) called as apply_it(double, triple) ran triple (3) where f denotes double (2). The cycle was just two such locals pointing at each other. Fixed at the root instead: dispatch split into dispatch_call_with_requirements_inner (a source-level NAME, which a local callable may shadow -- that is how f(x) on a local lambda works, and it stays) and dispatch_resolved_operation (an already-resolved Symbol, which no local may shadow; the OpRef arm goes here). An OpRef application now resolves in exactly ONE HOP BY CONSTRUCTION, so there is no chain to bound. StepOutcome::Dispatch was therefore NOT shipped: it was built and proven green first, then dropped -- it would bound a chain that can no longer occur, at the cost of a Box + trampoline round-trip on every HOF call. Note for 027.2/047, which cite this WI as the precedent for StepOutcome::Suspend: that precedent does not exist; introduce Suspend on its own merits. By-catch fixed: resolved dispatch skips the wrapper feeding the recent-dispatch ring, so OpRef-reached ops (i.e. every HOF call) went missing from StepsExhausted -- the one diagnostic this WI exists to protect. Same gap was already present on the WI-444 carrier-override and WI-350 spec-op-by-value arms; all now note the impl they actually run. Code 354356ce, pushed to main. Suite green on the rebased tree (73 binaries, 2754 passed), incl. upstream WI-700, which now mints OpRefs for NULLARY ops straight into the rewritten arm. Four tests, each verified to fail with its fix removed.
