## description

Implement proposal docs/proposals/053-fact-mutability.md "Per-Functor Fact Monotonicity" (committed c0c3e59c). Give the KB a per-functor write policy — a single value, NOT a store-level one (both the in-memory KB and any external store hold a MIX of functors). This delivers the LANGUAGE mechanism + the loud runtime guard; the Rust KB cache optimization behind the guarantee is WI-665 (out of scope here). No grammar change.

SCOPE / PHASES:

A. REFLECT SUBSTRATE (stdlib/anthill/reflect/reflect.anthill). Add `sort Monotonicity { entity constant  entity monotone  entity non_monotone }` and `operation fact_monotonicity(functor: Symbol) -> Monotonicity`, with a catch-all default `rule fact_monotonicity(?) = monotone` (append-only is the KB's add-friendly default). constant = no assert/no retract; monotone = assert only (append-only); non_monotone = assert + retract (retract/update). Exactly one value per functor. A project marks its retractable functors by rule, e.g. `rule fact_monotonicity(WorkItem) = non_monotone`.

B. RUNTIME GUARD (the load-bearing safety piece; rustland kb + eval). The KB's write paths consult fact_monotonicity outside loading: (1) `retract` of a functor whose monotonicity is not non_monotone -> LOUD error (this is the SOLE guard — retract is the non-monotone step that desyncs re-derived structure and falsifies caches); (2) `assert` of a `constant` functor -> loud error; assert is otherwise permitted (monotone default). Sites: KB.assert/retract (kb/mod.rs), the eval `Store` builtin assert/retract (eval/builtins.rs ~2225/2279), and Store.persist/retract on the persistence side. Static where the functor is known at load = LoadError naming it; dynamic otherwise = the Error effect (037). Per repo principle "loud error over silent skip." NOTE: the guard must key off the SAME monotonicity value the reflect predicate exposes (single source of truth), and must NOT fire during a load phase (loader legitimately establishes facts).

C. STORAGE INTEGRATION (stdlib/anthill/persistence/* ; 007/036 coherence). The owning store gives a functor's monotonicity: in-memory via the reflect rule (A); an EXTERNAL store via a `monotonicity` field added to its per-functor binding (007 §7 QueryBinding; §6 FileStore convention). A store's WRITE CAPABILITY (its ability to persist/retract, 007 §4) BOUNDS the value: `monotonicity <= capability` (non_monotone needs a retract-capable store; monotone a persist-capable one; constant none). Load-time consistency check, loud on a value exceeding capability (e.g. a non_monotone functor on an append-only sink). Capability propagates DOWN a store's backend stack (036 §"Modify[s] covers the backend reach", like Modify[s] -> s.backend) — distinct from the store<->its-many-functors relation. The in-memory default store has full capability and bounds nothing.

OUT OF SCOPE: the Rust KB cache work (build-once for constant/monotone, invalidate-on-retract for non_monotone; simp_gate_cache functor-specific fix) — that is WI-665, which DEPENDS ON this WI (it needs the monotonicity mechanism + guard to exist). No new grammar (Monotonicity/fact_monotonicity are ordinary reflect sorts/ops like StoreCaps/caps; the guard is runtime behavior; the storage field extends an existing binding).

ACCEPTANCE: (1) `fact_monotonicity(F)` queryable, default monotone; a project rule can set a functor non_monotone or constant. (2) retract of a non-non_monotone functor is a loud error; a functor marked non_monotone retracts cleanly; assert of a constant functor is a loud error; assert of a monotone functor succeeds. (3) an external store's per-functor binding carries monotonicity, and a value exceeding the store's write capability is a loud load-time inconsistency. (4) the loader still establishes all facts during a load phase without tripping the guard. (5) full suite green; a synthetic test per (2)/(3). MAY split into per-phase WIs (A substrate / B guard / C storage) if landing incrementally. Implements proposal 053; relates to 007/036/037; gates WI-665 (cache) and WI-660 (provides_index rework).
