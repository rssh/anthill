## description

anthill-todo backend, INCREMENT 2 of WI-437: ItemPerFileStore -- A NEW Store IMPLEMENTATION. Design: backend-github-coordination.md §4, §5, §5.1, §5.2, §8.3, §10; §14 row 2. Ships conflict-free multi-developer work on STATE CHANGES (the WI-437 driver: git conflicts in workitems.anthill). One directory per status, one file per item, holding EVERY fact about that item -- its WorkItem, its Feedback, its Tags, its MirrorEntry link. Two developers claiming two different items touch two different files; two claiming the SAME item get a rename/rename conflict, which is loud and correct because they genuinely disagree.

CORRECTED 2026-08-16 by the WI-1113 doc amendment. This ticket was filed from the pre-amendment doc and said "FileConvention::StateDirs alongside Flat/ByDomain/SingleFile" with "IndexedFileStore gains the relocation rule". BOTH ARE WRONG, and §5.2 now says why. IndexedFileStore exists entirely for one model -- many facts share a file, and a fact is addressed by its BYTE OFFSET within it; its fields are inner: FileStore, source_map: HashMap<RuleId, (PathBuf, Span)>, pending_span_retracts, by_id. File-per-item is the opposite model: one file IS one item, it is addressed by PATH, a state change RENAMES it, and a retract can mean deleting the file. None of the span machinery carries over. A "convention" that shares no mechanism with its siblings is a second store wearing the first one's name.

SO: write ItemPerFileStore as a SIBLING implementation of trait Store (anthill-core/src/persistence/mod.rs -- six methods: persist, retract, update, flush, owned_monotonicity, retrieve). It does NOT implement trait IndexedStore, because there are no spans to address. FileConvention is UNTOUCHED by this work: it keeps its own meaning, the filename policy of stores that append into shared files.

Work: (1) ItemPerFileStore in anthill-core persistence, parameterized {root, status_field, id_field, ref_field} so anthill-core stays domain-neutral and stage0's field names live in the CLI's configuration of it, not in the library. (2) Content-DRIVEN routing, where FileStore::fact_path is content-BLIND: a WorkItem goes to <status_dir>/<id>.anthill (the status field picks the directory), and Feedback/Tag/MirrorEntry go to the file of the item they name (an index lookup on the referencing field). (3) The §5.1 RELOCATION RULE, owned by THIS store: one flush holding a retract and a persist of the same primary key at differing paths executes as a file MOVE -- rename the source, rewrite the item's block in place, every other block in that file rides along untouched. That is what makes "moving an item moves its feedback" fall out of existing single-flush atomicity instead of needing a new spec operation. (4) Directory names DERIVED from the status functor's snake_case short name, via the same term_functor_name reflection status_short already uses -- there must be no second list of statuses anywhere, so a new WorkStatus variant cannot drift out of sync with the layout. (5) The anthill-side entity declaration in the persistence stdlib, plus a "provides ItemPerFileStore language rust" block and its Store trait facts, so a project can WRITE the binding at all. (6) HOST WIRING: the source-map seeding in anthill-todo/src/main.rs (store.record_source(rule_id, path, span)) is IndexedFileStore-specific -- spans into shared files -- so build_store grows a per-backend arm that associates PATHS instead, WITHOUT disturbing the existing one. (7) fsck plus the §10 load checks: the directory is an index and the fact is the truth, and that redundancy must be CHECKED, not assumed -- a crash between the two filesystem steps of a move leaves either a file whose directory disagrees with its status fact or an item present in two files. (8) Loader coverage (collect_anthill_files already recurses). Tests run against a NULL forge.

SELF-HOSTING (§14.1): the two stores COEXIST, and this repo's own tracker stays on IndexedFileStore through increment 5. Develop and test against a FIXTURE project via -d <tmpdir>, never the live tracker. The backend lands BEFORE any project declares it -- the host hard-refuses a declared store this build does not provide (WI-830), so declaring it early leaves the tracker unusable.

SCOPE ADDED 2026-08-16 by WI-1113, and it is a prerequisite inside this ticket rather than a separate one (the change is smaller than this note): `open_store` moves here from increment 1, together with the spec restructuring it needs. Design doc §8.2.1 carries the measurement.

WI-1113 attempted `open_store` and it does not load. The obstruction is structural. WI-402's existential is recognized by `detect_existential_carrier`, which looks for `-> C ensures Spec[C, ...]` with C in the spec application's FIRST POSITIONAL slot -- the carrier -- then rewrites the return type to the spec with that slot dropped, so the body must return a value whose sort PROVIDES the spec. That is the shape of the delivered KVStore fixture: `sort MemStore { provides KVStore[K = ..., V = ...] }`, carrier and members distinct.

WorkItemStore is not that shape. Its only parameter IS `State` (proposal 036 / WI-203), satisfaction is spelled `fact WorkItemStore[State = WIS]`, and WIS is the member value -- nothing provides the spec as a carrier. Measured, all three built and run:
  * `-> C ensures WorkItemStore[C]` -> "type mismatch in open_store.return: expected WorkItemStore, got WIS"
  * `-> C ensures WorkItemStore[State = C]` -> "unresolved name 'C'"; the NAMED form is not detected as an existential at all, only the first-positional one is
  * `FileBasedWorkitemStore.wis(...)` from namespace scope -> "expected known operation or arrow-typed variable, got unknown functor"

The third is independent of the existential and matters on its own: a namespace-level factory cannot construct an impl's state at all, so `open_store` would have to live INSIDE one impl -- where it can no longer select between impls, which was its point.

SO: to get the factory, WorkItemStore needs a carrier sort that `provides WorkItemStore[State = ...]` instead of a bare instance fact. That is a change to the store spec itself; it only pays for itself once a SECOND impl exists to select between, and this ticket is already opening store.anthill to add one. Do the restructuring here, then `open_store` on top of it.

WHY IT MATTERS BEYOND TIDINESS: the host currently hand-builds the impl's state value, interning `anthill.todo.store.FileBasedWorkitemStore.wis` and its `backend` / `id_counter` field names. That is the last place the host knows one backend's internals, beyond the single legitimate native step of mapping a declared store to a compiled backend. It is also the reason a second store cannot simply be declared and used.

TWO THINGS NOT TO CHASE HERE. (1) The counter seed stays host-side: the bundle has no `String -> Int64` to recover a number from an id like "WI-1042", so it cannot compute its own seed -- and under coordination the parameter disappears entirely (§8.3), `alloc_id` reading the forge registry instead of counting. (2) Selection is ALREADY solved and does not need `open_store`: `sort Main` declares `sort State = ?` with `requires WorkItemStore[State]`, and the host discharges it with a requirement dictionary. `open_store`'s value is removing the host's knowledge of the state SHAPE, not choosing an impl.

ALSO MEASURED, relevant to how carefully to write call sites here: a BARE spec-op call such as `stamp_format(s, ...)` still loads AND runs correctly even with no member import, because the operation is in scope through `requires WorkItemStore[State]`. WI-402's caveat -- that a bare call does not resolve through an existentially-typed receiver -- bites only once a receiver actually IS existential, which is what this ticket introduces. So the test that finally distinguishes `WorkItemStore.op(...)` from `op(...)` is one THIS ticket adds; before it, both spellings pass.

THE STORE KEEPS BLOCKS, NOT BYTE OFFSETS (design §5.2.1). An item file holds several rows, so a retract must still name one block inside a file, and the obvious answer -- the same (path, span) map with new routing -- breaks on the very feature this store exists for: a relocation rewrites the whole file at a new path, so every offset goes stale, and stale offsets do not error, they drop the wrong bytes. record_file consumes the host's spans to CUT the file into blocks and keeps none.

LANDMINES for whoever is next.
* A Store NEVER learns the RuleId of a row it writes: kb::extent::persist_mirrored calls mirror.persist BEFORE assert_fact. A runtime-appended block is unaddressable until the next load; retracting it is a loud refusal by design.
* Being a ROW and being ADDRESSABLE must be separately represented. After a relocation the item block is a row with a dead RuleId; one Option<RuleId> conflated that with a blank line, and 'no rows left, delete the file' then deletes the item mid-move.
* kb.make_name_term("a.b.C") interns the WHOLE DOTTED STRING as one unresolved symbol, so local_name_of gives back a.b.C. Use try_resolve_symbol + make_name_term_from_sym. The store now refuses a path segment containing a separator, which is what caught it.
* A retract captures its row's path when BUFFERED, so a satellite retracted in the same flush that moves its item names the OLD path.
