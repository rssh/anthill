## Description

A NAMED LOGICAL VARIABLE IN A RETURN ESCAPES WI-1063's SKOLEMIZATION — the headline exploit survives a two-character edit, for the second time.

WI-1063 made a return's unwritten slot EXISTENTIAL and opens it to a fresh rigid at
each call, refusing the laundering chain. Its delivery note records that "at a call
only an ANONYMOUS slot opens", justified by `LogicalStream.empty() -> LogicalStream[?A]`
writing a NAMED variable in a return on purpose. That exemption is a general escape
hatch. MEASURED on the delivered tree, one program per row, `takes_pure(s: Stream[T =
Int64, E = {}])` throughout:

  A  -> Stream[T = Int64]              (partial, slot omitted)   REFUSED  <- WI-1063
  B  -> Stream[T = Int64, E = ?E]      (NAMED row variable)      LOADS    <- THE HOLE
  C  -> Stream[T = Int64, E = ?]       (anonymous wildcard)      REFUSED
  D  -> List[T = ?A]                   (NAMED type variable)     REFUSED at the
                                                                 DECLARATION

Row B is row A with `E = ?E` written instead of omitted, and `{Error}` reaches a slot
declaring `E = {}` — the exact unsoundness WI-1063 exists to stop. This is the same
class as the hole WI-1063's own review found late ("`takes_pure(mk)` — the bare nullary
name, no parentheses — loading clean while `takes_pure(mk())` was refused"): the rule is
right and its coverage has a seam.

IT IS A DIVERGENCE FROM THE SPEC, NOT AN UNDOCUMENTED DESIGN DECISION — checked after
the fact, and it changes who carries the burden. kernel-language.md describes return
skolemization thoroughly (the polarity rule, body-packs/use-opens, freshness per
opening, the call as mint site, the rejected body-check alternative, the self-sort
exception) and NOWHERE exempts a named variable. Two passages bear on it and both point
the other way:

  * §"In a RETURN the quantifier flips to exists" enumerates FOUR spellings — a bare
    reference, a partial application, an explicit `?`, an operation type parameter —
    and calls the first three existential. A NAMED `?E` is not in the list at all.
  * §"Sort composition" states outright: "A sort binding can also be a logical variable
    (`?` or `?name`). This is used to express existential quantification over type
    parameters", the named form differing only in that it "binds across the term".

So per the spec `?name` IS existential; the name buys SHARING across occurrences, not
exemption from opening. The anonymous-only rule exists only in WI-1063's delivery note.
The spec now records the divergence at the site, with this ticket number.

ROW D IS THE INCONSISTENCY THAT SAYS WHICH WAY TO FIX IT. For a TYPE parameter the body
check already treats a named return variable as universally quantified and refuses the
declaration ("expected List[T = ?A], got List[T = Int64]"): the body cannot produce a
list good for EVERY element when it has an Int64 one. For an EFFECT ROW the same body
check does not fire, so B is caught by neither the body nor the call.

THE RULE TO TRY, and it separates every legitimate corpus use from the leak — and it is
what "binds across the term" already means, read at the signature: a named variable
occurring in BOTH a parameter and the return is BOUND BY THE SIGNATURE — the caller
instantiates it, it is ordinary parametric polymorphism, and nothing should open it. A
named variable occurring ONLY in the return has nothing to share with, is unbound, and
is exactly the existential the polarity rule describes. Measured against the corpus:

  mplus(a: LogicalStream[?A], b: LogicalStream[?A]) -> LogicalStream[?A]      BOUND, fine
  interleave(a: LogicalStream[T = ?A, E = ?E], b: …) -> LogicalStream[…]      BOUND, fine
  empty() -> LogicalStream[?A]                                                UNBOUND
  widenB(s: Stream[T = Int64, E = {Error}]) -> Stream[T = Int64, E = ?E]      UNBOUND  <- leak

So the only corpus case the rule would newly bite is `empty`, which is precisely the
declaration WI-1063 cited as its justification — and `empty` has two ways to say what it
means without an unbound return variable, BOTH MEASURED TO WORK:

  (1) an OPERATION TYPE PARAMETER — `empty[A]() -> List[T = A]`. Loads, serves two
      element types in one program, and when nothing pins it the diagnostic is already
      the right one: "expected a type for 'A', got unconstrained — use `mk[A = …](…)`".
      §5.6 says an operation type parameter in a return is the CALLER's to instantiate,
      which is the universal this position actually wants.
  (2) NOTHING + COVARIANCE — `empty() -> List[T = Nothing]`, leaning on the declared
      `fact Covariant(sort: List, param: T)`. Loads. The Scala answer; needs subtyping
      to do the work where (1) needs none.

WHY `List.empty` DOES NOT LEAK TODAY, which is worth knowing before touching anything:
it is a SELF-SORT member, so the bare `List` in its return is a self reference taking
this instance's parameter (WI-1061's self-sort exception), not a fresh existential. A
namespace-level `operation mk() -> List = nil()` fed to `want(l: List[T = Int64])` IS
refused ("got List[T = ?T]"). So the stdlib's `empty`s survive by two different escape
hatches — self-sort for `List`/`Set`/`Map`, named variable for `LogicalStream` — and
neither of them SAYS "for all".

A THIRD OPTION, the user's, and it is the one that says what is meant: SPELL THE
QUANTIFIER. The polarity rule infers ∀ in a parameter and ∃ in a return; an explicit
`forall`/`exists` in a type would let a return declare the universal `empty` wants
instead of relying on a hatch. Bigger than (1) or (2) — grammar plus typer — but it
retires the guessing that WI-1076 and this ticket are both instances of.

ACCEPTANCE: row B is REFUSED, at the call like row A (or at the declaration like row D
— say which and why); rows A, C, D keep their verdicts; `mplus`/`interleave`'s
signature-bound variables still load and
`wi1076_self_representing_spec_carrier_test::mplus_unifies_an_empty_stream_with_a_non_empty_one`
stays green; whichever spelling `empty` moves to is measured at all seven corpus tiers;
kernel-language §"In a RETURN the quantifier flips to ∃" states the bound-vs-unbound
rule; each test says which case fails when the change is backed out. cargo-test green
via rustland/scripts/test.sh.

REFERENCE: WI-1063 (the polarity rule, the call as mint site, and the ANONYMOUS-only
exemption this ticket questions), WI-1061 (parameter positions and the self-sort
exception that hides `List.empty`), WI-1059, WI-402 (the explicit `ensures` existential),
WI-401 (the escape gate), WI-1076/WI-1077 (the sibling "the language does not say it, so
the kernel guesses" cluster), kernel-language §"Expansion during unification" and §5.6.
