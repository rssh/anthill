## Description

Proposal 050 "operation call" modification rule + 025 §"Proof for operation contracts" — call-site operation contracts (requires/ensures) over Γ. A SIBLING consumer of WI-537 (the 050 substrate); NOT on WI-067's critical path (effect discharge rides branch conditions and Γ, not contracts) and therefore does NOT block WI-067 — filed because it is part of proposal 050 and the main thing that richly POPULATES Γ. At a call y = callee(args), build σ (callee params ↦ actual args, result ↦ y), then: (1) requires IS CHECKED — the callee's precondition σ(requires) must follow from Γ_in, discharged by the SAME resolver query (and, failing the trivial flow, the same in-body-proof fallback) used for a guarded effect; an undischarged precondition is an obligation/error, never a silent pass. (2) ensures IS ASSUMED — Γ_out = Γ_in ∪ { σ(ensures) }: the callee's postcondition (result ↦ y) becomes a known fact for the code after the call. This is how contract knowledge flows: an op that "ensures neq(result,0)" lets a later div(_, y) refute its eq(y,0) guard straight from Γ with no branch test written; ensures facts are in practice the main populator of Γ beyond branch conditions and bindings. Plus 025 §"Proof for operation contracts": a proof targeting the implicit contract rule via the <operation>.<clause> naming convention (e.g. push.ensures). DISTINCT FROM WI-347 (DELIVERED), which checks OVERRIDE refinement (a providing sort's op vs the spec op — precondition no stronger, postcondition no weaker); THIS is CALL-SITE checking, which is unimplemented — op requires_clause/ensures_clause exist in the IR (OperationInfo.requires/ensures) but are unused across stdlib/examples and never checked at a call. Depends on WI-537 (needs Γ + the resolver bridge). Acceptance: cargo-test green; a test shows a callee's requires checked against Γ at a call site (error when undischarged, pass when Γ entails it) and its ensures available as a Γ fact after the call.
