## description

A type-directed list-literal desugaring is LOAD-ORDER SENSITIVE and fails SILENTLY.

MEASURED (WI-934, examples/sql-store/). A list literal in a field whose declared type is List[T = X] desugars to a cons(head:, tail:) spine, so a rule can destructure it. Whether that desugaring happens depends on the order the files were handed to the loader, and the losing order LOADS CLEAN.

Driven, same two files, same KB helper (try_load_kb_with_files), only the order swapped:
  sql.anthill then demo.anthill -> account_column_type answers 1 solution ("text")
  demo.anthill then sql.anthill -> account_column_type answers 0 solutions
Neither order produces a parse error, a load error, or any diagnostic. sql.anthill declares 'entity QueryBinding(... columns: List[T = ColumnDef] ...)'; demo.anthill asserts a QueryBinding fact whose columns argument is a '[a, b, c]' literal and a rule matching 'cons(head: ColumnDef(...), tail: ?)' against it.

WHY IT IS SURPRISING. scan_definitions is documented as 4-pass precisely so cross-file order does not matter -- pass 1 defines every name across every file before any pass 2 runs, which is what makes cross-file mutual recursion work (WI-321, wi321_cross_file_mutual_recursion_test). Field TYPES ought to be knowable regardless of order by the time a fact body is converted. Something in the literal-desugaring path reads the declared field type from state that is only populated once the DECLARING file has been loaded, not merely scanned.

WHY IT IS QUIET, and this is the part that makes it dangerous. Sibling rules that bind the same field to a bare variable ('columns: ?cols') are UNAFFECTED and keep answering, so a suite that reads the list as a whole stays green while the rule that walks the spine goes to zero. In the losing order the literal stays a flat n-ary node (measured separately: the same literal in an UNTYPED fact argument is always a flat node, which is the same representation), so the cons pattern simply matches nothing.

WHAT TO DECIDE:
 (a) Make the desugaring order-independent -- read the declared field type from the pass-1 definition table rather than from loaded state, so both orders produce the spine. This is the fix that matches WI-321's contract.
 (b) If (a) is not reachable, make the loss LOUD: a list literal in a position whose declared type is a List[T = X] that is not yet known must be an error naming the file that declares the field, not a silent flat node. The project's stated direction is a loud error over a silent skip.

BLAST RADIUS TO MEASURE FIRST: how many .anthill sites across stdlib/, examples/, anthill-todo/ and the test corpus put a list literal in a List-typed field of an entity declared in a DIFFERENT file, and how many of those are destructured by a cons pattern anywhere. Only the destructured ones can be silently wrong today; the rest are latent.

WORKAROUND IN PLACE: rustland/anthill-core/tests/sql_store_example_test.rs pins the order with an EXAMPLE_FILES constant reconciled against the directory (the anthill::stdlib::SOURCES + stdlib_drift_test shape). That is a local fix for one example, not a fix for the language.

ACCEPTANCE: both load orders of the two examples/sql-store/ files produce the same answers, DRIVEN (resolve the goal, assert the solution), or the losing order is refused with a located diagnostic naming the field and its declaring file; a test drives BOTH orders so they cannot silently diverge again; cargo-test green via rustland/scripts/test.sh.

SOURCE: measured while delivering WI-934 (2026-08-02), by an alphabetical directory walk that broke the example and loaded clean.

WHERE 'expected' COMES FROM. self.kb.entity_field_types(new_functor) (load.rs ~8874 / ~8911 / ~9068). That registry is written by register_entity_field_types (load.rs ~13727) while LOADING the file that declares the entity.

SO THE ORDER DEPENDENCE IS DIRECT: converting demo.anthill's fact argument reads entity_field_types(QueryBinding). If sql.anthill was loaded first the entry is there, expected is List-shaped, and the literal becomes a spine. If demo.anthill is converted first the entry is absent, expected is None, and the literal stays a ListLiteral — which is the SAME representation an untyped argument gets, and is exactly what was measured independently.

WHY THIS IS A GAP AND NOT THE DOCUMENTED ORDER-SENSITIVITY. scan_definitions is 4-pass precisely so cross-file order does not matter (WI-321, wi321_cross_file_mutual_recursion_test): pass 1 defines every NAME across every file before any pass 2 runs. But entity_field_types is a LOAD-time registry, not a scan-time one, so this type-directed decision sits outside that guarantee. The separate documented order-sensitivity in anthill-stl/src/stdlib.rs is about 'provides' dispatch hijacking — a different mechanism, and not this.
