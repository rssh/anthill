BUG (typing; WI-1056 residue, DRIVEN end-to-end and PRE-EXISTING): an UNWRITTEN sort parameter is FLEXIBLE inside the operation body, where it must be RIGID. It is fresh at each call -- 's: Stream[T = Int64]' is 's: Stream[T = Int64, E = ?]' and '?' is a NEW variable per instantiation -- so the operation is universally quantified over it and its BODY may only do what holds for EVERY row. Today the body sees a flexible variable that satisfies any demand. THE PROGRAM, driven, both lines load on main: 'operation takes_pure(s: Stream[T = Int64, E = {}]) -> Int64'; 'operation feed(s: Stream[T = Int64]) -> Int64 = takes_pure(s)' -- which SHOULD be refused at its own declaration, since it claims any row and hands it to something accepting only the empty one; and then 'operation caller(s: Stream[T = Int64, E = {Error}]) -> Int64 = feed(s)', where the same variable is flexible again and binds to {Error}. An effectful stream reaches an operation that declared it wanted none. Each half looks correct alone, which is why neither was ever reported. ROOT CAUSE, LOCATED: rigidify_op_type_params (typing.rs) skolemizes exactly two families -- the operation's OWN [T] params (rec.type_params) and its ENCLOSING sort's (parent_sort_params, WI-942). A parameter of ANOTHER sort left unwritten in a parameter's TYPE (Stream's E in 's: Stream[T = Int64]') is in neither family, so it is never rigidified. A SECOND LEAK, MEASURED SEPARATELY AND SHARPER: 'operation feed[E](s: Stream[T = Int64, E = E]) -> Int64 = takes_pure(s)' ALSO loads -- and there E IS in rec.type_params and IS rigidified. Fix both, and drive the [E] spelling as its own case -- it is the one that proves the check, not the skolemizer.
