## Description

Grammar: make a GENERAL one-component named tuple type `(a: A)` writable. WI-763 admitted the ONE-component form only for the DENOTED shape (`(who: "name")`, a one-entry keep spec), leaving an ASYMMETRY: `(a: "x")` is a 1-tuple type but `(a: A)` is not a type at all. CAUSE, measured during WI-763: `(a: A)` is EXACTLY `arrow_params`' single form (`seq('(', $._tuple_type_arg, ')')`, grammar.js), and the two readings are told apart only by whether `->` follows the `)` -- lookahead PAST the closing paren, which is not LR(1). The denoted form needs no fork because a literal after `:` cannot begin a `_type`, so `field_decl` is already dead; that is why only it was admitted, via prec(1). ROUTES: (a) declare a conflict `[$.arrow_params, $.tuple_type]` and let GLR keep both readings alive to the `->` -- costs a stack fork on EVERY named single-param arrow type, the cost WI-763 deliberately refused; (b) leave the surface alone. DECIDE (a) vs (b) on measured parse cost, not on symmetry alone. NOTE this is NOT the same question as bare `(A)`: spec docs/kernel-language.md and WI-620 state a single parenthesized element is GROUPING and NOT a 1-tuple, so `(A)` must stay grouping -- only the NAMED single component is in scope here, and admitting it makes `(a: A)` and `(A)` mean different things, which needs a spec decision before any grammar edit. ACCEPTANCE if (a): `(a: A)` parses as a one-component tuple_type; `(a: A) -> B` still parses as an arrow; docs/kernel-language.md TupleType production updated; corpus green; workspace green via scripts/test.sh.
