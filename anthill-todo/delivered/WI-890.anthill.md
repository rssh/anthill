## Description

`String` AND `BigInt` HAVE NO C++ BINDING BLOCK AT ALL, so every operation of theirs is now a LOUD cpp codegen refusal — which is right, and is also a gap somebody should close now that it is visible.

STATE AFTER WI-886. `rustland/anthill-cpp-gen/anthill/` carries `float.anthill` and `int64.anthill`; there is no `string.anthill` and no `bigint.anthill`, though `rustland/anthill-stl/anthill/` has both on the rust side. Before WI-886 a call to `String.length(s)` in a cpp-targeted spec emitted `length(s)` — a C++ function that does not exist — into a header codegen reported no problem with. It now refuses at codegen time naming the operation, the carrier, and the clause that would fix it (`unlowerable_operation`, rustland/anthill-cpp-gen/src/lib.rs), and `wi886_host_operation_mapping_test::an_operation_with_no_body_and_no_cpp_realization_is_a_codegen_error` uses `String.length` as its subject precisely because the gap is real.

SO THIS TICKET IS THE FILL, NOT A BUG. `String` maps to `std::string` already (a `TypeMapping` in stdlib/anthill/realization/cpp_std.anthill), so its VALUES lower; only its OPERATIONS have no realization.

THE SURFACE, from stdlib/anthill/prelude/string.anthill: `concat`, `length`, `substring`, `contains`, `indexOf`, `startsWith`, `endsWith`, `toUpper`, `toLower`, `trim`, `replace`, `split`, `repeat`, `isEmpty`, plus the `Ordered` family WI-876 declared (`compare`/`gt`/`gte`/`lt`/`lte`/`max`/`min`).

THE ONE THING THAT MUST NOT BE SKIPPED: WI-884 settled that `String`'s INDEX UNIT IS THE UNICODE SCALAR, not the byte, for `length`/`substring`/`indexOf` alike — it MEASURED that the host `str::find` answers in BYTES (`"éb".find("b")` = 2 where the character index is 1) and that a byte answer makes `substring(s, indexOf(s, sub), ...)` cut the wrong span. `std::string` is BYTES throughout, so the naive `s.find(sub)` / `s.substr(i, n)` mapping REPRODUCES exactly the defect WI-884 refused, silently, for any non-ASCII input. A correct cpp realization needs scalar-indexed helpers, which is more than an expression template can carry — expect this to want either a small `anthill_runtime.hpp` helper set (the header is already copied beside every generated one) or a documented ASCII-only restriction stated in the binding and enforced somewhere. WI-884 also settled that the EMPTY PATTERN occurs at every boundary and that `split` keeps its empty pieces; both must hold in C++ too, and `std::string::find("")` already answers 0, which is compatible.

`BigInt` is a different question and may belong in its own ticket: `cpp_std.anthill` maps no `BigInt` type at all, so there is no host type to realize operations against — C++17 has no arbitrary-precision integer in the standard library. Decide whether the cpp profile supports `BigInt` (naming a vendored type through a `carrier` clause and an `artifact`) or declares it out of scope, and write that down; the current state — a type mapping failure rather than an operation gap — is at least loud.

REFERENCE: WI-886 (which made the gap loud and left the fill), WI-884 (the index unit and the empty-pattern semantics, both MEASURED), `rustland/anthill-cpp-gen/anthill/float.anthill` for what a cpp binding block looks like and what `host_fn` means under `language cpp`.

ACCEPTANCE: `String`'s operations lower to C++ that COMPILES AND COMPUTES THE SAME ANSWERS AS THE RUST HOST on a non-ASCII input (the WI-884 round trip `substring(s, indexOf(s, sub), +length(sub)) = sub` driven through generated C++), or the restriction is stated in the binding block and the operations it cannot realize stay a loud refusal; `wi886_host_operation_mapping_test::every_rust_realized_primitive_operation_is_realized_in_cpp` covers `String` once it has a block; the `BigInt` question is answered in writing either way; full workspace green via rustland/scripts/test.sh.
