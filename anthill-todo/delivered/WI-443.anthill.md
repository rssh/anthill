## Description

Converter+loader: IDENTIFIER-receiver dot calls — route 'args.find(...)' to dot_apply when the identifier is a local binding (the deferred 'p.x' identifier case, convert.rs ~888). TODAY: dot syntax (WI-278) works for receivers the scope-blind converter can recognize as values — '?x' vars in rules, call-result chains ('iterator(xs).find(is_big)' loads clean, probed 2026-06-11), literals — dispatched via sort-guarded [simp] dot rules + the default method fallback on the receiver's least sort. But a BARE IDENTIFIER receiver (an op param or let-binding, e.g. 'args.find(lambda ...)' / 'xs.find(is_big)') is classified as a NAME by is_value_receiver (convert.rs ~892) and flattened to a qualified name — fails loudly as 'unknown functor xs.find', since at parse time 'args.find' and 'Stream.find' are indistinguishable. FIX DIRECTION: defer the name-vs-value classification to the loader/typer, which knows the scope — an identifier-rooted dot callee whose root identifier resolves to a local binding (op param / let / lambda binder) becomes Expr::DotApply (receiver preserved); one that resolves to a sort/namespace keeps qualified-name flattening; an identifier that resolves to NEITHER stays the loud unknown-functor error (no silent fallback). Watch the WI-411 short-name hazard in reverse: a param named like a sort in scope should prefer the local binding (shadowing, like every binder language) — pin with a test.
