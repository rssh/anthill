## Description

A sort application in a RULE BODY bypasses both WI-709 type-argument checks: `convert_term` builds it as a plain `Term::Fn` at load, a THIRD lowering path that reaches neither the loader's `type_expr_to_child` (type position) nor the typer's sort-application arm (value position). Repro (probed while delivering WI-709): `rule bad(?x) :- eq(?x, is_modifiable(Cell[W = Int64]))` LOADS and RESOLVES to a solution, with the undeclared `W` riding into the term — the very divergence WI-709 closed for the other two positions. Nothing observes it today only because `is_modifiable` (like every Type-taking reflect op) keys on the head sort and ignores type ARGUMENTS; it is a live trap for the first consumer that reads them, and for WI-708. Scope note: in a rule body a sort-headed application is not syntactically distinguished from an ordinary data-constructor term, so the check must be keyed on the functor's kind (`kind_of(f) == SymbolKind::Sort`) at the `convert_term` site, and must tolerate LOGIC VARIABLES in argument positions (`List[T = ?x]` is a legitimate rule-body type pattern — reflect rules write them), which the two value/type-position callers never see. The rule itself already exists and is shared: `KnowledgeBase::check_sort_type_args`. Acceptance: the repro above fails at LOAD with the same `InvalidTypeArgument` diagnostic the other two positions raise; a rule-body parameterized type with variable arguments still loads; cargo test green.
