## description

THE REQUIRES-SHADOW LINT (WI-346) FIRES ON A DELIBERATE REFINEMENT AND ADVISES A REPAIR THAT WOULD BREAK IT. These are the stdlib's only two load warnings, printed on every `anthill check` and — since WI-1047 gave `query` the stdlib — on every `anthill query` too:

  warning: operation `map` in `anthill.prelude.FiniteCollection` shadows the inherited
  `anthill.prelude.Iterable.map` (`FiniteCollection` requires `Iterable`); `requires` does
  not override — the two are distinct operations. Qualify … or rename `map` to silence.
  …and the same for `filter`.

THE STDLIB IS NOT WHAT IS WRONG — MEASURED, driven, on the shape the lint is about. A `List` provides BOTH: `FiniteCollection` explicitly (list.anthill:170) and `Iterable` transitively via `Stream` (WI-495). So `xs.map(f)` is genuinely contested. Annotating the return type makes the choice observable:
  operation probe(xs: List[T = Int64]) -> Stream[T = Int64, E = {}] = xs.map(lambda x -> x)
      -> REFUSED: "expected Stream[...], got FiniteCollection[C = FiniteMappedStream[...], ...]"
  operation probe(xs: List[T = Int64]) -> Int64 = xs.map(lambda x -> x).size()
      -> LOADS CLEAN
Dispatch picks `FiniteCollection.map`, the MORE SPECIFIC one, deterministically — which is exactly what the design says it is for (finite_collection.anthill:52-57, WI-599 "THIN": "UNLIKE Iterable.map/filter (→ lazy maybe-infinite Stream), these RETURN a FiniteCollection, so a pipeline over a finite source stays consumable: `xs.map(f).size()` keeps type-checking"). There is NO silent wrong answer behind the warning, and the mismatched-expectation case is a LOUD type error naming both types. Renaming `map` — the lint's own advice — would destroy the design.

WHAT IS WRONG IS THE PREDICATE: `check_requires_shadows` (load.rs) compares SHORT NAMES ONLY. It builds `spec_short` from the required spec's own ops and warns on any short-name hit, never looking at signatures — so it cannot tell a deliberate REFINEMENT (different return type; a distinct operation by construction) from an accidental collision (identical signature; the author probably believed `requires` overrides). It already exempts a PROVIDER's own op ("a legitimate override, not a shadow", via `sort_provides`); a spec that `requires` another and refines its operation has no such exemption, and a spec hierarchy refining an operation is a normal thing to write.

OPTIONS, in the order they were weighed (a DECISION is needed, which is why this is a ticket and not an inline fix):
 (a) NARROW to same-signature shadows — warn only where the shadowing op's signature MATCHES the spec's, the case where the author probably meant to override. Silences both stdlib warnings with no stdlib edit and keeps the lint's stated purpose. Needs a test that a same-signature shadow STILL warns, else the lint is silently retired.
 (b) An explicit opt-out marker on the refining op (attribute or metadata convention) — keeps the lint's full reach, but needs new surface syntax and every future refinement pays the annotation.
 (c) RETIRE the lint — driving shows dispatch decides correctly and a mismatch is already a loud type error, so it may catch nothing the typer misses. Cheapest; gives up a guard not proven useless outside this one case.

ACCEPTANCE: the stdlib loads with ZERO warnings; whichever option is taken, a test DRIVES the case the lint is kept for (under (a): a same-signature shadow still warns; under (c): the removal is justified by showing the typer already reports what it reported); the two dispatch rows above re-measured unchanged, since the point is that the stdlib's behaviour is already right; each test says which case fails when the change is backed out. `cargo-test` green via rustland/scripts/test.sh. REFERENCE: WI-346 (the lint); WI-599 (the FiniteCollection map/filter design); WI-495 (List's transitive Iterable); WI-1047 (which surfaced these on `query`).
