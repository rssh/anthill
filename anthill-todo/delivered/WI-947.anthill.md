## description

SCALAND DIAGNOSTICS REPORT A BYTE OFFSET, NEVER `file:line:col` — port rustland's WI-745/852/854 to scaland. MEASURED (2026-08-03, during the parser resync): every scaland span is built by `AnthillParser.mkSpan(s, e) = Span(fileName, s, e, 0, 0, 0, 0)` — row and col are hard-coded 0 at EVERY construction site, and 27 of the parse-error sites additionally pass `mkSpan(0, 0)`, so they carry no offset either. What a user sees today: `Parse error at 9975: Position 128:91` (fastparse's own rendering, only on the whole-parse failure path) or, for a collected `ParseError`, nothing locational at all. A LoadError is worse: `LoadError.Other(message: String)` — the variant the WI-727 variadic-capture refusals and several others use — has NO span field, so those diagnostics cannot point anywhere even in principle. rustland fixed the same three gaps: WI-745 (blocking load errors get a file identity), WI-852 (a parse error names its file and position, like a load error does), WI-854 (resolve line:col through a PER-SOURCE INDEX, not a rescan of the file per error). WORK: (a) a per-source line index built once per file, byte offset -> (row, col); (b) `mkSpan` populates row/col from it, and the ~27 `mkSpan(0, 0)` sites get real indices (most already have an `Index` available or can take one cheaply); (c) `LoadError.Other` gains a span, or is split into located variants — the WI-727 refusals are the driving case, and `Param` carries no span today so the parser must capture one; (d) one renderer that prints `file:line:col: message` for both error families. ACCEPTANCE beyond the tool passing: a test that parses a fixture with a known-bad line and asserts the reported row/col, and a load-error twin — 'it produces an error' is not evidence the position is right. NOTE what is already correct and needs no work: the WI-850 type-param-default refusal's offset was MEASURED exact across three whitespace shapes (offset lands on the identifier, not the preceding space), so the `Index`-before-whitespace hazard a review predicted does not occur here.
