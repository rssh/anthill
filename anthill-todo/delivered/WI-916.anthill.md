## Description

ONE QUESTION ('which functor does this host name denote?'), THREE FAILURE SHAPES, and one name resolved TWICE. In kb/extent.rs: `register_extent_owner` (~596) returns the typed `ExtentRegError::UnresolvableName(name)`, while `retract_persistent` (~524) and `update_persistent` (~562) return `ExtentError::Backend(format!("persistent retract/update: unknown owner \`{name}\`"))` — a NAME-RESOLUTION failure classified as a BACKEND failure, stringly. WI-908 made the resolution one function; the failure should be one error too. Deeper: `FactRefInner::External { functor: String }` (~69) carries an UNRESOLVED NAME where `Resident` carries a resolved `RuleId`, so every retract/update re-runs the ladder on a string `register_extent_owner` ALREADY resolved and stored in `extents.mounts` — all three `FactRef::external` sites (~1329/1343/1370) pass `self.functor_name.clone()`. Two independent resolutions of one name, and a load between mount and retract can make them disagree. PROPOSAL: hand the resolved `Symbol` back to the source at registration and let `External` carry it; that leaves the MOUNT as the sole `resolve_name_in_global` caller and makes the three-shapes problem mostly vanish. NOT DRIVEN (code-read, /code-review altitude pass on WI-908). FIRST STEP: drive the disagreement — mount, load a shadowing declaration, then retract. ACCEPTANCE: one resolution per name and one error type for its failure; cargo-test green via scripts/test.sh.
