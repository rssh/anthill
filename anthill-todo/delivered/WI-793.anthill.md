## Description

List.foldLeft / foldRight WITH A LAMBDA CALLBACK OVER A LIST LITERAL DOES NOT LOAD -- the path-dependent element type xs.T never resolves for a lambda binder, so the callback body fails to typecheck on a program that is correct. MEASURED on the WI-784 delivery commit (all four cases, exact diagnostics):

  (1) CONTROL, loads clean:
      operation drive() -> Int64 = List.foldLeft([1, 2, 3], 0, shift)
      with operation shift(acc: Int64, x: Int64) -> Int64 = acc * 10 + x

  (2) THE DEFECT, 1 load error:
      operation drive() -> Int64 =
        List.foldLeft([1, 2, 3], 0, lambda (acc, x) -> acc * 10 + x)
      "5:52: type mismatch in add.b (op-arg): expected Int64, got xs.T"

  (3) CONTROL, loads clean -- the SAME lambda against a DECLARED parameter:
      operation drive(xs: List[T = Int64]) -> Int64 =
        List.foldLeft(xs, 0, lambda (acc, x) -> acc * 10 + x)

  (4) foldRight is affected identically:
      List.foldRight([1, 2, 3], 0, lambda (x, acc) -> acc * 10 + x)
      "5:53: type mismatch in add.b (op-arg): expected Int64, got xs.T"

THE BOUNDARY IS NARROW AND BOTH OBVIOUS READINGS ARE WRONG. It is NOT "lambdas break List.foldLeft" -- case 3 uses the same lambda and loads. It is NOT "list literals break List.foldLeft" -- case 1 uses the same literal and loads. It takes the LITERAL receiver AND the LAMBDA callback TOGETHER. A declared List[T = Int64] parameter pins the element type and the same lambda then typechecks; a named operation carries its own declared Int64 parameter types and does not need xs.T resolved at all.

A WI-517 BINDER ANNOTATION DOES NOT OVERRIDE IT -- verified, not assumed:
  List.foldLeft([1, 2, 3], 0, lambda (acc: Int64, x: Int64) -> acc * 10 + x)
gives the SAME error at 5:66. This matches the documented rule that the context type wins over the annotation (kernel-language.md section 4.7), which means the user has NO in-source workaround at the call site short of hoisting the list into a typed binding or naming an operation.

WHY IT MATTERS: List is the concrete workhorse collection and a literal is the most natural receiver, so xs.foldLeft([...], 0, lambda ...) -- close to the most idiomatic higher-order call in the language -- is unavailable. FiniteCollection.foldLeft is NOT affected (its callback is typed with a plain Element type param rather than a path-dependent projection), which is the route WI-784's own fold test drives.

RELATION TO WI-784: adjacent, NOT the same defect, and NOT fixed by it. WI-784 was closure ARITY at eval; this one blocks LOAD one rung earlier, so the closure is never reached. Found while verifying a claim in WI-784's test comments -- the first two characterisations written down were both wrong (see above), which is why the pinned test carries two controls rather than a single failing case.

ALREADY PINNED: known_gap_list_foldleft_lambda_over_a_literal_does_not_load in rustland/anthill-core/tests/include/wi784_closure_arity_test.rs asserts the CURRENT wrong behaviour (case 2 fails to load with an xs.T diagnostic) plus controls 1 and 3, so the boundary stays visible in the suite. It FAILS when this is closed -- replace case 2 with a positive load-and-evaluate assertion.

ACCEPTANCE: List.foldLeft([1, 2, 3], 0, lambda (acc, x) -> acc * 10 + x) LOADS and EVALUATES to 123, agreeing with the named-operation spelling; foldRight likewise; the element type is pinned from the literal receiver so no annotation is needed, and an annotated binder that CONTRADICTS the element type is still rejected; controls 1 and 3 keep loading; the pinned known-gap test is converted to a positive assertion; full workspace green via scripts/test.sh.

ROOT CAUSE = AN ORDERING DEPENDENCY, which is why the dot form worked. One argument's HINT depends on another argument's TYPE, but the `Expr::Apply` arm built hints for EVERY argument and only then pushed the argument Visits -- so at hint time nothing had been typed, the receiver included. WI-485 worked around it with three readers that need no typing (env binding / rule schema / stamp); none covers an ordinary expression. The dot form escaped because the `DotApply` frame pushes only its receiver's Visit and reads that result before the args are typed (WI-443) -- the correct shape, already in the codebase.

IMPLEMENTATION. I first built the shallow fix (a fourth 'synthesizing' rung calling `type_check_node` re-entrantly on the receiver). It worked and was fully green, but /code-review flagged it as a bandaid at the wrong altitude, and the user directed the ordering fix instead. THAT is what landed: a new `ApplyHints` build frame stages the projection-receiver arguments, visits them FIRST on the SAME work-stack, completes the param->arg-type map from their results, then builds the hints and visits the rest. The receiver is typed ONCE.

The ordering fix subsumed four review findings the probe had earned rather than merely relocating them: no double typing; no `[simp]` fuel reset (the probe restarted a fresh `SIMP_FUEL` budget); no re-derivation of the simp gate (the probe re-ran the allocating `simp_equation_rids` scan per probe); and -- the one that mattered -- NO SWALLOWED ERROR. The probe did `.ok()`, the exact shape CLAUDE.md's loud-over-silent rule names. Under staging a staged argument's `Err` rides into the `Apply` frame and `collect_arg_errors` reports it; `a_staged_receiver_that_fails_to_type_reports_its_own_error` drives that.
