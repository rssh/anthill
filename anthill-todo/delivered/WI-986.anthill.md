## Description

SCALAND: `requires`'s UNRESOLVED-NAME DIAGNOSTIC NAMES A SCOPE THE NAME WAS NEVER SEARCHED IN, AND CAN ASSERT SOMETHING FALSE. WI-962 replaced the literal string `"requires"` in `Loader.processRequires` with `kb.scopeDisplayName(scope)`. But the lookup two lines above is `kb.symbols.byQualifiedName.get(nameStr)` — a GLOBAL, fully-qualified lookup that walks no scope chain at all. So the message reports a scope that had nothing to do with the resolution. MEASURED: `namespace demo / sort Widget end / sort S { import demo.Widget; requires Widget } end` renders `unresolved name 'Widget' in scope 'demo.S'` — and `Widget` IS resolvable in `demo.S`, it is imported there. The reader is sent to inspect a scope in which the name is present, and the actual rule (a `requires` must be written fully qualified) is never stated. A TOP-LEVEL `requires nosuchspec` — grammatical, since `requiresDeclItem` is an alternative of `declaration` — renders `in scope '_global'`, trading a literal that named no scope for a synthetic name the reader cannot open. `LoadError`'s own field doc says `scopeName` is "the scope the name was RESOLVED AGAINST — what the reader must inspect"; this filler contradicts it. WORK: either make the lookup match the claim (resolve through the scope chain, so the name really was searched in the named scope) or make the claim match the lookup (say the requirement must be fully qualified, and name the requirement, not a scope). The first is the better language answer if a `requires` may name an imported spec; settle that against docs/kernel-language.md first. `DiagnosticLocationTest` covers only the inside-a-sort form with a name absent everywhere, which is why this passed. ACCEPTANCE: a test whose subject name IS resolvable in the named scope — the measured case above — asserting the rendered diagnostic is true of the tree it describes. Say at the site which test fails when the change is backed out. Found by code review (2026-08-04). Related: WI-962, WI-957.
