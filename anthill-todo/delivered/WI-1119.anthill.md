## description

THE DOT SPELLING AND THE NAMED SPELLING DISAGREE ON A `requires`-CONSTRAINED TYPE-PARAMETER RECEIVER. In one program, `Desc.describe(x)` loads and evaluates while `x.describe()` is REFUSED AT LOAD with `type mismatch in <unresolved receiver>.describe: expected operation declared on the receiver's sort, got no such member (dot dispatch)`. Decide what the dot means here, then make the two spellings agree.

MEASURED 2026-08-16 while verifying WI-823, on the shared `common::DESC_INSTANCES` fixture. IDENTICAL FOR ALL THREE `requires` SPELLINGS, which is what says this is NOT WI-823's op-param gap: an op-param clause (`operation probe[PT](x: PT) -> Int64 requires Desc[PT] = x.describe()`), an op-scoped sort-param clause (`sort HT = ?` + `operation probe(x: HT) requires Desc[T = HT]`), and a SORT-LEVEL clause (`requires Desc[T = HT]` on the sort) all fail at the same site with the same message. Unchanged by backing WI-943 out, so it neither predates nor follows from the op-param identity fix.

TWO CONTROLS THAT WORK, which is what makes this a DIVERGENCE rather than a general limit on abstract receivers: a CONCRETE receiver (`operation probe(x: Leaf) = x.describe()`) loads and gives 1; and an ABSTRACT-SPEC receiver (`operation probe(x: Desc) = x.describe()`) loads and gives 1 in BOTH spellings -- the dot and the named form already agree there. Only a receiver typed as a `requires`-constrained TYPE PARAMETER diverges.

SPEC STATUS -- UNLEGISLATED, NOT A STATED REFUSAL, and this is the first thing to settle. docs/kernel-language.md par. 3538 legislates the dot on an abstract-spec receiver ("the dot instead hands the call to the spec operation and the value decides it -- the same reader the qualified spelling reaches"), and par. 3592 states that a dot "reaches the same rule" as the named spelling. The same par. 3538 lists "a call whose carrier is a type parameter" as a recognised case for the NAMED spelling. Neither says what a dot on a `requires`-constrained type parameter does. So the spec decides this before the implementation can; the sibling cases both point at "hand it to the spec operation and let the value decide", which is what the named spelling already does here via the WI-562/WI-943 licence.

MECHANISM, READ AT THE SITE AND CONFIRMED BY INSTRUMENTING IT (kb/typing.rs, the `DotApply` frame that ends in `DotDispatchNoMatch`): `recv_sort = sort_functor_of_view(kb, &recv.ty)` is `None` for a type-parameter receiver, and the ENTIRE member ladder sits inside `if let Some(s) = recv_sort` -- the receiver's own member (`find_operation_in_scope`), the WI-281 provided-spec fallback (`find_spec_op_for_provided_sort`) and the WI-614 required-spec fallback (`find_spec_op_for_required_sort`) are all skipped wholesale, and the arm falls through to `DotDispatchNoMatch` with no receiver to name -- hence `<unresolved receiver>` in the message. The miss is therefore a MISSING RUNG, not a wrong answer from an existing one.

WHY THIS IS A TICKET AND NOT AN INLINE FIX -- MEASURED AT THE FRAME, not assumed (the size estimate was itself probed, per the follow-up-on-follow-up rule). Instrumenting the miss shows the constraining spec IS reachable for the two OP-SCOPED shapes: `env.op_requires()` holds exactly one entry, `required_sort = Desc`, at the moment of the miss. It is NOT reachable for the SORT-LEVEL shape: `env.op_requires()` is EMPTY there, and the chain would have to come from the enclosing sort instead. So a fix needs (i) TWO chain sources composed at one read -- op-scoped and sort-level -- which is the exact shape this repo keeps re-finding as a defect when only one is wired (WI-945, WI-1098); (ii) the sigma-alignment matching a chain entry's carrier against the receiver's type VARIABLE, which is `reached_carrier_matches_call`'s question asked from the other side; (iii) an AMBIGUITY rule for two constraining specs declaring one member name -- par. 3538's tie machinery does not currently reach this because no dispatch is attempted at all; and (iv) the par. 3538 decision above.

BLAST RADIUS ON EXISTING CODE IS ZERO BY CONSTRUCTION: the shape does not load today, so no stdlib file, example or fixture can be written in it -- whatever is decided, nothing existing changes meaning. What a fix changes is which programs are ACCEPTED. That also means the risk is one-directional and there is no migration.

ACCEPTANCE: par. 3538 gains a sentence saying what a dot on a `requires`-constrained type-parameter receiver does, and the implementation matches it. If the decision is that it dispatches like the named spelling (the direction both sibling cases point), then all three spellings above LOAD and EVALUATE to the depth-coded values their named twins produce, DRIVEN to a value and not merely to a clean load; the two working controls (concrete receiver, abstract-spec receiver) stay green as the CONTROL that the new rung did not widen anything else; a member name declared by TWO constraining specs is REFUSED naming both, with a driven test; and the refusal for a member NO constraining spec declares stays a `DotDispatchNoMatch` -- but naming the receiver's parameter rather than `<unresolved receiver>`. If instead the decision is that the dot is deliberately refused here, the message must say so (naming the parameter and the specs that constrain it) instead of reporting "no such member", and par. 3538 must record why the two spellings differ.
