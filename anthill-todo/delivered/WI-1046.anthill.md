## Description

THE BOOLEAN OPERATORS ARE POSITION-DIRECTED IN THE SPEC AND WERE NOT IN FACT. `docs/kernel-language.md` §6.6 (WI-529) states it verbatim: "`not`, `or`, and `and` each name a dispatched value operation on `Bool` ... inside an operation body (evaluated), but a goal form in a rule body (resolved) ... Resolution is by syntactic position, not by a distinct glyph or operand type." WI-529 routed ONE direction (a redirect from the primitives to the Bool ops inside an op body) and left the rule-body direction to the implicit-prelude FALLBACK, which sits BELOW scope resolution — so any name in scope shadows it.

MEASURED, driven, one ordinary import, five rows (`fact l(1)`, `fact r(1)`, `fact empty(99)`):
  rule pipe(?x)     :- l(?x) | r(?x)          expected 2 | no import 2 | WITH `import anthill.prelude.Bool` 0
  rule comma(?x)    :- l(?x), r(?x)           expected 1 | 1 | 1            (CONTROL)
  rule nafTrue(?x)  :- l(?x), not(empty(?x))  expected 1 | 1 | 0
  rule nafFalse(?x) :- l(?x), not(r(?x))      expected 0 | 0 | 0
  rule amp(?x)      :- l(?x) & r(?x)          — | 0 | 0
The `nafTrue` row is a WRONG ANSWER, not a missing one: negation-as-failure over a goal that fails must SUCCEED. `nafFalse` is why it is the row to drive — it reads 0 under the defect and 0 when correct.

CORRECTION TO THIS TICKET'S ORIGINAL TEXT — one of its two measurements was FALSE. It claimed `rule neg(?x) :- l(?x), not(l(?x) & r(?x))` "parses clean, loads clean, and `neg` does not resolve", i.e. a rule vanishing silently. RE-MEASURED with a control: `rule neg(?x) :- l(?x)` — no `&` at all — ALSO does not resolve, and the same body with head `uniq1046` DOES. The cause is the head NAME: `neg` resolves to `anthill.prelude.Numeric.neg`, so per WI-896 the rule concludes about the prelude symbol instead of introducing its own. Documented behaviour, nothing to do with `&`. The real second defect is the import capture above, which the original text did not have.

DELIVERED. (1) `Loader::route_body_goal_boolean`, the mirror of WI-529's `redirect_op_body_boolean`, applied at GOAL POSITIONS: an `in_body_goal` flag rides from each top-level body atom down through the goal slots of the connectives above it and turns off at every data slot, so a goal's ARGUMENT keeps the value reading. (2) Which slots are goals now comes from ONE shared table, `KnowledgeBase::goal_arg_slots`, read by the query walk (WI-863), the rule-body walk (WI-1034) and the loader — which needs the answer while still BUILDING the body and so cannot ask either walk. (3) `&` in a goal position is REFUSED naming the comma (`LoadError::BooleanOperatorInGoalPosition`), since §6.6 says there is no `kernel.and` to route it to. (4) §6.6 updated: the claim was true of one direction only.

BLAST RADIUS ZERO, measured: `Bool.and`/`.or`/`.not` appear in NO rule-body goal position across stdlib+bindings, +testcases, +examples, +anthill-todo. The probe's CONTROL is that the same walk finds `anthill.reflect.not` 3-4x and `anthill.kernel.push_choice` once.

FOUND WHILE TESTING, now pinned: `&` binds LOOSER than `=` (priority 2 vs 3), so `?r = ?a & ?b` is `and(eq(?r, ?a), ?b)` — the `and` is the top-level GOAL. That loaded clean and never fired; it is now loud. Coverage + the three-column back-out table: `wi1046_boolean_goal_routing_test`. REFERENCE: WI-529; WI-1034 (which found this); WI-896 (the `neg` correction); §6.6.
