## Description

A loader DECLARATION RECORD does not conform to the field types reflect declares for it -- 685 measured mismatches, in 7 classes, and the whole family is one question: what does a reflect record's slot actually hold?

MEASURED under WI-928 (stdlib + Rust host bindings), by letting typing.rs's check_entity_facts run over them:
  EntityInfo.name              180x  expected Symbol, got <the named sort> (Expr, Pattern, MemberKind, ...)
  MemberInfo.name              180x  expected Symbol, same shape
  ProofRecord.witness          128x  expected Term, got ProofWitness
  ProofRecord.parametric_context 128x expected Term, got List
  SortInfo.constructors elem    50x  expected Symbol, got <the named sort>   (reported as 'SortInfo.head' -- the cons cell's field, outer entity name)
  OperationInfo.params elem     17x  expected Term, got TypeExtractor / EffectExpression
  OperationInfo.return_type      2x  expected Term
ZERO of the 685 is a user fact. Every one is a record the loader wrote about a declaration.

WHY IT IS NOT SIMPLY A BUG IN EITHER SIDE. The loader writes a reflect HANDLE into these slots -- a name term for a name, a KB term handle for a term, a structured witness for a witness -- and check_value_against_type asks a SUBTYPE question. Reaching a handle from a value is a CONVERSION (as_term / term_as_entity, WI-406) and deliberately NOT subsumption: 'Term' is not a top type (user decision, 2026-06-06). So the check as it stands reports a mismatch for every well-formed record, and 'make Term a top type' is the one fix that is ruled out in advance.

CURRENT STATE (WI-928): check_entity_facts SKIPS declaration records, keyed on KnowledgeBase::is_metadata_functor -- the same predicate as WI-630's write-side tripwire, so the set the loader may write and the set the check skips cannot drift. That restores exactly the status quo (these facts were unreachable before free-standing entities got a SortInfo) and is documented in place. It is a boundary, not a repair.

THE QUESTION THIS TICKET OWNS: can the reflect schema and the loader's writes be brought into agreement, so declaration records are checked like any other fact? Directions, in rough order of promise:
 (a) DECLARE WHAT THE SLOT HOLDS. EntityInfo.name : Symbol may simply be wrong if what is stored is a NAME REFERENCE whose type is the referenced sort; likewise ProofRecord.witness : Term for a ProofWitness value. Cheapest to try, and it may absorb 5 of the 7 classes. Note the corpus evidence that a declared type nobody checks drifts from the data: WI-928 found WorkItem.description : Option[T = Term] and Feedback.content : Term holding 921 + 894 prose strings, and corrected both to String.
 (b) TYPE THE HANDLE RELATION. Give Symbol / Term a checking rule that recognizes a name reference / a term handle without making Term a top type -- the WI-385 arg/field-validation family's unfinished half.
 (c) CONVERT AT THE WRITE. Have the loader write through the explicit conversion, so the slots hold what they declare.
CONSTRAINT: whatever lands must keep 'Term is not a top type' true. Verify against the user's WI-406 decision before touching types_compatible.

ACCEPTANCE: either declaration records type-check (and the WI-928 skip in check_entity_facts is deleted), or the reason they cannot is written down in the spec next to the reflect schema and the skip cites it. cargo-test green via rustland/scripts/test.sh.

SOURCE: measured while delivering WI-928 (2026-08-02). The 685 were invisible until then because reflect's records are declared as free-standing entities and a free-standing entity emitted no SortInfo, so no constructor list ever named one.
