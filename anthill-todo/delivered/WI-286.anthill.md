## description

Rule-body dot_apply terms were generated malformed (pre-existing fallout from committed 27af763 / WI-278b, uncaught because that commit validated only -p anthill-core while the qfnra_field_access fixture lives in anthill-smt-gen). convert_term (the rule/fact/query TERM path, load_rule -> convert_term) converted the converter-emitted parse dot_apply(receiver, Ident(name), ...) GENERICALLY — leaving receiver/name positional and (via entity-field expansion) stuffing a fresh var into the dot_apply entity args field — instead of the canonical reflect dot_apply(receiver:, name:, args: List) that convert_expr (the op-body occurrence path) builds. So op-body and rule-body dot_apply had INCONSISTENT representations and smt-gen (a TERM consumer reading rule_body) failed emit with 'unhandled arithmetic op dot_apply'. Fix: convert_term re-encodes dot_apply into the canonical reflect form (matching convert_expr; children stay bare terms, which term consumers read), guarded on the converter shape (>=2 positional + Ident name) so a user-written dot_apply token / a user entity dot_apply falls through to generic conversion (else pos_args[1] panics — caught in /code-review, regression-tested by parse_test::user_written_dot_apply_token_does_not_panic). smt-gen as_field_access reads an empty-args dot_apply as a field access (nested chains recurse). Acceptance: qfnra_field_access tests green; full anthill-core + anthill-smt-gen green; a user dot_apply token does not panic the loader. Refs: docs/design/simp-dot-finding.md; relates to WI-278/WI-282.
