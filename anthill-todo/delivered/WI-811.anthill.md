## description

Unify the mount drain; read_facts(Resolve) delegates to the resolver instead of a second mount path. Mounting (proposal 057) is integrated in TWO places, both draining the same ExtentSource::query cursor over the shared kb.extents registry: resolve.rs::drain_extent_rows (per-frame mounted-extent cursor feeding SLD candidates AFTER the resident ones, WI-797) and extent.rs::read_mounted_facts (drain-fully + re-filter by bound_matches/row_has_functor, WI-773). Same substrate, DUPLICATED drain-and-match logic -- an artifact of read_facts (WI-773) and resolver-mount (WI-797) landing as separate steps in the 057 cluster: the substrate got shared, the drain did not. FIX: (1) extract ONE shared mount-drain helper so exactly one place speaks ExtentSource::query; both call sites ride it. (2) When the read_facts Resolve policy lands (WI-774) it MUST delegate to the resolver -- which already mounts, evaluates bodies, and can aggregate most-specific-first -- NOT add a THIRD mount path: Resolve IS SLD. NOTE: read_facts(Refuse) is a GENUINELY non-resolving read (find candidates, reject any with a body, return fact heads) -- SLD is the wrong engine for it (SLD would evaluate the very bodies Refuse rejects), so Refuse stays a candidate-read sharing only the substrate. Net target: SLD-over-(resident UNION mounted) is one engine; read_facts(Resolve) is its facade; read_facts(Refuse) is the non-resolving table read over the same candidate-find. Relates WI-774, WI-780, WI-773, WI-812.
