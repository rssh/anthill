## Description

RUSTLAND: `emit_member_fact` REDERIVES ITS WHOLE SYMBOL SET PER MEMBER. Per `MemberInfo` fact it does `resolve_symbol("anthill.reflect.MemberInfo")`, three `intern`s (`name`/`kind`/`parent`), a `format!("anthill.reflect.MemberKind.{kind_name}")` HEAP ALLOCATION, and a second `resolve_symbol` on that freshly-built string. Every one of those is loop-invariant across `emit_member_facts_for_items`, which is the sole caller (9 call sites inside it, one per member kind). At ~750 members per stdlib load that is ~750 `format!` allocations and ~1500 string-hash lookups. WORK: hoist into the caller — the `MemberInfo` symbol, the three field symbols, and a `kind_name -> Symbol` table built once (there are ~7 kinds: Constructor, Sort, Operation, Rule, Namespace, Const, plus the `kind` variable arm). The existing `EntityInfoSyms` struct is the shape this codebase already uses for exactly this (`Loader::entity_info_syms`), so mirror it rather than inventing one. WHY IT IS FILED SEPARATELY AND NOT AS PART OF WI-1028: it is entirely outside that ticket's diff, and it is a PERF change, which in this repo means it needs a measurement rather than a green suite — the suite is only the control for "the facts are identical", which is the easy half. SIZE IT FIRST: this was found while measuring WI-1028's scope-term derivations, and the reviewer's count says this one call dwarfs every derivation in that diff combined — so take a before/after (`ANTHILL_ITEM_TIMING=1`, or a load-time measurement on the stdlib corpus) and record BOTH numbers, not just the after. If the measured win is immaterial, say so and close it rather than landing a hoist on the strength of an operation count. ACCEPTANCE: the emitted `MemberInfo` facts are byte-identical over the stdlib corpus (assert the fact SET, not just that the load is green — a hoist that dropped a kind would still load); a before/after load-time measurement recorded in the delivery; say at the site which test fails when the change is backed out, and say plainly which pass either way by design. Found by code review of WI-1028. REFERENCE: WI-1028.

CLOSED BY MEASUREMENT — THE HOIST WAS WRITTEN AND REVERTED. No perf change landed; what landed is a doc comment at `emit_member_fact` recording the numbers.

MEASURED, release, stdlib load, n=25 (best-of-5 first, then quartiles when the first pair looked like a regression):
  without the hoist  min 0.0397s
  with    the hoist  min 0.0380-0.0392s, median 0.0411-0.0415s over two runs
Indistinguishable. The arithmetic agrees and should have been done first: ~750 `format!`s at ~100ns are ~75µs of a 40ms load — 0.4%, well under this measurement's ~10% spread.

THE REVIEW NOTE THAT MOTIVATED THE TICKET WAS TRUE AND IRRELEVANT. "Dwarfs every scope-term derivation in the diff combined" is correct — and both are negligible. A relative comparison between two negligible costs reads as significance; "dwarfs X" is only a finding once X is known to matter. Recorded in docs/process/converging.md as the general lesson.

A SECOND REASON NOT TO WANT IT, found by measuring rather than reasoning: the natural hoist is per-SCOPE, and the `MemberKind` map costs 7 `resolve_symbol`s per scope. At ~147 scopes and ~750 members that is MORE string lookups than it removes. A real hoist would have to cache per Loader, which is more machinery for a 0.4% ceiling.

ONE THING THE ATTEMPT DID EARN: the exhaustive `KINDS` list panicked on the first stdlib load with "MemberKind `Enum` is emitted but absent" — the computed `SortWithBody` arm yields `Enum`, which my list missed. Loud beat silent exactly as intended. Nothing to fix in the reverted code (the `format!` path handled `Enum` fine); the episode is noted because it is the argument for the panic over a fallback, should anyone build this later.

THE DOC COMMENT IS THE DELIVERABLE: it states the numbers, the 0.4% arithmetic, and the per-scope trap, so the next reader does not re-derive this from an operation count. Filed and closed the same day; had it sat Open it would have read as pending work indefinitely, because the operation count is persuasive and nobody re-measures a backlog item.
