## description

WI-204 enabler: implement static-dispatch rewrite for spec ops in typer's check_apply. Blocker for WI-204 (port cmd_X bodies through WorkItemStore spec ops). Today the dispatch hook in kb/typing.rs::check_apply (typing.rs:719) calls find_unique_impl_op to validate that spec→impl resolution is unambiguous, but does NOT actually rewrite the call. At runtime the eval still tries to invoke the spec op (which has no body) and errors 'unknown operation: <name>'. Per docs/design/spec-instance-dispatch.md the static form should rewrite the call's fn symbol from <Spec>.<op> to <UniqueImpl>.<op> at typing time so the runtime sees a direct impl call. Design: pure rewrite plus side hashtable for occurrence provenance. (a) Allocate a new apply term: same args, same effects, but `fn = <UniqueImpl>.<op>`. The new TermId is hash-consed normally — no extra named arg, no shape divergence. (b) Insert (new_term_id → original_fn_sym) into a KB-level `dispatch_origin: HashMap<TermId, Symbol>` map (or similar) so reflection, proof-record specialization, and debug/error tooling can recover the spec call ("this was originally WorkItemStore.commit, dispatched per fact WorkItemStore[State = WIS]"). The interpreter never reads `dispatch_origin` — runtime semantics are identical to a hand-written qualified-impl call. (c) Caller of `check_apply` substitutes the new TermId in place of the original; substitution propagates upward through nested expressions via standard hash-consed re-allocation. Why pure rewrite + side table over alternatives: inline-annotation (apply gains a named `spec_op` arg) splits apply into two hash-consed shapes (with vs. without spec_op) — defeats sharing between dispatched and direct-impl call sites. Side table keeps apply uniform AND preserves provenance; consistent with anthill's existing pattern of out-of-band per-occurrence data (e.g., source spans). Acceptance: cargo-test green; new test asserts that `next_id(s)` for s : Cell[V = WIS] resolves to FileBasedWorkitemStore.next_id at typing time, dispatch_origin records the original WorkItemStore.next_id symbol, and the eval runs the impl body without 'unknown operation' errors. Driver: WI-204 currently must work around with qualified impl calls (FileBasedWorkitemStore.next_id) to bypass the missing rewrite. Out of scope: dynamic dispatch (vtable-style runtime KB lookup, deferred per spec-instance-dispatch.md); coherence priority resolution (single-impl world today, future WI when multi-impl projects appear).
