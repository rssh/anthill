## Description

SOUNDNESS BUG: a BUILTIN call nested as an OPERAND in a rule body is neither reduced nor delayed — it falls through to a STRUCTURAL comparison, so an arithmetic guard is silently, unconditionally TRUE. REPRO (probed): given fact num(v: 1..3), 'rule not_diag(?x,?y) :- num(v:?x), num(v:?y), neq(sub(?x,?y), 1)' admits ALL 9 pairs, INCLUDING (2,1) and (3,2) which the guard must exclude — sub(2,1) = 1, so neq(1,1) is false. The guard does nothing. Dual symptom: 'rule doubled(?x,?y) :- num(v:?x), eq(?y, add(?x,?x))' — doubled(1,2) FAILS although 1+1=2. So the same root cause yields a false POSITIVE in the neq direction and a false NEGATIVE in the eq direction. ROOT CAUSE (traced): (1) reduce_op_value (kb/resolve.rs:5402) returns a builtin call UNREDUCED — its comment says 'A builtin (field_access, arith, eq, ...) is reduced by its own path, not folded. Only a CONCRETE operation (one with a stored body) folds' — but 'its own path' only exists when the builtin is the goal's OWN functor; nested as an operand, sub(?x,?y) is simply left as a term. (2) is_unreduced_op_call (kb/resolve.rs:5698) returns 'self.builtins.get(functor).is_none() && ...' — FALSE for sub, because sub IS a builtin — so eq_operands (kb/resolve.rs:4442) does NOT delay. (3) sem_eq_values (kb/resolve.rs:4061) then reaches the structural verdict: the term sub(2,1) differs structurally from 1, hence neq is TRUE. NOTE this contradicts what wi483_rule_body_method_eval_test.rs:10-14 claims the design does — 'a COMPLEX op-call (body needs the interpreter — arithmetic, match/if/let, recursion) is LEFT uninterpreted, treated as un-ground (it residualizes / delays), NOT a loud error'. It does NOT residualize; it silently decides. Residualizing would be honest (and, with WI-737, would raise); deciding structurally is a wrong answer. MINIMAL FIX (the soundness floor, independent of any evaluation feature): make is_unreduced_op_call recognize BUILTIN calls in operand position so a non-evaluated operand DELAYS instead of being compared structurally. That converts every case above from a silent wrong answer into an honest flounder — which WI-737 then turns into a raise. Making it actually COMPUTE is a separate, additive step (see the functional-flattening ticket). GUARD the fix: an operand that is a genuine DATA constructor (cons/some) must still compare structurally — only OPERATION/builtin calls delay; anthill can tell them apart (unlike Prolog, where 1+2 is legitimately a term). ACCEPTANCE: neq(sub(?x,?y),1) no longer admits (2,1); eq(?y, add(?x,?x)) no longer silently fails; both surface as an honest residual/raise rather than a decision; structural comparison on constructor terms is unaffected; a regression test pins both directions; cargo-test green via scripts/test.sh.
