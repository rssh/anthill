## description

USER-DIRECTED, done inline after WI-956. Two renames that turned into a defect.

1. `KnowledgeBase::resolve_sym(Symbol) -> &str` sat one truncation from `resolve_symbol(&str) -> Symbol` and ran the OPPOSITE way. Renamed `local_name_of`.

2. NOT `short_name_of`, which is where the interesting part is. MEASURED over stdlib + anthill-stl: 53 of 2598 symbols answer with a DOTTED name. All are WI-341 callback places — `register_callback_places` (load.rs) defines every place in the OPERATION's scope keyed by its path relative to that op, so `anthill.prelude.Monad.flatMap.f._1` is filed under `f._1`. The dot is load-bearing: it keeps `f._1` distinct from a sibling callback's `g._1` in one flat `scope.locals` map. So the stored name is the name WITHIN THE DECLARING SCOPE, not a single segment.
   Renamed with it: `SymbolDef.short_name` -> `local_name`, `SymbolTable::name` -> `local_name`, and its "backward compatibility" alias `SymbolTable::resolve` DELETED (2 callers). `codegen/rust.rs`'s own `resolve_sym` helper (same meaning, String) went too.
   NOT renamed, deliberately: `typing::short_name_of(&str)`, `anthill-cpp-gen`'s copy, `anthill-smt-gen::short_name`, and the LANGUAGE-level `anthill.reflect.short_name`. Those really do slice the last segment, and they exist BECAUSE the stored name is not one — `builtin_short_name`'s `rsplit` is what turns `f._1` into `_1`. Composing them (`short_name_of(kb.local_name_of(sym))`) is a real idiom; they are not interchangeable, and both docs now say so.

3. THE DEFECT the rename exposed, spotted by the user: `SortAliasIndex.by_name` was keyed on that name ALONE. A local name identifies nothing outside its scope — 37 SortAlias sources are named `T` after a stdlib load — so `sort_alias_by_name` answered with whichever came first, i.e. an unrelated declaration's variable. It was documented as "a NAME-DIRECTED GUESS" and had already caused one measured bug: WI-943 found a bracket parameter reaching it and being answered `anthill.kernel.T`, so `cmp[T]` and `cmp2[T]` shared one var. WI-943 fixed that caller and LEFT THE GUESS.

DECISION: removed, not re-keyed on `(parent, local_name)`. THE MEASUREMENT that settled it — with `sort_alias_by_name` forced to `None`, the FULL WORKSPACE ran 4091 tests, 0 failures; with `find_sort_alias_var`'s matching second pass ALSO deleted, again 4091/0. Nothing wanted it. Re-keying would have preserved a rung no caller needs and left every caller owing a parent it does not always have.

REMOVED: `SortAliasIndex.by_name`; `sort_alias_by_name`; `type_param_global_var`'s third rung (the very one WI-943 measured going wrong); `find_sort_alias_var`'s second pass. `resolve_sort_alias` and `sort_alias_exact` MERGED — WI-943 split them only so an identity-wanting reader could dodge the guess, and with the guess gone they were the same function.

RETRACTS PART OF WI-956 ITEM 1. That item widened `scan_sort_aliases`' predicate to `(functor, target)` so `find_sort_alias_var` could reject a non-Var target PER FACT and let the scan continue past it. That was correct while a by-name pass could see several same-named candidates; with only an exact match there is at most one candidate (`sort_alias_exists` dedup-guards emission; MEASURED, 103 facts over 103 distinct sources), so the predicate is back to `Fn(Symbol)` and the caller post-filters. WI-956's test for that property is retired with it — a test whose subject no longer exists.
