## description

Convert stdlib typeclass-satisfaction sites from rule-based to operation-with-body form. Today many sorts that satisfy a typeclass declare 'fact TypeclassName[...]' and then provide 'rule op_name(...) = ...' clauses to 'implement' the typeclass's operations. Per proposal 018 (expression bodies), the correct shape is 'operation op_name(...) -> RetType = match arg case ... -> ...' — operation declaration with a carrier-refined signature and a body that the evaluator executes, NOT a rule that the resolver matches. The rule-based form leaks behavior into the resolver/unification path instead of providing a real operation implementation that the evaluator can call. Audit and convert: list.anthill (length, member, append; nth via IndexedSeq; split via Iteration; insert, empty via Collection), map.anthill (operation laws across the file), bigint.anthill, and any other prelude sorts that follow the same anti-pattern. Once converted, library/001-map.md Phase 4 can write List→Stream / PersistentMap→MapReadable provisions in the correct form. Driver: discussed during library/001-map.md authoring (2026-05-28) when adding 'fact Stream[T]' to List surfaced the conflated rule-as-operation-implementation pattern. Reference proposal: docs/proposals/018-expressions-and-operation-implementation.md. Example of the correct shape: stdlib/anthill/cli/help.anthill:45 (render_args operation with match body).
