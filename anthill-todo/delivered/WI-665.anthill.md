## Description

MECHANISM (governs the build-once reflection-fact indexes: op_records/WI-656, sort_alias_index/WI-659, provides_index/WI-660, and future SortInfo/RequiresInfo indexes). PROBLEM: these typed indexes are built once at type-check start over loader-emitted reflection facts (OperationInfo, SortAlias, SortProvidesInfo, ...), but some are READ AT RUNTIME by paths that can in principle mutate those facts via eval `Store` assert/retract -- e.g. sort_provides is reached from the resolver simp guard, provider_spec_view_bindings from eval dispatch. A build-once, never-invalidated index then reads a STALE relation (the WI-607 ABA hole). WI-660's stopgap -- drop the whole index to None on ANY assert/retract and rebuild only at the next type-check -- is WRONG on two counts: (1) it invalidates on mutations to UNRELATED functors, though the index depends on exactly one functor; (2) after the drop it is not rebuilt until the next type-check, so runtime callers fall to a full linear scan indefinitely. "Just erasing caches on mutation" is not acceptable. SAFETY INVARIANT (must hold for every such cache): EITHER the functor(s) the cache depends on are IMMUTABLE, so build-once is sound by construction; OR the cache is invalidated ONLY by a mutation to a depended-on functor AND rebuilt lazily on next use. Two arms to satisfy it: ARM (a) IMMUTABILITY, SURFACED IN THE LANGUAGE -- mark reflection functors immutable, visibly in source. Surface sub-options: (a1) an explicit `immutable(Functor)` fact/declaration; (a2) immutable-by-DEFAULT plus an explicit `mutable` mark on the functors that genuinely mutate (user/data facts written by Store). Then a runtime Store assert/retract targeting an immutable functor is a LOUD error (LoadError / eval error) -- per repo principle "loud error over silent skip" -- never silent staleness. Effect: op_records / sort_alias_index / provides_index (and future SortInfo/RequiresInfo indexes) become sound build-once with ZERO invalidation machinery. ARM (b) FUNCTOR-SPECIFIC INVALIDATE + REBUILD-ON-USE -- for functors that must stay mutable: the cache records the set of functors it depends on; the assert / retract / unindex_functor choke points invalidate a cache ONLY when the mutated functor is in that set (not on every mutation); and the cache is stored as RefCell<Option<..>> with a lazy accessor that REBUILDS on first use after invalidation (never a permanent scan fallback). RECOMMENDATION: arm (a), immutable-by-default + explicit `mutable` opt-in (a2). It is the most general -- it makes the whole family of reflection-fact indexes sound build-once with no per-cache invalidation code, and it turns an illegal runtime mutation into a clear diagnostic. The vast majority of loader-emitted structural facts are never rewritten; only user/data functors mutated via Store need `mutable`. Arm (b) is the fallback for any functor that must stay mutable. NOTE on simp_gate_cache (mod.rs:477): it already rebuilds-on-use (drops to None, recomputed lazily) -- that half is fine -- but it invalidates on ALL mutations, not just the eq/unify [simp]-rule functors it depends on; bring it under the same functor-specific rule (arm b) since [simp] rules CAN be asserted at runtime (so those functors are legitimately mutable, not immutable). SCOPE / ACCEPTANCE: a functor-immutability notion exists and is visible in source (chosen surface); a runtime eval Store assert/retract of an immutable functor produces a loud error, not silent success; op_records / sort_alias_index / provides_index drop their invalidation hooks (arm a) OR gain functor-specific invalidate + lazy rebuild-on-use (arm b) -- NO cache uses "erase on any mutation, never rebuild"; simp_gate_cache invalidation becomes functor-specific; WI-660 is resolved under the chosen arm (its current drop-on-any-mutation is removed); full suite green; a synthetic test that Stores an immutable reflection fact gets the loud error, and (arm b path) a mutable-functor cache rebuilds correctly on next use after invalidation. RELATED: WI-607 (deferred sort_provides cache; its note that a correct cache needs an epoch/choke-point signal and that COUNT-keying is ABA-unsound -- immutability sidesteps both), WI-656/659/660 (the build-once indexes this governs), WI-661 (carrier-agnostic-heads umbrella).

### 2026-07-08T10:41:29Z — feedback — user

Design converged into docs/proposals/053-fact-mutability.md "Per-Functor Fact Monotonicity" (committed c0c3e59c). The original recommendation here (immutable-by-default reflection functors + explicit `mutable` marker, loud error on runtime Store) is SUPERSEDED. Landed design: mutability IS the Modify effect (037), not a new axis; a single per-functor enum `anthill.reflect.fact_monotonicity(functor: Symbol) -> Monotonicity {constant, monotone, non_monotone}`, default `monotone` (append-only — the KB is add-friendly), NOT overlapping mutable/appendable booleans; per-functor because both the in-memory KB and any external store hold a MIX of functors (007 §8's one FileStore owns WorkItem/Project/Feedback/ToolDef), so the value is given by the OWNING store — an in-memory reflect rule, or a `monotonicity` field on an external store's per-functor binding (007 §6/§7) — and bounded by the store's write capability (`monotonicity <= capability`, propagating down the backend stack per 036). Mutation = RETRACT; retract of a non-`non_monotone` functor is the SOLE loud guard, assert stays the default. No grammar change. CACHE INVALIDATION IS RUST / OUT OF SCOPE for the language proposal — so THIS WI's remaining scope is the Rust KB cache implementation behind the guarantee (build-once for constant/monotone, invalidate-on-retract for non_monotone; plus the simp_gate_cache functor-specific fix), not the design. WI-660 (provides_index, stashed) reworks under this.
