## description

anthill-todo: `delete` must not leave an item's dependent rows behind. Today `WorkItemStore.forget` (store.anthill) retracts ONLY the WorkItem row -- `find_stored_by_id(stored_facts_of(kb(), WorkItem), target)` -- so an item's Feedback and Tag rows outlive it. FOUND BY MEASUREMENT during WI-1118's migration rehearsal: this repo's own tracker carried two orphaned Feedback rows naming a WI-237 whose WorkItem had been deleted, plus three depends_on edges (WI-240, WI-241, WI-260) still pointing at it. Under the single-file store an orphan row is invisible -- it just sits in workitems.anthill -- which is why it went unnoticed for months.

THE BLOCKER IS A DELIBERATE PRIOR DECISION, and this ticket's real work is revisiting it. WI-666 / proposal 053 declares Feedback (and StoreFormat) `monotone` and WorkItem + Tag `non_monotone` in store.anthill. `Store.retract` refuses a non-`non_monotone` functor LOUDLY, so today Feedback CANNOT be retracted at all: cascading to it is not a code change, it is a change to Feedback's write policy. Tag is already non_monotone and could be cascaded immediately. So decide first: is append-only Feedback still right, given that it makes every delete leak rows by construction?

TWO READINGS OF 'DEPENDENT', AND THEY ARE VERY DIFFERENT IN BLAST RADIUS -- pick one explicitly rather than letting the implementation decide:
  (a) THE ITEM'S SATELLITE ROWS -- Feedback and Tag keyed by `workitem: <id>`, i.e. the rows that describe the item being deleted. This is the orphan case above and is almost certainly what is wanted.
  (b) WORK ITEMS THAT NAME IT IN depends_on -- a true cascade delete of other work items. Far more destructive, and in this tracker WI-237 would have taken WI-240, WI-241 and WI-260 with it. If (b) is wanted at all it should be opt-in (--cascade) and should print what it is about to remove.

WHAT THE NEW LAYOUT CHANGES (WI-1118, delivered): an orphan is no longer invisible. ItemPerFileStore files a satellite in its item's file, so a row naming no item has nowhere to go; `LayoutFault::OrphanRow` reports it at every startup and via fsck, deliberately NON-blocking. Migration therefore carries pre-existing orphans into <root>/orphaned.anthill rather than refusing (refusing would lock out any tracker that had ever deleted an item with feedback). So the symptom is now loud -- but delete still creates new ones.

A THIRD OPTION WORTH WEIGHING against cascading: keep Feedback append-only and make `delete` REFUSE an item that still has satellites, naming them, with an explicit flag to proceed. That preserves the audit trail the monotone declaration exists for, and turns a silent leak into a decision the user makes. Whichever is chosen, say at the site which tests fail when it is backed out.

Acceptance: a test that DRIVES it -- add an item, attach feedback and a tag, delete, and assert on the store's actual rows (not just that delete exited 0). Under ItemPerFileStore additionally assert the item's file is gone rather than left holding stranded satellites, which is what `retracting a row leaves the item file standing` / `deleting an item strands its satellites loudly` currently pin.
