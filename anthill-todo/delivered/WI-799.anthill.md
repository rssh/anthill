## Description

TupleAlign (kb/typing.rs) names the SITE, not the discipline, and its ByName variant no longer aligns by name -- WI-788 made it a positional zip, and its own doc concedes the name is now 'about names PARTICIPATING, not about the correspondence being built from them'. A reader reaching for 'align by name' will pick it and get positional alignment. EVIDENCE THE NAMING MISLEADS: WI-788 shipped a comment claiming the two modes differ in EXACTLY ONE way (width); /code-review caught that there are TWO (width, and the synthetic _1.._n escape that ByName must NOT have -- granting it would relate (a: Int64, b: String) to (Int64, String), which 004 rule 4 forbids). FIX: replace the enum with a policy struct naming both axes, e.g. { width: Prefix|Exact, names: Exact|ExactOrSynthetic }, with DATA = {Prefix, Exact} and PARAM_LIST = {Exact, ExactOrSynthetic}. THIS ALSO UNBLOCKS A REAL DEFECT the two-mode enum cannot express: unify_named_tuple is an EQUALITY relation but takes the PREFIX-width mode, so unification of two named tuples is ASYMMETRIC -- unify((x: A, y: B), (x: A)) succeeds while the arguments swapped fail, and unification is used bidirectionally by the resolver. That is PRE-EXISTING (the old by-name arm was width-subtyping in the same direction) and is documented in place on unify_named_tuple, not fixed. 'Exact width, names exact' is the third discipline it wants. Found by /code-review on WI-788. ACCEPTANCE: the two axes are data, not variant names; unify_named_tuple takes exact width and the asymmetry is gone (or a measured reason it must stay is recorded); full workspace green via scripts/test.sh.
