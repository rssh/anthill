## Description

Proposal 056 — POSITIONAL variadic capture is a HALF-LANDED feature with a DOUBLE-BIND bug, not an unbuilt one. Split out of WI-1129 (which owns the rule-head rest-pattern face, §2.3); this ticket owns the positional half, the records, and the diagnostic.

MEASURED 2026-08-18 (probe `anthill-core/tests/include/wi1130_probe_test.rs`, temporary — delete before delivery):

  operation cap[R](...rest: R) -> R = rest
    cap(rest: 5)    -> Int(5)
    cap(a: 5).a     -> Int(5)
    cap(5)          -> LOAD ERROR:
                         type mismatch in cap.rest (op-arg): expected Int64, got ()
                         type mismatch in cap.rest (op-arg): expected a named argument matching a
                           distinct unbound parameter, got named argument 'rest' binds a parameter
                           already given

  operation cap[R](x: Int64, ...rest: R) -> R = rest
    cap(1, rest: 2) -> Int(2)
    cap(1, a: 2).a  -> Int(2)
    cap(1)          -> R = () — the empty capture, OQ #6. WORKS.
    cap(1, 2)       -> the same double-bind pair
    cap(1, 2, a: 3) -> `expected Int64, got (a: Int64)` + the same 'already given'
    cap(1, 2, 3)    -> the pair, PLUS the WI-1100 arity error ("expected 1 argument — the parameter
                       list declares, plus any named arguments the `...rest` capture collects, got 3")

THE MECHANISM, TRACED (not read). Read `expected Int64`: `R` was inferred FROM THE POSITIONAL ARGUMENT. So a positional leftover DOES bind the capture parameter directly — exactly as 056's status line and kernel-language.md §5.4 say — and then `normalize_variadic_capture` (rustland/anthill-core/src/kb/typing.rs) fires anyway and appends its own synthesized `rest: ()` / `rest: (a: Int64)`, giving one parameter a SECOND binding. Its already-normalized guard asks only "does a named argument name the capture parameter"; it never asks "is the capture slot already filled POSITIONALLY".

TWO CORRECTIONS TO THIS TICKET'S OWN EARLIER TEXT, both measured. (i) It ruled record (3) "FALSE as written — what binds directly is an argument that NAMES the capture parameter ... A positional one errors." Wrong about the mechanism: the positional one binds too, and is then clobbered. (ii) Its probe row `cap(1) -> Int(1)` does not reproduce — with body `= rest`, `cap(1)` yields `R = ()`.

DECISION (2026-08-18, with the user): FINISH WHAT THE SPEC ALREADY STATES — a positional leftover binds the capture parameter DIRECTLY, `R` the value's own type. NOT the `_N` reading of §3 OQ #2. Three reasons, in order of weight:
  * The `_N` reading would CREATE a divergence that does not exist today: `cap(5)` -> `(_1: 5)` while `cap(rest: 5)` -> `5`. Two spellings of one argument, two different values, both legal and silent.
  * It would falsify the records that are currently RIGHT (the status line, `normalize_variadic_capture`'s doc comment, kernel-language.md §5.4) in order to rescue the two that are wrong.
  * Zero clients want it. Every capture site in the tree is name-keyed: `fix` (stdlib/anthill/prelude/relation.anthill:361), `where_run`:228, `join_run`:285 — and where_run/join_run MINT their labels (`__anthill_row_param_N__`, WI-1127). WI-731 states its `rename` surface does not use the positional half. The sole consumer, `Without`, drops columns BY NAME, so a `_1` field naming no column is a load error in the reduction: every `_N` capture would be dead on arrival.
Refusing positional leftovers outright was also considered and rejected: the capture parameter IS a parameter occupying a position, so refusing would refuse a call the ordinary positional rule already binds.

SCOPE.
  (a) THE FIX: `normalize_variadic_capture` must not fold when the capture slot is already filled positionally. One clause on the existing guard.
  (b) THE MIXED CASE `cap(1, 2, a: 3)` — slot filled positionally AND a named leftover with nowhere to go — needs a LOCATED refusal naming the author's own argument (`a`) and why it cannot be placed. The synthesized capture record must never appear in a user-facing message. This is the WI-757 class: today the message reads `expected Int64, got (a: Int64)`, describing the rewrite rather than the source.
  (c) `cap(1, 2, 3)` — two positional leftovers, one slot. The WI-1100 arity error already words this well; keep it, and make it the ONLY error rather than one of three.
  (d) THE RECORDS. Under this decision exactly two are false and must be corrected: 056 §3 OQ #2 and §5, both of which claim a positional leftover lands in `R` as `_N` and that positional variadics are therefore "already subsumed". They are not: exactly ONE positional leftover is admitted (it binds the slot), and it EXCLUDES named leftovers. The other three — 056's status line, `normalize_variadic_capture`'s doc comment, and kernel-language.md §5.4 (~line 1802, the capture-parameter paragraph) — become true AS WRITTEN; verify them word by word rather than assuming, and drop the doc comment's "positional capture is a deferred follow-up" clause, since nothing is deferred. NOTE THE FIFTH RECORD the earlier scoping missed: kernel-language.md §5.4 states the same claim as the status line, and is what a reader consults first.

NOT IN SCOPE, left standing deliberately: the LABEL-keyed divergence. `cap(a: 5)` binds `rest` to the record `(a: Int64)` while `cap(rest: 5)` binds it to the bare `Int64` — whether a leftover's label happens to equal the capture parameter's name decides record-or-raw-value. That is the explicit-record guard, which also stops the fold re-firing on every re-type, and it stays.

ACCEPTANCE — DRIVEN, with controls and a stated back-out.
  * `cap(5)` and `cap(rest: 5)` both evaluate to 5 — assert the VALUE, and assert the two AGREE (that agreement is the decision).
  * `cap(1, 2)` against `cap[R](x: Int64, ...rest: R)` evaluates to 2.
  * `cap(1, 2, a: 3)` is refused by a message naming `a`; assert the text does NOT contain the synthesized record spelling.
  * `cap(1, 2, 3)` is refused by the arity error ALONE — assert the error COUNT is 1. That count is what pins the double-bind removal; it is 3 today.
  * CONTROLS, unchanged: `cap(a: 5).a` = 5, `cap(1, a: 2).a` = 2, `cap(rest: 5)` = 5; wi727_fix and wi1127_condition_param green (both ride the named capture).
  * BACK-OUT stated at the test site: name which rows go red when the guard clause is removed. THE TRAP: the empty-capture row (`cap(1)` -> `()`) passes BOTH ways — with no positional leftover the fold is already correct — so it measures nothing and must be labelled as such at the site. Same shape as WI-1129's degenerate capture row.
  * Delete the probe: `anthill-core/tests/include/wi1130_probe_test.rs` and its `mod` line in `anthill-core/tests/wi_tests.rs`.
  * cargo-test green via rustland/scripts/test.sh.
