## description

A DERIVED provision is REFUSED BY THE NEXT PHASE's provider-coverage check, so a KB that loaded clean cannot be loaded into again -- `load_stdlib` then `load_incremental` fails on WI-664's own derived `NonEq` rows.

MEASURED, at 51d17d22 (i.e. BEFORE WI-1098 -- this is WI-664's, not WI-1098's; the same
probe fails identically with WI-1098's whole source change stashed):

  let mut kb = KnowledgeBase::new();
  load::load_stdlib(&mut kb, &stdlib_and_rust_bindings, &NullResolver)   -- OK
  load::load_incremental(&mut kb, &[&any_user_file], &NullResolver)      -- FAILS:

    'anthill.reflect.Expr' provides 'anthill.prelude.NonEq' but backs no operation
     'anthill.prelude.NonEq.nonEqRefl' (no default on 'anthill.prelude.NonEq', no own
     'nonEqRefl' on 'anthill.reflect.Expr')
    ... and the same for anthill.reflect.TermRepr, anthill.reflect.LiteralRepr,
        anthill.geometry.EulerAngles, anthill.geometry.Vec3

Those five are EXACTLY the composites `eq_derive` classifies Partial and derives
`NonEq` for. The user file is irrelevant -- an empty namespace fails the same way.

THE MECHANISM IS THE PLACEMENT TRICK, AND IT IS SINGLE-PHASE ONLY. `eq_derive::run`
stands AFTER `check_provider_operations` precisely so a derived `NonEq`'s `nonEqRefl`
witness is not held to op-backing (it is a propagated classification, not a declared
primitive -- eq_derive.rs's module header states this as the reason for its position).
Within ONE phase that works. But the FACT persists in the KB, and every subsequent
`load_phase_inner` runs `check_provider_operations` again -- now with the derived rows
already in the relation, and this time the check reaches them BEFORE eq_derive re-runs.
So the dodge protects the row that is being created and not the row that already exists.

WHY THE SUITE IS GREEN: nearly every test builds a KB with ONE `load_all`. The
two-phase path is exercised by `incremental_load_test`, whose fixtures load
`stdlib_dir()` ALONE -- without `rustland/anthill-stl/anthill/`, so `Int64`/`String`
never provide `Eq`, so almost nothing classifies at all and the five carriers above are
not reached. That is the same "corpus cannot reach the bug" shape as WI-979.

TWO DIRECTIONS, and the choice is the work:
 (a) MARK a derived provision, and have the provider-coverage checks skip it. Honest --
     the checks are about what an AUTHOR claimed -- but `SortProvidesInfo` is
     deliberately byte-identical across every producer (load.rs `load_provides_conditions`
     records that four places hard-code its field list), so a third field is not free.
 (b) Make the checks phase-aware -- only check provisions asserted THIS phase. The
     loader already tracks per-phase `LoadResult.fact_rule_ids`, so the information
     exists; the question is whether "checked once, ever" is the right contract for a
     check whose premise (a backing operation) a later phase could remove.

ACCEPTANCE:
 - `load_stdlib` + `load_incremental` over the FULL closure (stdlib + anthill-stl,
   i.e. `common::collect_stdlib_and_rust_bindings`) loads clean, DRIVEN, with a
   user file that uses a derived-`NonEq` carrier so the classification is not vacuous;
 - `incremental_load_test`'s fixtures move to the full closure, or say at their site
   why the stdlib-alone corpus is the subject -- as written they cannot reach this;
 - CONTROL: a genuinely unbacked HAND-WRITTEN provision is still refused in phase 2,
   with the same message it gets in phase 1 (whichever direction is taken must not
   turn the check off);
 - say at each test site which tests fail when the change is backed out;
 - full workspace green via rustland/scripts/test.sh.
