## description

FINISH occ_head: every form whose TERM TWIN EXISTS must have a structural view. Two forms are still ViewHead::Opaque with a twin sitting right there (SetLit / TupleLit), and one MECHANISM turns a structural head into Opaque on a symbol lookup. CONTEXT: surfaced reviewing WI-815, which made GoalKey the fact-dedup key and so made occ_head's under-determination a soundness surface rather than a precision one. THE RULE THIS RESTORES IS THE FILE'S OWN, stated in term_view.rs's WI-814 note: "the view's whole contract is that it reads what the term twin reads ... a view that DISAGREES with its own twin is a cross-carrier miss, which is a WRONG ANSWER, not a precision loss" (WI-425). Today one source `{1}` gives Fn{anthill.reflect.SetLiteral, pos_args: [1]} on the term carrier and Opaque on the occurrence carrier -- the disagreement the rule forbids -- and because views_structurally_equal has NO (Opaque, Opaque) arm, a set literal is not even equal to ITSELF through the occurrence carrier. That is precisely the defect WI-814 fixed for Lambda.

WHY IT HAS NO OWNER: it is a SEAM BETWEEN TWO DELIVERED TICKETS, not a regression. WI-027 gave ListLiteral its term twin and occurrence-build and "deliberately left the siblings to keep scope tight". WI-559 (Delivered) closed that remainder -- SetLit/TupleLit got term twins (node_occurrence.rs try_occurrence_to_term, the WI-559 arms) and correct occurrence-builds. WI-814 (Delivered) built the VIEW side, for Lambda / If / Let / Match / Proof / all five Pattern variants, and its delivery note lists THREE known gaps EACH WITH AN OWNER (Let.type_annotation -> WI-819, Pattern::Tuple.labels -> WI-803, the *Within family -> WI-816). SetLit/TupleLit are in NEITHER list. Each ticket was complete against its own acceptance; nobody owns the intersection. ListLit is complete on BOTH sides today while its two siblings are complete on the TERM side only -- the same asymmetry WI-027 opened and WI-559 closed, still open one layer up. VERIFIED: WI-816 is strictly LambdaWithin/HoApplyWithin/ConstructorWithin; no other ticket names SetLit/TupleLit/SetLiteral for the view.

WHAT KEPT IT INVISIBLE, worth naming because it is the reusable lesson: the other three gaps got TICKET NUMBERS; this one got a JUSTIFICATION in the `_ => ViewHead::Opaque` comment -- "SetLit / TupleLit: path-B siblings of ListLit. That reads as a PRINCIPLED exclusion and is not one: WI-559 already fixed the functor, the child carrier and the labels ON THE TERM SIDE, so mirroring the twin is exactly what REMOVES the guessing. Inventing a key set would be guessing; nobody is proposing that. A reason in place of an owner is what kept it off every list.

PART A -- SetLit. Mechanical, no open question. The twin is occ_build_fn(kb, SetLiteral, elems, &[]) -- elements in pos_args, byte-identical in shape to ListLiteral. The view arm is a copy of the ListLit arm: functor_view_head(kb, f, es.len(), 0), with children from the same slice. fingerprint_into walks positional children in index order, so no ordering question arises at all.

PART B -- TupleLit, and THE ONE PLACE THE OLD COMMENT HAD A REAL POINT, misfiled. The head itself is equally mechanical -- functor_view_head(kb, f, positional.len(), named.len()), the twin being occ_build_fn(kb, TupleLiteral, positional, named). THE HAZARD IS NOT IN THE HEAD, IT IS IN fingerprint_into's SORT: it emits named args in `keys.sort_by_key(|s| s.index())` order, and justifies that with "a Term::Fn is sorted-by-name, an occurrence is a fixed slice, so sorting is what makes a Term and a Node agree". THAT PREMISE IS FALSE FOR THIS FUNCTOR, and that is the finding: TermStore::alloc does NOT canonicalize (it hash-conses the Term as given), and occ_build_fn does NOT call canonicalize_record_named_args -- so a TupleLiteral TERM PRESERVES SOURCE ORDER, while a sorted GoalKey does not. Since WI-788 makes tuple order IDENTITY (an ORDERED PRODUCT is the documented exemption from canonical named-arg sorting, rustland/CLAUDE.md), `(a: 1, b: 2)` and `(b: 2, a: 1)` are DIFFERENT tuples with DIFFERENT TermIds that would share ONE GoalKey. A naive mirror therefore trades "every tuple collapses" (today, Opaque is payload-free) for "order-variant tuples collapse" -- better, but still an over-dedup, and over-dedup DROPS an answer in seen_goals and DROPS A FACT in value_fact_dedup (WI-815). DECIDE, do not assume: either fingerprint_into stops sorting for ORDERED-PRODUCT functors (which needs a predicate naming them -- the same exemption canonicalize_record_named_args already encodes), or the tuple's order is carried some other way. CHECK WHETHER THE SAME HOLE IS ALREADY LIVE for Value::Tuple, which views as Functor{functor: None, ..} and whose named keys go through the same sort -- if so this is pre-existing and wider than TupleLit, and should be stated as such rather than introduced-and-blamed on this ticket.

PART C -- a structural head must not be CONTINGENT ON A SYMBOL LOOKUP. wrapped_expr_head / wrapped_expr_keys resolve the reflect qname with `kb.try_resolve_symbol(qname)?` and, on None, fall through to `_ => ViewHead::Opaque` -- documented as "fail-soft, as such a KB holds no loader-built occurrence of it". Same invariant, opposite policy, and they cannot both be right: if the invariant holds the `?` arm is dead code that DEGRADES instead of erroring; if it does not, the panic fires one layer down anyway. Degrading is the worse half -- Opaque is PAYLOAD-FREE, so it does not lose precision, it makes two structurally DIFFERENT ifs compare EQUAL and share a GoalKey, converting "reflect not loaded" into wrong answers rather than an error. (3) views_structurally_equal starts answering TRUE for two identical set literals, where it answered FALSE even for a literal against itself.

CONSEQUENCE FOR WI-815, do this as part of the change: wi815_a_lossy_key_degrades_to_no_dedup (kb/mod.rs) uses Expr::SetLit as its GENUINELY-OPAQUE subject, via the wi815_head(functor, n, opaque) builder.
