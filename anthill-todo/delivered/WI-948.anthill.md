## Description

RUSTLAND'S `parse_equation_lhs` DECIDES 'IS THIS HEAD AN EQUATION?' FROM THE FUNCTOR NAME, not from the WI-618 `minted` provenance that exists to replace exactly that kind of re-derivation. FOUND 2026-08-03 porting the pass-3 rule-introduced-functor scan to scaland, whose twin was fixed in the port; the rust side is untouched and is the reason this is a ticket. TODAY (rustland/anthill-core/src/parse/convert.rs, `parse_equation_lhs`): a body-less single-head rule is read as an EQUATION when the head is a 2-ary `Term::Fn` whose functor name satisfies `pratt::is_equation_functor` (eq / unify / struct_eq). Nothing checks that the node was BUILT by the infix desugar. CONSEQUENCE, two directions, both silent: (1) `rule eq(?a, ?b)` — a legitimate 2-ary PREDICATE head written as an ordinary call — is misread as an equation, its 'LHS' is the variable `?a`, `rule_introduced_functor_name` falls through its `Term::Fn` match to `None`, and NO symbol is introduced for `eq/2`; a later `import ns::{eq}` of it then fails and every reference falls back to a bare interned name. (2) `rule struct_eq(f(?x), g(?x))` written as a call introduces `f` stamped `SymbolKind::EquationFunctor` instead of `Goal` — WI-898's distinction inverted for that rule. FIX: guard the equation reading on `parse_terms.is_minted(head)` — the store already carries the mark (pratt.rs:176 marks every infix desugar) and the same function calls `is_minted` two lines later on the SUBJECT, so this is one condition, not new machinery. `SimpleTermStore::minted`'s own doc comment states the principle being violated: provenance is carried, not re-derived from a name. Scaland's `Loader.parseEquationLhs` already has the guard and a test (`WI-618: a written eq(?a, ?b) head is a predicate, not an equation`) — port both. ACCEPTANCE: the two directions above as tests that FAIL on today's rustland.
