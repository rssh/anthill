## Description

A PARAMETER AN OPERATION MERELY ACCEPTS CANNOT BE TOLD FROM ONE IT RECEIVES ON — the residue of WI-1076, and it needs surface syntax.

`spec_carrier_param` (kb/typing.rs, WI-1076) identifies a spec's carrier parameter
as the first declared type parameter some declared operation TAKES AS A PARAMETER.
"Takes" is WIDER than "receives on", which is what should decide. All seven of
WI-1076's mis-filed stdlib provisions are now closed — six by that predicate and
the seventh by repairing a DECLARATION (see below) — so what remains is a shape
the corpus does not currently contain but a user can write today:

  (1) A SPEC THAT ACCEPTS ITS OWN ELEMENT.
      `Set.insert(s: Set, x: T)` and `Map.put(m: Map, key: K, value: V)` receive on
      the sort and also take the element, so `T` / `K` answers as the carrier
      parameter. A user writing `sort IntSet provides Set[T = Int64]` gets the
      provision filed at `Int64` and no inferred default row. No stdlib provision of
      either exists, so nothing measures it today.

THE SEVENTH ROW WAS A BUG IN THE DECLARATION, NOT A LIMIT OF THE PREDICATE, and
that is the repair to prefer wherever it applies. `LogicalStream.pure` read
`pure(x: T) -> LogicalStream`, reusing the SORT's element parameter for a value it
merely lifts. As `pure[A](x: A) -> LogicalStream[A, {}]` the question stops being
asked and `Relation provides LogicalStream` reads its provider. The bare return was
independently lossy: it expands to `LogicalStream[T = ?, E = ?]` with a FRESH
variable, so lifting an `Int64` into a `String`-element stream LOADED CLEAN
(measured; pinned by `pures_own_type_parameter_threads_its_argument_type`).

IT WAS WRONG FROM THE FIRST DAY, and the vintage is not the excuse it looks like.
`pure` was written 2026-02-23 (`9e6b81c1`) and the first OPERATION type parameter
landed 2026-06-10 (WI-424), but a shared LOGICAL VARIABLE said the same thing and
needed nothing new: `pure(x: ?A) -> LogicalStream[?A, {}]` type-checks today
(measured — same refusal as the bracket form), and the neighbouring `mplus(a:
LogicalStream{T = ?A}, b: LogicalStream{T = ?A})` was written that way IN THE SAME
COMMIT, two lines below. Types are terms and they unify, so operation-level
polymorphism was always expressible; `pure` reached for the sort's parameter
instead. An audit under this ticket should therefore look for the SHAPE, not for
declarations of a certain age.

A NULLARY PRODUCER IS A DIFFERENT CASE AND LOOKS CORRECT AS WRITTEN. `empty()` has
no argument to relate its result to, so a fresh variable per use IS the polymorphism
and no parameter is wanted. MEASURED: `List.empty() -> List` (bare, hence
`List[T = ?]`) loads into `List[T = Int64]` and `List[T = String]` in one program.
`LogicalStream.empty() -> LogicalStream[?A]` is the same spelling class (§5.6: a
bare reference, a partial application and an explicit `?` all leave the slot to the
body; an OPERATION type parameter is the CALLER's to instantiate and is the loud
`got unconstrained` when a call pins it from nothing — which a bare `empty[A]()`
would be). So `empty` should NOT gain a bracket parameter, and `mplus`'s shared
`?A` is already the right idiom. The stdlib nevertheless spells `empty` five ways
— `-> List`, `-> Set`, `-> Map`, `-> LogicalStream[?A]`, `-> C`, `-> SortedSet[T =
T, O = O]` — and only the last has `pure`'s shape (a member typed at the SORT's own
parameters); that one is worth checking.

NOT MEASURED, and worth settling here: whether `List[Nothing]` + covariance is the
intended alternative to fresh-per-use. Both mechanisms exist — `Nothing` is the
declared bottom sort and `fact Covariant(sort: List, param: T)` is asserted in
reflect/typing.anthill — but `empty` uses unification, not subsumption. In a
term-unification setting fresh-per-use needs no variance machinery at all, which is
an argument for keeping it; the question is whether the two can disagree anywhere.

  (2) CARRIER-PARAMETERIZED SPEC DECLARING ITS ELEMENT FIRST AND ACCEPTING IT.
      BoxHolder | Holder | Int64          <- explicit `C = Box` DISCARDED
      `sort Holder { sort Element = ?; sort C = ?; operation peek(c: C); operation
      has(c: C, e: Element) }` — `has` accepts `Element`, which is declared first, so
      `Element` answers and the written `C = Box` binding is thrown away. Not a
      regression (the old positional read answered the same), but it is why WI-1076's
      "declaration order retires the positional assumption" holds only while no
      operation takes the earlier parameter.
      Pinned: `an_accepted_element_declared_first_still_wins_over_the_carrier_param`.

WHY THE OBVIOUS FIXES WERE MEASURED AND REJECTED (WI-1076 tried both):

  * `spec_is_self_representing` (WI-614) — "does any operation take the SORT
    itself" — closes (1), and REFUSES A PROGRAM THAT LOADS. A spec may declare BOTH
    a carrier parameter and a self-receiving operation; gating on
    self-representation discards its explicit `C = Box` binding and the load fails
    with a `requires Holder[Element = …]` mismatch. Fixture:
    `a_spec_with_both_a_carrier_param_and_a_self_receiver_keeps_its_binding`.
  * "the op does not RETURN the spec sort" (producer vs observer) separates `pure`
    from `peek` on today's corpus but misclassifies a plausible `operation add(c: C,
    x: Int64) -> Coll` as having no carrier — the UNSAFE direction, since a false
    no-carrier verdict throws a written binding away while a false carrier verdict
    merely leaves a provision where it was.

The sound discriminator already exists and cannot be used here: eval's
`carrier_param_receiver_for_values` gates on `provision_binds_param_to_carrier` —
"does the value's carrier provide the spec with THAT param bound to the carrier" —
which is provision-relative, so asking it inside `provision_carrier_binding` is
circular, and asking it across provisions makes the answer depend on which
provisions happen to exist.

WHAT MUST BE DECIDED, and it is a LANGUAGE question, which is why this is a ticket
and not an inline fix: nothing in the surface says which parameter is a spec's
carrier (059's fact-ban section: no `spec` keyword, no `SymbolKind::Spec`; the
kernel infers spec-hood from shape everywhere). Options, smallest first:

  (a) mark the carrier parameter in the declaration (`sort C = ? carrier`, or a
      `self` convention) — makes the illegal state unrepresentable and gives
      `spec_carrier_param` a declaration to read instead of a heuristic;
  (b) declare spec-hood (`spec Iterable … end`) and derive the carrier from it;
  (c) leave it inferred and accept the residue, documenting the rule as
      "a parameter no operation takes is not a carrier" — which is what ships today.

(a) and (b) are grammar + loader + spec changes and would let every shape reader in
kb/typing.rs stop guessing — `spec_is_self_representing`, `spec_carrier_param`,
`self_receiver_param_index` and `carrier_param_receiver` are four inferences of one
undeclared fact.

ACCEPTANCE: the chosen option is recorded in kernel-language §5.1 (which carries
this ticket number at the gap) and in 058 §3.6; both pinned rows above are
re-measured and updated; `self_provides(Relation, LogicalStream)` holds; the
mixed-shape and witness controls in `wi1076_self_representing_spec_carrier_test`
still pass UNCHANGED — they are what the rejected predicates broke; each test says
which case fails when the change is backed out. cargo-test green via
rustland/scripts/test.sh.

REFERENCE: WI-1076 (closed six of seven; measured and rejected both alternatives),
WI-1069 (settled what a provides clause's bindings mean), WI-614
(`spec_is_self_representing`), WI-424 (`provision_binds_param_to_carrier`, the
sound but provision-relative gate), WI-860, proposal 058 §3.6, kernel-language §5.1.

WHAT THE WI-1079 DEPENDENCY DOES AND DOES NOT GIVE THIS TICKET — correcting a claim made when the edge was added. The dependency was recorded on the reasoning that "a bounded binder is WI-1077's vehicle". That was too strong, and the grammar refutes it: `operation_type_param` is `seq(field('name', identifier), optional(seq('=', field('default', _type))))` where the `= default` arm is parsed ONLY to give a good diagnostic (WI-850 refuses it; kernel-language §5.4 says `TypeParam ::= Name`), and `sort_type_param`'s optional list is the HIGHER-KINDED member list `F[T, …]`, not a bound. So NO binder form in the language carries a bound, and WI-1079 does not add one.

BOUNDS EXIST ONLY AT SORT LEVEL and are ALREADY REFLECTED: a sort's `requires Eq[T]` (and the `effects E` desugaring `sort E = ? requires EffectsRuntime[Effects = E]`) is a separate clause emitted as `SortRequiresInfo`. Nothing to add there either.

SO THIS TICKET'S OPTIONS (a) AND (b) STILL REQUIRE NEW SURFACE — `sort C = ? carrier`, or a `spec` keyword. WI-1079 does not deliver the marker; what it delivers is the type-form layer (`PolyType(binders, body)` as a `TypeExtractor` variant, plus `Skolem` / `FlexVar`) that such a marker would be reflected THROUGH. The dependency stands for that weaker reason, and it is a real one: today a declared type PARAMETER reads in reflect as `SortRef(T)`, indistinguishable from a concrete sort — which is precisely the conflation that produced WI-1076's defect (`provision_carrier_binding` filters the binding's base on `SymbolKind::Sort`, and a type parameter PASSES that filter, so `List provides Stream[T]` filed its carrier at `T`). A carrier marker attached to a binder the reflect layer cannot tell from a sort would inherit that same confusion.

ALSO: the residue this ticket owns is unchanged in SHAPE but smaller in POPULATION. `LogicalStream.pure` was fixed at the DECLARATION (commit d26bced5) rather than by widening `spec_carrier_param`, which is the repair to prefer wherever a spec reuses its own type parameter by accident. What remains is the INTENDED reuse — `Set.insert(s: Set, x: T)`, `Map.put(m: Map, key: K, value: V)` — plus the element-declared-first face pinned by `an_accepted_element_declared_first_still_wins_over_the_carrier_param`.
