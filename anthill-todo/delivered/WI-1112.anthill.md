## description

PERF: `SortRequiresInfo` IS THE ONE REFLECT RELATION WITH NO INDEX, AND ITS SCAN IS THE LARGEST SINGLE COST IN A LOAD — 83 ms of ~1100 ms, 2917 scans per load.

MEASURED, not suspected (WI-1111 review, 2026-08-16). Instrumenting a stdlib load with counters/timers around the requires-chain builder gives, per load:

  direct_requires calls=2917  total=97.2 ms
    collect_sort_requires  = 83.4 ms   (86 % of it)   <-- the `requires` half
    self_supplied_entries  = 12.4 ms   (13 %)         <-- WI-1110's addition
  provision_is_conversion calls=4919
  supplies_any_operation_of calls=62, 0.4 ms

`collect_sort_requires` (kb/typing.rs) does `kb.rules_by_functor(requires_sym)` — a FULL SCAN of every `SortRequiresInfo` fact in the KB — and then filters by `sort_ref == sort_sym`. It is called once per `direct_requires`, and `direct_requires` runs 2917 times per load (the requires-TREE recursion reaches it per node, so the per-sort memoization on `requires_chain_cache` does not cover it).

THE ASYMMETRY IS THE FIX. Every sibling reflect relation already has a `SymbolKeyedFactIndex` on the KB — `provides_index` (by carrier AND by spec base, WI-660/WI-672), `sort_info_index`, `sort_alias_index` — and `SortRequiresInfo` has none. `self_supplied_entries`, added by WI-1110 and doing the same job on the provides side, costs 12 ms BECAUSE it goes through `provides_rids_by_carrier`. The requires side doing the same work costs 83 ms because it does not. `provides_index`' own doc records that the scanning form took a stdlib load from 0.10 s to 0.18 s — an 80 % regression — which is the same measurement from the other side.

SCOPE: add `requires_index: Option<SymbolKeyedFactIndex>` keyed by canonical `sort_ref`, built and dropped at the same points `provides_index` is, and route `collect_sort_requires` through a `requires_rids_by_sort` helper mirroring `provides_rids_by_carrier` (including its `rids_or_scan` fallback, so a KB with no index still answers).

THE HAZARD IS A STALE INDEX, AND IT IS THE REASON THIS IS ITS OWN TICKET RATHER THAN AN INLINE TWEAK. A missed `SortRequiresInfo` fact is not a slow answer, it is a MISSING REQUIREMENT — a dictionary slot that silently stops existing, so a program that should be refused loads clean and dies at eval. That is WI-954's measured failure mode ("a stale index answers EMPTY"), and `SortRequiresInfo` is REASSERTED during load (`resolve_requires_bindings` finalizes the facts; `mark_requires_finalized` exists for exactly that), so the build points need auditing against every producer rather than copied from `provides_index` by shape. `invalidate_requires_chain_cache` already marks where the relation is known to change; the index must be dropped at least there.

ACCEPTANCE:
 * `collect_sort_requires` no longer scans when the index is live — MEASURED by the same in-process instrument (min-of-K over repeated loads in ONE process, first dropped as warmup; a shell-sampled `anthill check` spans 34x on one binary and cannot see a 10 % change).
 * every producer of a `SortRequiresInfo` fact either runs before the build point or drops the index — enumerated in the ticket's delivery note, not assumed, and each named with its site.
 * a driven fixture that would LOSE a requirement under a stale index: assert a `SortRequiresInfo` fact after the index is built and show the requirement is still found (the WI-954 shape).
 * full workspace green.

REFERENCE: WI-1111's review (where it was measured); `provides_index` / `SymbolKeyedFactIndex` / `rids_or_scan` (kb/typing.rs) for the shape to mirror; WI-660/WI-672 for the provides-side history; WI-954 for the stale-index failure mode.
