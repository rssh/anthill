WHY THE RESTRICTION IS NOT PRINCIPLED (the question this ticket answers). It is ENFORCEMENT COVERAGE, not semantics. Written in exactly two places: load.rs:11918-11924 (comment) + load.rs:11934-11941 (the error), and docs/design/constrained-term-substrate.md:389 "*Enforcement scope (deliberate):* the bound is enforced **only** where it can be". "Deliberate" is NARROW — it means "we chose loud-error over silently-ignored", NOT "relational typed heads are meaningless"; and "where it CAN be" means WHERE THE CODE EXISTS: `typed_pattern_bounds_hold` has exactly ONE call site, resolve.rs:2991, inside `apply_eq_rules`. THE SAME DOC SAYS THE OPPOSITE ABOUT MEANING (:310): "A **non-operation head** (a bare relation with no executable twin) is typed the **same way** — same conventions, same owed-on-consumption, same carried-type firing. Op-head vs non-op-head is **not a typing distinction**." TWO CORROBORATIONS: (i) the TYPER cannot enforce the bound either (its match keys by fresh globals, not the synthetic-DeBruijn entries the check reads), so simp_rewrite.rs:499 SKIPS typed rules ENTIRELY — enforcement is PARTIAL even inside the blessed `[simp]` path, and the doc files that as a "follow-on", which a principle would not tolerate. (ii) The M1 steelman ("SLD matching must stay type-blind — structural matching never branches on a type, else regress") CUTS THE OTHER WAY: the doc's desugaring (:325) is `head(…, ?x, …) :- conforms(typeof(?x), T), body` — an ordinary SLD goal over the sort lattice + instance facts, so "the engine sees one more goal, never a type". The RELATIONAL case is the one that fits M1 MOST naturally (no fold-into-matching at all); the EQUATIONAL case is the one that NEEDED the clever constraint+wakeup machinery, because a rewrite fires by MATCHING, not by running a body. The restriction has the difficulty exactly BACKWARDS relative to meaning.

WHY 052 WANTS IT (not merely permits). `relation_clause_columns` (typing.rs:3822) ALREADY reads `rule_type_bounds` FIRST (:3838) — explicit bound, else `collect_rule_var_types` inference, else a fresh var (an unconstrained column). The typing half is BUILT AND WIRED; it never receives a bound only because the loader rejects it two steps earlier. Today the SOLE way to type a 052 column is to launder it through an entity FIELD — which is why examples/classic-mini/map-colouring carries a `Palette` wrapper sort it should not need; its own comment admits it (colouring.anthill:29-31): "an entity field (`c: Colour`) is what tells the typer a column is a Colour, which is why the palette is an entity + facts rather than a rule". SOUNDNESS — the original ticket's "NOT a soundness bug in the resolver" is WRONG under 052: the annotation becomes LOAD-BEARING FOR THE CONSUMER'S TYPE. `Relation[(wa: Colour)]` is a claim the row-destructurer relies on; a declared-but-unenforced bound = the typer asserting what the resolver never checked, because a rule subgoal constrains nothing (WI-079). That is worse than a silent skip, and it is why enforcement (not merely recording) is in scope.

HOW IT COMPILES.
  rule f(?x: T, ?y) :- body
    HEAD   f(?x, ?y)                            -- stripped; structurally bare so discrim indexes it identically. EXISTS (WI-582)
    BOUND  install_rule_type_bounds(db(?x), T)  -- EXISTS (kb/mod.rs:3766)
    BODY   domain(?x, T), body                  -- NEW: the only new machinery
    SCHEMA relation_clause_columns → column T   -- EXISTS (typing.rs:3838)
`domain(?x, T)` is MODE-DIRECTED: (in) `?x` BOUND → the three-valued conformance test on its CARRIED type (WI-578 value_type_term): holds → keep; refuted → fail this binding; under-determined → SUSPEND, never NAF-decide an undecided guard (WI-067). (out) `?x` UNBOUND → DELAY + rotate, re-asked once a later goal binds it; still-unbound at the end → flounder LOUDLY via the WI-737 route (`Error[RelationFloundered]`), never presented as a definite row. THE KEY CONSEQUENCE: because the goal actually RUNS, the guard reading and the declaration reading MEET — the declared schema is true BY CONSTRUCTION (the relation only ever yields conforming rows) rather than a typer assertion WI-079 cannot back. That is precisely a CLP(FD) domain, and it is what makes the 052 column type honest WITHOUT waiting on WI-079. Prepend (not append): rotation delays it to where it can decide in mode (out) anyway, while mode (in) prunes earliest.

PROBLEMS / COSTS (honest).
  (1) `conforms`/`typeof` ARE NOT GOALS TODAY — verified: no `conforms` / `subsort` / `provides` builtin in resolve.rs. The doc's desugaring is MEANING, not code. A NEW DELAYABLE BUILTIN is the actual work, and it must be classified against WI-739's REORDERABILITY rule (a builtin that must not be reordered may not delay on a caller var; `neq` is the precedent — it suspends and rotation re-asks it, so `domain` sits on the same side).
  (2) TWO ROUTES, ONE SYNTAX: equational + `[simp]`/`[unfold]` KEEPS the match-time wakeup (`typed_pattern_bounds_hold` at apply_eq_rules); relational gets the goal. The doc already anticipates the split (:352-355 — the body-guard form "is the fallback for a guard that spans several variables"). An UNTAGGED equational head keeps today's loud rejection (no body to prepend to, no wakeup site).
  (3) MULTI-CLAUSE LUB falls out of 052's existing rule, no new machinery: a clause declaring `?x: Colour` against a sibling inferring `Int64` is disjoint → LOAD ERROR, never a silent widening to Term (052 §"The schema T"; WI-287 join).
  (4) A `[simp]`-tagged RELATIONAL head — decide and state it (probably: the tag is meaningless on a `:-` head; today it is what the guard demands, which is backwards).

ACCEPTANCE: `rule f(?x: T, ?y) :- body` on a RELATIONAL head LOADS with no WI-582 error and its column types as T (`Relation[(x: T, …)]`, via the already-wired relation_clause_columns path); a body goal binding `?x` to a non-T value FILTERS that solution rather than yielding it (the schema is true by construction); an UNBOUND `?x` DELAYS and is re-asked after a later goal binds it (`rule f(?x: String) :- eq(?x, "abe")` MUST work and yield one row); a still-unbound `?x` at the end FLOUNDERS loudly (WI-737 route), never a silent non-check; a nonexistent sort in that position stays a loud `unresolved name` (it already is); the existing WI-582 `[simp]`/`[unfold]` equational path is UNCHANGED (wi582_typed_rule_pattern_test green); cargo-test green via scripts/test.sh. NOTE the map-colouring `Palette` wrapper is NOT retired by this ticket — the facts still GENERATE; only the column TYPE stops depending on the entity field.
