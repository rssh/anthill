## description

scaland Bootstrap emits an eponymous single-constructor sort as 'enum X: case X(...)' + a separate 'XOps' trait -- the nested X.X that WI-926 forbids.

MEASURED (2026-08-02, delivering WI-935). scaland Bootstrap.generate on the new stdlib/anthill/geometry.anthill emits, for 'sort Vec3 { entity Vec3(x,y,z); operation vec_add(...) = ... ... }':

  package anthill.geometry

  enum Vec3:
    case Vec3(x: Double, y: Double, z: Double)

  trait Vec3Ops:
    def vecAdd(a: Vec3, b: Vec3): Vec3
    def vecSub(a: Vec3, b: Vec3): Vec3
    def vecScale(c: Double, v: Vec3): Vec3
    def vecZero(): Vec3

Two defects in one output. (1) 'enum Vec3: case Vec3(...)' is exactly the nested 'Vec3.Vec3' that docs/kernel-language.md 6.3 / WI-926 rule out -- an eponymous constructor IS its sort, ONE symbol, and the correct emission is a single 'case class Vec3(x: Double, y: Double, z: Double)'. (2) the members are split into a SEPARATE 'Vec3Ops' trait, so the type a consumer holds and the operations on it are two declarations rather than one.

THIS IS THE SAME DEFECT WI-931 FIXED ON THE RUST SIDE, in the other backend. cpp-gen emitted 'struct Vec3' TWICE for this shape (a C++ redefinition error) because classify_namespace built a data band from the entity-field registry and a traits band from OperationInfo parents, and one symbol satisfied both. The fix was at classify_namespace (the three bands are DISJOINT by contract) plus emit_entity_struct_by_symbol (one symbol, one struct). cpp-gen now emits fields THEN operations in one struct -- pinned by rustland/anthill-cpp-gen/tests/wi931_eponymous_struct_test.rs and, since WI-935, by lf1_test::lf1_vec3_and_euler_emit_correctly against the real stdlib Vec3. scaland's Bootstrap has the same band split and has NOT had that fix.

PRE-EXISTING, SURFACED NOW. It is not caused by WI-935. It went unexercised because the tree shipped no stdlib sort of this shape -- WI-931's own fixture comment says so ('the tree currently ships no sort of this shape, and a rule with no example is exactly the one that rots'). WI-935 made Vec3 the first one, which is what exposed it.

WHAT WI-935 DID INSTEAD, so this is not silently encoded as correct: BootstrapTest 'WI-170: standalone entity -> case class' was RE-POINTED from Vec3 to EulerAngles (still a standalone entity, so the test still measures the claim in its name). Vec3's current output is deliberately NOT asserted anywhere -- pinning it would make the bug the contract. scaland core is at its pre-WI-935 baseline (8 failed / 232 passed, all 8 pre-existing: ParseTest:931 plus seven downstream of the cpp_std parse error).

ACCEPTANCE: Bootstrap emits ONE declaration for an eponymous single-constructor sort -- a 'case class' carrying the fields, with the operations on it (companion or trait-on-the-same-name, whichever matches scala-forward-mapping) -- driven by a test that generates from the real stdlib geometry and asserts the absence of 'enum Vec3' AND the presence of the case class. A CONTROL that a NON-eponymous multi-constructor sort still emits an enum, and that a plain standalone entity is unchanged. sbt test at or below the current baseline.

SOURCE: measured while delivering WI-935.

EPONYMY IS KEYED ON THE ANTHILL NAME, and that is load-bearing rather than pedantic. `Names.scalaTypeName` is MANY-TO-ONE, and stdlib already contains the near-miss: `enum anthill.prelude.Pair { entity pair(fst: A, snd: B) }` -- the constructor is `pair`, the sort `Pair`, and both PascalCase to `Pair`. Comparing the EMITTED names would have collapsed Pair into a case class and broken a delivered test; comparing the written names keeps it a Sum, which is what §6.3 says ("keyed on the name matching"). The classifier checks "any eponymous constructor" BEFORE "exactly one constructor" for the same reason -- reversing those two lines is what makes Pair the wrong shape.

DEFECT (2) OF THE TICKET IS ANSWERED BY A SCALA LIMIT, NOT IMPLEMENTED. The ticket asks for the operations "on it", citing cpp-gen putting an eponymous sort's fields AND operations in one `struct` (WI-931). That collapse has NO Scala analogue: a C++ member function DECLARATION needs no definition, while Scala has no abstract member in an instantiable `case class`, and bootstrap emits signatures only (bodies are the KB-driven gen's, proposal 034). So the members stay on the `<Sort>Ops` contract §2.3 already uses for EVERY sort with constructors -- a uniform mapping rule, not a carve-out for eponymous sorts. What §6.3 buys in Scala is that the TYPE is one declaration. docs/kernel-language.md §6.3 said "the fields and operations belong to one type in every backend", which over-claimed; it now states that what every backend owes is one declaration OF THE SORT'S OWN NAME, and that a differently-named companion is not the forbidden shape.

BEYOND THE TICKET -- THE INVARIANT IS NOW TOTAL. §6.3 also admits an eponymous variant ALONGSIDE siblings (WI-946), and Scala has no spelling for that at all: the sum and one of its cases would have to be one name in one scope. That is REFUSED (`BootstrapError`, located) rather than emitted as `enum S: case S`, which would be the nested S.S in a second guise. So after this change no Bootstrap path can emit a nested X.X -- a stronger claim than "the single-constructor case is fixed".
