## Description

anthill-todo backend, INCREMENT 2c of WI-437: ALLOCATION IS A POLICY, and ContentHash is the local one. Design: backend-github-coordination.md §3.2 (config split), §6.5 (the policy), §12 (the two open lengths), §14 row 2c. Closes the SECOND half of the §1 driver -- id collisions -- with NO NETWORK, after WI-1114 closed the first (textual conflicts) with file-per-item. Together they mean WI-437's shipping value needs no GitHub at all.

THE IDEA. The forge had two FUSED roles: allocator (§6.1 stake-by-creation) and mirror (§7). They are independent. Split them, make allocation a POLICY on the ExtentBinding.store precedent (a Term naming a thing to BUILD, resolved by the host to a compiled-in implementation), and the local policy needs no coordination at all: mint the id from the item's own author, created timestamp and description.

THE ID HAS THREE PARTS, EACH DOING A DIFFERENT JOB:
  WI-20260817-a3f9c-item-per-file-store
     |time  | |hash| |slug                |
  time  ORDERS -- lexicographic sort is chronological, so ls / a sorted depends_on / plain sort all read in order with no comparator that knows anything. This is the ONLY valuable property of WI-NNN (it is monotone, not that it is short), and putting time first is what gives it back.
  hash  IDENTIFIES -- and is the ONLY part carrying identity. The other two are renderings, so adding or changing a rendering can never make two items collide.
  slug  DESCRIBES -- frozen at creation, decorative, MAY BE ABSENT. It is what makes a file-per-item tree browsable: ls open/ under a bare hash is 125 lines of noise, with slugs it is a table of contents. Answers the browsability objection §12 raised against the directory-per-item variant, for free. Also restores sayability ("the item-per-file-store one").

REFERENCE GRAMMAR -- ONE RESOLUTION LADDER, ANY FRAGMENT. WI- stays the reference MARKER; everything after it is a resolvable fragment. Accept: hash prefix (WI-a3f9c), time-hash (WI-20260817-a3f9c), slug or slug prefix (WI-item-per-file-store), full id. Ambiguity is REPORTED with candidates, never resolved by precedence -- a slug is NOT unique (two items may both be fix-flaky-test) and neither is a short hash prefix forever, so one mechanism handles both. The marker matters most IN PROSE: feedback text cites other items constantly, and a bare item-per-file-store in a sentence is a phrase, not a citation; keeping WI- means references stay greppable and linkifiable exactly as WI-1114 is today.

WHAT THE PROPERTY ACTUALLY IS, because the name oversells it: MINTED LOCALLY WITHOUT COORDINATION. NOT verifiability -- the hash input is the description AT CREATION, and descriptions here are edited for months (WI-1114's own was corrected by an amendment days after filing), so the input is not preserved and the id cannot be recomputed later. The id is OPAQUE: a minting rule, not an integrity check. Do not build a does-the-hash-still-match check; it is guaranteed to rot. The one thing hashing gives over plain entropy is IDEMPOTENCE -- a retried add re-derives the same id and heals instead of creating a second item -- plus it needs no entropy source, so alloc_id loses its External row and becomes a pure function of values the bundle already holds.

WORK. (1) Coordination(allocation: Term, forge: Option[T = Term], access: ForgeAccess) -- ONE forge field, not one per role, or a StakeByCreation project names its forge twice, which is the two-writable-homes failure §7's principle exists to prevent. Entities ContentHash / StakeByCreation. LOUD load check: StakeByCreation with forge: none has nothing to allocate against and is refused naming both fields; ContentHash with a forge is the ordinary mirrored config, not an error. (2) A `created` field on WorkItem -- A REAL PREREQUISITE, not a nicety: the entity has none today (status carries since/at for some variants, Open carries nothing), so there is no timestamp to hash AND nothing for list to sort by once ids stop ascending. The chronological order the tracker shows today is an ACCIDENT of dense ids. (3) The minting rule + slug rule, total and deterministic: lowercase, keep [a-z0-9], collapse other runs to a single -, cut at a word boundary near 30 chars, drop trailing -. AN EMPTY SLUG IS LEGAL AND THEN OMITTED -- a description that is entirely non-ASCII (this project writes Ukrainian) or entirely punctuation must still yield an id, so the slug can never be load-bearing. (4) The resolution ladder, in the CLI arg path and reusable by anything that linkifies prose. (5) Delete the counter seed in main.rs (it parses WI-NNN digits) and the id_counter parameter of FileBasedWorkitemStore.open, which WI-1114 just added.

GRANDFATHERED, NEVER RENUMBERED. WI-1114 appears in 4700+ feedback texts, commit messages, branch names, conversations. Renumbering the 1110 existing items breaks every one of those to buy nothing. Two id shapes coexist permanently; every site reading an id must stay shape-agnostic. It already is -- the id is a String and WI-1114's check_segment cares only that it names one path component -- EXCEPT the counter seed, which item (5) deletes.

COLLISIONS are possible, bounded and LOUD: two different items collide only if one author writes two different descriptions in the same second that also hash alike in the chosen width (birthday bound ~0.2% at 5 hex on a heavy 64-item day). Reached, it is exactly the state LayoutFault::DuplicateId already names (§10, delivered WI-1114), and add refuses rather than overwriting.

WHAT THIS DELETES ELSEWHERE: §6.1's retry loop, §6.2's External row on alloc_id, §6.3's failure taxonomy, §6.4's provisional ids AND their reconciliation (the rename plus depends_on rewrite, the fiddliest machinery in the doc), §6.4's honest-cost note about references escaping before they are permanent (there is no before), §10's dangling-allocation check, §8.3's counter seeding. Three of §8.3's five substitution-contract points serve allocation only; a mirror-only forge needs the other two. And access: disabled() then degrades NOTHING (today it degrades add to a provisional id) -- the forge becomes a pure publishing channel and the null forge a first-class configuration rather than a test fixture.

TIMING -- THIS IS WHY IT IS FILED NOW. The tracker migrates EXACTLY ONCE (§11, §14.1). Ids are part of what it migrates into, the same argument that put WI-1120 (file format) ahead of WI-1118. Deciding after the migration means migrating twice. So WI-1118 gains an edge on this.

STILL OPEN (§12), both cheap to decide and expensive to change afterwards: the hash width and the slug width -- render a real list at two or three settings and look at it. And whether StakeByCreation is worth building at all once this lands (§12): it is strictly more machinery for a dense ordered sequence nothing requires; the one thing it offers that no local policy can is a registry visible to a STALE CHECKOUT. Answer that after living on ContentHash, not before -- and deleting it later is easy precisely because allocation is now a policy.

DESIGN SETTLED 2026-08-17, after working the numbers. Seven changes to what this ticket was filed with; the design doc (§6.5, new §6.6, §10, §11, §12) is authoritative and this summarises the deltas.

1. CROCKFORD BASE32, NOT HEX -- 0123456789ABCDEFGHJKMNPQRSTVWXYZ (0-9, A-Z minus I L O U), five characters = 25 bits = 33.5M per partition. Hex was wrong twice: 5 bits per char against 4, so the same width holds 32x the space; and Crockford does not merely EXCLUDE confusables, it REMAPS them on decode (i/l to 1, o to 0), which matters because the reference ladder assumes people retype fragments out of commit messages.

MIXED-CASE ENCODINGS ARE EXCLUDED, AND NOT ON TASTE. base58 and base64 were the denser candidates. The id goes in a FILENAME and this project develops on macOS, where APFS is case-insensitive by default. MEASURED: WI-20260817-aB3f9 and WI-20260817-Ab3f9 resolve to ONE file and the second write silently clobbers the first. Under case folding base58's 58 symbols collapse to ~33 usable ones -- below a clean base32, and noisier. bech32 passes the case test but spends SIX characters on a BCH checksum, more than the whole payload, to solve offline validation we do not have (the tracker is the authority; a mistyped fragment matches nothing ~99.997% of the time). RULE, whatever the alphabet: mint in ONE canonical case and compare ids CASE-INSENSITIVELY, so the filesystem's folding can never decide identity.

2. THE DUPLICATE CHECK COMPARES THE <time>-<hash> PREFIX, NEVER THE WHOLE ID STRING. This is the one that a naive implementation gets wrong and it is silent when wrong. Two items whose hashes collide have DIFFERENT DESCRIPTIONS, hence different slugs, hence DIFFERENT FILENAMES -- so a whole-string comparison misses every collision. The id: field stores the full string and WI-1114's PathDisagreement still compares that; only the duplicate predicate looks at the prefix.

3. AN ATTEMPT COUNTER MAKES A SINGLE WRITER COLLISION-PROOF. The birthday bound is the wrong model: the CLI holds the whole tracker and can look before it writes. h := H(author, created, description, attempt), attempt = 0,1,2..., re-hash until free. MEASURED on this repo (78 active days, mean 9.9 items/day, BUSIEST DAY 35): a re-hash essentially never happens; even a hypothetical 1-per-second factory re-hashes ~111 times out of 86400 mints. INTERACTION TO GET RIGHT: this must not break idempotent retry -- when attempt 0 is occupied, compare the occupant, and if author/created/description all match it IS this item from a half-finished run, so succeed with that id; advance the attempt only for a genuinely different item.

4. THE TIME COMPONENT IS A TUNABLE PARTITION, AND THAT IS THE SCALING LEVER, not a longer hash. Two items collide only within a partition. At one item per second the DIRECTORY fails first anyway -- 86400 files in open/, 31M a year, and ItemPerFileStore holds a block model of each -- and day to hour costs three characters while buying 24x on directory size AND 24x on collision scope together.

5. NEW §6.6, THE CROSS-WRITER CASE, and the surprise is that GIT USUALLY WILL NOT CONFLICT. Different slugs mean different filenames, so git merges two colliding items perfectly cleanly: no conflict, no markers, exit 0. Nothing at the VCS or filesystem level can notice. THE TRACKER IS THE ONLY POSSIBLE DETECTOR -- which also rules out a merge driver or a merge hook, because the case that matters never reaches them (and §12 already notes hooks are invisible and easily uninstalled). It is the ordinary load-time check every command already runs.

6. IT IS A DIFFERENT FAULT FROM DuplicateId, WITH THE OPPOSITE REMEDY, so they must be split. Same content in two files = interrupted-move debris, delete one, cannot auto-pick (what WI-1114 built). Different content = two real items whose hashes collided, renumber the loser, CAN auto-pick. Distinguishable by comparing author/created/description. New fsck --renumber, deliberately NOT part of --fix: that verb moves a file to match its fact, this one changes an IDENTITY. THE LOSER IS CHOSEN BY A DETERMINISTIC TOTAL ORDER and this is load-bearing -- both checkouts must reach the same answer without talking or the repair creates a second, worse divergence. Later created loses; ties on author, then full description. Re-minting is deterministic too, so two checkouts resolving independently produce BYTE-IDENTICAL trees and git merges the two fixes with no conflict. It rewrites the filename, id: field, satellites' workitem: fields and every depends_on; it REPORTS prose mentions rather than rewriting them, since a WI- in feedback may legitimately mean the winner.

7. MIGRATION MUST BACK-DATE created FROM GIT HISTORY, not stamp the migration date. Stamping one date puts all 1110 items in a single partition, where the collision scope is the whole tracker at once -- a COIN FLIP at 25 bits, against 0.002% at the busiest real day. Back-dating is also simply true (git knows when each id first appeared in workitems.anthill), and approximate commit dates are fine because created is used for ordering and minting, neither of which needs better than a day.

CORRECTION TO THE FILED DESCRIPTION: it claims this deletes §6.4's reconciliation. It does not -- it DEMOTES it, from machinery every offline add needs to a repair run when two unsynced writers collide. Still a large win, and the rare path can be much simpler than the routine one, but the machinery does not vanish.

ALSO SMALL: recognise merge-conflict markers in an item file and say so, rather than emitting a generic parse warning (safe today -- the loader warns and skips, and refuse_unknown_occupant will not write over a file the store never read -- but unhelpful).

STILL OPEN (§12): the slug width (render a real list at two or three settings and look); whether the id needs a version marker; whether destructive commands should echo the resolved item (a mistyped fragment hits a DIFFERENT real item about 1 in 30000 at 25 bits -- comfortable for show, less so for delete). NOTE the hash width is NOT irreversible: ids are grandfathered anyway, so if five ever proved narrow you would mint six tomorrow and every existing id would keep working.

SLUG WIDTH SETTLED: 30 characters, cut at a word boundary. The id shape is now fully settled: WI-<YYYYMMDD>-<5 Crockford base32>-<slug up to 30>. Design §6.5 carries the reasoning; §12's slug-width question is closed.

MEASURED on 772 of this tracker's own descriptions, which is where 30 comes from -- it is the knee of the ambiguity curve:
  cap 16 -> 231 items (30%) share a slug
  cap 24 ->  75 items (10%)
  cap 30 ->  32 items (4%)     <- knee; median id 45 chars, filename 56
  cap 40 ->   6 items (0.8%)   for ten more characters
  cap 50 ->   2 items (0.3%)
24 to 30 halves the ambiguity for 7 characters; 30 to 40 halves it again for 10; past 40 buys nothing.

BLOG/SEO CONVENTIONS DO NOT TRANSFER, and it is worth knowing why rather than just ignoring them. The consensus there is 3-5 words / 50-60 characters, and the closest precedents by SHAPE are the id-authoritative-plus-decorative-slug systems -- Stack Overflow /questions/<id>/<slug> (a wrong slug just redirects; the id decides), Medium's title-slug-plus-hash, Notion's title-plus-32-hex, Linear's /issue/ENG-123/<slug>. But in every one of those the slug lives in a URL, where nobody reads it in a column. Ours is stacked in ls and list output, so TERMINAL WIDTH is the binding constraint, not search engines.

A REPEATED SLUG IS NOT A DEFECT -- IT GROUPS A FAMILY. The largest duplicate sets at 30 are anthill-todo-backend x8 (the WI-437 increments themselves) and typer-wi-447-bare-form-prereq x4. In an ls that reads as structure rather than noise. The only cost is that the resolution ladder reports candidates for such a slug, and that candidate list is itself informative. So do not treat slug duplication as something to engineer away.

FILESYSTEM HEADROOM CHECKED, nothing is close to binding. A 56-char filename sits far under the universal 255 component limit (ext4/XFS/btrfs count BYTES, NTFS/FAT32-LFN count UTF-16 chars, APFS ~255). The constraint that actually binds first is WINDOWS MAX_PATH = 260 for the WHOLE PATH, not the component -- a typical deep checkout plus our filename lands around 133, with room to spare even at a 50-char slug; git for Windows has core.longpaths if a checkout is buried unusually deep. AND BECAUSE THE SLUG RULE EMITS ONLY [a-z0-9-], filenames are pure ASCII, so 255 bytes and 255 characters are the same number here and the UTF-8 bytes-vs-chars mismatch that bites ext4 never arises. FAT32/exFAT survive on USB sticks and every EFI System Partition but not as a git working tree (no symlinks, no permission bits, 4GB file cap -- git objects long before filenames do); what they contribute is one more CASE-INSENSITIVE filesystem, which the canonical-case rule already covers.

NO VERSION MARKER IN THE ID -- settled, and recorded in §12 with the reasoning because the impulse recurs.

The purpose a marker would serve is knowing WHICH RULE minted an id, and that only pays if the rule can be RE-RUN. It cannot: §6.5's hash input includes the description AT CREATION, which drifts. author and created survive as immutable fields, but one missing input is enough, so the marker would record a rule for a recomputation that can never happen.

Nothing else needs it either. PARSING is already unambiguous by shape -- legacy WI-1114 is WI- plus pure digits, the new form is WI- plus eight digits plus a hyphen, and a third scheme would be shaped distinguishably because one CHOOSES its shape. A HASH WIDTH CHANGE needs nothing: a 5-character hash never equals a 6-character one, which is the correct answer since they are different ids, and the ladder's prefix matching spans both widths. And THE DATE IS ALREADY A SOFT ERA MARKER FOR FREE -- ids are chronological, so 'everything from <date> uses scheme 2' is a one-line table, imperfect only where two checkouts straddle a binary upgrade, and nothing breaks there because nothing decodes.

AGAINST IT, and this is the part that decided it: a character in every id forever, in every filename and every depends_on entry, in the one segment this design fights to keep legible -- and more sharply, A VERSION MARKER ON AN OPAQUE TOKEN ADVERTISES A DECODABILITY THIS DESIGN DELIBERATELY DOES NOT OFFER. Stamping v1 implies a promise to interpret v1 later. There is nothing to interpret, and implying otherwise invites someone to build exactly the does-the-hash-still-match check §6.5 warns will rot.

THE IMPULSE IS NOT WRONG, IT IS IN THE WRONG PLACE. If the tracker ever needs to know which minting scheme it is on, that is StoreFormat(version:) -- WI-434, already exists, already gates the tracker, already stamped by migration in §11 step 4. A minting-scheme change IS a store-format change: one fact for the whole tracker, rather than a character in 1112 ids and every reference to them.

§12 is now down to one open question: whether destructive commands should echo the item they resolved.
