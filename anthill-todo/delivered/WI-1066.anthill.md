## Description

scala-gen: a SELF-REPRESENTING algebra still emits a false `extends` — Bootstrap reads a sort's SHAPE where the rule is about its CARRIER, so `trait Set[T] extends Eq[T]` ships and nothing can see it.

SPLIT FROM WI-1064 (2026-08-09), which took the data-sort half and states this half as a known over-approximation at its site and in §2.7a. Not a defect that ticket introduced: the emission is unchanged from before it.

THE RULE, already written down and already the ticket's own reason (docs/scala-forward-mapping.md §2.7a, kernel §8.7): a sort-level `requires` "conditions every provision, and supplies every body's evidence" — it is the requirement DICTIONARY, and the is-a claim is `provides`. So `requires` -> `extends` is right ONLY where the two coincide, i.e. where the required spec's carrier slot is bound to the declaring sort's own CARRIER.

WHAT BOOTSTRAP DOES INSTEAD: `extendsClause` matches on `SortShape`. Algebra (no constructors) -> supertrait, unconditionally. That is a PROXY for the carrier question — exact for a sort WITH constructors (the sort is the carrier, so a requirement can only be over something else) and merely usually-right without them.

WHERE THE PROXY IS WRONG — a self-representing algebra, whose carrier is the sort itself although it declares no constructors. MEASURED emissions, all three currently shipping:
 * `trait Set[T] extends anthill.prelude.Eq[T]` — set.anthill:6 says in its own header "the carrier is `Set` itself — like Map / List / Stream, ops take `s: Set` — and `T` is the element type", and its real claim is `provides Eq[T = Set]` / `provides PartialEq[T = Set]` eleven lines below. The `requires Eq[T]` constrains the ELEMENT. This is the identical requires/provides juxtaposition WI-1064 cites as its proof for the data case.
 * `trait Map[K, V] extends anthill.prelude.Eq[K]` — map.anthill:16's `requires Eq[T = K]`, over the KEY.
 * `trait VectorSpace[V, F] extends Ring[F]` — algebra.anthill:65. Carrier is `V` (ops take `a: V, b: V`); `Ring[F]` is over the SCALAR. Not self-representing at all — an ordinary carrier-parameter algebra whose requirement is simply over a DIFFERENT parameter. So the defect is not confined to self-representation, and a fix keyed only on that would miss this one.

WHY NOTHING CATCHES IT, which is the reason it needs a ticket rather than a follow-up glance: all three COMPILE. A Scala trait tolerates unimplemented members, so `ScalaCompile.assertCompiles`, the whole-closure peel and the refusal-set test are all blind. The consequence is silent: an implementor of the emitted `trait Set[T]` must supply `eq(a: T, b: T)` / `neq` over ELEMENTS, an obligation `sort Set` never declared, and it sits alongside Set's own `operation eq(a: Set, b: Set)` as an overload.

IDENTIFYING THE CARRIER, and the reason this is not a one-liner. The carrier is not a position and not a naming convention — it is what the sort's OPERATIONS take as their receiver, with everything else in the bracket a parameter of that algebra. Three shapes, all in the prelude:
 1. carrier is an explicit parameter — `FiniteCollection { sort C = ?; sort Element = ?; effects E = ? }`, ops take `c: C` (the source comments `sort C = ? -- carrier`).
 2. carrier is the sole parameter — `PartialEq { sort T = ? }`, ops take `a: T, b: T`. This is what makes `trait Ord[T] extends Eq[T]` correct.
 3. self-representing — `Set { sort T = ? }`, ops take `s: Set`. NO type variable is the carrier.
A workable syntactic test: the carrier is the sort itself if any operation receives the sort's own name (shape 3) or it has constructors; otherwise it is the parameter the operations receive. THE TRAP: `sort Eq` (eq.anthill:35) declares NO operations at all — it adds only a law — so it has no receiver to read, and it is one of the two cases pinned green today (`trait Eq[T] extends PartialEq[T]`, WI-170/WI-644). Whatever rule is chosen must answer for it, and "the sole parameter" is the obvious fallback but must be stated rather than assumed.

THE SECOND HALF, once the carrier is known: `requires Ring[F]` must be compared to the carrier, which means knowing WHICH ARGUMENT of `Ring[…]` is its carrier slot — the required sort's own declaration, in another file. That is the cross-file wall proposal 034 puts in front of Bootstrap (WI-1062 item 2, WI-1065). A test that avoids it: does the requirement mention the declaring sort's carrier AT ALL among its arguments? Covers the measured corpus (`Iterable[C = C, …]` mentions `C`; `Ring[F]` does not mention `V`; `Eq[T]` in Set does not mention `Set`) and is weaker than the real question — a requirement naming the carrier in a NON-carrier slot would falsely qualify. State and defend it, or take the KB-driven route.

WHAT THE OMITTED `extends` BECOMES is the same question WI-1064 answered for data sorts, and the answer does not transfer: an algebra sort has no constructor FIELDS to carry the requirement, so `checkDischarged`'s "is it typed by a field" test has no analogue. The candidates are an operation PARAMETER typed by it (`List.member requires Eq[T]` is the operation-level form, kernel §8.7), a `using` clause (WI-1022), or a refusal. Deciding this is most of the ticket.

ACCEPTANCE: §2.7a states the carrier rule with its reason and drops the "known over-approximation" paragraph WI-1064 left there; `Set` / `Map` / `VectorSpace` no longer emit a supertrait for a requirement over a non-carrier parameter, asserted on the emitted TEXT (a compile cannot see this — say so at the test site); `trait Ord[T] extends Eq[T]` and `trait Eq[T] extends PartialEq[T]` (WI-170/WI-644) and `FiniteCollection`'s own `requires Iterable[C = C, …]` are unchanged, each with a control assertion; the no-operations `sort Eq` case is decided explicitly; what an omitted algebra-sort `requires` becomes is stated and driven; and the peeled-closure measurement is re-run and recorded (`4 -> 3 -> 2 -> 4 -> clean, 32 files` after WI-1064). Say at each test site which assertion fails when the arm is backed out. sbt test green.
