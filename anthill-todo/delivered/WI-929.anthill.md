## Description

HARDEN the symbol category SET against name-collision merges: several has_kind readers were written when a symbol carried exactly ONE category, and WI-925 made define/define_qualified_only ACCUMULATE.

ALL FINDINGS BELOW ARE LATENT. The WI-925 /code-review agent grepped every .anthill in the repo (409 sort/namespace declarations) and found NO live instance of any of them; the full workspace is green at 3992/0. Filed so they are not lost, not because anything is broken today.

PROVENANCE: from the WI-925 /code-review correctness agent. I independently verified only the two it found that WERE live -- the by-qualified-name arm dropping SymbolKind::Entity, and symbol_is_value_place losing exclusivity -- and both are already FIXED in WI-925. The items below are REPORTED, NOT independently re-verified; DRIVE each before fixing it.

ROOT CAUSE (common to most): define reuses an existing symbol on a repeated SHORT NAME in one scope, and now records the second declaration's category too. So two genuinely different declarations sharing a name merge their categories, and any has_kind reader that meant the EXCLUSIVE question ("was declared as X") silently widens.

(1) MOST SEVERE -- SILENT TRIGGER-SORT HOLE. Item::SortWithBody (load.rs ~2618) reuses an existing by_qualified_name symbol WITHOUT calling define. If that qualified name was already claimed by a non-Sort declaration -- an explicit namespace, an implicit namespace minted by ensure_intermediate_namespaces for a dotted name, or an operation, scanned earlier in the same file OR in ANY earlier file since pass 1 is global -- then the sort's symbol never gets SymbolKind::Sort while register_sort still runs. sort_of_head(X) then returns None where it used to return Some(X), and collect_trigger_sorts DROPS the trigger sort of a constraint whose pattern head is X: the guard is registered under no sort and never re-fires on an assert. A silent hole on a clean load -- the failure mode this repo's development principles single out.

(2) CLOSED AS INTENTIONAL IDENTITY. `is_sort_scope` widens on a merged Namespace/Sort. Source shape:
    namespace Foo ... end
    sort Foo = Int64
yields kinds {Namespace, Sort}, so `is_sort_scope` answers TRUE for the one scope term at
that address. That is Proposal 059's model: once the sort exists, `namespace Foo` is a
secondary entry to it, not an independent namespace whose scope must keep a namespace-only
identity. The inclusive category question is therefore required here.

(3) CLOSED AS LOAD-BLOCKED. Item::AbstractSort ALWAYS defines, so a later `sort Foo =
Int64` merges Sort into a namespace Foo that pass 1 previously walked as a non-sort scope.
An `entity Bar` written in that earlier `namespace Foo` does expose different intermediate
pass-1/load answers. But after the sort declaration makes the block a Proposal 059
secondary entry, R3 refuses the entity before a successful KB can observe either derived
shape. Repairing the rejected intermediate would create no capability and would obscure
the actual enforcement boundary.

(4) FIXED -- DOTTED DECLARATIONS BYPASSED SECONDARY-ENTRY CLASSIFICATION. The original theory here is superseded: `entity E.Bar(...)` does not become a constructor of the free-standing entity `E`; `Bar` is self-sorted and has no strict parent sort. The live defect was proposal-059 parity. A dotted declaration is classified at the address its prefix names, so `entity E.Bar(...)` and `operation E.f(...)` are content at `E`, equivalent to writing them inside `namespace E ... end`. `SecondaryEntryPass::enter_scope` classified only the explicit spelling while its `at_item` hook was empty, allowing the dotted spelling to bypass R3/R4. The fix classifies a dotted non-scope declaration at its immediate prefix when that address is a sort, without recursively reaching an ordinary namespace such as `E.Inner`.

(5) load.rs ~11964, the guard "if !has_kind(head_resolved, Sort) { return None }", is a live WIDENING: every free-standing entity now carries Sort, so a two-segment "E.Member" in type position no longer bails. It falls into the else arm, which looks up by_qualified_name of "<E_qn>.<Member>" -- and emit_entity_info registers entity FIELDS under exactly that key. So "entity Foo(Bar: Int64)" plus a type annotation "x: Foo.Bar" resolves to the FIELD symbol as a sort ref. Latent only because uppercase field names are unusual; the arm's own doc ("Enum.Entity") no longer describes what reaches it.

(6) CLOSED AS UNREACHABLE AFTER FULL VALIDATION. `logical_sort_qn` must retain its inclusive `has_kind(Sort)` normalization for genuine inner self-named sort registrations. The only false-positive shape needs three same-named declarations: `namespace app.Config` containing `sort Config`, plus a sibling `sort Config` that merges Sort into the namespace symbol. It does reproduce the wrong intermediate collapse of `app.Config.Config` to `app.Config`, under both source orders, but Proposal 059 R4 independently rejects the inner `sort Config` for capturing the outer sort's name. No successfully loaded program observes the collapse. The stale exclusive-category comment was replaced with that measured enforcement boundary; executable code is unchanged.

(7) DOWNWARD ASYMMETRY. register_self_sort pushes into sort_entities, so sort_children(E) == [E] and constructors_of_sort(E) == [E] for a wrapped entity, while constructor_parent_sort cuts the fixpoint on the UPWARD side only. Current readers are harmless (sort_constructor_syms feeds match candidates; the exhaustiveness reader is gated on sort_kind == Enum, unreachable for a free-standing entity), but the asymmetry needs either a strict downward view or a stated reason none is needed, recorded next to constructor_parent_sort's doc.

(8) FIXED -- DOTTED ENTITY OWNERSHIP USED SYNTACTIC RATHER THAN ACTUAL SCOPE. `sort S { entity a.B(...) }` resolved B at `S.a.B` but treated the syntactically enclosing `S` as its constructor parent in every derived view: pass-1 marking and variant exposure, `register_entity_of`, `SortInfo`, induction/domain generation, and `MemberInfo`; field lowering and `load_entity` also ran in S rather than namespace `S.a`. The fix carries the symbol and declaring scope pass 1 recorded, emits the member row at that address, and limits every sort-body aggregate to genuinely direct entity children. Carrying the symbol is load-bearing: after entering `S.a`, resolving the original relative spelling `a.B` again can be captured by a distinct `S.a.a.B`. The dotted spelling now matches the explicit `namespace a { entity B(...) }` control: B is its own single-constructor sort, has no strict parent, is absent from S's constructors, resolves a field type local to `a`, and constructs/evaluates successfully.

APPROACH NOTE: do NOT sweep the ~58 remaining "kind_of == Some(K)" predicate sites mechanically. The two readings coincide for every symbol carrying ONE category, so only a site-by-site judgement can tell which was meant -- a blind sweep is exactly how (5) and the already-fixed symbol_is_value_place bug arise.

ACCEPTANCE: each item above either driven to a failing case and fixed, or closed with a recorded measurement showing it unreachable; a name-collision fixture (namespace + same-named sort; free-standing entity + dotted child) added as a regression test; cargo-test green via scripts/test.sh.
