## description

A LOAD MUST BE A FUNCTION OF THE PROGRAM, NOT OF ITS SPELLING ORDER — AND FOR A SORT DECLARING ONE OPERATION NAME TWICE, IT IS NOT.

MEASURED, on a sort declaring `q_op(x: T, y: T) -> T` and `q_op(x: T) -> T`:
  * both declarations resolve to the SAME `Symbol`;
  * TWO `anthill.reflect.OperationInfo` facts carry that one name;
  * `op_info::lookup_operation_info` returns whichever it reaches first, so the SAME sort answers arity=2 when the 2-ary is written first and arity=1 when the 1-ary is. The load is CLEAN either way — nothing warns, nothing errors.
Swapping two declarations that the language says nothing about must not change an answer. That is the property this ticket is about; the refusal below is the instrument.

DO WE SUPPORT OVERLOADING? TWO THINGS WEAR THAT NAME, AND ONLY ONE IS OURS.
  * ACROSS SORTS — `List.map` / `Stream.map` / `FiniteCollection.map`: YES, and it is not really overloading. These are distinct symbols with distinct qualified names, chosen by CARRIER, and §8.7's ladder specifies the choice. Proposal 011 OQ4.2 calls it 'overloading across sorts'. This is WI-1048's whole subject.
  * WITHIN ONE SCOPE, keyed on signature: NO, AND IT IS NOT REPRESENTABLE. `SymbolTable::define` (intern.rs ~544) states the invariant in its own comment — 'one name in one scope is still one symbol' (WI-926) — and `by_qualified_name` is a 1:1 map. An operation IS its qualified name. A second declaration therefore does not overload; it silently merges into the first symbol and leaves an orphan `OperationInfo` behind.

MEASURED DEMAND FOR IT: ZERO. 345 operation names across stdlib, stdlib+examples/github-todo and stdlib+anthill-todo — 0 carrying more than one `OperationInfo`. An independent SOURCE scan finds exactly three repeated operation names in the stdlib (`splitFirst`, `collect`, `iterator`) and ALL THREE are cross-sort pairs (`MappedStream`/`FilteredStream`, `FiniteMappedStream`/`FiniteFilteredStream`) — carrier dispatch, not overloading. Nothing in the corpus overloads accidentally or otherwise.

IF IT WERE EVER WANTED, THE KEY IS ARITY, NOT ARGUMENT TYPES — and the key is the cheap part. Arity is known at declaration, needs no type information, and is already materialized (`op_info::declared_arity`). Argument types are not tractable HERE specifically, for reasons the language itself creates: types carry logical variables and unify, there is subtyping and effect-row structure, and dispatch DELAYS on unbound vars — so overload selection would have to run before or during the very unification that determines the argument types (proposal 011 OQ7.1 already names 'overload resolution failure' as the failure mode). A parameter can also be a `Value::Node` arrow with no `TermId` at all (a `denoted` `-Modify[x]` callback), which a type-keyed index cannot key — measured in WI-1048. But EITHER key costs the name->symbol invariant that the whole reflect layer is built on (`OperationInfo(name: Symbol)`, `scope(?name, ?S)`, `KB.operations`), and the carrier dimension already absorbs the demand overloading exists to serve. RECOMMENDATION: do not add it. Refuse the duplicate.

WHY ORDER-INDEPENDENCE ALONE IS NOT ENOUGH: making `lookup_operation_info` deterministic (always first, always last) would restore the property and still leave one written `operation` silently unreachable — a program where a declaration does not exist and nothing says so. Refusal gives BOTH: the same error in either order, and no silent loss.

WANTED: refuse the second declaration at load, LOUDLY. 'Make illegal state unrepresentable', same family as WI-805 (duplicate tuple label), WI-808 (entity field distinct), WI-809 (named-arg distinct) — and it needs their treatment: a sentence in docs/kernel-language.md saying an operation name is declared at most once per scope (the spec is currently SILENT on this; §8.7 specifies only the cross-sort ladder), plus a doc-commented enforcement site.

THE INSTRUMENT — corrected from this ticket's first draft. Do NOT check 'the symbol table already has this name' in `scan_definitions` pass 1. The prelude bootstrap PRE-DEFINES operation symbols (`kb.symbols.define("eq", "anthill.prelude.PartialEq.eq", ...)`, load.rs ~4563, WI-718/WI-967) and the stdlib source then declares `operation eq` into that same scope, so a state-based pass-1 check fires on every pre-registered prelude op. Check instead, as a WHOLE-KB pass beside `check_requires_shadows`: AT MOST ONE `OperationInfo` FACT PER OPERATION SYMBOL. That is immune to the bootstrap by construction, and MEASURED so — pre-registration emits no `OperationInfo`, and `PartialEq.eq` / `Ord.compare` / `Numeric.add` each read exactly 1 after a full stdlib load. It also needs no pass-1 bookkeeping and survives the same file being scanned twice (the CLI embeds the stdlib).

OPEN QUESTION for whoever takes it: what is the distinctness DOMAIN — operations only, or every member name in a sort body (operation vs entity vs sub-sort vs const)? The spec should say, since §6.3's free-standing-entity spelling makes the entity/sort boundary a live question. Note `define` deliberately ACCUMULATES categories for the sort/namespace case (WI-926/WI-979), so the answer is not 'refuse every re-declaration'.

ALSO MEASURED, and NOT a defect — recorded so nobody re-investigates: the load is already independent of FILE order. Reversing the stdlib file list yields identical fact counts, rule counts, warnings and errors. WI-321's 4-pass `scan_definitions` is what buys that. The live order-dependence is DECLARATION order within a scope, which is this ticket. A corpus-scale pin for the file-order half does not exist yet and would be cheap.

ACCEPTANCE: a sort with two same-named operations is a LOAD ERROR naming the sort, the name, and both spans; the prelude and the full stdlib still load clean (the control that the bootstrap was not caught); a test drives BOTH declaration orders and gets the SAME refusal — the WI-979 idiom, where the two fixtures are identical but for order and that is the whole experiment; each test says which case fails when the change is backed out. `cargo-test` green via rustland/scripts/test.sh. REFERENCE: WI-1048 (found it); WI-926/WI-979 (the one-name-one-symbol invariant and its category accumulation); WI-805/808/809 (the distinctness family); WI-718/WI-967 (bootstrap pre-registration); WI-321 (file-order independence); proposal 011 OQ4.2/OQ7.1.
