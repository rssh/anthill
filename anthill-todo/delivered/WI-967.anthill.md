## Description

Every KB-building fixture calls register_prelude and register_standard_builtins, and load_all does both again.

VERIFIED in load.rs:
  load_all (4191)          -> calls register_prelude(kb) itself, line 4196
  register_prelude (3531)  -> calls kb.register_standard_builtins() itself, line 3547

So the house sequence

    let mut kb = KnowledgeBase::new();
    load::register_prelude(&mut kb);
    kb.register_standard_builtins();
    load::load_all(&mut kb, &refs, &resolver)

does register_prelude twice and register_standard_builtins twice. It is written that way at every fixture in the workspace - anthill-core/tests/common, anthill-smt-gen/tests/common, anthill-cpp-gen/tests/common, the new anthill-core/src/kb/test_support.rs, and the ~24 sites WI-964 covers.

NOT A BUG TODAY. register_prelude documents itself idempotent ('Idempotent: skipped on re-entry or when stdlib has already been scanned', via register_stdlib_scopes), and the suite is green, so nothing observable depends on the second pass. WI-959 deliberately did NOT change it: dropping two lines from one fixture while every other fixture keeps them is how the next reader concludes the fixture is the odd one out.

THE QUESTION IS WHICH DIRECTION IS RIGHT, and it is a real fork:
  (a) The caller's two lines are redundant - delete them everywhere and let load_all own the setup. Cheapest, but only sound if NO caller depends on prelude symbols existing BEFORE load_all runs (e.g. a fixture that interns or resolves a name between construction and load).
  (b) load_all should NOT silently re-register - a function that mutates setup its caller already performed is the thing that made (a) hard to see. Then load_all takes an already-prepared KB and the callers keep their lines.
Answer it by MEASUREMENT: delete the caller lines in one fixture, run; then make load_all's internal register_prelude a panic-if-already-registered, run. Each tells you something different about who actually depends on what.

WATCH FOR: load_incremental (load.rs:4216) already skips register_prelude deliberately, so whatever rule is chosen must keep the incremental path coherent with it - that asymmetry is the existing evidence about intended ownership and should be read before deciding.

ACCEPTANCE: one stated owner of prelude/builtin registration, applied uniformly, with the reason written where the ownership lives; load_incremental's asymmetry explained or removed; cargo-test green.
