## Description

GIVE `anthill.prelude.Pair` ITS CANONICAL ORDERING — lexicographic fst-then-snd, the order every neighbouring language gives a pair (Haskell Ord (a,b), Rust Ord for (A,B), Python tuples, std::pair). BLOCKED ON WI-876, and that is the whole reason it is a separate ticket. BUILT AND DRIVEN AT WI-858, THEN WITHDRAWN: Pair providing PartialOrd/Ordered itself works end to end — MEASURED Ordered.compare answering -1 / 1-on-tie / 0 with no bracket anywhere, and SortedSet.empty[T = Pair[Int64, Int64]]() sorting to (1,9)(2,1) with no ordering bracket at all. Nothing in the prelude ordered a Pair before, so it is a capability ADDED, not a choice imposed. It was withdrawn because it costs SEVEN operations in pair.anthill where ONE would do: compare carries the lexicographic logic, and max/min/gt/gte/lt/lte are each one line restating 'call compare, check the sign'. Seven-or-nothing — MEASURED, the LOAD check demands max/min (not resolver builtins, so op_backed finds no backing) and EVAL demands the other four (the spec-op builtins are host-scalar-only, so gt(pair(2,1), pair(1,9)) dies 'expected Ordered scalars of matching type, got Entity and Entity' on a program that loaded clean). Six workaround operations in the standard library for a defect that already has a ticket is the wrong trade. WORK, once WI-876 lands: add `requires Ordered[A]`, `requires Ordered[B]`, `provides PartialOrd[Pair]`, `provides Ordered[Pair]` and the single `compare` body to pair.anthill; delete nothing else. NOTE the shared-chain consequence, which WI-869 owns and which should be re-checked here: those two requires clauses sit on the SAME chain as the PartialEq ones, so every Pair nominally demands ordered components — false for Pair[Term, Term] and unenforced (no use-site check exists for Ordered, unlike Eq's). MEASURED harmless (the slots go unresolved and nothing reads them) but it is a second over-claim beside Eq[Pair]'s. ALSO NOTE what shipping this re-opens: with Pair self-providing, a program declaring a RIVAL pair ordering cannot reach the canonical one — the bare goal is ambiguous and [Ordered = Pair] is refused because Pair is a CONCRETE provider (058 §3.5 check 3, the value decides). Rung 2a (WI-861) closes that with no edit to pair.anthill, so this ticket does not need it but should assert the interaction. ACCEPTANCE: pair.anthill gains the ordering with ONLY compare; a bracket-less Ordered.compare and a bracket-less SortedSet over pairs both work; the full inherited surface (gt/gte/lt/lte/max/min) works with NO further members; wi858_pair_orderings_test's two program-declared orderings still coexist and still tie loudly at a bracket-less compare; full workspace green via rustland/scripts/test.sh. REFERENCE: stdlib/anthill/prelude/pair.anthill's header; design/058-implementation.md §9; WI-876.
