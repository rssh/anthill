## description

Three SortAlias walks survive outside typing.rs's consolidated one, and one test-side reader has five copies.

WI-943 collapsed typing.rs's SortAlias readers into `sort_alias_exact` / `sort_alias_by_name` / `scan_sort_aliases` (and DELETED `sort_alias_target_exact`, a third exact-match copy whose caller was doing a full linear scan on a post-index path). The /simplify reuse pass found what it did NOT reach.

1. `find_sort_alias_var` (rustland/anthill-core/src/kb/load.rs ~11580, 2 callers) is a near-verbatim twin of `scan_sort_aliases`: same two-pass exact-then-by-name shape, same `rules_by_functor(SortAlias)` -> `fact_head_term` -> `pos_args[0]` functor -> `pos_args[1]` walk, same value-fact-skip caveat spelled out again in its own comment. NOT a mechanical swap, and this is why WI-943 left it: its `Term::Var(_)` filter is on the TARGET and sits INSIDE the loop (a non-Var target is skipped and the scan CONTINUES), so it cannot be a post-filter. Reuse needs the predicate widened to `(functor, target)` and `scan_sort_aliases` raised to `pub(crate)`.

2. Cannot and should not be consolidated — recorded so the next reader does not retry it: `build_sort_alias_index` (one pass building THREE maps over ALL facts; `scan_sort_aliases` returns on first match); `reconstruct_sort_params`' pre-index tail (collects EVERY alias under a parent prefix — see the sibling ticket on its keying); `sort_alias_exists` (load.rs ~13359, keys on pos-0 TermId equality and reads the head via `rule_head_value`/`pos_arg` PRECISELY so a `Value::Node` head still dedups — `scan_sort_aliases` skips exactly those heads via `fact_head_term`, so reuse would silently break the WI-390 dedup).

3. TEST SIDE: 'SortAlias source symbol -> target Var::Global id' is hand-rolled in five files — wi210_dispatch_test.rs (`subst_with_param`), wi221_defer_to_requirement_test.rs (`subst_with_param`), wi224_sld_resolution_test.rs (`goal_for`), wi452_marked_param_backing_var_test.rs (`has_backing_var`), wi943_type_param_identity_test.rs. `tests/common/mod.rs` has no such helper. Lift one there and route all five through it (`has_backing_var` becomes `.is_some()`).

4. `ground_rigid_projection_if_concrete` (typing.rs) gates its owner check with `kind_of(sort) != Some(SymbolKind::Operation)` while `op_declared_type_param_var` uses `has_kind`. `kind_of` is documented (intern.rs) as 'the keyword the declaration opened with — for DISPLAY only … Not a test for what the name can be used as: see `has_kind`.' Pre-existing; WI-943 is what made the two siblings by pointing both at `op_info::declared_type_param_var`. DECIDE, do not assume: the `kind_of` gate there may be doing MORE than 'owner is an operation' (it is the WI-383 op-vs-sort projection split), so check whether the two questions are actually the same before merging them.

ACCEPTANCE: cargo-test green; each item either done or CLOSED IN THE TICKET with the reason (item 2 is already closed above — do not reopen it).
