## Description

WI-582 x WI-279 gap surfaced while delivering WI-902: a TYPED PATTERN BOUND on a DOT rule is SILENTLY IGNORED. load.rs installs `?x: T` bounds (`install_rule_type_bounds`) on any `[simp]`/`[unfold]` EQUATIONAL head, and refuses every other rule shape loudly precisely because "a non-rewrite rule would silently ignore it". A dot rule -- `rule dr: dot_apply(?e, m, ?x: T) = rhs(...) [simp]` -- passes that check, but the site the loader names as the enforcer (the resolver's `apply_eq_rules` / `typed_pattern_bounds_hold`) never sees a `dot_apply` head on the path the rule is written for: a dot rule is matched by `typing::try_fire_dot_rule` against a surface `Expr::DotApply` occurrence, and that function never reads `kb.rule_type_bounds`. The other typer site, `simp_rewrite::try_fire`, SKIPS typed-bound rules outright (WI-582), so the two firing sites disagree about which rules they fire.

MEASURED (2026-07-31, delivering WI-902): inside `sort Holder`, `rule dr: dot_apply(?e, bump, ?x: String) = wrap(?e, ?x) [simp]` with `operation consumer(h: Holder) -> Int64 = ?h.bump(5)` -- an UNSATISFIABLE bound (`5` is not a String) -- loads CLEAN and FIRES: the stored consumer body is the rewrite's output (`wrapped(...)`), not a `bump` no-match. The bound is consulted nowhere.

SECOND CONSEQUENCE, recorded at `simp_rewrite::macro_expanded_rhs_head`: the WI-702/054 effectful-rewrite gate's macro exemption is keyed on the conditions `try_fire` applies, one of which is "no typed-pattern bounds". Since WI-902 the dot site DOES macro-expand, so an `Error`-declaring macro (WI-757's rejection channel) under a typed-bound dot rule is refused at load with the "a directional rewrite DUPLICATES, REORDERS, or DROPS the matched call" message even though its call is expanded away and never reaches runtime. MEASURED: the rejection AND that refusal are both reported for one such rule. Deliberately left conservative in WI-902 (loud, and refused before WI-902 too) rather than widening a safety gate around a rule shape that is itself broken.

DECIDE AND FIX one of: (a) ENFORCE the bound in `try_fire_dot_rule` -- the typer holds each matched occurrence's stamped `inferred_type`, so the check is the occurrence-side twin of `typed_pattern_bounds_hold`; this is the honest reading of what the author wrote and makes `macro_expanded_rhs_head`'s exemption correct by construction. (b) REFUSE a typed-bound dot rule at LOAD, extending load.rs's existing loud check to a `dot_apply` LHS -- cheapest, makes the illegal state unrepresentable, and consistent with the rule the same check already states. Prefer (b) unless a client actually needs a bounded dot rule; note (b) is a behaviour change for any program relying on today's ignored bound (none in stdlib/examples -- verify).

ACCEPTANCE: a typed-bound dot rule either ENFORCES its bound (a receiver/arg outside it does not fire, asserted by a test whose bound is unsatisfiable, as the measurement above) or is REFUSED at load with a message naming the rule; the divergence note in `macro_expanded_rhs_head`'s doc comment is retired together with the case it describes; WI-582 and WI-279 dot-dispatch tests stay green; cargo-test green via scripts/test.sh.
