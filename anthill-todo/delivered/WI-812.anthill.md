## Description

read_facts resident selection pushdown via the discrim tree + O(1) bodied-rule gate. read_facts's RESIDENT arm is a LINEAR scan over the functor bucket (rules_by_functor) + per-row bound_matches, NOT a discrim-indexed lookup -- because the generic accessor lacks the functor's field SCHEMA to build a full-arity discrim query pattern (extent.rs comment). It is the ONLY read path in the KB that does not use the discrim tree (both query_view and SLD do). Consequences: (a) O(bucket) reads where a discrim index would be O(matching) -- the MOUNTED arm already pushes the selection down and indexes, the resident arm scans; (b) the BLANKET bodied-refusal (functor-wide, WI-770/772) is ENTANGLED with the full-bucket scan. FIX: (1) give read_facts the functor's field schema (the KB has it -- canonicalize_record_named_args keys on DECLARED field order) so it builds a discrim query and pushes the selection down (indexed + naturally scoped). (2) Factor the blanket bodied-refusal into an O(1) per-functor has_bodied_rule cached flag (cf. WI-635 head_has_vars, WI-646 O(1) gate) so 'find matching rows' (indexed) and 'is this functor a pure table' (O(1)) are SEPARATE concerns -- and blanket-vs-scoped becomes a DELIBERATE choice, not a scan artifact. NOTE vs WI-811: distinct -- WI-811's Resolve->SLD gives the Resolve path discrim indexing for free, but read_facts(Refuse) is a non-resolving read WI-811 leaves as a scan, so this WI (resident Refuse indexing + the O(1) gate) stands on its own.
