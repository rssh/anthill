## Description

A RULE HEAD's binding depends on DECLARATION ORDER. It must not.

MUST AGREE WITH docs/proposals/059-secondary-entries.md R6, which defines the
correct behaviour; this ticket implements it. Do not re-decide the policy here --
if the implementation cannot meet R6, amend 059 rather than diverging from it.

THE POLICY IS NOT IN QUESTION. kernel-language.md §"A rule head functor is
resolved, not declared" (WI-896) already says it: the functor runs the ordinary
ladder and the rule contributes a clause to whatever it lands on; only when the
ladder finds NOTHING does the rule introduce the name, scoped where written. The
defect is WHEN "the ladder finds nothing" is evaluated -- measured, against a
HALF-BUILT name table, so textual order decides the answer.

MEASURED (resolving the goal after load; counts are answers):

  namespace s2                      namespace s1
    rule p(1)                         sort Rec
    sort Rec                            entity Rec(n: Int64)
      entity Rec(n: Int64)              rule p(2)
      rule p(2)                       end
    end                               rule p(1)
  end                               end

  s2.p(2)=1   s2.Rec.p=<no symbol>    s1.p(2)=0   s1.Rec.p(2)=1

Same pair, opposite order, two different programs: one predicate with two
clauses, versus two predicates with one clause each.

NOT A COMPANION QUESTION -- the identical split occurs with `namespace Rec ...
end` (a proposal-059 secondary entry) in place of the sort body: enclosing rule
written before => joins; written after => mints `Rec.p`. Both spellings agree
with each other and disagree with themselves across orders.

WHY IT MATTERS: this is the source-order dependence the WI-925/926 category-set
work exists to remove, in the one name kind that still has it. It also silently
decides whether a rule EXTENDS someone else's predicate -- and extension is
non-monotone: MEASURED, `rule q(0) :- not p(2)` has one answer, and adding a
single `rule p(2)` from an inner scope takes it to zero. A true statement becomes
false, and proofs discharged from it (WI-537/538/539/558) were verified against a
knowledge base that no longer exists. Which of the two readings you get should not
turn on where in the file someone put a line.

REQUIRED BEHAVIOUR (059 R6): the binding is computed against the FINISHED
program, never the scanned prefix -- scopes outermost-first, all of a scope's
heads together. The two programs above must both give the FIRST row's answer
(`p(2)=1`, no `Rec.p`), since in the finished program `p` does resolve from
inside `Rec`. A scope wanting its own name where an enclosing one resolves
DECLARES it, the remedy §WI-896 already prescribes.

LIKELY MECHANISM, to confirm rather than assume: the mint decision is taken in
`scan_rule` during scan_definitions sub-pass 1, i.e. while the table that
decides it is still being built. Every other name kind is order-free because
pass 1 defines all of them before any pass 2 runs (the WI-321 cross-file
mutual-recursion invariant); a rule head escapes it by being introduced during
that pass. Note sub-pass 3 also registers unlabeled rule head-functor Goals --
establish which pass actually takes the decision before changing either.

WATCH FOR: a circular case the fix must define rather than stumble into -- an
inner and an outer head that would each introduce, with nothing else declaring
the name. Outermost-first makes the inner one see the outer and join; confirm
that is what lands.

MIGRATION RISK, to MEASURE FIRST: today's join-vs-mint split is load-bearing
somewhere or it is not, and the answer decides the size of this ticket. Before
changing behaviour, count the places in stdlib / anthill-stl / examples /
anthill-todo / fixtures where an inner rule head currently MINTS only because
its enclosing predicate is declared later in the file -- each becomes a join and
changes meaning. If that count is not zero, the fix needs a migration, not just
a reorder of passes.

ACCEPTANCE: the two programs above load to the same KB. A test asserts, for BOTH
orders and BOTH spellings (sort body and secondary entry), the same predicate
identity and the same answer counts -- four rows, since a pair that agrees in
only one order measures nothing. Say at the test site which rows fail when the
fix is backed out (the enclosing-rule-written-after rows do; the others pass
either way, by design, as the control). cargo-test green via
rustland/scripts/test.sh.

THE FIX IS A CHANGE OF QUESTION, NOT A SCHEDULE. Sub-pass 3's guard asked
`name_denotes_for_rule_head` -- "has a symbol been minted" -- and this is the one pass
whose own work changes that answer, so the same head got one verdict written above a sort
and the opposite below it. It now asks whether some scope this one can SEE already
INTRODUCES the name: a property of the finished text, same answer in every order. "Can
see" is the RESOLVER'S OWN WALK over an overlay of the program's rule heads
(`resolve_captured_name_with_overlay`), not a second traversal -- a hand-built one missed
the per-hop path properties and refused three programs that load clean.

A ROUND-BASED FIXPOINT, NOT A RECURSION, and this is the load-bearing choice. The relation
is NOT monotone (more owners => more yielders => fewer owners), so a demand-driven
recursion must break cycles provisionally, and anything cached under such a break reaches
readers outside the cycle. The first implementation did that and was MEASURED
order-dependent: six permutations of three files gave two different programs. Three rules
replace it -- see `Ownership`'s doc. `<global>` may own what is written at it and is never
yielded to. No depth bound is needed, the recursion being gone.

THE TICKET'S "LIKELY MECHANISM" WAS WRONG AND SAID TO CHECK: the mint is `scan_rule_goal`
in sub-pass 3, not `scan_rule` in sub-pass 1, which defines only a rule's LABEL.
