## description

AN ARITY-ONLY ARROW MISMATCH RENDERS 'expected X, got X' — the SAME text on both sides, so the diagnostic that owns every callback arity defect cannot express the defect it owns. MEASURED live on the WI-794 delivery commit:

  operation apply3(f: (a: Int64, b: Int64, c: Int64) -> Int64) -> Int64 = f(1, 2, 3)
  operation drive() -> Int64 = apply3(lambda (x: String, y) -> 0)

  'error: 4:32: type mismatch in apply3.f (op-arg): expected (a: Int64, b: Int64, c: Int64) -> Int64, got (a: Int64, b: Int64, c: Int64) -> Int64'

Both rendered arrows are byte-identical. The user is told two types do not match and shown the same type twice; nothing in the message says the ARITY is what differs, and the actual mistake (a 2-binder lambda at a 3-parameter slot) is nowhere in the text.

ROOT CAUSE, not verified beyond reading: WI-791 made an arrow's parameter-list ARITY a GROUND SIBLING of the param slot rather than part of the param type, and the type renderer walks the param spine only — so two arrows differing solely in the arity child render identically. The renderer is the likely locus (type_display_name_value and the arrow arm it dispatches to), not the check, which is correctly refusing the program.

WHY IT MATTERS MORE NOW THAN IT DID: this was pre-existing and cosmetic. WI-794 made it LOAD-BEARING. The per-binder annotation check deliberately STANDS DOWN when binder count and component count disagree — because at unequal arity the index zip pairs binder i with an unrelated component, and blaming a specific annotation for a missing parameter is worse than saying nothing (measured on WI-794's first cut: 'binder y: expected String, got Int64' against an annotation that was fine). That suppression is justified in the code by 'leaving the arity defect to whichever check genuinely owns it' — and the check it hands off TO is this one. A deferral target that renders the mismatch as 'expected X, got X' makes the handoff a downgrade, not a delegation.

SCOPE NOTE, measured while reviewing WI-794: the handoff only happens at all for a lambda in ARGUMENT position, where arrow subsumption fires. In a let-destructure or a match arm there is no arrow to subsume, so a misaligned pattern's annotation contradiction is reported by nobody at load time. That is NOT a defect to fix here and was deliberately NOT filed: the binder never binds in those positions — a misaligned let-destructure fails loudly at RUNTIME ('error: match_failed', exit 1, verified) and a misaligned match arm is dead code that falls through to the next arm (verified). Recorded so the next reader does not re-derive the same alarm.

ACCEPTANCE: an arity-only arrow mismatch produces a diagnostic in which the two rendered sides DIFFER, and which states the arity of each (e.g. 'expected a 3-parameter function, got 2 parameters'); the example above names the real fault; an arity-AND-type mismatch still reports the type difference it already reports; existing arrow diagnostics that differ in a param TYPE are unchanged; wi791/wi782/wi794 suites stay green; full workspace green via scripts/test.sh.
