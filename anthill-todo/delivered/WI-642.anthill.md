## Description

Extend the `MissingRequiresForSpecOp` static check from operation bodies to RULE / relation clause bodies, so a clause that calls a `requires`-carrying spec-op whose requirement is neither declared nor satisfiable is a LOAD error, not a silent resolution-time failure.

GAP: today the requirement-diagnostic pass `req_insertion::run` (rustland/anthill-core/src/kb/req_insertion.rs:46-50) walks ONLY `kb.op_bodies` (op_bodies_iter) and emits `MissingRequiresForSpecOp` (WI-325, req_insertion.rs:79) for OPERATION bodies. Rule / relation clause bodies (`body_nodes`) are NOT walked, so a rule-body spec-op call with an unsatisfiable requirement is caught only at RESOLUTION -- the WI-300 `find_dictionary(X)` goal (resolve.rs:3909) just fails / floats -- never at load. This violates the repo principle "prefer a loud error over a silent skip."

FIX DIRECTION (kb/req_insertion.rs + typing.rs): walk each rule's clause body (`body_nodes`) for spec-op calls (the same UnresolvedSpecOp / spec-op-dispatch shape req_insertion already recognizes in op bodies), and for each resolve the requirement against (a) a `requires` declared on the enclosing rule/sort, or (b) an available provision (WI-300 / WI-292 provides-resolution); if NEITHER, emit `MissingRequiresForSpecOp` (or the direct-call analogue at typing.rs:2614) at load. Reuse the op-body machinery -- a coverage extension of req_insertion (or a sibling pass over body_nodes), not new diagnostic logic.

LOAD-BEARING DISTINCTION (WI-292): a STATICALLY-MISSING requirement (no provision can satisfy it AND it is not declared) is an ERROR; an UNDER-DETERMINED requirement (the grounding type is not yet bound at the current substitution) is NOT an error -- it SUSPENDS as a residual (WI-292 resolve-or-suspend / WI-067, never NAF-decide). The static check must report ONLY the former: a requirement unsatisfiable for ALL groundings AND undeclared -- never one that is merely not-yet-ground, and never a polymorphic rule that legitimately propagates `requires X` to its callers.

DRIVER: proposal 052 (docs/proposals/052-rules-as-stream-valued-operations.md, section "Requirements in a clause body -- the rule-body dictionary (WI-300), and checking a missing one"). A relation is a rule; its clause bodies calling spec-ops should fail at LOAD when a requirement can never be met. The runtime path is WI-300 (delivered); this is its STATIC face.

ACCEPTANCE: a rule whose body calls a spec-op (e.g. `eq` from `Eq[T]`) with T a concrete sort that provides NO `Eq` instance, and with no `requires Eq[T]` on the enclosing rule/sort, is a LOAD error (`MissingRequiresForSpecOp` or the direct-call analogue) -- verified it errors at load, not only at query time; a rule that DECLARES `requires Eq[T]` (propagating) loads clean; a polymorphic rule whose grounding is under-determined SUSPENDS (does not error); existing op-body MissingRequiresForSpecOp diagnostics are unchanged; cargo test green. REF: WI-325 (MissingRequiresForSpecOp, the op-body diagnostic this extends), WI-300 (rule-body requirement goals / find_dictionary, delivered -- the runtime path this statically checks), WI-292 (resolve-or-suspend -- the under-determined-vs-missing distinction), WI-420 (bare-op unsatisfiable requirement analogue), req_insertion.rs:46-79, typing.rs (MissingRequiresForSpecOp at 106/287/467, no-instance error at 6331). Rust-only (typer; scaland has no typer).
