## Description

A sort application's type-argument NAMES are not validated against the sort's declared type params -- and the WRITTEN and EVALUATED positions disagree about what to do with a stray one. Repro: `Cell` declares one type param `V`. Written in TYPE position, `c: Cell[W = Int64]` has its stray `W` binding DROPPED at load (see make_parameterized_type's own comment: 'also covers an over-applied non-parametric sort whose stray bindings were dropped at load'). Written in VALUE position (WI-707), `is_modifiable(Cell[W = Int64])` type-checks and eval builds `Fn{Cell, named: [(W, Int64)]}` -- a type term carrying an UNDECLARED parameter. So the two positions do not merely differ in strictness, they build DIFFERENT TERMS for the same written type, which is exactly the hash-consing divergence WI-707 otherwise closed by routing eval through the canonical make_parameterized_type builder. Nothing observes it today only because no consumer reads type ARGUMENTS (every Type-taking reflect op keys on the head sort); it is a live trap for the first one that does (and for WI-708, which will make type args actually carry bindings). Decide ONE rule and apply it to BOTH positions -- do not half-fix it in eval, which is why WI-707 deliberately left it. Options: (a) LOUD (preferred, per CLAUDE.md loud-over-silent): an undeclared type-param name is an error at load, in type position AND in value position -- a typo like Cell[W = Int64] is a bug the user wants to hear about, and the current silent drop hides it; (b) keep dropping, but drop in BOTH positions so the terms agree. Under (a), also check the ARITY of positionals: eval already errors loudly when a positional type arg has no declared param to bind (finish_sort_type), but the typer accepts it -- so the diagnostic arrives at eval instead of load. Scope note: the natural home is the typer's sort-application build arm (kb/typing.rs, the WI-707 arm that returns the Type result), which can validate binding names + positional arity against type_params_of_sort at type-check time, making eval's runtime guard unreachable-by-construction rather than the only check. Acceptance: Cell[W = Int64] behaves identically in a type annotation and in a value argument (both loud, or both dropped); a positional type arg with no declared param to bind is diagnosed at LOAD, not at eval; cargo test green.
