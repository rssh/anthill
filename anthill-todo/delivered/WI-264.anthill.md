## Description

Refactor typer to propagate structured errors instead of losing them as None. Today the typer's surface API is Option<TypeResult>: type_check_node and every check_* helper (check_apply_iter, check_constructor_iter, check_if_expr, check_list_literal, check_set_literal, check_tuple_literal, check_lambda etc.) return None on any failure — unresolved name, missing constructor, unification mismatch, undefined field, dispatch NoMatch, dispatch Ambiguous, unknown Apply functor — without distinguishing them. Consequence: a localized typing failure several frames deep silently cascades upward, the operation body's type comes back as None, and the only feedback is an eprintln from one of the few sites that bothered to log (resolve at typing.rs ~1242, ~1249). The WI-204 fix made this concrete: a let-bound entity constructor returning None corrupted the body's typing env via a TypingEnv::empty() fallback in LetAfterValue; removing the fallback now requires the typer to bail out the entire let on None — which is correct strictness but still loses the WHY. Driver: development principle now in CLAUDE.md — 'avoid fallbacks, better know about errors early'. Refactor: change the typer's return type to Result<TypeResult, TypeError> (TypeError already exists at typing.rs:28 with TypeMismatch / UnknownField / NoParentSort / UnresolvedName / Other variants — extend with NoConstructor, NoFieldTypes, DispatchNoMatch, DispatchAmbiguous, UnknownApplyFunctor, BottomExpr as needed); thread the Result through type_check_node, visit_type, build_type, the iterative work-stack frames (results vec stores Result instead of Option), and every check_* helper. Aggregate sibling errors when multiple sub-expressions fail (e.g., list literal with two ill-typed elements collects both). Surface errors at the operation-body driver loop (typing.rs ~5214) instead of relying on per-site eprintln. Retire the eprintln-based dispatch error messages — DispatchOutcome::NoMatch / Ambiguous become TypeError variants the loader's diagnostic emitter reads. Cross-cutting touches: ~30 call sites returning Option<TypeResult>, ~12 TypeBuildFrame variants, the iterative work-stack's results: Vec<Option<TypeResult>>, plus the loader's emit-warnings pass that currently fishes through env.diagnostics — diagnostics for non-exhaustive match should keep that path (warning, not error), but type errors get the new Result channel. Acceptance: typer's public signature is Result-based; running an ill-typed body produces a TypeError whose variant identifies the specific failure mode and whose span (where available) points at the offending sub-expression; existing eprintln dispatch logs in typing.rs retire; the WI-204 fix's strict propagation (LetAfterValue / check_tuple_literal_constructor) becomes Result propagation naturally; cargo-test green with the existing failure-path tests updated to assert on TypeError variants rather than just 'load failed'. Driver follow-up to WI-204 / Phase B2 — same principle.
