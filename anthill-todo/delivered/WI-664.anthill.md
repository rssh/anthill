## Description

Congruent Eq/NonEq derivation for COMPOSITE carriers (entities + named tuples): a composite's equality lawfulness must PROPAGATE from its fields — an entity / named-tuple is lawful `Eq` iff ALL its fields are `Eq`, and is `NonEq` (partial) if ANY field provides `NonEq` (or only `PartialEq`). This is Rust's rule: `derive(PartialEq)` works on a struct with an `f64` field, but `derive(Eq)` fails unless every field is `Eq`. Follows WI-658, which added the `NonEq` spec + witness (`nonEqRefl`) + the load-time `Eq` ⊥ `NonEq` mutual-exclusion check for bare carriers (Float).

TWO COUPLED AXES — both are required; deriving the classification is toothless without fixing the behavior:

AXIS 1 — CLASSIFICATION (derive the provision from field types): for each entity sort / named-tuple, auto-derive its equality provision: all-fields-Eq => `provides Eq[X]`; any-field-NonEq (e.g. a `Float` field) => `provides NonEq[X]` (+ PartialEq), NOT Eq. The composite's witness `nonEqRefl()` = the constructor with the NonEq field bound to that field's witness (`Point.nonEqRefl() = Point(x: Float.nonEqRefl(), y: <any>)`). Composes with WI-658's check: a user `provides Eq[Point]` over a Float-containing Point becomes a load error automatically.

MUST FIX AS PART OF THIS TICKET (WI-658 review carry-over): WI-658's `check_eq_noneq_exclusive` (typing.rs) currently keys the Eq/NonEq grouping on the carrier's BASE sort symbol, so a PARAMETRIC carrier that legitimately provides `Eq` at one instantiation and `NonEq` at another (`Box[T = Int]` lawful, `Box[T = Float]` partial — the very case this ticket introduces) would be FALSELY flagged as providing both. Harmless today (only the non-parametric leaf `Float` provides NonEq), but this ticket makes it reachable — so BEFORE deriving per-instantiation Eq/NonEq for composites, make the check binding-aware: key on the spec's carrier-binding VALUE (the full instantiated carrier term), not just the base symbol. See the `LIMITATION` note in the check's doc comment.

AXIS 2 — BEHAVIOR (the actual soundness fix, interpreter + resolver): `semantic_equal` (eval/builtins.rs ~496) and its resolver mirror `sem_eq_core` (kb/resolve.rs) SHORT-CIRCUIT on structural reflexivity (step 2, `views_structurally_equal`) BEFORE any field-wise consideration — so `eq(Point(nan, 0), Point(nan, 0)) = true` TODAY. The nested Float's non-reflexivity is LAUNDERED (step 1's IEEE path fires only on a bare Float PAIR, not two entities). This DIVERGES from the field-wise C++ `operator==` codegen (WI-644 step 4), which propagates `double`'s IEEE `==` to false — the exact WI-645 interpreter-vs-codegen divergence, one level up through composition. FIX: gate the structural reflexivity shortcut so a term that (transitively) contains a partial carrier recurses field-wise (`eq(Point(nan,_), Point(nan,_))` reduces to `eq(nan,nan) AND ... = false`). CRUCIAL: `===` / `struct_eq` MUST stay structural-reflexive (`nan === nan = true`) for hash-consing / dedup — only the SEMANTIC `eq` recurses. Touches the hot reflexivity path; scope carefully.

EVIDENCE (probe 2026-07-07): `semantic_equal` step 2 returns structural-true for two identical Float-containing entities; there is no field-wise-congruent entity/tuple eq, and no field-type-driven Eq/NonEq derivation (grep: none). Bare Float is correct (WI-644/658); the moment Float is wrapped, the structural shortcut re-launders it.

RELATED (note as further propagation, not in this ticket's core): the same laundering affects `Option[Float]`, ordinary tuples, and `Set`/`Map` over Float — the general law is "a composite is Eq iff its components are." This ticket covers entities + named tuples (the requested scope); the parametric-container propagation is a further follow-up.

ACCEPTANCE: an entity / named-tuple with a Float (NonEq) field derives NonEq, not Eq; a user `provides Eq[<such composite>]` is a load error (via the WI-658 check); `eq(Point(nan,_), Point(nan,_)) = false` in the interpreter, AGREEING with the C++ codegen; `Point(1.0, 2.0) eq Point(1.0, 2.0) = true`; `===` stays structural (`Point(nan,_) === Point(nan,_) = true`, hash-consing intact); all-Eq-field composites still derive and behave as Eq; full workspace suite green. Depends on WI-658.
