## Description

scaland's parser cannot read a one-component tuple type, so Rust and Scala now accept different languages. SITE: AnthillParser.scala's tupleType (scaland/core/src/main/scala/anthill/parse/AnthillParser.scala, ~line 314) = ('(' ~ ')') | ('(' ~ tupleTypeArg ~ (',' ~/ tupleTypeArg).rep(1) ~ ')') -- the .rep(1) forces two or more components, so there is no one-component alternative at all. For '(a: Int64)': arrowType backtracks (no '->'), tupleType fails the .rep(1), and simpleType cannot start at '('. DIVERGENCE BEGAN AT WI-763 (the denoted keep spec '(who: "name")') and is widened by WI-766, which also RESTRUCTURED the Rust grammar: an arrow's parameter list IS a tuple_type there now, with no separate arrow_params production, and a bare '(A)' parses as a one-component tuple and is refused at CONVERSION rather than by the grammar. Porting the .rep(1) fix alone would leave the two implementations structurally different even where they agree on the accepted language. CONSEQUENCE: any stdlib/ or examples/ file adopting the newly-admitted form loads in rustland and fails to parse in scaland, and NO test catches the split -- the two parsers are never run over the same corpus. Per docs the Rust implementation is ground truth. WORTH DECIDING FIRST, and recording on this ticket: whether scaland is still intended to track the kernel language, since the answer changes this from a port to a deprecation. ACCEPTANCE if tracking: scaland parses '(a: A)', '(a: "x")' and '(A) -> B', rejects a bare '(A)' as a type, and a shared-corpus test asserts both parsers accept/reject the same files so the next divergence is caught; sbt test green.
