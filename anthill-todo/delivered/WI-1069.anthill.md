## Description

A `provides` CLAUSE'S BINDINGS ARE NOT A CARRIER SELECTOR, AND NOTHING SAYS SO — a
clause naming another carrier files SILENTLY under the sort it is written in.

MEASURED (WI-1000), both rows on one program:

  namespace Rec  provides Show[T = Other]  end   ->  SortProvidesInfo(Rec,   Show)
  fact Show[T = Other]        one level out      ->  SortProvidesInfo(Other, Show)

`load_provides_clause` (kb/load.rs) takes the PROVIDING SORT from `domain` — the
enclosing scope's owner — and the clause's bindings are the SPEC's arguments. So
`provides Show[T = Other]` says "the enclosing sort provides Show at T = Other",
which is almost never what someone writing `T = Other` means. It does not refuse,
it does not warn: the program loads and the wrong carrier is on record, which is
the input to the backing obligation, coherence and dispatch alike.

NOT INTRODUCED BY WI-1000. The shape has always been admissible inside a `sort X …
end` body, where it behaves identically. WI-1000 admitted `provides_clause` in a
namespace body (059 R3 needs it: a secondary entry's allowed spelling of a spec
claim), so the same trap is now reachable one more place — and it refuses the
genuinely subjectless case, a `provides` in a namespace with no sort at its address
(`LoadError::ProvidesClauseNeedsSort`). What it did NOT do is decide this one.

WHAT MUST BE MEASURED BEFORE ANY REFUSAL, and it is the whole cost of the change:
HOW MANY `provides` CLAUSES IN stdlib / anthill-stl / anthill-cpp-gen / examples /
anthill-todo BIND THE SPEC'S CARRIER PARAMETER TO SOMETHING THAT IS NOT THE
ENCLOSING SORT. The count decides whether this lands as a refusal, a warning, or
nothing. A legitimate population plausibly exists — a spec parameter that is not
the carrier (`provides Effect[T = ConsoleOutput]` on `sort Console`, kernel-language
§8.7 "one carrier declaring one spec twice") binds a non-self type ON PURPOSE, so
the rule cannot be "every binding must name the enclosing sort". The discriminator
has to be the SPEC'S CARRIER PARAMETER specifically, and identifying that parameter
is itself unsettled — nothing declares a sort to BE a spec (059's fact-ban section:
no `spec` keyword, no `SymbolKind::Spec`, every reader infers it from shape).

SO THIS IS NOT A ONE-LINE GUARD, which is why it is a ticket and not an inline fix.

ACCEPTANCE: the corpus count above is MEASURED and reported first, naming each site;
then either (a) a refusal naming the clause, the binding and the enclosing sort, with
a control showing the legitimate non-carrier-parameter population still loads, or (b)
a recorded decision that the shape is legal with the spec sentence to match. Either
way kernel-language.md §5.1's paragraph "A `provides` clause names its subject by
WHERE it is written" is updated to say what the bindings mean. Each test says which
case fails when the change is backed out. cargo-test green via rustland/scripts/test.sh.

REFERENCE: WI-1000 (measured it, admitted the production in a namespace body,
`ProvidesClauseNeedsSort`), 059 R3 "A SPEC CLAIM, written `provides`", 058 §4
(retiring the `fact X[…]` spelling — this is the question that spelling change
would inherit), WI-1032 (two provisions of one spec at one application), §8.7.
