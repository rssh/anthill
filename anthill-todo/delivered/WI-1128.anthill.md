## Description

WI-714/WI-731 follow-up: join over a 1-COLLAPSED or MEMBERSHIP operand. SPLIT OUT OF WI-731 (user, 2026-08-18), which now owns only the column-name COLLISION half; the two are independent and this one is expected to be much cheaper, so bundling them would have made each change's measurement answer for the other.

TODAY, a LOUD LOAD ERROR and correctly so: concat_named_tuple_types (rustland/anthill-core/src/kb/typing.rs) refuses an operand that is not a named-tuple type, with "[concat] operand a must be a named-tuple type (a relation with at least two named columns); a 1-collapse / membership schema is not supported". So r1.join(r2, cond) does not load when either row 1-collapsed.

WHY THE NAME IS MISSING: a relation with ONE free head variable presents its schema as that element rather than as a 1-field record (Relation[Board], not Relation[(board: Board)]), and a ZERO-column relation presents as Unit. The 1-collapse happens at the TYPER's schema boundary, so by the time Concat runs there is no field name left to merge — and a merged schema needs one for every column, since a row is materialized as a named tuple keyed by column name and join_run fills the condition's holes by that same name.

FIX DIRECTION: 052 OQ5 keeps the STORED element as the 1-field record, so the name is likely RECOVERABLE at the boundary rather than reconstructed — find the site that collapses it and read the pre-collapse name there, instead of inventing one (an invented _1 / left would be a name no rule declared, the same defect that sank automatic qualification for WI-731). CENSUS FIRST: the 1-collapse is not only Concat's problem — find every reader that assumes a named-tuple schema (Without's reducer for fix, Project's for project, join_run's merged column set, the materialization that builds a row) and say which of them a recovered name fixes and which still refuse. A fix measured on Concat alone would leave the others refusing for the same reason.

MEMBERSHIP (0-column, Unit) MAY NOT BE THE SAME QUESTION and should be decided separately in this ticket: a 0-column relation has NO columns to merge, so joining one is arguably a filter rather than a join, and the honest answer may stay a refusal with a message naming negate/where instead. Decide it, do not let it fall out of the 1-column fix.

ACCEPTANCE: a join with a 1-collapsed operand either RUNS end-to-end with the recovered column name, selecting the right rows (drive the values, not "it loads"), or stays a loud error whose message names the fix and the reason; the 0-column/membership case is decided explicitly and its verdict stated at the refusing site; nothing keyed on join's identity in the typer (Concat stays a general type constructor); a back-out measurement is stated at the test site; existing wi714_join / wi728 / wi732 tests green; cargo-test green via scripts/test.sh.

CORRECTION AND MATERIAL CHANGE OF CONCLUSION, after /code-review high (2026-08-18). The framing in the entry above is incomplete in a way that changes the answer, not just the wording.

THE ERASURE IS OF ARITY, NOT MERELY OF THE NAME - and this CHANGES THE ANSWER, it does not decorate it. The entry above frames the whole ticket as a lost column NAME. That is the arity-1 case of a bigger fact: `collapse_schema` returns the sole column's TYPE, so a collapsed schema no longer says HOW MANY columns it came from. Three readings become indistinguishable at type level, not one:
 * arity 1 - the name is gone (what the ticket was filed about);
 * arity 0 vs 1 - `Unit` is both "no columns" and "one `Unit`-typed column" (WI-728's recorded limit);
 * arity n vs 1 - a named tuple is both "n columns" and "ONE column whose type is that n-field tuple". THIS ONE WAS MISSED, by the ticket and by my first pass.

WHY THE THIRD ONE MATTERS MORE THAN THE OTHER TWO. It CANNOT be refused: the collapsed reading is spelled exactly like the ordinary working case, so refusing it would refuse every ordinary join.
