## Description

Stream.head / headOption / tail RESOLVE under SLD but do NOT EVALUATE -- a rule-backed spec op has no interpreter path. CONTEXT: surfaced (again) closing WI-714's consumption story; a general Stream/eval gap, NOT relation-specific. stream.anthill defines the consumption laws equationally -- 'rule head(?s) = fst(?p) :- splitFirst(?s) = some(?p)' (stream.anthill:97-104) -- and stream.anthill:78-80 states the consequence outright: 'the interpreter has no equational-rewrite fallback, so the law rules below alone make isEmpty resolvable but not evaluable'. eval.rs:1624-1633 implements it: a spec op whose ONLY definition is equational rules has no own sort_ops entry, so the inherited entry points back at the body-less spec op (impl_target == target), the 'if impl_target != target' guard at eval.rs:1634 skips it, and the call falls through to a loud UnknownOperation. The one eval->SLD bridge (WI-625, eval.rs:1653-1662) cannot rescue it: eq_bridge_target (eval.rs:1755) returns None unless args.len() == 2, so arity-1 head(s) is out immediately, and its own doc says functional rule-backed ops 'carry no predicate goal to prove and stay a loud UnknownOperation'. CONSEQUENCE: on any Stream carrier that does not OVERRIDE them with a body (a Relation, a LogicalStream), '.head' / '.headOption' / '.tail' type fine and then fail at eval -- the ops that DO run are the body-backed ones (takeN / find / isEmpty / map / filter) and the primitive splitFirst. Ops with a default BODY (takeN, isEmpty) were given one for exactly this reason (the WI-362 pattern: 'the body is the same one splitFirst step'). Every WI-714 test hand-rolls headOption out of splitFirst as a result. FIX DIRECTIONS (pick one): (a) give head/headOption/tail DEFAULT BODIES over splitFirst, the WI-362 pattern already used for takeN/isEmpty/find -- smallest, uniform, keeps the laws as laws; (b) an equational-rewrite fallback in eval -- much larger, and the interpreter deliberately has none. RELATED: WI-567 (split head into a total headOption + a guarded-Error head on concrete List) is a DIFFERENT ticket -- it is about the guarded-Error TYPING of an empty head, and notes 'the eval-side raise of an empty head is a WI-567 follow-on, NOT yet wired'. This ticket is the plain evaluability of the happy path on an abstract carrier. ACCEPTANCE: 'r.headOption' / 'r.head' on a Relation (and on any LogicalStream) EVALUATE, returning the first materialized row; the empty case behaves per the declared type (headOption -> none); 052's NotFound table and relation.anthill's doc comment can drop their 'does not evaluate, use splitFirst' caveats; the wi714 tests can spell .headOption directly; cargo-test green via scripts/test.sh.
