## Description

AN OPERATION'S OWN DESCRIPTION BLOCK IS PARSED AND SILENTLY DROPPED — the grammar
accepts it, the IR has nowhere to put it, and NO `DescriptionInfo` fact is emitted.

MEASURED (WI-1000), two spellings against one sentinel string, counting
`anthill.reflect.DescriptionInfo` facts after a full load:

  describe show {< SENTINEL >}                     1 hit    -- standalone `describe`
                                                            DescriptionInfo(target: show, …)

  {< SENTINEL >}                                   0 hits   -- the operation's OWN block
  operation show(x: Rec) -> Int64 = 7

WHERE IT IS LOST, exactly: `grammar.js` `operation_declaration` opens with
`repeat(field('description', $.description_block))`, and `operation_entry` (the
`operation { … }` block form) does not even have that. `parse::ir::Operation` has no
`descriptions` field — compare `AbstractSort.descriptions` and
`SortWithBody.descriptions`, which both exist and both reach `emit_desc_fact` — so
`convert_operation` never reads the field and the text is gone before the loader.
Nothing warns. `grep -n '"description"' parse/convert.rs` finds four readers; none
of them is an operation.

WHY IT MATTERS BEYOND TIDINESS. §4.1 makes a description block "free-form text,
preserved as KB facts", and the reflect layer is what a tool reads to document an
API — so today an operation, the single most documentation-worthy declaration in the
language, is the one that cannot carry documentation attached to itself. It also
forced a decision elsewhere: 059 R3 admits a standalone `describe` in a secondary
entry whose target the entry declares, and one of the reasons recorded for admitting
it rather than refusing it outright is precisely that a `describe` is TODAY THE ONLY
WAY to document a member (WI-1000; docs/proposals/059-secondary-entries.md, the R3
classification table). Closing this gap does not overturn that verdict — the rule is
keyed on the TARGET, not on the absence of an alternative — but the reason should be
re-read at the site when it does.

SCOPE: add `descriptions: Vec<String>` to `parse::ir::Operation`, read the field in
the operation converter (both the long form and `operation_entry`, adding the
`repeat(field('description', …))` the block form lacks), and emit `DescriptionInfo`
from `load_operation` the way `load_abstract_sort` already does for a sort. Check
whether a `const` has the same hole while there (`parse::ir::Const` likewise carries
no `descriptions`) and say so either way.

ACCEPTANCE: an operation's inline `{< … >}` emits a `DescriptionInfo` naming that
operation, DRIVEN by reading the fact back — not by asserting the program loads;
same for the `operation { … }` entry form; a control shows the standalone `describe`
spelling still emits exactly one fact and the two do not double-emit when both are
written; a tree-sitter corpus case pins the block form's new `description` field. Each
test says which case fails when the change is backed out. cargo-test green via
rustland/scripts/test.sh.

REFERENCE: WI-1000 (measured it; the 059 R3 `describe` verdict that cites it),
kernel-language.md §4.1 (description blocks), §5.4 (operation), `load_abstract_sort`
/ `emit_desc_fact` as the working precedent.
