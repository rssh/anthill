## description

Proposal 056 section 2.3 — THE RULE-HEAD REST-PATTERN FACE of variadic capture, the half that never shipped. 056 is marked Delivered (WI-727) and its OPERATION face is genuinely live (measured below), but section 2.3 is absent from the language, not merely unwired.

MEASURED ABSENT, by grep on the current tree: the token appears in EXACTLY ONE grammar rule — tree-sitter-anthill/grammar.js:538, the `param` rule ("optional(field('rest', token('...')))"). A RULE HEAD cannot carry it, so nothing downstream could implement it. 056's own status line lists it under "First-increment scope / deferred", which is accurate.

WHAT SHIPPED, so the boundary is not guessed (probes, since removed): `cap[R](x: Int64, ...rest: R)` called `cap(1, a: 2, b: 3).a` returns Int(2); the capture as the only parameter, `cap(a: 5).a`, returns Int(5); the EMPTY capture `cap(1)` is the identity (OQ #6). That is the operation face, sections 2.1 + 2.2, and it is what `fix` runs on and what WI-1127 reused for where_run / join_run.

WHAT SECTION 2.3 IS FOR, and why it is not cosmetic. The operation face hands the callee a record whose TYPE is built from each argument's TYPE — normalize_variadic_capture (rustland/anthill-core/src/kb/typing.rs) does `captured_fields.push((*label, r.ty.clone()))`. So a captured argument's VALUE is gone by the time a return-type constructor reduces, and kernel-language section 4.5 says why that cannot be worked around: "a name reaches type position only as a denoted, since there are NO SINGLETON TYPES". A captured `"name"` therefore arrives as `String`. The rule-head face is the other channel: it binds the leftover named args as one record OCCURRENCE that a compile-time macro reads AS SYNTAX (043.1 / WI-722), where the labels and their sub-occurrences are still present — the same channel `guarded_of` / `conjoin_of` already use for a row lambda. It is the only way a variadic construct can get a NAME to the type level.

DRIVING CLIENT: WI-731 (join column-name collision), whose agreed surface is a `rename` operator. `r.rename(who: r.name)` needs exactly this: variadic named arguments delivered as syntax so the macro can read `name` and splice both the runtime spec and the denoted map its return-type constructor consumes — precisely how the typer already splices `project_run[Keep](r, spec: Term)`. Without section 2.3 the only spelling that works today is the explicit type argument `r.rename[Map = (who: "name")]()`, whose ergonomic gain over the existing `r.(who: name, dept: dept, age: age)` is thin — which is what makes this a blocker rather than a nicety. WI-731 is set to depend on this ticket.

SCOPE: (1) GRAMMAR — a rest pattern in a rule head, reusing the SAME fused `...` lexer token the `param` rule already carries (056 records that token as probed conflict-free; the corpus was 176 tests then, re-measure). (2) LOADER — record the rule-head capture, the analogue of `record_op_capture_param` (kb/mod.rs), gated on the same "at most one, TRAILING" conformance the operation face enforces (kb/load.rs), so a malformed head gets no capture entry and the real diagnostic is not buried. (3) The `[simp]` macro engine — pass the collected record as ONE occurrence argument to the macro. (4) The reflect occurrence API the macro reads it with — 056 section 2.3 names sub_occurrences and component names; verify those exist and are reachable from a host macro rather than assuming it.

THIS IS A LANGUAGE CHANGE, so it owns spec text: kernel-language.md section 8.3 (rule heads) plus the section 11 collected grammar. 056's own Affects line already says so. Note the asymmetry with the operation face, which IS specced — section 4 parameters carries "Variadic capture parameter (`...name: R`, proposal 056 / WI-727)" and says nothing about a rule-head face.

ACCEPTANCE: a rule head written with a rest pattern LOADS and its macro RECEIVES the leftover named arguments as one record occurrence whose component LABELS and sub-occurrences it can read — driven end-to-end by a macro that splices something observable and asserting the spliced result's value, never "it loads"; at most one and trailing stays a loud load error on the rule-head face as it is on the operation face; the operation face is UNCHANGED, with the wi727_fix / wi1127_condition_param tests named as the ones that must stay green and a back-out measurement stated at the new test's site; kernel-language.md section 8.3 + section 11 carry the new production; the tree-sitter corpus gains a case and the full corpus is re-measured; cargo-test green via scripts/test.sh.

NOT THIS TICKET: POSITIONAL capture. Measured on the current tree, a positional leftover is a LOAD ERROR in every arrangement — `cap(5)`, `cap(1, 2)`, `cap(1, 2, a: 3)` — contradicting BOTH records in opposite directions: 056 section 3 OQ #2 says "a positional leftover lands in R as a `_N` field" and section 5 says positional capture is "already subsumed ... not needed, and not built", while the status line and normalize_variadic_capture's doc comment say "a positional leftover binds the capture parameter directly". Neither happens. The diagnostic is also poor — two errors, both blaming `cap.rest (op-arg)`, a parameter the author never wrote. That is a separate ticket.
