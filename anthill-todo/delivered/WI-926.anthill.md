## description

A single-constructor sort's NAME resolves to the SORT, so the persistence loader deserializes every row of such a section against an EMPTY field schema and files the fact under the sort symbol. MEASURED with a probe over `sort Project { entity Project(name: String, language: String) }`: `test.Project` -> Symbol(172), sort_kind=Some(Sort), constructor_parent_sort=None, entity_field_names=None; `test.Project.Project` -> Symbol(173), sort_kind=None, constructor_parent_sort=Some(172), entity_field_names=Some(2). The sort takes the plain qualified name and the constructor takes the nested one. `term_ser.rs::resolve_entity_functor` resolves a section's `meta.entity` with `try_resolve_symbol` and therefore lands on 172; the caller then does `kb.entity_field_names(functor).map(..).unwrap_or_default()`, so the `None` becomes an EMPTY field list and every row in the section is reconstructed with no schema -- WI-501's whole point is that reload MUST consult each field's declared type. The rows are additionally asserted with the SORT as their head functor, which is why `toml_ser_test` then finds them via `rules_by_functor(try_resolve_symbol("test.Project"))`: the test and the bug agree with each other. Driving the fix confirms the shape -- resolving through to the single constructor makes the section load with the real 2-field schema, and `toml_ser_test::load_toml_primitives` then fails at its own `rules_by_functor` query because the stored head functor legitimately moves from 172 to 173. So the fix is a persistence BEHAVIOUR change with round-trip tests encoding the current shape, which is why WI-922 did not smuggle it in (the site carries the measurement as a comment).
