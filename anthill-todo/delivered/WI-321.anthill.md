## Description

Cross-file mutually-recursive sort/enum declarations: loader robustness + policy. The loader's scan_definitions is a 4-sub-pass walk (rustland/anthill-core/src/kb/load.rs:225-258): pass1 defines all names across all files; pass2 resolves requires + imports; pass3 registers rule-head Goal functors; pass4 retries deferred predicate imports. This shape ACCIDENTALLY supports cross-file mutual structural dependencies (each file's pass1 ignores the other's content, so both names exist before either file's pass2 runs). Example uncovered during WI-320 (code-review finding #14): effect-expression.anthill imported Type from sort.anthill while sort.anthill (post-WI-320) imported EffectExpression — a mutual cycle whose soundness depended entirely on pass1 being unconditional. SHORT-TERM FIX (WI-320 last commit): colocated EffectExpression into sort.anthill, eliminating that specific cross-file cycle. But the GENERAL question remains: (1) is cross-file mutual structural recursion a SUPPORTED pattern (with documented robustness invariants the loader must preserve), or an INCIDENTAL one (works today, may regress)? (2) Should the loader DETECT cross-file structural cycles and warn / require they be in one file, mirroring how many module systems forbid cross-file mutual recursion (e.g., OCaml's module rec requirement, Rust's per-mod resolution boundary)? (3) Should there be a TEST that pins the invariant (a fixture with a benign cross-file cycle that must keep loading)? (4) Should anthill add a cross_file_recursive annotation or directory-as-module convention to ALLOW the pattern explicitly where intended? RISKS if left unaddressed: (a) a future refactor to a single-pass / streaming loader would re-expose the cycle silently; (b) imports may evolve to carry pass1-needed info (typed-symbol selective imports, qualified-name resolution touching parent files) which deadlocks the cycle; (c) load_incremental (skip-register_prelude path) has the same scan; user code mirroring this pattern across two user files would silently work today but is undocumented. TASK: (a) decide the policy — supported vs incidental, with docs in CLAUDE.md or a comment in scan_definitions; (b) if supported, add a fixture test asserting cross-file mutual structural deps load (e.g., two test files where each entity references the other's Type); (c) if forbidden, add a scan_definitions pass that detects the cycle (DFS over imports + entity field types) and reports a clear error; (d) update brainstorm/proposal docs that hand-wave the 2-pass scan handles cycles with a precise statement of which cycles are actually supported. Surfaced by WI-320 code-review finding #14 (Type vs EffectExpression cycle); the underlying mutual recursion remains (Type/EffectExpression are co-defined data) — colocation hides the cycle but doesnt remove the structural dependency, which any tooling that walks Type field types must still handle.
