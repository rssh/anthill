## Description

Operation-call-model: thread ResolvedTree through dispatch into the IR emitter. WI-224 already produces ResolvedTree::Conditional { impl_sort, sub_resolutions, ... } from resolve(), and WI-227 already has emit_tree_as_projection capable of turning a full tree (including nested Conditionals and FromScope leaves) into nested construct_requirement IR. The two are not yet connected at the dispatch site: find_unique_impl_op (typing.rs:2351-2364) pattern-matches both Leaf and Conditional into DispatchOutcome::Unique(impl_op_sym) and discards the sub_resolutions. From check_apply's perspective the only handle to the resolved impl is its symbol, so record_apply_within_concrete → build_projected_requirements_list runs with callee_spec_sort = spec_sort (the spec) and projects the spec's requires_chain via flat lookup — never invoking emit_tree_as_projection on the actual resolved tree. Symptom: WI-227's emit_tree_as_projection is only reachable today through Strategy 3's synthetic SLD recurrence inside build_dep_projection (the WI-227 test calls it directly). A conditional impl in real anthill source has no path that produces nested construct_requirement IR. Scope: (a) extend DispatchOutcome with a Resolved(ResolvedTree) variant (or thread the tree out-of-band) so check_apply can read it; (b) in the Pin-now arm, pass the full tree to record_apply_within_concrete instead of just impl_op_sym; (c) inside build_projected_requirements_list, when a callee dep's projection comes from a resolved Conditional, emit construct_requirement(impl, [sub-projections...]) directly via emit_tree_as_projection rather than re-running resolve() per dep; (d) fix the latent callee_spec_sort asymmetry — the projection should walk the impl's requires_chain (the actual callee's requirements) rather than the spec's empty chain. Out of scope: defer-to-requirement still resolves at runtime; dynamic dispatch is its own WI; effect propagation through conditional sub-resolutions follows WI-209's substitution rule. Acceptance: cargo-test green; a new integration test where 'fact Eq[T = List[T = A]] :- Eq[T = A]' is registered, a Pin-now call to eq(...) at T = List[Int] is rewritten to apply_within whose requirements list contains construct_requirement(EqList, [construct_requirement(IntEq, nil)]) — not the current empty/spec-projected list. Reference: docs/design/operation-call-model.md §'Call rewrite cases', §'Resolution' (Output ResolvedTree is the direct input to the requirement-insertion pass).
