## Description

BUG (silent wrong-place write): `anthill-todo -d <dir> init` IGNORES -d and scaffolds into the CURRENT DIRECTORY, then reports success naming no path. Every other subcommand honors -d via find_project_dir; init alone hardcodes the cwd.

VERIFIED LIVE (2026-07-17, found during WI-744's code review; run_init is NOT touched by that diff — this is pre-existing):
    cd /tmp/elsewhere
    anthill-todo -d /tmp/target-proj init
      -> 'created anthill-todo/ with:'   exit 0
    ls /tmp/target-proj   -> EMPTY          (the -d target got nothing)
    ls /tmp/elsewhere     -> anthill-todo/  (the scaffold landed here)
The message says 'created anthill-todo/' with no absolute path, so nothing in the output reveals where it went. A following 'anthill-todo -d /tmp/target-proj list' then correctly honors -d, finds no project, and (post-WI-744) says so loudly — but the user has an anthill-todo/ sitting in whatever directory they happened to be in.

LOCUS: rustland/anthill-todo/src/main.rs run_init — 'let dir = cwd.join("anthill-todo")' (~line 354), reached from the dispatch at ~line 494 which returns BEFORE find_project_dir is ever consulted. Contrast every other command, which routes through find_project_dir(explicit_dir) and honors -d.

WHY IT MATTERS BEYOND THE OBVIOUS: this is the same family as the -d footgun WI-744 just closed on the READ side (discovery accepted any directory NAMED anthill-todo, so 'anthill-todo list' from rustland/ silently resolved to the CLI's own crate). WI-744 fixed discovery by MARKER (is_project_dir: project.anthill / workitems.anthill must be present). init is the WRITE side of the same mistake: it decides where the project lives by position rather than by instruction. Note the two now interact usefully — after a misplaced init, discovery from the intended dir fails LOUDLY instead of reporting 'No work items found', which is how this was noticed at all.

FIX: run_init must honor -d. Two sub-decisions: (1) with -d given, scaffold at <dir>/anthill-todo (or at <dir> itself if it is already the project dir? decide, and note find_project_dir treats '<cwd>/anthill-todo exists' and 'cwd IS the project' as distinct arms); (2) the success message must print the ABSOLUTE path it created, so a wrong-place write is visible even when the flag is right — the current message would not have revealed this bug even to someone looking straight at it. Consider also erroring rather than silently re-scaffolding if a project already exists at the target (untested today).

ACCEPTANCE: 'anthill-todo -d <dir> init' creates the project under <dir> and nothing under the cwd; the success message names the absolute path created; running init from a different cwd than -d is covered by a test (anthill-todo/tests/ — note EVERY existing test passes -d, so the discovery/init interaction has no coverage at all today, which is why this survived); 'anthill-todo -d <dir> list' immediately after 'init -d <dir>' finds the project; cargo-test green via scripts/test.sh.
