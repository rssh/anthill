## Description

FOUND WHILE DRIVING WI-975 (see docs/proposals/059-secondary-entries.md).
`sort X ... end` that REUSES an existing symbol never records the Sort category,
so a `namespace X` written BEFORE the sort silently breaks the sort.

MEASURED, one pair, the two declarations in both orders:

  namespace q4a                     namespace q4b
    namespace Rec                     sort Rec
      operation helper(...)             entity Rec(n: Int64)
    end                               end
    sort Rec                          namespace Rec
      entity Rec(n: Int64)              operation helper(...)
    end                               end
  end                               end

  ns-first:   kind_of=Some(Namespace)  has_kind(Sort)=FALSE
              has_kind(Entity)=FALSE   nested `q4a.Rec.Rec` EXISTS
  sort-first: kind_of=Some(Sort)       has_kind(Sort)=true
              has_kind(Entity)=true    nested `q4b.Rec.Rec` absent

So in ns-first order the name is not a Sort, `is_sort_scope` is therefore false,
the EPONYMOUS CONSTRUCTOR never collapses (§6.3 / WI-926), and a phantom nested
`X.X` is defined. Downstream, a member call on such a receiver reports the sort
as `q3b.Rec.Rec` and dot dispatch misses.

CAUSE, in `scan_items_pass1`'s `Item::SortWithBody` arm (kb/load.rs ~2700):

    let (sym, is_new) = if let Some(&existing) = kb.symbols.by_qualified_name.get(&qualified) {
        (existing, false)                      // <-- no add_kind(Sort) here
    } else {
        (kb.symbols.define(&short, &qualified, SymbolKind::Sort, ...), true)
    };

This is EXACTLY the defect WI-926 fixed one arm below. The `Item::Entity` arm
records its category explicitly, with a comment saying why: "Recorded from the
DECLARATION, not from which arm above produced the symbol -- two of the three
never call `define`, so relying on `define` to carry the category silently loses
it." `SortWithBody` has the same two-arm shape and was never given the same fix.

NOTE the reuse branch is also the PRELUDE-bootstrap path (`register_prelude`
defines `anthill.prelude.List` before stdlib's `sort List ... end` reuses it) --
that one is unaffected because `register_prelude` already defines with Sort, so
the fix is additive there.

RELATED, decide together: `SortWithBody`'s reuse branch also skips the
`add_parent` that wires the sort's scope to its enclosing scope, which is why
`entity X(...)` followed by `sort X ... end` produces a body that resolves
NOTHING from outside itself. Proposal 059 R1 refuses that shape outright, so
that half may become unreachable rather than fixed -- but the category loss
above is reachable via `namespace X` + `sort X`, which R2 explicitly BLESSES.

ACCEPTANCE: both declaration orders give the same categories and the same
eponymous collapse. A test asserts, for the pair above, `has_kind(Sort)` and
`has_kind(Entity)` true in BOTH orders and no nested `X.X` in either, and drives
a member call on the receiver in BOTH orders. Say at the test site which
assertions fail when the fix is backed out (the ns-first row does; sort-first
passes either way, by design, as the control). cargo-test green via
rustland/scripts/test.sh.

DELIVERED (2026-08-04). ONE LINE SHIPPED, AND ONE REVERTED — the revert is the
more useful half of this ticket.

WHAT LANDED. `add_kind(sym, SymbolKind::Sort)` unconditionally after the two-arm
lookup in scan_items_pass1's Item::SortWithBody arm. `define` accumulates
categories (WI-926) but the reuse arm never calls it, so the `sort` keyword's own
category was lost whenever the name already existed. Exactly the fix the
Item::Entity arm already carries, for the same two-arm shape; idempotent, so the
prelude-bootstrap path is unaffected.

WHAT I BUILT, MEASURED GREEN, AND THEN REVERTED. Driving found a second
`is_new` gate on the same arm — the variant-exposure link — and I un-gated it,
added an idempotent `add_parent_once`, and ran the full workspace suite: 0
failures. /code-review then refuted it three ways, each of which I re-drove myself
before acting:

  1. `is_new` is false for TWO populations, and un-gating serves the wrong one.
     register_prelude pre-registers anthill.prelude.{List, Option, TypeExtractor,
     EffectExpression} and anthill.reflect.{MemberKind, Expr, Pattern}, all
     re-declared with variants in stdlib source, so all seven gained an exposure
     link they never had — ~55 short names newly bare-resolvable. DRIVEN
     consequence: bare `guarded` under wildcard imports goes from resolving
     uniquely to LogicalQuery.guarded to AMBIGUOUS against
     EffectExpression.guarded. Both directions measured by flipping the one line.
  2. It silently half-wired the shape this ticket deliberately left refused.
     `entity Rec(n)` + `sort Rec { entity Inner }` started loading clean with bare
     `Inner` resolving OUT, while the body still could not see IN (the enclosing
     link stays gated). And MY OWN PINNING TEST FOR THAT SHAPE COULD NOT SEE IT —
     its fixture had no variant, so `has_variant` was false and the new path was
     never entered. A pinning test blind to the change it pins is not a pin; the
     fixture now carries a variant.
  3. My justification for `add_parent_once` was FALSE. I wrote that a duplicate
     parent link 'can turn a unique resolution into Ambiguous'. It cannot:
     resolve_in_scope_recursive has a `visited` guard (intern.rs:672) and dedups
     matches (723-725), and a genuinely duplicated identical link (via a plain
     `import <ns>.C` beside `sort C { entity Red }`) loads clean. The helper was
     harmless and existed to prevent a harm that does not occur.

THE LESSON, and it is the one this ticket should be remembered for: A GREEN FULL
SUITE WAS NOT EVIDENCE. There is exactly one wildcard import in the whole repo,
inside a parse test, so nothing in-tree could trip the ambiguity. I had flagged

passing tests in place of measuring it. The corpus does not exercise a resolution
