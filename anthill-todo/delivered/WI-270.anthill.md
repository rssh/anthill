## Description

Refactor typer to thread top-down expected type. Add an `expected: Option<TermId>` parameter to `type_check_node` / `TypeWorkOp::Visit` / `TypeBuildFrame::*` so the typer carries the caller-side type hint into each sub-expression. The hint flows through Let value (from annotation), Match branches, If branches, Lambda body (from arrow decomposition), and Apply/Constructor return-type unification before the unresolved-type-param check fires. Driver / unblocks: (a) closes WI-269 (proposal 042) Phase D `acceptance case 4` — "unresolved type-param diagnostic" — by giving check_apply_iter a way to seed subst from caller context before deciding whether any op type-param Var remains unbound. The current Phase D leaves a `// TODO(diag):` marker in typing.rs::seed_op_type_args for the silent-drop site. (b) retires two ad-hoc side-channels that solve the same problem piecemeal: `SimpleTermStore.let_type_annotations` (proposal 035 form 1, threaded through let_expr as `type_name`) and `SimpleTermStore.call_type_args` (proposal 042 Phase B, threaded through apply as `type_args`). Once `expected` is the normal flow, both side-channels can be deleted and the loader stops poking at them. (c) enables natural inference for 0-arg constructors and pure HOFs in annotated positions: `let xs: List[Int] = nil()`, `operation foo() -> List[Int] = nil()`, `Map.empty()` without the let_type_annotations workaround. Shape per arm: Apply / Constructor — unify `expected` with the call`s return type before the unresolved check, so caller context flows into the seed; Let — pass annotation to value, own `expected` to body; Match — pass `expected` to each branch body, widen result; If — pass `expected` to both branches; Lambda — if `expected` is an arrow, decompose and pass the inner return type to the body; literals / Var / Ref — ignore. Cost estimate: ~10–15 visit_X handlers gain a 3–5 line expected-forwarding block, plus a 2-line `if let Some(exp) = expected { unify_types(kb, &mut subst, exp, op.return_type); }` at the Apply/Constructor build. The iterative typer`s Visit/Build threads `expected` as a field. Acceptance: cargo-test green; the side-channels `let_type_annotations` and `call_type_args` are removed; WI-269 Phase D`s TODO(diag) marker is replaced by a real diagnostic that names the unconstrained type-param and suggests `op[T = ...]`; `term_as_entity(t)` with no caller context produces a clean error, with caller context (`let v: Option[WorkItem] = term_as_entity(t)`) it pins E to WorkItem; `let xs: List[Int] = nil()` typechecks without a workaround. Out of scope: subtyping / variance changes; effect-row top-down inference. Risk: touching every Visit arm of the iterative typer is invasive; staging the migration (introduce field with default None, migrate arms one at a time, then delete the side-channels) reduces blast radius.
