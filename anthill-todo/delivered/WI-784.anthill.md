## Description

Multi-binder LAMBDAS cannot be applied at all -- `enter_closure` is strictly UNARY, so a lambda passed as a function VALUE and applied with N arguments traps while the identical call with a named OPERATION succeeds. Lambdas and operations are therefore NOT interchangeable as function values, and the failure is invisible at load. MEASURED end-to-end (fresh Interpreter per case, positive control fires): `operation apply_arrow(f: (acc: Int64, x: Int64) -> Int64) -> Int64 = f(3, 10)` gives Ok(Int(-7)) for `apply_arrow(sub2)` but `ArityMismatch{op: "closure", expected: 1, got: 2}` for `apply_arrow(lambda (acc, x) -> acc - x)`. THE STDLIB IS ALREADY WRITTEN AGAINST THE BROKEN CONVENTION: prelude/list.anthill:83 is `foldLeft(t, f(init, h), f)` and :87 is `f(h, foldRight(t, init, f))` -- both apply the callback with TWO SEPARATE ARGUMENTS, and FiniteCollection.foldLeft/foldRight delegate to them (finite_collection.anthill:47,50). Measured, BOTH SPELLINGS LOADING CLEAN: `foldLeft([1, 2, 3], 0, shift)` = Ok(Int(123)) but `foldLeft([1, 2, 3], 0, lambda (acc, x) -> acc * 10 + x)` = ArityMismatch{expected: 1, got: 2}. So `xs.foldLeft(0, lambda (a, b) -> a + b)` -- the single most idiomatic higher-order call in the language -- typechecks and then traps at eval. ARITY-ZERO TWIN: `enter_closure`'s `args.len() != 1` rejects 0 as well as 2; prelude/delay.anthill:50 builds `delayed(lambda () -> a)` and :61 forces it with `case delayed(t) -> t()`, routing through dispatch_call with an empty arg vec into the same rejection -- hidden only because Delay's one test (wi516_graded_effect_row_test.rs) is load-only. ROOT CAUSE: `spread_eta_args` (eval.rs ~1675-1706) converts a single tuple argument into N positional args for `Value::OpRef` ONLY, matching the op's declared arity; there is NO closure-side counterpart, and `enter_closure` (eval.rs ~1849) rejects `args.len() != 1` outright because a multi-binder lambda is ONE TUPLE PATTERN -- see proposal 018-expressions-and-operation-implementation.md:114 ("Lambda always takes _one_ argument. Multiple parameters use tuple destructuring"), eval/closure.rs:31-34 and eval/eval.rs:768-771. Note 018 nonetheless shows `fold(lambda (acc, x) -> add(acc, x), zero, my_list)` and `zip_with(lambda (a, b) -> ...)` as INTENDED usage at :126-128,:194,:201, so the proposal contradicts itself and the stdlib followed the intended form. WHY IT NEVER SURFACED (all verified, no counterexample found): (a) every EVALUATED higher-order call site across stdlib/examples/tests passes a named OPERATION, never a lambda -- ~30 sites (addp, shift, count_l, noisy_add, add_name, ...), zero lambdas; (b) every multi-binder lambda that IS written is either applied with ONE tuple (eval_test.rs:722,726,730; wi620_paren_lambda_param_test.rs:58-59; wi517_typed_lambda_binder_test.rs:97) or never applied at all -- the where/join row lambdas are erased into a LogicalQuery as syntax at compile time (relation.anthill:133,178-179), which is why the repo's most common multi-binder lambda (join's `lambda (c, q) -> ...`, 9 occurrences) never reaches enter_closure; (c) every site that MIXES the two is LOAD-ONLY -- wi605_bare_arrow_lambda_test.rs:81 passes a multi-binder lambda to foldRight, and wi605_bare_arrow_lambda_test.rs:110-130 defines `operation apply2(arrow: (a: Int64, b: Int64) -> Int64, x, y) = arrow(x, y)` describing itself as "the foldLeft `f(init, h)` pattern" -- both asserted only via load_errors, each one `interp_for` away from failing. NOT TRACKED ANYWHERE UNTIL NOW: the failure is recorded only as a discarded "control" sentence inside WI-783's description, whose delivery commit (07ecdec5) explicitly REFUTED it as evidence for that ticket (the trap fires on plain POSITIONAL `f(3, 10)` too, so it never had anything to do with named arguments) and whose fix touched only kb/typing.rs -- eval.rs was never opened, so enter_closure was never in scope. WI-783's reorder makes this path MORE reachable: it now rewrites `f(x: 10, acc: 3)` into a positional `f(3, 10)`, landing directly on the broken call. FIX DIRECTION: mirror `spread_eta_args` on the closure side -- have `enter_closure` accept N arguments by tupling them when the binder is an N-element tuple pattern (and accept 0 for a nullary binder). That fixes the arity-0 twin at the same time and requires NO stdlib change, since the existing `f(init, h)` convention keeps working. ACCEPTANCE: `foldLeft([1, 2, 3], 0, lambda (acc, x) -> acc * 10 + x)` evaluates to 123, agreeing with the named-operation spelling; a 2-binder lambda applied as `f(3, 10)` and as `f((3, 10))` both evaluate; a nullary `lambda () -> 5` forced via `t()` evaluates; a regression test drives the LAMBDA and OPREF spellings of the SAME call and asserts they AGREE end-to-end -- using a FRESH Interpreter per case, because reusing one after a trapped call returns a bogus Internal("deliver: parent frame had no awaiting state") on every later call and reads as a second independent bug; the two load-only wi605_bare_arrow_lambda_test.rs cases gain eval assertions; full workspace green via scripts/test.sh.

### 2026-07-20T15:03:52Z — feedback — claude

DELIVERED. A closure now accepts an N-argument application, so a lambda and a named operation are interchangeable as function values.

ROOT CAUSE AND SHAPE OF THE FIX. dispatch_call has two callable arms. The OpRef arm ADAPTS its arguments (spread_eta_args, eval.rs:1675: one tuple argument spreads across a multi-parameter op). The Closure arm did not adapt at all -- enter_closure opened with a flat args.len() != 1 rejection. The fix is that arm's missing DUAL, gather_closure_arg: since a multi-binder lambda is ONE tuple pattern, N arguments are GATHERED back into the tuple its binder list destructures. Where spread_eta_args spreads one into N, this gathers N into one. That is why no stdlib change was needed: the existing f(init, h) convention now lands correctly.

The 0-component case falls out of the same rule rather than needing its own arm -- lambda () -> a is a Pattern::Tuple of zero components, so a zero-argument call gathers to the empty tuple and matches. That closed the arity-zero twin for free.

WHAT LANDED: eval/eval.rs gather_closure_arg + the enter_closure call site (the arity decision now needs the param pattern, so it moved after the closure-arena read); Pattern::binder_arity in kb/node_occurrence.rs; lambda_written_arity rewritten to call it; docs/kernel-language.md section 4.7 gained an "Applying a lambda" paragraph; new suite wi784_closure_arity_test.rs (10 tests); the two load-only wi605 cases now DRIVE.
