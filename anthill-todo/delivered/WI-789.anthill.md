## description

`TermPrinter` ERASES a `_`-prefixed tuple field label at ANY index, so printing a tuple type emits text the parser rejects -- or, where it does reparse, silently RENAMES the field. `is_positional_name` (persistence/print.rs ~992) tests `n.strip_prefix('_').is_some_and(|d| !d.is_empty() && d.bytes().all(|b| b.is_ascii_digit()))` -- any underscore followed by digits, regardless of which index the component sits at -- and its sole caller `write_named_tuple_element` (~969) then drops the label entirely: `if !positional { write name; ": " }`. MEASURED via `TermPrinter::print_term` on a declared parameter type: `(_01: Int64, b: Int64)` prints as `(Int64, b: Int64)` and `(_2: Int64, b: Int64)` prints as `(Int64, b: Int64)`. Both lose the label. That output is then REJECTED by the parser -- "tuple type cannot mix positional and named fields" -- so the printed form does not round-trip at all; and in the shapes where such text does reparse, the loader mints `_1` for slot 0, i.e. a silent field RENAME across a persistence round-trip. The control `(a: Int64, _b: Int64)` prints intact, so the loss is exactly the `_`+digits class. WHY NOW: these are precisely the two shapes WI-786 pinned as USER labels -- `leading_zero_label_is_not_synthetic` and `synthetic_name_for_the_wrong_index_stays_named` assert that `_01` and a `_2` written first are user labels that keep their position and stay reachable by name. Before WI-786 the classifier and the printer AGREED (both treated any `_`+digits as positional); WI-786 narrowed the classifier to the exact synthetic name for a component's OWN source index and did not narrow the printer, so the two now contradict each other and a shipped test asserts one side of the contradiction. This is PRE-EXISTING -- the printer behaved this way before WI-786 -- but WI-786 turned it from a shared (wrong) convention into an explicit disagreement, which is why it is worth closing now rather than later. BROADER CONTEXT: the `_N` positional-label convention has EIGHT independent minters (parse/convert.rs `intern_positional_label`, kb/load.rs x2, kb/typing.rs x4, persistence/term_ser.rs) and FIVE independent recognizers spelling FIVE different rules -- this printer (`_`+digits, any index), `is_synthetic_positional_label` (eval/eval.rs, exact synthetic name for its own index, rejects leading zeros), `is_positional_tuple_names` (kb/typing.rs ~23775, bare `parse::<usize>()`, so `_01` IS positional), `field_access` (eval/builtins.rs ~280, `strip_prefix` + parse, any index), and `validate_projection_labels` (parse/convert.rs, rejects ANY `_` prefix). No single owner. FIX DIRECTIONS: (a) narrow `is_positional_name` to match `is_synthetic_positional_label` -- the label must be the synthetic name for its own index -- which requires threading the element index into `write_named_tuple_element` (the caller already iterates, so the index is in hand); (b) better, extract the convention to ONE owner: a `positional_label(index) -> String` / `positional_label_index(label) -> Option<usize>` pair in `intern.rs`, which sits below parse/, kb/, eval/ and persistence/ in the dependency order and is therefore callable from every producer and consumer, then route all five recognizers through it so a future narrowing cannot land in one and miss four. (b) also closes the term_ser 0-based drift filed separately. Found by /code-review on 93b23188 (two review angles independently drove the print-then-reparse failure). ACCEPTANCE: printing a tuple type whose label is `_`-prefixed but NOT the synthetic name for its own index preserves the label, so `(_2: Int64, b: Int64)` and `(_01: Int64, b: Int64)` print in a form the parser accepts and that reloads to the same type; a genuine positional tuple type still prints without labels (`(Int64, Int64)`, not `(_1: Int64, _2: Int64)`); a regression test asserts print-then-reparse is the IDENTITY on both shapes, not merely that printing does not panic; if direction (b) is taken, the five recognizers share one definition; full workspace green via scripts/test.sh.
