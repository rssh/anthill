## description

A DUPLICATE-labelled tuple literal loads clean and yields a WRONG-TYPED value. MEASURED end-to-end: `operation take(t: (b: Int64, a: String)) -> String = t.a` with `operation drive() -> String = take((a: 1, b: 2, a: "ess"))` loads with ZERO errors and drive() returns Int(1) from an operation declared -> String. (Pinned live by duplicate_label_alignment_resumes_after_the_previous_match in wi800_tuple_threading_alignment_test, which RECORDS the wrong answer rather than endorsing it.) TWO things meet. (1) NOTHING REFUSES THE DUPLICATE: a tuple literal may carry the same label twice, typing as (a: Int64, b: Int64, a: String). Spec 4.5 does not state that component names must be distinct -- but the spec's own projection rule already gives the reason it should: `x.(a, a)` and the rename collision `x.(k: f1, k: f2)` are load errors because 'a duplicate-key tuple would silently drop the later column' (kernel-language.md, Distinct keys), and a call's named arguments likewise reject a 'duplicated label'. The one construct that can MINT such a tuple is the one place the rule is missing. (2) THE RELATION AND THE READER THEN PICK DIFFERENT COMPONENTS: align_named_tuple_slots (kb/typing.rs) is name-keyed and order-PRESERVING -- the scan resumes AFTER the previous match -- so expected `a`, searched after `b` matched slot 1, takes slot 2 (the String) and the program conforms; field_access (eval/builtins.rs) reads by name and takes the FIRST `a` (the Int64). Same wrong-typed-value class as WI-788, reached through LABELS rather than through order. FIX DIRECTION: refuse a duplicate label where a named tuple is BUILT -- the literal, and the tuple TYPE -- which makes the disagreement UNREACHABLE rather than arbitrating it. Teaching both sides to pick the same component is NOT sufficient: a component reachable by neither its name nor its position is still a component nothing can read, which is precisely what the spec's Distinct-keys rule refuses elsewhere. Found while delivering WI-800, by probing whether its two candidate correspondences (first-match by name vs the cursor scan) could disagree on a real program -- they can, and the program that shows it is accepted. ACCEPTANCE: the program above is REFUSED at load with a located diagnostic naming the duplicated label; spec 4.5 states the distinctness rule alongside the existing projection/named-argument ones; the wi800 test is updated to assert refusal; full workspace green via scripts/test.sh.
