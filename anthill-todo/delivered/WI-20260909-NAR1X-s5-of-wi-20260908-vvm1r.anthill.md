## Description

S5 of WI-20260908-VVM1R (umbrella): THE OP->RULE REQUIREMENT CHANNEL, for POLYTYPES -- requirement-channel.md sec 10 item 3, pulled in because 'if we extend rules to handle types, polytypes should be there' (user, 2026-09-09).

THE CROSSING DROPS THE SLOT TODAY. prove_rule_predicate(pred, args) (resolve.rs:6071) takes a predicate symbol and ground args and nothing else; prove_rule_predicate_value (eval.rs:3084) calls it from an eval frame that HOLDS frame.requirements and passes none of them. The rule->rule crossing, by contrast, already works: WI-1040's a_clause_dictionary_crosses_a_rule_boundary_and_is_checked drives a caller's ?d bound in sigma reaching the callee's ?d = require[...] with CHECK mode firing. It is specifically the OP->RULE edge that has no parameter.

THE CHANNEL SHAPE, and it is lighter than the signature change sec 10 item 3 offered as its alternative. prove_rule_predicate builds its OWN ResolveConfig locally, and ResolveConfig already carries gamma (proposal 050 / WI-537) -- a typer-narrowed overlay consulted at the candidate step, whose own doc says it 'rides the config, not the per-frame assumed_facts stack' BECAUSE it is global to one resolve call. Caller-supplied dictionaries are that same shape: global to one prove_rule_predicate call. So the channel is a ResolveConfig field seeded from frame.requirements and read at builtin_find_dictionary's out arm -- SUPPLY where the local derivation is Undecided, CHECK where it is unique (WI-860: two derivations of one relation must agree; disagreement is a loud failure, never a precedence win). That is sec 6's rule already written down, given a carrier.

WHAT THE ANCHOR DOES AND DOES NOT COVER -- state this at the site, because the two halves look alike and are not. Carrier BOUND at the call: the rule grounds its own requirement from the head (typeof(?x)) and needs no channel; a supplied slot would merely have to agree. Carrier NOT derivable from any value the callee holds: only the caller's slot knows the instantiation. That second case has a precise marker -- op_has_spec_carrier_param == false (Monoid.unit(), a nullary or all-content spec op): no carrier argument exists, so no carried type can be read, and neither the witness scan nor the anchor can say anything.

A BOUNDARY TO NAME RATHER THAN PROMISE: PredicateProof is Proved / Refuted / Undecided / Undefined -- a CLOSED GROUND TEST. A generative p(?out) from an operation body does not traverse this edge at all, so this ticket delivers the ground call whose requirement the callee cannot derive, NOT generative use. Say so at the acceptance so it is not mistaken for something delivered.

THE SECOND HALF IS ATTRIBUTION, which is why this depends on S4. sec 10 item 3 names it: 'the caller-name -> spec attribution at the boundary'. Attribution by spec base is the first cut; where the caller holds two slots for one spec at different carriers, the carrier decides -- the SAME carrier-directed rule S4 establishes for the weave. One rule, two readers; a second spelling of it would drift.

ACCEPTANCE. A rule whose requirement is at a CARRIER-LESS spec op, called as a ground test from a POLYMORPHIC operation that holds the dictionary, answers -- asserted BY VALUE, with two suppliers answering different numbers. CONTROLS: with the ResolveConfig field dropped, that row answers the WRONG supplier or fails (name which, do not merely say it regresses); a rule whose carrier IS derivable answers identically with and without the channel (passes either way BY DESIGN -- this is what says the channel serves only the underivable case, and it must be stated at its site rather than left implicit); a SUPPLIED dictionary that disagrees with a UNIQUE local derivation fails LOUDLY naming both, per WI-860, and is not silently preferred. cargo-test green via scripts/test.sh.
