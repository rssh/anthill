## Description

Stdlib: lift `map` and `find` onto `Iterable` (the shared read interface) so EVERY iterable — List, Stream, a future non-Stream Set — gets them, not only Streams. TODAY (WI-064) `map` lives on MappedStream only and `find` on Stream; both reach a List solely via List-provides-Stream. GOAL: `Iterable.find(c: C, pred) -> Option[Element] effects E` and `Iterable.map(c: C, f) -> Stream[Dst, E]` as real MEMBERS of Iterable deriving via `iterator(c)`. DESIGN (probed 2026-06-07, reverted to clean): `find` in BOTH Stream and Iterable is FINE — ops are sort-scoped, NO definition-time collision; only an UNqualified call where both names are in scope on a List (provides both) is ambiguous, avoidable by qualify/import. Intended layering: keep `Stream.find` as the direct engine (recurses on splitFirst, element/effect thread via the receiver type, WI-380); `Iterable.find` is the general one delegating `Stream.find(iterator(c), pred)`. Same for map: keep the `mapped` carrier + its splitFirst in MappedStream, expose `Iterable.map` = `mapped(iterator(c), f)`. BLOCKER (the real one, NOT the collision): the ABSTRACT-CARRIER iterator-walk. In an Iterable member body, `iterator(c)` where `c: C` returns `Stream[?_, ?_]` — it does NOT carry Iterable's own Element/E — so neither a delegating nor a recursive Iterable.find/map can be typed. Probe errors: `s.annotation: expected Stream[E=E, T=Element], got Stream[E=?_, T=?_]` (element+effect do not thread in the abstract body) and `<op>.effects: expected declared [], got undeclared effect ?_` at concrete List call sites. The CONCRETE walk IS delivered (`collect(List.iterator(xs))` -> List[Int64], wi368_iterator_threading_test, via WI-379/380/393); the ABSTRACT walk is not. THIS WI is the stdlib CONSUMER / ACCEPTANCE of the path-dependent PROJECTION cluster, which per `anthill-todo list --tag typing` (2026-06-07) is the ACTIVE FRONT of the typing sequence: WI-397 is `<- next`, then WI-398 -> WI-399 -> WI-400 -> WI-376 -> WI-374, with WI-424 sitting immediately after as the consumer (NOT parked, NOT deprioritized — that was a stale read; the live sequence is authoritative). The ELEMENT half needs WI-376 path-dependent projection types (`iterator(c) -> Stream[c.T]`; design in docs/design/path-dependent-types.md, status:design / unratified); the EFFECT half is WI-374's stated abstract-carrier-walk acceptance (`walk(c: C) ... = collect(iterator(c))` stays effect-polymorphic). NUANCE: WI-374's example op carries `where C provides Iterable` (an EXTERNAL op); here find/map are MEMBERS of Iterable (c: C is Iterable's own carrier, iterator a sibling op) — same underlying need but the member framing is not currently tested. PROBE ARTIFACTS for the implementer (all reverted): convert `fact Iterable[List[T], T]` -> `provides Iterable[C=List[T], Element=T, E={}]` (write the pure effect, like `provides Stream[T,{}]`) and `fact Iterable[C=Stream, Element=T]` -> `provides Iterable[C=Stream, Element=T, E=E]`; qualified-path + type-args (`Stream.find[Elem=...]`) does NOT parse — pin via a typed `let s: Stream[T=Element, E=E] = iterator(c)`, which then exposes `iterator(c) = Stream[?_,?_]` as the core gap. ACCEPTANCE: `Iterable.find` + `Iterable.map` defined as members deriving via iterator; an acceptance test calls find/map on a List (via List-provides-Iterable) AND ideally a non-Stream Iterable, typecheck + EVAL green; cli/parse.anthill's `find` imported from Iterable; existing wi064/wi368/wi357/wi365 + full anthill-core stay green. Rust/stdlib (acceptance) + typer behind it is WI-374/WI-376.
