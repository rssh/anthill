## Description

Give codegen a RESOLVING KnowledgeBase so realization predicates can be real anthill rules. TODAY codegen is a strictly READ-ONLY consumer: CodegenContext holds a shared kb borrow (anthill-cpp-gen/src/lib.rs:281) and every query goes through kb.query_view (kb/mod.rs:3204), which takes &self and is a DISCRIMINATION-TREE HEAD MATCH -- it returns (RuleId, Substitution) for rules whose HEAD structurally matches and NEVER executes a body. Real SLD (KnowledgeBase::resolve, kb/resolve.rs:2835) takes &mut self because it calls kb.alloc / kb.intern -- it opens rules with fresh vars and hash-conses built goal terms into the TermStore. CONSEQUENCE (the actual motivation): every fact-driven realization lookup must encode its overlay/priority logic CALLER-SIDE in Rust instead of in a rule body. WI-089's addendum specified a fully-qualified anthill.realization.lower_type predicate resolved by SLD -- "the discrimination tree IS the table; the rule IS the overlay logic" -- but what shipped is the Rust query_type_mappings + select_keyed pair, and lower_type does NOT exist as an anthill predicate anywhere in stdlib/. WI-576 hit the same wall and shipped realizes_effect as a Rust fn for the same reason. So the in-language form BOTH WIs specified is blocked purely by this borrow choice. NOT AN EXTERNAL CONSTRAINT -- the shared borrow is codegen's own API decision: run_codegen_cpp (anthill-cli/src/main.rs:919) binds the KB from load_kb_with_stdlib, owning it outright, and could pass a mutable borrow. What makes it awkward is that CodegenContext is threaded as a SHARED borrow through deeply nested emit functions and keeps its own mutable state (requested_includes, type_params, value_bindings, emitting_namespace) behind RefCells precisely so it can be shared; ~29 ctx.kb uses + 47 free fns taking a KnowledgeBase reference in cpp-gen alone, plus emit_traits_struct / emit_namespace_header_with_profile are public API used across ~37 test files, plus anthill-rust-gen and anthill-smt-gen have the same shape. SHAPE TO WEIGH (do not pre-decide): (a) CodegenContext holds the KB in a RefCell of a mutable borrow, with an accessor returning Ref and a resolve method taking RefMut -- mechanical but panic-prone, since any Ref held across a resolve call is a runtime BorrowMutError, and today's code freely binds a local kb from ctx.kb and holds it across calls; (b) a narrow Resolver seam the context owns, so only the ~5 realization-query call sites change and ordinary ctx.kb reads stay immutable; (c) a resolve PRE-PASS with a mutable KB before emission, materializing answers into tables -- but that re-introduces exactly the reader/table layer WI-089 deleted, so it is the fallback, not the goal. TRAP TO RECORD REGARDLESS OF SHAPE: if someone writes realizes_effect (or lower_type) as a BODIED rule in realization.anthill and reads it through the EXISTING query_view path, the head matches but the BODY IS NEVER EVALUATED -- the guard conditions are silently skipped. Today that mostly degrades to a miss (the field readers return None on a var-valued field rather than a wrong string), but it is a silent-wrong-answer waiting for a rule whose head is ground enough. Either make the realization-query call sites refuse bodied rules, or land this WI before any realization predicate is written as a rule. ACCEPTANCE: codegen can execute an SLD query against the KB; at least one realization lookup (lower_type or realizes_effect) is expressed as a fully-qualified anthill rule in anthill.realization and read by codegen through RESOLUTION rather than head-matching, with its overlay/priority logic in the rule body rather than in select_keyed; the existing cpp-gen suite stays green (it is the regression surface for the borrow refactor); cargo-test green via scripts/test.sh.
