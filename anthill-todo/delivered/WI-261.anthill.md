## description

Proposal 041: operation result naming + named-tuple result syntax. Today 'result' is reserved in ensures clauses (kernel-language.md §5.4) but nowhere else; multi-result operations have no named-result form. This proposal lifts 'result' to be reserved across the whole operation declaration (effects rows, ensures, future reflection queries) and adds named-tuple result syntax for multi-output operations: 'operation make_pair() -> (a: Cell[Int], b: Cell[Int])'. Drives: 027.1 effect-discharge revision (Modify[result] needs the name to refer to); multi-result effect attribution ('effects Modify[a], Modify[b]'); ensures/requires readability when there is more than one output; reflection queries that want to refer to result fields by name. Scope: (1) reserve 'result' in effects rows + any other operation-level position that takes a term referring to outputs; (2) add named-tuple result syntax — '-> (name1: T1, name2: T2)' — desugars to a tuple return with the named fields preserved as accessor symbols in the operation's local scope; (3) typer accepts 'result.field' and the bare 'a'/'b' names as references to result components within ensures/effects; (4) cross-reference the kernel-language spec §5.4 to document the broadened 'result' scope; (5) tree-sitter grammar update for the named-tuple form. Out of scope: the discharge analysis itself (027.1's job); reflection queries that introspect result names (follow-up). Acceptance: cargo test green; existing single-return operations with 'ensures' continue to parse and check; a new test exercises 'operation foo() -> (a: T, b: T) ensures ne(a, b)' and 'effects Modify[a], Modify[b]'; webots emitter / safety_common compile unchanged.

## Feedback

### 2026-05-17T10:45:31Z — user

Scope reduced after review: §4.5 already provides named-tuple types in return position (spec even shows 'divmod -> (quotient: Int, remainder: Int)' as the example), and §6.7 already provides 'term.identifier' field projection. Multi-result effect attribution falls out as 'effects Modify[result.a], Modify[result.b]' using existing features. 041 is therefore just one change: extend the typer's lookup chain in effects rows to admit 'result' as a name (parallel to ensures, which already does this). No grammar change, no new symbol kind, no new desugaring. See docs/proposals/041-operation-result-naming.md for the simplified design.

### 2026-05-17T11:05:41Z — user

Implementation landed. Single-return Modify[result] works via natural scope lookup. Multi-result Modify[result.field] works via a workaround in scan_operation_params that pre-registers 'result.<field>' synthetic Param symbols per named-tuple-return field — works because the load-time remap_name treats dotted names as qualified-name lookups. The deeper fix (type-level dot-projection that generalizes to params like Modify[c.field]) is filed as WI-262. The workaround can be removed once WI-262 lands. 4 new tests in wi261_result_in_effects_test.rs covering: single return, single return with params, multi-result tuple, and param-named-'result' conflict.
