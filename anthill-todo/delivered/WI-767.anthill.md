## description

anthill query (CLI) FLOUNDERS on a rule whose body must enumerate an unbound variable, while the SAME rule resolves definitively via KnowledgeBase::resolve. Found while validating WI-760. REPRO: a namespace with `entity Local(name: String, val: String)`, two `fact Local(...)`, and `rule loc(?n) :- Local(name: ?n, val: "one")`. Through `anthill query -p stdlib -p <file> 'ns.loc(?n)'` the answer is the residual `loc(?#0) [?n = ?#0]` -- 1 result, ?n UNBOUND. Through the Rust API (kb.resolve with a Value goal) the identical rule returns ONE DEFINITE solution (empty residual) binding ?n = "a". Confirmed on both a local entity with local facts AND an imported stdlib fact (EffectMapping -> ResultWrap). A rule with a fully GROUND body resolves fine through the CLI, so the trigger is specifically a body goal carrying an unbound variable to enumerate. WHY IT MATTERS: this is a user-facing tool and the failure mode is a silent wrong answer -- the CLI reports '1 result(s)' rather than an error, so a correct rule reads as broken and an author will 'fix' a rule that was never wrong. It also makes the CLI useless for exactly the debugging it exists for. I nearly abandoned a correct WI-760 rule design on the strength of this output; only re-testing through kb.resolve showed the rules were fine. SUSPECTS (not investigated): the CLI's goal construction/var linkage differs from the test-side pattern (query vars may not be linked into answer_links, cf. WI-624), or it resolves with a config that delays/rotates rather than enumerating.
