    2. anthill-todo/src/main.rs:80 `collect_files_recursive` + :106 `collect_anthill_files` -> Result<Vec<PathBuf>, Vec<String>>
    3. anthill-core/src/persistence/file_store.rs:99 `collect_anthill_files` + :109 `collect_recursive` -> Result<_, PersistenceError>

COPIES 1 AND 2 ARE BYTE-IDENTICAL. Verified by diffing the two 22-line bodies with comments stripped: exactly ONE line differs, and only cosmetically — `has_extension(&path, extensions)` vs its inlined `path.extension().and_then(|e| e.to_str()).map_or(false, |e| extensions.contains(&e))` equivalent. WI-744 added the same 4th parameter (`errors: &mut Vec<String>`), the same recursion threading, and the same user-facing error string (`format!("cannot read directory {}: {e}", dir.display())`) to BOTH, by hand, in two crates. That is the cost, already paid once.

THE HOME ALREADY EXISTS AND IS ALREADY IMPORTED. `anthill-stl` (lib name `anthill`) is depended on by both binaries and both already `use anthill::{runner, stdlib}` (anthill-todo/src/main.rs:5, anthill-cli/src/run.rs:9) — so the move needs NO new dependency. anthill-stl/src/runner.rs's module doc states the charter verbatim: shared CLI mechanics live there "so the two binaries stay byte-identical in their error formatting and exit codes" — and a duplicated user-facing error string is exactly that. NOTE runner.rs is about RUNTIME bootstrap; a file-collection helper is arguably its own module (anthill-stl/src/files.rs) rather than a runner concern. Decide.

SCOPE / SPLIT:
  - Copies 1+2: move `collect_files_recursive` + `has_extension` to the shared home. The POLICY wrappers (`collect_anthill_files`) legitimately differ per binary — anthill-cli errors on a non-existent path, anthill-todo skips it — so they STAY per-binary and call the shared traversal. This is the increment that pays for itself immediately.
  - Copies 4-6: three verbatim clones exist only because Rust integration tests cannot share a `tests/common/` module across crates. The fix is a shared helper in a crate they all already depend on (anthill-core), not more copying.
  - Copy 3 (file_store.rs) is the interesting one: it already implements this traversal in the FAIL-FAST `Result<(), _>` shape with `?` propagation and no out-param. See the ALTITUDE note below — it may be the shape the others should adopt, in which case it is the base, not another copy.

ALTITUDE (a real question, settle it before moving code): WI-744 gave copies 1+2 an `errors: &mut Vec<String>` OUT-PARAM so a scan reports EVERY unreadable directory rather than just the first. A reviewer argued for the fail-fast `Result` shape instead, on the grounds that (a) all three callers discard the collected `files` the instant `errors` is non-empty, so continuing the scan is dead work whose only observable effect is printing N lines instead of 1; (b) an out-param is not `#[must_use]` — a caller that forgets `if !errors.is_empty()` silently restores the exact warn-and-continue bug WI-744 exists to kill, whereas a `Result` cannot be ignored; and (c) file_store.rs:109 already does it the other way. COUNTER-ARGUMENT, for the record: `collect_anthill_files` ALREADY accumulates other faults (path-does-not-exist, not-an-.anthill-file) across multiple paths into that same vec, so a dir-read error joining them is coherent, and reporting every bad path in one run is a genuine (if small) UX win. The two shapes cannot both be shared — pick one, and say why in the code.
  Settled and NOT up for revisit: `Vec<String>` rather than a `LoadError` variant is CORRECT. These are filesystem faults, terminal (printed once, then exit; never matched on), and a `LoadError::Io` would directly dilute the invariant WI-744 established at kb/load.rs's `pub enum LoadError` doc ("every variant BLOCKS the load ... callers print and exit, they do not triage"), which is a statement about the LANGUAGE, not about the filesystem.

RELATED DUPLICATION, same theme, fold in only if cheap:
  - The `for e in &errs { eprintln!("error: {e}"); } return Err(EXIT);` block now occurs ~8x across the two binaries (cli/main.rs x5-6, run.rs:182, todo/main.rs x2), five of them added or rewritten by WI-744. A `report_errors(errs) -> ()` in the same shared home collapses them. Held out of WI-744 deliberately: the loop is 3 trivial lines, the two binaries disagree on the exit code (run.rs returns EXIT_COMPILE=2, cli/main.rs returns a bare Err(1) consistent with its own ~10 error returns), and the nicer `LoadError::format_with_source` renderer is structurally unusable at these sites (see WI-745). Worth revisiting once WI-745 gives errors a file identity, since that is when the presentation actually changes.
  - anthill-cli/tests/{run_cmd_test,load_cmd_test}.rs share ~25 lines of harness (`bin()`, `fixtures_dir()`, `struct Output`, the Command runner) by copy. anthill-cli/tests/ has no `common/` module, unlike anthill-core / anthill-cpp-gen / anthill-smt-gen, which all do. Two copies is where this pattern starts, not where it ends.

WHY IT MATTERS (not just tidiness): the three error policies genuinely disagree TODAY. An unreadable stdlib directory makes copy 4 panic (`expect("read dir")`), copy 8 return an empty Vec and fail the suite as a mysterious missing-symbol error, and copy 1 report it cleanly — same fault, three behaviors, no shared test. And the next behavior change (a symlink-loop guard, a max-depth cap, honoring .gitignore, skipping target/ and node_modules/ — the last of which WI-746 will want) costs the same doubled-or-octupled edit; the first time someone patches only the crate they were looking at, the two CLIs silently disagree about which files constitute a project. That divergence is invisible to tests: each binary's suite exercises only its own copy.

ACCEPTANCE: one traversal implementation, in a crate the consumers already depend on; copies 1+2 gone and both binaries calling it, with their differing POLICY wrappers retained; copies 4-6 gone (a shared helper the three test suites call); copies 7+8 gone or justified in a comment; ONE error policy, with the choice between out-param and fail-fast `Result` stated in the code; `anthill load`/`check`/`query` and every `anthill-todo` command behave identically before and after (the WI-744 tests — run_cmd_test.rs, load_cmd_test.rs, cmd_default_parity_test.rs — are the guard); cargo-test green via scripts/test.sh (FULL workspace, per WI-569: a core-type change needs the whole workspace, not -p anthill-core).
