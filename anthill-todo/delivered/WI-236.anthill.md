## Description

Host API for seeding cross-sort requirement dictionaries at entry-op call. Today interp.call(qname, args) only handles same-sort recursion: seed_entry_requirements (rustland/anthill-core/src/eval/mod.rs:448) populates the entry op's frame.requirements with self-referential placeholders (functor = the parent sort itself, no sub-deps). The code comment explicitly notes 'cross-sort dispatch through the requirement would need a richer entry API to express which impls back the parent's requires'. This blocks polymorphic bundles: a bundle whose sort Main declares 'sort State = ?; requires WorkItemStore[State]' can be loaded but cannot be run from Rust, because the host has no way to supply a real WorkItemStore dictionary rooted at the chosen impl (e.g. FileBasedWorkitemStore). The runtime error surfaces as 'requirement_at_current(slot=N): frame has only M requirements' or similar mis-dispatch when the placeholder dictionary's empty sub-tree doesn't match the expected impl structure. Required: (a) a new host API alongside Interpreter::call, e.g. interp.call_with_requirements(qname: &str, args: &[Value], requirements: Vec[Value::Requirement]) -> Result[Value, EvalError], that lets the caller supply pre-built requirement dictionaries instead of relying on seed_entry_requirements. (b) helper(s) on Interpreter for constructing a dictionary from Rust: alloc_requirement(impl_sort_sym, sub_handles) is already present; add a convenience that takes a structured spec like 'impl=FileBasedWorkitemStore, subs=[]'. (c) keep the existing self-referential fallback for callers that don't need cross-sort impls; document the difference. (d) operation-call-model.md gains a section §'Host-to-entry-op boundary' describing both modes. Acceptance: new test verifies a cross-sort polymorphic entry op (e.g. a small Driver with 'requires WorkItemStore[State]' whose body calls WorkItemStore.lookup) executes the FileBasedWorkitemStore.lookup body when invoked via call_with_requirements supplying the dictionary; the same op invoked via plain interp.call still hits the existing 'cross-sort needs richer API' fallback path with a clear diagnostic; cargo-test green. Driver: WI-204 polymorphic refactor of bundle Main — once this lands, sort Main { sort State = ?; requires WorkItemStore[State]; ... } can be used and the bundle becomes impl-agnostic (WIS-naming retires from main.anthill). Out of scope: implicit inference of impl from runtime value-level evidence (e.g. unwrap Cell[?S] to discover S from the wis(...) functor — a more ambitious WI); full proposal-027 effect-handler discharge integration.
