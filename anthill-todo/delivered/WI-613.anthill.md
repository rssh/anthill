## Description

BUG: defer-to-requirement attribution conflates two same-spec requirements over different type params (requires Eq[A], requires Eq[B]). find_requires_slot (typing.rs:7998) attributes a body spec-op call to a requires-chain slot via .position(entry_matches_subst); entry_matches_subst -> dispatch_values_match (typing.rs:11740) returns TRUE UNCONDITIONALLY at line 11748 when the CANDIDATE (the requires entrys bound param) is a type-param value (the "universally-quantified candidate matches any per-call value" open-T defer rule). Correct for a SINGLE open param (requires Eq[T]); but with TWO same-spec requires over DISTINCT params, BOTH entries wildcard-match ANY call, so .position always returns the FIRST (Eq[A], index 0). Consequence: a body call eq(y:B) is attributed to Eq[A]s slot -> req_name_for_chain_index(0) -> reads Eq[A]s __req dict -> dispatches through the WRONG dictionary at runtime. NB name synthesis is NOT the bug: synth_req_names (typing.rs:20228) already disambiguates by full spec TermId (__req_eq_idA vs __req_eq_idB); the bug is ATTRIBUTION picking the wrong index, so the correct name is never selected for the second param. REACHABILITY: latent -- needs a sort/op with two requires of the SAME spec over DIFFERENT type params, both dispatched in the body (e.g. zip[A,B] requires Eq[A], requires Eq[B]); likely absent from current stdlib so untriggered, but a soundness hole. FIX DIRECTION (design discussion): mangle the STATIC type param INTO the requirement name at elaboration, used identically by writer (requires slot) and reader (body op), so attribution is a by-name match on the param-carrying mangled name -- eliminating the .position/dispatch_values_match wildcard step. Consistent with wire-by-type-param-at-elaboration (NOT a runtime ground-type hash). Blocks WI-300 (rule-body requirement goals reuse this attribution + requirement-frame machinery). Acceptance: cargo-test green + a regression test with two same-spec/different-param requires both dispatched.

The three keying options weighed: (a) POSITIONS -- moves attribution to elaboration (fine) but makes the RUNTIME env positional again = the WI-237 escaping-closure hazard; rejected, keep the runtime env NAMED. (b) MANGLED NAME -- works, but a stringly-typed stand-in for the type identity. ROBUST form of (c): compare spec-instances by STRUCTURAL type identity -- TermId== fast-path when both interned, structural compare (views_structurally_equal / the DiscrimKey the discrim tree already uses) otherwise; this subsumes (b) (mangled string = weaker structural key). RECOMMENDATION: (c)-structural -- fix the param-identity comparison in dispatch_values_match/entry_matches_subst, keep the runtime requirement env NAMED (no positional regression). ### 2026-07-02T05:07:23Z — feedback — user

ADDENDUM (structural value hash option). A structural value hash is the FAST-PATH half only -- "if it is unique" cannot be assumed: hashes collide (birthday bound), and a bare hash-as-key trusting uniqueness reintroduces the misroute PROBABILISTICALLY (two distinct spec-instances colliding -> wrong dict = the same bug, nondeterministic). Safe form = HASH + STRUCTURAL EQUALITY (hash to bucket O(1), structural compare to confirm on hit). That is exactly what the existing mechanisms already are: hash-consing (structural Hash+Eq -> unique TermId = option c), the discrim trees DiscrimKey (carrier-agnostic structural key, works for TermId AND Value::Node), and any HashMap<structural-key>. So all options collapse to ONE: structural identity, hash for speed + structural equality for correctness. Reuse DiscrimKey / Term Hash + views_structurally_equal; NEVER trust the hash alone. Recommendation unchanged ((c)-structural); hard rule: hash buckets, structure decides.
