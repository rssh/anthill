## description

Arrow-type parameter names are dropped + positional naming off-by-one (impl violates kernel-spec). docs/kernel-language.md §5.4 (line ~312) says arrow params CAN be named ('using the same syntax as named tuple elements'); §4.5 says positional tuple elements desugar to _1,_2,_3 (1-BASED). But the impl: (1) TypeExpr::Arrow.params is Vec<TypeExpr> (parse/ir.rs:167) — NO name slot; convert_arrow_type (convert.rs:1673) sees the field_decl child and extracts only the type, DROPPING the name; (2) the multi-param arrow lowering (load.rs:5326-5344) wraps params in a named_tuple keyed format!('_{}', i) — 0-BASED and synthetic — whereas plain tuples (convert.rs:241) correctly use format!('_{}', index+1) (1-based). So a callback (a:S, t:T)->S lowers to a named_tuple with fields _0/_1 and the names a/t lost — inconsistent with both plain tuples and the spec. FIX: (a) TypeExpr::Arrow.params -> Vec<(Option<Symbol>, TypeExpr)> preserving the field_decl name; (b) convert_arrow_type captures field('name') from each field_decl child; (c) the load.rs arrow named_tuple lowering uses the real name when present, else _{i+1} (1-based, matching tuples/spec); (d) update consumers: codegen/rust.rs:352,417 (iterate name/type pairs) + load.rs:886 (build_instantiation_term over pairs) + load.rs:752/753 unaffected. ACCEPTANCE: (a:S,t:T)->S lowers to a named_tuple with fields a,t (not _0,_1); an UNNAMED (A,B)->C lowers to _1,_2 (1-based, matching plain tuples); existing tests green. PREREQUISITE for WI-351 (place symbols foldLeft.f.a / foldLeft.f.t require the real callback-param names). Spec is correct; this conforms the impl to it.
