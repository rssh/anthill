## Description

`anthill-todo add` HARDCODES `cargo-test` as a new work item's acceptance and never reads `Project.tools` or `Module`, so a ticket whose work is in another language records a gate that cannot observe it.

MEASURED 2026-08-10 while correcting 25 mislabeled scaland tickets in bulk (commit fd7a0f35).

THE MECHANISM, one operation. `resolve_acceptance` (rustland/anthill-todo/anthill/main.anthill:2014):
  match raw
    case nil() -> tools_to_acceptance(cons("cargo-test", nil()))
    case cons(_, _) -> tools_to_acceptance(raw)
`--acceptance <tool>` exists and is repeatable, so a caller CAN say; the hardcoded fallback is what nobody overrides. Over the tracker: 1009 items carried `cargo-test` and 43 `scaland-sbt-test`, and every one of the 43 is hand-written into a multi-line resync-era record. The CLI has never emitted anything but `cargo-test`.

WHY A WRONG TOOL IS NOT LOUD, which is why it survived a thousand tickets. For a scaland ticket, `cargo-test` is VACUOUSLY SATISFIABLE: a scala-gen change cannot fail the Rust suite, so the recorded criterion passes while measuring nothing the ticket is about, and the real gate ("sbt test green") sits in description prose where nothing reads it. That is the repo's own principle -- a test that passes both with and without the change measures nothing -- one level up, at the ticket. WI-1020 is the sharpest instance: its whole subject is that string-matching was not evidence, and its acceptance then named a tool blind to its outcome.

WHAT THE DOMAIN ALREADY SUPPLIES, so this is wiring and not a schema change. `Project(tools: List[T = String], modules: Option[T = List[T = String]], ...)` and `Module(name, root, language, build, sources)`, where a module's `language` is REQUIRED and its `build` is its own -- the multi-language carrier, which is why `Project.language` is a single `Option[T = String]`. anthill-todo/project.anthill (fd7a0f35) now declares `Module(name: "rustland", root: "rustland", language: "rust", build: "cargo")`, the scaland peer, and `tools: ["cargo-test", "scaland-sbt-test"]`. NOTHING READS ANY OF IT -- main.anthill never mentions `Project` -- so the file is a source of truth with no reader, the same shape WI-1060 removed from scala_std's type_map.

THE OPEN QUESTION IS THE TICKET'S REAL CONTENT: how does `add` know which module a ticket belongs to? A description is prose. Three candidates, all real:
 (a) An explicit `--module scaland` flag, resolved through `Module.build` to a tool. Dumb and honest; a wrong answer becomes a typo rather than a silent inheritance.
 (b) DERIVE it from paths named in the description -- the module whose `root` is a prefix of a path the text mentions. Works for the scala-gen cluster, which names `scaland/core/src/...`; fails for a ticket that names no path, and a partial derivation that silently falls back to the primary is today's defect with more machinery in front of it.
 (c) Make acceptance REQUIRED when the project declares more than one module: no default at all, `add` refuses without `--acceptance`. Loudest, matches "prefer a loud error over a silent skip", and costs every caller one flag.

ALSO TO DECIDE: whether `Project.tools` is even the right source. It is a flat list of tool NAMES with no link to a module, so `["cargo-test", "scaland-sbt-test"]` cannot say which gates what without reading `Module.build`. And there are no `ToolDef` facts anywhere in this repo, so a tool name is presently an uninterpreted string -- nothing would run it.

SCOPE: choose (a), (b) or (c); wire `resolve_acceptance` to it. `cmd_add` and `cmd_insert` BOTH call it, so fix the one operation rather than two call sites. No change to `list`/`show` -- this is about what `add` RECORDS. If the answer is (c), measure first how many existing test fixtures call `add` with no `--acceptance`, because every one of them has to be updated.

ACCEPTANCE: a test that runs `add` through the CLI in a project declaring TWO `Module` facts and asserts the acceptance WRITTEN to workitems.anthill is not the primary's tool for a ticket belonging to the other module -- asserted on the written text, because the defect is precisely that this value is recorded and never read. CONTROL in the same test: a single-module project still gets its one tool with no flag, so the change cannot be satisfied by refusing everything. State at the test site which of (a)/(b)/(c) was chosen and why the other two were not.

SOURCE: found while correcting 25 mislabeled scaland tickets (fd7a0f35). The recurrence warning is currently prose in anthill-todo/project.anthill, which is exactly the kind of unread note this ticket exists to replace.
