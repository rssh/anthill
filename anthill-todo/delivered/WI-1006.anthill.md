## Description

`anthill-todo list` orders ids LEXICOGRAPHICALLY, so at id 1000 the newest items stop appearing last.

REPORTED BY USER, 2026-08-05, on the real project: "list does not show
WI-XXXX where XXXX > 1000". They were shown — buried mid-list.

MEASURED, before the fix, on the project's own data:
  WI-093 WI-094 WI-1000 WI-1002 WI-1003 WI-1004 WI-1005 WI-102 WI-128 ...
"WI-1000" compares below "WI-102" at the fourth character, so every
four-digit item wedges between WI-094 and WI-102.

CAUSE. main.anthill's `merge_by_id` compared whole id STRINGS with
`Ordered.lt`. Its caller `chrono_topo` documents the top-level cursor as
advancing CHRONOLOGICALLY, and ids are allocated monotonically (`max + 1`,
anthill-todo/src/main.rs), so the number IS the age — which is what makes
numeric order the chronological one and the string compare simply wrong.

FIX. `id_before` compares the trailing DIGIT RUN, leading zeros dropped, by
(length, then code units) — numeric order once no leading zero survives, and
needing no string->Int64 parse, which `anthill.prelude.String` does not
declare. Ties fall back to the whole id so the order stays TOTAL and the
merge sort stays stable and deterministic; an id with no digit run gives ""
and sorts first, a defined place rather than a trap.

THE ZERO-STRIP IS LOAD-BEARING and has its own test, because the tempting
simplification (compare the digit run AS WRITTEN by length) gets the reported
case right and "WI-0094" vs "WI-999" backwards.

TESTS: cmd_list_id_order_test (3). Both backouts were RUN, and the two
failing rows are not interchangeable — restoring `lt` fails only
four_digit_ids_sort_after_three_digit; dropping `drop_leading_zeros` fails
only zero_padding_does_not_decide_the_order. ids_below_the_boundary_are_
unchanged passes in all three configurations, by design.
