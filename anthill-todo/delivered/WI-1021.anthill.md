## description

scaland TypeGen rewrites a sort's OWN name through the prelude type map, so a sort's members reach Scala typed by a DIFFERENT type -- measured, `PairOps` declares `def fst(p: Tuple2): A` and does not compile.\n\nMEASURED (2026-08-05, delivering WI-940). Bootstrap.generate on stdlib/anthill/prelude/pair.anthill emits into Pair.scala:\n\n  trait PairOps[A, B]:\n    def fst(p: Tuple2): A\n    def snd(p: Tuple2): B\n    def eq(a: Tuple2, b: Tuple2): Boolean\n\nThe anthill declarations are `operation fst(p: Pair) -> A`, `snd(p: Pair) -> B`, `eq(a: Pair, b: Pair) -> Bool` -- every receiver is written `Pair`, the sort the file declares. `scala-cli compile --scala 3.6.3` on that file reports FOUR "Missing type parameter for [T1, T2] =>> (T1, T2)", one per `Tuple2` occurrence: Scala 3's `Tuple2` is a type constructor and a bare mention of it is an error.\n\nMECHANISM, and it is one line. `TypeGen.mapPrelude` (scaland/core/src/main/scala/anthill/codegen/scala/TypeGen.scala:45-62) maps prelude type NAMES to Scala stdlib counterparts by SHORT NAME, unconditionally: `case "Pair" => "Tuple2"`. That table exists for CONSUMERS -- a project sort with a `Pair[A, B]` field should reach Scala as `Tuple2[A, B]` -- but it fires just as readily inside pair.anthill itself, where `Pair` denotes the very type being emitted three lines up. The generator therefore declares `case Pair(fst: A, snd: B)` and then types its own members by something else.\n\nNote the entry is doubly wrong here even for a consumer: it drops the type ARGUMENTS. `TypeExpr.Simple(Pair)` -- an unparameterized written occurrence, which is what an operation's `p: Pair` is inside its own sort body -- renders through the `Simple` arm (TypeGen.scala:12-13), which has no bindings to pass on. A consumer writing `Pair[A = X, B = Y]` goes through the `Parameterized` arm and does get `Tuple2[X, Y]`; the receiver-position occurrence has nowhere to get them from, because in anthill it does not need them -- the sort's own parameters are in scope.\n\nTWO CANDIDATE FIXES, and the choice is the ticket:\n (a) SUPPRESS the mapping for a name the file itself declares -- TypeGen would have to be told the enclosing declaration's name, which it is not today (`render(sym, te)` takes no context). Smallest change, and it leaves the `Pair -> Tuple2` mapping intact for real consumers.\n (b) DROP `case "Pair" => "Tuple2"` from mapPrelude. Anthill's `Pair` is a nominal sort with named fields `fst`/`snd` and its own `eq`; Scala's `Tuple2` is structural. They are not the same type, and a `provides Eq[Pair]` cannot attach to `Tuple2`. Check the other suspect entries at the same time -- `List -> List`, `Set -> Set`, `Map -> Map`, `Stream -> LazyList` have the same nominal-vs-host question, and `Option -> Option` collides with anthill's own `none`/`some` constructors.\nWhichever is chosen, say WHY the other was refused.\n\nACCEPTANCE: driven by WI-1020's compile harness -- the emitted prelude closure compiles, and a test names `Pair.scala` as the file that did not. A CONTROL that a genuine consumer's use of the prelude type still maps as intended (or, if (b) is chosen, that the fact it no longer maps is asserted and not incidental). Say at the test site which assertion fails when the fix is backed out. sbt test green.\n\nSOURCE: measured while delivering WI-940.
