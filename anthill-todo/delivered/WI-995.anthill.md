## description

An import is scoped to the ADDRESS, not to the file it is written in — so one file changes how names resolve in another.

THE RULE (user decision, 2026-08-04): an import resolves ONLY in the file where it
is listed, and it is SPENT BEFORE any merging. An import maps a local name to a
Symbol; once names are Symbols it has no further job.

THE DIVERGENCE. `process_imports` writes into the table keyed by SCOPE, and a
scope is the address: `namespace X` and `sort X` both alloc `Fn{X,[],[]}`, which
hash-conses to one TermId, so every text writing into one address shares one
import table. Fixtures A-D (see history) measured drive() = 1/2/1/2; C names the
reach (the address, not the text), D places the ticket (plain namespace-level
import scoping, no sort at the address, so NOT 059's secondary entries).

MEASURED, 2026-08-11 — the cost the ticket demanded before any behaviour change.

INSTRUMENT (landed, default-off). `SymbolTable` now records WHO WROTE each import:
`ImportOrigin::{Builtin, File(idx), Declaration}` on both the alias table
(`import_origin`) and the import-contributed parent links (`import_parent_origin`).
`resolve_in_scope` answers twice while auditing — as today, and under
`ImportVisibility::OwnFileOnly` — and records the disagreements. A counterfactual,
not a proxy: counting import statements or shared addresses measures exposure, not
whether any name actually reaches across.
`ANTHILL_FILE_LOCAL_IMPORTS=1` ENFORCES the rule instead of auditing it.

RESULT 1 — THE .anthill CORPUS COSTS ZERO. Six groups (stdlib alone; +rust host
bindings; +github-todo; +anthill-todo; +webots-modelling; +anthill-testcases),
69-94 files, 10.9k-24.1k resolutions each: 0 cross-file dependencies in every one.
WHY: 238 of 250 imports are SELECTIVE (which add no parent link), 12 plain, 0
wildcard, and 0 top-level imports — so nothing lands in the shared `_global` table.
The one shared-address duplicate is instructive: stdlib/anthill/geometry.anthill
and rustland/anthill-stl/anthill/geometry.anthill BOTH write
`import anthill.prelude.{Float}` into `namespace anthill.geometry` — duplicated
because each file imports what it uses, which is the discipline the rule mandates.

RESULT 2 — THE SUITE COSTS 43 TESTS (4440 passed / 43 failed, vs 4483 / 0 at
baseline; 29 binaries both runs, so neither masks a compile error). The corpus zero
is honest but does not reach what the fixtures reach. TWO causes, only one a cost:

  (a) IMPORTS STOP RE-EXPORTING — 12 tests (wi844_sorted_set_driver_test).
      stdlib/anthill/prelude/int64.anthill:7 writes
      `import anthill.prelude.Numeric.{add, sub}` INSIDE the Int64 scope, and the
      fixture writes `import anthill.prelude.Int64.{sub}` — importing a name that
      is in Int64 only because Int64's own file imported it there. Under the rule:
      `unresolved import 'anthill.prelude.Int64.sub'`. This is the ticket's own
      anticipated case, it is CORRECT (imports are not re-exports, as in most
      languages), and the repair is per-site: `Int64.{sub}` -> `Numeric.{sub}`.

  (b) THE QUERY PATH HAS NO FILE TO BE LOCAL TO — 31 tests (wi853, wi907, wi908,
      wi914, wi916, wi917, wi919). NOT a migration cost — a design gap that must
      close before the rule can land. `-i <ns>` synthesizes its OWN single-file
      source containing `import <ns>`, then the query resolves at `_global` where
      no file is asking, so a strict rule blinds every query to its own `-i` flags:
      "'mk' in query pattern does not resolve to a known functor".

TWO PREMISES OF THIS TICKET WERE WRONG, both found by reading the code:
  - AN IMPORT WRITES TWO THINGS. Beyond `Scope.imports` (one reader), `Plain` and
    `Wildcard` imports call `add_parent`, whose list is SHARED with `requires` and
    enclosing links. Suppressing an edge on a foreign import's say-so would also
    suppress it where a `requires` independently justifies it — hence
    `ImportOrigin::Declaration`, recorded by every non-import `add_parent`.
  - "SPENT BEFORE MERGING" IS NOT TRUE TODAY. `Scope.imports` survives the load:
    the typer (typing.rs) and `anthill query` both resolve through it. Deleting the
    table after load is NOT a valid implementation of the rule.

WHERE THE FILE IDENTITY COMES FROM — settled, and it needs no new carrier.
`SourceSpan { source: SourceId, span }` already IS "a span with file identity", and
`NodeOccurrence.span` is a `SourceSpan`, so every occurrence already knows its file;
`Loader.source_id` is fixed for the whole file. File must NOT go on `Term`/`TermId`
(it would break hash-consing — two identical terms in two files would stop sharing
a TermId) nor on `TermView` (a file is not a carrier property). It is a property of
a SITE. The gap is only that the SYMBOL TABLE recorded no writer; that is now closed.

DELIVERED 2026-08-11 (backward compatibility explicitly NOT a constraint — user).
The rule is the DEFAULT; `ANTHILL_FILE_LOCAL_IMPORTS` existed only to measure and is
deleted. Full suite 4483 passed / 0 failed, 29 binaries, 0 compile errors.

WHAT THE FILE IDENTITY IS. `SourceId` — the identity `SourceSpan` already carries, so
an occurrence names its own file with no lookup table. Source registration is HOISTED
ahead of `scan_definitions` (`register_sources`), so the scan, the declaration pass and
the load pass share one id per file. A load-slice INDEX was tried first and is wrong:
`load_incremental`'s phase 2 and the CLI's query scan each index from 0 again, so a
slice position silently aliases one file onto another.

THE ASKING FILE. `SymbolTable::set_asking_file` is ambient during the load, which is
honest there — a `Loader` IS a file (`Loader.source_id` is fixed for the whole file).
The TYPER needed nothing, on evidence rather than assumption: its one `resolve_in_scope`
is gated on `is_type_param`, always a scope local, and the enforced run produced zero
typer-side failures with the asking file `None` throughout typing.

`ImportOrigin::Invocation` — the channel for a FILE-LESS asker. `anthill query -i <ns>`
parses its flag from a synthetic one-line source; attributing that to a "file" made the
flag local to it and so invisible to the very query it was passed to serve. A flag
belongs to the RUN, like the prelude's own aliases. `common::supply_invocation_imports`
is the in-process spelling, used by the fixtures below.

THE 26 SITES REPAIRED, and none needed a mechanism redesign:
  - wi844 (12): ONE line — `Int64.{sub}` -> `Numeric.{sub}`. Passes under BOTH the old
    and new rule, so it is a strict improvement, not a compatibility shim.
  - wi907 (3), wi917 (3), wi919 (1), wi908 (2), wi916 (4): imports moved to the
    invocation channel. These fixtures' own comments said they were modelling `-i` all
    along ("`-i <ns>.*` twice is the CLI spelling"). A MOUNT never needed an import to
    supply a namespace — it takes a fully qualified name and always did (verified) —
    so the earlier claim that persistence needed a new import channel was WRONG.
  - wi853 (1): INVERTED, and its module header rewritten rather than deleted. It taught
    top-level import sharing as a deliberate difference from "the file-local import of
    most languages", reasoning the language "has no per-file scope to attach a narrower
    one to". This ticket supplies that scope. An assertion was ADDED that a top-level
    DEFINITION still crosses files, so the refusal is pinned as being about imports and
    not about `_global` going private.

WI-916'S HAZARD IS NARROWER NOW, stated at its site. It built its contest by loading a
second FILE whose top-level import contested the mount name for everyone; that route is
closed by construction. The contest now comes through a second `-i` after the mount — a
genuine sequence — so the defect stays live and the Symbol-keying fix still stops it.

SPEC UPDATED (`docs/kernel-language.md`): the "Where an import may be written" passage
(which stated the OPPOSITE rule), the `resolve_in_scope` step 2, the import-forms list
(both things an import writes), and the implicit-namespace merging bullet.

THE AUDIT SURVIVES THE FLIP, inverted: it now resolves the PRE-RULE way and reports
where that disagrees, so it keeps measuring instead of trivially agreeing with itself.

REVIEW ROUND (/code-review high) FOUND A REAL HOLE IN THE FIX, worth recording because
the delivered control could not catch it.

  THE RULE WAS KEYED ON THE NAME, NOT THE SYMBOL. `Scope.imports` is a `HashMap`
  (last write wins). Step 1b asked only "did SOME visible origin write an entry under
  this name" and then returned the MAP's winner — so with file A writing
  `import a.{X}` and file B `import b.{X}` at one address, A read B's `X`, decided by
  load order. That is the very non-locality this ticket removes, surviving inside its
  own implementation. `visible_import` now returns the visible WRITE's own symbol out
  of `import_origin` (last visible write wins, preserving in-file last-write-wins).

  WHY FIXTURE D MISSED IT, and the lesson: D's foreign import is the ONLY write of
  that name, so name-keying and symbol-keying AGREE there. A one-writer fixture cannot
  distinguish "which name" from "whose name". `wi995_two_files_importing_one_name_each_
  read_their_own` drives the two-writer case (distinct field labels, so a mix-up is a
  closed-label load error; both load orders) and was VERIFIED to fail with the fix
  backed out — while fixture D passed throughout that back-out.

  `contested_import_entries` had the same defect from the other side: it filtered on
  ORIGIN difference, so it flagged two files importing the SAME target (harmless) and
  missed one file importing two DIFFERENT targets under one name. Now filters on symbol.

FIVE MORE, all fixed: the public `scan_definitions` cleared the asking file, so the
shipped scan-then-RESOLVE path (`anthill query`) made the scanned source's own imports
invisible to the resolution that followed — it now leaves it set; the instrument's own
`alias_entries` guard counted `Builtin` prelude aliases and so would have passed on a
run that recorded no file-written import at all; a helper was inserted between
`mount_extent`'s doc/attribute and `mount_extent`; a dropped negation inverted a spec
sentence; and the per-edge origin probe is now gated on a per-scope flag, so the scopes
with no file-scoped import parent (all but ~10 in the stdlib) answer with a field read.

NOT TAKEN: moving the origin onto `ScopeInclusion` to drop the side table. Its derived
`PartialEq` is `add_parent`'s dedup key and WI-994 established that a scope's parents
are a SET; an origin field would split links differing only by writer and silently undo
that. The per-scope flag buys the same lookup cost without touching the key.
