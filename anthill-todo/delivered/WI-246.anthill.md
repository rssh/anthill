## Description

Extend NodeOccurrence/Expr migration to rule body atoms. Currently (WI-242) only operation bodies, lambda bodies, and if/match/let branches become Expr/NodeOccurrence; rule body atoms (e.g. add(?x, 1) inside rule r(?y) :- Foo(?x), ?y = add(?x, 1)) stay as hash-consed Term. This WI extends the migration: rule body atoms become Rc<NodeOccurrence> with NodeKind::Expr, so the typer/eval/codegen see uniform Expr structure regardless of whether content lives in an operation body or a rule body. Affects: kb/load.rs (rule body atom conversion), kb/resolve.rs (SLD resolution walks NodeOccurrence atoms), kb/discrim.rs (discrimination tree keys), kb/subst.rs (substitution applied through NodeOccurrence). Acceptance: cargo-test green; rule body atoms are structurally Rc<NodeOccurrence>; no Term::Fn at rule-body positions in loaded KB; resolver indexes occurrences by functor for discrimination tree matching. Out of scope: type terms, fact bodies, query patterns (those stay as Term — they are structural KB facts, not positional expressions).

### 2026-05-23T21:21:31Z — feedback — user

Root-cause + right approach (traced in WI-297). Rule-body atoms should be produced as occurrences NATIVELY in the front-end, NOT derived from terms via materialize_from_handle. Today convert.rs builds Term::Fn for bodies and mod.rs:638 derives body_nodes by RE-INFERRING Expr structure from the functor NAME (visit_fn key dispatch). Term::Fn is structurally poorer than Expr (it does not record apply-vs-constructor-vs-if), so the re-inference assumes 'apply(...) is a call' and is LOSSY for reflection patterns: apply(fn:?f, args:?Args) collapses to an empty Apply<apply>() (verified — subject foo(1,2) survives via the UnknownFn path, but the recognized-key apply pattern is interpreted and emptied). Same class as int_lit(value:?)->Bottom that WI-297 patched for leaf keys (push_unknown_fn). RIGHT FIX: build body occurrences directly from the CST (structure + spans known there), eliminating both the term intermediary AND the re-inference — no materialize_from_handle for bodies, no loss. ASYMMETRY (confirmed): HEAD stays a hash-consed TermId because it is SEARCHED in the discrimination tree (must be canonical/span-free); BODY atoms are GOALS (resolved, never searched -> no hash-consing) so they can be occurrences only, dropping body: Vec<TermId> (the De Bruijn opener, delay pre-check, and dedup all either have occurrence equivalents or reify on demand — none is a correctness need). This subsumes WI-298 (no TermId-pattern / control-flow special-casing) and the compound-form occurrence_term work; the lens-patch framing in WI-300 is the WRONG direction and is superseded.
