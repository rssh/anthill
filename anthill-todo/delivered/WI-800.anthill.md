## Description

thread_expected_tuple_field (kb/typing.rs ~2311) still matches expected component types by SHORT NAME, order-blind, after WI-788 made every relation around it order-sensitive. For a permuted literal (b: "ess", a: 3) against an expected (a: Int64, b: String) it threads the expected type of 'a' into the component NAMED a -- the SECOND written component -- before the order mismatch is reported. NOT A SOUNDNESS BUG: the relation still refuses the program, and this function is a hint-threading no-op on a miss, not a type relation. It is a DIAGNOSTIC-QUALITY defect -- the inference hint lands in the wrong slot and can mis-aim the error that follows. FIX: thread positionally with the same name agreement the relations now use. Its doc comment was updated by WI-788 to say this explicitly rather than changing behavior mid-ticket. Found by /code-review on WI-788. SMALL. ACCEPTANCE: threading is positional with name agreement; a test drives a permuted literal and asserts the diagnostic names the right component; full workspace green via scripts/test.sh.
