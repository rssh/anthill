## Description

THE SPEC AND THE LOADER DISAGREE ON WHETHER `=` IS AN EQUATIONAL-RULE HEAD — the spec says only `<=>` is, the loader accepts BOTH, and the stdlib is written both ways. kernel-language.md §5.3 ('Equational rules') states: 'The head connective is `<=>`, **not** `=`: `=` (`Eq.eq`) is a semantic equality *test* that never binds, whereas an equational rule head *unifies* the redex with the rule's LHS and derives the RHS.' THE IMPLEMENTATION DOES NOT MAKE THAT DISTINCTION: `is_equational_head` (kb/load.rs) classifies through `is_equality_connective_functor` (kb/mod.rs), which matches the `eq` symbol OR the `unify` symbol — i.e. both spellings, deliberately, with a WI-526 comment saying a `<=>`-spelled equation 'stays cite-required-by-default exactly like its `=`/`eq` predecessor'. MEASURED by driving all four (connective × attribute) combinations on one shape (`the_head_connective_is_not_what_enables_an_equation`, wi884_sibling_backing_test): with `[simp]`, `=` and `<=>` BOTH fire and answer 10; without it, BOTH die `OperationBodyMissing`. THE ANSWER TRACKS THE ATTRIBUTE ALONE. THE COST IS NOT HYPOTHETICAL — it already produced a wrong diagnosis in a shipped comment. WI-884 read §5.3, concluded that `Bool.ite`'s dead rule-level reduction was CAUSED by `bool.anthill` spelling its case laws with `=`, and wrote that into two files before driving refuted it; the real cause is that those laws are UNTAGGED (WI-881: `[simp]` is the enablement). The error runs the other way too: a reader who trusts §5.3 will believe an `=`-spelled `[simp]` rule is inert when it fires. THE STDLIB IS WRITTEN BOTH WAYS, so this is not dormant: `=` heads appear in bool.anthill (13, including the two `ite` cases), algebra.anthill (the Ring and VectorSpace law blocks), map.anthill, logical_stream.anthill (two `interleave` rules that read as a DEFINITION rather than a law), and reflect.anthill:89-90, which carries `[simp]` ON AN `=` HEAD — the exact combination §5.3 says cannot exist. DECIDE ONE WAY. (a) The spec is right and the loader should REFUSE (or warn on) an `=`-spelled equational head — a breaking change to every file above, needing a migration. (b) The loader is right and §5.3 should say the two connectives are INTERCHANGEABLE in a rule HEAD, with `<=>` the preferred spelling, and should state the test-vs-bind distinction only where it actually holds (guards, contracts, `ensures` — which §5.3 already lists separately). (c) They should genuinely differ, which requires naming what an `=`-headed bodyless rule IS if not an equation, and what becomes of the ones in the stdlib today. (b) is the cheap one and is probably right, but settle it by reading what `is_equality_connective_functor`'s CALLERS depend on — the resolver's eq/non-eq candidate triage, `simp_equation_rids`, and WI-139's cite-required unindexing all read it — not by preferring the cheap option. ACCEPTANCE: kernel-language.md §5.3 and the loader agree; a test pins the decision across all four (connective × attribute) combinations — WI-884's exists and asserts TODAY's behaviour, so it either stands or is inverted deliberately; if (a), the stdlib is migrated and the refusal names the file and line; full workspace green via rustland/scripts/test.sh. REFERENCE: WI-884 (which was misled by §5.3 and drove the refutation), WI-881 ('[simp] is the enablement, not the direction'), WI-887 (`Bool.ite`, the operation the wrong diagnosis was about), kb/load.rs `is_equational_head`, kb/mod.rs `is_equality_connective_functor`, kernel-language.md §5.3.
