## description

An entity constructor's NAMED ARGUMENT naming no declared field is accepted EVERYWHERE — `fact mk(a: 1, bogus: 2)` over `entity mk(a: Int64)` loads clean. Refuse it, at the loader's ONE term-conversion funnel, beside the POSITIONAL over-arity check that is already there.

MEASURED MATRIX (HEAD b0411496 + WI-849 working tree, 2026-07-28). `sort Box entity mk(a: Int64) end`, then one `bogus:` label too many. EVERY constructor position LOADS CLEAN:
  (a) fact head — `fact mk(a: 1, bogus: 2)`;
  (h) fact head, positional + unknown named — `fact mk(1, bogus: 2)`;
  (d) a DIFFERENT entity's fact — `fact outer(inner: 1, bogus: 2)`;
  (b) operation body — `operation go() -> Box = mk(a: 1, bogus: 2)`;
  (i) NESTED in an operation body — `outer(inner: mk(a: 1, bogus: 2))`;
  (j) rule HEAD — `rule mk(a: ?x, bogus: 2) :- on(v: 1)`;
  (c) rule BODY atom — `rule r(?x) :- mk(a: ?x, bogus: ?y)`;
  (e) constraint body — `constraint c :- mk(a: ?x, bogus: ?y)`.
CONTROLS: an OPERATION call with the same shape IS refused — `take(a: 1, bogus: 2)` gives "named argument 'bogus' names no param" (`named_arg_coverage_errors`, WI-426/WI-783) — and a well-formed `fact mk(a: 1)` still loads. So this is ONE missing check on the ENTITY-CONSTRUCTOR side, not eight independent holes.

WHY IT IS SILENT, mechanically. Two readers, both keyed the same way and both blind in the same direction:
  * `check_constructor_iter` (`kb/typing.rs`) iterates the DECLARED FIELDS and looks each one up in the supplied named args (`field_types.iter()` … `named_args.iter().find(|(s, _)| s == field_sym)`). A supplied label matching no declared field is never visited, so its value's type is NEVER CHECKED — the WI-805 shape exactly ("reachable by neither its name nor its position, with its declared type never checked").
  * `canonicalize_record_named_args` (`kb/resolve.rs:4013`) sorts by declared field order via `order.get(s).copied().unwrap_or(usize::MAX)` — an unknown label sorts LAST and rides into the hash-consed term as a real named arg.
So the extra field is BUILT, STORED and INDEXED: it participates in discrim matching and in structural equality, it just corresponds to nothing declared. `fact mk(a: 1, bogus: 2)` and `fact mk(a: 1)` are DIFFERENT terms, so a query written the other way silently fails to match.

`TypeError::UnknownField { span, entity_name, field }` ALREADY EXISTS for precisely this (`kb/typing.rs:51`), with a Display arm (:432, "unknown field '{}' in entity {}") and a `LoadError` conversion (:649) — and is CONSTRUCTED NOWHERE in the crate. The diagnostic was designed and never wired.

WHERE THE CHECK GOES — the funnel, not the eight producers. `Loader::convert_term`'s constructor arm (`kb/load.rs` ~7743-7830, the `new_functor` / `new_named` / `new_pos` block) is the SINGLE path every one of (a)(c)(d)(e)(h)(j) reaches, and it ALREADY hosts the positional twin of this check: `PositionalPlan::OverArity` raises "constructor '…' given N positional argument(s) but has M unfilled field(s)" at :7753. An unknown NAMED label is that error's missing sibling and belongs on the same gate (`kb.entity_field_names(functor).is_some()` — a functor with no declared schema has nothing to check against). This is deliberately NOT eight per-producer checks: "enumerate the droppers" is the WI-805 / WI-839 mistake, and cases (i) and (e) were both found only by running the matrix.

OPEN QUESTION THE IMPLEMENTATION MUST SETTLE BY MEASUREMENT, not by guessing: whether operation BODIES (cases b, i) come through the same loader arm or need the check in `check_constructor_iter` too. If a second site is genuinely needed, say so in a comment and give the two ONE shared helper so their messages cannot drift — the WI-839 rule.

EXCLUSIONS to verify against the FULL SUITE rather than assume:
  * REFLECT-FORM functors. `positional_to_named_plan` already skips `anthill.reflect.*` and the reflect meta-ctors for the POSITIONAL rule; whether the NAMED rule needs the same exemption is UNMEASURED. Note the loader's own `OperationInfo` fact carries a `type_params` named arg that is NOT in the declared `OperationInfo` entity (reflect.anthill:641 lists name/params/return_type/effects/requires/ensures/meta) — but it is built by `kb.alloc(Term::Fn{…})` directly (load.rs:13670), NOT through `convert_term`, so it should not reach this check. CONFIRM that by running the suite; do not assume it.
  * ORDERED PRODUCTS (named tuples, `anthill.reflect.TupleLiteral`): a tuple's labels are the AUTHOR's, not a declared schema, so it must not be checked. Expected to fall out of the `entity_field_names(...).is_some()` gate — verify.
  * SUGAR-GENERATED facts (the loader's own emissions that DO go through convert_term) are the real risk. The suite is the measurement.

ACCEPTANCE: every one of (a)(b)(c)(d)(e)(h)(i)(j) above is REFUSED with a diagnostic naming the entity AND the offending label; the two controls still behave (the operation-call message unchanged, `fact mk(a: 1)` still loads); a well-formed named tuple with arbitrary labels still loads; `TypeError::UnknownField` is either the variant used or deleted as dead — not left constructed-nowhere; full workspace green via rustland/scripts/test.sh.
