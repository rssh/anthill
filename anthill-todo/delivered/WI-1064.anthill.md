## Description

scala-gen: `requires` -> `extends` (§2.7) is unsound in two shapes -- a refining override and a data sort that requires an algebra. Decide what a sort-level `requires` becomes when a supertrait cannot carry it.

MEASURED 2026-08-09, delivering WI-1062. Not an effect question and not caused by that ticket -- WI-1062 put six prelude files into the emitted tree for the first time, and three of them carry this defect. It was invisible while they were refused.

THE MAPPING TODAY: `Bootstrap.emitSort` renders every `Item.RequiresDeclItem` into the sort's `extends` clause (`docs/scala-forward-mapping.md` §2.7: 'a `requires` can be either a type-class supertrait or a `using` context parameter'; the named-slot half is WI-1022's, and it is REFUSED today). A Scala supertrait is nominal subtyping, and anthill's `requires` is not.

SHAPE 1 -- A REFINING OVERRIDE. `finite_collection.anthill` writes `requires Iterable[C = C, Element = Element, E = E]` and then `operation map(c, f) -> FiniteCollection[...]`, where `Iterable.map` returns `Stream[...]`. In anthill the return types are related through `provides` (a FiniteCollection provides Iterable); in Scala `FiniteCollection` is not a subtype of `Stream`, so RefChecks reports `error overriding method map in trait Iterable ... has incompatible type`. Same for `filter`. TWO errors.

SHAPE 2 -- A DATA SORT REQUIRING AN ALGEBRA. `finite_combinators.anthill`'s `FiniteMappedStream` has an `entity` and `requires FiniteCollection[...]`, so it emits `enum FiniteMappedStream[...] extends anthill.prelude.FiniteCollection[SrcC, Src]` -- and an enum CASE cannot leave inherited members abstract: `class Fmapped needs to be abstract, since it has 9 unimplemented members`. Bootstrap emits signatures only (bodies are the KB-driven gen's, proposal 034), so no bootstrap emission can ever satisfy them. Same for `FiniteFilteredStream`. TWO errors.

MEASURED CLOSURE, peeling the failing files off and recompiling (`dotc` ends the run at the phase that first reported an error, so a single count hides everything later phases say):
  before WI-1062:  11 -> 3 -> clean, 33 files
  after  WI-1062:   4 -> 3 -> 4 -> clean, 39 files
That last round of 4 is this ticket, in the three files named above.

CANDIDATE ANSWERS, none obviously right, which is why this is not an inline fix:
 1. Put the `extends` on the `<Sort>Ops` TRAIT rather than on the data declaration. Fixes shape 2 and matches §2.3's split (the data type vs the contract an implementation satisfies), but `FiniteMappedStreamOps` declares `collect`/`iterator` and would then inherit `FiniteCollection`'s whole surface -- and it does not fix shape 1.
 2. Emit `requires` as a `using` witness (`(using ev: Iterable[C, Element])`) rather than a supertrait, which is §2.7's other half and is what WI-1022 already owns for the NAMED slot. Uniform, and it drops nominal subtyping entirely -- so a consumer that relied on `FiniteCollection <: Iterable` loses it.
 3. Refuse the constructs that cannot be spelled -- a `requires` on a sort with constructors, and a member whose signature conflicts with an inherited one -- putting three more files back in the refusal set. Loud, and it re-opens the cascade WI-1062 just closed.
Whichever is chosen, §2.7 must say it: today it offers two mappings and does not say when each applies, which is how one of them came to be applied unconditionally.

ACCEPTANCE: §2.7 states the rule with its reason; the emitted FiniteCollection / FiniteMappedStream / FiniteFilteredStream compile in the prelude closure (or are refused with the construct named, and the refusal-set test in BootstrapTest records them); the peeled closure measurement above is re-run and recorded. Say at each test site which assertion fails when the arm is backed out. sbt test green.

SOURCE: measured while delivering WI-1062.

THE REQUIRES NAMES A CARRIER, AND ON A DATA SORT IT IS NEVER THIS SORT -- which re-cuts the ticket's two shapes into two problems with two different owners and retires all three candidate answers as stated. Driven 2026-08-09 against the delivered tree.

SHAPE 2 IS NOT "requires -> extends is unsound on a data sort". IT IS BOOTSTRAP EMITTING THE WRONG ONE OF TWO ADJACENT LINES. finite_combinators.anthill:48-51 reads, in order: `requires FiniteCollection[C = SrcC, Element = Src, E = ES]`; `entity fmapped(source: FiniteCollection[C = SrcC, Element = Src, E = ES], fn: ...)`; `provides FiniteCollection[C = FiniteMappedStream, Element = T, E = {ES, EF}]`. The REQUIRES binds the carrier slot to SrcC -- a PARAMETER -- so it constrains the field's type and says nothing whatever about FiniteMappedStream. The sort's claim about ITSELF is the provides, whose carrier slot IS the sort. `Bootstrap.emitSort` collects only `Item.RequiresDeclItem`; `Item.ProvidesClauseItem` falls through its `case _` and is dropped in silence (~28 provides clauses across 11 prelude files, not one of them read). So the emitted `extends` is built from the CONSTRAINT and the is-a claim is discarded -- and the 9-unimplemented-members error is an obligation the sort never incurred.

THE RULE THIS GIVES §2.7, decidable from syntax so proposal 034's KB-free rule survives: a `requires` becomes a SUPERTRAIT only on an ALGEBRA sort, where the requirement is over the same carrier the sort is an algebra over; on a sort WITH CONSTRUCTORS the sort IS the carrier, no `requires` in the corpus binds the carrier slot to it, and the requirement is a context bound on an input (§2.7's other half, WI-1022's `using`) or a refusal until that half exists. `Bootstrap.SortShape` ALREADY draws exactly that line (Algebra vs Record/Sum), and `renderMainSort` computes `ext` ONCE and hands the same string to all three branches -- which is mechanically how one decision came to be applied to three different situations.

MEASURED BY GREP over every `requires` in stdlib/anthill/prelude: the rule reclassifies exactly finite_combinators.anthill:48 and :87 and leaves every currently-green supertrait untouched -- eq.anthill:35/59, ordered.anthill:17/77/78, numeric.anthill:8, lattice.anthill:5/30, field.anthill:13, set.anthill:13, map.anthill:16, algebra.anthill:65, and finite_collection.anthill:25's own `requires Iterable[C = C]`. So the pinned `trait Eq[T] extends PartialEq[T]` (WI-170/WI-644) and §2.7's own `Ord extends Eq` worked example stay exactly as they are.

HOW RUSTLAND ANSWERS IT: it does not, and the three reasons are worth recording because together they say the rust bootstrap is not a template here. (a) SCOPE -- rustland/anthill-stl/build.rs:95 generates SIX hand-picked stdlib files (stream, logical_stream, meta, reflect, store, filesystem), chosen by whether a rust consumer exists; finite_collection / finite_combinators / iterable are not among them, so rustland has never been asked this question, and scaland's whole-39-file closure is a strictly harder bar than rustland sets itself. (b) SHAPE 1 IS LEGAL RUST -- COMPILED, not recalled: a subtrait redeclaring a supertrait method with an incompatible return type builds clean, because rust SHADOWS rather than overrides; any ambiguity surfaces at a CALL SITE (E0034) and a signature-only skeleton emits none. Scala's `extends` means override and is checked at the declaration, which is why the identical mapping is caught here and not there. (c) SHAPE 2 IS SILENTLY DROPPED -- `SortInfo::from_items` collects `Item::RequiresDecl` into `supertraits` (codegen/rust.rs:221) and `emit_sort_as_enum` (:1156) never reads the field, because a rust data type carries no conformance in its declaration; docs/rust-forward-mapping.md:290 also records that bootstrap strips the BINDINGS, so `[C = SrcC]` never reaches the output at all. A silent skip is what this repo's principles forbid, so (c) is evidence and not a model -- though that rust needs NOTHING on the data declaration is itself a hint that a `requires` on a data sort carries no is-a obligation to begin with.

BOOKKEEPING: this ticket says "three files" but names three SORTS in TWO files -- FiniteMappedStream and FiniteFilteredStream both live in finite_combinators.anthill, and finite_stream.anthill carries no `requires` at all (only `provides`).
