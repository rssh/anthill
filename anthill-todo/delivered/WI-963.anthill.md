## Description

make_type_var interns a TRANSIENT inference wildcard into the PERSISTENT term store - a representation question, not a performance one.

NOT A PERFORMANCE TICKET. Its predecessor WI-960 was, and was REJECTED on measurement: make_type_var runs 6 times in a full stdlib + host-bindings load (see WI-960's feedback). Do not reopen that framing; the question here is where these terms should LIVE, and it is worth answering at zero calls per second.

THE SHAPE. `make_type_var(name) -> TermId` (kb/mod.rs) builds `type_var(name: <sym>)` through make_entity_term, so it is HASH-CONSED and REFCOUNTED into TermStore. CLAUDE.md's representation note reserves hash-consing for PERSISTENT, HEAVILY-SHARED structure - asserted facts, rule heads, nominal sort identities - and states that transient terms (query patterns, occurrence-derived twins) are deliberately NOT interned: they ride as Value::Node/Entity and match structurally, since the discrimination tree keys on DiscrimKey, never on TermId identity. A `?_` standing for an under-determined type is transient by definition - WI-578's own doc calls it 'the TOTAL fallback for an under-determined type'.

MEASURED at the call sites (11 production, 2 test):
  8 of 11 immediately write `Value::term(kb.make_type_var(fresh))` - the TermId is incidental, an artifact of the return type.
  3 genuinely want a term: TypeChild::Ground (typing.rs:2059), and the two in reconstruct_sort_params (typing.rs), whose results feed make_parameterized_type building a hash-consed type SPINE.
  Every caller passes a CONSTANT literal name - "?_", "?T", "?param", "?result", "?pat", "?logical_var", "?ungrounded" - so there are ~7 distinct wildcard terms in the store, not one per inference site. That bounds the leak: this is not unbounded growth, which is exactly why it is a design question and not a bug.

WHY IT MATTERS BEYOND TIDINESS: the return type is what made WI-960's memo alternative UNSAFE. TermStore is refcounted with a free_list and alloc() increments even on a hash-cons HIT, so a cached TermId can dangle and one returned without an incref over-decrements every caller. Any future caching, sharing, or cross-phase reuse of these wildcards inherits that hazard purely from the carrier choice.

THE DECISION TO MAKE, not a prescription: (a) leave it - the ~7 interned wildcards are cheap and the 3 term-wanting callers need the TermId anyway, in which case WRITE THAT REASON at make_type_var so the next reader stops re-deriving it; or (b) give the 8 Value-wrapping callers a Value-returning twin and keep the TermId form for the 3 spine builders, which needs a check that a Value-carried type var unifies and subtypes identically to the interned one (WI-342/348 carrier-neutrality); or (c) something else the reader finds. Option (b) is only worth it if the carrier-neutral path is already total for type vars - CHECK before choosing, do not assume.

ACCEPTANCE: driven, whichever option wins. If (a): the reason is at the site and a test pins that the 3 term-wanting callers actually need a TermId (make_parameterized_type's spine), so a later reader cannot delete the justification as speculation. If (b): a test that the SAME under-determined type unifies/subtypes identically through both carriers - assert the verdict, not that it loads - plus the control naming which assertion fails if the Value form is routed through a path that re-interns. cargo-test green.

SOURCE: user question during WI-960 ('why we use TermId in WI-960?').

### 2026-08-03T12:29:51Z — feedback — user

ANSWERED BEFORE STARTING - and the answer TILTS AGAINST this ticket's own premise. USER asked: 'why make_type_var returns TermId and why it create term, why Var is not enough?'

A BARE Var IS NOT AN UNKNOWN TYPE, IT IS A MALFORMED ONE. type_head (typing.rs) reads head.functor_sym(); ViewHead::Var(_) returns None (term_view.rs:72), so a bare Var in type position classifies as TypeHead::Error. The type language is a DECLARED vocabulary - stdlib/anthill/prelude/sort.anthill:309 declares 'entity TypeVar(name: Symbol)' beside SortRef / Parameterized / the arrow - and type_head dispatches on the functor's QUALIFIED NAME. Var is simply not in that vocabulary. Types are terms in it so anthill code can read them through reflect; that is the design, not an accident of the API.

THE SEMANTICS DIFFER, AND THE DIFFERENCE IS LOAD-BEARING. Var::Global is a LOGIC variable: unification BINDS it, and the discrim tree treats a flex Global as a wildcard var-edge matching any subterm. type_var(name: "?_") is INERT - compatible-with-anything in the unify/subtype dispatch WITHOUT committing. That is fresh_type_var's documented M6 flounder posture. With a logic var the first unification turns 'I do not know this type' into 'it is now Int64' and propagates that commitment to every occurrence of the same VarId. WI-384's comment already says it at the site: 'a type_var WILDCARD (not a bare logic Var)'.

IDENTITY, the point this ticket got backwards: type_var hash-conses per NAME, so every "?_" is ONE shared term - ~7 in the whole store across all 7 literal names. A Var::Global carries a unique VarId, so two 'unknown's would be structurally UNEQUAL and every site would need a fresh_var allocation. Per-name interning of a declared vocabulary member is NOMINAL IDENTITY, which CLAUDE.md's representation note lists as exactly what SHOULD be hash-consed - not the 'transient query pattern' this ticket compared it to. The 8 Value::term(...) call sites are not evidence of a wrong carrier; they are callers of a term-producing builder whose product legitimately IS a term.

CONSEQUENCE: option (b) (a Value-returning twin) is NOT indicated - it would hand callers a carrier that type_head cannot classify unless it re-wraps the same entity term, i.e. the same term by another road. Option (a) is the answer: leave the representation, and WRITE THE REASON AT make_type_var so the next reader stops re-deriving it. Narrowing this ticket to that.
