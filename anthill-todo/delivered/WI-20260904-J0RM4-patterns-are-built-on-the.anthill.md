## Description

PATTERNS ARE BUILT ON THE PERSISTENT CARRIER, which is the opposite of what the architecture note says. CLAUDE.md's representation note states that 'transient terms (query patterns, occurrence-derived twins) are deliberately NOT interned; they ride as Value::Node/Entity carriers and match structurally'. `convert_query_term` (kb/load.rs:16889) does the reverse: it takes `&mut KnowledgeBase`, returns a `TermId`, calls `kb.alloc(term)` -- which is `self.terms.alloc(..)` on the HASH-CONSED store -- and then `expand_bare_entity_pattern(kb, tid, false)`, which calls `fill_entity_named_args` in PATTERN position and mints `kb.fresh_var(field)` + `kb.alloc(Term::Var(..))` for every field the query did not write. So every query pattern, and one fresh interned var per omitted field, lands in the KB's permanent store. THE INTERNER IS MONOTONE BY DESIGN (WI-SPGBP recorded that ids RE-ENTER only via the `rules` rollback), so nothing reclaims them: a long-running process -- `anthill run`, the reflect KB layer, a server, a test loop -- grows the term store and the VarId counter without bound, once per query. NOTHING IS WRONG WITH THE ANSWERS; this is a leak and a layering inversion, not a miscomputation. That is why it has stayed invisible: the CLI exits after one query. THE SUBSTRATE ALREADY EXISTS. `TermView` has seven carriers (TermIdView, TermId, Value, Rc<NodeOccurrence>, ViewItem, ReflectedExpr) and the discrimination tree keys on structural `DiscrimKey`s and never on `TermId` identity -- CLAUDE.md states this explicitly as the reason hash-consing is NOT implied by being indexed. So a `Value::Node`-carried pattern indexes and matches identically today; the query path simply never migrated. Neighbouring checks are already carrier-neutral and generic over `TermView` (`is_reflect_term_type`, `is_option_type`), which is the idiom to follow. THE BLOCKER IS THE FILLER. `fill_entity_named_args` (kb/load.rs:16762) is TermId-bound in its signature (`named: &mut SmallVec<[(Symbol, TermId); 2]>`) and allocates both fills into the intern store. It is shared by THREE callers that WI-20260902-CZJ2N deliberately unified so that 'two spellings of section 8.3's all-fields-fresh pattern must not have two fillers' -- the converter's own `Fn` arm, `expand_bare_entity_subject`, and `expand_bare_entity_pattern`. So it cannot simply be forked for the query path without re-splitting the thing CZJ2N joined; it has to become carrier-parametric. NOTE THE ASYMMETRY THAT MAKES THIS TRACTABLE: a pattern written in SOURCE (a rule body, or a `Term`-typed field like `FactHolds(pattern: E(id: ?x))`) is PERSISTENT and interning it is legitimate. Only the RUNTIME-constructed query pattern is transient. The fix therefore need not change the loader's own paths -- it needs the filler to be able to build on a non-interning carrier, and the query entry point to ask for one. ACCEPTANCE: `convert_query_term` builds a pattern on a carrier-neutral carrier (`Value::Node` / `TermView`) with no `kb.alloc` and no `fresh_var` reaching the persistent store; `fill_entity_named_args` is carrier-parametric and its three callers keep ONE filler; a test DRIVES it by running N queries against a loaded KB and asserting the term-store length and the VarId counter are UNCHANGED after the first (today they grow linearly -- that is the control, and it must fail when the change is backed out); matching results are identical before and after, including the section 8.3 all-fields-fresh expansion and WI-1096's list-literal shape agreement; cargo-test green via scripts/test.sh. RELATED: the same free function is also mis-named for what it does -- it runs in BOTH value and pattern position and its stated purpose is discrim-tree slot uniformity, not query handling -- and it is a free function inside a 28k-line load.rs; a rename and a move to its own module belong with this work.

THE QUERY PATTERN IS THE LAST POSITION THAT STILL MUST BE ONE, which is the strongest form of this ticket's argument and was not stated in the description: it is not that patterns COULD be carrier-neutral, it is that every neighbour already is and this one position was left behind.

THE ARGUMENT FOR VALUE is that CLAUDE.md's representation note names `Value::Node`/`Entity` for exactly this population, and that the fact-head side already carries patterns that way, so a query pattern and the value fact it searches for would ride the same carrier.

THE ACCEPTANCE WAS WRONG IN TWO PLACES, measured rather than argued.

(a) THE VarId COUNTER CANNOT BE HELD FLAT AND MUST NOT BE. It is a u32 counter and retains nothing -- it is not the leak. Recorded as a NOTE row (the_var_counter_still_moves_and_that_is_correct), green either way.

(b) A SECOND, SMALLER LEAK REMAINS, AND IT IS THE RESOLVER'S. MEASURED on the fixture: convert+resolve of a RULE goal grows the store by exactly 1 per query, all of it AFTER the conversion; a FACT-matching goal grows it by 0. The slot is with_fresh_vars' De Bruijn opening -- term_from_debruijn allocs a Term::Var(Global(fresh)) for the head slot a query var linked to -- and Substitution is TermId-keyed throughout, so closing it means moving the substitution layer, which is bigger than this whole ticket. NOT filed as a ticket (the queue is at 170 open): it is ASSERTED instead, by resolution_of_a_rule_goal_still_grows_the_store_by_one, which asserts both halves and goes RED when someone closes it -- an unasserted known leak is how one survives its own fix.
