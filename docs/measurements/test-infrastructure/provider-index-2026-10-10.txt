#   the stdlib's own load                      413 provision clauses, 89 condition clauses     BEFORE and AFTER

# /code-review, the same three results). Each binary run SIX times, twelve listings:
#   the rows, rule ids dropped, clause numbers masked, sorted     ONE listing — all twelve are the same file

#   the listing as printed                                        twelve different files, six and six
# So: the same rows and the same conditions, BEFORE and AFTER, in all three loads.
#
# AND A FINDING THAT IS NOT THIS CHANGE'S: the tree before it does not print the same listing twice.
#   * The derived rows get their rule ids in another order at every run. `eq_derive::composite_sorts` walks
#     `entity_field_types`' keys, a `HashMap` with the standard per-process seed, and the derivations assert in that
#     order.
#   * `anthill.prelude.Result`'s two derived `NonEq` clauses — `:- NonEq[T]` and `:- NonEq[E]`, each carrying the
#     `PartialEq` conditions — are numbered 4 and 5 one way round or the other, run to run: in the stdlib's own

#     They are the only rows that differ once rule ids are dropped. The order is that of `Result`'s two
#     constructors as `KnowledgeBase::constructors_of_sort` lists them, and it walks `entity_parent`, a `HashMap`;
#     the comment at `derive_conditional_noneq` says the clause indices do not depend on a hash iteration order.
#   Both are in BEFORE as in AFTER (each of the four set-listings came out of both binaries). Not fixed here;
#   filed 2026-10-11 as WI-20261011-6GMCN.

== 6. the name table under the index's keys (found by /code-review, 2026-10-11) ==
# A bucket key is `canonical_sort_sym` of a symbol in the row's head, computed when the row is asserted. The build
# this index used to be computed every key again at each rebuild — two or three times a load — so a key that the
# name table moved under was put right by the way. `SymbolTable::set_canonical`, the one write of
# `by_qualified_name`, now counts a write that moves the canonical symbol of a symbol that already exists (the name
# was interned before it was declared; a qualified name is defined a second time under another local name; a
# layer's discard puts an earlier table back), and the index computes its keys again, by a walk of the relation,
# at the first read or filing after the count has moved.
#
# How often that happens in a load — a temporary line in both re-keying branches (not kept), the bench at ITERS=1,
# nine loads (a full load, one before the typer, and later loads plain, sealed and into copies):
#     re-keyings: 0 in all nine.   The count does not move in a stdlib load or in the bench's user load.
# So a read pays one comparison of two integers for it, and a `define` one more lookup of its name; section 1's
# second take is with both in.
# The unit row that drives both moves, and what it fails on, is in section 4.
