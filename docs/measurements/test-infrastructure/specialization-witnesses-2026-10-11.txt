# (docs/design/test-infrastructure.md §4).
# Sections 1–7 (15:50 – 16:06) are THE MEASUREMENT, taken before anything was built; the shape was then decided
# with the user: an index, the pass still a walk of every row, and no rule about loads.
# Sections 8–10 are the tree as delivered; section 11 is what /code-review changed on the way to it, and an older
# defect it found; section 12 is one traced run of anthill-core's suites, and section 13 the gate and the recipes.

# Tree:    main at e1796c00 (anthill-core's sources as WI-20261011-A3NND left them, 5d7e9fd9, and the typer changes
#          of WI-20261011-12VZB merged since).
#          The MARKED binary is that tree with temporary marks inside the three witness passes (not kept): a clock and
#          a count for each step of `load::register_specialization_witnesses`, a clock for the collection of names and
#          for the walk in `register_requires_axiom_witnesses` and `register_induction_axiom_witnesses`, and a switch
#          that runs the three passes again straight after the first. All of them off unless ANTHILL_LOAD_TIMING=1.
#          The PROBE binary is the marked one with a temporary switch for each of section 6's three shapes.
# Profile: anthill-core at opt-level 2, the two tree-sitter crates at 3 (the gate's build); debug assertions on.
# Bench:   docs/measurements/test-infrastructure/bench_load.rs, ITERS=15, one thread; medians of 15.

# What the marks cost: the pass's mark reads 9.9–10.7 ms in the marked binary where the pass's own clock reads
# 9.6–10.4 — the difference is the printing of the line of counts, 0.25–0.3 ms, inside the load's mark and outside
# the pass's. The steps add up to the pass's own clock within 0.05 ms.
#
# SO: on a later load 9.0–9.7 ms of the pass's 9.5–10.4 is the scan — for each of 392 rows, every one of the 127
# record names tested for the prefix `<spec>.requires.`, the prefix built by a `format!` inside the test, 49 784
# times, 0.18–0.19 us each — and 0.33 ms is everything else. It asserts nothing: 52 names built, 52 found.
# The standard library leaves 127 records: 42 requires-axioms, 33 induction principles, 52 specializations.
#
# WHY THE LATER LOAD IS THE DEARER, both factors of the product:
#   * rows, 102 -> 392. The pass stands ABOVE the derivations in `load_phase_inner`, so the load that derives a
#     provision does not show it to its own pass, and every later load does. Of the 311 rows the library's load
#     derives, 21 carry a mark the pass reads (`derived_provision_origin_of`, `is_unbacked_derived_provision`: the
#     forwarded rows and the unbacked `NonEq`); 290 carry none — the derived `PartialEq` / `Eq` and the `TypeValue`
#     rows — and are decoded and scanned for. None of their specs has a law, so they match nothing (38 rows with
#     a law on both kinds of load), and that is the only reason the two kinds of load leave the same records.
#   * names, 75 -> 127: the 52 records the library's own pass asserts are in the set every later pass scans.

== 7. the listing of the records is not the same listing run to run — the tree BEFORE anything was built ==
# A temporary example (not kept) loads the stdlib's 87 files in one call and prints every `ProofRecord` — its rule
# id, fact or rule, and the head as source text (the `rule`, the witness with its `parametric` and `substitution`);
# then seals that load, loads a user file and prints them again; then prints them for the stdlib and that file in
# ONE call. Run six times with section 5's user file: SIX different files, and with the rule ids dropped and the
# lines sorted, ONE.
# The laws of a row are emitted in the order the filter meets them, which is the iteration order of a
# `std::collections::HashSet` of the names — another order in every process, and in every set of one process. So a
# provision of a spec with two laws has its two records in either order (`MappedStreamFinite provides
# FiniteCollection`: `EffectsRuntime_E` then `Iterable_C_E_Element`, or the other way), and their rule ids with them.
# The same kind of finding as WI-20261011-6GMCN's (the derived provisions follow a `HashMap`'s order), at another site.
