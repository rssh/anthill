## 1. Substrate (pre-existing, unchanged)

- **Declare**: witness sorts (WI-450, named by their sort symbol) and instance facts (WI-431, unnamed — the §3.1 nameability gate's reason). `SortProvidesInfo(sort_ref, spec)` records every provision.
- **Select**: the 042 bracket channel — `parse/convert.rs` → `build_call_type_args` (`load.rs`) → `seed_op_type_args` (`typing.rs`). Phase 0 (WI-839) closed every silent drop site: an unmatched key at a classified call is loud even when the callee declares no type params; a rule-/term-body bracket is a loud not-supported-here refusal, keyed on the `ParseAux type_args` channel (a rule-body *type application* is a different producer and stays checked).
- **Thread**: `Value::Requirement(handle)` dictionaries, `construct_requirement`, per-call frames rebuilt from `sub_requires` (`design/operation-call-model.md`, `design/requirement-dictionaries.md`). Selection changes only where `ResolvedTree::leaf { impl }`'s `impl` comes from.

## 2. Classifier work (proposal §3.3–§3.4) — delivered

- **Key resolution rule 1** spans the op's and the enclosing sort's type params — the sort-level seeding leg was a missing feature, built as WI-841 (one more WI-708-style key); the two scopes never both answer because the collision is refused at the declaration (phase 1's guard). Rule 1 matches by symbol identity on bare labels; rule 2 (spec short name) is a lookup gated by the same-spec context — WI-672's discipline, `same_label` family 2, never a short-name identity comparison.
- **A named slot's parameter is read back out of σ** once argument unification completes (`selections_from_slot_bindings` → `InstanceSelection`, WI-844): the bracket, the argument's type, and an eta'd op reference's expected arrow (`attach_eta_dispatch_dict`) are **three producers of one channel**. They are compared **unconditionally** — ranking them re-opens first-match across two same-spec slots (measured: a bracket `[A = ByLength]` beside an argument-typed `B = Alphabetical` deleted the conflict refusal under a ranked cut). `push_selection` owns the rule; the conflict diagnostic names both witnesses without attributing a producer, because a mixed pair is reachable. An **abstract** binding derives nothing (`is_type_param_value`) — that is what keeps `report[T, O]` a forward.
- **Merge safety** is argument-position type-variable agreement — WI-836, delivered; without it `union` across two orderings loaded clean. Omission-means-any is `check_sort_type_args` requiring no declared param be bound.
- Guards: the §3.3 shadowing refusals at the declaration; qualified keys refused (`unknown type-param`, no resolution rung by design — a resolved key would make selection depend on caller imports, while `build_concrete_dispatch_dict` takes no scope at all).

## 3. Ladder mechanics (proposal §3.2) — tiers 1–3 delivered, 2a proposed

- Tier 3 is `DispatchOutcome::Ambiguous` (carrying the tied providers) → `TypeError::DispatchAmbiguous` → `LoadError::UnselectedInstance`, rendered with a typed `TieRepair` decided at the render boundary. `LoadError::AmbiguousWitness` is **deleted**, not gated. `AmbiguousInstanceFact` and `MixedProviderKinds` (WI-838's one grouping per `(spec, dispatch carrier)` over all provider kinds) remain — they are the §3.1 nameability gate; the group loop gates on `Provider::is_nameable`.
- **Boundaries, each driven and pinned** (WI-843): a tie whose candidates are all concrete has no bracket (§3.5 check 3 refuses explicit witnesses there — the value decides); a sub-goal's tie propagates verbatim and must be stamped at its own level, not the outer goal's (`resolve_at_goal` mis-attribution, fixed); a **specificity-ordered pair never reaches tier 3** — `pick_most_specific` answers silently. That last is a recorded *widening* (tier 2 reaching cases the old load refusal made unreachable); WI-841's committed acceptance depends on it; making it loud would be a new coherence rule needing its own measurement.
- **Rung 2a (proposed)**: at the classifier's tie, consult `default_provider` (a materialized index over the §6 facts — the `EqDispatchIndex` pattern; the relations are the authority, the hot path reads the index). Flip inventory to assert at delivery: `two_string_orderings_make_a_bare_compare_ambiguous` becomes the acceptance (bracket-less `compare` = host order beside two loadable witnesses); WI-855's `AmbiguousRequirement` on the self-provider + rival pair resolves to the self-provider (the witness-only tie keeps it); the value-directed `AmbiguousSpecOpDispatch` likewise where one candidate is the carrier's own. Prerequisite: the coherence grouping had to gain the **self-provider candidate kind** — measured absent at WI-855 (*"a self-provider is a candidate of neither kind"* — `provision_binds_any_op` and `witness_dispatch_carrier` both missed it), which is also why `one_default` could not be checked. **Delivered as WI-859**; see §11.

## 4. Resolve hook (proposal §3.3's pinning) — delivered, one correction

`resolve(goal, scope)` step 0: a pinned goal returns the pinned provider after validation — as a `leaf` **only when both halves of its dictionary are empty** (§7's layout: the spec's own `requires` chain, then the provider's); anything else yields the conditional node with those sub-goals resolved. (Corrected 2026-07-30: the leaf-always reading built an arity-0 dictionary that dies at eval. Settled by WI-857 — and note the correction as first written was still too narrow, blaming only the *witness's* chain: the carrier-keyed case has no witness chain to bear and died anyway, because the missing half was the SPEC's.) Sub-resolutions search, except that a sub-goal the SELECTED provider itself provides resolves witness-locally (§7's locality rule); a bracket key cannot reach them (pinning changes which subgoals exist).

**Slot routes**: a `requires` slot is served by the enclosing sort's dictionary build, the spec-op dispatch, or an **op-scoped** clause — and the op-scoped route has no dictionary channel (`synth_req_names` is keyed by the parent sort; WI-822 leg 1, open), so WI-841 refuses a selection there whenever ≥2 providers answer, accepting only the sole-provider case. An op-scoped clause's spec is a bare application, so `goal_from_requires_entry` yields a bindings-free goal that every provider matches — a check routed through it passes vacuously; witness validation therefore runs once at the call site. A selection is keyed by the **spec** (a `SortGoal`'s coordinate): two anonymous same-spec slots are indistinguishable to a pin — two keys naming different witnesses for one spec are refused at the site.

## 6. Defaults implementation (proposal §3.6) — proposed

Reflect-layer file (a sibling section of `reflect/typing.anthill`, or `reflect/instance.anthill`): `entity DefaultProvider(spec, provider)`, `entity Coherent(spec)` (deferred data rows re-homing the `Eq` family list — ownership only, the check exists), `self_provides`, `default_provider` (declared ∪ inferred — consumers read the derived relation only), `constraint one_default`, `constraint coherent_one_target`. Load checks materialize into Rust (the `EqDispatchIndex` pattern); `DefaultProvider`'s provider field is a sort reference in a fact argument — proven surface (`fact Covariant(sort: List, param: T)`, proposal 035). Validation reuses §3.5 check 1 as a load check. No-displacement needs no code: the inferred row + `one_default` refuse the displacing fact. **Conditional defaults need no code either** — the declared-row rule joins through `provides`, which for a conditional provision holds only where its chain discharges (proposal §3.6/§5's `ListOrd` row) — but `one_default` must compare rows at **unifiable** carriers, so a ground default beside a parametric one for one family is refused: layering defaults by specificity would be a boundary-3-style widening — pin the refusal in phase 8's acceptance, don't inherit the question. **The inline sugar** (`default provides`, proposal §4) is loader work: one optional leading modifier token (the `internal` pattern; a trailing `[default]` was rejected — a bracket list after a bracketed type invites a GLR tie) desugaring in the converter to a `DefaultProvider` row with `provider =` the enclosing sort. The same family gives `coherent sort X … end` → a `Coherent(spec: X)` row (the `enum sort` precedent; arrives with the deferred re-homing), and `coherent` on a *provision* is refused — a provision must not foreclose coexistence for a spec/carrier it does not own. **`provides`-vs-`fact` synonymy is measured** (probe q5): a witness spelled with `provides Spec[T = Foreign]` loads and runs identically to the `fact` spelling — one construct, two conventional spellings — which grounds proposal §4's retirement of the `fact` spelling for provisions. Migration scope for that retirement: the stdlib bindings' fact rows (`anthill-stl/anthill/*.anthill`), the wi84x fixtures, examples, and the binding-block idiom (proposal 038's `provides X language rust` blocks); the deprecation warning sits at the loader's provision-lowering site, which already distinguishes a provision fact from a plain one. Namespace-level op-binding instance facts are out of scope (outside sorts; already quarantined by the nameability gate). Deferred: `within:` scoped rows (explicit field, NOT placement — a fact inside a sort already means "this sort provides"; scoped rows are classification-time only, so a sort with a scoped row and a rule body dispatching the same goal is refused); per-carrier `NoDefault`.

## 7. WI-857 — the gate (DELIVERED 2026-07-30), and the probe matrix

**Settlement.** One layout, one owner (`kb::typing::dict_layout`), stated in full in [`operation-call-model.md`](./operation-call-model.md) §"Dispatch rule": a dictionary for spec `S` supplied by provider `P` bundles `S`'s own direct `requires` chain (the **prefix** — what `requirement_at_sort`'s projection path indexes and what a body owned by `S` reads when dispatch lands on the spec's own op) then `P`'s (the **suffix** — what `P`'s member body reads); `P == S` contributes one list, which is also the parent-bundle dictionary's shape. `expand_dispatching_dict` hands the frame exactly the half its target's parent owns and is loud when the target's parent is a third sort with a chain of its own. Three further decisions, each forced by measurement:

- **An unresolved spec-half slot is RECORDED, not refused** (`ResolvedRequiresNode::Unavailable` → an empty bundle over a marker functor). Demanding it resolve broke **33 tests**: a spec-level `requires` is routinely satisfied only loosely, since `check_provider_requires` falls back to a base-level existence check wherever σ leaves a binding abstract — `FiniteCollection requires Iterable[C = C]` holds for a `List` only through `List provides Stream provides Iterable`, which no `Iterable[C = List[…]]` provision matches. Dispatching through the marker is refused (one owner: `dispatch_via_sort_ops_table`), so a slot nobody reads costs nothing and a slot somebody reads names the requirement that has no provider.
- **The LOCALITY rule** is in (see §4), as the review required.
- **Every producer must build a layout-valid dictionary.** The host-entry stand-ins (`seed_entry_requirements`, `call_with_requirements`' `__req_self`) were `functor` with NO sub-slots, which the layout reads as claiming that functor's whole chain and bundling none; they now carry marker sub-slots. Found by driving, not by inspection — wi818's value-directed rescue died on the arity check.

**The split it settled** was visible in the design doc as well as the code: the dictionary **producer** walked the *provider's* `requires` chain while `expand_dispatching_dict` named the frame from whatever the *dispatched target's parent* declared and `requirement_at_sort` indexed the *spec's* — and `operation-call-model.md`'s frame-push pseudo-code said "one per impl's `requires`" two paragraphs above a worked example that indexes the spec's. The three agreed only when the provider was a chain-free witness. Probes (scratchpad `q4a`–`q4g`, `anthill load`/`run` at HEAD; reproducers spelled in WI-857's feedback entry, all now pinned in `wi857_dictionary_layout_test.rs`):

| shape | spec's own chain | load | eval |
|---|---|---|---|
| parametric witness, own chain 2, spec chain **empty** (local `Sized`) | 0 | clean | **threads** — 3+6=9 through the conditional chain |
| same form over `Ordered`, nothing provides `Eq`/`PartialOrd[Duo]` | 2 | **refused** — provider must provide or the goal must resolve at the bindings | — |
| carrier provides `Eq` componentwise + witness bundles own `PartialOrd`+`Ordered`, parametric | 2 | clean — `Eq` leg discharged from the carrier, `PartialOrd` from the witness | **dies both routes** (σ-pinned and searched): `dispatching dict … arity 0 but its requires chain has 2 entries`; count stays 2 with own chain cut to 1 ⇒ frame named from the **spec's** chain |
| ground, chain-free, bundled, slot-free body | 2 | clean | **runs** (−1) |

Every row above now RUNS (`-1`, `9`, `-1`, `-1`; the refused row still refuses, correctly — nothing provides its `Eq`/`PartialOrd[Duo]`). Rows 1 and 4 were the accidental agreements and are kept as the controls: a mis-sliced half would surface only as a wrong value there, since their providers declare no `requires`.

**Consequences, as of delivery**: WI-857 no longer gates §3.8's library goal or rung 2a — phases 7 and 8c are unblocked. `check_provider_requires`'s discharge rule is unchanged and now doubly load-bearing, because the spec half is built from the same walk it checks (`provider_requires_subgoals` has one owner): provider-provides OR resolves-at-the-bindings (binding-precise and transitive when σ grounds; base-level fallback when abstract). The provider's own `requires` chain still does **not** discharge a spec-level requirement — the conditional spelling stays refused, exactly as the brainstorm drove.

**Conditional provisions (proposal §3.8)**: the provider-chain spelling works for the provision's *own* evidence — q4a threads it — while the chain does **not** discharge the *spec's* requirements (`check_provider_requires` never consults it; the brainstorm's obstacle-B drive). The per-clause `provides X :- goals` surface would need grammar plus per-provision chains; with the layout now settled it has a place to land — a per-provision chain is a second contributor to the **provider half**, not a new half. Phase 7 gave it a shipped driver and a ticket: **WI-869**, because a sort's one chain must serve `PartialEq[Pair]` and `Eq[Pair]` at two different strengths and cannot. ✅ **DELIVERED — see §16**, where the driver turned out to be a regression rather than an over-claim, and where the design landed on one slot set per sort with per-provision *strictness*.

**The composition leg, DRIVEN at phase 7 and found UNWIRED (WI-870).** Binding a witness's own *named* slot inside a bracket value (`O = ListOrd[OE = LexFst]`, proposal §3.3/§5) was the one composition never measured — the q4 series drove only the inferred form. Measured on the shipped `PairByFst`: the value's bracket list **is** validated against the witness (an unknown slot name is refused, naming `A, B, OA, OB`) and then **discarded** — `[Ordered = PairByFst[OA = PairBySnd]]`, whose value provides no `Ordered[Int64]` at all, loads clean and computes the unbound answer. `selection_witness_sym` reads the base functor (its own comment already says "a witness may carry type arguments"); nothing consumes the arguments, and a sub-goal resolves with `selected: &[]` by design. A **silent drop**, and a defect rather than a gap because `TieRepair::SubGoal` prints this exact spelling as the repair — an author who follows the diagnostic gets the identical error back.

Probe harness note: `anthill query -p` diverges from `anthill load` (sort-level member imports refused; panics on `realization.CarrierBinding` with the bindings dir) — drive reproducers via `anthill run` + a `Main` sort.

## 9. Phase 7 — the library, and the line it did not cross (DELIVERED 2026-07-30)

`stdlib/anthill/prelude/pair.anthill` gives `Pair` componentwise `PartialEq`/`Eq`. It does **not** give it an ordering, and that is the phase's substantive finding. *(Superseded — WI-876 removed the boilerplate cost and WI-869 removed the shared-chain blocker; `Pair` now ships four conditioned provisions and the canonical lexicographic order. §16.)*

**The instruction was "two orderings of one carrier in the shipped prelude". It was a PROXY for "exercise the mechanism outside the suite", and both readings turned out wrong for this carrier.** Shipping two co-equal witnesses hands every downstream bracket-less pair compare a tier-3 error the consumer never opted into — obstacle A, which the brainstorm's Options table judged absent for `Pair` by evaluating `Pair` as it *was* (self-providing nothing) rather than as the change would leave it. Shipping ONE canonical ordering avoids that (a pair *has* a canonical order — every neighbouring language gives `(a, b)` lexicographic `fst`-then-`snd`) and was implemented and driven end to end: `Ordered.compare` answering `-1`/`1`-on-tie/`0` bracket-free, a `SortedSet` of pairs sorting with no bracket. It was then withdrawn, because of what it cost.

**What it cost: seven operations in `pair.anthill` where one would do.** `compare` carries the logic; `max`/`min`/`gt`/`gte`/`lt`/`lte` are each one line restating "call `compare`, check the sign". Two checks force them, for different reasons — the LOAD check demands `max`/`min` (not resolver builtins, so `op_backed` finds no backing), and EVAL demands the rest (the spec-op builtins are scalar-only). Seven-or-nothing: drop any and either the load fails or `gt(pair, pair)` dies at run time on a program that loaded clean.

**The root cause is a grammar gap, and it is WI-876 — since DELIVERED 2026-07-30; see §10.** `Ordered.compare` / `PartialOrd.gt` & co. were registered on the SPEC op, so one implementation served every carrier that never wrote its own. That was not a design choice: a `provides X language rust` block admitted `artifact`, `carrier`, `namespace_map`, facts and rules — and **nothing that maps an operation to a host function** — so `Int64`'s host `compare` had nowhere to be keyed. `Int64` providing `Ordered` with no anthill-level `compare` is itself legitimate (`check_provider_operations` deliberately skips a host carrier); the defect was only *where* the implementation is keyed. The fix was exactly the one named here: add the mapping clause, key the scalar implementations per carrier, delete the spec-op registrations, and let `ordered.anthill`'s derivation — stated only as laws, and a rule is not backing (WI-818) — carry real default bodies, now unshadowed. A structural carrier now needs **only `compare`**.

**`PartialEq` is the control that shows this is a defect and not a necessity**: `eq` needs no per-carrier member on `Pair`, because `builtin_eq` → `semantic_equal` already dispatches to a carrier's own `eq`. One of the two builtin families learned to dispatch; the other did not.

**So the phase ships the equality and leaves the ordering to WI-876**, and `wi858_pair_orderings_test` drives 058's coexistence over `Pair` with **two PROGRAM-declared orderings** — which is a cleaner driver than WI-844's `String` anyway: `String` has a host `Ordered` provider, so its ties are three-way and a bracket-less compare there can never succeed; `Pair` provides no ordering, so two witnesses tie exactly two ways and every repair is writable.

**Other measured results, unchanged by the withdrawal**: the equality chain is `PartialEq`, not `Eq` — an `Eq` chain makes `Pair[A = Float, B = Int64]` a LOAD ERROR (WI-835's `NonEq` check), i.e. `Pair` stops being a general PRODUCT; and a sort's `requires` chain is SHARED by every provision it makes, so `provides Eq[Pair]` over-claims (`Set[T = Pair[Float, Int64]]` loads while `Set[T = Float]` is refused) — **WI-869**, delivered; §16 re-attributes the surviving half of that measurement to the ABSENCE of a positive use-site check, not to the provision. Three further spin-offs: **WI-870** (a bracket-value slot binding is validated then dropped), **WI-871** (a componentwise provider's second requirement slot is read from the first), **WI-872** (a provision's carrier is matched by SHORT NAME at dispatch), **WI-873** (`dispatch_origin` keeps one rewrite per spec op).

**The lesson**: a library change is where a design's conditions get their first real carrier — and where a phase instruction's letter can come apart from its purpose. `Pair` was the tree's first structural `Ordered` provider, so it was the first thing to test whether "provides `Ordered`" means anything without seven lines of boilerplate. It did not. Declining to ship the boilerplate is what turned that into a ticket instead of a precedent.

## 10. WI-876 — the host mapping (DELIVERED 2026-07-30)

`operation_map { compare: "ordered_compare" }` is the missing clause: the operation-level peer of `carrier`, saying which host FUNCTION realizes one of a carrier's operations. It lands as a flat `anthill.realization.OperationMapping` fact and the evaluator's builtin registry reads those facts instead of a hardcoded spec-op list. `Int64`/`String`/`BigInt` map `compare` + `gt`/`gte`/`lt`/`lte`; `Float` maps the four IEEE comparisons and NO `compare` (it provides `PartialOrd`, not `Ordered`) — so "Float's order is IEEE" is a fact in Float's own binding instead of a `float_pair` branch inside a comparison shared with the total carriers.

**Three parts move together and none works alone**: the mapping (the implementation gets a per-carrier key), the DEFAULT BODIES on `PartialOrd.gt`/`gte`/`lt`/`lte` and `Ordered.max`/`min` (unshadowed at last), and the carriers DECLARING the operations they map — an operation must EXIST for a registration to attach to, body-less, the `LogicalStream.splitFirst` shape. `wi876_operation_mapping_test` drives a structural carrier that writes `compare` alone and gets all nine.

**Two findings the ticket did not predict.**

*"Executable" had two definitions and one of them was a body.* `carrier_override_op` — eval's WI-444 "does the carrier override this defaulted spec op?" — filtered on a runnable BODY, so a member whose implementation is the HOST's read as ABSENT and the spec's default ran INSTEAD of the carrier's own host code. It is not a hypothetical: `gt(nan, 1.5)` fell into `PartialOrd`'s `compare`-based default and died `OperationBodyMissing {Ordered.compare}` (`Float` has no `compare`), and a `String` comparison inside a program's witness ordering fell through into an `AmbiguousSpecOpDispatch` between `String`'s own `compare` and the program's two witnesses — six `wi844_sorted_set_driver_test` arms. Both now share ONE predicate with the load check: `op_is_executable` = body │ builtin │ host mapping. Inverting it re-breaks exactly two of this ticket's tests, which is how it was verified.

*The derivation's `requires` had exactly one place it could live.* `PartialOrd.gt`'s default body reads `Ordered.compare`, which `PartialOrd` does not require (the dependency runs the other way) — a `MissingRequiresForSpecOp` load error. It cannot move to `Ordered`, because `sort_ops` has ONE slot per (carrier, short name) and a carrier providing both specs would take whichever pass 2 reached first — HashMap order, a coin flip. And `PartialOrd` cannot `requires Ordered[T]` at SORT level: `Float` provides one and not the other. What is left is the OP-SCOPED `requires Ordered[T]` (`list.anthill`'s `member` precedent), which says the right thing — this DERIVATION needs a total order — and demands nothing of a carrier that supplies its own comparisons.

**The deliberate behaviour change**: an `Ordered` operation on a carrier that provides no `Ordered` no longer resolves. `Ordered.max(1.5, 2.75)` used to answer `2.75` — through a spec-op builtin that ignored provisions entirely and used `total_cmp`, under which NaN ranks LARGEST, the "same program, opposite answers by backend" that `wi645_float_nan_ieee_test` exists to forbid. The ordering family went first because it had a demonstrated defect; the mechanism is proved on it. The SLD-side registry (`kb.register_builtin_tags`) is still a hardcoded list — it runs BEFORE `load_all`, so there are no facts to read — but its entries are no longer spec-op-keyed: **WI-879**.

### 14.1 Why the refusal is keyed per CALL SITE and not at the declarations

Recorded once here because it is otherwise re-derived at each ticket, and because §11 left a fork open that §13 made reachable.

The question is real: WI-1012's refusal carries the call's span in `dedup_key`, so N call sites give N errors, while `AmbiguousEqDispatch` says it once at the index build. And the pass is BUILDABLE — `EqDispatchIndex` already is exactly it for `eq` (`collect_spec_op_suppliers_by_carrier` plus route 1 per carrier), and generalising it over every body-less spec op is mechanical. "We cannot" is not the answer.

**The `eq` family's load refusal is licensed by something no other spec op has: no call site to blame.** Equality dispatches from unification, so §3.7's rule ("a read that SELECTS goes loud on the second candidate") has nowhere else to fire. Every other spec op has a call, and §3.2 tier 3 fixes BLAME at it.

**And WI-1027's measurement makes the declaration-level form unsound for this family, not merely redundant.** A two-supplier carrier is not by itself an error — six delivered programs have one, resolved by a bracket the call site writes or by a specificity order the goal establishes. A declaration-level check has no call site, therefore no bracket and no goal, therefore cannot apply either tier; it would have to refuse `wi857`'s program at its declarations. That is precisely the symptom §4.1 removed the old load refusal for, and which WI-843's note pins: delete every call and the load still failed.

**A third fact, independent of both:** none of this ticket's three reproducing fixtures forms a coherence GROUP of two at all. The carrier writes no provision in two of them and the rival is a lone witness in the third, so `provider_coherence_groups_with` sees a group of one and the size gate skips it. The tie the typer refuses is mostly invisible to the grouping — so a declaration-level home would not be the grouping's, it would be a new whole-KB pass beside it.

**Hence the fork §11 declined stays declined**, and for a reason it could not have had. §11 recorded the deeper alternative — gate kind 3 on the carrier owning at least one of the spec's ops, splitting cell (1, 0, 1) by construction — and rejected it only because "the rival half would then need a VERDICT of its own, a new load refusal, the one thing 8a scoped itself out of". WI-1012 and WI-1027 have now built that verdict, so the stated blocker is gone; the alternative is still wrong, for two reasons that outlive it. It would site the verdict where tiers 1 and 2 cannot be consulted (above). And the gate is per-SPEC while the tie is per-OP: a two-op spec whose carrier owns op A while a fact binds op B is ONE dictionary, and the alternative makes it a group of two and refuses it. It would trade an undecidable cell for a false positive, not for a decision.

**What the per-call keying costs, and why it is affordable.** N errors for N call sites, with `dedup_key` collapsing repeats of one (op, carrier, span). Measured inert on the corpus (0 tied pairs), and each error names the call whose text the author has to change — which is what tier 3 asks for. If the count ever becomes a nuisance, the fix is a declaration-level *warning* keyed per (spec op, carrier) beside the call-site error, not instead of it.

## 15. WI-1032 — two provisions that say the same thing are one candidate (DELIVERED 2026-08-06)

§14's recorded bad rendering, closed — and driving it found the worse half of the same defect first.

**What §14 recorded.** With the carrier ALSO self-providing the spec, a route-1-vs-route-2 supplier conflict reached `DispatchOutcome::Ambiguous` rather than the supplier guard, and printed `2 instances provide Desc (Leaf, Leaf)` — one carrier named twice — with `TieRepair::ValueDirected`, whose repair ("pin the carrier through the call's receiver") cannot apply because the carrier is already pinned. §13 had given the supplier tie its own variant precisely to avoid that rendering; here it came back through the other arm.

**The defect underneath it, which the recorded note did not see.** Drop the fact's op binding — `sort Leaf { provides Desc[T = Leaf]; operation describe … }` beside a bare namespace-level `fact Desc[T = Leaf]` — and there is no conflict at all: one dictionary written in two places. MEASURED: the CALL was refused, with the same `(Leaf, Leaf)` message. A program with a single implementation, rejected by a diagnostic naming one carrier twice and advising a repair that changes nothing.

**Which coherence cell that is — the first cut of this section said (1, 0, 1) and review MEASURED otherwise.** `Provider::Fact` is recorded only when the provision BINDS an op (`binding_op_symbol` demands a `SymbolKind::Operation` value) and a bare `fact Desc[T = Leaf]` binds a SORT, so both provisions classify as `SelfProvider(Leaf)`, `record` collapses them, and the group holds ONE — cell (0, 0, 1), which the size gate skips and `fact_beside_self_provider_is_one_carrier` never sees. So §11's licence was NOT falsified by this shape; the claim that it was is withdrawn. The shape that IS in (1, 0, 1) is the op-binding pair, which genuinely has a conflict — exactly what the licence covers, and what it correctly routes to a per-op reader.

**One missing dedup is the whole cause, and the rule was already written down one layer over.** `Provider::SelfProvider`'s doc says it: *"Two self-provisions of one spec by one carrier are therefore ONE candidate, which is right: they name one member set, and a disagreement between their BINDINGS is `ConflictingProvisionBindings`'s (WI-842), not a second dictionary."* The LOAD grouping applied it; `collect_provides_candidates` built two structurally identical `Candidate`s and `pick_most_specific` refused to choose between them.

**Dedup is not first-match, and the distinction is structural rather than argued.** A `Candidate` is `(impl_sort, resolved_head_bindings, impl_subst, head_specificity)`, and every downstream product — the resolved tree node, the subgoals `requires_chain(impl_sort)` instantiates through `impl_subst` — is a function of exactly those fields. Two EQUAL candidates therefore resolve identically, so picking either is picking the same thing. Candidates differing in ANY field are all kept, and `pick_most_specific` still refuses among them.

**And the rendering is fixed by ROUTING, not rewording.** The op-binding leg is why: the candidate loop `continue`s on any binding that is not a spec TYPE param, so a `fact Desc[T = Leaf, describe = otherDescribe]` differs from a bare `provides Desc[T = Leaf]` in nothing `Candidate` records. The dedup collapses that pair too — correctly, because *as provisions* they agree — and the genuine conflict then reaches the reader that can see it: §14's supplier guard, which names both texts by supply route and offers `KeepOne`. The `Ambiguous` exclusion §14 argued for is unchanged and still driven: a WITNESS rival is a distinct `impl_sort`, does not dedup, and stays a provider tie.

**The collector's dedup is NOT the whole fix**, and the first cut of this section said it was — "no remaining driver, so a dedup in `render_instance_tie` would be untested code". **Review built the driver.** The shape tried (one provision binding a second type param, the other omitting it) does not tie, because the ground binding raises `head_specificity` and tier 2 picks it. But two provisions binding DIFFERENT extra params — `provides Desc[T = Leaf, A = Int64]` beside `fact Desc[T = Leaf, B = Int64]` — both score +1 (the goal leaves `A` and `B` unresolved and `dispatch_values_match` accepts a var against a concrete value), tie at equal specificity, and differ in `resolved_head_bindings`, so the collector cannot collapse them. Measured with the collector dedup already in place: the defect verbatim.

So `render_instance_tie` now dedups the rendered names BY CANONICAL PROVIDER — a rendering rule that cannot hide a rival, since two distinct providers have distinct canonical symbols — and when that leaves one name the repair is a new `TieRepair::OneProviderTwoProvisions`. Not `KeepOne` either: the provisions may AGREE (one binding `A`, another `B`, which `provider_spec_view_bindings` merges into one view), so what the author has to do is write them as ONE provision.

**The dedup has a second consumer, and the soundness argument above does not cover it.** That argument is about the CHOSEN candidate; `check_selection_bindings` reads the SET SIZE, gating `UnthreadableSelection` on `candidates.len() > 1`. The flip is always 2→1 with both entries equal, so it only removes a spurious refusal — one that also rendered the carrier twice in its own `candidates` field — and its doc already argues the sole-provider case is exact rather than lenient. That is also why the dedup belongs in the collector rather than at the tie.

**Blast radius, and it is wider than the ticket first claimed.** Corpus-inert (full workspace suite green), but two shapes outside the original list changed behaviour, both found by review MEASURING the controls rather than believing them. Byte-identical facts hash-cons to ONE fact only WITHIN a namespace; the same `fact Desc[T = Leaf]` asserted from a second namespace is a distinct fact, so the retroactive-instance shape WI-431 exists to support — a downstream file asserting an instance for a sort it did not declare — was refused at the call and now dispatches. And the same op bound twice in two syntaxes was refused and now loads.

**Back-out, measured, two independent changes with two independent controls.** Reverting the collector dedup fails three tests; reverting only the renderer's name dedup fails one. That last test is also the control for "dedup is not first-match", which review found nothing else discriminated: replace the collector's field-wise equality with an `impl_sort`-only compare and every other row still passes, because their candidate pairs share a carrier whose `sort_ops_lookup` answers the same op either way.

**One consistency gap, recorded not closed.** The collector compares the carrier canonically (as `push_supplier_deduped` does, and for its stated reason) but the binding KEYS raw, where `check_provision_binding_agreement` and `provider_spec_view_bindings` compare by param SHORT NAME "because a param resolved in two import scopes can carry two Symbols for one spec parameter". The failure direction is safe — the dedup silently does not fire, leaving today's refusal — and no driver exists, so it is stated rather than strengthened.

## 16. WI-869 — a condition belongs to its provision (DELIVERED 2026-08-06)

Delivers §3.8's per-clause form and §4's second production: `provides X[…] :- goals`.

**The driver was not the over-claim, it was a REGRESSION.** Phase 7 recorded the shared chain as a claim that is too strong (`provides Eq[Pair]` rides a `PartialEq` chain). WI-877 then measured the other direction, which is worse: a sort's chain is threaded WHOLESALE at every dispatch through the carrier, so adding `requires Ordered[A], requires Ordered[B]` to `Pair` — the only spelling the implementation accepted — turned `PartialEq.eq(pair(fst: 1.5, snd: 1), …)` into a LOAD ERROR. An ORDERING requirement broke EQUALITY, because `Float` provides `PartialOrd` and not `Ordered`. The other two spellings are refused by the implementation (op-scoped on an OVERRIDE strengthens the precondition; no requirement at all fails the abstract-coverage check), so there was no way to order a `Pair` at all without giving up its equality.

**The design decision, and it is the one worth stating**: the SLOT SET is per SORT, the STRICTNESS is per PROVISION. A per-provision slot set was the obvious reading of "a second contributor to the provider half", and it does not work: the frame layout is per-sort everywhere it is read (`synth_req_names`, `DictLayout::slots_for`, eval's frame push), so a body owned by the carrier would see a different frame depending on which of its sort's provisions dispatched to it. Instead `provider_dict_chain(carrier)` is the `requires` chain followed by every provision's conditions, deduplicated — and a slot contributed by a SIBLING provision is placed as `Unavailable` at a dispatch that did not earn it. `Unavailable` is refused at any use (WI-857), so a body that names evidence its provision did not declare is loud rather than silently answered — driven by `reading_a_sibling_provisions_evidence_is_loud`.

**One predicate had to move with it, and its old spelling is why the first cut loaded clean and died at eval**: "does a call into this sort need a dictionary threaded" was `!requires_chain(s).is_empty()`. `Pair` now declares NO sort-level `requires` at all, so that answered "no" while its bodies read the slots its provisions put there — an EMPTY frame under an op that names `__req_ordered`. `sort_reads_requirement_slots` is the one owner for all three sites.

**Zero cost when nothing is conditioned**: `provider_dict_chain` hands back the *same* `Rc` as `direct_requires_chain_rc` for a carrier with no conditional provision, so every pre-WI-869 program shares its chain rather than merely matching it.

**The refusal now names the condition.** `DispatchOutcome::NoMatch` carries the goal the search failed on, verbatim from the resolution that observed it (WI-828's rule, one level over), so `Ordered.compare` on a `Pair[Float, Int64]` says `unresolved: anthill.prelude.Ordered[T = anthill.prelude.Float]` instead of only that no impl matched.

**What it does NOT close, re-attributed by measurement.** `Set[T = Pair[Float, Int64]]` still loads. Not an over-claim any more — the provision is conditioned and `Eq[Pair[Float, Int64]]` genuinely fails — but there is NO POSITIVE use-site check for `requires Eq`: the only refusal at a written type site is the `NonEq` one, and a key providing *nothing at all* is accepted too (measured; pinned as the second control in `wi858_pair_orderings_test`). The remaining halves are the composite `NonEq` derivation `eq.anthill` calls a follow-up, and a positive use-site discharge.

**THE REVIEW FOUND FOUR MISSED FRAME-PRODUCERS, and that is the finding worth keeping.** The rule "producer and namer must read ONE chain" was carried entirely in prose, and `synth_req_names` moving to the dictionary chain silently desynchronized every site that kept reading the declared one: `resolve_bridge_requirements` (the value-directed bridge — this is the one that made `PartialOrd.gt` on a pair die where a direct `Ordered.compare` worked, since the two routes fill the frame differently), `attach_eta_dispatch_dict`, `req_insertion::chain_for` (the SECOND producer of the positional `caller_requires` list whose first producer had moved), and `call_with_requirements`' WI-857 layout check — the last one reintroducing, three lines below it, exactly the divergence its own comment warns against. All four are fixed; three were invisible to a green suite. **The deeper fix, not taken here and worth its own increment**: both chains are the same bare `Rc<Vec<RequiresEntry>>`, so nothing but a comment prevents picking the wrong one. A `DictChain` newtype accepted only by the layout readers would have made all four compile errors — the repo's own "make illegal state unrepresentable over check logic".

**Two residues recorded rather than hidden.** (1) The conditions are a loader-written KB record, not a fact, so `check_provider_requires` and the reflect `provides/2` rule still read `Pair`'s provisions as UNCONDITIONAL — the conditions bind on the dictionary path alone. Making them fact-observable (a `ProvidesConditionInfo(sort_ref, provided, condition)` entity, leaving `SortProvidesInfo` untouched) is what a positive use-site discharge and a condition-aware coherence check would need. The first cut justified the side table by claiming a widened `SortProvidesInfo` would break `reflect/typing.anthill`'s `provides/2` rule; that was FALSE — the loader fills unnamed fields with fresh vars (WI-716), and the rule eleven lines below names 2 of `SortInfo`'s 7 fields and matches. The comment now says what actually holds. (2) `scaland` links a condition's spec scope exactly as it links a `requires` — the first cut dropped conditions at the load phase on the stated grounds that "scaland has no dictionary layer, so this changes nothing it computes", which was also false: a `requires` in scaland *is* a parent-scope link, and moving `pair.anthill`'s two `requires PartialEq` clauses into conditions had silently removed two parent links from its `Pair` scope.

**And it delivered WI-877 with it**, because the acceptance could not be stated otherwise: `pair.anthill` ships four conditioned provisions and ONE operation (`compare`), the whole inherited comparison surface coming from WI-876's default bodies. The cost is that `Pair` is now a CONCRETE `Ordered` provider, so a program declaring a rival makes a bracket-less pair compare a three-way tie naming the prelude's own, which `[Ordered = Pair]` cannot select (§3.5 check 3). Taken knowingly — WI-877's feedback measured it and chose the lexicographic order as `Pair`'s identity — and asserted in `wi858_pair_orderings_test` so the choice cannot lapse silently.
