## 1. Substrate (pre-existing, unchanged)

- **Declare**: witness sorts (WI-450, named by their sort symbol) and instance facts (WI-431, unnamed — the §3.1 nameability gate's reason). `SortProvidesInfo(sort_ref, spec)` records every provision.
- **Select**: the 042 bracket channel — `parse/convert.rs` → `build_call_type_args` (`load.rs`) → `seed_op_type_args` (`typing.rs`). Phase 0 (WI-839) closed every silent drop site: an unmatched key at a classified call is loud even when the callee declares no type params; a rule-/term-body bracket is a loud not-supported-here refusal, keyed on the `ParseAux type_args` channel (a rule-body *type application* is a different producer and stays checked).
- **Thread**: `Value::Requirement(handle)` dictionaries, `construct_requirement`, per-call frames rebuilt from `sub_requires` (`design/operation-call-model.md`, `design/requirement-dictionaries.md`). Selection changes only where `ResolvedTree::leaf { impl }`'s `impl` comes from.

## 2. Classifier work (proposal §3.3–§3.4) — delivered

- **Key resolution rule 1** spans the op's and the enclosing sort's type params — the sort-level seeding leg was a missing feature, built as WI-841 (one more WI-708-style key); the two scopes never both answer because the collision is refused at the declaration (phase 1's guard). Rule 1 matches by symbol identity on bare labels; rule 2 (spec short name) is a lookup gated by the same-spec context — WI-672's discipline, `same_label` family 2, never a short-name identity comparison.
- **A named slot's parameter is read back out of σ** once argument unification completes (`selections_from_slot_bindings` → `InstanceSelection`, WI-844): the bracket, the argument's type, and an eta'd op reference's expected arrow (`attach_eta_dispatch_dict`) are **three producers of one channel**. They are compared **unconditionally** — ranking them re-opens first-match across two same-spec slots (measured: a bracket `[A = ByLength]` beside an argument-typed `B = Alphabetical` deleted the conflict refusal under a ranked cut). `push_selection` owns the rule; the conflict diagnostic names both witnesses without attributing a producer, because a mixed pair is reachable. An **abstract** binding derives nothing (`is_type_param_value`) — that is what keeps `report[T, O]` a forward.
- **Merge safety** is argument-position type-variable agreement — WI-836, delivered; without it `union` across two orderings loaded clean. Omission-means-any is `check_sort_type_args` requiring no declared param be bound.
- Guards: the §3.3 shadowing refusals at the declaration; qualified keys refused (`unknown type-param`, no resolution rung by design — a resolved key would make selection depend on caller imports, while `build_concrete_dispatch_dict` takes no scope at all).

## 3. Ladder mechanics (proposal §3.2) — tiers 1–3 and 2a delivered

- Tier 3 is `DispatchOutcome::Ambiguous` (carrying the tied providers) → `TypeError::DispatchAmbiguous` → `LoadError::UnselectedInstance`, rendered with a typed `TieRepair` decided at the render boundary. `LoadError::AmbiguousWitness` is **deleted**, not gated. `AmbiguousInstanceFact` and `MixedProviderKinds` (WI-838's one grouping per `(spec, dispatch carrier)` over all provider kinds) remain — they are the §3.1 nameability gate; the group loop gates on `Provider::is_nameable`.
- **Boundaries, each driven and pinned** (WI-843): a tie whose candidates are all concrete has no bracket (§3.5 check 3 refuses explicit witnesses there — the value decides); a sub-goal's tie propagates verbatim and must be stamped at its own level, not the outer goal's (`resolve_at_goal` mis-attribution, fixed); a **specificity-ordered pair never reaches tier 3** — `pick_most_specific` answers silently. That last is a recorded *widening* (tier 2 reaching cases the old load refusal made unreachable); WI-841's committed acceptance depends on it; making it loud would be a new coherence rule needing its own measurement.
- **Rung 2a — ✅ DELIVERED as WI-861; see §26.** At the classifier's tie, consult `default_provider` (a materialized index over the §6 facts — the `EqDispatchIndex` pattern; the relations are the authority, the hot path reads the index). Two populations, one predicate (`defaults::default_among`): PROVISIONS at `resolve_inner`'s `pick_most_specific` tie, and SUPPLIERS at the three faces of `AmbiguousSpecOpDispatch`. Withheld at a NAMED requirement slot (proposal §3.4), which is the one thing the flip inventory did not anticipate and the one place a default would have turned a loud refusal into a silent wrong answer. **WI-1094 then gave the named slot its own mechanism** — inference INTO THE TYPE, at the call site, for a binder still FLEX — so the gate now covers only the sub-goal recursion; see §27. Prerequisite: the coherence grouping had to gain the **self-provider candidate kind** — measured absent at WI-855 (*"a self-provider is a candidate of neither kind"* — `provision_binds_any_op` and `witness_dispatch_carrier` both missed it), which is also why `one_default` could not be checked. **Delivered as WI-859**; see §11.

## 4. Resolve hook (proposal §3.3's pinning) — delivered, one correction

`resolve(goal, scope)` step 0: a pinned goal returns the pinned provider after validation — as a `leaf` **only when both halves of its dictionary are empty** (§7's layout: the spec's own `requires` chain, then the provider's); anything else yields the conditional node with those sub-goals resolved. (Corrected 2026-07-30: the leaf-always reading built an arity-0 dictionary that dies at eval. Settled by WI-857 — and note the correction as first written was still too narrow, blaming only the *witness's* chain: the carrier-keyed case has no witness chain to bear and died anyway, because the missing half was the SPEC's.) Sub-resolutions search, except that a sub-goal the SELECTED provider itself provides resolves witness-locally (§7's locality rule); a bracket key cannot reach them (pinning changes which subgoals exist).

**Slot routes**: a `requires` slot is served by the enclosing sort's dictionary build, the spec-op dispatch, or an **op-scoped** clause — and all three now thread a selection (**WI-1091**, §28). The history is worth keeping because the refusal it retired was correct while it stood: the op-scoped route was served by value-directed dispatch, which never sees a selection, so WI-841 refused one there whenever ≥2 providers answered, accepting only the sole-provider case. WI-822 leg 1 gave the op-scoped chain real frame slots (`op_dict_entries`: the sort's slots then the operation's) and a call site that fills them honouring `selected`, and the refusal STAYED, because what leg 1 did not change is which channel the callee's BODY reads — it deferred to an op slot only where value-direction could not answer at all. WI-1091 moved that placement, having first supplied the four routes leg 1's measurement had shown could not fill a slot; the body now reads an op-scoped slot wherever it reads its sort's. An op-scoped clause's spec is a bare application, so `goal_from_requires_entry` yields a bindings-free goal that every provider matches — a check routed through it passes vacuously; witness validation therefore runs once at the call site. A selection is keyed by the **spec** (a `SortGoal`'s coordinate): two anonymous same-spec slots are indistinguishable to a pin — two keys naming different witnesses for one spec are refused at the site.

## 6. Defaults implementation (proposal §3.6) — DELIVERED as WI-860; see §19

Reflect-layer file (a sibling section of `reflect/typing.anthill`, or `reflect/instance.anthill`): `entity DefaultProvider(spec, provider)`, `entity Coherent(spec)` (deferred data rows re-homing the `Eq` family list — ownership only, the check exists), `self_provides`, `default_provider` (declared ∪ inferred — consumers read the derived relation only), `constraint one_default`, `constraint coherent_one_target`. Load checks materialize into Rust (the `EqDispatchIndex` pattern); `DefaultProvider`'s provider field is a sort reference in a fact argument — proven surface (`fact Covariant(sort: List, param: T)`, proposal 035). Validation reuses §3.5 check 1 as a load check. No-displacement needs no code: the inferred row + `one_default` refuse the displacing fact. **Conditional defaults need no code either** — the declared-row rule joins through `provides`, which for a conditional provision holds only where its chain discharges (proposal §3.6/§5's `ListOrd` row) — but `one_default` must compare rows at **unifiable** carriers, so a ground default beside a parametric one for one family is refused: layering defaults by specificity would be a boundary-3-style widening — pin the refusal in phase 8's acceptance, don't inherit the question. **The inline sugar** (`default provides`, proposal §4) is loader work: one optional leading modifier token (the `internal` pattern; a trailing `[default]` was rejected — a bracket list after a bracketed type invites a GLR tie) desugaring in the converter to a `DefaultProvider` row with `provider =` the enclosing sort. The same family gives `coherent sort X … end` → a `Coherent(spec: X)` row (the `enum sort` precedent; arrives with the deferred re-homing), and `coherent` on a *provision* is refused — a provision must not foreclose coexistence for a spec/carrier it does not own. **`provides`-vs-`fact` synonymy is measured** (probe q5): a witness spelled with `provides Spec[T = Foreign]` loads and runs identically to the `fact` spelling — one construct, two conventional spellings — which grounds proposal §4's retirement of the `fact` spelling for provisions. Migration scope for that retirement: the stdlib bindings' fact rows (`anthill-stl/anthill/*.anthill`), the wi84x fixtures, examples, and the binding-block idiom (proposal 038's `provides X language rust` blocks); the deprecation warning sits at the loader's provision-lowering site, which already distinguishes a provision fact from a plain one. Namespace-level op-binding instance facts are out of scope (outside sorts; already quarantined by the nameability gate). Deferred: `within:` scoped rows (explicit field, NOT placement — a fact inside a sort already means "this sort provides"; scoped rows are classification-time only, so a sort with a scoped row and a rule body dispatching the same goal is refused); per-carrier `NoDefault`.

## 7. WI-857 — the gate (DELIVERED 2026-07-30), and the probe matrix

**Settlement.** One layout, one owner (`kb::typing::dict_layout`), stated in full in [`operation-call-model.md`](./operation-call-model.md) §"Dispatch rule": a dictionary for spec `S` supplied by provider `P` bundles `S`'s own direct `requires` chain (the **prefix** — what `requirement_at_sort`'s projection path indexes and what a body owned by `S` reads when dispatch lands on the spec's own op) then `P`'s (the **suffix** — what `P`'s member body reads); `P == S` contributes one list, which is also the parent-bundle dictionary's shape. `expand_dispatching_dict` hands the frame exactly the half its target's parent owns and is loud when the target's parent is a third sort with a chain of its own. Three further decisions, each forced by measurement:

- **An unresolved spec-half slot is RECORDED, not refused** (`ResolvedRequiresNode::Unavailable` → an empty bundle over a marker functor). Demanding it resolve broke **33 tests**: a spec-level `requires` is routinely satisfied only loosely, since `check_provider_requires` falls back to a base-level existence check wherever σ leaves a binding abstract — `FiniteCollection requires Iterable[C = C]` holds for a `List` only through `List provides Stream provides Iterable`, which no `Iterable[C = List[…]]` provision matches. Dispatching through the marker is refused (one owner: `dispatch_via_sort_ops_table`), so a slot nobody reads costs nothing and a slot somebody reads names the requirement that has no provider.
- **The LOCALITY rule** is in (see §4), as the review required.
- **Every producer must build a layout-valid dictionary.** The host-entry stand-ins (`seed_entry_requirements`, `call_with_requirements`' `__req_self`) were `functor` with NO sub-slots, which the layout reads as claiming that functor's whole chain and bundling none; they now carry marker sub-slots. Found by driving, not by inspection — wi818's value-directed rescue died on the arity check.

**The split it settled** was visible in the design doc as well as the code: the dictionary **producer** walked the *provider's* `requires` chain while `expand_dispatching_dict` named the frame from whatever the *dispatched target's parent* declared and `requirement_at_sort` indexed the *spec's* — and `operation-call-model.md`'s frame-push pseudo-code said "one per impl's `requires`" two paragraphs above a worked example that indexes the spec's. The three agreed only when the provider was a chain-free witness. Probes (scratchpad `q4a`–`q4g`, `anthill load`/`run` at HEAD; reproducers spelled in WI-857's feedback entry, all now pinned in `wi857_dictionary_layout_test.rs`):

| shape | spec's own chain | load | eval |
|---|---|---|---|
| parametric witness, own chain 2, spec chain **empty** (local `Sized`) | 0 | clean | **threads** — 3+6=9 through the conditional chain |
| same form over `Ord`, nothing provides `Eq`/`PartialOrd[Duo]` | 2 | **refused** — provider must provide or the goal must resolve at the bindings | — |
| carrier provides `Eq` componentwise + witness bundles own `PartialOrd`+`Ord`, parametric | 2 | clean — `Eq` leg discharged from the carrier, `PartialOrd` from the witness | **dies both routes** (σ-pinned and searched): `dispatching dict … arity 0 but its requires chain has 2 entries`; count stays 2 with own chain cut to 1 ⇒ frame named from the **spec's** chain |
| ground, chain-free, bundled, slot-free body | 2 | clean | **runs** (−1) |

Every row above now RUNS (`-1`, `9`, `-1`, `-1`; the refused row still refuses, correctly — nothing provides its `Eq`/`PartialOrd[Duo]`). Rows 1 and 4 were the accidental agreements and are kept as the controls: a mis-sliced half would surface only as a wrong value there, since their providers declare no `requires`.

**Consequences, as of delivery**: WI-857 no longer gates §3.8's library goal or rung 2a — phases 7 and 8c are unblocked. `check_provider_requires`'s discharge rule is unchanged and now doubly load-bearing, because the spec half is built from the same walk it checks (`provider_requires_subgoals` has one owner): provider-provides OR resolves-at-the-bindings (binding-precise and transitive when σ grounds; base-level fallback when abstract). The provider's own `requires` chain still does **not** discharge a spec-level requirement — the conditional spelling stays refused, exactly as the brainstorm drove.

**Conditional provisions (proposal §3.8)**: the provider-chain spelling works for the provision's *own* evidence — q4a threads it — while the chain does **not** discharge the *spec's* requirements (`check_provider_requires` never consults it; the brainstorm's obstacle-B drive). The per-clause `provides X :- goals` surface would need grammar plus per-provision chains; with the layout now settled it has a place to land — a per-provision chain is a second contributor to the **provider half**, not a new half. Phase 7 gave it a shipped driver and a ticket: **WI-869**, because a sort's one chain must serve `PartialEq[Pair]` and `Eq[Pair]` at two different strengths and cannot. ✅ **DELIVERED — see §16**, where the driver turned out to be a regression rather than an over-claim, and where the design landed on one slot set per sort with per-provision *strictness*.

**The composition leg, DRIVEN at phase 7 and found UNWIRED (WI-870).** Binding a witness's own *named* slot inside a bracket value (`O = ListOrd[OE = LexFst]`, proposal §3.3/§5) was the one composition never measured — the q4 series drove only the inferred form. Measured on the shipped `PairByFst`: the value's bracket list **is** validated against the witness (an unknown slot name is refused, naming `A, B, OA, OB`) and then **discarded** — `[Ord = PairByFst[OA = PairBySnd]]`, whose value provides no `Ord[Int64]` at all, loads clean and computes the unbound answer. `selection_witness_sym` reads the base functor (its own comment already says "a witness may carry type arguments"); nothing consumes the arguments, and a sub-goal resolves with `selected: &[]` by design. A **silent drop**, and a defect rather than a gap because `TieRepair::SubGoal` prints this exact spelling as the repair — an author who follows the diagnostic gets the identical error back. ✅ **DELIVERED — see §18.**

Probe harness note: `anthill query -p` diverges from `anthill load` (sort-level member imports refused; panics on `realization.CarrierBinding` with the bindings dir) — drive reproducers via `anthill run` + a `Main` sort.

## 9. Phase 7 — the library, and the line it did not cross (DELIVERED 2026-07-30)

`stdlib/anthill/prelude/pair.anthill` gives `Pair` componentwise `PartialEq`/`Eq`. It does **not** give it an ordering, and that is the phase's substantive finding. *(Superseded — WI-876 removed the boilerplate cost and WI-869 removed the shared-chain blocker; `Pair` now ships four conditioned provisions and the canonical lexicographic order. §16.)*

**The instruction was "two orderings of one carrier in the shipped prelude". It was a PROXY for "exercise the mechanism outside the suite", and both readings turned out wrong for this carrier.** Shipping two co-equal witnesses hands every downstream bracket-less pair compare a tier-3 error the consumer never opted into — obstacle A, which the brainstorm's Options table judged absent for `Pair` by evaluating `Pair` as it *was* (self-providing nothing) rather than as the change would leave it. Shipping ONE canonical ordering avoids that (a pair *has* a canonical order — every neighbouring language gives `(a, b)` lexicographic `fst`-then-`snd`) and was implemented and driven end to end: `Ord.compare` answering `-1`/`1`-on-tie/`0` bracket-free, a `SortedSet` of pairs sorting with no bracket. It was then withdrawn, because of what it cost.

**What it cost: seven operations in `pair.anthill` where one would do.** `compare` carries the logic; `max`/`min`/`gt`/`gte`/`lt`/`lte` are each one line restating "call `compare`, check the sign". Two checks force them, for different reasons — the LOAD check demands `max`/`min` (not resolver builtins, so `op_backed` finds no backing), and EVAL demands the rest (the spec-op builtins are scalar-only). Seven-or-nothing: drop any and either the load fails or `gt(pair, pair)` dies at run time on a program that loaded clean.

**The root cause is a grammar gap, and it is WI-876 — since DELIVERED 2026-07-30; see §10.** `Ord.compare` / `PartialOrd.gt` & co. were registered on the SPEC op, so one implementation served every carrier that never wrote its own. That was not a design choice: a `provides X language rust` block admitted `artifact`, `carrier`, `namespace_map`, facts and rules — and **nothing that maps an operation to a host function** — so `Int64`'s host `compare` had nowhere to be keyed. `Int64` providing `Ord` with no anthill-level `compare` is itself legitimate (`check_provider_operations` deliberately skips a host carrier); the defect was only *where* the implementation is keyed. The fix was exactly the one named here: add the mapping clause, key the scalar implementations per carrier, delete the spec-op registrations, and let `ordered.anthill`'s derivation — stated only as laws, and a rule is not backing (WI-818) — carry real default bodies, now unshadowed. A structural carrier now needs **only `compare`**.

**`PartialEq` is the control that shows this is a defect and not a necessity**: `eq` needs no per-carrier member on `Pair`, because `builtin_eq` → `semantic_equal` already dispatches to a carrier's own `eq`. One of the two builtin families learned to dispatch; the other did not.

**So the phase ships the equality and leaves the ordering to WI-876**, and `wi858_pair_orderings_test` drives 058's coexistence over `Pair` with **two PROGRAM-declared orderings** — which is a cleaner driver than WI-844's `String` anyway: `String` has a host `Ord` provider, so its ties are three-way and a bracket-less compare there can never succeed; `Pair` provides no ordering, so two witnesses tie exactly two ways and every repair is writable.

**Other measured results, unchanged by the withdrawal**: the equality chain is `PartialEq`, not `Eq` — an `Eq` chain makes `Pair[A = Float, B = Int64]` a LOAD ERROR (WI-835's `NonEq` check), i.e. `Pair` stops being a general PRODUCT; and a sort's `requires` chain is SHARED by every provision it makes, so `provides Eq[Pair]` over-claims (`Set[T = Pair[Float, Int64]]` loads while `Set[T = Float]` is refused) — **WI-869**, delivered; §16 re-attributes the surviving half of that measurement to the ABSENCE of a positive use-site check, not to the provision. Three further spin-offs: **WI-870** (a bracket-value slot binding is validated then dropped), **WI-871** (a componentwise provider's second requirement slot is read from the first), **WI-872** (a provision's carrier is matched by SHORT NAME at dispatch), **WI-873** (`dispatch_origin` keeps one rewrite per spec op) — DELIVERED 2026-08-19: the rewrite table was keyed by a term `req_insertion` synthesized as `apply(fn = Ref(functor), args = nil())`, which hash-consing collapsed onto one key per callee, so the recorders' idempotence guard dropped every call site after the first (47 classified sites, 16 entries). It is keyed by `CallSite` now.

**The lesson**: a library change is where a design's conditions get their first real carrier — and where a phase instruction's letter can come apart from its purpose. `Pair` was the tree's first structural `Ord` provider, so it was the first thing to test whether "provides `Ord`" means anything without seven lines of boilerplate. It did not. Declining to ship the boilerplate is what turned that into a ticket instead of a precedent.

## 10. WI-876 — the host mapping (DELIVERED 2026-07-30)

`operation_map { compare: "ordered_compare" }` is the missing clause: the operation-level peer of `carrier`, saying which host FUNCTION realizes one of a carrier's operations. It lands as a flat `anthill.realization.OperationMapping` fact and the evaluator's builtin registry reads those facts instead of a hardcoded spec-op list. `Int64`/`String`/`BigInt` map `compare` + `gt`/`gte`/`lt`/`lte`; `Float` maps the four IEEE comparisons and NO `compare` (it provides `PartialOrd`, not `Ord`) — so "Float's order is IEEE" is a fact in Float's own binding instead of a `float_pair` branch inside a comparison shared with the total carriers.

**Three parts move together and none works alone**: the mapping (the implementation gets a per-carrier key), the DEFAULT BODIES on `PartialOrd.gt`/`gte`/`lt`/`lte` and `Ord.max`/`min` (unshadowed at last), and the carriers DECLARING the operations they map — an operation must EXIST for a registration to attach to, body-less, the `LogicalStream.splitFirst` shape. `wi876_operation_mapping_test` drives a structural carrier that writes `compare` alone and gets all nine.

**Two findings the ticket did not predict.**

*"Executable" had two definitions and one of them was a body.* `carrier_override_op` — eval's WI-444 "does the carrier override this defaulted spec op?" — filtered on a runnable BODY, so a member whose implementation is the HOST's read as ABSENT and the spec's default ran INSTEAD of the carrier's own host code. **The deliberate behaviour change**: an `Ord` operation on a carrier that provides no `Ord` no longer resolves. `Ord.max(1.5, 2.75)` used to answer `2.75` — through a spec-op builtin that ignored provisions entirely and used `total_cmp`, under which NaN ranks LARGEST, the "same program, opposite answers by backend" that `wi645_float_nan_ieee_test` exists to forbid. **Not migrated**: every other spec-op-keyed registration (`Numeric.add`, `String.concat`, `Bool.not`, …) has the same latent hole and the same fix available. The ordering family went first because it had a demonstrated defect; the mechanism is proved on it. The SLD-side registry (`kb.register_builtin_tags`) is still a hardcoded list — it runs BEFORE `load_all`, so there are no facts to read — but its entries are no longer spec-op-keyed: **WI-879**.

## 12. WI-1010 — a default is not a supplier (DELIVERED 2026-08-05)

## 16. WI-869 — a condition belongs to its provision (DELIVERED 2026-08-06)

Delivers §3.8's per-clause form and §4's second production: `provides X[…] :- goals`.

**The driver was not the over-claim, it was a REGRESSION.** Phase 7 recorded the shared chain as a claim that is too strong (`provides Eq[Pair]` rides a `PartialEq` chain). WI-877 then measured the other direction, which is worse: a sort's chain is threaded WHOLESALE at every dispatch through the carrier, so adding `requires Ord[A], requires Ord[B]` to `Pair` — the only spelling the implementation accepted — turned `PartialEq.eq(pair(fst: 1.5, snd: 1), …)` into a LOAD ERROR. An ORDERING requirement broke EQUALITY, because `Float` provides `PartialOrd` and not `Ord`. The other two spellings are refused by the implementation (op-scoped on an OVERRIDE strengthens the precondition; no requirement at all fails the abstract-coverage check), so there was no way to order a `Pair` at all without giving up its equality.

**The design decision, and it is the one worth stating**: the SLOT SET is per SORT, the STRICTNESS is per PROVISION. A per-provision slot set was the obvious reading of "a second contributor to the provider half", and it does not work: the frame layout is per-sort everywhere it is read (`synth_req_names`, `DictLayout::slots_for`, eval's frame push), so a body owned by the carrier would see a different frame depending on which of its sort's provisions dispatched to it. Instead `provider_dict_chain(carrier)` is the `requires` chain followed by every provision's conditions, deduplicated — and a slot contributed by a SIBLING provision is placed as `Unavailable` at a dispatch that did not earn it. `Unavailable` is refused at any use (WI-857), so a body that names evidence its provision did not declare is loud rather than silently answered — driven by `reading_a_sibling_provisions_evidence_is_loud`.

**One predicate had to move with it, and its old spelling is why the first cut loaded clean and died at eval**: "does a call into this sort need a dictionary threaded" was `!requires_chain(s).is_empty()`. `Pair` now declares NO sort-level `requires` at all, so that answered "no" while its bodies read the slots its provisions put there — an EMPTY frame under an op that names `__req_ord`. `sort_reads_requirement_slots` is the one owner for all three sites.

**Zero cost when nothing is conditioned**: `provider_dict_chain` hands back the *same* `Rc` as `direct_requires_chain_rc` for a carrier with no conditional provision, so every pre-WI-869 program shares its chain rather than merely matching it.

**The refusal now names the condition.** `DispatchOutcome::NoMatch` carries the goal the search failed on, verbatim from the resolution that observed it (WI-828's rule, one level over), so `Ord.compare` on a `Pair[Float, Int64]` says `unresolved: anthill.prelude.Ord[T = anthill.prelude.Float]` instead of only that no impl matched.

**What it does NOT close, re-attributed by measurement.** `Set[T = Pair[Float, Int64]]` still loads. Not an over-claim any more — the provision is conditioned and `Eq[Pair[Float, Int64]]` genuinely fails — but there is NO POSITIVE use-site check for `requires Eq`: the only refusal at a written type site is the `NonEq` one, and a key providing *nothing at all* is accepted too (measured; pinned as the second control in `wi858_pair_orderings_test`). The remaining halves are the composite `NonEq` derivation `eq.anthill` calls a follow-up, and a positive use-site discharge.

**THE REVIEW FOUND FOUR MISSED FRAME-PRODUCERS, and that is the finding worth keeping.** The rule "producer and namer must read ONE chain" was carried entirely in prose, and `synth_req_names` moving to the dictionary chain silently desynchronized every site that kept reading the declared one: `resolve_bridge_requirements` (the value-directed bridge — this is the one that made `PartialOrd.gt` on a pair die where a direct `Ord.compare` worked, since the two routes fill the frame differently), `attach_eta_dispatch_dict`, `req_insertion::chain_for` (the SECOND producer of the positional `caller_requires` list whose first producer had moved), and `call_with_requirements`' WI-857 layout check — the last one reintroducing, three lines below it, exactly the divergence its own comment warns against. All four are fixed; three were invisible to a green suite. **The deeper fix is taken at §17**, but not in the shape the review proposed — see there for why a newtype over the chain's RETURN type would have caught almost none of them.

**Two residues recorded rather than hidden.** (1) The conditions are a loader-written KB record, not a fact, so `check_provider_requires` and the reflect `provides/2` rule still read `Pair`'s provisions as UNCONDITIONAL — the conditions bind on the dictionary path alone. Making them fact-observable (a `ProvidesConditionInfo(sort_ref, provided, condition)` entity, leaving `SortProvidesInfo` untouched) is what a positive use-site discharge and a condition-aware coherence check would need. The first cut justified the side table by claiming a widened `SortProvidesInfo` would break `reflect/typing.anthill`'s `provides/2` rule; that was FALSE — the loader fills unnamed fields with fresh vars (WI-716), and the rule eleven lines below names 2 of `SortInfo`'s 7 fields and matches. The comment now says what actually holds. (2) `scaland` links a condition's spec scope exactly as it links a `requires` — the first cut dropped conditions at the load phase on the stated grounds that "scaland has no dictionary layer, so this changes nothing it computes", which was also false: a `requires` in scaland *is* a parent-scope link, and moving `pair.anthill`'s two `requires PartialEq` clauses into conditions had silently removed two parent links from its `Pair` scope.

**And it delivered WI-877 with it**, because the acceptance could not be stated otherwise: `pair.anthill` ships four conditioned provisions and ONE operation (`compare`), the whole inherited comparison surface coming from WI-876's default bodies. The cost is that `Pair` is now a CONCRETE `Ord` provider, so a program declaring a rival makes a bracket-less pair compare a three-way tie naming the prelude's own, which `[Ord = Pair]` cannot select (§3.5 check 3). Taken knowingly — WI-877's feedback measured it and chose the lexicographic order as `Pair`'s identity — and asserted in `wi858_pair_orderings_test` so the choice cannot lapse silently.

## 17. WI-1033 — the conditions become facts, and the layout invariant becomes a type (DELIVERED 2026-08-06)

Two halves. WI-869 recorded a provision's conditions in a KB side table with one reader, so they bound on the dispatch path and nowhere else; and it broke the "producer and namer read ONE chain" invariant four times, which prose could not prevent.

**The conditions are `ProvidesConditionInfo(sort_ref, provided, condition)` facts** — one per goal, joined to the provision by the very view that provision carries. A separate entity, leaving `SortProvidesInfo` byte-identical: a provision has MANY conditions, "one fact per clause" is the shape `SortRequiresInfo` already gives "one requirement of one sort" (a condition IS a requirement, scoped to a provision instead of to a sort), and `SortProvidesInfo`'s field list is hard-coded in four places. The side table and `ProvisionConditions` retire.

**And the fact path now CHECKS them.** `check_provider_requires`' self-provision arm accepts a provision because the carrier itself provides the spec that provision requires — justified as "the element-conditionality is already inherited from the outer provision", which held by construction when a carrier had ONE chain and is now a claim about two independent condition lists. It can be false: `provides Ord[C] :- PartialOrd[E]` beside `provides Eq[C] :- Eq[E]` would certify `Ord[C]` at bindings where the `Eq[C]` it requires does not hold. So the outer conditions must ENTAIL the inner ones — a condition entails another when its spec is or transitively requires the other's (`sort_refines`, the relation `refines/2` names) at the same binding VALUES. `Ord[E]` entails `Eq[E]`; `PartialOrd[E]` does not. Refused as its own `LoadError::ProvisionConditionsTooWeak`, because `UnsatisfiedProviderRequires` says "does not provide" and advises "add a fact" — both false here: the carrier does provide it, the condition is what is too weak.

**`DictChain` makes the layout invariant a type — but not the way the review proposed.** A newtype over the chain's RETURN value would have caught almost none of WI-869's four misses, because no site *passes* a chain to the namer: each one *calls* `synth_req_names(kb, symbol)` and the namer re-derives. So the chain OWNS its namer instead — `DictChain { owner, entries }`, with `entries()` and `names()` off one value and `provider_dict_entries` the only constructor; `synth_req_names` is private. Every zip site now takes both halves from one chain, and `build_dep_projection`/`chain_for` — the producer pair that was actually desynchronized — is typed end to end. VERIFIED by backing `chain_for` out to the declared chain: a compile error, where before it was silent. `DictChain::unnamed` covers the no-enclosing-sort caller, and is not a back door: an unnamed chain answers `None` to every name, so a smuggled declared chain produces no dictionary rather than a mis-indexed one.

**Not covered by the type, and said here rather than implied**: `attach_eta_dispatch_dict`'s question is `is_empty()`, which no naming discipline reaches. `sort_reads_requirement_slots` is its one owner, socially and not structurally. Same for the two `req_name_for_chain_index` sites that name a `FromScope` slot from a resolved tree — typing those needs the chain threaded into `ResolutionScope`.

**THE ENTAILMENT RULE WAS WRONG THREE WAYS, and the adversarial review caught all three with repros the suite could not see.** (1) It compared the two conditions' binding VALUES as a sorted SET, dropping the param→value pairing: with `Big[X,Y] requires Small[X,Y]` it accepted `Big[P,Q]` as entailing `Small[Q,P]` — same values, swapped pairing, and unsound — while REFUSING `M2[P,Q]` as entailing `E1[P]` (which it plainly does) because the sets differ in size. The rule is now what the spec says: `q` is entailed when it IS `pc`, or is one of `pc`'s spec's transitive `requires` INSTANTIATED at `pc`'s bindings (`build_child_subst_map` over `requires_chain` — the composition `explain_dep_refusal` already uses), compared PER PARAMETER. (2) Conditions were grouped by the provided BASE, which unions two clauses providing one spec — but across clauses they are a DISJUNCTION, so adding a second, independent way for `Lo[D]` to hold turned a clean load into a refusal. `ProvidesConditionInfo` gained a `clause` index, and the quantifiers are now "for EVERY clause of the outer there EXISTS a clause of the inner all of whose conditions are entailed". (3) `DictChain::unnamed`'s "cannot produce a mis-indexed dictionary" was FALSE for the `FromScope` path, which named its slot from a separately-passed `caller_sort`; `emit_tree_as_projection` takes the chain now, `caller_sort` is gone from four signatures, and the claim is true. All three are pinned by arms that flip.

## 18. WI-870 — the composition leg, and the second producer it had to reach (DELIVERED 2026-08-06)

§7's parting finding, closed. §3.3's rule is that pinning does not reach into the resolution tree — `resolve_inner`'s step 0 fires only at `stack.is_empty()` — so steering a witness's own sub-goal is written by binding the witness's NAMED slot in the key's VALUE position, `f[Spec = W[Slot = Chosen]]`. That text was parsed, validated against the witness's parameters, and then dropped.

**A selection is now `(spec, witness, slots)`**, where `slots` is what the value's own bracket bound on the witness's named requirement slots — recursively, since the bound witness may carry bindings of its own. The two channels are exclusive by construction rather than by precedence: `spec_sort` keys the goal the CALL made, a `SlotSelection` keys a sub-goal of the provider one level up, and the value's bracket is the only thing that can key the second. Nothing about the mechanism is per-level, which is why nesting needed no separate arm and is driven at depth 2.

**Keyed POSITIONALLY, because the spec cannot key it.** 058's own example declares two slots of ONE spec (`requires OA: Ord[A]`, `requires OB: Ord[B]`), and after substitution at a homogeneous carrier their goals are *identical* — `Ord[Int64]` twice. So a `SlotSelection` carries the slot's index in the witness's DICTIONARY chain, and per §7's dual lesson that index has one owner (`dict_chain_index_of_named_slot`) which states the identity and VERIFIES it: `NamedRequirementSlot.slot` is the declaration's position among the scope's `requires` items, `direct_requires` reads one `SortRequiresInfo` fact per such item in that order, and `provider_dict_chain` prefixes that chain — so the entry found there must demand the very spec the slot was recorded for. A disagreement is an error rather than a `debug_assert`, because a mis-indexed pin is silent: it resolves a real goal with a real provider and computes a wrong answer. The test's per-slot arms pin the same thing from outside, with the two slots bound to OPPOSITE orderings so an off-by-one flips the sign rather than changing provenance.

**The second producer is the half the ticket did not name, and 058 §5 writes it on its own second line.** A named slot IS a type parameter (§3.4), so `SortedSet.empty[T = …, O = ListOrd[OE = LexFst]]()` puts the nested binding in the value's TYPE, and every later call carries it as an ARGUMENT with no bracket of its own. `selections_from_slot_bindings` — WI-844's σ-read producer — took `sort_functor_of` and kept the BASE, exactly as `selection_witness_sym` did, so fixing only the bracket would have re-dropped the pin one call later and left the type parameter doing none of the work §3.4 gives it. Both producers now read one function. Backing that half out alone fails exactly one test.

**Two validation decisions, each with an exclusive control.**

*Only a NAMED REQUIREMENT SLOT becomes a selection.* A witness's plain parameters share the same bracket, so `LexFst[A = Int64]` binds a type and selects nothing; reading every entry as a selection would turn a type argument into a provider name.

*§3.5 check 3 is NOT a sub-slot's, and this is the one place the sub-selection's validation differs from the outer one's.* That check refuses naming a CONCRETE provider because at a call site the argument's own value already directs dispatch, so an explicit witness could only agree redundantly or contradict silently. A witness's requirement slot has no value — it is a dictionary slot the typer resolves — so naming a carrier's own provision there is the meaningful answer. Driven with the identical name in both positions: `[Ord = Pair]` is refused, `[Ord = LexFst[OA = Pair]]` runs. Applying check 3 to the sub-slot fails that arm and nothing else. Check 1 IS shared: a value that provides the slot's spec nowhere is refused at the site, and the binding-precise "provides it, but not at THESE bindings" is the resolution's — the WI-841 split repeated one level down, refused in the AUTHOR's vocabulary (`the call bound slot 'OA' of 'W' to 'X'`) because the outer wording would send them to the bracket's key.

**A guard was built and then deleted, and the argument is worth keeping.** The first cut refused a binding for a slot this dispatch does not answer — WI-869 fills a sibling provision's condition with `Unavailable` without searching, so pinning one would be written text with no effect, the same silent drop one level in. It is unreachable: a binder is minted only for a sort-level `requires O: Spec[…]` (§4's `:- goals` tail is a list of spec instantiations and admits no name), and a sort-level slot conditions EVERY provision, so `strict_mask` answers `true` for exactly the slots an author can write. Untestable check logic in place of a stated invariant; the statement now sits at `slot_pin_at`, which is where the arm would go if a condition ever gains a binder.

**Corpus-inert, and the mechanism is opt-in by construction**: `slots` is empty for every bare witness, so a call that writes no nested bracket takes the same path it did before. Full workspace green (29 binaries, 4276 tests).
