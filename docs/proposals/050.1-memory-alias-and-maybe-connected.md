# Proposal 050.1: Memory relations in the logical environment — `memory_alias` and `memory_maybe_connected`

## Status: Draft (2026-10-15). Asked by the user on 2026-10-15 while scoping WI-20261014-6T5C6: a write through a `let`- or pattern-bound name is dropped by what the BINDER is, never by what it stands for; the repair is a memory half of Γ in the spirit of separation logic, and a declared `ensures memory_maybe_connected(…)` on an operation's result. ## The problem

A `Modify[x]` label over a name bound by a `let` or by a pattern is DELETED from the row at the
end of a `match` arm and at the operation boundary. The typer marks every such binder a "local
resource" (`TypingEnv::declare_local_resource` — `typing/build.rs` for `let x = …`,
`typing/pattern.rs` for a pattern binder), and `external_effects` (`typing/result.rs`, called at the
arm's end in `typing/build.rs` and by `region::op_boundary_effects`) drops every label naming one.
The reason is sound for a cell made inside the body — no caller can see it (WI-314, "local state is
externally pure"). But the decision reads the binder, not the memory, so a name that stands for the
caller's own cell is dropped exactly like a fresh one. Measured on `5da88f1f`:

```anthill
operation put(c: Cell[V = Int64], n: Int64) -> Int64 effects Modify[c] =
  let _ = Cell.set(c, n)
  n
operation f(p: Cell[V = Int64]) -> Int64 =            -- declares nothing
  let x = p
  put(x, 7)
operation g(l: List[T = Cell[V = Int64]]) -> Int64 =  -- declares nothing
  match l
    case nil() -> 0
    case cons(h, rest) -> put(h, 8)
```

Both load and both write their argument: `f(c)` and `g([d])` from a `go()` over two fresh cells
answer `7878`. So does `match p case x -> put(x, 1)`. Two more shapes, the same hole:

```anthill
operation first(l: List[T = Cell[V = Int64]]) -> Option[T = Cell[V = Int64]] =
  match l
    case nil() -> none()
    case cons(h, rest) -> some(h)
operation viaCall(l: List[T = Cell[V = Int64]]) -> Int64 =   -- a call's result
  match first(l)
    case some(c) -> put(c, 9)
    case none() -> 0
operation viaBox(p: Cell[V = Int64]) -> Int64 =               -- through a constructed value
  let b = box(c: p)
  match b
    case box(c) -> put(c, 6)
```

`viaCall([d])` writes 9 into `d` and `viaBox(c)` writes 6 into `c`, neither declaring anything
(`9669`).

It is not only a wrong row. A slot that forbids its callback to write the cell it is handed,
`g: (x: Cell[V = Int64]) -> Int64 @ {Eff, -Modify[x]}`, admits `f` — `f`'s row is empty — and the
"read-only" callback moves the cell from 1 to 7 (`readOnly(c, f)` answers `17`). Written `put(p, 7)`
without the `let`, `f` is refused, "undeclared effect: Modify[T = p]": one write, two spellings,
two verdicts.

The one place the typer follows memory instead of names is an operation's own callback
parameter: the flow facts (`reflect/feed.anthill`, WI-352) and `keep_modify` at the boundary
(WI-353) turn `f(h)` over a `match l` element into `Modify[l]`. They reach that shape and no other —
`let v = f; v(p)` drops the write (WI-20261014-7EZS6's addendum; measured: loads with nothing
declared), and so does `f(p.c)` at `f: (k: Cell[V = Int64]) -> Int64 @ {Modify[k]}` (measured
likewise).

And what a `let` does to a cell is not written down. The stdlib calls `Cell` a "typed mutable
reference" whose `new` "allocates a fresh handle"; `docs/design/cell-runtime.md` makes the handle
the identity, so a copy of the value is the same cell — which is what the runs above show. The
kernel spec says only "two places of the same type are two resources" (§5.6), which, read literally,
makes `x` and `p` two resources — the assumption the drop rests on. Proposal 046 lists "aliasing —
two parameters that are the same cell" as open.

## 1. Regions, and two relations over places

A **place** is what §5.6 admits in a `Modify` target: a name in scope — a parameter, `result`, a
`let`, pattern or lambda binder, an ambient resource (a nullary constructor, a value-producing
zero-argument operation) — or a field path off one (`c.contents`).

Only a place whose type can hold a resource takes part: a sort that provides `Modifiable`, a type
holding one in a field or a type argument, a function value (it may capture one), and an open type
parameter, which may be instantiated to any of these. A name over an `Int64` is in no relation, and
at a call that fixes a type parameter to such a type the relations over it are dropped.

**Regions.** Each such place reaches a set of REGIONS, the memory it may lead to:

- an **outside region** for each parameter and each ambient resource the body names — memory the
  caller owns;
- a **fresh region** for each allocation the body makes. A fresh value is connected with nothing:
  its region is new, and no other place reaches it until the body puts it somewhere.

A place's region set is what the body derived (§2). Regions are SHARED, never copied: a value built
from `m` lies in `m`'s own regions, and a store that makes one memory hold another unites the two
regions into one (§2), so every place in either — an enclosing container included — sees the
connection, however long before it was bound. Where control flow joins, the sets are united and
every union either path made is kept, so a set says where a place's memory may lie, and every
reader takes a shared region as sharing.

The two relations:

- **`memory_alias(a, b)`** — `a` and `b` are the same resource: whatever is written through one is
  read through the other. In Γ only where it holds on every path to the point (050's facts, joined
  by the meet). Reflexive, symmetric, transitive; two aliases reach the same regions.
- **`memory_maybe_connected(a, b)`** — the memory of `a` and the memory of `b` may overlap: a write
  through one may be seen through the other. `memory_alias(a, b)` implies it. The name says what a
  clause naming it promises — possibly, not certainly — and its negation is separation:
  `not memory_maybe_connected(a, b)` is `a * b`. No relation says "certainly shares": coverage goes
  by identity and regions (§1.3, §3), an update through a name by `memory_alias` (§5.4). For two
  places it has one of three answers:
  - **connected** — their region sets meet;
  - **separate** — they do not meet, and one of the two reaches no outside region, or both reach
    only ambient resources, which are distinct slots (§5.6). A fresh value is separate from
    everything it was not put into;
  - **unknown** — they do not meet, and each reaches an outside region of a different parameter (or
    one a parameter's and one an ambient resource's): the caller may pass one cell twice, or a list
    and an element of it. The answer is then the hypothesis `memory_maybe_connected(r, s)` over
    those two outside regions themselves, and the body carries both cases (§1.2).

### 1.1 The separation-logic reading

| separation logic | here |
|---|---|
| `x = y` (one address) | `memory_alias(x, y)` |
| `x ↦ _ * y ↦ _` (disjoint) | separate: `not memory_maybe_connected(x, y)` |
| the footprint of `x` | the regions `x` reaches |
| allocation, `x := new …` | a fresh region — connected with nothing |
| the frame rule, `{P} c {Q} ⊢ {P * R} c {Q * R}` | a write through `x` touches only facts over places that may share with `x` (§1.2, §5.3) |
| a postcondition saying where the result lives | `ensures memory_maybe_connected(result, l)` (§4) |
| a precondition `p * q` | not assumed — both cases are carried (§1.2); `requires not memory_maybe_connected(p, q)` states it |

It is an abstract interpretation, not the logic: no points-to contents (a cell's value is Γ's
ordinary `Cell.get(x) ≡ v` fact) and no spatial conjunction in the surface. What it keeps is which
regions a place reaches, which places are one resource, and, for a pair it cannot decide, both
answers.

### 1.2 Both cases, and the caller decides

Inside an operation nothing says whether two parameters share memory. Γ carries what holds in each
case, as facts guarded by the hypothesis — the guard shape of 048's conditional effects:

```anthill
operation f(p: Cell[V = Int64], q: Cell[V = Int64]) -> Int64 effects Modify[p] =
  let v = Cell.get(q)       -- Γ: v ≡ Cell.get(q)
  let _ = Cell.set(p, 5)    -- Γ: v ≡ Cell.get(q) :- not memory_maybe_connected(p, q)
  Cell.get(q) - v           -- 0 where p and q are separate, 5 - v where they are one cell
```

- A write through `x` removes the facts over places connected to `x`, keeps the facts over places
  separate from it, and keeps each other fact guarded by `not memory_maybe_connected(r, s)` for the
  unknown pairs it involves. A fact carries only the hypotheses it needs; the ways `n` parameters
  can share are not enumerated.
- A postcondition the body shows under a hypothesis is guarded the same way. A call discharges the
  guard from the caller's Γ as it refutes an effect's guard (048): proved, the fact holds; refuted,
  it is dropped; where the caller's arguments are its own parameters, the guard is re-keyed onto
  them and stays a hypothesis of the caller.
- An operation whose facts need one case says so in its `requires`:
  `requires not memory_maybe_connected(p, q)` is separation logic's `p * q` (a move that clears its
  source after copying needs it). A call is held to it as to any `requires` (050).
- A hypothesis decides facts only, never what a row covers (§1.3): two memories that overlap need
  not contain each other. The effect row does not split.

### 1.3 What `Modify[x]` declares

Two halves, and they read the relations in opposite directions.

- **What the body owes: containment.** Every location the operation writes lies in the memory of a
  name in its row — a parameter or ambient resource whose region it is, or `result` for a fresh
  value it returns. §3 checks it by the regions: a write through `x` is charged to every outside
  region `x` may lie in, each by its own name, so `let y = if b then p else q` and `Cell.set(y, 1)`
  owe `Modify[p]` and `Modify[q]` both. A connection never covers a write: that two memories may
  overlap — or even do — does not make either contain the other, and no hypothesis (§1.2) is
  consulted.
- **What the caller may assume: invalidation.** What shares no memory with a name in the row is
  unchanged. The caller re-keys `Modify[p]` onto its argument and removes or guards every fact over
  a place connected to that argument in its own Γ, where it knows its arguments: `f(c, c)` sees
  `Modify[c]`, and the facts over the cell it passed as `q` go with it. This is "`Modify[x]`
  modifies everything connected to `x`" (user, 2026-10-15) — the caller's half; a may-overlap is
  what it needs.

So the row does not split. A write through `q` is `Modify[q]`, whatever `p` and `q` share:

```anthill
operation g(p: Cell[V = Int64], q: Cell[V = Int64]) -> Unit effects Modify[p] =
  Cell.set(q, 1)                         -- refused: the write is in q's memory, not p's
```

This refines §5.6's effect-env condition, "for all resource names `s` not in the `Modify` set:
`Env_after(s) = Env_before(s)`", into two sentences: every location the operation changes lies in
the memory of a name in the `Modify` set; and for all resource names `s` connected to no name in
that set, `Env_after(s) = Env_before(s)`. As written today the condition is false for `f(c, c)`,
where writing `p` changes `q`.

## 2. How the relations enter Γ (050's modification rules, memory half)

- **Seed Γ₀.** Each parameter reaches an outside region of its own, and so does each ambient
  resource the body names. Two parameters, or a parameter and an ambient resource, are an unknown
  pair (§1.2); two ambient resources are separate.
- **`let x = y`**, `y` a name: `memory_alias(x, y)`; `x` reaches `y`'s regions.
- **`let x = y.f`**, a field path: `memory_alias(x, y.f)`; `x` reaches `y`'s regions.
- **`let x = ctor(a₁, …, aₙ)`**, and a tuple or a collection literal: `x` lies in the regions of
  every `aᵢ` — the same regions, not a copy of their sets. An immutable value adds no region of its
  own.
- **`let x = lambda …`**: `x` reaches the regions of every name the lambda captures.
- **`let x = op(a₁, …, aₙ)`**: the callee's memory postconditions (§4), with its parameters mapped
  to the arguments and `result` to `x` — 050's call rule, unchanged:
  `memory_maybe_connected(result, aᵢ)` makes `x` reach `aᵢ`'s regions, `memory_alias(result, aᵢ)`
  makes it an alias. What the callee does not declare, `x` does not reach: it is fresh, a region of
  its own, connected with nothing — the default for every operation, generic ones included (decided,
  §8).
- **A pattern** `match s case P` (and a destructuring `let`): a binder that is the whole scrutinee
  (`case x`) aliases `s`; a binder inside a constructor, tuple or collection pattern reaches `s`'s
  regions. A scrutinee that is no name is read as if a `let` had bound it to a fresh one.
- **A call that stores**: the callee's clause may connect two of its ARGUMENTS — `Map.put(m, k, v)`
  declares `ensures memory_maybe_connected(m, value)` (§4) — and the call UNITES their regions. The
  connection then reaches every place in either region, not only `m` and its aliases: after
  `let b = box(m: m)` and then `Map.put(m, k, v)`, `b` and `v` are connected, as they must be — `v`
  is reachable through `b`. Copied at `b`'s binding, `b`'s set would never gain `v`'s region, and a
  write through `v` would keep the facts over `b`. The same holds for `Cell.set(c, v)` wherever `V`
  can hold a resource (a cell's payload being cell-free is in `cell-runtime.md`'s design and is not
  enforced: `Cell[V = List[T = Cell[V = Int64]]]` loads today).
- **A join** after an `if` or a `match`: aliases meet; region sets unite, and every union of regions
  either path made is kept. `let y = if b then p else q` leaves `y` lying in both outside regions
  and aliasing neither, and `p` and `q` stay the pair they were.
- Nothing disconnects. A write may in fact separate two places (`Map.remove`); keeping them
  connected is sound.

## 3. Where a label over a name goes — where the name's scope ends

A label naming a place — `Modify[x]` first of all — is resolved where `x`'s scope ends. Where `x`
is an alias of a parameter or an ambient resource, or of a field path off one, the label is
re-keyed onto that one alone — onto the path exactly (`Modify[c.contents]`): the write is in its
memory, whatever else its region came to hold. Any other `x` is charged by the regions it reaches:
for each outside region, onto every parameter or ambient resource that region belongs to — one, or
several where a store united their regions (§2) — each onto the parameter itself (§5.6:
`Modify[c.rep]` is covered by `Modify[c]`). A fresh region the operation returns is
`Modify[result]` (027.1); a fresh region it does not return adds nothing — the write is to the
body's own memory. `result` joins Γ at the boundary, bound to the body's value. So:

| body | label | at the boundary |
|---|---|---|
| `let x = p` … `put(x, 7)` | `Modify[x]` | `Modify[p]` — refused where `f` declares nothing |
| `case cons(h, _) -> put(h, 8)` over `l` | `Modify[h]` | `Modify[l]` |
| `let b = box(c: p)` … `case box(c) -> put(c, 6)` | `Modify[c]` | `Modify[p]` |
| `let c = Cell.new(1)` … `put(c, 5)`, `c` not returned | `Modify[c]` | dropped — WI-314, unchanged |
| `let c = Cell.new(1)` … `c` | `Modify[c]` (from `new`'s `Modify[result]`) | `Modify[result]` — 027.1's escape |

The re-key follows the regions the body DERIVED for `x`, never a hypothesis between two
parameters: by §1.3 a write through `p` is `Modify[p]`, whatever `p` may share with. Read through
the hypotheses instead, every write through one parameter would be charged to every other.

This is 046 §1's well-scoped output — "no variable bound by the callee's (or a callback's)
parameters" — asked at every scope rather than only at a call: a row never names a binder outside
its scope. It replaces `declare_local_resource` and `external_effects`: what decides is the
regions, not the binder's kind. The arm's end and the operation boundary are where labels are
dropped today; a `let` body's end, an `if` branch's end and a lambda body's end are scope ends too,
and each gets the same reading — at a lambda's end the places in scope are its binders and the
enclosing body's names, and the label is re-keyed onto those whose regions it reaches, so the
lambda's arrow row names nothing else.

The regions are read where the scope ends, so a write made BEFORE a later connection is charged as
well — a fresh cell written and then stored into a parameter's map is charged `Modify[m]`, which the
store charges anyway. Reading them at the point the label is incurred is the precise alternative;
whether it is worth the cost is §8 C.

## 4. Declaring what the result shares: `ensures memory_maybe_connected(result, …)`

An operation says what memory a call of it leaves shared — where its result lives, and what it
stores into what — with ordinary `ensures` clauses over `result` and its parameters (§5.4 admits
both there):

```anthill
operation first(l: List[T = Cell[V = Int64]]) -> Option[T = Cell[V = Int64]]
  ensures memory_maybe_connected(result, l) =
  match l
    case nil() -> none()
    case cons(h, rest) -> some(h)

operation chain(b: Builder, x: Int64) -> Builder
  ensures memory_alias(result, b) = …

operation put(m: Self, key: K, value: V) -> Unit effects Modify[m]
  ensures memory_maybe_connected(m, value) @[host_implemented]
```

**At a call** the clause is assumed into the caller's Γ with the parameters mapped to the arguments
and `result` to the binder, as every `ensures` is (050; `assume_call_ensures`); a
`memory_maybe_connected` clause unites the regions there, as a store in a body does (§2). `viaCall`
then binds `c` connected to `l`, and its write is `Modify[l]`.

**The two relations have opposite polarities.**

- **`memory_maybe_connected` is a SUMMARY**, with the effect row's polarity: an upper bound.
  Declaring more sharing than the body makes is imprecise, never unsound — as a row may declare an
  effect the body never incurs. An anthill body is CHECKED at its boundary, over every pair of
  places a caller can name — its parameters, the ambient resources it names, and `result`: each pair
  the body leaves sharing a region, where nothing at entry said they did, must be named by a clause.
  `first` without its clause is refused there, and so is a body that wraps `Map.put(m, k, v)` and
  returns `Unit` without `ensures memory_maybe_connected(m, v)` — its caller would keep `m` and `v`
  apart after the store. A host operation's clause is trusted, as its row is (the realization
  layer). A member that provides a spec operation, and an override, may declare less sharing than
  the spec, never more — a refinement leg beside the effects one (kernel-language §8.7, "Operation
  override"; `check_override_refinement`). So a collection needs no rule of its own (user,
  2026-10-15): a collection spec's operations carry their clauses like any operation —
  `MutableCollection.insert(c: C, elem: Element) -> Bool effects Modify[c] ensures memory_maybe_connected(c, elem)`
  — a call through the spec reads the spec's clause, and the member that runs is held to it by this
  leg.
- **`memory_alias` is a PROMISE**, with an ordinary postcondition's polarity: the caller takes the
  result for the argument itself and updates one through the other (§5.4). An anthill body must
  establish it on every return path — the alias classes join by meet, so the boundary reads it off
  Γ as it reads any fact. A host operation's is trusted. A member and an override must keep it, as
  they keep any `ensures` (no weaker): an implementation returning a fresh cell cannot provide an
  operation whose spec promises `memory_alias(result, b)`, or its callers would read a write to the
  result as a write to `b`. A promised alias counts as declared sharing as well.

A `requires` writes the same relations where an operation's facts need its arguments separate
(§1.2).

## 5. What reads them

### 5.1 The effect boundary

§3. The measured programs are refused where nothing is declared, and run once their operation
declares the write (`f … effects Modify[p]`) — `viaCall` once `first` also says what its result
shares (§4).

### 5.2 Applying a function value

WI-20261014-7EZS6: applying a function value does not read its own parameter at the argument.
With §2, the application `w(q)` makes the callee's binder at position `i` an alias of the
argument at position `i` — what a named call does by its re-key — and §3 carries the write from
there: `w(q)` writes `Modify[q]`, `let v = w; v(h)` over `h` from `match l` writes `Modify[l]`, and
`f(p.c)` writes `Modify[p]`. A plain rename at the application WITHOUT this proposal would turn
`f(h)` from the flow facts' `Modify[l]` into a `Modify[h]` the arm then drops — which is why 7EZS6
and WI-20261014-6T5C6 (an arrow naming its own parameter outside a parameter list) wait on §3.

The flow facts are the operation-level summary of exactly this for an operation's own callback
parameter: `flow(direct, z, f.a)` is an alias at the application, `flow(element_of, xs, f.t)` a
connection. Once §3 and the application rule read Γ, they are redundant for an operation with a
body; whether anything else reads them is measured before they are retired.

### 5.3 The kill and the frame rule

`abstract-interpreter-and-rules.md` §6.1 adds a kill to 050's call rule — a `Modify[c]` kills every
Γ fact that depends on `c` — and §6.3 takes "depends" to be "the resource term occurs in the fact
(syntactic first cut)". Under aliasing the syntactic cut is unsound:

```anthill
let x = p
let v = Cell.get(p)      -- Γ: v ≡ Cell.get(p)
let _ = Cell.set(x, 5)   -- Modify[x]: kills facts mentioning x; v ≡ Cell.get(p) survives, stale
```

With regions, `Modify[x]` kills every fact over a place connected to `x`, keeps the facts over
places separate from it, and keeps the rest guarded by the hypotheses they involve (§1.2) — the
frame rule, now with a footprint. (The kill is not implemented today, and Γ already holds
`v ≡ Cell.get(p)` for a pure call — §6.1's open hole; this is what the kill reads when it lands.)

### 5.4 Strong update through an alias

`Cell.set(x, v)`'s `ensures Cell.get(x) ≡ v` holds of every alias of `x`; the bridge reads it
through `memory_alias`. A connection without an alias gives nothing: the write may have hit a
different part.

## 6. The spec text this asks for (to be agreed)

In kernel-language §5.6, beside "A `Modify` target is a PLACE":

> A value of a modifiable sort is a reference to its resource. Binding it — by a `let`, a pattern,
> or an argument — names the same resource and copies nothing. An operation that returns a fresh
> resource makes a new one, and a fresh resource shares memory with nothing. Within a body, two
> places name one resource (`memory_alias`) or may share memory (`memory_maybe_connected`) as the
> bindings, patterns, constructions and the callees' declared postconditions say. Whether two
> parameters share memory is not known inside the operation: what the body shows is shown for both
> cases, a fact that holds in one case only holds under that case as its condition, and the caller,
> which knows its arguments, decides it. Every location an operation writes lies in the memory of a
> name in its `Modify` set: a parameter or ambient resource it writes through, or `result` when it
> returns a fresh resource. A write that reaches none of them is a write to the body's own memory
> and is not part of the row, and memory that may overlap a name's does not count as that name's.
> What shares no memory with a name in the `Modify` set is unchanged by the call. The memory a call
> leaves shared among its arguments, the ambient resources and its result is what the operation's
> `ensures memory_maybe_connected(…)` clauses say, an upper bound; `ensures memory_alias(result, a)`
> promises that the result is `a` itself, and holds on every return, as any postcondition does.

The effect-env condition, "for all resource names `s` not in the `Modify` set: `Env_after(s) =
Env_before(s)`", becomes: every location the operation changes lies in the memory of a name in the
`Modify` set, and for all resource names `s` that share memory with no name in that set,
`Env_after(s) = Env_before(s)`. And "Two places of the same type are two resources" becomes "two
places that share no memory are two resources".

## 7. Implementation, in stages

1. **Regions and the boundary** (WI-20261014-7EZS6 and WI-20261014-6T5C6 wait on it). On `Env`,
   beside `FlowEnv`, forked with it and joined natively: the alias classes, joined by meet, and the
   regions — a second persistent union-find, which a store unites and a join keeps every union of;
   a place holds region ids, never a copied set (`abstract-interpreter-and-rules.md` §6.6: a
   structured component with a fact view). The fact
   view answers `memory_alias` / `memory_maybe_connected` to the bridge as a computed relation, the

## 8. Open questions

Decided (user, 2026-10-15), and no longer open: whether two parameters share is not assumed either
way — Γ carries both cases and the caller decides (§1.2); a fresh value is connected with nothing;
`Modify[x]` modifies everything connected to `x`, which is the caller's half of §1.3, so a row does
not split. The may-relation is named `memory_maybe_connected`, so that a clause reads as the upper
bound it is and its negation as separation. And a result no clause speaks of is connected with
nothing — generic operations included; the stdlib writes `ensures memory_maybe_connected(…)` where
its operations share (§7 stage 3). Considered and not taken: a parametric default, connecting a
result to every argument whose type shares a type parameter with it, which would have spared the
generic accessors their clauses.

Settled by the review of the same day (four findings, each folded in): a write is covered by
containment in a declared name's memory, never by an overlap (§1.3); `memory_alias` is a promise
with a postcondition's polarity, `memory_maybe_connected` a summary with the row's (§4); a store
unites regions rather than updating an alias class, so an enclosing container sees it (§2); and a
body's boundary check covers every sharing it leaves among the places a caller can name, not only
`result`'s (§4).

- **C. Granularity.** Soundness needs no direction: a write through a parameter is that parameter's
  alone (§3), so after `Map.put(m, k, q)` a write through `q` is `Modify[q]`, and the caller, told
  `memory_maybe_connected(m, q)`, invalidates `m`; regions come from the operations' clauses, so a
  collection needs no rule of its own (§4). What direction would still buy is precision, as directed
  relations `entity_field(x, f, y)` and `contains(x, y)`: a write through `x` changes neither the
  values `x` held nor `x`'s siblings, where a region set takes their facts too. So would a guard by
  the branch condition at a join (`let y = if b then p else Cell.new(0)` reaches `p` only where
  `b`), and reading the regions where a label is incurred rather than where its scope ends. Is any
  of them needed now, for anything measured?
- **D. Ambient resources** are outside regions (§2). Open: whether a zero-argument resource
  operation's result is an alias of the resource or a part of it.
- **E. A lambda's captures, and a callback parameter's places** — the binder an arrow names
  (WI-20261002-DNDZF) is a place of the arrow, aliased to the argument at each application. And
  what a function value leaves shared: an arrow type carries no `ensures`, so applying
  `f: (a: Cell[V = Int64], b: Box) -> Unit @ {Modify[a]}` may store `b` into `a` and nothing says so
  — the gap §4 closes for an operation, one level up. Either an application of a function value
  whose row writes unites the regions of everything it was handed with what it writes, or an arrow
  type gains the clause.
- **F. The package.** Decided (user, 2026-10-15): the two relations live in a package of their own,
  `anthill.memory` — a top-level package beside `prelude`, `reflect` and `logic`
  (`stdlib/anthill/memory/`), written
  `import anthill.memory.{memory_alias, memory_maybe_connected}`. A rule body over the KB, outside
  Γ, answers nothing for them — they are Γ's.
- **G. A connection a call makes without declaring it** — a host collection that stores a value and
  says nothing — is trusted as declared; the census of stage 3 lists them.
