# Proposal 060.1: A rule's dictionaries are written — no requirement inferred in a rule body

## Status: Draft (2026-11-04). Decided with the user while closing WI-20261102-ATVC1: a rule takes a dictionary only where its clause writes `require[X]`, as an operation takes one only where it writes `requires X`; the inference of a rule body's requirements is withdrawn (option (b) of that discussion — "explicit everywhere", chosen over "explicit only between rules" for being one rule an author can read off the text). Revised the same day after an external review: §1 says where a requirement comes from at a concrete instance and at an abstract one, a conditional provision builds an abstract one from the written requirements as it does for an operation call, and §4 separates what load decides from what run time looks up. §8.1 and §8.3 decided by the user the same day. Nothing here is implemented; §8.2 is open.

## Extends: [060](060-clause-level-requirements-and-typed-heads.md) — §1 (`require[X]`, a dictionary into clause scope) and §3 (the annotation is an anchor).

## Relates to: WI-20260925-P7VP4 (a rule body's requirements inferred from its calls — withdrawn here), WI-20261102-ATVC1 (a rule-body goal hands its callee its caller's dictionaries — the forward slots are withdrawn, the citation marker stays), WI-300 (`requires(X)`, the guard tier — unchanged), WI-860 (a passed dictionary and a unique local row must agree — unchanged), kernel-language §5.3 (the paragraph on a clause's conditions), §5.4, §8.1 (a citation passes the caller's dictionaries into the clause).

## Tracked by: WI-20261104-J9SSG, tagged `proposal-060.1` (both stages of §7).

## The problem

Today a rule gets a dictionary in two ways. A call in its body that needs one gets a read the typer adds and nobody wrote (P7VP4):

```anthill
  rule cmp(?a, ?b, ?c) :- WeakOrd.compare(?a, ?b, ?c)
```

and since ATVC1 a rule that calls such a rule passes it on, through a slot nobody wrote either:

```anthill
  rule outer(?a, ?b, ?c) :- cmp(?a, ?b, ?c)
```

Over `sort Descending provides Ord[T = Int64]`, `operation viaOuter[A](x: A, y: A) -> Int64 requires WeakOrd[T = A] = outer(x, y).head.c` answers `4` at `Descending`, as the operation's caller chose. What `outer` takes is in no text: to see it a reader has to know that `cmp` calls `compare`.

The hidden slots do not extend to a recursion. `evenS` and `oddS` below call each other, and each would need a slot for every slot of the other:

```anthill
  rule evenS(?l) :- ?l <=> nil()
  rule evenS(?l) :- ?l <=> cons(?h, ?t), ?t <=> cons(?h2, ?r),
      WeakOrd.compare(?h, ?h2, ?c), Int64.lte(?c, 0), oddS(?t)
  rule oddS(?l) :- ?l <=> cons(?h, nil())
  rule oddS(?l) :- ?l <=> cons(?h, ?t), ?t <=> cons(?h2, ?r),
      WeakOrd.compare(?h, ?h2, ?c), Int64.lte(?c, 0), evenS(?t)
```

So ATVC1 passes nothing between them, and `isEven[A = Int64, WeakOrd = Descending]([5, 3, 1, 0])` answers `0` where it should answer `1`: below the top call each clause compares with `Int64`'s own order. Measured on `6c6df13a`. A design that collects the slots of a recursion was worked out and tried (each slot named by the dictionary it holds, the recursion's clauses routed again until nothing changes, a refusal where the types grow at each turn). It needed a fallback for reads no such name covers, and it still passed nothing, silently, where a column's type is a bare variable:

```anthill
  rule triA(?l) :- triB(?l)
  rule triB(?l) :- triC(?l)
  rule triC(?l) :- ?l <=> nil()
  rule triC(?l) :- ?l <=> cons(?h, nil())
  rule triC(?l) :- ?l <=> cons(?h, ?t), ?t <=> cons(?h2, ?r),
      WeakOrd.compare(?h, ?h2, ?c), Int64.lte(?c, 0), triA(?t)
```

`triA`'s `?l` is typed by nothing in its clause, so no slot of `triA` can name the element type `triC` compares at. `isTri[A = Int64, WeakOrd = Descending]([5, 3])` answers `0`, before and after that design.

## 1. The rule

> A requirement that a rule-body call or goal needs is supplied where the call is written, as an operation call's is (kernel-language §5.2). At a concrete instance it is built from the provisions at load, and nothing is written for it. At an instance that names a type variable of the clause, it is supplied by the requirements the clause writes with `require[X]`: the one at that instance, or one a conditional provision builds from them. Where none does, the clause is refused, naming the `require[…]` to write. A goal of another rule needs the requirements that rule's clauses write, at the goal's argument types; a call of an operation needs what its signature requires.

The operation-body rule this repeats, measured on `8de8c22e` over `Util.sign[A](x: A, y: A) requires WeakOrd[T = A]` and `Util.same[B](x: B, y: B) requires Eq[T = B]`: `concrete() = Util.sign(1, 2)` loads with nothing written and answers `-1`; `larger[A](x: A) requires Eq[T = A] = Util.same([x], [x])` loads and answers `1`, its `Eq[T = List[T = A]]` built from `Eq[T = A]` through `List`'s conditional `Eq`; the same `larger` without `requires Eq[T = A]` is refused, "requirement `Eq[T = List[T = A]]` cannot be supplied".

The programs above become:

```anthill
  rule cmp(?a: ?t, ?b: ?t, ?c) :- require[WeakOrd[T = ?t]], WeakOrd.compare(?a, ?b, ?c)
  rule outer(?a: ?t, ?b: ?t, ?c) :- require[WeakOrd[T = ?t]], cmp(?a, ?b, ?c)

  rule evenS(?l: List[T = ?e]) :- ?l <=> nil()
  rule evenS(?l: List[T = ?e]) :- require[WeakOrd[T = ?e]], ?l <=> cons(?h, ?t),
      ?t <=> cons(?h2, ?r), WeakOrd.compare(?h, ?h2, ?c), Int64.lte(?c, 0), oddS(?t)
  rule oddS(?l: List[T = ?e]) :- ?l <=> cons(?h, nil())
  rule oddS(?l: List[T = ?e]) :- require[WeakOrd[T = ?e]], ?l <=> cons(?h, ?t),
      ?t <=> cons(?h2, ?r), WeakOrd.compare(?h, ?h2, ?c), Int64.lte(?c, 0), evenS(?t)
```

- **A goal at a concrete instance** writes nothing: `rule ints(?c) :- cmp(1, 2, ?c)` loads, `cmp`'s `WeakOrd[T = ?t]` being at `Int64` there, built from `Int64`'s provision.
- **A goal at the caller's instance** passes the caller's requirement: `oddS(?t)` in `evenS` is at `?t: List[T = ?e]`, where `oddS` writes `WeakOrd[T = ?e]` and `evenS` holds it. `triA` and `triB` must write `require[WeakOrd[T = ?e]]` too, on `?l: List[T = ?e]`, or be refused at their goal.
- **A goal at a larger instance** passes what a provision builds from the caller's requirements. Over `rule same(?a: ?u, ?b: ?u) :- require[Eq[T = ?u]], PartialEq.eq(?a, ?b, true)`, `rule sameL(?x: ?t) :- require[Eq[T = ?t]], same(cons(?x, nil()), cons(?x, nil()))` loads: `same`'s `Eq[T = List[T = ?t]]` is built from `Eq[T = ?t]`. A recursion through such a goal builds one more level at each turn. Where no provision builds the instance, the clause is refused: `pb(cons(?l, nil()))` in a clause at `?l: List[T = ?e]` holding `WeakOrd[T = ?e]`, when `pb` writes `WeakOrd` at its element, needs `WeakOrd[T = List[T = ?e]]`, which no provision of `List` builds.

A citation from an operation is held to the same: a requirement the cited clauses write is built at load at a concrete instance, and at the operation's own type parameter is supplied by its `requires`, directly or through a provision, or refused, as a read is now (§8.1).

## 2. The anchor, extended to a variable inside a head type

060 §3 lets a clause write `require[X]` with no covered call where a typed head binding grounds X's parameters. Only a binding whose bound provides X is read so today:

```anthill
  rule skipN(?l: List[T = ?e]) :- require[WeakOrd[T = ?e]], ?l <=> cons(?h, ?t), chkN(?t)
```
```
error: … expected a typed head binding whose bound provides `WeakOrd` (or is `WeakOrd` itself),
or a body call to one of its operations, got this clause's head bound(s) — List — provide no `WeakOrd`
```

A type variable of a head binding's type grounds a parameter it is written at: `?e` is read off the carried type of `?l`'s value, its element, as `T` of `?x: T` is read off `?x`'s. With that, every requirement §1 asks for can be written.

## 3. A spec's own laws

A law written in a spec reads the spec at its own parameter, as the spec's own operations do, and writes no requirement: `constraint compare_congruent: eq(compare(?a, ?b), 0) :- eq(?a, ?b)` in `sort Ord` is at `Ord`'s `T`. This is the one rule body in the standard library that the inference reads today at a type variable (measured on `6c6df13a`).

## 4. At run time

Load decides where each requirement comes from (§1); run time reads it. Where a caller passes it — a goal of another rule, a citation from an operation — the clause receives the dictionary load routed there, built or the caller's own, and checks it against its local row where that row is unique (WI-860). Where no caller exists — a query, and a constraint or a proof the checker runs — a written `require[X]` finds the dictionary from the carried types when its goal runs, and waits while the anchoring value is unbound; this is the only place a dictionary is looked up at run time.

## 5. What goes

- The inferred reads of a rule body: a spec operation's call and an operation's call with `requires` of its own (P7VP4's two demand kinds), at a type variable. A call at a concrete type was dispatched by its type and keeps that.
- ATVC1's forward slots. Its citation marker stays: it is how a goal passes what §1 supplies, the caller's written requirement or a dictionary built at load, from provisions or from the caller's requirements.
- kernel-language §5.3's sentences that a call owes its dictionary whether or not `require[X]` is written, and that a goal of another rule's body passes what that rule was passed.

## 6. The spec text this asks for (to be agreed)

§5.3, replacing "Writing `require[X]` names the dictionary or shares it among calls; the call owes it either way" and the ATVC1 sentences after it:

> A requirement that a rule-body call or goal needs is supplied as an operation call's is (§5.2): at a concrete instance it is built from the provisions, and at an instance that names a type variable of the clause it is supplied by the requirements the clause writes with `require[X]`, directly or through a conditional provision; the clause is refused where none supplies it. A goal of another rule needs the requirements that rule's clauses write. Over `rule cmp(?a: ?t, ?b: ?t, ?c) :- require[WeakOrd[T = ?t]], WeakOrd.compare(?a, ?b, ?c)`, `rule ints(?c) :- cmp(1, 2, ?c)` loads, `rule outer(?a, ?b, ?c) :- cmp(?a, ?b, ?c)` is refused, and `outer` loads with `?a: ?t, ?b: ?t` and `require[WeakOrd[T = ?t]]` written. Where no caller passes a written requirement — a query — it is found from the carried types when its goal runs.

060 §3's anchor sentence gains the variable inside a head type (§2).

## 7. Stages

1. The anchor of §2 and the law rule of §3. Additive: a rule can write what §1 will ask, and nothing is refused yet.
2. The refusal of §1, with the inference and the forward slots withdrawn (§5), and every program of the suite, the examples and anthill-todo that relied on them rewritten to write its requirements. Each rewritten row is driven to the answer it gave before; ATVC1's rows through `outer`, `outer2`, the connectives and the recursion are rewritten so, and `evenS`/`oddS` answer `1` / `0`.

## 8. Open questions

1. The domain read of an inferred column (060 §2.3, a column inferred at a parametric data sort gets `SortDomain.fill` at a type variable). Decided (user, 2026-11-04): it is the column's own type test, generated from the clause's typing as a typed head's is, and needs no `require` written; it is passed between rules only where the column's type is written.
2. A rule declared in a sort that has a requirement: does it use the sort's requirement with nothing written, as the sort's operations do, or write `require[…]` as any other rule?

   ```anthill
   sort Ranked[T]
     requires O: WeakOrd[T = T]
     entity ranked(a: T, b: T)
     operation order(r: Self) -> Int64 = WeakOrd.compare(r.a, r.b)
     rule ordered(?r: Self, ?c) :- ?r <=> ranked(a: ?x, b: ?y), WeakOrd.compare(?x, ?y, ?c)
   end
   ```

   With `sort Descending provides Ord[T = Int64]` comparing `b - a` and `mk() -> Ranked[T = Int64, O = Descending] = ranked(a: 5, b: 3)`, measured on `8de8c22e`: `Ranked.order(mk())` and `Ranked.ordered(mk()).head.c` both answer `-2` — the operation uses the sort's `O` with nothing written, and so does the rule, its read being the requirement `O` states for `?r`'s type (kernel-language §8.1). Proposed: so it stays under §1 — a rule of a sort writes no `require` for what the sort's requirements state, as the sort's operations write none, and as a spec's own law (§3).

   Found while measuring, a defect of its own, the same before WI-20261102-ATVC1, and fixed (2026-11-04): where only the citation's bracket named the slot, `Ranked[T = Int64, O = Descending].ordered(ranked(a: 5, b: 3)).head.c` answered `1`, `Int64`'s own `compare`, while the operation cited the same way answered `-2`. The argument's type alone stood for the column, and it leaves `O` open; the citation now reads the argument's type met with the column's. Two cases stay as they are, and are this question's: the same rule cited as `Ranked[T = Int64].ordered(…)`, `O` written nowhere, answers `1` where the operation is refused for the unsupplied `O`; and a rule whose column is not typed at the sort (`rule order(?p, ?c) :- ?p <=> box(a: ?x, b: ?y), …` in `sort Box`) reads no bracket, as row (g) of WI-20261102-ATVC1 does not.
