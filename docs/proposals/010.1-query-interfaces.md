## 2. The problem: one query, two readings

A query written as text is typed where it is read (`convert_query_terms` calls `typing::route_query_goals`). A query a program builds as a value is not: `execute_logical_query` lowers it and hands it to the resolver.

```anthill
sort Pt
  entity pt(x: Int64, y: Int64)
  provides PartialEq[T = Pt]
  provides Eq[T = Pt]
  operation eq(a: Pt, b: Pt) -> Bool =
    match a case pt(ax, ay) -> match b case pt(bx, by) -> PartialEq.eq(ax, bx)
end

operation ask(goal: Term) -> String effects Error[ResolveStreamFailure] =
  match splitFirst(execute(kb(), pattern_query(term: goal)))
    case none() -> "no answer"
    case some(p) -> "answered"

entity Goal(g: Term)
fact Goal(g: pt(1, 2) = pt(1, 9))
rule viaFact(?s) :- Goal(g: ?g), ?s <=> ask(?g)
```

- The query `pt(1, 2) = pt(1, 9)` is typed at `Pt` and runs `Pt.eq`: `true`.
- `viaFact(?s)` answers `"answered"` too, but no load chose `Pt.eq`: the stored goal is the code `eq(pt(1, 2), pt(1, 9))`, and the resolver's equality index read the operand's constructor when the goal ran. So did `ask(make_fn("anthill.prelude.PartialEq.eq", [as_term(pt(1, 2)), as_term(pt(1, 9))]))`.

073 §6.2 removes that index ("nothing reads a value's carried type at run time"), and 058 §3.9 says run time performs no typing. With both, the value-built query has no reading.

## 3. Typed and untyped queries

A query is a clause with no head, and it is translated as a clause is (060, 060.1): what it writes declares its requirement slots. A query is **typed** when the typer reads it and **untyped** when nothing does; the two differ in what fills the slots.

### 3.1 The slots a query declares

| written in the query | slot | generated goals |
|---|---|---|
| `Spec[T = A]` as a goal | `Spec` at `A`: its dictionary (060.1) | the read of that dictionary |
| `?x: T` | `SortDomain[T]` (060 §2.3) | a type test before the rest of the query, `SortDomain[T].fill(?x)` after it |

A call that needs a requirement at a type the query fixes declares no slot: the dictionary is built from the provisions at that type, as in a clause. A type reaches a query as its `SortDomain` dictionary; a `Type` value never fills a slot (055 §4).

The translation is the one `install_typed_head_domain_goals` (`kb/typing/rules.rs`) gives a rule with a typed head, run over the query. Today it runs per rule only, which is why a typed variable in a query reaches the converter unlowered and panics.

### 3.2 Typed query

Processed by the typer, in three places:

- the shell's text (`anthill query`, `--query-file`), typed when it is read;
- `KB.execute(kb, q)`, which types the `LogicalQuery` it is handed when it reads it, before the search;
- a query written in code, typed at load where it is written: a relation cited in an operation body (052).

Its type variables are introduced by a bracket, as a rule head introduces them: `[A] ?a: A, ?b: A, PartialEq[T = A], ?a = ?b`. Its slots are filled by the typing: from the types the query fixes (its arguments' types, a bracket on a relation's goal), or, in code, from the enclosing operation's frame. A slot nothing fills is refused where the query is typed, and `KB.execute` reports it as `malformed_query(detail)`, the typer's message as the detail. Reading a query at `KB.execute` is a load of the query: it ends before the search starts, so nothing during the search chooses a member (058 §3.9).

Measured today, over `rule sameR[A](?a: A, ?b: A) :- PartialEq[T = A], ?a = ?b` and the `Pt` of §2:

| query | answer |
|---|---|
| shell: `sameR(pt(1, 2), pt(1, 9))` | `true`, `A = Pt` from the arguments |
| shell: `sameR[A = Pt](pt(1, 2), pt(1, 9))` | `true`, `A` from the bracket |
| shell: `sameR(?a, ?b)` | refused: "needs a requirement, `PartialEq` at `sameR`'s `A` … a query has no caller to pass the dictionary" |
| code: `same(pt(1, 2), pt(1, 9))` over `operation same[A](a: A, b: A) -> Int64 effects Error requires PartialEq[T = A] = match sameR(a, b).splitFirst() case none() -> 0 case some(_) -> 1` | `1`: the dictionary `same` was handed reaches `sameR`'s `=`, and the equality index is not read |

Wanted, `KB.execute` typing what it reads:

| query handed to `KB.execute` | answer |
|---|---|
| the stored `eq(pt(1, 2), pt(1, 9))` of §2 | one solution, through `Pt.eq` |
| `make_fn("anthill.prelude.PartialEq.eq", [as_term(pt(1, 2)), as_term(pt(1, 9))])` | one solution, through `Pt.eq` |
| `make_fn("anthill.prelude.PartialEq.eq", [as_term(pt(1, 2)), as_term(1)])` | `malformed_query`: a `Pt` and an `Int64` compared |
| `sort_query(sort: as_term(Color))` | as today |

### 3.3 Untyped query

Not processed by the typer. `KB.execute_untyped(kb, q, dictionaries)` runs a `LogicalQuery` as it is built. The query's slots are its parameters, and the caller passes a dictionary for each. Its type variables are query variables:

```
?a: ?t, ?b: ?t, PartialEq[T = ?t], ?a = ?b
```

run with `Dictionary.instance[PartialEq[T = Pt]]()` for the `PartialEq` slot and `Dictionary.instance[SortDomain[T = Pt]]()` for each `?x: ?t`. A dictionary is used as given. A slot given none is an error when the query runs, as today's is ("the requirement `anthill.prelude.PartialEq` of a clause was passed by no caller"). A query that writes no slot runs as today's `execute` runs it: `as_term(pt(x: 1, y: fresh_var[Int64]("y")))` answers (measured).

Today `KB.execute` is this interface without the dictionaries: `make_fn("p4.sameR", [as_term(pt(1, 2)), as_term(pt(1, 9))])` fails with that `evaluation_failure`, and a goal of `PartialEq.eq` itself is answered by the equality index (§2), the reading 073 §6.2 removes.

## 4. Open questions

- **Q1. How a passed dictionary meets its slot.** By its spec, one dictionary per spec (058 §3.9's anonymous slot), or by the slot's position in the query; and whether it binds `?t`, as 060.1 binds `?p` in `Sp[C = Red, P = ?p]` to the type the provision writes.
- **Q2. How a `LogicalQuery` value writes a slot.** `make_fn` takes a name and terms only, and a goal stored in a fact cannot carry a bracket (`fact Goal(g: sameR[A = Pt](…))` is a load error). Neither writes `PartialEq[T = ?t]` or `?x: ?t` yet. *Answered for a typed variable* (WI-20261124-C6VN0): `typed_query(var: ?x, type: T, query: q)` is `?x: T` written in `q`. A requirement goal (`PartialEq[T = ?t]`) and a type variable (`?x: ?t`) are still unwritable.
- **Q3. A written query form in code** for a conjunction that names no rule (010's OQ11.4 comprehension, or a typed `LogicalQuery` literal), or is a named rule enough.
- **Q4. The shell's query** is one goal: `account(?id, ?o, ?b), gt(?b, 1000)` is a syntax error. Give it a conjunction and the `[A]` introducer.
- **Q5. `limited` and `projected`.** Honour the count and the projection, or refuse them; dropping them is a silent skip.
- **Q6. `LogicalQuery`'s quantifiers and aggregations.** Implement them, or remove them in favour of stream and relation operations (010 R4).
- **Q7. Carried over from 010, still open:** fact metadata in results (OQ2.3), ordering and determinism (OQ12), scored streams (OQ14), query syntax (OQ11, OQ15).

## 5. Spec amendment

kernel-language §5.3, after "A query is typed where it is read, as a rule body's goal is":

> A query is a clause with no head: a requirement written as a goal and a typed variable declare its slots, as a clause's do. `KB.execute` types the query it is handed before it runs it, and reports one the typer refuses as `malformed_query`. `KB.execute_untyped` runs a query no typer reads: a dictionary passed with it fills each slot it writes, and a slot given none is an error when it runs.

## 6. Stages

Tagged `proposal-010.1`; stages 1 and 2 are rows of WI-20261105-CBRD2 (proposal 073 stage 4, item 5), decided with the user 2026-11-15.

1. **Typed `KB.execute`** (§3.2): `KB.execute` types its lowered goals as `convert_query_terms` does and reports a refusal as `malformed_query` (delivered 2026-11-15). A query built as a value is then decided at its types, except that an `=` at a composite (`Option[T = Pt]`) still reaches the equality index, as in a rule body: the resolver does not yet read the dictionary the typer hands it there. A guard registered with `KB.add_guard` is still run untyped. Both remain WI-20261105-CBRD2's before the index's run-time readers go.
2. **A typed variable in a query** (§3.1): a typed query translates `?x: T` as a typed head is translated, the type's goals joined with the pattern (delivered 2026-11-15; a `LogicalQuery` value writes one with `typed_query` since WI-20261124-C6VN0). Its goals stand around the goal it is written in, so under `not` or in a branch of `|` it types that negand or branch. A type that leaves a parameter unwritten is refused, and so is one that cannot fit its column, held to the whole query at its top level and to its own goal in a negand or branch, as a rule head's bound is to its body; a pattern no typer reads refuses a typed variable. WI-20261105-CBRD2. The type is also the one the typer reads the variable at in that goal, as a head's bound is in the body: delivered with the guard only, `PartialEq.eq(?xs: List[Int64], ?ys: List[Int64])` was refused, nothing fixing the element (measured 2026-11-24), and is decided at `List[Int64]` since WI-20261124-C6VN0.
3. **`KB.execute_untyped`** (§3.3), after Q1 and Q2. WI-20261115-DHN42, pre-opened.
4. Q4, the shell's conjunction and `[A]` introducer: WI-20261115-TFPME. Q5 and Q6, `LogicalQuery`'s `limited`, `projected`, quantifiers and aggregations: WI-20261115-JQ0DG. Q3, a written query form in code: WI-190 (quasi-quote patterns), noted there.
