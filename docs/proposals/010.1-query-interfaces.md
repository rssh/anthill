## 2. The problem: one query, two readings

A query written as text is typed where it is read (`convert_query_terms` calls `typing::route_query_goals`). A query a program builds as a value is not: `execute_logical_query` lowers it and hands it to the resolver.

```anthill
sort Pt
  entity pt(x: Int64, y: Int64)
  provides PartialEq[T = Pt]
  provides Eq[T = Pt]
  operation eq(a: Pt, b: Pt) -> Bool =
    match a case pt(ax, ay) -> match b case pt(bx, by) -> PartialEq.eq(ax, bx)
end

operation ask(goal: Term) -> String effects Error[ResolveStreamFailure] =
  match splitFirst(execute(kb(), pattern_query(term: goal)))
    case none() -> "no answer"
    case some(p) -> "answered"

entity Goal(g: Term)
fact Goal(g: pt(1, 2) = pt(1, 9))
rule viaFact(?s) :- Goal(g: ?g), ?s <=> ask(?g)
```

- The query `pt(1, 2) = pt(1, 9)` is typed at `Pt` and runs `Pt.eq`: `true`.
- `viaFact(?s)` answers `"answered"` too, but no load chose `Pt.eq`: the stored goal is the code `eq(pt(1, 2), pt(1, 9))`, and the resolver's equality index read the operand's constructor when the goal ran. So did `ask(make_fn("anthill.prelude.PartialEq.eq", [as_term(pt(1, 2)), as_term(pt(1, 9))]))`.

073 §6.2 removes that index ("nothing reads a value's carried type at run time"), and 058 §3.9 says run time performs no typing. With both, the value-built query has no reading.

## 3. Two interfaces

### 3.1 Pre-typed: typed where it is read

A query that arrives as data — text at a prompt (`anthill query`, `--query-file`) or a `LogicalQuery` value handed to `KB.execute` — is typed when it is read, with the typing a written query gets (kernel-language §5.3). This is the interactive shell's interface. Reading is a load of the query: it happens before the search starts, as the CLI's does, so nothing during the search chooses a member.

A query the typer refuses is not run. `KB.execute` reports it as `malformed_query(detail)`, the typer's message as the detail.

Wanted:

| query handed to `KB.execute` | answer |
|---|---|
| the stored `eq(pt(1, 2), pt(1, 9))` (§2) | one solution, through `Pt.eq` |
| `make_fn("anthill.prelude.PartialEq.eq", [as_term(pt(1, 2)), as_term(pt(1, 9))])` | one solution, through `Pt.eq` |
| `make_fn("anthill.prelude.PartialEq.eq", [fresh_var[Term]("a"), fresh_var[Term]("b")])` | `malformed_query`: a query has no caller to pass `PartialEq` |
| `sort_query(sort: as_term(Color))` | as today |

### 3.2 Post-typed: typed where it is written

A query written in code is typed at load where it is written. A requirement it leaves open at a type parameter of the enclosing operation is passed from that operation's frame, as a call's dictionaries are (074 §1.4, group two). The relation cited as a stream (052) is this interface, and it works today:

```anthill
rule sameR[A](?a: A, ?b: A) :- PartialEq[T = A], ?a = ?b

operation same[A](a: A, b: A) -> Int64 effects Error requires PartialEq[T = A] =
  match sameR(a, b).splitFirst()
    case none() -> 0
    case some(_) -> 1
```

`same(pt(1, 2), pt(1, 9))` answers `1` through `Pt.eq`, the dictionary `same` was handed reaching `sameR`'s `=` (measured; the equality index is not read). A structural comparison would answer `0`.

What it does not cover: a conjunction written in code without naming a rule. `LogicalQuery` is built from `Term`s, which carry no load types, so any query built from it is pre-typed (§3.1).

## 4. Open questions

- **Q1. A written query form.** Is a named rule enough for a post-typed query, or does an operation body need an anonymous written query whose goals the load types (010's OQ11.4 comprehension, or a typed `LogicalQuery` literal)?
- **Q2. Typed query variables (010 OQ5.3).** `?bal: Int64` in a query: read as a rule head's bound is, or refused. Today it panics.
- **Q3. A conjunctive CLI query.** `--pattern` takes one goal; the harness's `common::query_goals` types several together. Give the CLI the same, or keep a conjunction a rule.
- **Q4. `limited` and `projected`.** Honour the count and the projection in `execute`, or refuse them; dropping them is a silent skip.
- **Q5. `LogicalQuery`'s quantifiers and aggregations.** Implement them, or remove them in favour of stream and relation operations (010 R4).
- **Q6. Carried over from 010, still open:** fact metadata in results (OQ2.3), ordering and determinism (OQ12), scored streams (OQ14), query syntax (OQ11, OQ15).

## 5. Spec amendment

kernel-language §5.3, after "A query is typed where it is read, as a rule body's goal is":

> A query a program builds as a value is typed when `KB.execute` reads it, before it runs, and one the typer refuses is reported as `malformed_query`. A relation cited in an operation body is typed where it is written, and a requirement it leaves open at a type parameter of that operation is passed from the operation's frame.

## 6. Stages

1. **Pre-typed `execute`** (§3.1): `execute_logical_query` types its lowered goals as `convert_query_terms` does and reports a refusal as `malformed_query`. With it, a value-built query no longer reaches the equality index, and the index's run-time readers can go (WI-20261105-CBRD2, item 5).
2. Q2 and Q4, the two defects.
3. Q1, Q3 and Q5, each as decided.
