# 027.4: Error Effect — `reify` at the `Error` layer, and `Result` as its denotation

## Status: DELIVERED (2026-09-09) — all five steps

`Error.reify` and `anthill.prelude.Result` are in the prelude and anthill catches a raise
end to end. Measured: `Error.reify(lambda () -> mayFail(0 - 1))` returns
`err(boom("negative"))` and the payload destructures in anthill; and the DRIVER runs —
`Error.reify(lambda () -> KB.loaded(cons(src, nil)))` returns `err(load_failed(ds))` with
the LOADER'S OWN PROSE intact, which is the arm that kept the guardians
`LoadChecker.check` in host Rust:

| candidate | caught diagnostic |
|---|---|
| `namespace ok.one end` | — (the `ok` arm) |
| `namespace broken.` | ``source 0: 1:1: syntax error near `namespace broken.` `` |
| `operation f(n: Int64) -> String = n` | `type mismatch in f.return (op-return): expected String, got Int64` |

**Each diagnostic names the CHECK THAT RAN and what it wanted**, which is why the payload
is worth catching rather than counting: the second row locates the failure and says which
source it was in, and the third is a repair instruction — the operation, the slot, and
both sides of the mismatch. A checker that answered "1 error" would prove a list of the
right length arrived and nothing about its content, and the model on the other end of the
guardians loop learns nothing from it. The acceptance asserts the PROSE for that reason.

## Depends on: 027 (effect handlers — the `HandlerAction` carrier, `Throw`), 013 (effects as sorts and facts), 045 / WI-307 (effect rows), WI-329 (handler discharge — the static half, delivered)

## Relates to: 047 (effects as monads — this makes its §9 step 2 concrete for one effect), 027.2 (the `Branch` twin, which needs the continuation machinery this one does not), WI-078 (027 phase B, claimed), WI-SPGBP (`KB.loaded`, the driver)

## Motivation

**Nothing in anthill can catch anything.** Measured: no operation anywhere in
`stdlib/anthill/` reifies an effect. (`anthill.reflect.KB.reify` exists —
`reflect.anthill:495`, `reify(kb: KB, t: Term) -> TermRepr` — but that is the Term ↔
TermRepr bridge, an unrelated use of the word; see the naming note below.) WI-329's
capstone
`wi329.solver.reify` (`tests/include/wi329_handler_discharge_test.rs:466`) is a
body-less `= 0` fixture returning `Int64`, present to prove a *typing* rule; it is not
an implementation and must not be read as one. So every operation declaring
`effects Error` — 15 declarations in the stdlib alone — is uncatchable from anthill.

The raise half, by contrast, works end to end. Measured with `anthill run` on

```anthill
operation may_fail(n: Int64) -> Int64 effects {Error[Boom]} = raise(boom("kaboom"))
```

which prints `before` then `error: boom(why: "kaboom")`. The route is
`Error.raise` → `error_raise` (`eval/builtins.rs:6224`) → `Interpreter::raise_error`
(`eval/effects.rs:625`) → `EvalError::Raised { payload }`.

The concrete driver is `anthill.reflect.KB.loaded` (WI-SPGBP): it loads candidate
source into a discardable layer and raises `load_failed(diagnostics)` when the
candidate does not parse or does not load. A checker's *whole job* is to catch that
and report the diagnostics. Today it cannot, which is why the guardians example's
`LoadChecker.check` is host-bound Rust (`tests/guardians_test.rs:419`) for one
irreducible reason: its `Err(e) => load_failure_to_rejected(interp, e)` arm.
`KB.loaded` and `guardians.gate` are already anthill; only the catch is not.

## Design

### The pair, and why there are exactly two operations

047 §3 gives the shape, and it is Filinski's:

```
reflect : M a -> a            -- inject a monadic value into direct-style code
reify   : (() -> a) -> M a    -- capture a direct-style computation as a monadic value
```

At `M = Result`, `reflect` is **already implemented** — an effect *operation* is a
reflect, so `raise(x) = reflect(err x)`. What is missing is `reify`. That is the whole
of this proposal.

```anthill
sort anthill.prelude.Error
  import anthill.prelude.{Nothing, Result}
  sort T = ?

  operation raise(error: T) -> Nothing effects Error[T]

  -- The boundary. Runs `body`; a raise inside it aborts here and becomes `err`.
  -- `T1` is the payload, inferred from the body's row.
  operation reify[Rho, X, T1](body: () -> X @ {Error[T1], Rho}) -> Result[E = T1, T = X]
    effects {Rho}
end
```

`raise` puts a payload into the channel and `reify` takes one out — the two halves of one
layer. `T1` is an ordinary operation type parameter, inferred from the body's effect row
(`Error[T1]` is shorthand for `Error[T = T1]`, which names this very sort at `T1`), and it
flows into the result as `Result[E = T1]`. A caller writes nothing.

**What `Error[T1]` in the PARAMETER row is doing, and why deleting it is not an option.**
Measured, by dropping the label and leaving `body: () -> X @ {Rho}`:

| signature | caller | verdict |
|---|---|---|
| `body: () -> X @ {Error[T1], Rho}` | declares no effects | loads |
| `body: () -> X @ {Rho}` | declares no effects | `undeclared effect: Error[T = Boom]` |
| `body: () -> X @ {Rho}` | declares `{Error[Boom]}` | loads — but nothing was discharged |

**The label IS the discharge.** A handler's whole type is "the label present on the body
side, absent from the result" — WI-329's `(body: () -> X @ {K, ρ}) -> X @ {ρ}`. There is no
`handle` keyword and no per-effect typer rule; the shape of the signature is the entire
mechanism. Delete `K` and `ρ` simply absorbs it, so the label escapes to the caller. What
is left is not a handler, only a wrapper that happens to return a `Result`. It is also the
only occurrence that names the payload, so `T1` — and hence `Result[E = T1]` — comes from
nowhere else.

**Why `T1` and not the sort's `T`, and the typer fix that makes it available.** Both
spellings type-check the payload correctly — measured, each refuses a wrong `[T1 = Other]`
/ `[T = Other]` binding and a wrong result annotation. `T1` is the better one: it says in
the signature that the payload is a parameter of THIS operation, inferred from the body,
and it leaves the caller nothing to write. The sort's-`T` spelling additionally exposes an
unused bracket slot (`Error.reify[T = Other](…)` is accepted and inert).

`T1` did not load for a USER-DEFINED effect sort before this proposal, and the reason was a
defect rather than a rule. `sort Error { sort T = ? }` makes `Error` a SPEC sort — the
typeclass shape — so a call to a member with an abstract spec parameter must have a
covering `requires`. The check (`kb/typing.rs`, WI-325) walked EVERY type parameter of the
spec sort and asked "is it bound?", without asking whether the operation being called uses
it. `reify[Rho, X, T1]` names the sort's `T` nowhere — not a parameter, not the return, not
the effect row — so nothing can dispatch on it and no witness could supply it, yet it was
flagged abstract. Whether that flag became a diagnostic was then decided by
`spec_warrants_abstract_check`'s NAMESPACE leg, so byte-identical source loaded under
`anthill.*` and was refused outside it.

**What the check was standing in for, and why removing it here is right.** The verdict was
namespace-gated in BOTH directions — measured on `sort MySpec { sort T = ?  operation
ping() -> Bool }` called `MySpec.ping()`:

|            | user namespace | `anthill.*` |
|---|---|---|
| before (b) | refused        | **loads**   |
| after (b)  | loads          | loads       |

So (b) does not open a hole; it makes user code agree with the behaviour the stdlib has
always had. And the message it removes was never the right one for this program: `ping` is
body-less with no provider, so `anthill run` dies with "operation has no body", and adding
`requires MySpec[T = …]` to the enclosing sort would not make it runnable — there is still
no implementation. `missing requires` was a PROXY for "unimplemented operation", firing
inconsistently. Detecting the real condition is a separate, missing check; it is not what
this loop asks and it is not in scope here.

The fix is a filter in that loop: skip a spec parameter the called operation's signature
never mentions AND that no receiver carries.

```rust
let has_receiver = self_recv_spec.is_some() || carrier_param_info.is_some();
if !signature_mentions && !has_receiver { continue; }
```

Both conjuncts are load-bearing, and each was measured by breaking it:

- `type_mentions_spec_param`, not an `occurs_in_view` on the alias var — a declared
  parameter type names a spec param by SYMBOL (`Ref(MySpec.T)`) as readily as by variable.
  The var-only test let `MySpec.same(a: T, b: T)` through on an abstract `T`, which is
  exactly WI-325's case.
- `!has_receiver` — a RECEIVER carries the spec's parameters even when the signature never
  writes them. `render(w: Widget)` on `sort Widget { sort T = ? }` names `Widget.T`
  nowhere, yet its witness is selected per carrier, so `T` is part of the instantiation
  being sought. Without this conjunct
  `wi325_missing_requires_test::user_defined_self_receiver_spec_without_providers_errors_on_abstract_call`
  goes red — a wholly-unimplemented self-receiver spec loaded clean.

The pair `self_recv_spec.is_some() || carrier_param_info.is_some()` is already this file's
spelling of "this call dispatches on nothing" — `enclosing_requires_clause` tests the same
two. Full suite after the fix: 6650 passed, 0 failed, unchanged from the baseline total.

**The name is doubly used, deliberately.** `anthill.reflect.KB.reify(kb, t) -> TermRepr`
already spells it, for the unrelated Term ↔ TermRepr bridge. Different sorts, so no
resolution collision — and scoping this one as a MEMBER of the effect sort is what keeps the
two apart at every call site (`Error.reify` versus `KB.reify`). It is also 047 §2's own
rule, that an effect's monad is declared in that effect's API, and it leaves room for
`Branch.reify` / `Suspension.reify` to follow the same shape (027.2).

Naming the operation's parameter `T` — shadowing the sort's — remains a deliberate refusal
(proposal 058 §4.2 rule 1): *"A call-site bracket binds BOTH scopes, so
`Error.reify[T = …](…)` would have two targets and the reader cannot see which one it
hit."* Hence `T1`.

### `Result` — the denotation

047 §2's table assigns `Error` the monad `Result[_, T]` with `raise(x) ≙ Err(x)`. The
prelude has `Option` and no `Result` / `Either` (measured: no such declaration under
`stdlib/anthill/prelude`), and `Option` will not serve — it drops the payload, and the
payload *is* the answer a caller wants.

```anthill
enum anthill.prelude.Result
  sort E = ?                       -- the error payload type
  sort T = ?                       -- the success type — the `Monad` carrier's member
  entity ok(value: T)
  entity err(error: E)
end
```

Plus `map` / `flatMap` short-circuiting on `err`, and — cheaply, because it is writable
in anthill with no runtime work — the reflect direction:

```anthill
operation reflect[A, B](r: Result[E = A, T = B]) -> B effects Error[A] =
  match r
    case ok(v)  -> v
    case err(e) -> raise(e)
```

`reflect` is worth landing beside `reify` precisely because it is nearly free and it is
what makes the two an *isomorphism*: reify a computation, manipulate the `Result` as
ordinary data, reflect it back into effectful code. That is the difference between a
monad layer and a bare try/catch.

**`Result` provides `Monad`, and this is DRIVEN, not assumed.** `monad.anthill`'s own
header already names the instance — *"Effect denotations (047 §2) are instances of THIS
sort — `fact Monad[M = Result[E]]` (Error)"* — and the partially-applied carrier works.
DELIVERED as `stdlib/anthill/prelude/result.anthill`, beside `option` and after the
`monad` both provide into; measured with `anthill run`, dot-dispatching through the
`Monad` member on a `Result` receiver:

```anthill
provides Monad[M = Result[E = E], pure = resultPure, flatMap = resultFlatMap, map = resultMap]
```

Measured with `anthill run`, dot-dispatching through the `Monad` member on a `Result`
receiver:

| expression | output |
|---|---|
| `ok(3).map(x -> x + 39)` | `42` |
| `err(boom("nope")).map(x -> x + 39)` | `nope` — short-circuits, payload preserved |
| `ok(3).flatMap(x -> ok(x * 2))` | `6` |
| `err(boom("nope")).flatMap(x -> ok(x * 2))` | `nope` |

**This fixes the parameter NAMES.** `Monad[M[T]]` requires the carrier's member to be `T`,
so the success type is `T` and the payload is `E` — the spelling `monad.anthill` already
uses. `Error.reify`'s result is then `Result[E = T1, T = X]` — the payload in `E`, the
success value in `T`. Measured: that declaration and its call site load, and the
wrong-payload annotation control still refuses.

### Single-callback — on merit, NOT because the alternative is refused

`reify` returns a sum because that is what makes it a **monad layer**: the `Result` is a
value, so a caller may `map` / `flatMap` / pattern-match it, hand it on, or `reflect` it
back into effectful code. A recovery callback gives none of that — it consumes the failure
at the boundary and returns a plain value. 047 §3 specifies the sum form
(`reify : (() -> a) -> M a`) and §7 makes `try_catch(body, recover)` a **library function
over it**, not a primitive. That is the reason, and it stands on its own.

**The typer's current refusal of the two-callback form is a BUG and must not be read as
support for this shape.** WI-20260820-RDNS4 is open and says so in its own words: with
`operation two[Rho](a: () -> Int64 @ {Error[Int64], Rho}, b: () -> Int64 @ {Rho})`,
*"`Rho = {Clock}` is a valid solution in both; the typer rejects a well-typed program"* —
the first argument's unify closes the shared tail on its SUCCESS path before the second
can contribute. It is pre-existing (refused before and after WI-329), it is not about
handlers (the same failure occurs with no handled label at all), and it has an owner.

So the two designs are not in competition and this proposal does not depend on that
refusal standing. When RDNS4 lands, `try_catch(body, recover)` becomes writable as
ordinary sugar over `reify` + `match`, with no change to anything here.

### `reify` does **not** go through the handler registry

The interpreter does call effect handlers today, but for a narrow set. Measured:

- the registry is a **flat, global, per-`Interpreter`** `HashMap<Symbol, Option<EffectHandler>>`
  (`eval/effects.rs:487`) with `register` / `take` and **no push/pop and no scoping**
  (that is WI-078 phase B step (h), unlanded);
- **five** handlers are registered by `register_standard_effect_handlers`
  (`eval/effects.rs:786`): three `Console` kinds, `Modify`, and `Error`;
- there are **seven** dispatch sites, all of them `effect_dispatcher!` builtins
  (`eval/builtins.rs:6167`): `Console.print` / `println` / `eprint` / `eprintln` /
  `read_line`, and `ModifyRuntime.get` / `set`;
- **`Error.raise` is deliberately not one of them.** `eval/builtins.rs:6224` says why:
  an unhandled Console/Modify effect is a missing-capability `Internal` fault, but an
  unhandled `Error` must *default to Throw* so the payload is never lost.

Two reasons `reify` must stay off that path, and the second is the load-bearing one:

1. The registry has no dynamic extent. "Install a catching handler for the duration of
   this body" would be a register/remove pair around a flat map — wrong under nesting,
   and skipped on exactly the path that matters (the raise).
2. **A handler cannot express recovery at all.** `raise(error: T) -> Nothing` has no
   value to resume with, and `raise_error` already refuses the attempt loudly:
   *"Error handler resumed a raise (returned …) — Error is non-resumable"*
   (`eval/effects.rs:643`). A short-circuit needs a place to short-circuit *to*, and
   that place is not a handler — 047 §3 states the identity directly:
   **handler / `provide` = `reify` / `reset`.**

So this proposal adds **no handler-registry work**. `Error.raise` is unchanged; the
existing `Throw ⇒ EvalError::Raised` *is* the defunctionalized `reflect`. What is new is
only the abort target.

### The boundary is a frame

047 §4: *"`reset` is a frame (a boundary marker on the stack)"*, and §3: `Throw` is
*"a cheap abort, not a general capture"*. That is exactly what fits here.

`reify` cannot be an ordinary builtin. Measured: `BuiltinFn` is
`Fn(&mut Interpreter, &[Value]) -> Result<Value, EvalError>` (`eval/mod.rs:91`) — it
returns a `Value` and has no way to enter a closure. Re-entering `run()` from a builtin
is both what 047 §4 rejects ("it reburies continuations in the host stack, defeating the
stack's purpose") and unsafe in this tree: `deliver` (`eval/eval.rs:3350`) pops until the
activation stack is *empty*, with no per-`run` base, so a nested `run()` unwinds into its
caller's frames. `guardians_check` survives its `interp.call` only because every test
enters it at top level with an empty stack.

The mechanism, then:

- a new `AwaitState::ReifyBoundary` (`eval/frame.rs`), sibling to `OperationResult`;
- a dispatch arm for the registered `reify` symbol which — instead of the TCO frame
  replacement `enter_operation` performs (`eval/eval.rs:3148`) — sets the current frame's
  `awaiting` to `ReifyBoundary` and pushes the closure body above it;
- normal delivery into `ReifyBoundary` wraps the value as `ok(v)` and cascades, exactly
  as `OperationResult` cascades;
- `run()` intercepts `Err(EvalError::Raised { payload })`, unwinds to the nearest
  `ReifyBoundary` **at or above this `run`'s stack base**, and delivers `err(payload)`.

Keyed by **`Symbol`**, never by name — WI-897's rule: an operation's meaning is its
symbol. DELIVERED that way: `ErrorLayerSymbols` (`eval/mod.rs`) resolves `Error.reify`
and the two `Result` constructors once at `Interpreter::with_config`, beside
`ReflectSymbols`, so the per-dispatch test is one `Option<Symbol>` comparison.

**Three things the sketch above did not say, each settled by writing it.**

1. *The thunk is entered through a shared helper.* `reify`'s argument is a callable
   VALUE with no name bound to it, where an ordinary HOF's callback is a LOCAL that
   `dispatch_call_with_requirements_inner` looks up. That function's two callable arms
   moved out to `apply_callable_value`, which both now call — so the `OpRef` half (eta
   spread, captured dictionary, op-scoped slots) is not written twice. Its third arm is
   LOUD: at the HOF call site a non-callable is unreachable (the local is pre-filtered),
   but a `reify` ARGUMENT could be one.
2. *A placeholder frame, because entering is REPLACING.* `enter_closure` and
   `enter_operation` both TCO-rewrite the top frame, so the boundary pushes an
   `Expr::Bottom` frame for them to rewrite. `Bottom` and not something inert: it must
   never reduce, and if a future callable arm ever entered by PUSHING instead, this
   surfaces as a loud `Internal` rather than as a boundary that answers its own
   placeholder.
3. *The floor is pinned by a unit test and nothing else.* No anthill spelling reaches a
   nested `run()` with a boundary beneath it — the operation that re-enters `run()` on a
   live stack is reached from the RESOLVER, and a rule body's raise appears in no
   caller's effect row, so a typed `reify` cannot wrap it. `frame.rs`'s
   `the_boundary_scan_stops_at_the_floor` drives `topmost_reify_boundary` directly; delete
   `floor` and nothing else in the tree goes red. (The RAISE scan is what this proposal
   bounds. The SUCCESS path still rides `deliver`'s pre-existing unbounded pop, which is
   the wider defect noted under Open questions.)

Only `Raised` is caught. `Internal`, `StepsExhausted`, `UnhandledEffect`,
`UnsupportedHandlerAction` and the rest propagate unchanged: a reify boundary is a
handler for the `Error` *effect*, not a catch-all for interpreter faults.

`EvalError::Raised` has exactly two producers (`eval/effects.rs:593` from the handler's
`Throw`, `eval/effects.rs:650` the no-handler default) and two consumers
(`anthill-stl/src/runner.rs:121`, which renders it; `kb/simp_rewrite.rs:1563`, which
turns it into a macro rejection). The boundary is the third consumer and the only new one.

### Why this needs no continuation capture — the line separating it from 027.2

047 §5: first-order monads (`Result`, `State`, `Reader`) are *"the degenerate fragment of
reflection — abort/return, no real `shift`. No continuation capture, no prompt. For
`Error`, the monad genuinely is sufficient: try/catch is `Result` short-circuit."*

That is why this proposal does not wait on WI-078's remaining half. WI-078's own
2026-07-03 audit lists what is missing as `snapshot_eval_state` / `resume_with` /
`fail_branch` and the `Choice`/`Suspend` interpretation — **continuation capture** — which
047 assigns to the resumable effects (`Suspension`, WI-069; `Branch`, WI-070; and
027.2, which needs a whole `StepOutcome::Suspend`). `Error` runs the thunk and either
returns or aborts. No snapshot, no `Frame` clone, no activation-stack slice.

This is also why `Error` is 047 §9's step 2 and "the first green slice": it is the only
monad layer that reaches an end-to-end catch without any of that machinery.

## Typing

WI-329 already delivered the static half and needs nothing: a handler is an ordinary
operation sharing a row tail, `(body: () -> X @ {K, ρ}) -> X @ {ρ}`, checked by the
ordinary call-site row machinery with no per-effect rule. `Error.reify`'s signature is
that shape.

One typer defect stands between the declaration and a load, and it is **six lines**.
Measured by instrumenting `validate_callback_effect_row` (`kb/typing.rs:45041`) on
`reify[Rho, X, P](body: () -> X @ {Error[P], Rho})` applied to a body raising
`Error[Boom]`:

```
decl present  disp=Error[T = ?P]     arg T = Var(Global(1381))  chased=TermId(15856)
act  present  disp=Error[T = Boom]   arg T = TermId(15856)
```

`?P` **was already bound to `Boom`** — argument unification via `pair_present_labels`
did its job. The conformance check simply never looked inside the label:
`walk_value_to_resolved` (`kb/typing.rs:52699`) and its `walk_type` core
(`kb/typing.rs:53545`) chase a *top-level* variable chain and do not descend into an
`Fn`'s arguments, so `Error[T = ?P]` was compared structurally, unresolved, against
`Error[T = Boom]` and reported as *"a closed row … does not admit"*.

Fix: deep-resolve both label lists through σ with `walk_type_deep_value`
(`kb/typing.rs:5072`, which already exists and is already used for return types at
`kb/typing.rs:18735`) before comparing.

Measured after the fix:

| probe | before | after |
|---|---|---|
| a namespace-level `reify[Rho, X, P](body: () -> X @ {Error[P], Rho}) -> Result[E = P, T = X]` | refused | loads |
| the same spelled `Error[T = E]` | refused | loads |
| caller destructures `err(e)` → `case boom(w) -> w` | refused | loads |
| **control:** annotating the result with a wrong payload | refused | **still refused** (`expected … E = Other, got … E = Boom`) |
| the `Permission[C]` twin (`wrap[Rho, C](body: () -> Int64 @ {Permission[C], Rho})`) | refused | loads |

The defect was never `Error`-specific: any parameterized effect label whose argument is a
call-site-bound type parameter was affected, and `Permission[C]` is the second witness.
The control is what says the fix is not vacuous.

### A bare label, an `Error[?]` label, and what a typed `reify` may accept

Bare `Error` means `Error[T = ?]` — an unwritten type argument is an undecided one. The
question this proposal has to answer is not what the spelling means but **whether an
undecided payload may satisfy a `reify` that demands a decided one.** It may not, and the
rest of the type system already says so.

Measured in a VALUE slot, which is the house rule:

| declaration | slot | verdict |
|---|---|---|
| `mk() -> Option` (bare), returning `some("a string")` | `f(o: Option[T = Int64])` | **refused** — `expected Option[T = Int64], got Option[T = ?T]` |
| `mk() -> Option[T = ?]`, returning `some("a string")` | `f(o: Option[T = Int64])` | **refused**, and the declaration itself is refused too |
| `mk() -> Option` (bare) | `f[T](o: Option[T = T])` — a GENERIC slot | loads |

So `unify_types` is **not** in error. Its permissiveness — WI-338 F8's *"a bare sort vs
its instantiation"* pairing — is inference, and the VERDICT belongs to
`validate_arg_against_param`, which is strict: an undecided element type reaches a generic
slot and is refused by a concrete one. Two stages, and the split is correct.

The effect-row check does not follow that rule, and it disagrees with itself:

| declared callback row | body's row | verdict |
|---|---|---|
| `{Error[?], Rho}` | `{Error[Boom]}` | loads — *correct*, the declaration is the permissive side |
| `{Error[Boom], Rho}` | `{Error[?]}` | **loads** — the value-slot twin (W3 above) REFUSES |
| `{Error[Boom], Rho}` | `{Error[Other]}` | refused — so the check is not vacuous |
| `{Error[Boom], Rho}` | `{Error}` (bare) | refused |
| `{Error[P], Rho}` | `{Error}` (bare), caller pins `[P = Boom]` | refused |

Two spellings of one thing, opposite verdicts — and the *permissive* one is the row
check's own disagreement with value position, not the strict one. So "loosen bare to match
`[?]`" would propagate the loose verdict rather than repair the inconsistency.

**What this proposal takes from that.** A body that does not say what it raises cannot be
reified into a typed `Result` soundly: `Error.reify` would hand back `Result[E = T]` with
`T` pinned by the caller's annotation alone, and the runtime would then put whatever was
actually raised into an `err` the caller destructures as `T`. Measured, that pin is a LOUD
demand rather than a silent dangling variable — `expected a type for 'P', got
unconstrained — use `reify[P = …](…)`` — but supplying it is an *assertion*, not a
derivation. So:

- a typed `Error.reify` accepts a body that **declares its payload**, and that is the
  path the driver takes (next section);
- a body raising an undecided payload is honestly reified only into `Result[E = Term, T = X]`
  — the payload as a reflect `Term`. Measured and driven: a `Term`-typed value
  destructures with an ordinary entity pattern (`match t case boom(w) -> w` prints the
  field), so this is usable, not a dead end. Whether to ship that second overload at all
  is deferred until a caller needs it; the 47 bare-`Error` declarations in stdlib and
  examples are all host-raised, and the ones worth catching should be retyped rather than
  reified untyped.

**Not fixed here, and recorded rather than swept:** the `{Error[Boom], Rho}` ← `{Error[?]}`
row admitting an undecided payload where the value-slot twin refuses. It is pre-existing,
it is the opposite polarity from anything this proposal needs, and touching it would move
`Permission` too — proposal 064 / WI-CBRSW makes bare and `[?]` mean OPPOSITE things on
the LACKS side (*"A BARE `-Permission` is the general denial … A VARIABLE argument
(`-Permission[?]`) is NOT that and constrains nothing"*), so any rule about undecided
label arguments has to answer the absent side too. Needs its own owner.

### Retype `KB.loaded` to `effects Error[LoadFailed]`

It raises `load_failed(diagnostics)` and nothing else, so the bare declaration understates
what it knows. Retyping makes the payload *checked* at the reify site rather than asserted
— which matters here specifically because those diagnostics are fed back to a model as
repair feedback (the guardians loop), so a wrong payload type would surface as garbage
prose rather than as a type error. 47 bare-`Error` occurrences exist across stdlib and
examples; only the driver needs retyping now, and the rest keep working unchanged —
nothing reifies them, which is exactly the point: a raiser that wants to be caught says
what it raises.

**BLOCKED IN THE RUST BRIDGE, MEASURED, and left undone.** The row is what
`anthill-stl/build.rs` generates `KB::loaded`'s host signature from, so
`effects Error[LoadFailed]` makes it `Result<Box<dyn KB>, LoadFailed>` — over a type the
generated module does not contain, because `emit_only` is a CLOSURE THE AUTHOR STATES
(its own comment says so, for `LayerSymbol` / `LayerClause`). Naming `LoadFailed` there
gets one step further and hits two codegen defects: the generator emits a second
`use crate::prelude::{List, String}` (duplicate `List` — E0252) and there is no `String`
in the reflect prelude shim (E0432). Both are in the import emitter, both have their own
owner, and neither is what this proposal is about — so the retype is backed out with a
note at the declaration.

The consequence is that `KB.loaded` is **not yet reifiable**, and that is the typed
`reify` being CORRECT rather than a gap: measured,
`Error.reify(lambda () -> KB.loaded(cons(src, nil())))` is refused —
*"the lambda argument declares `Error`, which the closed row does not admit"* — exactly
the bare-label rule the section above argues for. A body that does not say what it raises
cannot be reified into a typed `Result`. Retyping the driver is what unblocks the
guardians `LoadChecker.check` rewrite; it is now a codegen ticket, not an effects one.

## Build path — where each step stands

1-5 ALL DELIVERED. Step 4's second half — the `KB.loaded` retype — cost one real codegen
defect (per-module import dedup) and two one-line settings; see above. Acceptance is
`wi_9wvt7_error_reify_test` (12 rows, including the `KB.loaded` driver) plus two
`frame.rs` unit tests and two `codegen_test` rows. Measured under a back-out of the
dispatch arm: 8 failed / 2 passed, the two being the typer control and the
escapes-outside-a-boundary control.

1. **Typer, two independent fixes.** (a) Deep-resolve effect-row labels in
   `validate_callback_effect_row` — six lines; tests are the `Permission[C]` twin and the
   wrong-payload control. (b) Skip a spec type parameter the called operation neither
   mentions nor receives, in the WI-325 abstract-param loop; tests are the two controls
   named above, each of which was measured going red under a weaker predicate. A
   bare-`Error` body stays *correctly* refused by a typed `reify` — no bare-label change.
   Both measured at 6650 passed / 0 failed.
2. **`Result`** — `stdlib/anthill/prelude/result.anthill`: the sort, `ok` / `err`,
   `map` / `flatMap`, `reflect`. Measure the `Monad` provision; do not fake it.
3. **The boundary** — `AwaitState::ReifyBoundary`, the dispatch arm, the `run()` catch,
   the per-`run` stack base. This is the risky increment and goes before the surface.
4. **`Error.reify`** — the declaration in `effects.anthill`, registered by symbol, and
   `KB.loaded` retyped to `effects Error[LoadFailed]`.
5. **Acceptance, driven.** Call an operation declaring `effects Error[…]` inside the
   boundary and assert the **recovered payload as a value**. Three controls, each stating
   at its site which tests fail when the change is backed out and which pass either way:
   (a) the same call outside the boundary still raises; (b) an enclosing operation
   declaring a row *without* `Error` loads, and backing the boundary out makes it
   "undeclared effect: Error"; (c) a body that does not raise returns the `ok` arm.

**Landmine for step 5, and it is why the acceptance must DRIVE.** `match` arms are not
checked against the scrutinee's sort. Measured, with no `reify` involved: `operation
f(b: Boom) -> Int64 = match b case other(n) -> n`, where `other` belongs to an unrelated
sort, **loads clean**; so does a bogus constructor pattern against a `Term`-typed
scrutinee (`case no_such_ctor_anywhere(x)`). So an acceptance that destructures the
recovered payload proves nothing at load time — it must run and assert the value. (The
payload TYPE is still checked, at the boundary that does check it: the wrong-annotation
control above.)

## Open questions

- **Guarded labels.** Measured: an operation declaring
  `effects { Error[Boom] :- eq(b, 0) }` (proposal 048 conditional effects) does **not**
  conform to an unguarded `{Error[Boom], Rho}` callback row; the unguarded twin loads.
  This removes `Int64.div` (`Error[DivisionByZero] :- eq(b, 0)`) and `Stream.head`
  (`Error[EmptyStream] :- isEmpty(s)`) as demos — the two most natural ones. Out of scope
  here; needs an owner.
- **Nested native re-entry.** The `run()` catch must be bounded by a per-`run` stack base,
  or a raise inside a builtin's `interp.call` could unwind frames the host stack still
  owns. The underlying defect — `deliver` popping past the base — is pre-existing and
  wider than this proposal; bounding the *scan* is what this one owes.
- **THE BOUNDARY CATCHES ON THE ERROR'S CARRIER, NOT ON THE PAYLOAD'S SORT — so
  `Result[E = T1]`'s `err` arm can hold a value of an unrelated sort.** This is the one
  known soundness gap in the layer, and it has two reachable causes.

  *`Rho` breaks its own promise.* A body declaring
  `{Error[Boom], Error[DivisionByZero]}` reified at `T1 = Boom` leaves the second label
  in the CALLER's row — the typer REQUIRES the caller to declare it as escaping — yet the
  boundary catches it too and delivers `err(division_by_zero(op: "Int64.div"))` inside a
  `Result[E = Boom]`. The type system is distinguishing two labels of one KIND that the
  runtime's single `Error` channel does not.

  *A host raise rides a row it does not appear in.* `raise_match_failed` /
  `raise_division_by_zero` raise `Error[MatchFailed]` / `Error[DivisionByZero]` payloads
  through the channel an operation declared as `Error[Boom]`. Two ways in, both measured
  and both loading clean: a GUARD-exhaustible match (`match n case k | k > 0 -> k`, whose
  pattern coverage is total and whose guard is not), and a non-exhaustive match on a
  NON-ENUM sort — exhaustiveness is checked only for `SortKind::Enum`, so
  `sort Colour { entity red  entity blue }` with `match c case red -> 1` loads with NO
  effect row at all. (An earlier draft of this section claimed "a non-exhaustive match is
  a LOAD error"; that is true for an `enum` and false for a `sort`, and the correction is
  what turns this from a curiosity into a second door.) The caller's
  `case err(e) -> match e case boom(w) -> w` then fails at RUN time, raising a second
  `match_failed` carrying the first.

  The boundary is not what is wrong — `Error[MatchFailed]` IS an `Error`, so catching it
  is right. Narrowing it needs `T1` AT RUN TIME (the dispatch arm drops `type_args` and
  `AwaitState::ReifyBoundary` is a unit variant) plus a rule for a payload that matches no
  boundary; both are design, not a line, and the second cause is upstream of `reify`
  entirely. Needs its own owner.

- **`Error.reify` works only from an OPERATION BODY.** MEASURED: `rule viaop(?r) :-
  caught(?r)` — the reify inside a bodied op — answers `?r = err(error: boom(why:
  "negative"))`, while `rule direct(?r) :- Error.reify(lambda () -> mayFail(0 - 1), ?r)`
  answers NO SOLUTIONS. The interception is on `dispatch_resolved_operation` /
  `dispatch_call_with_requirements_inner`, the in-body face; the host-entry face
  (`invoke_op_with_requirements`, which `bridge_op_to_eval` calls) has no boundary and
  falls to `unrunnable_target_error`, which the bridge turns into no-solutions.
  THE CONTROL SAYS THIS IS NOT NEW: an ordinary `operation nobody(n: Int64) -> Int64`
  with no implementation, called from a rule body, answers NO SOLUTIONS too. `reify`
  joins that class — WI-20260909-M8QWJ, "an operation with no implementation is callable
  at load" — rather than opening a new one. It is not a two-line addition either: that
  entry pushes onto a LIVE activation stack and `deliver` has no per-run floor, so a
  boundary installed there would be answered by a cascade that outruns it. The fix is the
  wider one this proposal already names.

- **The boundary is keyed to one name, so a USER-DECLARED effect layer's `reify` loads
  clean and traps at run time.** Measured with the sibling typing test's own fixture
  shape: `sort Err2 { operation reify[Rho, X, T1](body: () -> X @ {Err2[T1], Rho}) ->
  MyResult[E = T1, T = X] effects {Rho} }` loads — that is exactly what this ticket's two
  typer fixes bought — and running it dies "operation has no body: Err2.reify". Same
  class as the point above (M8QWJ), and the same question 027.2 will ask when
  `Branch.reify` wants a second hard-coded field: whether the boundary should be selected
  by a DECLARATION (a `provides`/fact naming the operation as an effect's reify) rather
  than by a symbol the interpreter hard-codes.

- **`Result` has no host `TypeMapping` in any realization profile.** `Option` has one in
  every profile (`rust_std.anthill:39`, `cpp_std.anthill:46-48`); grep finds none naming
  `Result` (the `ResultWrap` / `ResultTyped` hits are effect-mapping receivers, a
  different concept). Codegen is out of scope here by design, but per WI-891 the cpp-gen
  degrade path FAILS the build via `static_assert` rather than degrading quietly, so the
  first operation returning a `Result` breaks generated C++ with no diagnostic naming the
  missing mapping. `Result`'s two arms map onto `tl::expected` / `std::variant` (cpp) and
  `Result` (rust) — the shape `ResultWrap` already assumes.

- **Which delimiter wins, a registered `Error` handler or the innermost `reify`?** The
  handler is consulted FIRST (`raise_error` checks `effect_handlers` before defaulting),
  so it is dynamically outermost. With the stock `default_error_handler` this is
  invisible — it returns `Throw(payload)`, which maps back to `Raised` and reaches the
  boundary unchanged — but a handler installed through the public `register_effect_handler`
  changes the answer three ways: `Pure(v)` yields `Internal("Error handler resumed a
  raise … — Error is non-resumable")`, which the boundary passes straight through, so a
  declared discharge is void; `Fail`/`Choice`/`Suspend` escape as
  `UnsupportedHandlerAction`; and a handler that Throws a REWRITTEN payload makes the
  boundary deliver the handler's value rather than the raised one. Nothing states which
  should win, and `interp_for` registers no handlers, so the whole test suite runs in the
  one configuration where the question cannot arise.
