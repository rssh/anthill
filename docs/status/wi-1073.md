# WI-1073: implemented surface-language proposal audit

This inventory comes before the reference-spec amendments.  It answers two
different questions which proposal status headings often conflate:

1. did a proposal describe a source-language surface; and
2. did that surface reach the parser **and** an end-to-end consumer?

`grammar.js` is evidence that text is accepted, not by itself evidence that the
feature works.  A row is **implemented** only when the corresponding converter,
loader/typer/evaluator path exists and the tracker records the implementing work
as delivered (or the feature predates the tracker and has a landed implementation
commit).  **Partial** means precisely the delivered subset stated in the row;
parse-and-refuse forms remain unimplemented.  Proposal headings are recorded as
design history, not used as the verdict.

## Counts and method

- 66 numbered top-level proposal files were inspected (`001` through `060`,
  including decimal children and gaps in the numbering).
- 40 are surface candidates: they introduce, change, remove, or assign new
  meaning to a production, keyword, clause, declaration form, or existing term
  spelling.
- Of those 40, 25 have an implemented surface, 9 are partial, 5 are
  unimplemented, and 1 was merged into another proposal.
- The remaining 26 are representation, runtime, backend, CLI, library, or
  semantic-design proposals with no independent source-language surface.  They
  are listed after the table so exclusion is explicit rather than accidental.
- For each implemented/partial row, the check was: tracker state ->
  `tree-sitter-anthill/grammar.js` -> Rust conversion/load/typing/eval consumer ->
  `docs/kernel-language.md`.  `git log -- tree-sitter-anthill/grammar.js` was used
  only to recover proposal/WI provenance for productions whose proposal status
  text is stale.

## Gaps to close in this change

The twelve gap labels above are the writable output of the inventory.  WI-1073
owns all twelve; none is deferred to an unnumbered future task:

1. G1 — sort type-parameter binder spellings.
2. G2 — operation/const bodies and expression grammar.
3. G3 — quantified constraints, including loud unsupported boundaries.
4. G4 — proof, tactic, `using`, structured-proof, in-body-proof, and provides grammar.
5. G5 — symmetric/multi-head rule grammar.
6. G6 — cut.
7. G7 — current effect-row algebra and guarded effects.
8. G8 — `result` in effect rows.
9. G9 — operation type parameters in collected grammar.
10. G10 — named requirement slots.
11. G11 — delivered `require[X]` clause interpretation; retain the compatibility
    boundary between implemented directional typed patterns and WI-742's open
    plain-relational extension.
12. G12 — `enum`, the grammar-origin construct with no proposal owner.

The pre-existing `Description`/`DescriptionInfo` contradiction named when
WI-1073 was filed is no longer present at this revision: WI-1072 updated §4.1 to
`anthill.reflect.DescriptionInfo(target, content, index)`.  It is therefore not
silently carried as an open wrongness in this audit.

The collected grammar's stale head-tail collection literal, one-way rule,
body-less operation entry, and two-form effect productions were contradictions,
not merely omissions; they were corrected in place. The obsolete claim that
`const` was the only non-kernel declaration and the proof-obligation link to
constraint enforcement were corrected too. A further implementation
contradiction surfaced during review: ordinary denial constraints are stored
inert even though the old §§6.2 and 8.4 prose claimed enforcement. Both sections
now state that boundary and name WI-882, while quantified guards remain
documented as the working subset.

No proposal text was removed. Each proposal behind an incorporated surface now
links to the canonical section, and each amended/added canonical section links
back to its design record. Proposal 060 is named as a proposal throughout so it
cannot be mistaken for the unrelated work item WI-060.
