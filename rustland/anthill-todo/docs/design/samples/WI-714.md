WHERE/JOIN DESIGN (converged in a design session; implement next). FRAMING: a Relation is a QUERY (intensional, IQueryable), NOT a collection of rows — running it yields rows (extensional); the algebra composes queries->queries and rows appear only on consumption (head/toList). This is LINQ's IQueryable pattern: a query composed with lambdas, translated to a backend query, materialized only on enumerate.

MECHANISM for where(r, c -> eq(c.x,1)) -> guarded(r.query, goal):
(1) CONDITION = a lambda over a row. The lambda's SOLE job is the BINDER: it makes columns TYPED FIELD ACCESS (c.x resolved against the row schema, WI-638), never free logic vars; it is NEVER applied. REJECT the bare-logic-var / Prolog form eq(?x,1): binding ?x to r's column would be a cross-scope SHORT-NAME comparison (var name vs column name across scopes) = exactly what WI-672 eliminated -> unsound. The binder is load-bearing precisely because it converts a column reference from a name-match into a positional/typed access.
(2) COMPILE-TIME: parse the lambda's expression tree -> build a carrier-neutral QUERY-TERM RECIPE (a constructor, or equivalently a quoted query-term with column HOLES), parameterized over the columns. tree->query mapping (= LINQ tree->SQL; target = the LogicalQuery ADT 026.1 already in kb/execute.rs): atomic predicate eq/lt/le/ge/... -> goal atom; &&/||/! -> conjunction/disjunction/negation; c.x -> the column variable (by schema POSITION, not name); literal -> term constant. where -> guarded(r.query, goal); join -> conjunction (merge both rows' columns). PARTIAL: only the goal-expressible Bool subset; anything else (an if, a non-predicate call) is a compile error — the analog of LINQ's 'cannot translate to SQL'.
(3) RUNTIME: 'extract the query term' = instantiate the recipe with the relation's REAL column VarIds (fill the holes). The columns are the SEAM: holes at compile-time, filled at runtime. This is what makes it CODEGEN-SAFE — the recipe is plain code/data in generated Rust/C++, extraction is a plain call, NO lambda reflected on at runtime. PHASE RULE (established): the tree->query translation runs wherever the lambda-tree survives to runtime (interpreter closure.body, C# Expression<>, Scala Expr — LINQ-style); it is FORCED to anthill-compile-time only for a host that drops the tree (plain Rust Fn). anthill targets codegen -> compile-time.
(4) TERM = carrier-neutral representation (a Value spine: Value::Entity LogicalQuery constructors, VarId columns, Value::Term/Node leaves) — NOT a hash-consed TermId (WI-348 boundary). Same representation build_logical_query_value + rename_query_vars already use for negate/union.
(5) negate/union are the DEGENERATE case (no lambda -> no recipe; build the query term directly at runtime from operand query VALUES; DELIVERED). where/join ADD the compile-time recipe because they carry a lambda.

IMPLEMENTATION LOCUS (confirm at start of next session): RECOMMEND a COMPILE-TIME transform in the TYPER (Rust), reading the lambda's already-typed NodeOccurrence (c.x resolved against schema) and building the carrier-neutral LogicalQuery Value — uniform with negate/union (Rust builtins). The WI-722 anthill macro is the ALTERNATIVE user-EXTENSIBLE route (relational algebra authored in anthill via reflect) — it carries the alignment + new occurrence-build-builtin cost flagged in the prior WI-714 note and is NOT needed for BUILT-IN where/join. Column alignment is POSITIONAL (schema position -> the relation value's column VarId), never by name.

SEQUENCE: where->guarded (single row) FIRST; then join->conjunction (two row binders, merge column sets). project/fix stay separate (project = distribute-dot r.(f1,f2) -> projected, no lambda; fix = guarded+project sugar by named key).
